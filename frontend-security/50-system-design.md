# 前端安全系统设计题

> 回答结构：先澄清需求和约束 → 识别资产和威胁（信任边界）→ 给出分层的防御方案 → 说明监控和应急 → 讨论取舍和演进。

### S1. 设计集团级的统一登录（SSO）系统

- **难度**: 高级
- **标签**: SSO, OIDC, 认证

**澄清问题（面试时先问）**

- 有多少个应用？是否跨不同的注册域名？有没有移动端 App 和第三方应用？
- 需要支持哪些登录方式？（密码、短信、扫码、Passkeys、企业身份源）
- 对单点登出的要求？
- 有没有合规要求（等保、个人信息保护）？

**参考方案**

```text
              ┌───────────────────────────────┐
              │ 认证中心 sso.example.com       │
              │ - 登录页（多种方式 + MFA）     │
              │ - OIDC Provider（授权、令牌）  │
              │ - 风控（设备、IP、行为）       │
              │ - 会话管理（列表、撤销）       │
              └──────┬─────────────┬──────────┘
         授权码 + PKCE│             │后端通道登出
       ┌─────────────▼──┐   ┌──────▼─────────┐
       │ 应用 A 的 BFF  │   │ 应用 B 的 BFF  │
       │ 换取令牌       │   │                │
       │ 建立自己的会话 │   │                │
       └──────┬─────────┘   └──────┬─────────┘
              │HttpOnly Cookie      │
          浏览器（a.com）       浏览器（b.cn）
```

**关键设计**

- **协议**：OIDC 授权码 + PKCE；所有客户端注册精确的 `redirect_uri`
- **会话分层**：认证中心的会话（决定是否需要重新登录）+ 每个应用自己的会话（HttpOnly、SameSite=Lax）
- **令牌不进浏览器**：应用通过 BFF 持有令牌
- **登录方式**：Passkeys 优先、密码 + MFA、扫码登录（App 已登录时确认）；按风险要求升级认证
- **单点登出**：后端通道登出通知所有应用销毁会话；用户可以在安全中心查看和撤销设备
- **防护**：登录接口限流、撞库检测、验证码按风险出现；登录页严格的 CSP、`frame-ancestors 'none'`
- **审计**：登录、授权、令牌刷新、登出的审计日志

**关键指标**

- 登录成功率、登录耗时、MFA 通过率、撞库拦截量、异常登录告警数

**口述模板（2–3 分钟）**

我会基于 OIDC 设计一个认证中心，所有应用使用授权码加 PKCE 接入，`redirect_uri` 精确注册。

会话分两层：认证中心维护自己的会话，决定用户是否需要重新登录；每个应用通过 BFF 用授权码换取令牌，然后建立自己的 HttpOnly Cookie 会话。这样令牌不进入浏览器，应用之间也不共享 Cookie，可以跨不同的注册域名工作，一个应用被攻破也不会直接影响其他应用。

登录方式上优先推广 Passkeys，同时支持密码加 MFA 和扫码登录，按风险（新设备、异地）要求升级认证。登出通过后端通道通知所有应用销毁会话，用户可以在安全中心管理设备。

防护上，登录接口做限流和撞库检测，验证码只在高风险时出现，登录页设置严格的 CSP 并禁止被嵌入。最后记录完整的审计日志，监控登录成功率和异常登录。

**扩展追问**

- 第三方应用接入？→ 开放平台模式，见 S7。
- 认证中心挂了怎么办？→ 认证中心多活部署；已登录用户使用应用自己的会话，短时间内不受影响。

### S2. 设计 CSP 与前端安全监控平台

- **难度**: 高级
- **标签**: CSP, 监控

**澄清问题（面试时先问）**

- 多少个应用和域名？报告量级？
- 目标是推动 CSP 落地，还是同时监控其他安全事件（脚本变化、页面篡改）？
- 是否需要与告警和工单系统集成？

**参考方案**

```text
浏览器 ──CSP / TT 报告 (Reporting API)──┐
SDK ──加载的脚本清单、DOM 变化──────────┤
爬虫 ──定期扫描页面和响应头────────────┤
                                       ▼
                         ┌─────────────────────────┐
                         │ 接收层（限流、过滤）    │
                         └────────────┬────────────┘
                                      ▼
                         ┌─────────────────────────┐
                         │ 处理：降噪、归一化、聚合 │
                         │ - 过滤扩展 / 噪音       │
                         │ - 按应用 / 指令 / 来源聚合│
                         └────────────┬────────────┘
                                      ▼
                  ┌───────────────┬───────────────┬──────────────┐
                  │ 看板（覆盖率） │ 告警（突增）  │ 策略管理      │
                  └───────────────┴───────────────┴──────────────┘
```

**关键设计**

- **接收**：独立域名，限流（报告可能被刷），校验报告格式
- **降噪**：过滤浏览器扩展（`chrome-extension:` 等）、已知的无害来源；按 `(应用, 指令, 阻止的来源, 源文件)` 聚合
- **策略管理**：每个应用的 CSP 以配置形式管理，变更审批，先 Report-Only 再强制；可以按流量比例灰度
- **脚本清单监控**：SDK 上报实际加载的脚本（`PerformanceObserver` 的 resource 条目），与清单对比
- **告警**：报告量突增、出现新的来源、关键页面（支付）的脚本变化
- **看板**：每个应用的 CSP 状态（无 / Report-Only / 强制）、违规趋势

**关键指标**

- 应用 CSP 覆盖率、强制执行比例、违规量、告警的平均处理时间

**口述模板（2–3 分钟）**

平台分为数据收集、处理和应用三层。

数据来源有三种：浏览器通过 Reporting API 发送的 CSP 和 Trusted Types 报告；前端 SDK 上报页面实际加载的脚本；爬虫定期扫描页面和响应头。

接收层部署在独立域名，做限流和格式校验，因为报告接口是公开的，可能被刷。处理层的核心是降噪，过滤浏览器扩展产生的大量噪音，然后按应用、指令、被阻止的来源聚合。

上层提供三个能力：看板展示每个应用的 CSP 状态和违规趋势，帮助推动落地；告警在报告量突增或出现新来源时通知负责人；策略管理把 CSP 以配置形式管理，变更需要审批，支持先 Report-Only 再按流量比例强制执行。支付等关键页面额外监控脚本清单的变化，满足 PCI DSS 的要求。

**扩展追问**

- 报告中有用户的 URL 和数据怎么办？→ 报告中的 URL 去除查询参数，代码片段（`script-sample`）注意脱敏。

### S3. 设计供应链安全治理平台

- **难度**: 高级
- **标签**: 供应链

**澄清问题（面试时先问）**

- 多少个仓库？使用哪些包管理器？有没有私有包？
- 现在有没有私有代理仓库？
- 是否发布开源包或内部包？

**参考方案**

```text
开发者 / CI
    │ 安装依赖
    ▼
┌──────────────────────────────┐
│ 私有代理仓库                  │
│ - 缓存公共包                  │
│ - 恶意包拦截（情报 + 扫描）   │
│ - 冷却期（新版本延迟可用）    │
│ - 私有包的命名空间保护        │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐   ┌─────────────────────────┐
│ CI 检查                       │   │ 资产中心                  │
│ - 锁文件、禁止安装脚本        │──►│ - 每个应用的 SBOM        │
│ - SCA 漏洞扫描                │   │ - 依赖 → 应用的反向索引  │
│ - 新增依赖审批                │   │ - 漏洞存量与修复时限      │
│ - 密钥扫描                    │   └─────────────────────────┘
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 发布                          │
│ - 可信发布（OIDC，限制分支与工作流）│
│ - provenance、人工审批        │
└──────────────────────────────┘
```

**关键设计**

- **代理仓库**是统一的控制点：所有安装都经过它，可以拦截恶意包、执行冷却期
- **依赖混淆**：内部包使用公司的 scope 并在公共仓库占位；代理仓库对内部 scope 只从私有源获取
- **SBOM 反向索引**：出现新漏洞时，几分钟内查出受影响的应用
- **CI 隔离**：安装依赖的步骤不能访问发布凭证和生产密钥
- **自动化升级**：Renovate 批量提交修复 PR
- **发布安全**：自己的包使用可信发布，限制分支和工作流，发布需要审批

**关键指标**

- 高危漏洞的平均修复时长、拦截的恶意包数量、冷却期内被撤回的版本数、可信发布的覆盖率

**口述模板（2–3 分钟）**

我会以私有代理仓库作为统一的控制点。所有开发者和 CI 都从代理仓库安装，代理仓库根据威胁情报和扫描结果拦截恶意包，并执行冷却期，新发布的版本延迟几天才能被安装，大多数恶意版本会在这段时间内被发现和撤回。内部包使用公司的 scope，代理仓库只从私有源获取，防止依赖混淆。

CI 中检查锁文件、禁用依赖的安装脚本、做漏洞扫描和密钥扫描，新增依赖需要审批。每次构建生成 SBOM 存入资产中心，建立从依赖到应用的反向索引，出现新漏洞时可以快速定位受影响的应用，再通过 Renovate 批量提交修复。

发布方面，自己的包使用可信发布，并限制可以发布的分支和工作流，安装依赖的步骤与持有凭证的步骤隔离。

**扩展追问**

- 冷却期会延迟安全修复吗？→ 对安全更新设置例外，可以手动放行。

### S4. 设计第三方脚本的管理方案

- **难度**: 高级
- **标签**: 第三方脚本

**澄清问题（面试时先问）**

- 有哪些类型的第三方脚本？（统计、广告、客服、A/B 测试、支付）
- 谁可以添加脚本？（营销团队通过标签管理器？）
- 哪些页面是敏感页面？

**参考方案**

```text
┌────────────────────┐
│ 脚本注册中心        │  用途、负责人、供应商评估、允许的页面、数据范围
└─────────┬──────────┘
          ▼ 配置下发
┌────────────────────┐
│ 统一加载器（带 nonce）│ 按页面和用户同意状态加载
│ - 敏感页面白名单    │
│ - 隔离：iframe/Worker│
└─────────┬──────────┘
          ▼
┌────────────────────┐
│ 运行时监控          │  实际加载的脚本 vs 注册中心；内容哈希变化；外发请求
└────────────────────┘
```

**关键设计**

- **注册中心**：每个脚本必须登记，变更需要审批；定期审查
- **统一加载器**：页面只有加载器带 nonce，第三方脚本由加载器根据配置加载（依靠 `strict-dynamic`）
- **分级**：敏感页面（登录、支付、个人中心）默认不加载任何第三方脚本
- **隔离**：广告和客服放在沙箱 iframe；统计脚本可以放到 Worker
- **隐私**：在用户同意之前不加载
- **自托管**：可行时把第三方脚本自托管 + SRI，避免供应商的 CDN 被攻破
- **监控**：实际加载的脚本与注册中心对比，脚本内容哈希变化告警

**关键指标**

- 已登记脚本覆盖率、敏感页面的第三方脚本数、未登记脚本告警数、第三方脚本对性能的影响

**口述模板（2–3 分钟）**

核心思路是让所有第三方脚本可见、可控、可监控。

首先建立注册中心，每个脚本登记用途、负责人、供应商安全评估、允许加载的页面和可以访问的数据，变更需要审批。

页面上只有统一加载器带 CSP nonce，第三方脚本由加载器根据配置加载，依靠 strict-dynamic 获得信任，这样 CSP 不需要列出所有第三方域名。加载器根据页面类型和用户的隐私同意状态决定加载哪些脚本，登录、支付等敏感页面默认不加载第三方脚本。能隔离的脚本放到沙箱 iframe 或 Worker 中。

运行时监控实际加载的脚本，与注册中心对比，并监控脚本内容的变化，出现未登记的脚本或内容变化时告警。

**扩展追问**

- 第三方脚本被攻破（例如 polyfill.io 事件）怎么快速止损？→ 加载器的配置可以实时下发禁用；CSP 的允许来源可以快速移除；自托管的脚本不受影响。

### S5. 设计 UGC 富文本的内容安全方案

- **难度**: 高级
- **标签**: XSS, 富文本, UGC

**澄清问题（面试时先问）**

- 支持哪些内容？（富文本、Markdown、图片、视频、嵌入的第三方内容）
- 在哪里展示？（Web、App、管理后台、邮件、搜索结果摘要）
- 量级？有没有内容审核？

**参考方案**

```text
编辑器（白名单格式）
    │ 提交
    ▼
服务端
  - 校验长度和结构
  - 清洗（白名单，与渲染端使用同一套规则）
  - 图片转存（去除 EXIF、重新编码、限制格式）
  - 外链检查（恶意 URL 库）
  - 内容审核（机器 + 人工）
    │ 存储（清洗后的内容 + 原始内容用于审计）
    ▼
渲染
  - Web：再次清洗（DOMPurify）+ Trusted Types + 严格 CSP
  - 图片：独立域名（usercontent.example.com）
  - 链接：rel="noopener noreferrer nofollow ugc"，外链跳转确认页
  - 嵌入内容：白名单的平台，沙箱 iframe
  - 邮件 / 摘要：转为纯文本
```

**关键设计**

- **双端清洗**：服务端清洗是主要防线；渲染时再清洗，防止历史数据或其他写入途径绕过
- **结构化存储**（可选）：存储编辑器的 JSON 文档模型（ProseMirror / Lexical），渲染时由代码生成 HTML，从根本上避免 HTML 注入
- **独立域名**：用户上传的文件放在单独的注册域名，即使有问题也无法读取主站的 Cookie
- **SVG**：转为位图，或以 `Content-Disposition: attachment` 提供
- **管理后台**：审核界面同样严格清洗，管理后台使用独立域名和更严格的 CSP

**关键指标**

- 清洗拦截量、XSS 漏洞数、审核时效

**口述模板（2–3 分钟）**

我会从存储格式、清洗、隔离三个方面设计。

最好的方式是存储编辑器的结构化文档模型而不是 HTML，渲染时由代码把节点转换为 DOM，这样从根本上没有 HTML 注入。如果必须存储 HTML，就在服务端用白名单清洗，渲染时再用 DOMPurify 清洗一次，覆盖历史数据和其他写入途径。

渲染端开启严格的 CSP 和 Trusted Types 作为兜底。链接添加 `noopener noreferrer nofollow ugc`，外链经过跳转确认页。用户上传的图片转存、去除元数据，放在独立的注册域名。嵌入的视频等第三方内容只允许白名单平台，并放在沙箱 iframe 中。

还要特别关注管理后台：审核人员查看 UGC 时，管理后台是攻击者最想攻击的目标，所以管理后台要同样清洗，并使用独立域名和更严格的 CSP。

**扩展追问**

- Markdown 怎么处理？→ 渲染器禁用原始 HTML，链接和图片校验协议，渲染结果仍然经过清洗。

### S6. 设计电商支付页面的安全方案

- **难度**: 高级
- **标签**: 支付, PCI DSS

**澄清问题（面试时先问）**

- 卡号是否经过自己的系统？使用支付服务商的托管页面、iframe 还是直接集成？
- 是否需要满足 PCI DSS？
- 支付方式？（银行卡、第三方钱包）

**参考方案**

```text
订单确认页（自己的域名）
  - 只加载必要的脚本（无统计、广告、客服）
  - CSP：script-src nonce + strict-dynamic；frame-src 支付服务商；connect-src 白名单
  - frame-ancestors 'none'
    │ 嵌入
    ▼
支付服务商的 iframe（卡号输入、3DS 验证）
    │ 返回支付令牌
    ▼
自己的服务端
  - 金额、币种以服务端订单为准
  - 幂等键防止重复扣款
  - 支付结果以服务端回调（签名校验）为准
```

**关键设计**

- **减小合规范围**：卡号只在支付服务商的 iframe 中输入，自己的系统不接触卡号
- **父页面安全**：PCI DSS 6.4.3 要求支付页面的所有脚本有清单、授权和完整性保证；11.6.1 要求检测页面和头部的未授权修改
- **变更检测**：监控支付页面加载的脚本、关键 DOM 结构（是否被插入了额外的输入框）、CSP 头
- **业务安全**：金额以服务端为准、幂等键、支付结果以签名的服务端回调为准（前端的跳转结果只用于展示）
- **防点击劫持**：`frame-ancestors 'none'`

**关键指标**

- 支付成功率、脚本变化告警数、重复扣款数

**口述模板（2–3 分钟）**

第一原则是减小合规范围：卡号输入使用支付服务商的 iframe，自己的系统完全不接触卡号。

但父页面仍然很关键，因为父页面的脚本可以在 iframe 上方伪造输入框窃取卡号，这就是 Magecart 攻击。所以支付页面只加载必要的脚本，不加载统计、广告和客服。CSP 使用 nonce 加 strict-dynamic，`frame-src` 只允许支付服务商，`connect-src` 限制数据发送的目标，并禁止页面被嵌入。按照 PCI DSS 4.0 的 6.4.3 和 11.6.1，维护脚本清单并监控页面脚本、DOM 结构和响应头的变化。

业务层面，金额和币种以服务端订单为准，使用幂等键防止重复扣款，支付结果以签名校验后的服务端回调为准，前端跳转的结果只用于展示。

**扩展追问**

- 为什么支付结果不能以前端为准？→ 前端可以被篡改，也可能因为网络问题丢失跳转；服务端回调有签名，可以信任。

### S7. 设计 OAuth 开放平台

- **难度**: 高级
- **标签**: OAuth, 开放平台

**澄清问题（面试时先问）**

- 第三方应用的类型？（Web 服务端应用、单页应用、移动端、机器对机器）
- 开放哪些数据和能力？敏感程度？
- 是否需要审核第三方应用？

**参考方案**

```text
开发者控制台：注册应用、redirect_uri、申请 scope、密钥管理
        │
授权服务器：
  - 授权码 + PKCE（所有客户端强制 PKCE）
  - 同意页面（展示应用信息和权限）
  - 令牌：短期 access token + 轮换的 refresh token
  - 令牌撤销、内省
        │
资源服务器（开放 API）：
  - 校验令牌和 scope
  - 按应用和用户限流
  - 审计
        │
用户安全中心：查看和撤销已授权的应用
```

**关键设计**

- **redirect_uri 精确匹配**，不允许通配符
- **scope 最小化**：细粒度的 scope；敏感 scope 需要平台审核
- **同意页面**：防点击劫持（`frame-ancestors 'none'`）；清晰展示应用名称、开发者、权限；防止应用伪装（审核名称和图标）
- **公共客户端**（单页应用、移动端）：没有密钥，强制 PKCE；推荐它们使用 BFF
- **令牌**：access token 短期；refresh token 轮换 + 重用检测；可以考虑 DPoP 绑定
- **滥用防护**：恶意应用的举报和下架；异常调用检测
- **用户控制**：随时撤销授权

**关键指标**

- 授权转化率、令牌撤销数、恶意应用下架数、API 错误率

**口述模板（2–3 分钟）**

开放平台分为开发者控制台、授权服务器、资源服务器和用户安全中心。

授权流程统一使用授权码加 PKCE，公共客户端（单页应用、移动端）没有密钥，必须使用 PKCE。`redirect_uri` 精确匹配注册的地址，不允许通配符，防止授权码被发送到攻击者的地址。

权限方面，scope 要细粒度，敏感的 scope 需要平台审核。同意页面要防点击劫持，并清晰展示应用信息和权限，同时审核应用名称和图标，防止伪装成官方应用。

令牌方面，access token 短期有效，refresh token 每次使用后轮换并做重用检测。资源服务器校验令牌和 scope，按应用和用户限流并记录审计日志。用户可以在安全中心随时撤销授权。

**扩展追问**

- 第三方应用请求过多的权限怎么办？→ 审核时要求说明用途；支持增量授权，需要时再申请。

### S8. 设计低代码平台的用户脚本沙箱

- **难度**: 高级
- **标签**: 沙箱, 低代码

**澄清问题（面试时先问）**

- 用户脚本需要哪些能力？（读写表单数据、调用接口、操作 UI）
- 脚本的作者是谁？（同一租户内的开发者，还是任意用户？）
- 在前端执行还是服务端执行？对性能有什么要求？

**参考方案**

```text
平台页面（app.example.com）
  │ postMessage（结构化的 RPC）
  ▼
沙箱 iframe（tenant-xxx.sandbox-example.net，独立注册域名）
  sandbox="allow-scripts"（不含 allow-same-origin）
  CSP：connect-src 'none'（不能直接访问网络）
  │
  └─ 用户脚本 → 只能调用平台暴露的 API（通过 RPC）
                     │
平台宿主侧：
  - API 白名单，以当前用户的权限执行
  - 参数校验
  - 调用频率和超时限制
  - 审计
```

**关键设计**

- **隔离**：用户脚本运行在独立注册域名的沙箱 iframe 中，不含 `allow-same-origin`（不透明源），无法访问平台的 Cookie、存储和 DOM
- **能力模型**：沙箱中没有网络访问（CSP），所有能力通过宿主暴露的 RPC API 获得；宿主侧以当前用户的权限检查
- **资源限制**：宿主检测沙箱无响应（心跳），超时后销毁 iframe；更严格时在 iframe 中再用 Worker 或 WASM 引擎（QuickJS）执行，可以中断
- **多租户**：不同租户使用不同的子域名或独立的 iframe
- **服务端脚本**：使用隔离的 V8 isolate 或容器，限制 CPU、内存和网络

**关键指标**

- 沙箱逃逸事件数（目标为 0）、脚本执行超时率、API 拒绝调用数

**口述模板（2–3 分钟）**

首先排除 `eval` 加 Proxy 的方案，它只能防全局变量冲突，不是安全边界。

我会把用户脚本放到独立注册域名的沙箱 iframe 中执行，`sandbox` 只允许脚本，不允许同源，所以它是不透明源，无法访问平台的 Cookie、存储和 DOM。iframe 的 CSP 设置 `connect-src 'none'`，脚本不能直接访问网络。

用户脚本需要的所有能力都通过 postMessage 上的结构化 RPC 向宿主申请，宿主维护 API 白名单，以当前用户的权限执行，并做参数校验、频率限制和审计。

资源方面，宿主通过心跳检测沙箱是否卡死，超时就销毁 iframe；如果需要更细的控制，可以在沙箱内用 WASM 中的 JS 引擎执行，支持中断和内存限制。不同租户使用不同的子域名，互不影响。

**扩展追问**

- 用户脚本需要渲染自定义 UI 怎么办？→ 在沙箱 iframe 内渲染，或者让脚本返回声明式的 UI 描述（JSON），由宿主用受控的组件渲染。
