# 前端安全初级 Q&A

> 目标：建立前端安全的全景认识，掌握 XSS、CSRF、点击劫持、Cookie、认证、输入校验、安全响应头和供应链的基础防御。浏览器层面的机制见[浏览器原理](../browser/10-junior-qa.md)。本专题只讲防御，不提供攻击载荷。

---

## 一、安全全景与经典漏洞

### Q1. 前端安全主要关注哪些问题？

- **难度**: 初级
- **标签**: 全景

**答案**

| 类别 | 典型问题 |
|------|----------|
| 注入 | XSS、原型污染、SSR 状态注入 |
| 请求伪造 | CSRF、开放重定向、SSRF（SSR / BFF 中） |
| 界面 | 点击劫持、钓鱼页面嵌入 |
| 认证与会话 | 令牌泄露、会话固定、弱认证 |
| 数据泄露 | 敏感信息存储在前端、source map、接口返回多余字段、日志 |
| 供应链 | npm 依赖投毒、第三方脚本、CDN 被篡改 |
| 配置 | 缺少安全响应头、CORS 配置错误、调试接口暴露 |
| 访问控制 | **前端隐藏按钮不等于权限控制**，后端必须校验 |

**核心原则**：

- **前端的一切都可以被用户控制**：校验、权限、加密只能作为体验和辅助，最终防线在服务端
- **纵深防御**：多层防护，任何一层失效都不会导致完全失守
- **最小权限**：令牌、Cookie、第三方脚本只给必要的权限

**口述模板（30–60 秒）**

1. 一句话结论：前端安全关注注入、请求伪造、界面劫持、认证、数据泄露、供应链和配置问题。
2. 关键机制：XSS 和 CSRF 是最经典的，供应链是近年最突出的风险。
3. 对比或注意点：前端的一切都可以被用户控制，最终防线在服务端。
4. 可追问时补充：原则是纵深防御和最小权限。

**常见追问**

- OWASP Top 10:2025 中和前端最相关的是哪些？→ A01 访问控制（包括 CSRF、开放重定向、SSRF）、A03 供应链、A05 注入（包括 XSS）、A07 认证。

### Q2. 什么是 XSS？有哪几种类型？

- **难度**: 初级
- **标签**: XSS

**答案**

**XSS（跨站脚本）**：攻击者让自己的脚本在受害者访问的页面中执行，从而以受害者的身份操作（窃取数据、发起请求、修改页面）。

| 类型 | 恶意内容来源 | 是否经过服务端 | 例子 |
|------|--------------|----------------|------|
| **存储型** | 存储在服务端（数据库） | 是 | 评论、昵称中包含恶意脚本，所有访问者受影响 |
| **反射型** | URL 参数，服务端直接输出到页面 | 是 | 搜索页把关键词原样输出 |
| **DOM 型** | URL、`postMessage` 等，前端 JS 直接写入 DOM | 否 | `element.innerHTML = location.hash` |

**危害**：读取页面数据、以用户身份调用接口、修改页面内容（伪造登录框钓鱼）、窃取非 HttpOnly 的 Cookie 和 localStorage 中的令牌。

详见[浏览器原理初级 Q24](../browser/10-junior-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：XSS 是攻击者的脚本在受害者的页面中执行。
2. 关键机制：存储型来自数据库，反射型来自 URL 经服务端输出，DOM 型由前端 JS 直接写入 DOM。
3. 对比或注意点：DOM 型完全在前端发生，服务端的过滤无法防御。
4. 可追问时补充：危害包括窃取数据、以用户身份操作、伪造页面钓鱼。

**常见追问**

- 有了 HttpOnly Cookie，XSS 是不是就没危害了？→ 不是。脚本虽然读不到 Cookie，但可以直接在页面中以用户身份发请求（浏览器自动带上 Cookie）。

### Q3. XSS 的防御原则是什么？

- **难度**: 初级
- **标签**: XSS

**答案**

**核心：不要把不可信的数据当作代码。**

| 层 | 措施 |
|----|------|
| **输出编码**（最重要） | 按**输出的上下文**编码：HTML 内容、HTML 属性、JS、URL、CSS 各有不同的规则 |
| 使用安全的 API | `textContent` 而不是 `innerHTML`；框架默认的插值（自动转义） |
| **富文本** | 必须使用白名单清洗库（DOMPurify），不要自己写正则 |
| URL | 校验协议，只允许 `http:` / `https:`（防止 `javascript:`） |
| **CSP** | 即使出现注入，也限制脚本的执行 |
| Trusted Types | 从 API 层面禁止把字符串直接写入危险的汇点 |
| Cookie | `HttpOnly`，减少损失 |
| 输入校验 | 作为辅助（类型、长度、格式），**不能**替代输出编码 |

**为什么「输入过滤」不够**：同一份数据可能输出到不同的上下文；过滤规则容易被绕过；会破坏合法的数据（例如用户名中的 `<`）。

**口述模板（30–60 秒）**

1. 一句话结论：XSS 防御的核心是按输出上下文编码，不把数据当作代码。
2. 关键机制：使用框架的默认转义和 textContent，富文本用 DOMPurify 清洗，URL 校验协议。
3. 对比或注意点：输入过滤只是辅助，不能替代输出编码。
4. 可追问时补充：CSP 和 Trusted Types 作为纵深防御，HttpOnly 减少损失。

**常见追问**

- 为什么不同上下文的编码规则不同？→ 例如在 HTML 内容中 `<` 有意义，在 JS 字符串中引号和反斜杠有意义，在 URL 中 `javascript:` 协议有意义；用错编码等于没有编码。

### Q4. 什么是 CSRF？怎么防御？

- **难度**: 初级
- **标签**: CSRF

**答案**

**CSRF（跨站请求伪造）**：用户登录了 A 网站，访问攻击者的 B 网站时，B 网站让浏览器向 A 发送请求，**浏览器自动带上 A 的 Cookie**，A 以为是用户本人的操作。

**前提**：

- 使用 Cookie 认证（浏览器自动携带）
- 请求的参数可以被攻击者预测

**防御组合**：

| 措施 | 说明 |
|------|------|
| **SameSite Cookie** | `Lax`（浏览器默认）：跨站的 POST 请求不带 Cookie；`Strict`：任何跨站请求都不带 |
| **CSRF Token** | 服务端生成随机令牌，表单或请求头中携带，服务端校验；攻击者无法读取 |
| **校验 Origin / Referer** | 拒绝来自其他站点的修改请求 |
| 自定义请求头 | 跨站请求无法添加自定义头（会触发 CORS 预检） |
| 关键操作二次确认 | 支付、修改密码要求输入密码或验证码 |
| **不要用 GET 修改数据** | |

详见[浏览器原理初级 Q25](../browser/10-junior-qa.md)、[中级 Q27](../browser/20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：CSRF 利用浏览器自动携带 Cookie，让用户在不知情的情况下发出请求。
2. 关键机制：防御组合包括 SameSite、CSRF Token、校验 Origin。
3. 对比或注意点：SameSite=Lax 是默认值，但不能完全替代 Token（同站的子域名、GET 修改数据等情况）。
4. 可追问时补充：不要用 GET 修改数据，关键操作二次确认。

**常见追问**

- 使用 `Authorization: Bearer` 头的接口还需要防 CSRF 吗？→ 不需要，浏览器不会自动携带这个头；但令牌存储在前端会增加 XSS 的风险。

### Q5. 什么是点击劫持？怎么防御？

- **难度**: 初级
- **标签**: 点击劫持

**答案**

**点击劫持**：攻击者用透明的 iframe 嵌入目标网站，覆盖在诱导性的按钮上，用户以为点击的是攻击者页面的按钮，实际点击的是目标网站的按钮（例如「确认转账」「授权」）。

**防御**：

```http
Content-Security-Policy: frame-ancestors 'self'
X-Frame-Options: DENY
```

- `frame-ancestors`（CSP）：更灵活，可以指定多个允许的来源；**推荐**
- `X-Frame-Options`：兼容旧浏览器，只支持 `DENY` 和 `SAMEORIGIN`
- 两者都设置时，现代浏览器以 `frame-ancestors` 为准
- **必须作为响应头**设置，`<meta>` 中的 `frame-ancestors` 无效

详见[浏览器原理中级 Q29](../browser/20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：点击劫持用透明 iframe 嵌入目标网站，诱导用户点击。
2. 关键机制：通过 CSP frame-ancestors 或 X-Frame-Options 禁止被嵌入。
3. 对比或注意点：frame-ancestors 更灵活，必须通过响应头设置。
4. 可追问时补充：需要被合作方嵌入时，只允许指定的来源。

**常见追问**

- 用 JS 判断 `top !== self` 跳出 iframe 可以吗？→ 不可靠，可以被 iframe 的 `sandbox` 属性禁用脚本或跳转；应该用响应头。

### Q6. Cookie 有哪些安全属性？

- **难度**: 初级
- **标签**: Cookie

**答案**

| 属性 | 作用 |
|------|------|
| `HttpOnly` | JS 无法读取，减少 XSS 窃取 |
| `Secure` | 只在 HTTPS 中发送 |
| `SameSite=Strict / Lax / None` | 控制跨站请求是否携带；`None` 必须同时设置 `Secure` |
| `Domain` | **不设置**时只发送给当前主机（更安全）；设置后包括子域名 |
| `Path` | 路径范围（不是安全边界） |
| `Max-Age` / `Expires` | 过期时间；会话 Cookie 不设置 |
| `__Host-` 前缀 | 要求 `Secure`、`Path=/`、不能设置 `Domain` → 防止子域名覆盖 |
| `__Secure-` 前缀 | 要求 `Secure` |
| `Partitioned` | 第三方 Cookie 按顶级站点分区（CHIPS） |

**推荐的会话 Cookie**：

```http
Set-Cookie: __Host-session=随机值; Path=/; Secure; HttpOnly; SameSite=Lax
```

详见[浏览器原理初级 Q21](../browser/10-junior-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：会话 Cookie 应该设置 HttpOnly、Secure、SameSite。
2. 关键机制：HttpOnly 防止 JS 读取，Secure 只在 HTTPS 发送，SameSite 防 CSRF。
3. 对比或注意点：不设置 Domain 时只发送给当前主机，比设置了 Domain 更安全。
4. 可追问时补充：__Host- 前缀防止子域名覆盖 Cookie。

**常见追问**

- 子域名被攻破会影响主站的 Cookie 吗？→ 子域名可以设置 `Domain=example.com` 的 Cookie 覆盖主站的同名 Cookie（会话固定）；`__Host-` 前缀可以防止。

### Q7. 同源策略限制了什么？CORS 配置有哪些常见错误？

- **难度**: 初级
- **标签**: 同源策略, CORS

**答案**

**同源**：协议、主机、端口都相同。同源策略限制**读取**跨源的数据（脚本读取响应、DOM、存储），但**不限制发送**请求（这正是 CSRF 存在的原因）。

**CORS 常见的危险配置**：

| 错误配置 | 风险 |
|----------|------|
| 把请求的 `Origin` 原样回显到 `Access-Control-Allow-Origin`，并且 `Allow-Credentials: true` | **任何网站**都可以带着用户的 Cookie 读取接口数据 |
| 白名单用前缀或包含匹配（`origin.includes('example.com')`） | `example.com.attacker.net` 可以绕过 |
| 允许 `null` 来源 | 沙箱 iframe、本地文件可以伪造 `null` |
| 信任所有子域名 | 任一子域名的 XSS 都可以读取主站数据 |

**正确做法**：精确匹配的白名单；只有确实需要时才允许凭证；响应中设置 `Vary: Origin`。

详见[浏览器原理初级 Q22](../browser/10-junior-qa.md)、[中级 Q9](../browser/20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：同源策略限制读取跨源数据，但不限制发送请求。
2. 关键机制：CORS 由服务端声明允许哪些来源读取响应。
3. 对比或注意点：最危险的配置是回显 Origin 并允许凭证，等于对所有网站开放。
4. 可追问时补充：白名单要精确匹配，不要允许 null，响应带 Vary: Origin。

**常见追问**

- CORS 能防 CSRF 吗？→ 不能直接防。CORS 控制的是能否读取响应，简单请求（表单 POST）仍然会被发送到服务器。

### Q8. 为什么全站都要使用 HTTPS？

- **难度**: 初级
- **标签**: HTTPS

**答案**

- **防窃听**：公共 Wi-Fi 中，明文的 Cookie、令牌、表单数据可以被截获
- **防篡改**：运营商或中间人可以注入广告或恶意脚本（HTTP 页面中的任何脚本都可能被替换）
- **身份认证**：确认访问的是真实的网站
- **浏览器限制**：很多新的 API（Service Worker、地理位置、剪贴板、WebAuthn、HTTP/2 和 HTTP/3）只在安全上下文中可用；Cookie 的 `Secure`、`__Host-` 依赖 HTTPS

**配套措施**：

- **HSTS**：防止首次访问被降级（见[网络中级 Q23](../network/20-mid-qa.md)）
- 避免**混合内容**：HTTPS 页面加载 HTTP 资源，主动混合内容（脚本、iframe）会被浏览器阻止，被动混合内容（图片）会被自动升级或警告
- `upgrade-insecure-requests`（CSP）：自动把页面中的 HTTP 请求升级为 HTTPS

**口述模板（30–60 秒）**

1. 一句话结论：HTTPS 防止窃听、篡改和冒充。
2. 关键机制：HTTP 页面中的任何脚本都可能被中间人替换。
3. 对比或注意点：很多新的浏览器 API 只在 HTTPS 中可用。
4. 可追问时补充：配合 HSTS 防止降级，避免混合内容。

**常见追问**

- 内网系统需要 HTTPS 吗？→ 需要。内网也可能有被攻破的设备；而且很多浏览器 API 需要安全上下文。

### Q9. 令牌应该存储在哪里？

- **难度**: 初级
- **标签**: 认证, 存储

**答案**

| 存储位置 | XSS | CSRF | 说明 |
|----------|-----|------|------|
| **HttpOnly Cookie** | 无法读取（但可以借用身份发请求） | 需要防御（SameSite + Token） | **推荐**，尤其是长期凭证 |
| 内存（JS 变量） | 可以被读取，但只在当前页面生命周期内 | 不受影响 | 刷新后丢失，配合 HttpOnly 的刷新令牌 |
| localStorage | **可以被读取并长期保存**，窃取后可在任意地方使用 | 不受影响 | 不推荐存储长期令牌 |
| sessionStorage | 同上，标签页关闭后清除 | 不受影响 | 同上 |

**常见的推荐方案**：

- 会话型 Web 应用：HttpOnly + Secure + SameSite 的会话 Cookie
- SPA 调用独立 API：**BFF 模式**（令牌保存在服务端，浏览器只有会话 Cookie），或者访问令牌放内存 + 刷新令牌放 HttpOnly Cookie

**重要认识**：一旦存在 XSS，任何存储方式都无法完全保护用户（攻击者可以直接在页面中操作）；区别在于**令牌能否被带走**并在攻击者的环境中长期使用。

**口述模板（30–60 秒）**

1. 一句话结论：长期凭证推荐放在 HttpOnly Cookie 中，不推荐放在 localStorage。
2. 关键机制：localStorage 中的令牌可以被 XSS 读取并带走长期使用。
3. 对比或注意点：Cookie 需要额外防御 CSRF。
4. 可追问时补充：SPA 推荐 BFF 模式，或者访问令牌放内存、刷新令牌放 HttpOnly Cookie。

**常见追问**

- 存在 XSS 时 HttpOnly 还有意义吗？→ 有，它让攻击只能在用户打开页面期间进行，无法把凭证带走长期使用，缩小了损失。

### Q10. 前端可以存储哪些敏感信息？

- **难度**: 初级
- **标签**: 数据保护

**答案**

**不应该出现在前端代码或构建产物中的**：

- 后端的 API 密钥、数据库密码、第三方服务的私钥（Secret Key）
- 内部服务的地址和调试接口
- 未脱敏的用户隐私数据（身份证号、银行卡号全文）

**可以出现但要注意的**：

- **公开的密钥**（地图 SDK 的 Key、Stripe 的 publishable key）：本来就是公开的，需要在服务商后台**限制域名和权限**
- 前端环境变量：`VITE_`、`NEXT_PUBLIC_` 前缀的变量会被打包到客户端代码中

**常见泄露途径**：

- 把服务端密钥误用前缀暴露
- **source map** 部署到生产环境，暴露源码、注释和内部逻辑
- 代码仓库中提交了 `.env` 文件
- 接口返回了多余的字段
- 日志和错误上报中包含令牌、个人信息

**口述模板（30–60 秒）**

1. 一句话结论：服务端密钥、内部地址、未脱敏的隐私数据不能出现在前端。
2. 关键机制：带公开前缀的环境变量会被打包到客户端代码中。
3. 对比或注意点：公开的密钥要在服务商后台限制域名和权限。
4. 可追问时补充：常见泄露途径有 source map、.env 文件、接口多余字段、日志。

**常见追问**

- 前端代码混淆可以保护密钥吗？→ 不能，混淆只能增加阅读难度，运行时的值一定可以被获取。

## 二、认证基础

### Q11. Session 和 Token 认证有什么区别？

- **难度**: 初级
- **标签**: 认证

**答案**

| 对比项 | Session | Token（如 JWT） |
|--------|---------|-----------------|
| 状态存储 | 服务端（Redis 等） | 令牌本身（自包含） |
| 客户端携带 | Cookie 中的会话 ID | Cookie 或 `Authorization` 头 |
| 吊销 | 删除服务端会话即可 | **困难**（需要黑名单或短有效期） |
| 扩展性 | 需要共享会话存储 | 服务端无状态，验签即可 |
| 跨域 / 多端 | Cookie 跨域受限 | 方便（App、第三方） |
| 大小 | 会话 ID 很小 | 令牌较大，每个请求都携带 |

**选择**：

- 传统 Web 应用：Session 更简单、更容易吊销
- 多端、微服务、第三方：Token
- 常见组合：短期访问令牌（JWT）+ 可吊销的刷新令牌（服务端存储）

**口述模板（30–60 秒）**

1. 一句话结论：Session 在服务端存储状态，Token 把状态编码在签名的令牌中。
2. 关键机制：Session 容易吊销，Token 服务端无状态、容易扩展。
3. 对比或注意点：JWT 的主要问题是难以吊销，需要短有效期。
4. 可追问时补充：常见组合是短期访问令牌加可吊销的刷新令牌。

**常见追问**

- 用户修改密码后怎么让所有 JWT 失效？→ 令牌中包含用户的「令牌版本号」，修改密码时递增，验证时比较；或者维护吊销列表；配合短有效期。

### Q12. JWT 的结构是什么？有哪些安全注意事项？

- **难度**: 初级
- **标签**: JWT

**答案**

**结构**：`Header.Payload.Signature`，各部分 Base64URL 编码。

```text
Header：  {"alg":"HS256","typ":"JWT"}
Payload： {"sub":"123","role":"user","exp":1767225600,"iat":1767222000}
Signature：HMAC-SHA256(header + "." + payload, 密钥)
```

**重要认识**：Payload 只是**编码**，不是加密，任何人都可以读取 → **不要放敏感信息**。

**安全注意事项**：

| 问题 | 措施 |
|------|------|
| `alg: none` | 验证时**指定允许的算法**，不要信任令牌头中的 `alg` |
| 算法混淆（用 RSA 公钥作为 HMAC 密钥伪造） | 同上，固定算法 |
| 弱密钥 | HMAC 密钥足够长且随机（至少 256 位） |
| 不校验过期 | 校验 `exp`、`nbf`，以及 `iss`、`aud` |
| 无法吊销 | 短有效期 + 刷新令牌 |
| 敏感信息 | Payload 中只放必要的标识 |

**口述模板（30–60 秒）**

1. 一句话结论：JWT 由头部、载荷、签名三部分组成，载荷只是编码不是加密。
2. 关键机制：签名保证内容没有被篡改。
3. 对比或注意点：验证时必须固定允许的算法，校验过期时间、签发者和受众。
4. 可追问时补充：JWT 难以吊销，需要短有效期配合刷新令牌。

**常见追问**

- HS256 和 RS256 怎么选？→ HS256 签名和验证使用同一个密钥，适合单一服务；RS256 / ES256 私钥签名、公钥验证，适合多个服务验证同一个签发方的令牌。

### Q13. OAuth 2.0 是什么？授权码模式的流程是什么？

- **难度**: 初级
- **标签**: OAuth

**答案**

**OAuth 2.0**：**授权**协议，让用户授权第三方应用访问自己在某个服务上的资源，而不需要把密码给第三方。

**角色**：资源所有者（用户）、客户端（第三方应用）、授权服务器、资源服务器。

**授权码模式 + PKCE**（推荐用于所有客户端）：

```text
1. 客户端生成随机的 code_verifier，计算 code_challenge = SHA256(code_verifier)
2. 跳转到授权服务器：/authorize?response_type=code&client_id=...&redirect_uri=...
                     &scope=...&state=随机值&code_challenge=...&code_challenge_method=S256
3. 用户登录并同意授权
4. 授权服务器重定向回：redirect_uri?code=授权码&state=随机值
5. 客户端校验 state，然后用 code + code_verifier 换取令牌
6. 授权服务器校验 SHA256(code_verifier) == code_challenge，返回访问令牌
```

- `state`：防止 CSRF（攻击者把自己的授权码注入到用户的会话中）
- **PKCE**：防止授权码被截获后被他人使用

**不再推荐的模式**：隐式模式（令牌直接放在 URL 中）、密码模式（第三方拿到用户的密码）。

**口述模板（30–60 秒）**

1. 一句话结论：OAuth 2.0 是授权协议，让用户授权第三方访问资源而不交出密码。
2. 关键机制：授权码模式中，客户端先拿到授权码，再用授权码换取令牌。
3. 对比或注意点：PKCE 防止授权码被截获后被使用，state 防止 CSRF。
4. 可追问时补充：隐式模式和密码模式已经不推荐。

**常见追问**

- OAuth 和 OIDC 有什么区别？→ OAuth 是授权（能访问什么），OIDC 在 OAuth 之上增加了认证（用户是谁），返回 ID Token。

### Q14. 密码应该怎么处理？前端需要加密密码吗？

- **难度**: 初级
- **标签**: 密码

**答案**

**服务端存储**：

- 使用专门的**慢哈希**算法：**Argon2id**（推荐）、bcrypt、scrypt
- 不要使用 MD5、SHA-256 直接哈希（太快，容易被暴力破解）
- 每个密码使用随机盐（这些算法内置）

**前端传输**：

- **HTTPS 已经保证了传输安全**，前端再用 MD5 / SHA 哈希一次没有实质意义：哈希后的值就是新的「密码」，被截获同样可以登录
- 前端用 RSA 加密在某些场景下有意义（防止日志、中间代理明文记录密码），但不能替代 HTTPS

**前端的职责**：

- 密码强度提示（例如 zxcvbn），不强制复杂规则（NIST 建议更看重长度、检查已泄露的密码）
- `autocomplete="current-password"` / `"new-password"`，支持密码管理器
- 不在日志、错误上报、URL 中出现密码
- 登录失败的提示统一为「账号或密码错误」（防止用户枚举）

**口述模板（30–60 秒）**

1. 一句话结论：服务端用 Argon2id 或 bcrypt 等慢哈希存储密码。
2. 关键机制：慢哈希加随机盐，让暴力破解的成本很高。
3. 对比或注意点：前端再哈希一次没有实质意义，传输安全依赖 HTTPS。
4. 可追问时补充：前端负责强度提示、支持密码管理器、不在日志中出现密码。

**常见追问**

- 为什么不能用 SHA-256 存储密码？→ SHA-256 设计为快速计算，GPU 每秒可以计算数十亿次，弱密码很快就能被破解。

### Q15. 什么是多因素认证？Passkeys 是什么？

- **难度**: 初级
- **标签**: 认证, Passkeys

**答案**

**多因素认证（MFA）**：结合多种类型的因素：

- 知道的（密码）
- 拥有的（手机、安全密钥）
- 固有的（指纹、面部）

| 方式 | 安全性 | 说明 |
|------|--------|------|
| 短信验证码 | 较低 | SIM 卡劫持、可被钓鱼 |
| TOTP（验证器 App） | 中 | 可以被实时钓鱼（攻击者转发验证码） |
| 推送确认 | 中 | MFA 疲劳攻击（反复推送直到用户点同意） |
| **Passkeys / 安全密钥** | **高** | **抗钓鱼** |

**Passkeys**（基于 WebAuthn / FIDO2）：

- 注册时设备生成公私钥对，**私钥保存在设备中**（可以通过云同步），服务端只保存公钥
- 登录时服务端发送挑战，设备在用户验证（指纹、面部、PIN）后用私钥签名
- **抗钓鱼**：密钥对**绑定域名**，钓鱼网站的域名不同，浏览器不会使用该密钥
- 服务端泄露的只是公钥，没有可以被重放的秘密

**口述模板（30–60 秒）**

1. 一句话结论：多因素认证结合多种因素，Passkeys 是基于公钥密码的无密码认证。
2. 关键机制：私钥保存在设备中，登录时对服务端的挑战签名。
3. 对比或注意点：密钥绑定域名，钓鱼网站无法使用，所以能防钓鱼；短信和 TOTP 都可以被实时钓鱼。
4. 可追问时补充：服务端只存公钥，泄露也没有可以重放的秘密。

**常见追问**

- 用户换手机后 Passkey 会丢失吗？→ 同步型 Passkey 通过平台账户（iCloud 钥匙串、Google 密码管理器）同步；也可以注册多个 Passkey，并保留账户恢复流程。

## 三、输入与注入

### Q16. 前端校验和后端校验是什么关系？

- **难度**: 初级
- **标签**: 输入校验

**答案**

| 对比项 | 前端校验 | 后端校验 |
|--------|----------|----------|
| 目的 | **用户体验**（即时反馈） | **安全和数据正确性** |
| 能否绕过 | 可以（直接调用接口、修改 JS） | 不能（如果实现正确） |
| 是否必需 | 推荐 | **必需** |

**实践**：

- 前后端共享校验规则（例如同一个 Zod schema）
- 后端校验**所有**输入：类型、长度、格式、范围、枚举
- **白名单优于黑名单**：明确允许什么，而不是列举禁止什么
- 价格、数量、用户 ID、角色等关键数据**以服务端为准**，不信任客户端传来的值

**口述模板（30–60 秒）**

1. 一句话结论：前端校验为了体验，后端校验为了安全，后端校验必不可少。
2. 关键机制：前端的校验可以被直接调用接口绕过。
3. 对比或注意点：白名单优于黑名单，关键数据以服务端为准。
4. 可追问时补充：可以前后端共享同一套校验规则。

**常见追问**

- 前端把购买数量限制在 1–10，后端还要校验吗？→ 要，攻击者可以直接调用接口传入负数或极大值（负数可能导致退款或负价格）。

### Q17. 什么是 SQL 注入？前端工程师需要了解吗？

- **难度**: 初级
- **标签**: 注入

**答案**

**SQL 注入**：用户输入被拼接到 SQL 语句中，改变了语句的结构。

```ts
// 危险：字符串拼接
db.query(`SELECT * FROM users WHERE name = '${name}'`)

// 安全：参数化查询，输入只作为数据
db.query('SELECT * FROM users WHERE name = $1', [name])
```

**前端工程师需要了解的原因**：

- 全栈和 BFF 开发（Node.js、Next.js 的 Server Actions、Route Handlers）
- **NoSQL 注入**：MongoDB 中把用户输入的对象直接作为查询条件（`{ password: { $ne: null } }`）→ 校验输入的类型必须是字符串
- ORM 的原始查询接口（`$queryRawUnsafe`）同样有风险

**防御**：参数化查询 / ORM、输入类型校验、最小权限的数据库账号。

**口述模板（30–60 秒）**

1. 一句话结论：SQL 注入是用户输入被拼接到 SQL 中，改变了语句的结构。
2. 关键机制：参数化查询让输入只作为数据，不会被当作 SQL 的一部分。
3. 对比或注意点：NoSQL 中直接使用用户传入的对象作为查询条件同样危险。
4. 可追问时补充：全栈开发中必须了解，ORM 的原始查询接口也有风险。

**常见追问**

- ORM 能完全防止注入吗？→ 正常的查询接口可以，但原始 SQL 接口、动态的排序字段名（不能参数化）仍然需要白名单校验。

### Q18. 什么是开放重定向？怎么防御？

- **难度**: 初级
- **标签**: 重定向

**答案**

**开放重定向**：网站根据 URL 参数跳转（例如登录后跳回 `?redirect=...`），没有校验目标地址，攻击者构造 `https://good.com/login?redirect=https://evil.com`，利用可信域名诱导用户进入钓鱼网站。

**更严重的后果**：在 OAuth 流程中，开放重定向可能导致授权码或令牌泄露。

**防御**：

- **只允许站内的相对路径**，并且注意绕过：
  - `//evil.com`（协议相对 URL，会跳到其他域名）
  - `/\evil.com`（部分浏览器把 `\` 当作 `/`）
  - `javascript:` 协议
- 使用 `new URL(target, location.origin)` 解析后比较 `origin`
- 或者使用**白名单**映射（`?redirect=orders` → `/orders`）

**口述模板（30–60 秒）**

1. 一句话结论：开放重定向是网站根据参数跳转但不校验目标，被用于钓鱼。
2. 关键机制：利用可信的域名让用户放松警惕。
3. 对比或注意点：只允许站内路径，注意 // 和反斜杠等绕过方式。
4. 可追问时补充：用 URL 解析后比较 origin，或者使用白名单映射。

**常见追问**

- 为什么用字符串 `startsWith('/')` 判断不够？→ `//evil.com` 也以 `/` 开头，浏览器会把它解析为其他域名。

### Q19. 文件上传有哪些安全风险？

- **难度**: 初级
- **标签**: 上传

**答案**

| 风险 | 措施 |
|------|------|
| 上传可执行的脚本（服务端执行） | 文件存储在对象存储或不执行脚本的目录；不使用用户提供的文件名 |
| **上传 HTML / SVG 导致存储型 XSS** | 用户文件放在**独立的域名**（沙箱域名）；`Content-Disposition: attachment`；SVG 当作图片处理或清洗 |
| 伪造类型（扩展名和内容不一致） | 检查文件的**魔数**（文件头），不信任客户端的 `Content-Type` 和扩展名 |
| 内容嗅探 | `X-Content-Type-Options: nosniff` |
| 超大文件、压缩炸弹 | 限制大小；解压时限制解压后的大小 |
| 路径遍历（文件名包含 `../`） | 服务端生成随机文件名 |
| 恶意文件 | 病毒扫描 |
| 图片中的元数据（位置信息） | 处理时去除 EXIF |

**前端的职责**：类型和大小的预检查（体验）、预览时使用 `URL.createObjectURL`；安全校验在服务端。

**口述模板（30–60 秒）**

1. 一句话结论：文件上传的风险包括执行脚本、存储型 XSS、伪造类型、超大文件和路径遍历。
2. 关键机制：用户文件放在独立的域名，检查文件的魔数，服务端生成文件名。
3. 对比或注意点：SVG 和 HTML 可以包含脚本，不能和主站同域名直接展示。
4. 可追问时补充：设置 nosniff，去除图片元数据。

**常见追问**

- 为什么用户上传的文件要放在独立的域名？→ 即使文件中包含脚本，也运行在沙箱域名的源中，无法读取主站的 Cookie 和数据。

### Q20. 使用 `postMessage` 要注意什么？

- **难度**: 初级
- **标签**: postMessage

**答案**

`postMessage` 用于跨源窗口（iframe、弹窗）之间的通信。

**发送方**：

```ts
// 指定目标的 origin，防止消息被发送到被替换的窗口
iframe.contentWindow?.postMessage(data, 'https://partner.example.com')
// 不要使用 '*' 发送敏感数据
```

**接收方**：

```ts
window.addEventListener('message', (event) => {
  // 必须校验来源
  if (event.origin !== 'https://partner.example.com') return
  // 校验数据结构，不要把数据直接写入 DOM 或 eval
  if (typeof event.data?.type !== 'string') return
  // ...
})
```

**常见错误**：

- 不校验 `event.origin`，任何网站都可以发送消息
- 用 `includes` / `indexOf` 校验 origin（可以被绕过）
- 把消息内容直接写入 `innerHTML` → DOM XSS
- 使用 `'*'` 发送令牌

**口述模板（30–60 秒）**

1. 一句话结论：postMessage 发送时要指定目标 origin，接收时必须校验来源。
2. 关键机制：任何网站都可以向你的窗口发送消息。
3. 对比或注意点：origin 要精确匹配，消息内容要校验结构，不能直接写入 DOM。
4. 可追问时补充：不要使用 '*' 发送敏感数据。

**常见追问**

- `event.source` 有什么用？→ 可以进一步确认消息来自预期的窗口对象（例如特定的 iframe），并用于回复。

## 四、安全响应头

### Q21. 常用的安全响应头有哪些？

- **难度**: 初级
- **标签**: 响应头

**答案**

| 响应头 | 作用 | 推荐值 |
|--------|------|--------|
| `Content-Security-Policy` | 限制资源来源，缓解 XSS、点击劫持 | 见 Q22 |
| `Strict-Transport-Security` | 强制 HTTPS | `max-age=31536000; includeSubDomains` |
| `X-Content-Type-Options` | 禁止内容嗅探 | `nosniff` |
| `X-Frame-Options` | 防点击劫持（旧） | `DENY` 或用 CSP `frame-ancestors` |
| `Referrer-Policy` | 控制 Referer 泄露 | `strict-origin-when-cross-origin`（浏览器默认） |
| `Permissions-Policy` | 禁用不需要的浏览器功能 | `camera=(), microphone=(), geolocation=()` |
| `Cross-Origin-Opener-Policy` | 隔离浏览上下文 | `same-origin` |
| `Cross-Origin-Resource-Policy` | 限制资源被跨源加载 | `same-site` |
| `Cache-Control` | 敏感页面不缓存 | `no-store` |

**已废弃 / 不推荐**：`X-XSS-Protection`（浏览器已移除 XSS 过滤器，设置为 `0` 或不设置）、`Public-Key-Pins`（HPKP，已废弃）。

**口述模板（30–60 秒）**

1. 一句话结论：常用的安全头有 CSP、HSTS、nosniff、Referrer-Policy、Permissions-Policy、COOP。
2. 关键机制：CSP 缓解 XSS，HSTS 强制 HTTPS，nosniff 防止内容嗅探。
3. 对比或注意点：X-XSS-Protection 和 HPKP 已经废弃。
4. 可追问时补充：敏感页面设置 Cache-Control: no-store。

**常见追问**

- 怎么检查网站的安全头配置？→ 使用 Mozilla Observatory、securityheaders.com 等工具扫描，在 CI 中加入检查。

### Q22. CSP 是什么？基本怎么配置？

- **难度**: 初级
- **标签**: CSP

**答案**

**CSP（内容安全策略）**：通过响应头告诉浏览器哪些资源可以加载和执行，**即使页面被注入了脚本，也无法执行**。

**推荐的严格策略**（基于 nonce）：

```http
Content-Security-Policy:
  script-src 'nonce-随机值' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self';
```

```html
<script nonce="随机值" src="/app.js"></script>
```

| 指令 | 作用 |
|------|------|
| `script-src` | 允许的脚本来源；`nonce-xxx` 只允许带有匹配 nonce 的脚本 |
| `'strict-dynamic'` | 被信任的脚本动态加载的脚本也被信任（方便使用加载器） |
| `object-src 'none'` | 禁止插件 |
| `base-uri 'none'` | 防止注入 `<base>` 改变相对路径 |
| `frame-ancestors` | 防点击劫持 |

**要避免的**：`'unsafe-inline'`、`'unsafe-eval'`、过宽的域名白名单（白名单中的 CDN 可能托管了可以被利用的脚本）。

**上线方式**：先使用 `Content-Security-Policy-Report-Only` 收集违规报告，确认没有误伤后再强制执行。

详见[浏览器原理中级 Q28](../browser/20-mid-qa.md)、[中级 Q4–Q6](20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：CSP 告诉浏览器哪些资源可以加载和执行，即使有注入也无法执行。
2. 关键机制：推荐基于 nonce 加 strict-dynamic 的严格策略，加上 object-src 和 base-uri 限制。
3. 对比或注意点：避免 unsafe-inline 和过宽的域名白名单。
4. 可追问时补充：先用 Report-Only 收集报告，再强制执行。

**常见追问**

- nonce 每次请求都要变吗？→ 是的，每个响应生成新的随机值；固定的 nonce 可以被攻击者预测并使用。

### Q23. SRI 是什么？什么时候使用？

- **难度**: 初级
- **标签**: SRI

**答案**

**SRI（子资源完整性）**：给外部资源指定哈希，浏览器下载后校验，不匹配则拒绝执行。

```html
<script
  src="https://cdn.example.com/lib@1.2.3/lib.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"></script>
```

- 防止 CDN 被攻破或被篡改（例如 polyfill.io 事件）
- 跨域资源需要 `crossorigin` 属性，CDN 需要返回 CORS 头
- 构建工具可以自动生成（webpack-subresource-integrity 等）

**局限**：

- 只适用于**固定版本**的资源；动态变化的脚本（例如 `latest` 版本、按浏览器返回不同内容的 polyfill 服务）无法使用
- 第三方的统计、广告脚本通常会更新 → 只能通过 CSP、自托管或供应商管理控制

**口述模板（30–60 秒）**

1. 一句话结论：SRI 给外部资源指定哈希，浏览器校验后才执行。
2. 关键机制：防止 CDN 上的资源被篡改。
3. 对比或注意点：跨域资源需要 crossorigin 属性和 CORS 头。
4. 可追问时补充：只适用于固定版本的资源，动态变化的第三方脚本无法使用。

**常见追问**

- polyfill.io 事件中 SRI 能防护吗？→ 不能直接防护，因为该服务本身按浏览器动态返回不同的内容，无法使用 SRI；正确的做法是自托管 polyfill 或移除依赖。

### Q24. Referrer-Policy 和 Permissions-Policy 有什么用？

- **难度**: 初级
- **标签**: 响应头, 隐私

**答案**

**Referrer-Policy**：控制请求中 `Referer` 头包含多少信息。

- **风险**：URL 中包含敏感信息（重置密码的令牌、会话 ID、搜索词），跳转到第三方网站或加载第三方资源时通过 Referer 泄露
- 浏览器默认 `strict-origin-when-cross-origin`：同源发送完整 URL，跨源只发送源，HTTPS → HTTP 不发送
- 敏感页面可以设置 `no-referrer`
- 根本措施：**不要把敏感信息放在 URL 中**

**Permissions-Policy**：控制页面和 iframe 可以使用哪些浏览器功能。

```http
Permissions-Policy: camera=(), microphone=(), geolocation=(self), payment=(self "https://pay.example.com")
```

- 减少被注入的脚本或第三方 iframe 滥用功能的可能
- iframe 的 `allow` 属性在此基础上进一步限制

**口述模板（30–60 秒）**

1. 一句话结论：Referrer-Policy 控制 Referer 泄露的信息，Permissions-Policy 控制可以使用的浏览器功能。
2. 关键机制：URL 中的敏感信息可能通过 Referer 泄露给第三方。
3. 对比或注意点：浏览器默认跨源只发送源，但根本措施是不把敏感信息放在 URL 中。
4. 可追问时补充：Permissions-Policy 减少注入脚本和第三方 iframe 滥用功能。

**常见追问**

- 重置密码页面要注意什么？→ 令牌在 URL 中，页面上不要加载第三方资源，设置 `Referrer-Policy: no-referrer`，令牌一次性且短期有效。

### Q25. 什么是内容嗅探？`nosniff` 有什么用？

- **难度**: 初级
- **标签**: 响应头

**答案**

**内容嗅探（MIME Sniffing）**：浏览器在 `Content-Type` 缺失或不正确时，根据内容猜测类型。

**风险**：用户上传的「图片」或「文本」文件中包含 HTML 或 JS，浏览器嗅探为 HTML 执行 → XSS；或者把非脚本的响应作为脚本执行。

**`X-Content-Type-Options: nosniff`**：

- 浏览器严格按照 `Content-Type` 处理
- `<script>` 加载的资源如果不是 JS 类型，拒绝执行
- `<link rel="stylesheet">` 加载的资源如果不是 CSS 类型，拒绝应用
- 同时帮助 CORB / ORB 保护跨源的敏感响应

**配套**：服务端为所有响应设置正确的 `Content-Type`（包括 `charset`）。

**口述模板（30–60 秒）**

1. 一句话结论：内容嗅探是浏览器根据内容猜测类型，可能把用户上传的文件当作 HTML 执行。
2. 关键机制：nosniff 让浏览器严格按照 Content-Type 处理。
3. 对比或注意点：脚本和样式的类型不匹配时会被拒绝。
4. 可追问时补充：服务端要为所有响应设置正确的 Content-Type。

**常见追问**

- 所有响应都应该设置 nosniff 吗？→ 是的，几乎没有副作用，可以在网关统一添加。

### Q26. npm 依赖有哪些安全风险？

- **难度**: 初级
- **标签**: 供应链

**答案**

| 风险 | 说明 | 例子 |
|------|------|------|
| **已知漏洞** | 依赖中存在公开的漏洞 | 原型污染、ReDoS |
| **恶意包 / 投毒** | 维护者账号被盗，发布恶意版本 | chalk / debug（2025）、event-stream |
| **蠕虫** | 安装脚本窃取令牌，自动发布更多被感染的包 | Shai-Hulud（2025） |
| **拼写抢注** | 名称相似的恶意包（`reqeusts`） | |
| **依赖混淆** | 公共仓库中发布与内部包同名的高版本包 | |
| **维护者变更** | 包被转让给恶意的维护者 | |
| **安装脚本** | `preinstall` / `postinstall` 在安装时执行任意代码 | 开发者机器和 CI 中的密钥被窃取 |

- 提交锁文件，CI 中使用 `npm ci` / `pnpm install --frozen-lockfile`

- **禁用依赖的安装脚本**（pnpm 10、npm v12 默认不执行；按需允许）
- 新增依赖前评估（维护状态、下载量、维护者）
- 内部包使用作用域（`@company/`）并配置私有仓库

**口述模板（30–60 秒）**

1. 一句话结论：npm 依赖的风险包括已知漏洞、恶意投毒、蠕虫、拼写抢注和依赖混淆。
2. 关键机制：安装脚本会在安装时执行任意代码，是投毒的主要途径。
3. 对比或注意点：锁文件保证安装的版本一致，禁用安装脚本阻断主要攻击路径。
4. 可追问时补充：用 Dependabot 或 Renovate 监控漏洞，新增依赖前要评估。

**常见追问**

- 为什么开发者的电脑也是攻击目标？→ 上面有 npm 令牌、GitHub 令牌、云服务凭证、SSH 密钥，Shai-Hulud 就是窃取这些凭证进行传播。

### Q27. 锁文件有什么作用？

- **难度**: 初级
- **标签**: 供应链

**答案**

**锁文件**（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`）记录每个依赖（包括间接依赖）的**确切版本、下载地址和完整性哈希**。

**安全作用**：

- **版本固定**：`^1.2.0` 的范围内发布的恶意新版本不会被自动安装
- **完整性校验**：下载的包内容与记录的哈希不一致时安装失败（防止仓库或网络被篡改）
- 可审计：依赖变化通过代码审查可见

**实践**：

- 锁文件**提交到仓库**
- CI 中使用 `npm ci` 或 `--frozen-lockfile`（锁文件与 `package.json` 不一致时失败，而不是自动更新）
- 审查锁文件的变化（尤其是下载地址的变化，可能指向恶意的仓库）
- 依赖更新通过 Renovate 等工具集中进行，并设置**冷却期**（新版本发布若干天后再更新，给社区发现恶意版本的时间）

**口述模板（30–60 秒）**

1. 一句话结论：锁文件记录每个依赖的确切版本和完整性哈希。
2. 关键机制：防止范围内的恶意新版本被自动安装，并校验包的内容。
3. 对比或注意点：CI 中必须使用 npm ci 或 frozen-lockfile。
4. 可追问时补充：依赖更新设置冷却期，审查锁文件中下载地址的变化。

**常见追问**

- 为什么要有冷却期？→ 大多数恶意版本在发布后几小时到几天内被发现并下架，延迟几天更新可以避开这个窗口。

### Q28. 构建产物中可能泄露哪些信息？

- **难度**: 初级
- **标签**: 数据保护, 构建

**答案**

| 泄露 | 原因 | 措施 |
|------|------|------|
| 服务端密钥 | 误用了公开前缀的环境变量；直接 import 了服务端配置 | 只给公开变量加前缀；构建后扫描产物（gitleaks 等） |
| 源码 | 生产环境部署了 source map | 不公开部署 source map，只上传到错误监控平台 |
| 内部信息 | 注释、内部 API 地址、调试代码 | 构建时去除注释和调试代码 |
| 未发布的功能 | 功能开关在前端判断，代码已经打包 | 敏感功能按权限动态加载，或在服务端判断 |
| 依赖版本 | 暴露存在漏洞的依赖版本 | 及时升级 |

**source map 的正确做法**：

```text
构建生成 source map（hidden-source-map：不在 JS 中引用）
→ 上传到错误监控平台（Sentry 等）
→ 从部署产物中删除 .map 文件
```

**口述模板（30–60 秒）**

1. 一句话结论：构建产物中可能泄露服务端密钥、源码、内部信息和未发布的功能。
2. 关键机制：公开前缀的环境变量会被打包，source map 会暴露源码。
3. 对比或注意点：source map 只上传到监控平台，不部署到生产环境。
4. 可追问时补充：构建后扫描产物中的密钥。

**常见追问**

- 密钥已经泄露到了公开的代码中，怎么办？→ **立即轮换**密钥（删除代码不够，历史版本和缓存中仍然存在），然后检查访问日志评估影响。

### Q29. 第三方脚本有哪些风险？

- **难度**: 初级
- **标签**: 第三方脚本

**答案**

第三方脚本（统计、广告、客服、A/B 测试、监控）在页面中**拥有与自己代码相同的权限**：

- 读取页面内容（包括表单中的密码、信用卡号）
- 以用户身份发送请求
- 修改页面
- 第三方服务被攻破 → 所有使用它的网站同时受影响（Magecart 攻击窃取支付信息、polyfill.io 事件）

**措施**：

- **最小化**：定期审查，移除不再使用的脚本
- **自托管**并固定版本，配合 SRI
- CSP 限制脚本和数据发送的目标（`connect-src`）
- 敏感页面（登录、支付）**不加载**非必要的第三方脚本
- 隔离：在沙箱 iframe 中运行（Partytown 等方案在 Web Worker 中运行）
- 通过标签管理器添加脚本需要审批流程
- 合同和供应商安全评估

**口述模板（30–60 秒）**

1. 一句话结论：第三方脚本拥有与自己代码相同的权限，可以读取页面中的所有数据。
2. 关键机制：第三方被攻破时，所有使用它的网站同时受影响。
3. 对比或注意点：敏感页面不加载非必要的第三方脚本。
4. 可追问时补充：自托管加 SRI、CSP 限制、沙箱隔离、审批流程。

**常见追问**

- 支付页面对第三方脚本有什么合规要求？→ PCI DSS 4.0 要求支付页面维护脚本清单、说明每个脚本的必要性、保证完整性，并监控页面和响应头的变化。

### Q30. 前端加密、代码混淆有意义吗？

- **难度**: 初级
- **标签**: 加密

**答案**

**核心认识**：前端代码和数据运行在用户的设备上，**用户（或攻击者）拥有完全的控制权**。

| 手段 | 能做到 | 做不到 |
|------|--------|--------|
| 代码混淆 | 增加逆向的时间成本，保护算法细节 | 隐藏密钥、阻止调用接口 |
| 前端加密请求参数 | 增加爬虫和自动化的成本、避免中间代理明文记录 | 替代 HTTPS、防止有决心的攻击者 |
| 前端签名（防篡改） | 增加伪造请求的成本 | 密钥在前端，一定可以被提取 |
| 端到端加密（E2EE） | **有意义**：数据在服务端也无法读取（例如加密笔记、聊天） | 防止客户端本身被攻破 |

**正确的使用场景**：

- 风控和反爬：混淆 + 环境检测，作为成本手段，配合服务端的行为分析
- 端到端加密应用：使用 Web Crypto API，不要自己实现加密算法
- 本地数据保护：敏感数据尽量不存储在前端

**口述模板（30–60 秒）**

1. 一句话结论：前端混淆和加密只能增加成本，不能作为安全边界。
2. 关键机制：代码和密钥在用户设备上，一定可以被提取。
3. 对比或注意点：端到端加密是例外，它保证服务端无法读取数据。
4. 可追问时补充：风控场景中作为成本手段，配合服务端分析；加密使用 Web Crypto API。

**常见追问**

- 为什么不能自己实现加密算法？→ 加密算法的实现非常容易出错（时序泄露、随机数质量、模式选择），应该使用经过审计的标准库（Web Crypto API）。
