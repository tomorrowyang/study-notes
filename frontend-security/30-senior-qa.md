# 前端安全高级 Q&A

> 目标：能建设前端安全体系，在大型项目中落地 CSP 和 Trusted Types，设计认证架构，治理供应链和第三方脚本，处理框架漏洞和安全事件；回答时给出方案、取舍和推进路径。只讲防御。

---

## 一、体系建设

### Q1. 如何从零建设一个团队的前端安全体系？

- **难度**: 高级
- **标签**: 体系建设

**答案**

```text
1. 摸底（风险评估）
   - 资产清单：应用、域名、第三方脚本、依赖、对外接口
   - 现状扫描：安全头、依赖漏洞、密钥泄露、CSP
   - 威胁建模：识别高风险业务（登录、支付、UGC、管理后台）

2. 基线（规范 + 默认安全）
   - 安全编码规范：XSS、URL 校验、postMessage、令牌存储
   - 默认安全的基础设施：脚手架内置安全头、CSP、安全的请求库、清洗组件
   - 统一的认证 SDK、统一的富文本组件

3. 左移（开发流程）
   - CI：ESLint 安全规则、依赖扫描、密钥扫描、安全头检查
   - 依赖治理：锁文件、禁止安装脚本、冷却期、新增依赖审批
   - 高风险需求的安全评审

4. 运行时（监控与防护）
   - CSP 报告、Trusted Types 违规、异常脚本监控
   - 第三方脚本清单与变更监控

5. 响应（应急）
   - 漏洞接收（SRC）、分级、修复时限、复盘
   - 框架漏洞的快速升级流程

6. 度量与运营
   - 指标：高危漏洞数量和修复时长、CSP 覆盖率、依赖漏洞存量
   - 培训、安全周报
```

**推进的关键**：**默认安全**（让正确的做法成为最省事的做法）比规范和培训更有效。

**口述模板（30–60 秒）**

1. 一句话结论：按摸底、基线、左移、运行时监控、应急响应、度量运营六个阶段建设。
2. 关键机制：脚手架和基础组件内置安全能力，CI 中自动检查。
3. 对比或注意点：默认安全比规范和培训更有效。
4. 可追问时补充：用漏洞修复时长、CSP 覆盖率等指标衡量效果。

**常见追问**

- 怎么说服业务团队投入安全工作？→ 用真实的漏洞和事件说明风险；把安全能力内置到基础设施中，降低业务团队的成本；把安全指标纳入质量指标。

### Q2. 怎么在一个大型老项目中落地严格的 CSP？

- **难度**: 高级
- **标签**: CSP, 落地

**答案**

**常见障碍**：

- 大量内联脚本和内联事件处理器（`onclick="..."`）
- `eval`、`new Function`（老的模板引擎、某些库）
- 第三方脚本（统计、广告、客服）动态插入脚本
- 多个团队、多个仓库
- 页面被 CDN 缓存（nonce 难以每次生成）

**推进路径**：

```text
阶段 1：低风险的指令先强制执行
  object-src 'none'; base-uri 'none'; frame-ancestors 'self'
  （几乎没有兼容问题，立即获得收益）

阶段 2：脚本策略 Report-Only
  script-src 'nonce-{random}' 'strict-dynamic' https: 'unsafe-inline'; report-to csp
  → 收集违规，按来源分类（自有代码 / 第三方 / 扩展噪音）

阶段 3：改造
  - 服务端模板 / SSR 框架统一注入 nonce
  - 内联事件处理器改为 addEventListener
  - 替换使用 eval 的库
  - 第三方脚本通过受信任的加载器加载（strict-dynamic 信任加载器加载的脚本）

阶段 4：按页面 / 按流量比例强制执行
  - 先从新页面、低风险页面开始
  - 支付、登录等高风险页面使用更严格的独立策略

阶段 5：Trusted Types（Report-Only → 强制）

阶段 6：持续运营
  - CI 检查：禁止新增内联事件处理器和 eval
  - 监控报告量，异常时告警
```

**CDN 缓存的页面**：边缘函数注入 nonce，或使用基于哈希的策略。

**口述模板（30–60 秒）**

1. 一句话结论：先强制执行没有兼容问题的指令，脚本策略先 Report-Only，改造后按比例强制执行。
2. 关键机制：SSR 框架统一注入 nonce，内联事件改为 addEventListener，替换使用 eval 的库。
3. 对比或注意点：第三方脚本通过受信任的加载器加载，依靠 strict-dynamic 信任。
4. 可追问时补充：CI 中禁止新增内联事件和 eval，防止回退。

**常见追问**

- 第三方要求必须使用 `unsafe-eval` 怎么办？→ 与供应商沟通替代方案；把它隔离到独立的子域名或沙箱 iframe 中，主站保持严格策略。

### Q3. 威胁建模怎么做？举一个前端的例子

- **难度**: 高级
- **标签**: 威胁建模

**答案**

**STRIDE 模型**：

| 威胁 | 含义 | 对应的安全属性 |
|------|------|----------------|
| Spoofing | 冒充 | 认证 |
| Tampering | 篡改 | 完整性 |
| Repudiation | 抵赖 | 审计 |
| Information Disclosure | 信息泄露 | 机密性 |
| Denial of Service | 拒绝服务 | 可用性 |
| Elevation of Privilege | 提权 | 授权 |

**步骤**：画数据流图（标出信任边界）→ 对每个组件和数据流列举 STRIDE 威胁 → 评估风险 → 制定缓解措施 → 验证。

**例子：评论功能（支持富文本和图片）**

| 威胁 | 场景 | 缓解 |
|------|------|------|
| S | 冒充其他用户发评论 | 服务端从会话获取作者，不信任请求中的用户 ID |
| T | 修改别人的评论 | 修改时检查归属 |
| R | 发布违规内容后否认 | 审计日志（时间、IP、设备） |
| I | 存储型 XSS 窃取数据；图片中的 EXIF 泄露位置 | DOMPurify 清洗（存储和渲染时）、CSP、图片处理去除元数据、图片放在独立域名 |
| D | 大量发评论、超大的富文本 | 限流、内容长度限制、清洗库的性能限制 |
| E | 通过评论中的链接诱导管理员点击（CSRF / XSS 攻击管理后台） | 管理后台独立域名、严格 CSP、SameSite |

**口述模板（30–60 秒）**

1. 一句话结论：威胁建模是画出数据流和信任边界，用 STRIDE 逐项列举威胁并制定缓解措施。
2. 关键机制：STRIDE 分别对应认证、完整性、审计、机密性、可用性和授权。
3. 对比或注意点：在设计阶段做，比上线后修复成本低。
4. 可追问时补充：以评论功能为例，重点是存储型 XSS 和攻击管理后台。

**常见追问**

- 什么时候需要做威胁建模？→ 新的高风险功能（认证、支付、UGC、文件处理、开放接口）、架构变化（引入 SSR、BFF、新的第三方集成）时。

## 二、认证架构

### Q4. 设计一个多域名的单点登录（SSO）方案

- **难度**: 高级
- **标签**: SSO, 认证

**答案**

**场景**：`a.com`、`b.com`、`c.example.com` 共享登录。

**方案：基于 OIDC 的中心认证服务**

```text
1. 用户访问 a.com，没有会话 → 重定向到 sso.example.com/authorize（授权码 + PKCE + state + nonce）
2. SSO 检查自己的会话 Cookie（sso.example.com 域名下）
   - 没有 → 显示登录页 → 登录成功后建立 SSO 会话
   - 已有 → 直接跳过登录
3. 重定向回 a.com/callback?code=... → a.com 的后端（BFF）用授权码换取令牌，建立 a.com 自己的会话
4. 用户访问 b.com → 同样的流程，因为 SSO 已有会话，用户无感知
```

**关键设计**：

- 各应用**独立的会话**（各自域名下的 HttpOnly Cookie），不共享 Cookie
- `redirect_uri` **精确匹配**注册的地址（防止授权码泄露到攻击者的地址）
- **单点登出**：OIDC 的前端通道 / 后端通道登出，SSO 通知所有应用销毁会话
- 第三方 Cookie 受限的环境中，不依赖 iframe 检查 SSO 会话（静默认证）→ 使用顶级重定向
- 高风险应用可以要求重新认证（`prompt=login`、`max_age`）或更高的认证级别（MFA）

**口述模板（30–60 秒）**

1. 一句话结论：使用基于 OIDC 的中心认证服务，各应用通过授权码流程获得自己的会话。
2. 关键机制：SSO 服务维护自己的会话，已登录时用户无感知地跳转回应用。
3. 对比或注意点：各应用独立会话，不共享 Cookie；redirect_uri 必须精确匹配。
4. 可追问时补充：第三方 Cookie 受限时不依赖 iframe 静默认证；单点登出通过后端通道通知。

**常见追问**

- 为什么不用共享父域名 Cookie 实现 SSO？→ 只适用于同一父域名的子域名；任一子域名被攻破都会影响全部；跨不同的注册域名无法实现。

### Q5. 怎么在现有系统中落地 Passkeys？

- **难度**: 高级
- **标签**: Passkeys

**答案**

**渐进式落地**：

```text
阶段 1：作为第二因素或可选的登录方式
  - 已登录用户在安全设置中添加 Passkey
  - 登录页支持条件式 UI（自动填充中显示 Passkey）
阶段 2：引导
  - 登录成功后提示「创建 Passkey，下次一键登录」
  - 新用户注册时优先 Passkey
阶段 3：无密码
  - 允许用户删除密码（保留恢复方式）
```

**关键设计**：

| 方面 | 要点 |
|------|------|
| `rpId` | 选择注册域名（`example.com`），让子域名都能使用；**之后很难更改** |
| 多个 Passkey | 用户可以注册多个（不同设备、平台），列表中显示名称和最后使用时间 |
| **账户恢复** | 恢复流程是最薄弱的环节：邮件 + 额外验证、恢复码；恢复后通知用户 |
| 跨设备 | 混合传输（扫描二维码用手机登录） |
| 兼容 | 不支持的环境回退到其他方式 |
| 服务端库 | 使用成熟的库（SimpleWebAuthn 等）处理复杂的校验 |
| 指标 | Passkey 注册率、登录成功率、回退率 |

**口述模板（30–60 秒）**

1. 一句话结论：渐进式落地，从可选方式开始，引导用户创建，最后支持无密码。
2. 关键机制：条件式 UI 让 Passkey 出现在自动填充中，登录后引导创建。
3. 对比或注意点：rpId 之后很难更改，要选择注册域名。
4. 可追问时补充：账户恢复是最薄弱的环节，需要额外验证和通知。

**常见追问**

- 为什么账户恢复是最薄弱的环节？→ 攻击者无法钓鱼 Passkey，就会转而攻击恢复流程（例如通过客服社工、劫持邮箱）。

### Q6. 令牌安全怎么权衡？有没有「完美」的方案？

- **难度**: 高级
- **标签**: 令牌, 架构

**答案**

**没有完美的方案，只有针对威胁的取舍**：

| 威胁 | 内存令牌 | localStorage | HttpOnly Cookie | BFF |
|------|----------|--------------|-----------------|-----|
| XSS 窃取令牌带走 | 可以（页面期间） | **可以，长期** | 不可以 | 不可以（令牌不在浏览器） |
| XSS 在页面中借用身份 | 可以 | 可以 | 可以 | 可以 |
| CSRF | 不受影响 | 不受影响 | 需要防御 | 需要防御 |
| 刷新后保持登录 | 需要刷新令牌 | 可以 | 可以 | 可以 |
| 实现复杂度 | 中 | 低 | 低 | 高 |

**结论**：

- **XSS 是根本问题**：任何方案都无法防止 XSS 在页面中借用身份 → 首要任务是防 XSS（CSP、Trusted Types）
- 在此基础上，选择让令牌**无法被带走**的方案（HttpOnly Cookie / BFF）
- **DPoP**（令牌绑定）：令牌绑定到客户端的密钥对（私钥不可导出，存储在浏览器中），令牌被窃取后在其他设备上无法使用
- **设备绑定会话凭证（DBSC）**：Chrome 推进的方案，会话 Cookie 绑定设备的密钥，被窃取的 Cookie 在其他设备上无法使用（以官方进展为准）

**口述模板（30–60 秒）**

1. 一句话结论：没有完美的方案，XSS 是根本问题，任何存储方式都无法防止在页面中借用身份。
2. 关键机制：在防 XSS 的基础上，选择令牌无法被带走的方案，例如 HttpOnly Cookie 或 BFF。
3. 对比或注意点：Cookie 方案需要防 CSRF。
4. 可追问时补充：DPoP 和 DBSC 把令牌绑定到设备，被窃取后无法在其他地方使用。

**常见追问**

- 窃取 Cookie 的恶意软件（信息窃取木马）怎么防？→ 服务端的异常检测（IP、设备变化）、短会话、敏感操作重新认证；DBSC 这类设备绑定的方案专门针对这种威胁。

## 三、供应链

### Q7. 复盘 Shai-Hulud 事件：如果你的团队受到影响，怎么应急？

- **难度**: 高级
- **标签**: 供应链, 应急

**答案**

**发现**：

- SCA 工具或安全公告提示某些依赖版本是恶意的
- 查询所有仓库的锁文件和 SBOM，确定哪些项目在什么时间安装了受影响的版本

**止损**（按优先级）：

```text
1. 确定暴露范围：哪些机器（开发者电脑、CI 运行器）在受影响的时间段内执行了安装
2. 轮换凭证：这些环境中能访问到的所有凭证
   - npm 令牌、GitHub 令牌（个人和 CI）、云服务凭证、SSH 密钥、.env 中的密钥
3. 检查是否已被利用：
   - 自己维护的 npm 包是否有未授权的新版本 → 弃用并发布修复版本
   - GitHub 中是否出现了未知的仓库、工作流、提交
   - 云服务的访问日志
4. 清理：固定到安全版本、删除 node_modules 和缓存、重新安装
5. 如果构建产物可能被污染：重新构建并部署
```

**事后改进**：

- 禁用依赖的安装脚本（白名单）
- 依赖冷却期
- CI 中安装依赖的步骤与持有发布凭证的步骤隔离
- 开发者不在本机长期保存高权限的令牌
- 自己的包改用可信发布（限制分支和工作流）并要求人工审批

**口述模板（30–60 秒）**

1. 一句话结论：先通过锁文件和 SBOM 确定受影响的项目和环境，然后轮换所有可能泄露的凭证。
2. 关键机制：检查自己维护的包是否被发布了未授权的版本，检查 GitHub 和云服务的异常。
3. 对比或注意点：轮换凭证比删除依赖更重要，因为凭证可能已经被窃取。
4. 可追问时补充：事后禁用安装脚本、设置冷却期、隔离发布凭证。

**常见追问**

- 为什么要隔离安装依赖和发布的步骤？→ 安装步骤执行第三方代码（即使禁用了脚本，构建过程也会执行依赖的代码），不应该能够访问发布凭证。

### Q8. 设计一个依赖治理体系

- **难度**: 高级
- **标签**: 供应链, 治理

**答案**

| 环节 | 措施 |
|------|------|
| **准入** | 新增依赖需要评估：维护活跃度、下载量、维护者数量、许可证、是否有安装脚本、体积；自动化检查 + 人工审批 |
| **安装** | 私有代理仓库（缓存 + 拦截恶意包）、锁文件、禁止安装脚本、冷却期 |
| **更新** | Renovate 集中更新：分组、自动合并补丁版本（测试通过后）、安全更新优先 |
| **监控** | SCA 持续扫描所有仓库；恶意包情报；SBOM 存档 |
| **响应** | 高危漏洞的修复时限（例如 7 天）；紧急漏洞的全局扫描和批量升级能力 |
| **退出** | 定期清理未使用的依赖（knip、depcheck）；用原生 API 替代小工具库 |
| **度量** | 依赖总数、过期依赖比例、漏洞存量、平均修复时长 |

**减少依赖本身就是安全措施**：每个依赖都是一个信任关系。

**口述模板（30–60 秒）**

1. 一句话结论：依赖治理覆盖准入、安装、更新、监控、响应和退出六个环节。
2. 关键机制：私有代理仓库拦截恶意包，Renovate 集中更新并设置冷却期。
3. 对比或注意点：减少依赖本身就是安全措施。
4. 可追问时补充：建立紧急漏洞的全局扫描和批量升级能力。

**常见追问**

- monorepo 和多仓库在依赖治理上有什么差异？→ monorepo 统一版本、一次升级全部生效；多仓库需要集中的扫描平台和批量升级工具。

### Q9. 怎么治理页面中的第三方脚本？

- **难度**: 高级
- **标签**: 第三方脚本

**答案**

**清单化**：

- 每个第三方脚本登记：用途、负责人、加载的页面、数据访问范围、供应商的安全评估
- 定期审查，移除不再使用的

**加载控制**：

- 通过统一的加载器加载（便于控制、监控和 CSP 的 strict-dynamic）
- **敏感页面**（登录、支付、个人信息）白名单制，默认不加载
- 标签管理器（GTM 等）中的变更需要审批

**隔离**：

- 沙箱 iframe（广告、客服挂件）
- Web Worker（Partytown）
- 限制可以访问的数据（不在全局变量中暴露用户信息）

**运行时监控**：

- 对比页面实际加载的脚本与清单
- 监控脚本内容的哈希变化
- CSP `connect-src` 限制数据发送的目标，报告异常的外发请求

**合规**：PCI DSS 4.0（6.4.3、11.6.1）对支付页面的脚本清单、授权、完整性和变更检测提出了明确要求。

**口述模板（30–60 秒）**

1. 一句话结论：第三方脚本治理包括清单化、加载控制、隔离和运行时监控。
2. 关键机制：每个脚本登记用途和负责人，敏感页面白名单制。
3. 对比或注意点：能隔离的放在沙箱 iframe 或 Worker 中。
4. 可追问时补充：监控实际加载的脚本和内容变化；支付页面有 PCI DSS 的合规要求。

**常见追问**

- 营销团队要求随时添加脚本怎么办？→ 提供受控的流程（标签管理器 + 审批 + 只能在非敏感页面），平衡效率和安全。

## 四、框架与服务端

### Q10. 框架爆出严重漏洞（例如 React2Shell），你怎么组织应急？

- **难度**: 高级
- **标签**: 应急, 框架漏洞

**答案**

```text
T+0：获取信息
  - 官方公告：影响的版本、修复版本、是否有在野利用、临时缓解措施
  - 定级（CVSS 10、未鉴权 RCE、已有在野利用 → 最高优先级）

T+1h：定位影响范围
  - 通过 SBOM / 依赖扫描查询所有使用受影响包的应用（包括间接依赖）
  - 区分对外暴露的和内部的

T+数小时：临时缓解
  - WAF 规则（厂商通常很快提供）
  - 对高风险应用考虑临时下线受影响的功能

T+1 天内：升级
  - 按优先级升级到修复版本，跑核心测试后发布
  - 对无法立即升级的应用记录例外和缓解措施

同时：排查是否已被利用
  - 检查日志中的异常请求、异常进程、异常的外连
  - 如果怀疑被利用：轮换服务器上的密钥和凭证、重建实例

事后：复盘
  - 响应时长、阻碍（升级困难、测试不足）
  - 改进：依赖监控、自动化升级、更快的发布流程
```

**口述模板（30–60 秒）**

1. 一句话结论：获取信息并定级，用 SBOM 定位影响范围，先临时缓解再升级。
2. 关键机制：WAF 规则作为临时缓解，按优先级升级到修复版本。
3. 对比或注意点：同时排查是否已被利用，怀疑被利用时轮换密钥并重建实例。
4. 可追问时补充：事后复盘响应时长，改进依赖监控和发布流程。

**常见追问**

- 升级框架后出现破坏性变更怎么办？→ 安全修复通常在多个小版本线上提供补丁（例如 15.0.5、15.1.9），选择当前小版本线上的补丁版本，避免跨版本升级。

### Q11. Node.js 服务（SSR / BFF）怎么做安全加固？

- **难度**: 高级
- **标签**: Node.js

**答案**

| 方面 | 措施 |
|------|------|
| 运行环境 | 非 root 用户、只读文件系统、最小镜像（distroless）、及时更新 Node.js 版本 |
| **权限模型** | Node.js 的 `--permission`（限制文件系统、子进程、网络等的访问，以官方为准） |
| 输入 | 请求体大小限制、校验所有输入、防原型污染、防 ReDoS |
| 出站请求 | SSRF 防护、出站白名单（网络策略） |
| 密钥 | 从密钥管理服务读取，不写入镜像和代码；不打印到日志 |
| 错误 | 生产环境不返回堆栈；`unhandledRejection` 处理 |
| HTTP | 安全响应头（helmet）、超时（`headersTimeout`、`requestTimeout`）、防慢速攻击 |
| 依赖 | 见依赖治理 |
| 日志 | 结构化日志、脱敏、安全事件告警 |
| 进程 | 进程管理器重启、资源限制（内存、CPU） |

**口述模板（30–60 秒）**

1. 一句话结论：从运行环境、权限、输入、出站请求、密钥、错误处理等方面加固。
2. 关键机制：非 root 运行、最小镜像、Node.js 权限模型限制资源访问。
3. 对比或注意点：出站请求要防 SSRF，密钥从密钥管理服务读取。
4. 可追问时补充：设置请求超时防慢速攻击，日志脱敏。

**常见追问**

- 为什么要限制出站网络？→ 即使服务被攻破（例如 RCE），攻击者也难以外传数据或下载后续的恶意程序。

### Q12. 安全响应头怎么在大型系统中统一管理？

- **难度**: 高级
- **标签**: 响应头

**答案**

**挑战**：多个应用、多个团队、多种技术栈，配置不一致；CSP 每个应用不同。

**方案**：

```text
网关 / CDN 层：统一添加通用的头
  - HSTS、X-Content-Type-Options、Referrer-Policy、Permissions-Policy（默认值）
  - 移除泄露信息的头（Server、X-Powered-By）
应用层：应用相关的头
  - CSP（每个应用的资源不同，nonce 需要在渲染时生成）
  - frame-ancestors（是否允许被嵌入取决于业务）
  - COOP / COEP
```

**治理**：

- 安全头的基线配置以代码形式管理（基础设施即代码）
- 应用覆盖默认值需要说明原因并审批
- 持续扫描所有域名，与基线对比，偏离时告警
- 新应用的脚手架内置

**口述模板（30–60 秒）**

1. 一句话结论：通用的头在网关或 CDN 层统一添加，应用相关的头（CSP）由应用设置。
2. 关键机制：基线配置以代码形式管理，持续扫描所有域名。
3. 对比或注意点：CSP 的 nonce 需要在渲染时生成，所以在应用层设置。
4. 可追问时补充：应用覆盖默认值需要审批，脚手架内置。

**常见追问**

- 网关和应用都设置了同一个头会怎样？→ 可能出现两个头（例如两个 CSP 同时生效，取交集，可能导致误拦截）；需要明确约定由哪一层负责。

## 五、隔离与新领域

### Q13. 微前端架构中怎么做安全隔离？

- **难度**: 高级
- **标签**: 微前端

**答案**

**问题**：多个团队的子应用运行在同一个页面（同一个源）中：

- 任一子应用的 XSS 影响整个页面
- 子应用可以读取其他子应用和主应用的数据（全局变量、存储、Cookie）
- JS 沙箱（Proxy 代理 window）**不是安全边界**，只用于避免全局变量冲突

**隔离级别**：

| 方案 | 隔离程度 | 代价 |
|------|----------|------|
| 同源 JS 沙箱（qiankun 等） | **无安全隔离**（防冲突） | 低 |
| Shadow DOM | 只隔离样式和 DOM 查询 | 低 |
| **跨源 iframe** | **真正的安全隔离**（不同的源） | 通信、体验、性能 |
| 不同的子域名 + 独立部署 | 源隔离 + Cookie 隔离（不设置 Domain） | 需要 SSO |

**实践**：

- 可信的内部子应用：同源方案 + 统一的安全基线（CSP、依赖治理、代码审查）
- 不可信或第三方的子应用（插件、开放平台）：**跨源 iframe + sandbox + postMessage 协议**
- 主应用的令牌不暴露给子应用；子应用通过主应用提供的受限 API 访问能力

**口述模板（30–60 秒）**

1. 一句话结论：同源的 JS 沙箱不是安全边界，只能防全局变量冲突。
2. 关键机制：真正的安全隔离需要跨源 iframe。
3. 对比或注意点：可信的子应用用同源方案加统一的安全基线，不可信的用跨源 iframe 加 sandbox。
4. 可追问时补充：主应用的令牌不暴露给子应用，通过受限的 API 提供能力。

**常见追问**

- 为什么 Proxy 沙箱不是安全边界？→ 子应用的代码仍然可以通过各种途径访问真实的全局对象（例如通过 DOM 元素的 `ownerDocument.defaultView`、`Function` 构造函数）。

### Q14. 低代码平台允许用户编写脚本，怎么设计沙箱？

- **难度**: 高级
- **标签**: 沙箱

**答案**

**威胁**：用户脚本窃取其他用户的数据、调用未授权的接口、攻击平台、消耗资源。

**方案对比**：

| 方案 | 隔离 | 说明 |
|------|------|------|
| `eval` / `new Function` + `with` / Proxy | **不安全** | 可以通过原型链逃逸 |
| **跨源 iframe（sandbox）** | 浏览器级的源隔离 | 用户代码运行在独立的沙箱域名中，通过 postMessage 调用平台提供的 API |
| Web Worker | 无 DOM 访问 | 仍然是同源，可以发请求 |
| **WASM 中的 JS 引擎**（QuickJS） | 完全隔离的解释器 | 只暴露显式提供的 API；可以限制执行时间和内存 |
| 服务端执行（隔离的容器 / V8 isolate） | 进程或虚拟机级 | 需要服务端资源 |

**设计要点**：

- **能力模型**：用户脚本只能调用平台显式暴露的 API，API 在宿主侧以**当前用户的权限**检查
- 资源限制：执行超时、内存上限、调用频率
- 网络：沙箱中的代码不能直接访问网络，通过宿主代理并检查
- 不同租户的代码运行在不同的源中

**口述模板（30–60 秒）**

1. 一句话结论：eval 加 Proxy 不安全，要使用跨源 iframe、WASM 中的 JS 引擎或服务端隔离。
2. 关键机制：用户脚本只能调用平台显式暴露的 API，API 在宿主侧检查权限。
3. 对比或注意点：需要限制执行时间、内存和网络访问。
4. 可追问时补充：WASM 中的 QuickJS 可以完全控制暴露的能力和资源。

**常见追问**

- ShadowRealm 能解决这个问题吗？→ ShadowRealm（提案）提供独立的全局对象，但它与宿主在同一个进程和源中，设计目标是隔离全局状态而不是安全沙箱。

### Q15. App 内的 H5 页面（WebView + JSBridge）有哪些安全风险？

- **难度**: 高级
- **标签**: WebView, 移动端

**答案**

**JSBridge** 让 H5 调用原生能力（获取用户信息、支付、文件、相机、分享）。

| 风险 | 说明 | 措施 |
|------|------|------|
| **任意页面调用 Bridge** | WebView 加载了第三方页面或被注入的页面，调用敏感的原生能力 | **原生侧校验调用页面的域名**（白名单），按域名分配能力 |
| 开放重定向 / 任意 URL 加载 | 通过 URL 参数让 WebView 打开攻击者的页面 | WebView 只允许加载白名单域名；外部链接用系统浏览器打开 |
| 明文传输 | HTTP 页面被劫持后调用 Bridge | 只允许 HTTPS |
| 敏感数据通过 Bridge 返回 | 令牌、用户信息 | 最小化；返回给特定域名 |
| 文件访问 | `file://` 协议、允许通用文件访问 | 禁用文件访问 |
| 离线包被篡改 | 本地 H5 资源被替换 | 签名校验 |
| 旧版本的 WebView | 内核漏洞 | 使用系统更新的 WebView 组件 |

**口述模板（30–60 秒）**

1. 一句话结论：最大的风险是任意页面都能调用 JSBridge 的敏感能力。
2. 关键机制：原生侧校验调用页面的域名，按域名分配能力。
3. 对比或注意点：WebView 只允许加载白名单域名的 HTTPS 页面，外部链接用系统浏览器打开。
4. 可追问时补充：离线包签名校验，禁用文件访问。

**常见追问**

- 为什么不能在 H5 侧做权限判断？→ H5 页面可以被替换或注入，判断必须在原生侧根据实际加载的 URL 进行。

### Q16. AI 应用（Agent、RAG）的前端和 BFF 应该怎么防御提示词注入？

- **难度**: 高级
- **标签**: AI, 提示词注入

**答案**

**认识**：提示词注入**目前没有完全可靠的防御**，模型无法可靠地区分「指令」和「数据」→ 设计目标是**限制注入成功后的影响**。

**架构层面的防御**：

| 措施 | 说明 |
|------|------|
| **最小权限** | 模型可以调用的工具只有完成任务所需的最少能力；以当前用户的权限执行 |
| **人在回路** | 有副作用的操作（发邮件、付款、删除、修改权限）需要用户确认，并展示完整的参数 |
| **数据与指令隔离** | 不可信内容（网页、文档、邮件）用明确的标记包裹；处理不可信内容的模型不能调用敏感工具（双模型模式） |
| **输出处理** | 模型输出当作不可信的输入：渲染时清洗，链接和图片限制域名（防止数据外泄），不直接执行模型生成的代码 |
| 敏感数据 | 不要把不需要的敏感数据放入上下文 |
| 监控 | 记录工具调用，检测异常模式 |
| 速率和成本 | 限流、额度 |

**前端特有的**：

- Markdown 渲染禁用原始 HTML，图片只允许可信的域名（CSP `img-src`）
- 工具调用的确认界面清晰展示操作和参数
- 流式输出中的链接在完成前不可点击（防止中途的内容误导）

**口述模板（30–60 秒）**

1. 一句话结论：提示词注入目前没有完全可靠的防御，目标是限制注入成功后的影响。
2. 关键机制：最小权限的工具、有副作用的操作需要用户确认、不可信内容与指令隔离。
3. 对比或注意点：模型输出当作不可信输入，图片和链接限制域名防止数据外泄。
4. 可追问时补充：处理不可信内容的模型不应该能调用敏感工具。

**常见追问**

- 用另一个模型检测注入可行吗？→ 可以作为一层防御（检测明显的注入），但同样可以被绕过，不能作为唯一的防线。

### Q17. 前端安全监控应该监控什么？

- **难度**: 高级
- **标签**: 监控

**答案**

| 监控项 | 数据来源 | 能发现 |
|--------|----------|--------|

| 安全头 | 定期扫描 | 配置回退 |
| 证书 | 证书透明度日志、到期监控 | 误签、到期 |

**口述模板（30–60 秒）**

1. 一句话结论：监控 CSP 违规、脚本清单变化、页面完整性、依赖漏洞、安全头、证书和子域名。
2. 关键机制：CSP 报告可以发现 XSS 尝试和未授权的脚本。
3. 对比或注意点：支付页面要监控 DOM 结构，发现被注入的表单字段。
4. 可追问时补充：基于基线做异常检测，每个告警都有负责人。

**常见追问**

- Magecart 攻击是什么？→ 在电商的支付页面中注入脚本，窃取用户输入的信用卡信息，通常通过被攻破的第三方脚本或网站本身的漏洞注入。

### Q18. 发现一个线上 XSS 漏洞后，应该怎么处理？

- **难度**: 高级
- **标签**: 应急

**答案**

```text
1. 确认与定级
   - 复现（在测试环境），确认类型（存储型影响所有访问者，最严重）
   - 影响范围：哪些页面、哪些用户、是否能获取令牌、是否有 CSP 缓解
   - 是否已被利用（日志、CSP 报告中的异常）

2. 止损
   - 存储型：清理数据库中的恶意内容（批量清洗）
   - 临时：WAF 规则、关闭受影响的功能、收紧 CSP

3. 修复
   - 修复根因（输出编码 / 清洗），而不是只过滤特定的载荷
   - 排查同类问题（同一个模式在其他地方是否存在）

4. 恢复与影响评估
   - 如果令牌可能已被窃取：使相关会话失效
   - 如果涉及个人信息泄露：按法规评估是否需要通知用户和监管

5. 复盘
   - 为什么代码审查和扫描没有发现
   - 改进：增加 ESLint 规则、Trusted Types、清洗组件统一化
```

**口述模板（30–60 秒）**

1. 一句话结论：确认定级、止损、修复根因、评估影响、复盘改进。
2. 关键机制：存储型 XSS 要清理数据库中的恶意内容，可以先用 WAF 和关闭功能止损。
3. 对比或注意点：修复根因而不是过滤特定的载荷，并排查同类问题。
4. 可追问时补充：可能泄露令牌时使会话失效，涉及个人信息时评估通知义务。

**常见追问**

- 为什么不能只过滤报告中的载荷？→ 攻击者可以换一种写法绕过；根因是输出时没有正确编码。

### Q19. 前端在隐私合规方面需要做什么？

- **难度**: 高级
- **标签**: 合规, 隐私

**答案**

**相关法规**：中国《个人信息保护法》（PIPL）、《数据安全法》；欧盟 GDPR；以及行业规范（App 个人信息收集的相关规定）。

| 要求 | 前端的实现 |
|------|------------|
| **告知同意** | 隐私政策弹窗，**同意前不收集**（不初始化统计、不读取设备信息）；单独同意（敏感信息、跨境） |
| **最小必要** | 只收集业务需要的数据；权限（定位、相机）在使用时申请 |
| 可撤回 | 设置中可以撤回同意，撤回后停止收集 |
| Cookie 同意（GDPR） | 非必要的 Cookie（统计、广告）在用户同意后才设置 |
| 用户权利 | 查看、导出、删除个人信息、注销账号的入口 |
| 敏感信息 | 加密传输、脱敏展示 |
| **第三方 SDK** | 列出 SDK 清单及其收集的信息；SDK 也必须在同意后初始化 |
| 跨境 | 数据发送到境外的服务（统计、监控、AI）需要评估 |
| 未成年人 | 特殊保护 |

**口述模板（30–60 秒）**

1. 一句话结论：前端负责告知同意、最小必要收集、可撤回和用户权利的实现。
2. 关键机制：同意前不初始化统计和第三方 SDK，不读取设备信息。
3. 对比或注意点：第三方 SDK 也要在同意后初始化，并列出清单。
4. 可追问时补充：数据发送到境外的服务需要评估跨境合规。

**常见追问**

- 监控 SDK 的会话回放功能有什么合规风险？→ 可能录制个人信息；需要默认屏蔽输入、告知用户、数据存储位置符合要求。

### Q20. 支付页面的前端安全有哪些特殊要求？

- **难度**: 高级
- **标签**: 支付, 合规

**答案**

**PCI DSS 4.0** 中与前端直接相关的要求（2025-03-31 起强制，以官方为准）：

- **6.4.3**：支付页面上的**所有脚本**必须有清单、经过授权、说明必要性，并有机制保证**完整性**
- **11.6.1**：检测支付页面的**未授权修改**（包括 HTTP 头和页面内容），并告警

**实践**：

| 措施 | 说明 |
|------|------|
| **减小范围** | 使用支付服务商的托管页面或 iframe（卡号输入框在服务商的域名中），自己的页面不接触卡号 |
| 最少脚本 | 支付页面只加载必要的脚本，没有统计、广告、客服 |
| 严格的 CSP | nonce + strict-dynamic，`connect-src` 只允许支付相关的域名，`frame-src` 只允许支付服务商 |
| SRI | 固定版本的脚本 |
| 变更检测 | 监控页面脚本和关键头部的变化 |
| 防点击劫持 | `frame-ancestors 'none'` |
| 防重复提交 | 幂等键 |
| 金额 | 以服务端为准 |

**口述模板（30–60 秒）**

1. 一句话结论：支付页面要满足 PCI DSS 4.0 对脚本清单、完整性和变更检测的要求。
2. 关键机制：最有效的是使用支付服务商的托管页面或 iframe，自己的页面不接触卡号。
3. 对比或注意点：支付页面只加载必要的脚本，使用严格的 CSP。
4. 可追问时补充：监控页面脚本和头部的变化，金额以服务端为准。

**常见追问**

- 使用了服务商的 iframe，还需要关心 6.4.3 吗？→ 需要。承载 iframe 的父页面中的脚本可以覆盖或伪造 iframe（例如插入假的输入框），所以父页面同样在要求范围内。

## 七、取舍与趋势

### Q21. 安全和体验冲突时怎么权衡？

- **难度**: 高级
- **标签**: 权衡

**答案**

**原则**：

- **基于风险分级**：不同的操作采用不同的安全强度（浏览 → 无需验证；修改资料 → 已登录；支付 / 修改密码 → 重新认证或 MFA）
- **自适应**：正常情况无感知，异常时提高要求（新设备、异地登录时才要求验证）
- **让安全的方式也是方便的方式**：Passkeys 比密码更安全也更方便

**例子**：

| 冲突 | 权衡 |
|------|------|
| 会话时长 | 长会话 + 敏感操作重新认证 |
| 验证码 | 风险评分低时不显示（无感验证） |
| 严格 CSP 阻碍第三方脚本 | 敏感页面严格，营销页面放宽 |
| 每次登录都要 MFA | 可信设备记住一段时间 |
| 强密码规则 | 鼓励长密码 + 检查是否泄露，不强制复杂组合 |

**口述模板（30–60 秒）**

1. 一句话结论：按风险分级，不同的操作采用不同的安全强度。
2. 关键机制：自适应安全，正常情况无感知，异常时提高要求。
3. 对比或注意点：让安全的方式也是方便的方式，例如 Passkeys。
4. 可追问时补充：长会话配合敏感操作重新认证，验证码只在高风险时出现。

**常见追问**

- 产品要求「记住我」30 天，你怎么设计？→ 长期的刷新令牌（HttpOnly、轮换、重用检测）+ 设备绑定 + 敏感操作重新认证 + 用户可以查看和撤销设备。

### Q22. 前端安全在哪些情况下容易被忽视？

- **难度**: 高级
- **标签**: 经验

**答案**

| 容易被忽视的地方 | 原因 |
|------------------|------|
| **管理后台** | 「内部使用」，但被攻破后影响最大；常被 UGC 中的存储型 XSS 攻击 |
| **错误页、404 页** | 把 URL 原样输出 → 反射型 XSS |
| 邮件模板、PDF 生成、导出 Excel | 服务端渲染用户数据（CSV 注入：以 `=` 开头的单元格被 Excel 当作公式执行） |
| **旧的子域名、测试环境** | 无人维护，子域名接管、测试环境的弱密码 |
| 移动端 WebView | 不在 Web 团队的视野中 |
| SVG、Markdown 预览 | 「看起来只是图片 / 文本」 |
| 内部工具和脚手架 | 开发者的令牌泄露 |
| 依赖的依赖 | 只关注直接依赖 |
| 日志与监控 | 令牌和个人信息被记录 |

**口述模板（30–60 秒）**

1. 一句话结论：容易被忽视的地方包括管理后台、错误页、导出功能、旧子域名和 WebView。
2. 关键机制：管理后台被 UGC 中的存储型 XSS 攻击，影响最大。
3. 对比或注意点：导出 CSV 时以 = 开头的单元格可能被当作公式执行。
4. 可追问时补充：旧的子域名和测试环境无人维护，容易被接管。

**常见追问**

- CSV 注入怎么防？→ 导出时对以 `=`、`+`、`-`、`@`、制表符、回车开头的单元格加前缀单引号或转义。

### Q23. 如何评估一个开源库是否安全可用？

- **难度**: 高级
- **标签**: 供应链

**答案**

| 维度 | 检查项 |
|------|--------|
| 维护 | 最近的提交和发布、问题的响应速度、维护者数量（单人维护风险更高） |
| 流行度 | 下载量、依赖它的项目（注意刷量） |
| 安全历史 | 过往漏洞及修复速度、是否有安全策略（SECURITY.md） |
| 依赖 | 依赖树的大小、是否有安装脚本、是否有原生模块 |
| 发布 | 是否使用可信发布 / provenance、维护者是否开启 2FA |
| 代码 | 对于关键的库，抽查代码（网络访问、动态执行、混淆） |
| 许可证 | 是否与公司政策兼容 |
| 评分工具 | OpenSSF Scorecard、Socket 评分 |
| **替代方案** | 能否用原生 API 或少量自己的代码替代 |

**口述模板（30–60 秒）**

1. 一句话结论：从维护活跃度、安全历史、依赖树、发布方式、代码和许可证等方面评估。
2. 关键机制：单人维护、依赖树大、有安装脚本的库风险更高。
3. 对比或注意点：优先考虑能否用原生 API 替代。
4. 可追问时补充：使用 OpenSSF Scorecard 等工具辅助评估。

**常见追问**

- 一个很小的工具库（几十行代码）要不要引入？→ 通常不要，自己实现或使用原生 API；每个依赖都是一个长期的信任关系和攻击面。

### Q24. 你怎么在团队中推动安全文化？

- **难度**: 高级
- **标签**: 团队

**答案**

- **默认安全的基础设施**：让正确的做法成为最省事的做法（脚手架、组件、请求库）
- **在流程中嵌入**：代码审查清单、CI 自动检查、高风险需求的安全评审
- **安全冠军**：每个团队有一名对安全感兴趣的成员，作为接口人
- **分享真实案例**：内部漏洞复盘（不追责，关注改进）、行业事件解读
- **低成本的反馈**：扫描结果附带修复建议和示例
- **可度量**：安全指标纳入团队的质量看板
- **奖励**：发现和修复漏洞的认可

**口述模板（30–60 秒）**

1. 一句话结论：推动安全文化的关键是默认安全的基础设施和嵌入流程，而不是靠说教。
2. 关键机制：每个团队设安全冠军，扫描结果附带修复建议。
3. 对比或注意点：漏洞复盘不追责，关注改进。
4. 可追问时补充：安全指标纳入质量看板，对发现和修复漏洞给予认可。

**常见追问**

- 你推动过的一个安全改进是什么？→ 结合自己的经验，用 STAR 结构说明背景、行动和量化的结果（例如 CSP 覆盖率从 0 到 80%、依赖漏洞存量下降 70%）。

### Q25. 讲一个你参与的安全相关的项目经历

- **难度**: 高级
- **标签**: 项目经验

**答案**

**STAR 结构的参考**：

- **背景**：例如「公司有 30 多个前端应用，没有 CSP，曾经出现过一次存储型 XSS」
- **任务**：「在半年内让核心应用落地严格的 CSP」
- **行动**：
  - 统一的 SSR 框架插件注入 nonce
  - Report-Only 收集报告，建立报告平台按应用和来源聚合
  - 改造内联事件和 eval，推动第三方供应商升级
  - 按流量比例灰度强制执行
  - CI 中禁止新增内联事件
- **结果**：核心应用 CSP 覆盖率达到多少、拦截了多少次注入尝试、新增 XSS 漏洞数量下降
- **复盘**：遇到的困难（第三方脚本、CDN 缓存）、如果重来会怎么做

**准备其他可选的案例**：依赖治理、令牌存储改造、供应链事件响应、Passkeys 落地。

**口述模板（30–60 秒）**

1. 一句话结论：用 STAR 结构讲清背景、任务、行动和量化的结果。
2. 关键机制：行动要具体，说明技术方案和推进方式。
3. 对比或注意点：结果要有数据，例如覆盖率、拦截次数、漏洞数量变化。
4. 可追问时补充：说明遇到的困难以及如果重来的改进。

**常见追问**

- 推进中最大的阻力是什么？→ 通常是第三方脚本和业务团队的排期；解决方式是提供工具降低改造成本、按风险优先级推进、获得管理层支持。

### Q26. 前端安全有哪些值得关注的趋势？

- **难度**: 高级
- **标签**: 趋势

**答案**

（截至 2026-10，以官方为准）

- **供应链安全成为首要风险**：OWASP 2025 将其排到第三；npm 平台持续加固（吊销 classic token、默认不执行依赖的安装脚本、可信发布）；但攻击者在转向 CI / CD 配置缺陷
- **框架层的安全**：RSC 等新的服务端 / 客户端协议成为新的攻击面（React2Shell）
- **浏览器原生防御**：Trusted Types 跨浏览器支持、Sanitizer API、Fetch Metadata、跨源隔离
- **无密码认证**：Passkeys 普及；设备绑定的会话（DBSC）和令牌（DPoP）对抗凭证窃取
- **AI 应用安全**：提示词注入、输出处理、Agent 的权限控制
- **隐私**：第三方 Cookie 的去留、存储分区、隐私合规趋严
- **证书和传输**：证书有效期缩短、后量子密码

**口述模板（30–60 秒）**

1. 一句话结论：供应链安全成为首要风险，框架协议成为新的攻击面，浏览器的原生防御在增强。
2. 关键机制：npm 平台在加固，攻击者转向 CI / CD 配置缺陷。
3. 对比或注意点：AI 应用带来了提示词注入等新问题。
4. 可追问时补充：Passkeys 和设备绑定的会话在对抗凭证窃取。

**常见追问**

- 这些趋势对前端工程师的能力要求有什么变化？→ 安全不再只是 XSS 和 CSRF，需要理解供应链、CI / CD、服务端渲染、认证协议和 AI 应用的风险。
