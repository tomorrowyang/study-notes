# React 系统设计题（8 道）

> 回答结构：澄清需求 → 整体架构 → 关键模块 → 状态与数据流 → 性能 / 可访问性 / 异常 → 演进。

---

### S1. 设计一个企业级 React 组件库

- **难度**: senior
- **标签**: 组件库, 架构

**澄清问题**

- 服务多少业务线？是否多品牌、多主题？
- 是否需要支持 SSR / RSC？
- 无障碍等级要求？
- 是否有设计稿规范（Design System）？

**参考方案**

```text
Design Tokens（颜色、间距、字号、圆角）
  ↓ 构建为 CSS 变量 / TS 常量
Headless 层：状态与交互逻辑（useControllableState、焦点管理、键盘、ARIA）
  ↓
Styled 层：样式与主题（CSS Modules / Tailwind / 零运行时 CSS-in-JS）
  ↓
组件：Button、Form、Table、Dialog、Select ...
  ↓
文档与质量：Storybook、单测、视觉回归、a11y 自动检测
  ↓
发布：ESM 多入口、按需加载、changesets 语义化版本
```

**关键设计**

- 受控/非受控双模式统一由 `useControllableState` 实现
- Compound Components + Context 组织复杂组件（Tabs、Select）
- `asChild` / Slot 模式允许替换渲染元素
- 交互组件标记 `'use client'`，纯展示组件可在 RSC 中使用
- 样式零运行时，主题通过 CSS 变量切换
- 每个组件提供完整 TS 类型，泛型组件（Table、Select）

**口述模板（2–3 分钟）**

我会把组件库分为 Token、Headless 逻辑、样式、组件和工程化五层。Token 统一设计规范并输出 CSS 变量；Headless 层负责状态、键盘交互和 ARIA，保证可访问性；样式层使用零运行时方案，避免 RSC 和流式 SSR 下的运行时成本。复杂组件使用 Compound Components，所有表单类组件支持受控和非受控。工程上通过 Storybook 文档、交互测试、视觉回归保证质量，使用 changesets 管理版本，ESM 多入口保证 Tree Shaking。

**扩展追问**

- 业务想深度定制样式怎么办？→ 提供 className/style 透传、slot 级 className、CSS 变量和 Headless Hook 三个层次的定制能力。

### S2. 设计动态表单引擎（Schema 驱动）

- **难度**: senior
- **标签**: 表单, 低代码

**澄清问题**

- 字段数量规模（几十还是上千）？
- 是否需要联动、动态显隐、异步校验？
- Schema 来源：后端下发还是可视化搭建？

**参考方案**

```text
JSON Schema / 自定义 DSL
  ↓ 解析
Field Registry：type → 组件（Input、Select、DatePicker、自定义）
  ↓
Form Store：值、错误、touched、依赖图
  ├─ 校验：Zod / 自定义规则，同步 + 异步
  ├─ 联动：表达式或 effects，依赖图拓扑更新
  └─ 订阅：字段级订阅，只重渲染变化字段
  ↓
Renderer：递归渲染布局（分组、栅格、Tab、动态数组）
```

**关键设计**

- 字段级订阅（类似 React Hook Form / Formily）：输入一个字段不导致整表重渲染
- 联动规则声明式描述，构建依赖图，避免循环依赖
- 动态数组字段使用稳定 id 作为 key
- 表达式执行要沙箱化，禁止 eval 任意代码
- 大表单分步加载、虚拟化、按需注册组件

**口述模板（2–3 分钟）**

表单引擎由 Schema、组件注册表、表单状态和渲染器组成。Schema 描述字段类型、校验规则和联动关系；渲染器根据类型从注册表中取组件递归渲染。表单状态放在外部 store 中，字段通过 selector 订阅自己的值和错误，避免整表重渲染。联动规则构建依赖图，按拓扑顺序更新，同时检测循环依赖。校验使用 schema 库，支持异步校验和防抖。表达式不用 eval，而是受限 DSL 解析执行。

**扩展追问**

- 为什么不用一个大 useState 存全部字段？→ 任意字段变化会导致整个表单重渲染，上千字段时明显卡顿。

### S3. 设计百万行数据表格

- **难度**: senior
- **标签**: 性能, 虚拟化

**澄清问题**

- 数据在前端全量还是服务端分页？
- 是否需要排序、筛选、分组、编辑、固定列、列宽拖动？
- 是否需要导出？

**参考方案**

```text
数据层：服务端分页/游标 + TanStack Query 缓存
  ↓
表格逻辑：TanStack Table（Headless：排序、筛选、分组、列配置）
  ↓
虚拟化：行虚拟 + 列虚拟（TanStack Virtual）
  ↓
渲染：轻量单元格、固定列 sticky、编辑态按需挂载
  ↓
重计算：排序/聚合/导出放 Web Worker
```

**关键设计**

- 百万行不全量进前端，服务端分页 + 无限加载；前端全量时数据放 Worker
- 行列双向虚拟化，只渲染可视单元格
- 单元格默认只读展示，点击才挂载编辑器
- 选择状态存 id 集合（Set），不写入行对象
- 筛选输入用 useDeferredValue / Transition 保持输入流畅
- 导出走后端异步任务或 Worker 流式生成

**口述模板（2–3 分钟）**

首先不让百万行数据全部进入主线程：服务端分页或游标加载，结合 Query 缓存。表格逻辑使用 Headless 的 TanStack Table，渲染层做行列双向虚拟化。单元格保持轻量，编辑器按需挂载。排序、聚合等重计算放 Worker，筛选输入使用 Transition 保持交互流畅。选中状态用 id 集合单独存储，避免修改大量行对象。导出交给后端异步任务。

**扩展追问**

- 固定列和虚拟化怎么共存？→ 固定列使用 sticky 定位，虚拟化只作用于中间滚动列。

### S4. 设计中后台权限系统（菜单、路由、按钮）

- **难度**: senior
- **标签**: 权限, 路由

**澄清问题**

- 权限模型是 RBAC 还是 ABAC？
- 权限粒度：页面、按钮、字段、数据行？
- 权限变更是否需要实时生效？

**参考方案**

```text
登录 → 获取用户信息 + 权限码集合（Set）
  ↓
路由层：路由表声明 meta.permission，loader / 中间件校验，无权限重定向 403
  ↓
菜单层：根据路由表 + 权限过滤生成
  ↓
组件层：<Access code="order:delete"> / useAccess()
  ↓
请求层：401 跳登录，403 提示
  ↓
后端：每个接口强制鉴权（真正的安全边界）
```

**关键设计**

- 前端权限只控制体验，后端必须校验
- 路由懒加载 + 加载前校验，避免页面闪烁
- 权限数据缓存，并在切换角色/租户时整体失效
- 字段级权限：Schema 中声明，渲染层过滤
- RSC 场景在服务端组件中直接鉴权，不把无权数据发给客户端

**口述模板（2–3 分钟）**

用户登录后获取权限码集合。路由表中为每个路由声明所需权限，在路由 loader 中校验，没有权限直接重定向，避免先渲染再跳转。菜单从同一份路由表过滤生成，保证单一数据源。按钮级权限通过 Access 组件或 useAccess Hook 控制。请求层统一处理 401 和 403。最重要的是前端权限只是体验优化，真正的安全控制在后端接口；在 RSC 架构下，无权限的数据根本不应序列化到客户端。

**扩展追问**

- 权限实时变更怎么办？→ WebSocket 推送或请求 403 时刷新权限并重新生成路由。

### S5. 设计大型 React 应用的状态管理架构

- **难度**: senior
- **标签**: 状态管理

**澄清问题**

- 团队规模？多少业务模块？
- 是否 SSR / RSC？
- 是否需要离线、协作、撤销重做？

**参考方案**

```text
服务端状态：TanStack Query（或 RSC 直接取数）
URL 状态：路由 search params（筛选、分页、Tab）
表单状态：React Hook Form
全局客户端状态：Zustand（按领域切片），极少量
局部 UI 状态：useState / useReducer
跨组件共享但低频：Context（主题、语言、当前用户）
```

**关键设计**

- 先分类，避免把所有数据放一个全局 store
- 服务端状态以 queryKey 为中心，mutation 后精确失效
- 全局 store 按领域拆分，组件只用 selector 订阅
- SSR 时 store 按请求创建，通过 Provider 注入，避免跨请求数据泄漏
- 复杂流程（支付、上传、向导）使用状态机

**口述模板（2–3 分钟）**

我先把状态分为服务端状态、URL 状态、表单状态、全局客户端状态和局部 UI 状态。服务端状态交给 Query 管理缓存、过期和同步；筛选分页放 URL，便于分享和刷新恢复；表单交给表单库；真正的全局客户端状态很少，用 Zustand 按领域切片并通过 selector 订阅。SSR 时 store 每个请求独立创建。复杂流程使用状态机描述，避免多个布尔值组合出不可能状态。

**扩展追问**

- 为什么不只用 Redux？→ 可以，但服务端缓存、URL 同步、表单都不是 Redux 的强项，分类管理更简单。

### S6. 设计基于 Next.js App Router 的电商详情页渲染架构

- **难度**: senior
- **标签**: RSC, SSR, 缓存

**澄清问题**

- 流量规模？是否大促？
- 哪些数据是静态的（商品描述），哪些是动态的（价格、库存、个性化推荐）？
- SEO 要求？

**参考方案**

```text
页面外壳（RSC，静态/ISR）：商品标题、图片、描述
  ├─ <Suspense>：价格与库存（RSC，动态，短缓存）
  ├─ <Suspense>：推荐（RSC，个性化，流式）
  ├─ Client Component：购买按钮、规格选择、购物车（交互）
  └─ Server Function：加购、下单（鉴权 + 校验 + 幂等）
CDN：静态外壳缓存；动态部分流式补齐（部分预渲染）
```

**关键设计**

- 静态与动态分离：外壳预渲染/缓存，动态数据在 Suspense 中流式输出
- 交互部分最小化为 Client Component，减少 JS
- 数据请求在服务端并行，避免瀑布
- 加购使用 useOptimistic 乐观更新
- Server Function 鉴权、校验、幂等，防止重复下单
- 监控 LCP（主图优先级）、INP（规格切换）

**口述模板（2–3 分钟）**

我会把详情页拆为静态外壳和动态区块。标题、图片、描述是 Server Component，预渲染并通过 CDN 缓存，保证 LCP 和 SEO；价格、库存、推荐放在独立 Suspense 边界中流式输出，互不阻塞。交互部分如规格选择和加购是 Client Component，尽量小。加购通过 Server Function 实现，内部做鉴权、参数校验和幂等处理，前端用 useOptimistic 立即反馈。大促时外壳全走缓存，动态接口做降级。

**扩展追问**

- 价格缓存过期怎么办？→ 短 TTL + 按标签主动失效（revalidateTag），下单时服务端以实时价格为准。

### S7. 设计 IM 聊天消息列表

- **难度**: senior
- **标签**: 实时, 虚拟列表

**澄清问题**

- 单会话消息量？是否需要历史消息向上加载？
- 消息类型：文本、图片、文件、富文本？
- 是否需要已读、撤回、发送失败重试？

**参考方案**

```text
WebSocket 连接层：心跳、重连、消息去重（messageId）、顺序（seq）
  ↓
消息 Store：按会话规范化存储 byId + ids，外部 store + selector
  ↓
发送：本地临时消息（pending）→ ack 后替换 → 失败可重试
  ↓
列表：不定高虚拟列表、反向滚动、向上加载保持滚动位置
  ↓
渲染：消息气泡 memo，图片懒加载并预留尺寸
```

**关键设计**

- 消息按 seq 排序，用 messageId 去重
- 乐观发送 + ack 确认 + 失败重试
- 向上加载历史时记录 scrollHeight 差值，恢复滚动位置
- 新消息到达时：在底部则自动滚动，否则显示「有新消息」提示
- 图片预留宽高，避免布局抖动影响虚拟列表测量
- 后台标签页降低渲染频率，批量合并更新

**口述模板（2–3 分钟）**

连接层负责 WebSocket 心跳、重连和消息去重排序。消息以会话为单位规范化存储在外部 store，组件通过 selector 订阅当前会话。发送消息先插入本地 pending 消息，服务端 ack 后替换，失败可重试。列表使用不定高虚拟列表，向上加载历史时保持滚动位置；用户在底部时新消息自动滚动，否则提示新消息。大量消息涌入时批量合并更新，避免频繁渲染。

**扩展追问**

- 断线期间消息如何补齐？→ 重连后携带最后 seq 拉取增量。

### S8. 设计 React 应用首屏性能优化方案

- **难度**: senior
- **标签**: 性能, Web Vitals

**澄清问题**

- 当前指标：LCP、INP、CLS、JS 体积？
- CSR、SSR 还是 RSC？
- 用户网络和设备分布？

**参考方案**

```text
测量：RUM（web-vitals 上报）+ Lighthouse + Profiler
  ↓
渲染模式：CSR → SSR/流式 → RSC，按页面类型选择
  ↓
资源：路由分割、依赖瘦身、按需加载、modulepreload、图片优化（fetchpriority）
  ↓
数据：服务端并行取数、消除瀑布、缓存
  ↓
运行时：减少首屏渲染量、延迟非关键组件、Activity 预渲染下一页
  ↓
回归：性能预算（bundle size CI 检查）+ 线上告警
```

**关键设计**

- 先用 RUM 数据确认问题，按页面分级优化
- LCP：主图优先加载、关键 CSS、服务端渲染首屏内容
- INP：拆分长任务、Transition、减少水合成本（RSC 降低需要水合的组件）
- CLS：图片和广告预留尺寸、字体 `font-display` 与尺寸调整
- 构建产物分析（bundle analyzer），设置体积预算

**口述模板（2–3 分钟）**

先用 RUM 采集真实用户的 LCP、INP、CLS，找到最差的页面和环节。加载方面，根据页面选择渲染模式，内容型页面用 SSR 或 RSC 流式输出，减少客户端 JS；路由分割、依赖瘦身、主图高优先级加载。数据方面，在服务端并行请求，消除组件级瀑布。运行时方面，延迟非关键组件，长任务拆分，非紧急更新用 Transition。最后用性能预算和线上告警防止回归，并用数据对比优化前后效果。

**扩展追问**

- 如何证明优化有效？→ A/B 或发布前后对比 RUM 指标 P75，并关联业务指标（转化率、跳出率）。
