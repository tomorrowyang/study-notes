> 回答结构：澄清需求与量级 → 架构图 → 核心流程 → 数据存储 → 扩展性 → 可靠性 → 可观测性 → 演进。

### S1. 设计一个高并发短链服务

- **难度**: senior
- **标签**: 高并发, 缓存

**澄清问题**

- 日生成量和日访问量？（如生成 100 万/天，访问 1 亿/天）
- 短链是否需要过期、自定义、统计？
- 跳转用 301 还是 302？

**参考方案**

```text
生成：Client → API(Node) → ID 生成（号段 / Snowflake）→ Base62 编码 → MySQL
访问：Client → CDN/网关 → Node 跳转服务
                     ├─ 进程内 LRU（热点）
                     ├─ Redis（全量热数据）
                     └─ MySQL（兜底）
统计：跳转时异步写 MQ → 消费者聚合 → ClickHouse
```

**关键设计**

- ID：数据库号段模式或 Snowflake，Base62 编码 7 位约 3.5 万亿
- 跳转用 302（需要统计）；301 会被浏览器缓存，统计不到
- 读多写少：多级缓存，布隆过滤器防止不存在短链穿透
- 统计异步化：不阻塞跳转响应
- 防滥用：生成接口限流、恶意 URL 检测

**口述模板（2–3 分钟）**

短链服务读远大于写。生成时通过号段模式获取全局唯一 ID，Base62 编码后存 MySQL。访问路径是性能关键：Node 跳转服务先查进程内 LRU，再查 Redis，最后查数据库，并用布隆过滤器防止恶意不存在短链穿透。跳转使用 302 以便统计，统计信息投递 MQ 异步处理写入 ClickHouse。Node 服务无状态，水平扩展；生成接口限流并检测恶意链接。

**扩展追问**

- 同一个长链接重复生成怎么办？→ 对长链接哈希建唯一索引，命中则返回已有短链（视需求而定）。

### S2. 设计 Node BFF / API 网关层

- **难度**: senior
- **标签**: BFF, 网关

**澄清问题**

- 前端有几个端？后端服务有多少？
- 是否承担 SSR？
- 鉴权方式、QPS 量级？

**参考方案**

```text
Client
  ↓
网关（Nginx / API Gateway）：TLS、限流、WAF
  ↓
Node BFF
  ├─ 中间件：traceId、鉴权、日志、超时、错误统一
  ├─ 聚合层：并行调用下游 + DataLoader 合并 + 部分失败降级
  ├─ 缓存层：LRU + Redis
  └─ 下游客户端：连接池、熔断、重试（仅幂等）
  ↓
微服务（用户、订单、商品…）
```

**关键设计**

- 每个下游独立超时、熔断、连接池（舱壁隔离）
- 聚合接口按模块重要性降级：核心失败报错，非核心返回空
- 下游接口契约用 OpenAPI / gRPC IDL 生成类型
- BFF 只做聚合和适配，不写领域逻辑
- 全链路追踪：OpenTelemetry

**口述模板（2–3 分钟）**

BFF 位于网关和微服务之间，负责鉴权、聚合、裁剪和协议适配。请求进来先经过中间件建立 traceId 上下文、鉴权和超时控制。聚合层并行调用下游，用 DataLoader 合并相同请求，每个下游有独立的连接池、超时和熔断器，非核心模块失败时降级返回。热点数据进程内缓存加 Redis。BFF 保持无状态水平扩展，并用 OpenTelemetry 追踪到每个下游调用的耗时。

**扩展追问**

- BFF 会不会成为性能瓶颈？→ 无状态可水平扩展；关键是控制序列化成本和下游并发。

### S3. 设计 WebSocket 实时推送服务（支持百万连接）

- **难度**: senior
- **标签**: WebSocket, 扩展

**澄清问题**

- 在线连接数？消息频率？
- 单播、群组还是广播？
- 是否需要离线消息、送达确认？

**参考方案**

```text
Client ──WSS──> LB（支持长连接，按连接负载）
                 ↓
         Node 网关集群（每实例 5–10 万连接）
           ├─ 连接管理：userId → socket（本地 Map）
           ├─ 心跳、鉴权、限流
           └─ 订阅 Redis Pub/Sub 或 MQ 频道
                 ↑
业务服务 → 路由服务（userId → 网关实例，存 Redis）→ 定向投递
离线消息：存储服务（Redis / DB），上线后拉取
```

**关键设计**

- 连接层与业务层分离，网关只做连接和转发
- 路由表记录用户所在实例，定向投递而不是全量广播
- 心跳检测死连接，客户端指数退避重连
- 消息带 seq，客户端去重和补拉
- 发布时让客户端优雅迁移，避免重连风暴（随机延迟）
- 调优：文件描述符上限、内核 TCP 参数、每连接内存

**口述模板（2–3 分钟）**

我会把连接网关和业务服务分离。Node 网关集群负责维持 WebSocket 连接、鉴权和心跳，本地维护用户到连接的映射，并把用户所在实例写入 Redis 路由表。业务服务推送时先查路由，再通过 MQ 或 Redis 频道投递到对应网关实例。消息带递增 seq，客户端断线重连后按 seq 补拉离线消息。扩容时网关水平扩展，发布时分批断开并让客户端随机延迟重连，避免重连风暴。

**扩展追问**

- 单机能撑多少连接？→ 取决于内存（每连接几十 KB）、fd 上限和消息频率，需要压测确定。

### S4. 设计分布式定时任务与异步任务系统

- **难度**: senior
- **标签**: 任务队列

**澄清问题**

- 任务类型：定时任务、延迟任务、即时异步任务？
- 任务量与执行时长？
- 是否要求恰好一次？

**参考方案**

```text
API / 业务 → 任务队列（BullMQ on Redis / Kafka）
               ├─ 延迟队列（ZSET 按执行时间）
               ├─ 重复任务（cron）
               └─ 优先级队列
                     ↓
              Worker 集群（Node 进程）
               ├─ 并发控制、限速
               ├─ 超时、重试（指数退避）、死信队列
               └─ 幂等执行
                     ↓
              任务状态存储 + 监控面板（Bull Board）
```

**关键设计**

- 多实例定时任务避免重复执行：由队列统一调度（重复任务）或分布式锁
- 任务处理幂等，允许至少一次投递
- 长任务定期上报进度、可取消
- 失败重试有上限，最终进死信队列人工处理
- Worker 优雅关闭：停止拉取新任务，完成当前任务

**口述模板（2–3 分钟）**

任务系统以队列为核心。业务通过 API 提交任务，延迟任务按执行时间放入有序集合，cron 任务由队列统一调度，避免多实例重复触发。Worker 集群拉取任务，控制并发和速率，执行时有超时和重试，最终失败进入死信队列。所有任务处理必须幂等。Worker 收到关闭信号后停止拉取并完成当前任务。监控面板展示积压量、失败率和耗时，积压超过阈值时告警并扩容 Worker。

**扩展追问**

- Redis 宕机任务会丢吗？→ 开启持久化与主从；关键任务在数据库记录状态，可补偿重放。

### S5. 设计大文件上传与处理服务

- **难度**: senior
- **标签**: 上传, Stream

**澄清问题**

- 文件大小与类型？是否需要转码、缩略图？
- 是否需要断点续传、秒传？
- 存储：自建还是对象存储？

**参考方案**

```text
Client
  ├─ 1. 初始化：文件 hash、大小 → Node 返回 uploadId + 已上传分片 + 预签名 URL
  ├─ 2. 分片直传对象存储（S3/OSS Multipart Upload）
  └─ 3. 完成：Node 调用 CompleteMultipartUpload
                ↓
          MQ 事件 → 处理 Worker（转码 / 缩略图 / 病毒扫描）
                ↓
          更新状态 → 通知客户端（WebSocket / 轮询）
```

**关键设计**

- 文件数据不经过 Node，Node 只负责签名和元数据
- 秒传：hash 已存在直接关联
- 断点续传：查询已完成分片列表
- 处理流程异步化，Worker 使用 Stream 和子进程（ffmpeg）
- 校验：大小上限、类型魔数、病毒扫描
- 清理：未完成的分片上传定期清理（生命周期规则）

**口述模板（2–3 分钟）**

大文件上传我会采用前端直传对象存储的方案。客户端先计算文件 hash 请求初始化，Node 服务检查是否可秒传，否则创建分片上传任务并返回预签名 URL 和已上传分片。客户端并发上传剩余分片，完成后通知 Node 合并。上传完成事件投递到 MQ，由 Worker 异步执行转码、缩略图和安全扫描，处理结果通过 WebSocket 通知前端。Node 不承载文件流量，资源消耗可控。

**扩展追问**

- 如果必须经过 Node 上传？→ 流式解析 multipart 并直接 pipeline 到对象存储，限制大小和并发。

### S6. 设计 Node 服务的可观测性平台接入

- **难度**: senior
- **标签**: 可观测性

**澄清问题**

- 服务数量与调用链复杂度？
- 已有基础设施（Prometheus、ELK、Jaeger）？
- 采样和存储成本预算？

**参考方案**

```text
Node 服务
  ├─ --import ./otel.js（OpenTelemetry SDK + 自动埋点）
  ├─ 日志：pino JSON → stdout → Fluent Bit → ES / Loki
  ├─ 指标：RED + 事件循环延迟 + GC + 堆 → Prometheus
  └─ 追踪：OTLP → Collector → Jaeger / Tempo
                ↓
        Grafana 统一看板 + SLO 告警
```

**关键设计**

- 所有日志带 traceId，可从日志跳转到 trace
- Node 特有指标：事件循环延迟 P99、ELU、heapUsed、GC 暂停、活跃句柄
- 追踪采样：头部采样 + 错误 / 慢请求尾部采样
- 告警基于 SLO 和错误预算，避免告警风暴
- 按需诊断：信号触发 heap snapshot / CPU profile

**口述模板（2–3 分钟）**

我会用 OpenTelemetry 统一接入：启动时预加载 SDK 自动埋点 HTTP、数据库和 Redis，追踪数据经 Collector 进入 Jaeger 或 Tempo。日志用 pino 输出 JSON 到 stdout，自动附带 traceId。指标除了请求速率、错误率和延迟分位数外，重点采集事件循环延迟、GC 和堆内存。看板统一在 Grafana，告警基于 SLO。线上需要深度诊断时通过信号触发 CPU profile 和 heap snapshot。

**扩展追问**

- 全量追踪成本太高怎么办？→ 低比例头部采样，加上对错误和慢请求的尾部采样。

### S7. 设计秒杀活动的 Node 服务层

- **难度**: senior
- **标签**: 高并发, 一致性

**澄清问题**

- 峰值 QPS、库存数量？
- 是否允许超卖？（不允许）
- 下单后支付超时如何处理？

**参考方案**

```text
CDN：静态页面、倒计时
  ↓
网关：限流、黑名单、验证码 / 令牌
  ↓
Node 秒杀服务
  ├─ 资格校验（活动时间、用户限购）
  ├─ Redis Lua 原子扣减预库存（失败直接返回售罄）
  └─ 成功 → 投递 MQ（订单创建消息）立即返回「排队中」
  ↓
订单服务（消费 MQ）：创建订单、扣减数据库库存（乐观锁）
  ↓
支付超时 → 延迟消息 → 取消订单、回补库存
```

**关键设计**

- 层层过滤：CDN、网关限流、令牌、本地售罄标记、Redis 预扣
- Redis Lua 原子判断并扣减，防止超卖
- 下单异步化，MQ 削峰
- 数据库最终扣减使用乐观锁 / 条件更新 `stock > 0`
- 幂等：用户 + 活动维度唯一约束
- 本地内存售罄标记，减少 Redis 压力

**口述模板（2–3 分钟）**

秒杀的核心是把流量逐层削减，保护数据库。静态资源走 CDN，网关做限流和人机校验。Node 秒杀服务先校验资格，再用 Redis Lua 原子扣减预库存，失败立即返回售罄，并在本地标记售罄减少后续请求。扣减成功后投递 MQ 并立即返回排队中，订单服务异步消费创建订单，数据库用条件更新保证不超卖，用户维度唯一约束保证幂等。支付超时通过延迟消息取消订单并回补库存。

**扩展追问**

- Redis 扣减成功但 MQ 投递失败？→ 本地重试 + 失败回补库存；或记录 Outbox 由定时任务补偿。

### S8. 设计 SSR 渲染服务（Node 渲染集群）

- **难度**: senior
- **标签**: SSR, 性能

**澄清问题**

- 页面类型（内容型 / 交易型）与 QPS？
- 个性化程度？
- 渲染失败的降级要求？

**参考方案**

```text
CDN（缓存可缓存页面，stale-while-revalidate）
  ↓
Node SSR 集群
  ├─ 数据预取：并行请求 BFF，超时控制
  ├─ 流式渲染（renderToPipeableStream）
  ├─ 页面级 / 组件级缓存（Redis / LRU）
  ├─ 监控：渲染耗时、事件循环延迟、内存
  └─ 降级：超时或错误 → 返回 CSR 空壳
  ↓
BFF / 后端服务
```

**关键设计**

- SSR 是 CPU 密集，事件循环延迟是核心指标；按 CPU 扩容
- 流式渲染先输出外壳，改善 TTFB
- 可缓存页面在 CDN 缓存；个性化部分客户端补齐或流式填充
- 防止跨请求状态污染：store 按请求创建，避免模块级单例保存用户数据
- 内存泄漏防护：定期巡检，必要时滚动重启
- 熔断降级：负载过高时直接返回 CSR 页面

**口述模板（2–3 分钟）**

SSR 服务是 CPU 密集型 Node 服务。可缓存页面优先由 CDN 缓存，回源时 Node 并行预取数据并流式渲染，尽早输出页面外壳。个性化内容通过 Suspense 流式填充或客户端补齐。每个请求创建独立的状态容器，避免跨请求数据泄漏。核心监控指标是事件循环延迟和渲染耗时，按 CPU 水平扩容。负载过高或渲染超时时降级返回 CSR 空壳，保证可用性。

**扩展追问**

- 为什么 SSR 服务容易内存泄漏？→ 模块级缓存、全局单例保存请求数据、第三方库在服务端注册全局监听。
