> 目标：能从运行时原理解释线上现象，能用数据驱动排查性能和内存问题，能设计稳定、安全、可观测的 Node 服务。

## 一、运行时原理

### Q1. Node.js 的整体架构是什么？

- **难度**: senior
- **标签**: 架构, 原理

**答案**

```text
┌────────────────────────────────────────┐
│     用户代码 / npm 包（JavaScript）      │
├────────────────────────────────────────┤
│  Node.js 标准库（lib/*.js：fs、http…）   │
├────────────────────────────────────────┤
│  Bindings（C++）：连接 JS 与底层库       │
├──────────────┬─────────────────────────┤
│  V8          │  libuv                   │
│  JS 执行/JIT │  事件循环、线程池、       │
│  GC          │  异步 I/O、定时器         │
├──────────────┴─────────────────────────┤
│ 其他：llhttp、OpenSSL、zlib、c-ares、ICU、Undici、simdutf │
└────────────────────────────────────────┘
```

一次 `fs.readFile` 链路：JS API → C++ binding → libuv 把任务交给线程池 → 线程执行系统调用 → 完成后通知事件循环 → poll 阶段执行 JS 回调。

**口述模板（30–60 秒）**

1. 一句话结论：Node = V8 + libuv + C++ bindings + 标准库。
2. 关键机制：V8 执行 JS，libuv 提供事件循环和异步 I/O。
3. 注意点：网络 I/O 走系统多路复用，文件 I/O 走线程池。
4. 可追问时补充：N-API 原生扩展。

**常见追问**

- 为什么文件 I/O 不用 epoll？→ 普通文件在 Linux 上总是「就绪」，epoll 无效，因此 libuv 用线程池模拟异步（新内核可用 io_uring）。

### Q2. poll 阶段会阻塞多久？

- **难度**: senior
- **标签**: 事件循环, libuv

**答案**

poll 阶段计算超时时间：

- 有 `setImmediate` 待执行 → 不阻塞（超时 0）
- 有到期或即将到期的定时器 → 阻塞到最近定时器到期
- 没有定时器、但有活跃句柄（如监听的 server）→ 无限等待 I/O
- 没有任何活跃句柄和请求 → 事件循环退出

这解释了为什么空闲的 Node 服务 CPU 占用接近 0：它阻塞在 epoll_wait 上。

`timer.unref()` / `server.unref()` 可让句柄不阻止进程退出。

**口述模板（30–60 秒）**

1. 一句话结论：poll 阶段阻塞时间由 setImmediate 和最近定时器决定。
2. 关键机制：没有事做时阻塞在系统 I/O 多路复用等待中。
3. 注意点：活跃句柄决定进程是否退出。
4. 可追问时补充：unref 的用途。

**常见追问**

- 为什么脚本执行完进程不退出？→ 存在未关闭的句柄（定时器、socket、数据库连接）；可用 `process.getActiveResourcesInfo()` 排查。

### Q3. V8 内存结构是怎样的？容器中如何配置内存？

- **难度**: senior
- **标签**: 内存, V8

**答案**

V8 堆：

- **新生代**：短生命周期对象，Scavenge 复制回收，速度快
- **老生代**：长生命周期对象，标记清除 + 整理
- **大对象空间、代码空间**等

堆外内存：Buffer / ArrayBuffer、原生模块内存。

关键参数：

```bash
node --max-old-space-size=1536 app.js      # 老生代上限（MB）
node --max-semi-space-size=64 app.js       # 新生代半空间，可减少高分配场景的 Scavenge 次数
```

容器中：

- 新版 Node 会根据 cgroup 内存限制推算默认堆上限，但仍建议显式配置
- `max-old-space-size` 设为容器内存的 60–75%，为堆外内存、线程栈、原生库留余量
- 否则可能出现：V8 认为还能分配，但容器已触发 OOMKilled（无 JS 堆栈）

**口述模板（30–60 秒）**

1. 一句话结论：V8 分新生代和老生代，堆外内存单独计算。
2. 关键机制：分代回收，按对象存活时间采用不同算法。
3. 注意点：容器限制要大于堆上限并留余量。
4. 可追问时补充：OOMKilled 与 JS heap out of memory 的区别。

**常见追问**

- 「JavaScript heap out of memory」和「OOMKilled」区别？→ 前者是 V8 堆达到上限，后者是进程总内存超过容器限制被内核杀死。

### Q4. 如何解读 process.memoryUsage()？

- **难度**: senior
- **标签**: 内存

**答案**

| 指标 | 含义 |
|------|------|
| `rss` | 进程常驻物理内存总量（堆 + 堆外 + 代码 + 栈） |
| `heapTotal` | V8 已申请的堆大小 |
| `heapUsed` | V8 堆实际使用量 |
| `external` | V8 管理对象关联的 C++ 内存（含 Buffer） |
| `arrayBuffers` | ArrayBuffer 和 Buffer 内存（包含在 external 中） |

判断：

- `heapUsed` 持续上涨且 GC 后不回落 → JS 对象泄漏
- `rss` 上涨但 `heapUsed` 平稳 → 堆外泄漏（Buffer、原生模块）或内存碎片
- `external` 上涨 → Buffer 未释放（如流未正确消费）

`process.memoryUsage.rss()` 开销更小，适合高频采样。

**口述模板（30–60 秒）**

1. 一句话结论：rss 是总量，heapUsed 是 JS 对象，external 是堆外。
2. 关键机制：区分堆内和堆外泄漏。
3. 注意点：rss 高不一定是泄漏，要看趋势。
4. 可追问时补充：glibc 内存碎片可用 jemalloc 缓解。

**常见追问**

- GC 后 rss 为什么不下降？→ 内存分配器可能保留已释放内存以便复用，不立即归还操作系统。

## 二、性能排障

### Q5. 生产环境如何排查内存泄漏？

- **难度**: senior
- **标签**: 内存泄漏, 排障

**答案**

流程：

1. **确认**：监控 heapUsed / rss 在稳定流量下持续上升，GC 后不回落，最终 OOM 重启
2. **复现**：压测或回放流量（autocannon / k6）
3. **采集**：
   - 间隔拍摄多个 heap snapshot（`--heapsnapshot-signal=SIGUSR2` 或 `v8.writeHeapSnapshot()`）
   - `--heapsnapshot-near-heap-limit=2` 在接近上限时自动拍快照
4. **分析**：Chrome DevTools 对比快照，按 Retained Size 排序，查看 Retainers 引用链
5. **修复验证**：上线后观察曲线

常见原因：

- 无上限的 Map / 数组缓存（用 LRU + TTL）
- 每个请求注册的事件监听器未移除
- 定时器闭包持有大对象
- 全局保存请求对象
- 未结束的 Promise 链长期持有上下文
- Stream 未消费导致 Buffer 堆积

注意：拍快照会暂停进程且需要额外内存，生产中应先摘流量。

**口述模板（30–60 秒）**

1. 一句话结论：监控确认 → 复现 → 多次快照对比 → 引用链定位。
2. 关键机制：泄漏是无用对象仍被 GC Root 引用。
3. 注意点：快照会阻塞进程，在摘流量的实例上执行。
4. 可追问时补充：堆外泄漏排查。

**常见追问**

- 讲一次真实的泄漏案例？→ 用「现象 → 指标 → 快照中发现什么 → 根因 → 修复 → 效果」结构讲述。

### Q6. CPU 飙高如何排查？

- **难度**: senior
- **标签**: CPU, 性能

**答案**

1. 确认是哪个进程、是用户态还是 GC（`--trace-gc` 观察 GC 频率）
2. 采集 CPU Profile：
   - `node --cpu-prof app.js` 退出时生成 `.cpuprofile`
   - 运行中通过 `--inspect` 连接 DevTools 录制
   - Linux `perf` + `--perf-basic-prof`
3. 生成火焰图（DevTools、speedscope、0x、Clinic Flame）
4. 找最宽的「平顶」函数

常见原因：

- 正则回溯（ReDoS）
- 大 JSON 序列化
- 死循环、无退出条件的重试
- 频繁 GC（短时间大量对象分配）
- 同步加密 / 压缩
- 日志过多

**口述模板（30–60 秒）**

1. 一句话结论：CPU Profile + 火焰图定位热点函数。
2. 关键机制：采样调用栈，宽度表示耗时占比。
3. 注意点：区分业务 CPU 和 GC CPU。
4. 可追问时补充：Clinic.js 自动诊断。

**常见追问**

- 火焰图怎么看？→ 横轴是占用时间比例（不是时间顺序），纵轴是调用栈，找顶部宽块。

### Q7. 发布后 P99 延迟翻倍，如何排查？

- **难度**: senior
- **标签**: 性能, 排障

**答案**

系统化排查：

1. **范围**：所有接口还是部分接口？所有实例还是部分？与发布时间是否吻合？
2. **对比**：新旧版本 diff（依赖升级、Node 版本、配置变化）
3. **事件循环**：事件循环延迟是否升高 → 主线程有同步阻塞
4. **下游**：数据库、Redis、外部 API 延迟是否升高；连接池是否排队
5. **资源**：CPU、内存、GC 暂停、容器 CPU throttling
6. **线程池**：大量 fs / crypto 是否占满线程池
7. **采集证据**：CPU Profile、Trace 中最慢 span
8. **止血**：回滚优先，再定位根因

**口述模板（30–60 秒）**

1. 一句话结论：先回滚止血，再按事件循环、下游、资源、线程池逐层排查。
2. 关键机制：P99 敏感于偶发阻塞和排队。
3. 注意点：容器 CPU limit 导致 throttling 很常见。
4. 可追问时补充：分布式追踪定位最慢 span。

**常见追问**

- 为什么平均延迟正常但 P99 很高？→ 偶发的长任务、GC 暂停或连接池排队只影响部分请求。

### Q8. 高并发 HTTP 服务如何调优？

- **难度**: senior
- **标签**: 性能, HTTP

**答案**

- **架构**：多副本水平扩展，无状态设计
- **连接**：入站 keep-alive 超时大于 LB；出站使用连接池（Undici Pool / Agent）
- **序列化**：Fastify schema 序列化；避免大 JSON
- **缓存**：多级缓存（进程内 LRU + Redis），请求合并
- **数据库**：连接池大小、索引、批量查询、读写分离
- **CPU**：避免同步代码，热点函数优化，Worker 处理计算
- **压缩**：在网关层压缩，减少 Node CPU 负担
- **限流与降级**：保护下游，防止雪崩
- **压测**：autocannon / k6，对比优化前后 QPS 和 P99

**口述模板（30–60 秒）**

1. 一句话结论：扩副本、复用连接、减少序列化和阻塞、缓存与保护下游。
2. 关键机制：Node 吞吐受主线程 CPU 时间限制。
3. 注意点：先压测找瓶颈，不要盲目优化。
4. 可追问时补充：网关卸载 TLS 和压缩。

**常见追问**

- 单个 Node 实例 QPS 上不去，CPU 也不高？→ 可能是下游或连接池排队、线程池饱和或 DNS 解析瓶颈。

### Q9. cluster 和多容器副本怎么选？

- **难度**: senior
- **标签**: 部署, 扩展

**答案**

| | cluster | 多容器副本 |
|--|---------|------------|
| 进程管理 | 应用自己管理 | 编排平台管理 |
| 资源隔离 | 同一容器共享 | 每个副本独立限制 |
| 监控 | 需要聚合多个进程指标 | 天然按 Pod 维度 |
| 扩缩容 | 受单机核数限制 | 按负载自动扩缩 |
| 故障影响 | 主进程故障影响全部 | 单 Pod 故障影响小 |

推荐：K8s 环境一容器一 Node 进程，CPU request 1 核左右，按副本扩展。

**口述模板（30–60 秒）**

1. 一句话结论：容器环境优先多副本，虚机环境用 cluster。
2. 关键机制：编排平台提供更好的隔离和弹性。
3. 注意点：cluster 在容器中会让内存限制和信号处理复杂。
4. 可追问时补充：CPU 限制与 throttling。

**常见追问**

- 单 Node 进程给多少 CPU 合适？→ 主线程只能用一个核，request 约 1 核，limit 略高给 GC 和线程池留余量。

### Q10. 如何设计 Worker 线程池？

- **难度**: senior
- **标签**: worker_threads

**答案**

要点：

- 固定线程数（≈ CPU 核数 - 1）
- 有界任务队列，队列满时拒绝或降级（背压）
- 任务超时与取消（终止并重建线程）
- 线程异常后自动重建
- 大数据使用 Transferable 或 SharedArrayBuffer 减少复制
- 指标：队列长度、任务耗时、线程利用率

生产推荐 Piscina。

**口述模板（30–60 秒）**

1. 一句话结论：固定线程 + 有界队列 + 超时 + 自愈。
2. 关键机制：任务分发给空闲线程，忙时排队。
3. 注意点：无界队列会把内存压力转移到主线程。
4. 可追问时补充：手写简易线程池。

**常见追问**

- 数据传给 Worker 会复制吗？→ 默认结构化克隆复制；ArrayBuffer 可转移所有权。

## 三、分布式与可靠性

### Q11. 微服务间通信方式如何选？

- **难度**: senior
- **标签**: 微服务

**答案**

| 方式 | 特点 | 场景 |
|------|------|------|
| HTTP/JSON | 简单通用，可读性好 | 对外 API、BFF |
| gRPC | 二进制、强类型 IDL、HTTP/2 流 | 内部高性能调用 |
| 消息队列 | 异步解耦、削峰、可重放 | 事件驱动、最终一致性 |
| GraphQL | 前端按需取数 | BFF 聚合层 |

可靠性措施：超时、重试（指数退避 + 抖动 + 预算）、熔断、限流、幂等、链路追踪。

**口述模板（30–60 秒）**

1. 一句话结论：同步调用用 HTTP/gRPC，异步解耦用 MQ。
2. 关键机制：同步调用链越长，可用性越低。
3. 注意点：重试要配合幂等和熔断。
4. 可追问时补充：事件驱动与 Outbox 模式。

**常见追问**

- 服务 A 调 B 超时但 B 实际执行成功怎么办？→ 依赖幂等键和查询接口，或改为异步消息 + 状态回调。

### Q12. 如何实现分布式锁？有哪些坑？

- **难度**: senior
- **标签**: 分布式锁, Redis

**答案**

Redis 实现：

```text
加锁：SET lock:order:1 <uniqueToken> NX PX 30000
解锁：Lua 脚本，只有 value 等于自己的 token 才删除
```

坑：

- 不设置过期时间：持有者崩溃导致死锁
- 解锁不校验 token：误删别人的锁
- 业务执行超过过期时间：锁提前释放，需要续期（看门狗）
- 主从切换可能丢锁：对正确性要求高时使用 fencing token（单调递增版本号）或数据库约束

很多场景可以用数据库唯一约束、乐观锁替代分布式锁。

**口述模板（30–60 秒）**

1. 一句话结论：SET NX PX + 唯一 token + Lua 解锁。
2. 关键机制：过期时间防死锁，token 防误删。
3. 注意点：锁过期与业务耗时、主从切换。
4. 可追问时补充：fencing token。

**常见追问**

- Redlock 可靠吗？→ 存在争议（时钟漂移、GC 暂停），强一致需求用 fencing token 或数据库层保证。

### Q13. 消息队列在 Node 中如何使用？如何保证不丢不重？

- **难度**: senior
- **标签**: 消息队列

**答案**

Node 常用：BullMQ（Redis）、Kafka（kafkajs / Confluent 客户端）、RabbitMQ（amqplib）。

不丢：

- 生产者确认（ack / acks=all）
- 持久化
- 消费者处理成功后再手动提交 offset / ack
- 业务写库与发消息一致：Outbox 模式

不重：

- MQ 通常保证「至少一次」，重复不可避免
- 消费者实现幂等（消息 ID 去重表、唯一约束）

其他：死信队列、重试退避、消费并发控制、积压告警。

**口述模板（30–60 秒）**

1. 一句话结论：确认 + 持久化 + 手动提交保证不丢，幂等消费处理重复。
2. 关键机制：至少一次投递 + 幂等 = 效果上的恰好一次。
3. 注意点：先提交 offset 再处理会丢消息。
4. 可追问时补充：Outbox 与事务消息。

**常见追问**

- Node 消费 Kafka 如何控制并发？→ 按分区并发，分区内保持顺序；处理慢时控制 in-flight 数量。

### Q14. 熔断、降级、重试如何配合？

- **难度**: senior
- **标签**: 稳定性

**答案**

- **超时**：每次调用的上限
- **重试**：只对幂等请求和临时错误；指数退避 + 抖动；全局重试预算（如不超过请求量的 10%）
- **熔断**：失败率超过阈值时打开，快速失败；一段时间后半开试探
- **降级**：熔断或超时时返回缓存、默认值或简化功能
- **舱壁隔离**：不同下游使用独立连接池 / 并发配额，避免一个慢下游拖垮全部

Node 库：opossum（熔断）、p-retry、cockatiel。

**口述模板（30–60 秒）**

1. 一句话结论：超时兜底、重试有预算、熔断快速失败、降级保证核心体验。
2. 关键机制：熔断三状态：关闭、打开、半开。
3. 注意点：重试风暴会放大故障。
4. 可追问时补充：舱壁隔离。

**常见追问**

- 重试为什么要加抖动？→ 避免大量客户端同时重试形成脉冲流量。

## 四、安全

### Q15. Node 服务常见安全漏洞有哪些？

- **难度**: senior
- **标签**: 安全

**答案**

| 漏洞 | 示例 | 防御 |
|------|------|------|
| SQL / NoSQL 注入 | 字符串拼接 SQL；MongoDB 传入 `{ $gt: '' }` | 参数化查询、schema 校验类型 |
| 命令注入 | `exec(\`convert ${file}\`)` | execFile + 参数数组、白名单 |
| 路径穿越 | `../../etc/passwd` | resolve 后校验前缀、生成文件名 |
| SSRF | 服务端请求用户提供的 URL 访问内网 | URL 白名单、禁止内网 IP、DNS 重绑定防护 |
| 原型污染 | 深合并 `__proto__` | 过滤危险键、Map、schema 校验 |
| ReDoS | 嵌套量词正则匹配用户输入 | 安全正则、限制输入长度、RE2 |
| 反序列化 | 不安全的 serialize 库 | 只用 JSON |
| 敏感信息泄漏 | 错误堆栈返回给客户端 | 生产返回通用错误 |

另外：Helmet 设置安全头、限流防暴力破解、依赖漏洞扫描。

**口述模板（30–60 秒）**

1. 一句话结论：一切外部输入都不可信，按注入、文件、网络、对象四类防护。
2. 关键机制：参数化、白名单、校验、隔离。
3. 注意点：Node 进程拥有完整系统权限，漏洞危害更大。
4. 可追问时补充：Permission Model 最小权限。

**常见追问**

- 如何防止路径穿越？→ `path.resolve(root, input)` 后检查结果是否以 `root + path.sep` 开头。

### Q16. npm 供应链安全如何保障？

- **难度**: senior
- **标签**: 安全, 供应链

**答案**

风险：恶意包、依赖被投毒（账号被盗后发布恶意版本）、typosquatting、install 脚本窃取凭证。近年多次出现大规模 npm 投毒和自传播蠕虫事件，窃取开发者和 CI 中的 token。

措施：

- 提交 lockfile，CI 使用 `npm ci` / `pnpm install --frozen-lockfile`
- 禁用或审核 install 脚本（pnpm 默认不执行依赖的 postinstall，需显式允许）
- 设置新版本最短发布时间后才安装（如 pnpm `minimumReleaseAge`），规避刚被投毒的版本
- `npm audit`、Snyk、Socket 等扫描
- 私有镜像源和依赖白名单
- 发布侧：2FA、Trusted Publishing（OIDC）、provenance 签名
- CI 中最小化 token 权限

**口述模板（30–60 秒）**

1. 一句话结论：锁定版本、限制安装脚本、扫描漏洞、保护发布凭证。
2. 关键机制：依赖树中任何一个包都能在安装时执行代码。
3. 注意点：CI 环境变量中的 token 是攻击目标。
4. 可追问时补充：延迟安装新版本策略。

**常见追问**

- `npm audit` 能发现投毒吗？→ 只能发现已披露漏洞，零日投毒需要行为分析工具和延迟策略。

### Q17. Node 的 Permission Model 是什么？

- **难度**: senior
- **标签**: 安全

**答案**

通过 `--permission` 启用后，进程默认禁止文件系统、子进程、Worker、原生扩展等能力，需要显式授权：

```bash
node --permission \
  --allow-fs-read=/app \
  --allow-fs-write=/app/tmp \
  app.js
```

运行时检查：`process.permission.has('fs.write', '/app/tmp')`。

价值：限制被入侵或恶意依赖的破坏范围（纵深防御）。

局限：不是完整沙箱；不能替代容器隔离、最小权限用户和网络策略。

**口述模板（30–60 秒）**

1. 一句话结论：Node 内置最小权限机制，按需授权资源访问。
2. 关键机制：启动参数声明允许的路径和能力。
3. 注意点：它是纵深防御，不是安全边界本身。
4. 可追问时补充：结合容器只读文件系统和非 root 用户。

**常见追问**

- 第三方依赖试图读取 `~/.ssh` 会怎样？→ 未授权路径会抛出权限错误。

## 五、可观测性与上下文

### Q18. AsyncLocalStorage 的原理和性能？

- **难度**: senior
- **标签**: 异步上下文

**答案**

- 早期基于 `async_hooks`：在异步资源创建时复制当前上下文，回调执行时恢复；hooks 开销较大
- Node 24 起默认基于 **AsyncContextFrame**：上下文作为帧随 V8 的 continuation 传播，性能显著提升
- 与 TC39 提案 `AsyncContext` 方向一致，未来可能成为语言标准

注意：

- `enterWith` 会影响当前同步执行的剩余部分，容易造成上下文泄漏，优先 `run`
- 连接池、自定义队列等「回调在别处执行」的场景可能丢失上下文，需要 bind

**口述模板（30–60 秒）**

1. 一句话结论：ALS 让异步链路共享上下文，Node 24 起实现更高效。
2. 关键机制：上下文随异步延续传播。
3. 注意点：自定义调度器可能丢上下文。
4. 可追问时补充：TC39 AsyncContext。

**常见追问**

- 为什么不推荐直接用 async_hooks？→ API 底层、性能开销大，且大部分场景 ALS 已足够。

### Q19. 如何为 Node 服务建设可观测性？

- **难度**: senior
- **标签**: 可观测性

**答案**

三大支柱：

- **日志**：结构化 JSON、traceId、级别、脱敏
- **指标（Metrics）**：
  - RED：请求速率、错误率、延迟分位数
  - 运行时：事件循环延迟、ELU、heapUsed、GC 时间、活跃句柄数
  - 资源：连接池使用率、队列长度
- **追踪（Tracing）**：OpenTelemetry 自动埋点 http、数据库、Redis；跨服务传播 `traceparent`

告警基于 SLO（如 99.9% 请求 < 300ms），而非单个指标阈值。

**口述模板（30–60 秒）**

1. 一句话结论：日志、指标、追踪三位一体，用 OpenTelemetry 统一。
2. 关键机制：traceId 关联三类数据。
3. 注意点：Node 特有指标是事件循环延迟。
4. 可追问时补充：基于 SLO 的告警。

**常见追问**

- OTel 自动埋点如何生效？→ 启动时通过 `--import` 预加载注册钩子，拦截模块加载并打补丁。

## 六、架构

### Q20. 如何设计 Node BFF 层？

- **难度**: senior
- **标签**: BFF, 架构

**答案**

BFF（Backend for Frontend）职责：

- 聚合多个后端服务接口，减少前端请求次数
- 裁剪字段，适配不同端（Web、App、小程序）
- 统一鉴权、会话管理
- SSR / RSC 渲染

设计要点：

- 并行调用下游 + 超时 + 部分失败降级
- DataLoader 合并重复请求
- 不承载核心业务逻辑，避免成为新的单体
- 缓存热点聚合结果
- 链路追踪贯穿前端到后端

**口述模板（30–60 秒）**

1. 一句话结论：BFF 为前端聚合和裁剪数据，是前后端协作的适配层。
2. 关键机制：并行调用 + 降级 + 缓存。
3. 注意点：不要把领域逻辑放进 BFF。
4. 可追问时补充：GraphQL 作为 BFF 的选择。

**常见追问**

- 某个下游超时，聚合接口如何处理？→ 非关键模块返回空或缓存数据，标记降级；关键模块失败才整体报错。

### Q21. Serverless 中的 Node 冷启动如何优化？

- **难度**: senior
- **标签**: Serverless

**答案**

冷启动 = 拉起运行环境 + 加载代码 + 初始化依赖。

优化：

- 减小包体积：打包（esbuild）、Tree Shaking、移除无用依赖
- 延迟加载不常用模块
- 初始化逻辑放在 handler 外以便复用，但避免重型初始化
- 复用连接（全局变量缓存客户端）
- 预置并发 / 保温
- 使用 V8 编译缓存（`module.enableCompileCache()`）
- 选择更大内存（通常 CPU 配额也更高）

**口述模板（30–60 秒）**

1. 一句话结论：减少加载量、复用初始化、预置并发。
2. 关键机制：冷启动时间主要花在加载和初始化。
3. 注意点：数据库连接数易爆。
4. 可追问时补充：Edge Runtime 的限制和优势。

**常见追问**

- 为什么 Serverless 连接数据库要注意？→ 每个实例都会建连，并发上来后连接数超过数据库上限。

### Q22. Node、Deno、Bun 有什么区别？

- **难度**: senior
- **标签**: 运行时对比

**答案**

| | Node.js | Deno | Bun |
|--|---------|------|-----|
| 引擎 | V8 | V8 | JavaScriptCore |
| 语言 | C++ | Rust | Zig |
| TypeScript | 类型擦除支持 | 原生 | 原生 |

**口述模板（30–60 秒）**

2. 关键机制：引擎和实现语言不同。
3. 注意点：兼容性在边缘场景仍有差异。
4. 可追问时补充：Node 正在吸收 TS、测试、watch 等内置能力。

**常见追问**

- 迁移到 Bun 需要注意什么？→ 原生模块、边缘 API、性能基准要在真实业务中验证。

### Q23. 如何发布 Node 单可执行文件（SEA）？

4. 可追问时补充：macOS / Windows 签名。

### Q24. Node 如何扩展原生能力？N-API 和 WebAssembly 怎么选？

- **难度**: senior
- **标签**: 原生扩展

**答案**

- **Node-API（N-API）**：C/C++/Rust（napi-rs）编写原生模块，ABI 稳定，跨 Node 版本无需重新编译
- **WebAssembly**：跨平台、沙箱安全、无需编译到各平台，性能接近原生（有调用开销）

选择：

- 需要系统调用、调用现有 C 库、极致性能 → N-API（sharp、bcrypt）
- 纯计算逻辑、跨平台分发、浏览器复用 → WASM

原生模块注意：预编译二进制分发（prebuildify）、Alpine musl 兼容、Docker 构建环境。

**口述模板（30–60 秒）**

1. 一句话结论：系统级和极致性能用 N-API，可移植纯计算用 WASM。
2. 关键机制：N-API 提供稳定 ABI。
3. 注意点：原生模块增加构建和部署复杂度。
4. 可追问时补充：napi-rs 用 Rust 写扩展。

**常见追问**

- 为什么 Docker 中 bcrypt 安装失败？→ 缺少编译工具链或平台二进制不匹配，可换 bcryptjs 或多阶段构建。

### Q25. 如何制定 Node 版本升级策略？

- **难度**: senior
- **标签**: 版本管理

**答案**

- 只在 LTS 版本上运行生产
- 关注 EOL 日期，提前 6 个月规划升级（如 Node 22 于 2027-04 EOL）
- 发布节奏变化：Node 27 起每年一个大版本且均进入 LTS，升级节奏更可预测
- 升级步骤：
  1. 阅读 changelog 中的 breaking changes 和废弃项
  2. CI 增加新版本矩阵
  3. 检查原生模块兼容性
  4. 预发环境压测对比性能和内存
  5. 灰度发布，监控错误率与延迟
- 统一 Docker 基础镜像、`.nvmrc`、`engines`

**口述模板（30–60 秒）**

1. 一句话结论：跟随 LTS，按 EOL 规划，CI 矩阵 + 压测 + 灰度。
2. 关键机制：新版本通常带来 V8 性能提升。
3. 注意点：原生模块和废弃 API 是主要风险。
4. 可追问时补充：2026 起的新发布节奏。

**常见追问**

- 升级后内存升高怎么办？→ 对比 GC 参数和堆默认上限变化，必要时显式配置。

### Q26. 如何实现零停机发布？

- **难度**: senior
- **标签**: 部署, 稳定性

**答案**

- 滚动更新：逐个替换实例，保证最小可用副本数
- Readiness 探针：新实例预热完成才接流量
- 优雅关闭：SIGTERM 后停止接收新请求、处理存量请求
- preStop 延迟：等待负载均衡摘除
- keep-alive 连接主动关闭（`Connection: close` 或 `closeIdleConnections`）
- 数据库变更向前兼容（先加字段、再改代码、最后删旧字段）
- 长连接（WebSocket）：通知客户端重连，客户端自动重连 + 退避

**口述模板（30–60 秒）**

1. 一句话结论：滚动更新 + 就绪探针 + 优雅关闭 + 兼容的数据变更。
2. 关键机制：新实例就绪才接流量，旧实例处理完才退出。
3. 注意点：长连接和数据库变更最容易导致中断。
4. 可追问时补充：蓝绿与金丝雀发布。

**常见追问**

- WebSocket 服务如何零停机？→ 新旧实例并存，旧实例发送重连指令并逐步断开，客户端带退避重连。
