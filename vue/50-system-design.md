# Vue 系统设计题

> 回答结构：先澄清需求和约束 → 给出整体架构 → 讲清关键设计和取舍 → 说明指标和验证方式 → 回答扩展追问。Vue 方向的设计题重点考察组件抽象、状态管理、性能和工程化能力。

---

### S1. 设计一个企业级 Vue 组件库

- **难度**: 高级
- **标签**: 组件库, 架构

**澄清问题（面试时先问）**

- 使用方：内部多个业务线，还是开源？需要支持多少个产品？
- 是否需要多主题、暗色模式、品牌定制？
- 是否需要 SSR（Nuxt）支持？是否需要无障碍合规？
- 现有设计规范（Design Token）是否成熟？

**参考方案**

```text
packages/
├─ tokens/        Design Token（颜色、间距、字号）→ 生成 CSS 变量
├─ headless/      无样式的逻辑层：状态、键盘交互、焦点管理、ARIA（composable + 无样式组件）
├─ components/    带样式的组件：基于 headless + tokens
├─ icons/         图标（按需导入的 SVG 组件）
├─ utils/         通用工具
├─ resolver/      unplugin-vue-components 解析器，支持自动按需导入
└─ docs/          VitePress 文档 + 交互示例
```

**关键设计**

- **分层**：Headless 层负责行为和无障碍，样式层负责外观；业务线可以只使用 Headless 层自定义样式
- **主题**：Design Token 生成 CSS 变量，主题切换只修改变量；组件内部不写死颜色
- **API 规范**：
  - 统一的 props 命名（`size`、`disabled`、`loading`）
  - 表单组件统一 `v-model`，同时支持受控和非受控
  - 复合组件（Form / FormItem、Select / Option）通过 provide / inject 通信
  - 完整的 TypeScript 类型：泛型组件（Table、Select）、类型化插槽
- **按需引入**：每个组件独立入口，`sideEffects` 只标记样式文件，提供自动导入解析器
- **SSR**：不在 setup 中访问 window；ID 使用 `useId`；Teleport 的弹窗支持配置挂载点
- **质量**：单元测试（Vitest）、视觉回归测试（Playwright 截图）、无障碍测试（axe）
- **发布**：Changesets 管理版本；破坏性变更提供迁移指南和 codemod

**关键指标**

- 组件覆盖率、业务接入率
- 包体积（单组件按需引入后的大小）
- 缺陷数量、修复时长
- 无障碍检测通过率

**口述模板（2–3 分钟）**

1. **澄清**：先确认使用方的数量、主题定制需求和 SSR 需求。
2. **分层**：Token、Headless 逻辑层、样式组件层，业务方可以只用逻辑层。
3. **主题**：Design Token 生成 CSS 变量，切换主题只修改变量。
4. **API**：统一的 props 规范，支持受控和非受控，复合组件通过 provide / inject 通信，完整的类型。
5. **工程**：按需引入、文档、单元测试和视觉回归测试、Changesets 版本管理。
6. **演进**：破坏性变更提供 codemod，降低业务升级成本。

**扩展追问**

- 业务方需要深度定制某个组件的样式怎么办？→ 暴露 CSS 变量和 class 钩子；更深的定制使用 Headless 层自己实现。
- 怎么保证多个业务线使用的版本不会差异太大？→ 语义化版本、定期升级窗口、自动化升级工具和兼容性测试。

### S2. 设计一个 Vue 中后台框架

- **难度**: 高级
- **标签**: 中后台, 架构

**澄清问题（面试时先问）**

- 有多少个子系统？是否需要微前端？
- 权限模型：RBAC？是否需要数据权限？
- 是否需要多标签页（页签）、国际化、多租户？
- 页面以列表、表单、详情为主吗？

**参考方案**

```text
┌─────────────── 应用框架层 ───────────────┐
│ 布局（菜单、页签、面包屑）、主题、国际化            │
│ 登录与权限：动态路由、菜单、按钮权限               │
│ 请求层：拦截器（Token、错误处理、重试）、Vue Query  │
│ 全局状态：用户、权限、字典（Pinia）               │
└──────────────────────────────────────────┘
┌─────────────── 业务组件层 ───────────────┐
│ ProTable（配置化表格：查询、分页、列设置）         │
│ ProForm（Schema 表单：联动、校验）               │
│ 上传、字典选择、权限按钮、导出                     │
└──────────────────────────────────────────┘
┌─────────────── 业务模块 ─────────────────┐
│ 按领域拆分目录：views、api、stores、composables   │
└──────────────────────────────────────────┘
工程：Vite、代码规范、Mock、CI/CD、监控
```

**关键设计**

- **权限**：
  - 登录后获取权限码和菜单，生成动态路由（`router.addRoute`）
  - 刷新时在路由守卫中重新加载
  - 按钮权限使用权限组件或 `hasPermission`
  - 接口权限由后端保证
- **页签（多标签页）**：KeepAlive 缓存打开的页面，按路由 name 匹配；关闭页签时从 include 中移除；同一路由不同参数的页面需要用 `fullPath` 作为 key
- **ProTable**：查询表单、表格、分页、列配置统一封装；查询条件同步到 URL query，刷新后恢复
- **请求层**：统一错误处理（401 跳转登录、403 提示）、Token 刷新（并发请求时只刷新一次，其他请求等待）、请求取消
- **性能**：路由懒加载、组件库按需引入、大表格虚拟滚动、KeepAlive 设置 max
- **规范**：目录结构、命名、提交规范；代码生成器根据接口生成列表页和表单页

**关键指标**

- 页面开发效率（新页面平均开发时间）
- 首屏时间、路由切换时间
- 错误率

**口述模板（2–3 分钟）**

1. **澄清**：确认子系统数量、权限模型、是否需要页签和国际化。
2. **分层**：应用框架层、业务组件层、业务模块层。
3. **权限**：动态路由、菜单、按钮权限，接口由后端校验，刷新时重新加载权限。
4. **页签**：KeepAlive 加 include 缓存页面，关闭页签时移除。
5. **业务组件**：ProTable 和 ProForm 提升开发效率，查询条件同步到 URL。
6. **请求层**：统一的错误处理和 Token 刷新，并发刷新只执行一次。

**扩展追问**

- Token 过期时多个请求同时失败怎么办？→ 第一个请求触发刷新，其他请求进入等待队列，刷新成功后用新 Token 重试队列中的请求，失败则跳转登录。
- 页签中同一个详情页打开多个不同 ID 怎么缓存？→ KeepAlive 的 include 按组件名匹配，无法区分实例；需要用动态组件包装，以 fullPath 作为 key。

### S3. 设计一个复杂的动态表单系统

- **难度**: 高级
- **标签**: 表单, 架构

**澄清问题（面试时先问）**

- 表单规模：几十个字段还是数百个？
- 联动复杂度：显示隐藏、选项联动、值计算、跨字段校验？
- 表单配置来源：前端写死、后端下发、可视化搭建？
- 是否需要草稿、版本、审批流？

**参考方案**

```text
Schema（JSON）
  ↓
表单引擎
  ├─ 字段注册表：component 名称 → 组件
  ├─ 状态：values（reactive）、errors、touched、字段元数据
  ├─ 联动引擎：表达式 / 函数 → computed，自动追踪依赖
  ├─ 校验引擎：字段规则、跨字段规则、异步校验（竞态处理）
  └─ 渲染：布局（栅格、分组、标签页、步骤）→ 字段组件
  ↓
扩展：草稿保存、只读模式、打印、差异对比
```

**关键设计**

- **Schema**：字段名、组件、标签、默认值、校验规则、联动规则、布局信息
- **联动**：
  - 后端下发的配置不能是函数，使用安全的表达式（`{{ values.type === 'company' }}`），在受限的解释器中执行，**不使用 eval**
  - 表达式编译为 computed，Vue 自动追踪它依赖的字段
- **性能**：
  - 每个字段是独立组件，只读取自己的值和依赖
  - 数百字段：分组懒渲染（折叠面板、标签页中未显示的分组不渲染）
  - 避免在父组件中遍历所有值（例如实时计算整个表单的脏状态）
- **校验**：字段失焦时校验、提交时全量校验；异步校验（例如用户名是否重复）带防抖和竞态处理
- **自定义组件**：业务可以注册组件，遵循 `v-model` 协议

**关键指标**

- 输入延迟（INP）
- 表单渲染时间
- 配置到上线的时间

**口述模板（2–3 分钟）**

1. **澄清**：确认表单规模、联动复杂度和配置来源。
2. **Schema 驱动**：用 JSON 描述字段、校验、联动和布局，组件注册表映射到实际组件。
3. **联动**：使用安全的表达式，编译为 computed，自动追踪依赖。
4. **性能**：每个字段独立组件，只读取自己的数据；大表单按分组懒渲染。
5. **校验**：字段级和表单级规则，异步校验防抖并处理竞态。
6. **安全**：后端下发的表达式不能用 eval 执行。

**扩展追问**

- 为什么不能用 `new Function` 执行后端下发的表达式？→ 配置被篡改或注入时可以执行任意代码（XSS）；应该使用受限的表达式解析器，只允许访问表单数据和白名单函数。
- 怎么支持可视化搭建？→ 拖拽生成 Schema，编辑器和运行时共用同一个渲染引擎，保证所见即所得。

### S4. 设计一个低代码页面搭建平台

- **难度**: 高级
- **标签**: 低代码, 架构

**澄清问题（面试时先问）**

- 目标用户：运营人员（活动页）还是开发人员（中后台）？
- 输出：运行时渲染 Schema，还是生成源码？
- 需要支持哪些能力：数据源、事件、逻辑编排、多端？
- 物料：内置组件，还是允许业务注册自定义组件？

**参考方案**

```text
┌──────────── 编辑器 ────────────┐
│ 物料面板 │ 画布（iframe 隔离）│ 属性面板 │
│ 大纲树、撤销重做、快捷键、预览       │
└────────────────────────────────┘
          ↓ 产出 Schema（页面 JSON）
┌──────────── 协议 ──────────────┐
│ 组件树、属性、样式、数据源、事件、状态  │
└────────────────────────────────┘
          ↓
┌──────────── 渲染引擎 ──────────┐
│ Schema → 动态组件；数据源请求；事件执行 │
└────────────────────────────────┘
物料体系：组件 + 元信息（属性配置面板描述），独立构建发布
```

**关键设计**

- **Schema 协议**：组件树结构（`componentName`、`props`、`children`、`style`、`events`、`condition`、`loop`），协议要有版本号，支持升级迁移
- **画布隔离**：画布在 iframe 中渲染，样式和脚本与编辑器隔离；编辑器通过 postMessage 或共享状态与画布通信
- **物料**：每个组件附带描述文件（可配置的属性、类型、默认值、属性面板控件），物料独立构建，按需加载
- **渲染引擎**：递归渲染 Schema，用 `<component :is>`；表达式绑定（`{{ state.user.name }}`）在受限的作用域中求值
- **数据源**：声明式配置接口，引擎负责请求、加载状态、依赖刷新
- **编辑器状态**：Schema 存储在 store 中，所有修改通过命令完成，便于撤销重做和协同编辑
- **出码**：Schema 转换为 Vue SFC 源码，适合需要二次开发的场景

**关键指标**

- 页面搭建时间、复用率
- 渲染性能（大页面的首屏时间）
- 物料数量和使用率

**口述模板（2–3 分钟）**

1. **澄清**：确认目标用户、输出方式和需要的能力。
2. **三个核心**：编辑器、Schema 协议、渲染引擎，协议是两者之间的契约。
3. **画布隔离**：画布用 iframe 隔离样式和脚本。
4. **物料**：组件加描述文件，描述文件驱动属性面板，物料独立发布。
5. **渲染**：递归渲染 Schema，表达式在受限的作用域中求值，数据源声明式配置。
6. **编辑器状态**：基于命令修改 Schema，支持撤销重做。

**扩展追问**

- 低代码平台的边界在哪？→ 适合结构化、重复性高的页面；复杂交互和逻辑应该通过自定义组件（源码开发）扩展，而不是在平台中堆叠配置。
- 协议升级怎么兼容旧页面？→ Schema 带版本号，渲染前执行迁移函数，把旧版本升级到当前版本。

### S5. 设计一个 Nuxt SSR 电商站点

- **难度**: 高级
- **标签**: SSR, Nuxt

**澄清问题（面试时先问）**

- 页面类型：首页、商品列表、商品详情、购物车、结算？
- SEO 和首屏性能的要求？流量规模？
- 数据实时性：价格、库存需要多实时？
- 部署环境：Node 服务器、Serverless、边缘？

**参考方案**

```text
用户 → CDN（缓存页面和静态资源）
         ↓ 未命中
     Nuxt 服务（Nitro）
       ├─ 路由规则（routeRules）：
       │   首页：ISR / SWR 缓存 60 秒
       │   商品详情：SWR 缓存 + 价格库存客户端获取
       │   购物车、结算：仅客户端渲染（ssr: false）
       │   静态页：预渲染
       ├─ 数据获取：useFetch（服务端获取，payload 传给客户端）
       └─ 服务端 API（server/api）：BFF 聚合后端服务
```

**关键设计**

- **混合渲染**：Nuxt 的 `routeRules` 按路由配置渲染策略：

```ts
export default defineNuxtConfig({
  routeRules: {
    '/': { swr: 60 },
    '/products/**': { swr: 300 },
    '/cart': { ssr: false },
    '/about': { prerender: true },
  },
})
```

- **动态数据分离**：商品详情的主体内容（标题、图片、描述）服务端渲染并缓存；价格和库存在客户端实时获取，避免缓存导致的价格错误
- **性能**：
  - 首屏图片使用 `@nuxt/image`，优先级设置为高
  - 非首屏组件懒 hydration（`hydrate-on-visible`）
  - payload 只包含需要的字段（`pick`）
- **SEO**：`useSeoMeta`、结构化数据（JSON-LD）、sitemap
- **状态隔离**：使用 `useState` 和 Pinia，不使用模块级变量
- **降级**：服务端渲染失败时返回客户端渲染的页面

**关键指标**

- LCP、INP、CLS（核心网页指标）
- TTFB、缓存命中率
- 转化率

**口述模板（2–3 分钟）**

1. **澄清**：确认页面类型、SEO 要求、数据实时性和部署环境。
2. **混合渲染**：按路由选择策略，首页和详情页 SWR 缓存，购物车纯客户端，静态页预渲染。
3. **动态数据**：价格和库存客户端实时获取，主体内容缓存。
4. **性能**：首屏图片优先，非首屏组件懒 hydration，减小 payload。
5. **SEO**：元信息、结构化数据、sitemap。
6. **稳定性**：状态按请求隔离，服务端失败时降级为客户端渲染。

**扩展追问**

- 页面缓存后，登录用户的个性化内容怎么处理？→ 缓存的页面只包含公共内容，个性化部分（用户信息、推荐）在客户端获取，或者通过边缘计算注入。
- 商品更新后怎么让缓存失效？→ SWR 的过期时间加上主动清除（商品更新时调用 CDN 和服务端缓存的清除接口）。

### S6. 设计一个实时协作看板应用

- **难度**: 高级
- **标签**: 实时, 状态管理

**澄清问题（面试时先问）**

- 协作规模：同时编辑的用户数？
- 实时性要求：卡片移动是否需要实时看到其他人的操作？
- 冲突：两个人同时移动同一张卡片怎么办？
- 是否需要离线编辑？

**参考方案**

```text
客户端
  ├─ 本地状态（Pinia）：看板、列、卡片
  ├─ 乐观更新：操作立即生效，同时发送到服务端
  ├─ WebSocket：接收其他人的操作，合并到本地状态
  └─ 拖拽：基于 Pointer 事件，拖拽中只更新本地预览
服务端
  ├─ 操作校验和权限
  ├─ 排序：分数索引（fractional indexing）
  └─ 广播给同一看板的其他客户端
```

**关键设计**

- **排序**：卡片的顺序使用**分数索引**（例如在 "a" 和 "b" 之间插入 "an"），移动一张卡片只修改它自己的排序值，不需要重排整列，减少冲突
- **乐观更新**：本地立即更新，服务端失败时回滚并提示
- **冲突**：同一张卡片的并发修改按服务端顺序处理（最后写入优先）；复杂场景（同时编辑描述文本）使用 CRDT（Yjs）
- **性能**：
  - 卡片列表使用 `shallowRef`，按 ID 索引的 Map 存储，收到更新时只替换对应的卡片
  - 拖拽中只移动拖拽的元素（transform），放下时才更新数据
  - 大看板使用虚拟滚动
- **在线状态**：显示其他用户的光标或正在编辑的卡片（awareness）
- **重连**：断线后重新连接，根据版本号拉取增量更新

**关键指标**

- 操作同步延迟
- 冲突率、回滚率
- 拖拽帧率

**口述模板（2–3 分钟）**

1. **澄清**：确认协作规模、实时性要求和冲突处理方式。
2. **乐观更新**：本地立即生效，失败回滚。
3. **同步**：WebSocket 接收其他人的操作，合并到本地状态。
4. **排序**：分数索引让移动只修改一张卡片，减少冲突。
5. **性能**：shallowRef 加按 ID 的 Map，只替换变化的卡片；拖拽中只用 transform。
6. **可靠性**：断线重连后按版本号拉取增量更新。

**扩展追问**

- 为什么不用数组下标表示顺序？→ 插入或移动时需要修改后面所有卡片的下标，多人同时操作容易冲突。
- 收到大量远程更新时页面卡顿怎么办？→ 批量合并更新（每帧合并一次），使用 shallowRef 避免深度响应式。

### S7. 设计一个多语言、多主题的 Vue 应用架构

- **难度**: 中级
- **标签**: 国际化, 主题

**澄清问题（面试时先问）**

- 支持多少种语言？是否包括从右到左的语言（阿拉伯语）？
- 翻译文案的来源：前端维护还是翻译平台？
- 主题：只有亮色和暗色，还是支持品牌定制？
- 是否需要 SSR？

**参考方案**

```text
国际化
  ├─ vue-i18n：组合式 API（useI18n）
  ├─ 语言包按语言 + 按模块拆分，懒加载
  ├─ 翻译平台同步：CI 中拉取翻译，缺失的 key 告警
  ├─ 日期、数字、货币：Intl API
  └─ 语言检测：URL 前缀（SEO）> 用户设置 > Accept-Language
主题
  ├─ Design Token → CSS 变量
  ├─ 主题切换：修改根元素的 data-theme 属性
  ├─ 暗色模式：prefers-color-scheme + 用户选择，保存到 Cookie（SSR 可读取）
  └─ 组件库主题与应用主题共用变量
```

**关键设计**

- **语言包懒加载**：只加载当前语言和当前页面的模块；切换语言时异步加载
- **SSR**：语言和主题需要在服务端确定（从 URL 或 Cookie 读取），否则会出现闪烁和 hydration mismatch
- **避免主题闪烁**：在 HTML 的 head 中内联一段脚本，在渲染前设置 data-theme（纯客户端渲染时）
- **RTL**：使用 CSS 逻辑属性（`margin-inline-start`）、`dir="rtl"`
- **类型安全**：从默认语言包生成 key 的类型，避免拼写错误

**关键指标**

- 翻译覆盖率
- 切换语言和主题的耗时
- 语言包体积

**口述模板（2–3 分钟）**

1. **澄清**：确认语言数量、是否有 RTL 语言、主题需求和是否需要 SSR。
2. **国际化**：vue-i18n，语言包按语言和模块懒加载，格式化使用 Intl API。
3. **主题**：Design Token 生成 CSS 变量，切换主题只修改根元素的属性。
4. **避免闪烁**：SSR 时从 Cookie 读取主题和语言；纯客户端时在 head 中内联脚本提前设置。
5. **RTL**：使用 CSS 逻辑属性。
6. **流程**：与翻译平台同步，CI 检查缺失的翻译。

**扩展追问**

- 为什么主题偏好存 Cookie 而不是 localStorage？→ SSR 时服务端可以读取 Cookie，直接渲染正确的主题，避免闪烁和 hydration mismatch。

### S8. 设计 Vue 应用的前端监控与错误治理方案

- **难度**: 中级
- **标签**: 监控, 稳定性

**澄清问题（面试时先问）**

- 需要采集哪些数据：错误、性能、用户行为？
- 使用第三方服务（Sentry）还是自建？
- 数据量和采样要求？是否需要用户行为回放？

**参考方案**

```text
采集层（SDK）
  ├─ Vue 错误：app.config.errorHandler（组件名、生命周期信息）
  ├─ 全局错误：window.onerror、unhandledrejection、资源加载错误
  ├─ 请求错误：请求拦截器（接口、状态码、耗时）
  ├─ 路由：router.onError（懒加载 chunk 失败）、页面访问
  ├─ 性能：web-vitals（LCP、INP、CLS），路由切换耗时
  └─ 上下文：用户、版本、路由、设备、最近的操作记录（面包屑）
上报层：批量、采样、sendBeacon、离线缓存
服务端：聚合（指纹）、Source Map 还原、告警、与发布记录关联
```

**关键设计**

- **Vue 错误信息**：errorHandler 的 `info` 参数说明错误来源（渲染、setup、侦听器），附带组件名和组件树路径
- **chunk 加载失败**：发版后用户仍在使用旧页面，懒加载旧的 chunk 返回 404 → 在 `router.onError` 中捕获，提示刷新或自动刷新一次
- **错误边界**：关键模块用 onErrorCaptured 包装，出错时显示降级 UI，避免整页白屏
- **Source Map**：构建时上传到监控平台，不发布到线上
- **降噪**：过滤浏览器扩展错误、`ResizeObserver loop` 等良性错误、爬虫
- **路由切换性能**：在 `beforeEach` 和 `afterEach` 之间计时，加上组件渲染完成的时间

**关键指标**

- 错误率（按会话）、受影响的用户数
- 核心网页指标、路由切换耗时
- 告警准确率、问题修复时长

**口述模板（2–3 分钟）**

1. **澄清**：确认采集的数据类型和是否使用第三方服务。
2. **采集**：Vue 的 errorHandler、全局错误、请求错误、路由错误和性能指标。
3. **上下文**：附带组件信息、路由、版本和操作面包屑。
4. **特殊处理**：发版后懒加载 chunk 失败，在 router.onError 中提示刷新。
5. **服务端**：按指纹聚合，Source Map 还原，关联发布记录。
6. **降噪**：过滤扩展错误和良性错误。

**扩展追问**

- 怎么避免发版导致的 chunk 加载失败？→ 保留旧版本的静态资源一段时间；HTML 不缓存；检测到新版本时提示用户刷新。
