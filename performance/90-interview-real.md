# 前端性能优化真实 / 高频面试题

> 根据近年公开面经、技术社区讨论和 web.dev 等官方资料整理，按面试中的真实问法组织。`来源倾向` 表示这类问题常见于哪类岗位或面试轮次，不代表某公司的固定题库。每题给出简短答案，详细内容见链接。

---

### R1. 你做过哪些性能优化？效果怎么样？

- **难度**: 高级
- **标签**: 项目, 方法论
- **来源倾向**: 几乎所有前端岗位必问，中高级岗位会深挖

**答案**

用 STAR 结构，全程带数据：背景和业务影响 → 量化目标 → 定位过程（用什么数据发现了什么瓶颈）→ 每项措施及理由 → 技术指标和业务指标的结果 → 如何验证和防止劣化。不要罗列手段。

**口述模板（30–60 秒）**

1. **一句话结论**：先说结果，例如首页移动端 LCP P75 从 4.2 秒降到 2.3 秒，跳出率下降约 8%。
2. **关键机制**：通过 LCP 拆解发现加载延迟占比最高，原因是首图由 JS 渲染、首屏 JS 过大。
3. **对比或注意点**：措施包括首屏 SSR、首图高优先级、JS 拆分和图片格式优化，并说明取舍。
4. **可追问时补充**：用灰度对照验证效果，CI 中加入体积预算防止回退。

详见：[高级 Q22](30-senior-qa.md)、[高级 Q21](30-senior-qa.md)

### R2. Core Web Vitals 有哪些指标？阈值多少？

- **难度**: 初级
- **标签**: 指标
- **来源倾向**: 一面高频

**答案**

LCP（加载，≤ 2.5s）、INP（交互，≤ 200ms）、CLS（视觉稳定，≤ 0.1），按真实用户 P75 评估。INP 在 2024 年 3 月取代了 FID。

详见：[初级 Q2](10-junior-qa.md)

### R3. INP 和 FID 有什么区别？为什么要替换？

- **难度**: 中级
- **标签**: INP
- **来源倾向**: 近两年高频，检验资料是否过时

**答案**

FID 只统计第一次交互的输入延迟；INP 统计整个生命周期的所有交互，包括输入延迟、事件处理和渲染，取近似最差的一次。FID 好的页面后续操作可能非常卡，INP 更真实。

详见：[初级 Q4](10-junior-qa.md)、[高级 Q2](30-senior-qa.md)

### R4. 首屏加载慢，你会怎么排查？

- **难度**: 高级
- **标签**: LCP, 排查
- **来源倾向**: 场景题必问

**答案**

先用 RUM 数据确认范围（设备、网络、页面），再看 LCP 元素和四段拆解（TTFB、资源加载延迟、加载耗时、渲染延迟），找到占比最高的阶段针对性优化。用 Network 面板看瀑布和优先级，用 Performance 面板看主线程。

**口述模板（30–60 秒）**

1. **一句话结论**：先确认是哪类用户慢，再用 LCP 四段拆解定位。
2. **关键机制**：TTFB 看服务端和网络，加载延迟看资源发现时机，加载耗时看体积，渲染延迟看阻塞资源和 JS。
3. **对比或注意点**：CSR 页面常见的是串行请求链，需要 SSR 或数据内联。
4. **可追问时补充**：优化后用灰度对照验证。

详见：[中级 Q1](20-mid-qa.md)、[高级 Q6](30-senior-qa.md)

### R5. 页面点击卡顿，INP 很差，怎么定位和优化？

- **难度**: 高级
- **标签**: INP, 排查
- **来源倾向**: 近两年高频场景题

**答案**

用 web-vitals attribution 找到最差的交互元素和三段耗时（输入延迟、处理耗时、呈现延迟），结合 LoAF 找到脚本来源；本地开启 CPU 节流复现。优化：拆分长任务、先给反馈再做重活、Worker、缩小渲染范围、useTransition、虚拟列表。

详见：[中级 Q7](20-mid-qa.md)、[中级 Q9](20-mid-qa.md)、[高级 Q7](30-senior-qa.md)

### R6. 什么是长任务？怎么拆分？

- **难度**: 中级
- **标签**: 长任务
- **来源倾向**: 原理面高频

**答案**

主线程上超过 50ms 的任务，期间无法响应输入和渲染。拆分的核心是定期让出主线程：`scheduler.yield()`（让出后优先继续）、`setTimeout`、`postTask`、`requestIdleCallback`，计算密集型任务移到 Worker。

详见：[中级 Q8](20-mid-qa.md)、[手写 H2](40-coding-handwritten.md)

### R7. 什么是重排和重绘？怎么减少？

- **难度**: 初级
- **标签**: 渲染
- **来源倾向**: 一面必问

**答案**

重排是几何属性变化导致重新计算布局，重绘是外观变化导致重新绘制；transform 和 opacity 只触发合成。减少方法：批量修改样式、读写分离避免强制同步布局、动画只使用 transform 和 opacity。

详见：[初级 Q22](10-junior-qa.md)、[中级 Q13](20-mid-qa.md)

---

### R8. 10 万条数据怎么渲染？

- **难度**: 中级
- **标签**: 列表, 渲染
- **来源倾向**: 高频手写 / 场景题

**答案**

优先分页；必须全部展示时用虚拟列表（只渲染可见区域，用占位撑开滚动高度，不定高时预估加测量）；或者分片渲染（rAF + DocumentFragment）。千级复杂节点可以用 `content-visibility: auto`。

**口述模板（30–60 秒）**

1. **一句话结论**：首选分页，必须一次展示就用虚拟列表。
2. **关键机制**：根据 scrollTop 计算可见区域的起止索引，只渲染这些项和缓冲区。
3. **对比或注意点**：分片渲染避免长任务，但最终 DOM 节点数没有减少。
4. **可追问时补充**：不定高时用预估高度，渲染后测量修正，起始索引用二分查找。

详见：[中级 Q16](20-mid-qa.md)、[手写 H3](40-coding-handwritten.md)、[手写 H12](40-coding-handwritten.md)

### R9. 强缓存和协商缓存的区别？项目中怎么设计缓存策略？

- **难度**: 中级
- **标签**: 缓存
- **来源倾向**: 一面二面高频

**答案**

强缓存（Cache-Control max-age）不发请求；协商缓存（ETag / Last-Modified）发请求，未变化返回 304。策略：HTML 用 no-cache，带内容 hash 的资源用 `max-age=31536000, immutable`；发布时先传资源后更新 HTML，保留旧资源。

详见：[初级 Q15](10-junior-qa.md)、[中级 Q18](20-mid-qa.md)

### R10. preload 和 prefetch 有什么区别？

- **难度**: 初级
- **标签**: 资源提示
- **来源倾向**: 一面高频

**答案**

preload 以高优先级加载当前页面一定会用到的资源（LCP 图片、字体）；prefetch 以最低优先级在空闲时加载下一个页面可能用到的资源。preconnect 提前建立连接。

详见：[初级 Q21](10-junior-qa.md)

---

### R11. script 的 async 和 defer 有什么区别？

- **难度**: 初级
- **标签**: 关键渲染路径
- **来源倾向**: 一面必问

**答案**

两者都不阻塞下载；async 下载完立即执行，不保证顺序；defer 在 HTML 解析完成后按顺序执行。module 脚本默认是 defer 行为。

详见：[初级 Q20](10-junior-qa.md)

### R12. CSS 和 JS 会阻塞页面渲染吗？

- **难度**: 中级
- **标签**: 关键渲染路径
- **来源倾向**: 原理面高频

**答案**

CSS 不阻塞 DOM 解析，但阻塞渲染，并阻塞后续同步脚本的执行；同步 JS 阻塞 DOM 解析。优化：关键 CSS 内联、脚本 defer、按媒体查询拆分 CSS。

详见：[中级 Q4](20-mid-qa.md)、[浏览器原理](../browser/20-mid-qa.md)

### R13. SSR 一定比 CSR 快吗？

- **难度**: 高级
- **标签**: 渲染模式
- **来源倾向**: 高级岗追问

**答案**

不一定。SSR 改善 FCP / LCP，但增加 TTFB（服务端渲染耗时）和水合成本，水合期间可能无法交互。需要配合缓存、流式渲染、选择性水合或 RSC。

详见：[中级 Q5](20-mid-qa.md)、[高级 Q8](30-senior-qa.md)

### R17. 如何设计一个前端性能监控系统？

- **难度**: 高级
- **标签**: 监控, 系统设计
- **来源倾向**: 高级岗系统设计高频

**答案**

SDK（指标 + 归因 + 上下文，采样批量上报）→ 接入层（Kafka）→ 处理层（实时聚合 + ClickHouse 明细）→ 应用层（按维度 P75 大盘、基于基线的告警、下钻到会话、关联发布）。

**口述模板（30–60 秒）**

1. **一句话结论**：分为 SDK、接入、处理和应用四层。
2. **关键机制**：SDK 采集指标和归因，后端按维度计算分位数，告警基于基线的相对变化。
3. **对比或注意点**：SDK 本身必须轻量；只有指标没有归因无法定位问题。
4. **可追问时补充**：关联发布记录，自动对比发布前后的指标。

详见：[高级 Q19](30-senior-qa.md)、[系统设计 S1](50-system-design.md)

### R20. 防抖和节流的区别？手写一个

- **难度**: 初级
- **标签**: 手写
- **来源倾向**: 手写题必考

**答案**

防抖是停止触发一段时间后才执行（搜索输入），节流是固定间隔最多执行一次（滚动）。手写需要处理 this、参数、leading / trailing 和 cancel。

### R22. 为什么 transform 动画比 left / top 动画性能好？

- **难度**: 中级
- **标签**: 渲染, 动画
- **来源倾向**: 原理面高频

**答案**

left / top 改变布局，每帧都要重排、重绘；transform 不改变布局，元素在合成层上只需要重新合成，可以在合成线程中完成，主线程繁忙时也流畅。

详见：[初级 Q28](10-junior-qa.md)、[中级 Q14](20-mid-qa.md)、[浏览器原理](../browser/30-senior-qa.md)

### R24. App 内 H5 页面怎么实现秒开？

- **标签**: Hybrid

### R25. 怎么防止性能优化成果回退？

- **难度**: 高级
- **标签**: 治理
- **来源倾向**: 高级岗必问

**答案**

多层防线：开发期 ESLint 和脚手架默认最佳实践；CI 中 size-limit 和 Lighthouse CI 预算门禁；发布时灰度对比 RUM 指标；线上大盘告警和定期复盘。预算基于基线逐步收紧，提供豁免流程。

详见：[高级 Q20](30-senior-qa.md)、[高级 Q26](30-senior-qa.md)、[系统设计 S4](50-system-design.md)
