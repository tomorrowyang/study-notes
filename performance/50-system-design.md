# 前端性能优化系统设计与场景

> 回答结构：先澄清需求和约束 → 给出整体方案（文字图）→ 讲关键设计和取舍 → 用指标证明效果 → 回答扩展追问。

### S1. 设计一个前端性能监控平台

- **难度**: 高级
- **标签**: 监控, 平台

**澄清问题（面试时先问）**

- 接入规模：多少应用、日 PV？
- 覆盖哪些端：Web、H5（App 内）、小程序？
- 需要哪些能力：指标大盘、告警、问题定位、版本对比？
- 是否已有错误监控、日志平台可以复用？

**参考方案**

```text
SDK（浏览器）
  ├─ 指标：LCP / INP / CLS / FCP / TTFB（带 attribution）
  ├─ 诊断：LoAF、资源耗时（Resource Timing）、接口耗时、业务自定义打点
  ├─ 上下文：页面、版本、设备、网络、地区、用户分组
  └─ 上报：会话级采样、批量、sendBeacon、页面隐藏时 flush
        ↓
接入层：网关 → 校验 / 限流 / 补充 IP 地区 → Kafka
        ↓
处理层：Flink 实时清洗聚合（分钟级 P75） + 原始明细落 ClickHouse
        ↓
应用层
  ├─ 大盘：按页面、版本、设备、地区的 P75 / P95 趋势和分布
  ├─ 告警：与基线对比（同比、环比）的相对变化
  ├─ 下钻：指标 → 页面 → 维度 → 具体会话 → 归因（LCP 元素、慢脚本）
  └─ 发布关联：版本发布标记，自动对比发布前后
```

**关键设计**

- **SDK 轻量**：自身体积小、异步加载、不产生长任务；采集逻辑放在空闲时
- **采样**：按会话采样保证数据完整；低流量页面提高采样率；错误和极差值可以全量上报
- **数据量**：原始明细保留较短时间（例如 30 天），聚合数据长期保留
- **分位数计算**：ClickHouse 的 `quantile` 函数；实时链路用 t-digest 等近似算法
- **告警降噪**：样本量过小时不告警；持续多个周期恶化才告警
- **隐私**：不采集个人信息，URL 中的参数脱敏

**关键指标**

- 平台本身：SDK 体积和开销、上报成功率、数据延迟
- 业务价值：发现问题的平均时间、问题定位时间

**口述模板（2–3 分钟）**

我把平台分为 SDK、接入、处理和应用四层。SDK 采集 Core Web Vitals 及归因信息、LoAF、资源和接口耗时，附带版本、设备、网络等维度，按会话采样，批量用 sendBeacon 上报，页面隐藏时统一发送。接入层校验限流后写入 Kafka，处理层用 Flink 做分钟级聚合，原始明细写入 ClickHouse 用于下钻。应用层提供按维度的 P75 趋势大盘、基于基线相对变化的告警，以及从指标下钻到具体会话和归因信息的能力，并和发布记录关联，自动对比发布前后。SDK 本身必须轻量，不能影响页面性能。

**扩展追问**

- 怎么保证 SDK 不影响页面性能？→ 异步加载、数据处理放在空闲时、批量上报、在 CI 中监控 SDK 自身的体积和耗时。
- 小程序怎么采集？→ 使用小程序提供的性能 API 和生命周期钩子，指标体系对齐但定义不完全相同。

### S2. 电商首页首屏优化方案

- **难度**: 高级
- **标签**: LCP, 首屏

**澄清问题（面试时先问）**

- 当前 LCP P75 是多少？主要用户的设备和网络情况？
- 页面渲染方式：CSR 还是 SSR？
- LCP 元素是什么（通常是首屏 Banner 图片）？
- 个性化程度（推荐流、千人千面）？

**参考方案**

```text
请求链路
  CDN 边缘 ── 缓存页面框架（shell）、静态模块
    └─ 回源 SSR 服务（流式）
         ├─ 先输出 head（关键 CSS 内联、preload 首图、preconnect 图片 CDN）
         ├─ 首屏模块（Banner、导航）服务端渲染，首图直接写入 HTML，fetchpriority=high
         └─ 个性化推荐流：Suspense 流式填充，或客户端请求

资源
  ├─ 首屏 JS：只包含首屏交互，其余模块按可见性懒加载
  ├─ 图片：AVIF / WebP，按屏幕宽度提供，非首屏懒加载，统一宽高比防 CLS
  └─ 第三方：统计、客服在 load 之后加载

交互
  ├─ 水合：首屏外模块延迟水合
  └─ 下一步：商品卡片悬停 / 可见时预取详情页（Speculation Rules 或路由预加载）
```

**关键设计**

- **LCP 四段逐一优化**：TTFB（边缘缓存 + 流式）、加载延迟（首图写入 HTML + 高优先级）、加载耗时（格式和尺寸）、渲染延迟（关键 CSS 内联，脚本 defer）
- **个性化与缓存的平衡**：可缓存的 shell + 流式填充个性化部分
- **运营配置的图片**：图片上传平台强制压缩、转格式、限制尺寸
- **降级**：SSR 失败时降级为 CSR shell

**关键指标**

- LCP、FCP、TTFB 的 P75（按设备和网络分组）
- 首屏 JS 体积、首屏请求数
- 业务指标：跳出率、首屏点击率、转化率

**口述模板（2–3 分钟）**

我会先确认 LCP 的现状和 LCP 元素，电商首页通常是 Banner 图片。然后按 LCP 四段来设计：TTFB 方面，页面框架在 CDN 边缘缓存，回源走流式 SSR，先输出 head，内联关键 CSS，preload 首图；加载延迟方面，首图直接写在 HTML 中并设置 fetchpriority high，不懒加载；加载耗时方面，图片使用 AVIF / WebP 并按屏幕宽度提供；渲染延迟方面，首屏 JS 只包含首屏交互，其余模块按可见性懒加载，第三方脚本在 load 之后加载。个性化推荐流通过 Suspense 流式填充，不影响首屏缓存。最后用灰度对照验证 LCP 和跳出率的变化。

**扩展追问**

- 运营随意上传大图怎么办？→ 在图片上传平台和 CDN 图片服务中强制处理，而不是依赖运营的自觉。

### S3. 复杂中后台系统的交互性能（INP）治理

- **难度**: 高级
- **标签**: INP, 中后台

**澄清问题（面试时先问）**

- 哪些页面和交互最慢？用户设备情况（中后台通常是办公电脑，但数据量大）？
- 技术栈：React / Vue，状态管理方案？
- 典型数据规模：表格行数、表单字段数？

**参考方案**

```text
度量
  ├─ RUM：INP + attribution（交互元素、三段耗时、LoAF 脚本）
  └─ 按页面 × 交互元素聚合，找出 Top 10 最差交互

定位分类
  ├─ 输入延迟高：轮询、WebSocket 消息处理、大量定时任务占用主线程
  ├─ 处理耗时高：状态更新触发大范围渲染、同步计算（筛选、排序、汇总）
  └─ 呈现延迟高：表格 DOM 过大、复杂样式

治理手段
  ├─ 渲染：虚拟表格、状态下沉 / 细粒度订阅、useTransition
  ├─ 计算：Worker 中做筛选排序，结果分片应用
  ├─ 消息：WebSocket 消息合并，按帧批量更新
  └─ 框架：React Compiler / memo 治理，表单使用细粒度订阅

防劣化
  ├─ 交互性能 E2E 测试（Playwright 录制关键交互耗时）
  └─ INP 大盘与告警
```

**关键设计**

- **数据驱动**：先找到最差的交互，而不是全局优化
- **实时数据**：高频推送的消息先合并再更新状态，每帧最多更新一次
- **计算移出主线程**：数据量大的筛选、排序、聚合放到 Worker
- **组件库层面**：表格、表单组件统一优化，所有业务受益

**关键指标**

- INP P75 / P95，Top 交互的耗时
- 长动画帧数量
- 用户反馈中的卡顿问题数

**口述模板（2–3 分钟）**

中后台的 INP 问题通常来自数据量大。我先用 RUM 的 INP 归因数据，按页面和交互元素找出最差的十个交互，再按三段拆解分类：输入延迟高通常是轮询、WebSocket 消息处理占用主线程，我会把消息合并按帧批量更新；处理耗时高通常是状态更新导致整个表格或表单重新渲染，或者同步的筛选排序，我会用虚拟表格、细粒度订阅、useTransition，并把计算移到 Worker；呈现延迟高通常是 DOM 太大。优化尽量在组件库层面完成，让所有业务受益。最后用 Playwright 录制关键交互耗时作为回归测试，配合线上 INP 告警防止劣化。

**扩展追问**

- 实时推送每秒上百条消息怎么处理？→ 在 Worker 或主线程的缓冲区中累积，每帧（或每 100ms）合并一次再更新 UI，并只更新可见的行。

### S4. 性能预算与防劣化体系

- **难度**: 高级
- **标签**: 治理, CI

**澄清问题（面试时先问）**

- 团队规模、发布频率？
- 是否已有 CI 和监控平台？
- 是否有历史上性能回退的教训？

**参考方案**

```text
开发阶段
  ├─ ESLint 规则：禁止整包导入大依赖、禁止 barrel 导入
  └─ 脚手架默认最佳实践：图片组件、懒加载、分包配置

PR 阶段（CI）
  ├─ size-limit：首屏 JS / CSS 体积预算，PR 评论展示差异
  ├─ Lighthouse CI：关键页面多次运行取中位数，断言 LCP / TBT / CLS
  └─ 新增依赖检查：体积超过阈值需要审批

发布阶段
  ├─ 灰度：新版本小流量，对比 RUM 指标
  └─ 指标恶化超过阈值时告警或自动回滚

线上阶段
  ├─ 性能大盘与告警
  └─ 定期复盘：每月 Top 回退项与负责人
```

**关键设计**

- **预算来源**：基于当前基线设定，逐步收紧，避免一开始就无法通过
- **减少误报**：Lighthouse 多次运行、设置容忍区间；稳定的测试环境
- **豁免机制**：超预算需要说明原因、负责人和偿还计划
- **多层防线**：CI 只能拦截可在实验室测出的问题，线上灰度对比覆盖真实用户

**关键指标**

- 被 CI 拦截的回退次数
- 线上性能回退事件数和平均修复时间
- 核心指标的长期趋势

**口述模板（2–3 分钟）**

我会在开发、PR、发布、线上四个阶段建立防线。开发阶段通过 ESLint 和脚手架让最佳实践成为默认；PR 阶段用 size-limit 检查体积预算，用 Lighthouse CI 对关键页面多次运行取中位数并断言指标，结果展示在 PR 评论中；发布阶段灰度对比新旧版本的 RUM 指标，恶化超过阈值时告警或回滚；线上阶段有大盘和告警，并定期复盘回退项。预算基于当前基线逐步收紧，并提供豁免流程，避免门禁过严导致大家绕过它。

**扩展追问**

- Lighthouse CI 结果不稳定怎么办？→ 固定测试机器、多次运行取中位数、只对较大的变化报警，并把它作为辅助，以体积预算和线上指标为主。

### S5. 大数据量表格（类在线表格）的渲染方案

- **难度**: 高级
- **标签**: 渲染, 表格

**澄清问题（面试时先问）**

- 数据规模：行数、列数（例如 10 万行 × 200 列）？
- 是否需要编辑、公式、合并单元格、冻结行列？
- 是否需要协同编辑？

**参考方案**

```text
数据层
  ├─ 列式存储或分块存储，按需加载（分页拉取可见区域附近的数据）
  └─ 计算（排序、筛选、公式）在 Worker 中进行

渲染层（两种方案）
  ├─ DOM 方案：二维虚拟化（行 + 列），固定行高，单元格轻量
  └─ Canvas 方案：可见区域绘制到 Canvas，分层（网格层、内容层、选区层）
        ├─ 只重绘变化的区域
        ├─ OffscreenCanvas 在 Worker 中绘制（可选）
        └─ 编辑时在单元格位置覆盖一个 DOM 输入框

交互层
  ├─ 滚动：合成线程滚动 + 绘制缓冲区
  └─ 选区、拖拽：坐标计算，不依赖 DOM 事件委托
```

**关键设计**

- **选型**：十万级以下、交互简单用 DOM 虚拟化；百万级单元格、复杂交互用 Canvas
- **Canvas 的代价**：自行实现文本选择、无障碍、输入法、复制粘贴
- **增量计算**：公式依赖图，只重新计算受影响的单元格
- **内存**：数据分块，远离可见区域的块可以释放

**关键指标**

- 滚动帧率、首次渲染时间
- 编辑、排序等交互的响应时间
- 内存占用

**口述模板（2–3 分钟）**

先确认数据规模和交互需求。十万行以内、交互简单，我会用 DOM 二维虚拟化，固定行高，单元格尽量轻量。如果是在线表格那种百万级单元格、需要冻结、合并、公式的场景，我会用 Canvas 渲染：只绘制可见区域，按网格、内容、选区分层，只重绘变化的部分，编辑时在单元格位置覆盖一个 DOM 输入框。数据按块存储和按需加载，排序筛选和公式计算放到 Worker，公式用依赖图做增量计算。Canvas 的代价是需要自己实现文本选择、无障碍和复制粘贴，所以要评估投入。

**扩展追问**

- Canvas 方案怎么支持无障碍？→ 维护一个与可见区域对应的隐藏 DOM 结构或 ARIA 网格，供屏幕阅读器使用。

### S6. App 内 H5 秒开方案

- **难度**: 高级
- **标签**: Hybrid, 首屏

**澄清问题（面试时先问）**

- 有多少 H5 页面？更新频率？
- App 是否支持离线包、预创建 WebView？
- 当前打开耗时的组成（WebView 初始化、网络、渲染）？

**参考方案**

```text
用户点击入口
  ├─ [App] 复用预创建的 WebView（省去初始化 100–300ms）
  ├─ [App] 并行预取页面数据（通过 JSBridge 传给页面）
  └─ [App] 拦截资源请求，从本地离线包读取 HTML / JS / CSS

离线包体系
  ├─ 构建：每个业务产出离线包（资源 + manifest + 版本）
  ├─ 发布：离线包平台管理版本、灰度、回滚
  ├─ 下发：App 启动或空闲时检查更新，增量（diff）下载
  └─ 兜底：离线包不存在或校验失败时走线上资源

页面侧
  ├─ 首屏 SSR 或预渲染的 HTML 快照
  ├─ 从 JSBridge 获取预取的数据
  └─ 骨架屏写在 HTML 中
```

**关键设计**

- **耗时拆解**：WebView 初始化 → 网络请求 → 资源下载 → JS 执行 → 数据请求 → 渲染，逐段消除
- **离线包的一致性**：版本校验、签名防篡改、灰度、强制更新
- **数据预取**：App 知道要打开哪个页面，可以和 WebView 初始化并行请求数据
- **监控**：在 App 和 H5 两端打点，统一计算打开耗时

**关键指标**

- 页面打开耗时（从点击到首屏可见）P75
- 离线包命中率
- 白屏率

**口述模板（2–3 分钟）**

我会先拆解 H5 打开的耗时：WebView 初始化、网络、资源下载、JS 执行、数据请求和渲染。App 侧预创建并复用 WebView，省掉初始化；用户点击时并行预取页面数据，通过 JSBridge 交给页面；资源通过离线包从本地读取，消除网络耗时。离线包有专门的平台管理版本、灰度和回滚，App 空闲时增量更新，并有签名校验和线上兜底。页面侧使用预渲染的 HTML 和内联骨架屏。最终衡量从点击到首屏可见的 P75 和离线包命中率。

**扩展追问**

- 离线包更新不及时导致线上 Bug 怎么办？→ 支持强制更新和按版本禁用离线包，关键修复可以直接回退到线上资源。

### S7. 图片资源处理与分发平台

- **难度**: 中级
- **标签**: 图片, CDN

**澄清问题（面试时先问）**

- 图片来源：运营上传、用户上传（UGC）、商品图？
- 规模：日新增图片数、访问量？
- 需要哪些处理：缩放、裁剪、格式转换、水印？

**参考方案**

```text
上传
  ├─ 前端：客户端压缩（大图先缩放）、获取宽高
  └─ 服务端：存储原图到对象存储，记录宽高、主色

分发（图片服务 + CDN）
  URL：https://img.example.com/{id}?w=800&q=75&fmt=auto
  ├─ CDN 命中 → 直接返回
  └─ 未命中 → 图片服务实时处理（缩放、转码）→ 回写 CDN
       └─ fmt=auto：根据 Accept 头返回 AVIF / WebP / JPEG（响应 Vary: Accept）

前端组件
  ├─ 根据容器宽度和 DPR 生成 srcset
  ├─ 宽高比占位（防 CLS），主色或低质量占位图（LQIP）
  └─ 首屏 priority，其他懒加载
```

**关键设计**

- **尺寸档位有限**：只允许固定的宽度档位（如 320、640、960、1280），提高 CDN 命中率
- **格式协商**：`Vary: Accept` 让 CDN 按格式分别缓存
- **原图保护**：限制最大尺寸，防止被滥用请求超大处理
- **组件统一**：业务统一使用图片组件，最佳实践内置

**关键指标**

- 图片平均体积、CDN 命中率
- LCP 图片的加载耗时
- 处理服务的耗时和成本

**口述模板（2–3 分钟）**

图片平台分为上传、分发和前端组件三部分。上传时记录原图和宽高、主色信息。分发通过 URL 参数指定宽度、质量和格式，CDN 未命中时由图片服务实时处理并回写 CDN；格式设置为 auto 时根据 Accept 头返回 AVIF 或 WebP，并设置 Vary 让 CDN 分别缓存。为了提高命中率，宽度只允许固定档位。前端统一使用图片组件，根据容器宽度生成 srcset，用宽高比和主色占位防止 CLS，首屏图片高优先级，其他懒加载。

**扩展追问**

- 为什么限制宽度档位？→ 任意宽度会产生大量不同的缓存键，CDN 命中率低，回源处理成本高。

### S8. 内容站从 CSR 改造为 SSR / 边缘渲染

- **难度**: 高级
- **标签**: SSR, 架构

**澄清问题（面试时先问）**

- 为什么要改造：SEO、首屏性能还是两者都有？
- 内容更新频率？是否个性化？
- 团队对 Node 服务运维的能力？

**参考方案**

```text
渲染策略按页面类型选择
  ├─ 文章详情（更新少、访问多）：SSG / ISR，CDN 缓存
  ├─ 列表页（更新较频繁）：SSR + 边缘缓存（s-maxage + stale-while-revalidate）
  └─ 个人中心（个性化）：CSR 或 SSR 不缓存

服务架构
  CDN ── 边缘缓存 ── 渲染服务（Node 集群或边缘函数）── BFF ── 内容服务
                       ├─ 流式渲染
                       ├─ 页面缓存（Redis）
                       └─ 降级：渲染失败返回 CSR shell

改造步骤
  1. 代码同构：去除对 window、document 的直接依赖
  2. 数据获取改为路由级 loader
  3. 新框架（Next.js / Nuxt / React Router 框架模式）或自建
  4. 按页面灰度切换
```

**关键设计**

- **按页面选择渲染策略**，而不是全站 SSR
- **缓存是关键**：没有缓存的 SSR 在高流量下成本高、TTFB 不稳定
- **降级**：服务端异常或超时时返回 CSR shell，保证可用性
- **水合成本**：控制客户端 JS，考虑 RSC 或孤岛架构
- **运维**：容量规划、内存泄漏监控（SSR 服务中的全局状态泄漏很常见）

**关键指标**

- TTFB、LCP 的 P75
- SSR 渲染耗时、缓存命中率、降级率
- SEO 收录量、自然流量

**口述模板（2–3 分钟）**

我不会全站一刀切地做 SSR，而是按页面类型选择：文章详情更新少、访问多，用 SSG 或 ISR；列表页用 SSR 加边缘缓存和 stale-while-revalidate；个性化页面保留 CSR。服务架构是 CDN 边缘缓存在前，渲染服务做流式渲染并有 Redis 页面缓存，渲染失败或超时降级返回 CSR shell。改造先从代码同构开始，把数据获取改成路由级 loader，再按页面灰度切换。关键是缓存和降级，没有缓存的 SSR 成本高、TTFB 不稳定；另外要监控 SSR 服务的内存泄漏。

**扩展追问**

- 边缘渲染和中心化 SSR 怎么选？→ 边缘渲染 TTFB 低，但运行时受限（不能使用完整的 Node API），数据源在中心时还需要考虑数据访问延迟。
