# 前端性能优化高级 Q&A

> 目标：理解指标的计算细节和数据分析方法，能系统排查复杂的性能问题（首屏、交互、水合、内存），能建立性能治理体系并用数据证明收益。

---

## 一、指标与度量深入

### Q1. LCP 的计算有哪些容易被忽略的细节？

- **难度**: 高级
- **标签**: LCP, 指标

**答案**

1. **停止条件**：用户首次点击、按键（滚动不算）或页面隐藏后，不再产生新的 LCP 候选。所以页面在后台标签打开时，LCP 只统计可见期间
2. **元素被移除**：Chrome 中元素被移除后仍可作为 LCP（以前不是），轮播图等场景会受影响
3. **跨浏览器差异**：Chrome 测量到 `presentationTime`（像素实际显示），Firefox 和 Safari 测量到 `paintTime`，有几毫秒差异；Chrome 145 起也暴露 `paintTime`，便于横向对比
4. **预渲染页面**：LCP 应从页面激活（`activationStart`）开始计算，web-vitals 已处理
5. **bfcache 恢复**：从 bfcache 恢复视为新的页面访问，web-vitals 会用恢复后的第一帧计算
6. **跨源图片**：没有 `Timing-Allow-Origin` 响应头时，`renderTime` 为 0，只能拿到 `loadTime`
7. **图片的渐进加载**：图片首帧渲染时（而不是完全加载时）即可计为 LCP（Chrome 的渐进式图片处理以官方为准）

**口述模板（30–60 秒）**

1. 一句话结论：LCP 的细节在于停止条件、预渲染和 bfcache 的处理，以及跨源图片的时间精度。
2. 关键机制：用户交互后停止更新候选；预渲染页面从激活时开始计算。
3. 对比或注意点：跨源图片需要 Timing-Allow-Origin 才能拿到准确的渲染时间。
4. 可追问时补充：浏览器之间的测量终点略有不同，横向对比时要注意。

**常见追问**

- 自己用 PerformanceObserver 采集和 web-vitals 有什么区别？→ web-vitals 处理了预渲染、bfcache、后台标签页、停止条件等边界情况，自己实现容易出错。

### Q2. INP 的计算细节是什么？

- **难度**: 高级
- **标签**: INP, 指标

**答案**

1. **基于 Event Timing API**：浏览器记录每个事件的 `startTime`（输入时间）、`processingStart`、`processingEnd`、`duration`（到下一帧绘制）
2. **交互分组**：同一次交互会产生多个事件（`pointerdown`、`pointerup`、`click`），通过 `interactionId` 分组，取组内最长的 `duration`
3. **duration 精度**：以 8ms 为粒度取整
4. **取值**：交互少于 50 次时取最大值；超过 50 次时，每 50 次交互忽略一个最高值（近似取 P98）
5. **不计入**：滚动、悬停；只计入点击、触摸、按键
6. **没有交互的页面**：没有 INP 值
7. **跨浏览器**：Firefox 144、Safari 26.2 起支持 `interactionId`，Safari 的实现初期存在一些异常值（以官方为准）

**口述模板（30–60 秒）**

1. 一句话结论：INP 基于 Event Timing API，按 interactionId 把事件分组，取近似最差的一次。
2. 关键机制：每次交互取组内最长的 duration，交互超过 50 次时每 50 次忽略一个最高值。
3. 对比或注意点：滚动和悬停不计入，没有交互的页面没有 INP。
4. 可追问时补充：duration 是到下一帧绘制，所以包含渲染时间。

**常见追问**

- 为什么不取最大值？→ 交互多的页面难免有偶发的异常，忽略极少数最高值可以避免一次异常决定整个指标。

### Q3. Long Animation Frames（LoAF）怎么用来定位问题？

- **难度**: 高级
- **标签**: LoAF, INP

**答案**

LoAF（Chrome 123+）以**帧**为单位报告超过 50ms 的长帧，比 Long Tasks API 信息丰富得多：

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report({
      duration: entry.duration,
      blockingDuration: entry.blockingDuration,   // 阻塞时长
      renderStart: entry.renderStart,             // 渲染阶段开始
      styleAndLayoutStart: entry.styleAndLayoutStart,
      scripts: entry.scripts.map((s) => ({
        sourceURL: s.sourceURL,                   // 脚本文件
        sourceFunctionName: s.sourceFunctionName,
        invoker: s.invoker,                       // 例如 'BUTTON#buy.onclick'
        duration: s.duration,
        forcedStyleAndLayoutDuration: s.forcedStyleAndLayoutDuration, // 强制布局耗时
      })),
    })
  }
}).observe({ type: 'long-animation-frame', buffered: true })
```

**价值**：

- 知道是**哪个脚本、哪个函数**导致的长帧（区分业务代码与第三方脚本）
- 区分脚本耗时与渲染耗时
- 直接给出强制同步布局的耗时
- web-vitals 的 INP attribution 已关联交互对应的 LoAF

**口述模板（30–60 秒）**

1. 一句话结论：LoAF 以帧为单位报告长帧，并给出脚本级别的归因。
2. 关键机制：包括脚本来源、调用方、函数名、强制布局耗时、渲染开始时间。
3. 对比或注意点：Long Tasks 只告诉你有长任务，不告诉你原因。
4. 可追问时补充：线上按 sourceURL 聚合，可以快速发现拖慢页面的第三方脚本。

**常见追问**

- 跨源脚本能拿到归因吗？→ 只能拿到有限的信息（如 URL），函数名等细节受限于同源策略。

### Q4. 怎么分析真实用户性能数据（RUM）？

- **难度**: 高级
- **标签**: RUM, 数据分析

**答案**

1. **看分位数而不是平均值**：P75 用于达标评估，P95 / P99 用于发现长尾问题
2. **分维度**：页面、设备类型、设备性能、网络类型、地区、浏览器、新老用户（有无缓存）、App 内 / 浏览器
3. **看分布**：直方图可能是双峰（例如缓存命中与未命中），平均值会掩盖问题
4. **采样**：大流量网站按比例采样，但低流量页面要提高采样率以保证样本量
5. **区分变化原因**：指标变化可能来自用户构成变化（例如营销活动引入大量低端机用户），而不是代码问题
6. **与 CrUX 对齐**：CrUX 统计 28 天滚动窗口、只包含 Chrome 用户、有特定的入选条件；自建 RUM 与 CrUX 存在差异是正常的
7. **关联版本**：上报中带上发布版本号，方便对比发布前后

**口述模板（30–60 秒）**

1. 一句话结论：RUM 分析要看分位数、分维度和分布，而不是平均值。
2. 关键机制：按设备、网络、地区、版本拆分，找到问题集中的人群。
3. 对比或注意点：指标变化可能来自用户构成变化，要排除干扰。
4. 可追问时补充：上报带版本号，才能对比发布前后的效果。

**常见追问**

- 为什么自建 RUM 和 CrUX 数据不一致？→ 统计口径不同：CrUX 只包含 Chrome 用户、按 28 天滚动，采集条件也不同。

### Q5. 实验室数据很好但线上指标很差，可能是什么原因？

- **难度**: 高级
- **标签**: 度量, 排查

**答案**

| 原因 | 说明 |
|------|------|
| 设备差异 | 用户多为中低端安卓，CPU 比实验室模拟的更慢 |
| 网络差异 | 弱网、高延迟地区、跨国访问 |
| 缓存状态 | 实验室通常测首次访问；也可能反过来，线上命中缓存更多 |
| 用户行为 | 实验室没有交互，无法测 INP；用户可能在加载完成前就交互 |
| 个性化内容 | 登录态、A/B 实验、广告导致页面内容不同 |
| 第三方脚本 | 实验室可能被拦截或加载更快 |
| 页面生命周期 | CLS 在用户滚动、长时间停留后才出现 |
| 入口差异 | 用户从 App 内 WebView、搜索结果、社交平台进入 |

**解决**：用 RUM 数据找到问题人群（设备、网络、页面），在实验室中模拟这些条件复现。

**口述模板（30–60 秒）**

1. 一句话结论：主要原因是设备、网络、缓存状态和用户行为的差异。
2. 关键机制：实验室是固定环境，无法覆盖真实用户的多样性。
3. 对比或注意点：INP 和部分 CLS 只能在真实用户中测量。
4. 可追问时补充：用 RUM 分维度找到问题人群，再在实验室中针对性模拟。

**常见追问**

- 怎么在实验室中模拟低端机？→ CPU 节流 4–6 倍，或者用真机（WebPageTest 提供真实设备）。

## 二、复杂问题排查

### Q6. 首屏 LCP 线上 P75 为 4 秒，你会怎么排查和优化？

- **难度**: 高级
- **标签**: LCP, 排查

**答案**

**1. 确认范围**：按设备、网络、页面、地区拆分，看是普遍问题还是集中在某类人群。

**2. 看 LCP 元素和四段拆解**（RUM attribution 数据）：

| 占比最高的阶段 | 典型原因 | 优化 |
|---------------|---------|------|
| TTFB | SSR 慢、无 CDN、重定向 | 缓存、边缘、流式、103 Early Hints |
| 加载延迟 | LCP 图片由 JS 渲染、CSS 背景图、懒加载 | 写入 HTML、preload、fetchpriority |
| 加载耗时 | 图片大、格式旧 | AVIF / WebP、响应式尺寸、CDN |
| 渲染延迟 | 阻塞的 CSS / JS、等待水合或数据 | 关键 CSS、defer、SSR、减少主线程任务 |

**3. CSR 页面的典型链路**：HTML → 下载 JS（大） → 执行 → 请求数据 → 渲染 → 请求图片。每一步都是串行的。优化：SSR 或预渲染；首屏数据内联到 HTML；JS 拆分。

**4. 验证**：灰度发布，对比实验组和对照组的 P75。

**口述模板（30–60 秒）**

1. 一句话结论：先分人群确认范围，再用 LCP 四段拆解找到占比最高的阶段。
2. 关键机制：TTFB 问题看服务端和网络，加载延迟看资源发现，加载耗时看体积，渲染延迟看阻塞资源。
3. 对比或注意点：CSR 页面的瓶颈通常是串行的请求链，需要 SSR 或数据内联。
4. 可追问时补充：用灰度对照验证效果，而不是只看发布前后的数据。

**常见追问**

- 优化后 LCP 没有改善怎么办？→ 检查 LCP 元素是否变了（例如优化图片后 LCP 变成了一段文字），以及优化是否真正覆盖了问题人群。

### Q7. 用户反馈页面操作卡顿，你会怎么排查？

- **难度**: 高级
- **标签**: INP, 排查

**答案**

**1. 量化**：查看该页面的 INP P75 和最差交互（按交互元素聚合）。

**2. 拆解**：

- **输入延迟高**：交互时主线程被其他任务占用 → 查看 LoAF 中的脚本：定时器轮询、第三方脚本、水合、大量数据处理
- **处理耗时高**：事件处理函数慢 → 同步计算、状态更新导致大范围重渲染、同步的埋点
- **呈现延迟高**：渲染成本高 → DOM 过大、样式计算复杂、强制同步布局

**3. 本地复现**：CPU 节流，Performance 面板录制，查看 Interactions 轨道中最长的交互，展开对应的任务。

**4. 常见问题与处理**：

| 问题 | 处理 |
|------|------|
| 状态更新导致整页重渲染 | 状态下沉、memo、拆分 Context、`useTransition` |
| 大列表 | 虚拟列表 |
| 同步大计算 | Worker、分片 |
| 第三方脚本 | 延迟加载、门面模式 |
| 布局抖动 | 读写分离 |

**口述模板（30–60 秒）**

1. 一句话结论：先用 INP 数据找到最差的交互，再按三段拆解定位。
2. 关键机制：输入延迟看其他任务，处理耗时看事件回调，呈现延迟看渲染成本。
3. 对比或注意点：本地必须开启 CPU 节流才能复现。
4. 可追问时补充：LoAF 可以直接告诉你是哪个脚本导致的。

**常见追问**

- 卡顿只在某些用户中出现怎么办？→ 看这些用户的设备和数据量，很可能是数据量大的用户（例如列表很长）或低端设备。

### Q8. SSR 水合有什么性能问题？怎么优化？

- **难度**: 高级
- **标签**: SSR, 水合

**答案**

**问题**：

1. **重复工作**：服务端已经渲染过，客户端还要下载全部组件代码、重新执行渲染逻辑来绑定事件
2. **长任务**：水合通常是一个大任务，期间无法响应交互（页面看起来可用但点不动）
3. **数据重复**：服务端数据序列化到 HTML 中，增加 HTML 体积
4. **水合不匹配**：服务端和客户端渲染结果不一致，导致重新渲染

**优化**：

| 方案 | 原理 |
|------|------|
| 流式 SSR + 选择性水合（React 18+） | Suspense 边界内的内容独立水合，用户交互的区域优先水合 |
| React Server Components | 服务端组件的代码不发送到客户端，只有客户端组件需要水合 |
| 孤岛架构（Astro） | 页面默认是静态 HTML，只有交互组件（孤岛）水合 |
| 可恢复性（Qwik） | 不需要水合，事件触发时才加载对应代码 |
| 延迟水合 | 首屏外的组件在可见或空闲时才水合 |

**口述模板（30–60 秒）**

1. 一句话结论：水合需要重复执行组件代码，产生长任务，导致页面看起来可用但无法交互。
2. 关键机制：优化方向是减少需要水合的代码和把水合拆分。
3. 对比或注意点：RSC 和孤岛架构减少客户端代码，选择性水合优先处理用户交互的区域。
4. 可追问时补充：水合不匹配会导致额外的重新渲染，要排查日期、随机数等不确定输出。

**常见追问**

- 怎么衡量水合成本？→ Performance 面板中查看水合的长任务时长；React DevTools Profiler 查看水合阶段。

### Q9. React Server Components 对性能有什么影响？

- **难度**: 高级
- **标签**: RSC, React

**答案**

**收益**：

- **减少客户端 JS**：服务端组件（及其依赖，如 Markdown 解析器、日期库）不会发送到客户端
- **数据获取在服务端**：靠近数据源，避免客户端请求瀑布
- **流式传输**：配合 Suspense 逐步发送内容
- **自动代码分割**：客户端组件按需加载

**成本与风险**：

- 每次导航需要服务端渲染，服务端负载和 TTFB 增加，需要缓存策略
- 服务端组件中的串行 `await` 会形成服务端瀑布
- 客户端组件边界划分不当（`'use client'` 放得太高）会失去收益
- RSC payload 也有体积，过度传递数据会增大 payload

**口述模板（30–60 秒）**

1. 一句话结论：RSC 主要通过减少客户端 JS 和把数据获取移到服务端来提升性能。
2. 关键机制：服务端组件的代码不发送到客户端，只发送渲染结果。
3. 对比或注意点：服务端负载增加，'use client' 边界划分不当会失去收益。
4. 可追问时补充：服务端也会有请求瀑布，要并行获取数据。

**常见追问**

- `'use client'` 应该放在哪里？→ 尽量放在组件树的叶子节点（真正需要交互的组件），而不是页面顶层。

### Q10. 复杂中后台（大表格、大量表单）怎么优化？

- **难度**: 高级
- **标签**: 中后台, 渲染

**答案**

**大表格（万行 × 百列）**：

- **二维虚拟化**：行和列都虚拟化
- 固定行高，避免测量
- 单元格组件轻量化，避免每个单元格使用复杂组件
- 排序、筛选、聚合在 Worker 中进行
- 极端场景用 Canvas 渲染表格（例如在线表格产品）

**大表单（数百个字段）**：

- 非受控组件或细粒度订阅（React Hook Form），避免任意字段变化导致整个表单渲染
- 字段级状态管理，校验防抖
- 分组折叠，懒渲染不可见的分组

**数据层**：

- 大数据集不要放入响应式系统（Vue 用 `shallowRef`，React 避免放入频繁变化的 Context）
- 归一化数据结构，避免深拷贝

**口述模板（30–60 秒）**

1. 一句话结论：大表格用二维虚拟化和 Worker，大表单用细粒度订阅。
2. 关键机制：只渲染可见单元格，任意字段变化只更新该字段。
3. 对比或注意点：数据层要避免大数据进入响应式系统。
4. 可追问时补充：极端场景可以用 Canvas 渲染，绕开 DOM 的成本。

**常见追问**

- Canvas 表格的代价是什么？→ 需要自己实现文本选择、无障碍、可编辑单元格等，开发成本很高。

### Q11. 怎么针对低端设备做性能分级？

- **难度**: 高级
- **标签**: 设备, 分级

**答案**

**1. 设备分级依据**：

- `navigator.hardwareConcurrency`（CPU 核数）
- `navigator.deviceMemory`（内存，Chromium）
- UA 中的机型映射（App 内可以直接获取机型评分）
- 运行时测量：启动时跑一段基准测试，或根据历史帧率数据

**2. 分级策略**：

| 等级 | 策略 |
|------|------|
| 高端 | 完整功能和动画 |
| 中端 | 减少动画、降低图片质量 |
| 低端 | 关闭非必要动画和特效、减少首屏模块、简化组件、降低实时更新频率 |

**3. 原则**：

- 分级不应该影响核心功能
- 分级结果缓存，避免每次检测
- 用数据验证：分级后低端机的 INP 和 LCP 是否改善

**口述模板（30–60 秒）**

1. 一句话结论：根据 CPU、内存等信息给设备分级，低端设备降级非核心体验。
2. 关键机制：高端设备完整体验，低端设备关闭动画、减少模块、降低更新频率。
3. 对比或注意点：分级不能影响核心功能。
4. 可追问时补充：P75 通常由中低端设备决定，所以分级对指标的改善很明显。

**常见追问**

- `deviceMemory` 不准怎么办？→ 它是粗略值（且有上限），可以结合核数、机型和运行时帧率综合判断。

### Q12. 讲一个线上内存泄漏的排查案例

- **难度**: 高级
- **标签**: 内存, 案例

**答案**

**场景**：中后台 SPA，用户长时间使用后页面越来越卡，最终崩溃。

**排查过程**：

1. 复现：反复切换某两个路由，Performance monitor 显示 JS Heap 和 DOM 节点数持续增长，手动 GC 后不下降
2. 三快照对比：发现大量 `Detached HTMLDivElement` 和图表库的实例
3. 查看 Retainers：游离节点被图表库内部的 `resize` 监听闭包持有，监听注册在 window 上
4. 根因：组件卸载时没有调用图表实例的 `dispose()`，window 上的监听一直存在，引用了整个图表 DOM 和数据

**修复**：

```tsx
useEffect(() => {
  const chart = echarts.init(ref.current!)
  chart.setOption(option)
  return () => chart.dispose()
}, [])
```

**预防**：

- Code Review 检查副作用清理
- E2E 测试中加入内存回归（反复操作后检查堆大小）
- 线上监控长会话的内存趋势

**口述模板（30–60 秒）**

1. 一句话结论：通过三快照对比和引用链，定位到图表实例未销毁导致的泄漏。
2. 关键机制：window 上的监听闭包持有了游离 DOM 和数据。
3. 对比或注意点：SPA 中泄漏会随使用时长累积，短时间测试发现不了。
4. 可追问时补充：在 E2E 中加入内存回归测试防止再次出现。

**常见追问**

- 怎么在 E2E 中检测内存？→ Playwright 中通过 CDP 调用 `HeapProfiler.collectGarbage` 后读取 `Runtime.getHeapUsage`，对比操作前后的增长。

### Q13. 怎么治理第三方脚本？

- **难度**: 高级
- **标签**: 第三方, 治理

**答案**

**1. 盘点与归因**

- 列出所有第三方脚本：负责人、用途、加载方式、体积、主线程耗时
- 线上通过 LoAF 按 sourceURL 聚合主线程耗时

**2. 加载策略分级**

| 级别 | 示例 | 策略 |
|------|------|------|
| 关键 | 支付、登录 SDK | 按需加载（进入对应流程时） |
| 重要 | 监控、错误上报 | 异步加载，尽量早但不阻塞 |
| 一般 | 统计、广告 | `load` 后或空闲时加载 |
| 可选 | 客服、聊天 | 门面模式，用户交互时加载 |

**3. 技术手段**

- 自托管 + 长期缓存（注意更新机制）
- Partytown 等方案把部分脚本移到 Worker（适合纯统计类脚本，有兼容性风险）
- 用 CSP 控制可加载的域名

**4. 流程**：新增第三方脚本需要评审性能影响，设置性能预算。

**口述模板（30–60 秒）**

1. 一句话结论：先盘点和归因，再按重要程度分级加载，并建立准入流程。
2. 关键机制：LoAF 按脚本来源聚合主线程耗时，量化每个第三方的成本。
3. 对比或注意点：大部分第三方脚本可以在 load 后或交互时才加载。
4. 可追问时补充：新增第三方需要性能评审，避免无序增长。

**常见追问**

- 运营坚持要加某个统计脚本怎么办？→ 用数据说明它对指标和转化的影响，提出延迟加载的方案作为折中。

### Q14. 微前端架构有哪些性能问题？

- **难度**: 高级
- **标签**: 微前端

**答案**

| 问题 | 原因 | 处理 |
|------|------|------|
| 依赖重复 | 每个子应用打包了自己的 React、组件库 | 模块联邦共享依赖、externals + CDN |
| 加载链路长 | 主应用 → 获取配置 → 加载子应用入口 → 加载子应用资源 | 预加载子应用、配置内联到 HTML |
| 沙箱开销 | Proxy 沙箱拦截全局变量访问 | 减少全局访问，或者使用更轻量的隔离 |
| 样式重复和冲突 | 多个子应用加载相同的样式 | 共享样式库 |
| 内存 | 子应用卸载不彻底 | 规范卸载生命周期，检查泄漏 |
| 监控割裂 | 各子应用独立上报 | 统一的性能 SDK，在主应用中采集 |

**口述模板（30–60 秒）**

1. 一句话结论：微前端的主要性能问题是依赖重复、加载链路长和沙箱开销。
2. 关键机制：共享依赖、预加载子应用、规范卸载。
3. 对比或注意点：子应用切换时的内存泄漏很常见。
4. 可追问时补充：性能监控要在主应用中统一采集。

**常见追问**

- 怎么预加载子应用？→ 主应用空闲时预取子应用的入口和关键资源，或者根据用户行为预测。

### Q15. 首屏数据请求怎么优化？

- **难度**: 高级
- **标签**: 数据, 首屏

**答案**

**典型问题**：CSR 页面中，组件挂载后才发起请求，形成瀑布；首屏需要多个接口串行调用。

**优化**：

1. **提前发起**：
   - 在 HTML 中内联一段脚本，与 JS bundle 下载并行发起首屏请求
   - 路由 loader：路由匹配时就请求数据，而不是组件挂载时
2. **并行化**：没有依赖的请求同时发起
3. **聚合**：BFF 把多个接口聚合为一个，减少往返
4. **数据内联**：SSR 时把数据直接序列化到 HTML 中
5. **缓存**：SWR 策略，先展示缓存数据再更新
6. **App 内预取**：App 在打开 WebView 的同时请求数据，通过 JSBridge 传给页面

```html
<script>
  // 与主 bundle 下载并行发起首屏请求
  window.__FIRST_SCREEN__ = fetch('/api/home').then((r) => r.json())
</script>
<script type="module" src="/main.js"></script>
```

**口述模板（30–60 秒）**

1. 一句话结论：首屏数据请求要尽早发起、并行执行、减少往返。
2. 关键机制：在 HTML 中内联请求、路由 loader、BFF 聚合、SSR 数据内联。
3. 对比或注意点：组件挂载后才请求会形成瀑布。
4. 可追问时补充：App 内可以在打开 WebView 时并行预取数据。

**常见追问**

- 内联的请求失败了怎么办？→ 业务代码中检查 Promise 状态，失败时重新请求。

### Q16. 滚动性能有哪些优化点？

- **难度**: 高级
- **标签**: 渲染, 滚动

**答案**

1. **被动监听**：`{ passive: true }` 告诉浏览器监听器不会调用 `preventDefault`，浏览器不需要等待 JS 执行就可以滚动（合成线程滚动）

```js
window.addEventListener('touchstart', onTouch, { passive: true })
```

Chrome 对 window / document 上的 `touchstart`、`touchmove`、`wheel` 默认已经是 passive。

2. **避免滚动时执行重活**：用 IntersectionObserver 代替 scroll 监听计算位置
3. **滚动驱动动画**：使用 CSS Scroll-driven Animations（`animation-timeline: scroll()` / `view()`），在合成线程运行，不需要 JS
4. **非快速滚动区域**：带有非 passive 事件监听的区域，合成线程必须等待主线程，主线程忙时滚动卡顿
5. **固定定位元素和大量阴影、滤镜**：增加合成和绘制成本
6. **长页面**：`content-visibility: auto`

**口述模板（30–60 秒）**

1. 一句话结论：滚动优化的核心是让滚动在合成线程中完成，不依赖主线程。
2. 关键机制：passive 监听让浏览器无需等待 JS，滚动驱动动画也在合成线程运行。
3. 对比或注意点：非 passive 的监听会让该区域的滚动依赖主线程。
4. 可追问时补充：IntersectionObserver 代替 scroll 监听计算位置。

**常见追问**

- 为什么非 passive 监听会导致卡顿？→ 浏览器必须等待 JS 执行完，才知道是否调用了 preventDefault 阻止滚动。

### Q17. Web Worker 在复杂场景下怎么用？

- **难度**: 高级
- **标签**: Worker, 多线程

**答案**

1. **简化通信**：Comlink 把 Worker 包装成 RPC 调用

```js
// main.js
import * as Comlink from 'comlink'
const api = Comlink.wrap(new Worker(new URL('./worker.js', import.meta.url), { type: 'module' }))
const result = await api.analyze(data)
```

2. **降低传输成本**：
   - Transferable：`postMessage(buffer, [buffer])` 转移所有权，零拷贝
   - SharedArrayBuffer：多线程共享内存，配合 `Atomics` 同步；需要**跨源隔离**（`COOP: same-origin` + `COEP: require-corp`）
3. **OffscreenCanvas**：把 Canvas 渲染移到 Worker（图表、游戏）
4. **线程池**：按 `hardwareConcurrency` 创建多个 Worker，并行处理分片数据
5. **Worker 中的 WebAssembly**：计算密集型任务进一步加速

**注意**：Worker 的启动成本、内存开销、调试复杂度。

**口述模板（30–60 秒）**

1. 一句话结论：复杂场景下 Worker 需要处理通信成本、并行和渲染。
2. 关键机制：Comlink 简化通信，Transferable 和 SharedArrayBuffer 减少传输成本，OffscreenCanvas 移出渲染。
3. 对比或注意点：SharedArrayBuffer 需要跨源隔离，会影响第三方资源加载。
4. 可追问时补充：线程池按 CPU 核数创建，并行处理数据分片。

**常见追问**

- 跨源隔离有什么影响？→ 所有跨源资源都必须通过 CORS 或 CORP 明确允许被加载，否则会被阻止，第三方资源需要配合。

### Q18. 什么场景适合用 WebAssembly 提升性能？

- **难度**: 高级
- **标签**: Wasm

**答案**

**适合**：

- 计算密集型：图像 / 视频处理、音频编解码、压缩、加密
- 已有 C / C++ / Rust 库的移植：例如 FFmpeg、SQLite、OpenCV
- 需要稳定、可预测性能的场景（没有 JIT 预热和去优化）

**不适合**：

- DOM 操作密集的场景（Wasm 访问 DOM 需要经过 JS）
- 频繁的 JS ↔ Wasm 小粒度调用（边界开销）
- 简单逻辑（现代 JS 引擎已经很快，收益不明显）

**注意**：

- Wasm 文件体积可能很大，需要流式编译（`WebAssembly.instantiateStreaming`）和缓存
- 在 Worker 中运行，避免阻塞主线程

**口述模板（30–60 秒）**

1. 一句话结论：Wasm 适合计算密集型任务和移植现有的原生库。
2. 关键机制：接近原生的执行速度，性能稳定可预测。
3. 对比或注意点：DOM 操作和频繁的小粒度调用不适合。
4. 可追问时补充：放在 Worker 中运行，并用流式编译减少加载时间。

**常见追问**

- Wasm 一定比 JS 快吗？→ 不一定。对于普通业务逻辑，JIT 优化后的 JS 很快，加上边界开销，Wasm 可能没有优势。

### Q19. 怎么建立性能监控体系？

- **难度**: 高级
- **标签**: 监控, 治理

**答案**

```text
采集 SDK → 上报 → 清洗与存储 → 聚合分析 → 可视化与告警 → 归因与排查
```

- **采集**：Core Web Vitals + 归因、资源加载、接口耗时、长任务 / LoAF、业务自定义指标、错误
- **上报**：`sendBeacon`、批量、采样、页面隐藏时上报
- **存储**：时序数据库或 OLAP（ClickHouse），保留原始明细用于下钻
- **分析**：按页面、版本、设备、地区等维度计算 P75 / P95
- **告警**：基于基线的相对变化告警（例如 P75 比上周同期恶化 10%），而不是固定阈值
- **归因**：从指标下钻到具体的会话和资源

详见 [系统设计 S1](50-system-design.md)。

**口述模板（30–60 秒）**

1. 一句话结论：监控体系包括采集、上报、存储、分析、告警和归因。
2. 关键机制：采集指标和归因信息，按维度计算分位数，基于基线变化告警。
3. 对比或注意点：只有指标没有归因信息，就无法定位问题。
4. 可追问时补充：上报带版本号，关联发布记录。

**常见追问**

- 告警为什么用相对变化？→ 不同页面基线不同，固定阈值要么误报太多，要么漏报。

### Q20. 怎么设计性能预算和 CI 门禁？

- **难度**: 高级
- **标签**: 预算, CI

**答案**

**预算类型**：

| 类型 | 示例 |
|------|------|
| 资源预算 | 首屏 JS ≤ 170KB（gzip），单个 chunk ≤ 250KB |
| 指标预算 | Lighthouse LCP ≤ 2.5s、TBT ≤ 200ms |
| 数量预算 | 首屏请求数、第三方脚本数 |

**CI 门禁**：

- `size-limit`：PR 中报告体积变化，超出预算失败
- Lighthouse CI：对关键页面运行多次取中位数，断言指标
- 在 PR 评论中展示前后对比

**避免误报**：

- 实验室指标有波动：多次运行取中位数，设置容忍区间
- 预算基于当前基线逐步收紧，而不是一开始就设定理想值
- 提供明确的豁免流程（需要说明理由和负责人）

**线上**：发布后比较新版本的 RUM 指标，恶化时告警或自动回滚。

**口述模板（30–60 秒）**

1. 一句话结论：设置资源、指标和数量预算，并在 CI 中自动检查。
2. 关键机制：size-limit 检查体积，Lighthouse CI 检查指标，PR 中展示对比。
3. 对比或注意点：实验室指标有波动，要多次运行并设置容忍区间。
4. 可追问时补充：预算从当前基线开始逐步收紧，并提供豁免流程。

**常见追问**

- 体积预算为什么设置为 gzip 后的大小？→ 用户实际下载的是压缩后的大小；但也要关注压缩前的大小，因为解析和执行的成本与它有关。

### Q21. 怎么证明性能优化带来了收益？

- **难度**: 高级
- **标签**: 方法论

**答案**

**1. 技术指标**

- 发布前后对比：同期对比（避免周末、节假日的流量构成差异），看 P75 和分布
- **更严谨**：A/B 实验或灰度对照，同一时间段、随机分组，排除外部因素

**2. 业务指标**

- 转化率、跳出率、停留时长、留存
- 通过 A/B 实验建立因果关系；或者对比不同性能分组用户的业务指标（相关性，不是因果）

**3. 讲清楚**

- 优化前的基线和问题定位过程
- 具体措施和每项措施的贡献
- 结果：技术指标 + 业务指标
- 如何防止劣化

**常见问题**：只在本地 Lighthouse 中对比；发布前后对比时没有控制其他变量；把多个优化的效果混在一起。

**口述模板（30–60 秒）**

1. 一句话结论：最严谨的方式是 A/B 实验，同时看技术指标和业务指标。
2. 关键机制：随机分组对比，排除流量构成、季节等外部因素。
3. 对比或注意点：只做发布前后对比容易受其他变量影响。
4. 可追问时补充：拆分每项措施的贡献，才能指导后续的优化方向。

**常见追问**

- 没有 A/B 平台怎么办？→ 按地区或按用户 ID 灰度，用同期的对照组对比。

### Q22. 怎么在面试中讲一个性能优化项目？

- **难度**: 高级
- **标签**: 方法论, 面试

**答案**

用 **STAR + 数据**：

1. **背景（S）**：什么页面、什么用户、业务影响（例如首页移动端跳出率高）
2. **目标（T）**：量化的目标（LCP P75 从 4.2s 降到 2.5s 以下）
3. **行动（A）**：
   - 怎么定位：用了什么数据和工具，发现了哪些瓶颈，按影响排序
   - 做了什么：每项措施、为什么这样做、遇到的困难和取舍
4. **结果（R）**：技术指标、业务指标、如何验证、如何防止劣化

**示例**：

> 首页移动端 LCP P75 为 4.2 秒。通过 RUM 的 LCP 拆解发现，加载延迟占 45%——LCP 图片由 JS 渲染才插入，且首屏 JS 有 600KB。我做了三件事：首屏改为 SSR 并把首图写入 HTML、加 fetchpriority；首屏 JS 按路由和组件拆分，降到 220KB；首图改为 AVIF 并按屏幕宽度提供。灰度对照显示 LCP P75 降到 2.3 秒，跳出率下降约 8%。之后在 CI 中加入体积预算和 Lighthouse CI，防止回退。

**避免**：罗列一堆手段没有数据；数据无法解释来源；把团队的成果说成个人的。

**口述模板（30–60 秒）**

1. 一句话结论：用背景、目标、行动、结果的结构，全程带数据。
2. 关键机制：重点讲怎么定位瓶颈，以及每项措施的理由和贡献。
3. 对比或注意点：不要只罗列手段，没有数据的优化项目没有说服力。
4. 可追问时补充：说明如何验证效果和防止劣化。

**常见追问**

- 面试官问「为什么不用其他方案」？→ 提前准备取舍：例如为什么选 SSR 而不是预渲染，成本和收益分别是什么。

### Q23. 性能优化有哪些权衡？什么时候不应该优化？

- **难度**: 高级
- **标签**: 权衡

**答案**

| 权衡 | 说明 |
|------|------|
| 性能 vs 可维护性 | 过度的 memo、手写缓存、复杂的预加载逻辑增加维护成本 |
| 性能 vs 开发效率 | SSR 增加架构复杂度和服务器成本 |
| 加载 vs 交互 | 预加载更多资源可能抢占带宽，或增加主线程负担 |
| 体积 vs 请求数 | 拆分过细增加请求和瀑布 |
| 缓存 vs 一致性 | 缓存越激进，数据越可能过期 |
| 预渲染 vs 资源消耗 | 预测错误时浪费流量和电量 |

**不应该优化的情况**：

- 没有数据证明这是瓶颈
- 优化的收益远小于成本（例如为了 10ms 引入复杂架构）
- 已经达标，且业务没有更高的要求，资源应该投入到其他地方

**原则**：先度量，优化影响最大的瓶颈，验证效果，保持简单。

**口述模板（30–60 秒）**

1. 一句话结论：性能优化需要在可维护性、开发成本和一致性之间权衡。
2. 关键机制：先度量，只优化真正的瓶颈。
3. 对比或注意点：没有数据支撑的优化可能带来复杂度却没有收益。
4. 可追问时补充：已经达标的指标，资源应该优先投入到其他方面。

**常见追问**

- 怎么判断优化是否值得？→ 估算收益（影响的用户比例 × 指标改善幅度）与成本（开发、维护、服务器）。

### Q24. 动态内容的 TTFB 和缓存怎么兼顾？

- **难度**: 高级
- **标签**: TTFB, 缓存

**答案**

**问题**：个性化页面（登录态、推荐）难以缓存，每次都需要服务端渲染。

**方案**：

1. **拆分静态与动态**：页面框架和公共内容缓存在 CDN，个性化部分客户端请求或流式填充
2. **边缘缓存 + stale-while-revalidate**：

```text
Cache-Control: public, s-maxage=60, stale-while-revalidate=600
```

3. **按维度缓存**：按地区、语言、设备类型等有限维度缓存多份（`Vary` 头或缓存键）
4. **部分预渲染（PPR）**：静态 shell 在构建时生成，动态部分在请求时流式填充（Next.js 等框架支持，以官方为准）
5. **边缘渲染**：在离用户近的边缘节点渲染，配合边缘 KV 缓存数据

**口述模板（30–60 秒）**

1. 一句话结论：把页面拆分为可缓存的静态部分和个性化的动态部分。
2. 关键机制：静态部分 CDN 缓存，动态部分流式填充或客户端请求。
3. 对比或注意点：缓存键的维度要有限，避免缓存命中率过低。
4. 可追问时补充：部分预渲染就是这个思路的框架级实现。

**常见追问**

- 用 Cookie 区分用户的页面能缓存吗？→ 不能直接按 Cookie 缓存（命中率太低，还可能泄露数据），要把个性化部分剥离出来。

### Q25. 怎么把性能指标和业务目标关联起来？

- **难度**: 高级
- **标签**: 业务, 方法论

**答案**

1. **找到关键路径**：业务最重要的流程（电商的商品详情 → 加购 → 下单）
2. **定义业务性能指标**：例如「商品详情页首屏可用时间」「下单按钮响应时间」
3. **关联分析**：按性能分组（LCP 好 / 中 / 差）对比转化率，找到性能与业务的关系曲线
4. **实验验证**：通过 A/B 实验（例如人为增加延迟或进行优化），建立因果关系
5. **转化为收益**：例如「LCP 每降低 1 秒，转化率提升 X%」，用于争取资源

**注意**：相关不等于因果——网络差的用户可能本身转化率就低（地区、收入因素）。

**口述模板（30–60 秒）**

1. 一句话结论：找到关键业务路径，分析性能与转化的关系，并通过实验验证因果。
2. 关键机制：按性能分组对比业务指标，用 A/B 实验确认因果关系。
3. 对比或注意点：相关不等于因果，网络差的用户可能本身转化率就低。
4. 可追问时补充：把性能收益转化为业务语言，更容易争取资源。

**常见追问**

- 人为增加延迟做实验合适吗？→ 在小流量、短时间内做是业界常见的方法，但需要业务方同意。

### Q26. 怎么在团队中建立性能文化？

- **难度**: 高级
- **标签**: 治理, 团队

**答案**

1. **可见性**：性能大盘，每个页面的指标和趋势对团队公开
2. **责任**：每个核心页面有性能负责人，指标纳入团队目标
3. **流程**：
   - 需求评审时考虑性能影响（大依赖、第三方脚本、新的首屏模块）
   - CI 门禁和性能预算
   - 发布后监控和告警
4. **工具**：脚手架内置最佳实践（图片组件、懒加载、分包配置），让正确的做法成为默认做法
5. **知识**：性能问题复盘、分享会、优化案例库
6. **激励**：认可性能改进的工作

**口述模板（30–60 秒）**

1. 一句话结论：通过可见性、责任、流程、工具和知识沉淀建立性能文化。
2. 关键机制：大盘让问题可见，CI 门禁防止劣化，脚手架让最佳实践成为默认。
3. 对比或注意点：一次性的优化项目容易回退，需要持续的机制。
4. 可追问时补充：在需求评审阶段就考虑性能，成本最低。

**常见追问**

- 业务需求紧急，性能预算超了怎么办？→ 走豁免流程，记录技术债，并约定偿还时间。
