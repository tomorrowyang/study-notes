# 前端性能优化初级 Q&A

> 目标：掌握性能指标的定义和阈值、常用度量工具、最常见的优化手段。每题包含答案、口述模板和常见追问，边看边记。

---

## 一、性能指标

### Q1. 为什么要做性能优化？怎么衡量性能？

- **难度**: 初级
- **标签**: 概念, 指标

**答案**

**为什么**：性能直接影响业务。加载慢会增加跳出率、降低转化率；交互卡顿会影响用户留存；Google 搜索排名也参考 Core Web Vitals。

**怎么衡量**：用以用户为中心的指标，而不是单纯的 `onload` 时间：

| 维度 | 用户关心的问题 | 指标 |
|------|---------------|------|
| 加载 | 内容出来了吗？ | TTFB、FCP、**LCP** |
| 交互 | 点了有反应吗？ | **INP**、TBT（实验室代理） |
| 视觉稳定 | 页面会不会乱跳？ | **CLS** |
| 业务 | 核心功能能用了吗？ | 首屏可用时间、白屏率、接口耗时 |

**口述模板（30–60 秒）**

1. 一句话结论：性能直接影响转化和留存，要用以用户为中心的指标来衡量。
2. 关键机制：分为加载、交互、视觉稳定三个维度，核心指标是 LCP、INP、CLS。
3. 对比或注意点：onload 时间不能代表用户感受，页面可能早就能用或者 onload 后仍在加载。
4. 可追问时补充：除了通用指标，还要定义业务指标，例如首屏核心数据展示时间。

**常见追问**

- 为什么不用 `onload` 时间？→ 它受所有资源（包括非首屏图片、第三方脚本）影响，与用户看到内容的时间关系不大。

### Q2. Core Web Vitals 是什么？阈值是多少？

- **难度**: 初级
- **标签**: 指标

**答案**

Google 定义的三个核心用户体验指标：

| 指标 | 衡量 | 良好 | 需改进 | 差 |
|------|------|------|--------|-----|
| **LCP**（Largest Contentful Paint） | 加载：最大内容元素渲染时间 | ≤ 2.5s | 2.5–4s | > 4s |
| **INP**（Interaction to Next Paint） | 交互：交互到下一帧绘制的延迟 | ≤ 200ms | 200–500ms | > 500ms |
| **CLS**（Cumulative Layout Shift） | 视觉稳定：累积布局偏移 | ≤ 0.1 | 0.1–0.25 | > 0.25 |

评估方式：**真实用户数据的第 75 百分位（P75）**，移动端和桌面端分开统计。也就是说，75% 的访问达到「良好」才算合格。

**口述模板（30–60 秒）**

1. 一句话结论：Core Web Vitals 是 LCP、INP、CLS 三个指标。
2. 关键机制：分别衡量加载、交互和视觉稳定，阈值是 2.5 秒、200 毫秒、0.1。
3. 对比或注意点：按真实用户的 P75 评估，不是看 Lighthouse 分数。
4. 可追问时补充：INP 在 2024 年 3 月取代了 FID。

**常见追问**

- 为什么用 P75 而不是平均值？→ 平均值会被极端值影响，P75 能反映大多数用户的体验，同时不会被少数极端设备主导。

### Q3. LCP 是什么？哪些元素会被计入？

- **难度**: 初级
- **标签**: 指标, LCP

**答案**

LCP 是视口内**最大的图片或文本块**完成渲染的时间（相对于页面开始导航）。

**计入的元素**：

- `<img>`、`<svg>` 中的 `<image>`、`<video>` 的封面图（poster）或首帧
- 通过 `url()` 加载背景图的元素
- 包含文本节点的块级元素

**不计入**：透明度为 0 的元素、覆盖整个视口的背景图（被视为背景）、低信息量的占位图。

**特点**：

- 页面加载过程中，最大元素可能变化，浏览器会多次报告候选值，取用户首次交互（点击、按键）或页面隐藏前的最后一个
- 只计算视口内可见部分的大小

**口述模板（30–60 秒）**

1. 一句话结论：LCP 是视口内最大图片或文本块的渲染时间。
2. 关键机制：加载过程中会产生多个候选，用户交互后停止更新，取最后一个。
3. 对比或注意点：它比 FCP 更能代表主体内容出现的时间。
4. 可追问时补充：大部分页面的 LCP 元素是图片，所以图片加载优先级很关键。

**常见追问**

- 怎么知道 LCP 元素是哪个？→ DevTools Performance 面板中的 LCP 标记，或者用 PerformanceObserver 读取 `entry.element`。

### Q4. INP 是什么？为什么取代了 FID？

- **难度**: 初级
- **标签**: 指标, INP

**答案**

**INP**：统计页面整个生命周期内的所有点击、触摸、键盘交互，每次交互的延迟是**从用户输入到下一帧绘制**的时间，最终取**最差的一次**（交互次数很多时，每 50 次交互忽略一次最高值，避免偶发异常）。

**FID 的问题**：

- 只统计**第一次**交互
- 只统计**输入延迟**（事件处理开始前的等待），不包括事件处理本身的耗时和渲染耗时

所以一个页面可能 FID 很好，但后续操作非常卡。INP 覆盖整个生命周期和完整的交互延迟，更能反映真实的交互体验。

**口述模板（30–60 秒）**

1. 一句话结论：INP 衡量交互到下一帧绘制的延迟，取页面生命周期中最差的交互。
2. 关键机制：包括输入延迟、事件处理和渲染三段。
3. 对比或注意点：FID 只看第一次交互的输入延迟，遗漏了大部分卡顿。
4. 可追问时补充：滚动和悬停不计入 INP。

**常见追问**

- INP 差是不是接口慢？→ 不是。INP 只关心下一帧绘制，如果点击后立即显示 loading，即使接口很慢，INP 也可以很好。

### Q5. CLS 是什么？常见原因有哪些？

- **难度**: 初级
- **标签**: 指标, CLS

**答案**

CLS 衡量页面中**意外的布局偏移**。单次偏移分数 = 影响比例（受影响区域占视口的比例）× 距离比例（移动距离占视口的比例）。按**会话窗口**累加（偏移间隔小于 1 秒、窗口总时长不超过 5 秒），取最大的窗口。

用户交互后 500ms 内的偏移不计入（属于预期变化）。

**常见原因**：

- 图片、视频没有设置宽高
- 广告、iframe、嵌入内容动态插入
- 异步内容插入到已有内容上方
- Web 字体加载后替换导致文字尺寸变化
- 动画使用了 `top` / `left` 等会触发布局的属性

**口述模板（30–60 秒）**

1. 一句话结论：CLS 衡量意外的布局偏移。
2. 关键机制：偏移分数是影响比例乘距离比例，按会话窗口累加取最大值。
3. 对比或注意点：用户交互后 500 毫秒内的偏移不算。
4. 可追问时补充：最常见的原因是图片没有尺寸和动态插入内容。

**常见追问**

- 怎么修复图片引起的 CLS？→ 设置 `width` / `height` 属性或者 CSS `aspect-ratio`，让浏览器提前预留空间。

### Q6. TTFB、FCP、TBT 分别是什么？

- **难度**: 初级
- **标签**: 指标

**答案**

| 指标 | 含义 | 良好阈值 | 主要影响因素 |
|------|------|----------|-------------|
| **TTFB**（Time to First Byte） | 从发起导航到收到 HTML 第一个字节 | ≤ 0.8s | 重定向、DNS、TCP、TLS、服务端处理、CDN |
| **FCP**（First Contentful Paint） | 首次绘制任何文本、图片、非白色 canvas 的时间 | ≤ 1.8s | TTFB、阻塞渲染的资源 |
| **TBT**（Total Blocking Time） | FCP 到 TTI 之间，所有长任务超过 50ms 部分的总和 | ≤ 200ms | 主线程长任务 |

- TTFB 和 FCP 是诊断 LCP 的辅助指标
- TBT 是**实验室指标**，作为 INP 的代理（实验室中没有真实用户交互）

**口述模板（30–60 秒）**

1. 一句话结论：TTFB 衡量服务端响应，FCP 衡量首次内容绘制，TBT 衡量主线程阻塞。
2. 关键机制：TTFB 和 FCP 用来拆解 LCP，TBT 在实验室中代替 INP。
3. 对比或注意点：TBT 只能在实验室测，线上要看 INP。
4. 可追问时补充：TBT 只计算长任务超过 50 毫秒的部分，例如 70 毫秒的任务贡献 20 毫秒。

**常见追问**

- FP 和 FCP 有什么区别？→ FP 是首次绘制任何像素（包括背景色），FCP 要求绘制出内容。

### Q7. 白屏时间和首屏时间怎么统计？

- **难度**: 初级
- **标签**: 指标, 业务

**答案**

**白屏时间**：用户看到任何内容之前的时间。现代做法直接使用 **FCP**：

```js
new PerformanceObserver((list) => {
  const fcp = list.getEntriesByName('first-contentful-paint')[0]
  report('fcp', fcp.startTime)
}).observe({ type: 'paint', buffered: true })
```

**首屏时间**：首屏主体内容完整展示的时间。

- 通用指标：**LCP**
- 业务自定义：在首屏核心数据渲染完成后打点，用 `performance.mark('first-screen')`，或者 Element Timing API（给关键元素加 `elementtiming` 属性，Chromium 支持）

**白屏检测（异常）**：页面加载一段时间后，采样检查关键位置的元素是否仍是空容器，用于发现报错导致的白屏。

**口述模板（30–60 秒）**

1. 一句话结论：白屏用 FCP，首屏用 LCP 或业务自定义打点。
2. 关键机制：通过 PerformanceObserver 采集，业务打点用 performance.mark。
3. 对比或注意点：LCP 元素不一定是业务最关心的内容，所以需要业务指标补充。
4. 可追问时补充：白屏率是另一个指标，用于发现报错导致的页面空白。

**常见追问**

- 以前用 MutationObserver 计算首屏，现在还需要吗？→ 一般不需要，LCP 和 Element Timing 更准确，成本更低。

### Q8. 实验室数据和真实用户数据有什么区别？

- **难度**: 初级
- **标签**: 度量

**答案**

| 对比项 | 实验室数据（Lab） | 真实用户数据（Field / RUM） |
|--------|------------------|---------------------------|
| 来源 | Lighthouse、WebPageTest、DevTools | 用户真实访问上报、CrUX |
| 环境 | 固定设备、网络 | 真实设备、网络、地区多样 |
| 指标 | LCP、CLS、TBT（没有真实交互，无法测 INP） | LCP、INP、CLS |
| 优点 | 可复现、可调试、可用于 CI | 反映真实体验 |
| 缺点 | 不代表真实用户 | 噪音大、难调试 |

**正确用法**：用真实用户数据**发现问题和验证效果**，用实验室数据**定位和调试**。

**口述模板（30–60 秒）**

1. 一句话结论：实验室数据用于调试，真实用户数据用于评估。
2. 关键机制：实验室环境固定、可复现；真实数据覆盖各种设备和网络。
3. 对比或注意点：Lighthouse 分数高不代表用户体验好。
4. 可追问时补充：Google 搜索排名用的是 CrUX 的真实用户数据。

**常见追问**

- 两者数据不一致怎么办？→ 以真实数据为准，再在实验室中模拟真实用户的主要设备和网络条件复现问题。

## 二、度量工具

### Q9. Lighthouse 怎么用？分数怎么看？

- **难度**: 初级
- **标签**: 工具

**答案**

- 使用方式：DevTools 的 Lighthouse 面板、PageSpeed Insights（同时展示 CrUX 真实数据）、CLI、CI 中的 Lighthouse CI
- 性能分数由多个指标加权：LCP、TBT、CLS、FCP、Speed Index 等
- 报告下方的诊断建议（新版本中与 DevTools 性能面板的 Insights 统一）给出具体问题：未使用的 JS、阻塞渲染的资源、图片尺寸过大等

**注意**：

- 默认模拟中端手机和慢速 4G，分数波动较大，需要多次运行取中位数
- 浏览器插件会影响结果，建议使用无痕模式
- 分数是诊断工具，不是目标

**口述模板（30–60 秒）**

1. 一句话结论：Lighthouse 是实验室性能诊断工具，给出指标、分数和建议。
2. 关键机制：分数由 LCP、TBT、CLS 等指标加权计算。
3. 对比或注意点：分数有波动，要多次运行；不能代替真实用户数据。
4. 可追问时补充：可以集成 Lighthouse CI 做性能门禁。

**常见追问**

- 本地 Lighthouse 满分，线上用户还说慢？→ 本地网络和设备好，缓存也可能命中；要看真实用户数据。

### Q10. Network 面板应该看什么？

- **难度**: 初级
- **标签**: 工具

**答案**

- **瀑布图**：资源的加载顺序和依赖关系，找出串行加载（请求链）
- **单个请求的 Timing**：Queueing（排队）、Stalled、DNS、Initial connection、SSL、Request sent、**Waiting（TTFB）**、Content Download
- **优先级列**：资源加载优先级（Highest / High / Low），检查 LCP 图片是否为高优先级
- **体积**：传输大小（压缩后）与资源大小
- **缓存**：`(memory cache)`、`(disk cache)`、304
- **协议**：h2、h3
- **节流**：模拟慢速网络

**口述模板（30–60 秒）**

1. 一句话结论：Network 面板主要看瀑布图、请求耗时分解、优先级、体积和缓存。
2. 关键机制：通过 Timing 判断是网络慢、服务端慢还是下载慢。
3. 对比或注意点：要开启节流模拟真实网络，并禁用缓存测试首次访问。
4. 可追问时补充：重点检查 LCP 资源是否被延迟发现、优先级是否正确。

**常见追问**

- Waiting（TTFB）很长说明什么？→ 服务端处理慢或者网络往返慢，需要结合服务端日志定位。

### Q11. Performance 面板应该看什么？

- **难度**: 初级
- **标签**: 工具

**答案**

- **Main 轨道**：主线程火焰图，红色三角标记的是**长任务**（> 50ms）；颜色区分脚本（黄）、渲染/布局（紫）、绘制（绿）
- **Timings**：FCP、LCP、DCL、Load 标记
- **Interactions**：交互耗时，用于定位 INP 问题
- **Layout Shifts**：布局偏移位置
- **Bottom-Up / Call Tree**：按函数统计耗时
- **Insights 侧边栏**：LCP 拆解、INP 拆解、CLS 原因、渲染阻塞请求等诊断

**操作建议**：开启 CPU 节流（4x 或 6x）模拟中低端手机。

**口述模板（30–60 秒）**

1. 一句话结论：Performance 面板用于分析主线程在做什么。
2. 关键机制：看长任务、函数耗时、布局和绘制，以及各指标的拆解。
3. 对比或注意点：要开启 CPU 节流，否则开发机上的问题会被掩盖。
4. 可追问时补充：紫色的 Layout 后面带红色警告，通常是强制同步布局。

**常见追问**

- 怎么找到导致长任务的代码？→ 点击长任务，在 Bottom-Up 中按 Self Time 排序，定位到具体函数。

### Q12. 怎么在线上采集 Core Web Vitals？

- **难度**: 初级
- **标签**: 监控

**答案**

使用 Google 的 `web-vitals` 库：

```js
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals/attribution'

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,           // good / needs-improvement / poor
    id: metric.id,
    attribution: metric.attribution, // 归因信息，例如 LCP 元素、INP 的目标元素
  })
  // 页面卸载时也能可靠发送
  navigator.sendBeacon('/analytics', body)
}

onLCP(sendToAnalytics)
onINP(sendToAnalytics)
onCLS(sendToAnalytics)
```

- 底层基于 PerformanceObserver
- INP 和 CLS 会在页面隐藏时（`visibilitychange`）上报最终值
- `attribution` 构建版本提供定位问题所需的归因信息

**口述模板（30–60 秒）**

1. 一句话结论：用 web-vitals 库采集，用 sendBeacon 上报。
2. 关键机制：基于 PerformanceObserver，INP 和 CLS 在页面隐藏时上报最终值。
3. 对比或注意点：要上报归因信息，否则只知道慢，不知道为什么慢。
4. 可追问时补充：新版本支持 SPA 软导航的指标统计。

**常见追问**

- 为什么不在 `unload` 时上报？→ 移动端经常不触发 unload，而且 unload 会阻止页面进入 bfcache；应该用 `visibilitychange`。

## 三、常见优化手段

### Q13. 前端性能优化有哪些手段？

- **难度**: 初级
- **标签**: 综合

**答案**

按**加载链路**分类，而不是罗列：

| 环节 | 手段 |
|------|------|
| 网络 | CDN、HTTP/2 / HTTP/3、预连接、减少重定向 |
| 资源体积 | 压缩、Tree Shaking、代码分割、图片格式和尺寸、依赖治理 |
| 缓存 | 强缓存 + 协商缓存、Service Worker |
| 关键渲染路径 | 关键 CSS、`defer` 脚本、preload LCP 资源、SSR / SSG |
| 渲染 | 减少重排、合成层动画、虚拟列表、`content-visibility` |
| JS 执行 | 拆分长任务、Web Worker、减少无效渲染 |
| 感知 | 骨架屏、渐进加载、乐观更新 |

**口述模板（30–60 秒）**

1. 一句话结论：按照网络、资源、缓存、关键渲染路径、渲染、执行这条链路来优化。
2. 关键机制：每个环节对应不同的指标：网络和资源影响 LCP，执行影响 INP，布局影响 CLS。
3. 对比或注意点：先定位瓶颈再优化，不要盲目罗列手段。
4. 可追问时补充：结合一个自己做过的项目和数据来讲。

**常见追问**

- 优先做哪些？→ 根据数据，先解决对核心指标影响最大、成本最低的问题，比如 LCP 图片优先级、首屏 JS 体积。

### Q14. 资源压缩有哪些方式？

- **难度**: 初级
- **标签**: 网络

**答案**

**代码层**：

- JS 压缩（Terser、SWC、Oxc、esbuild）：删除空白、缩短变量名、删除死代码
- CSS 压缩（cssnano、Lightning CSS）
- HTML 压缩

**传输层**（`Content-Encoding`）：

| 算法 | 特点 |
|------|------|
| gzip | 兼容性最好 |
| Brotli（br） | 文本压缩率比 gzip 高 15%–25%，所有现代浏览器支持 |
| zstd | 压缩速度快，压缩率接近 Brotli；Chromium 和 Firefox 支持 |

**做法**：静态资源**构建时预压缩**为 Brotli（使用最高压缩等级），服务器根据 `Accept-Encoding` 返回；动态内容使用较低压缩等级实时压缩，或使用 zstd。

图片、视频等已压缩格式不要再 gzip。

**口述模板（30–60 秒）**

1. 一句话结论：代码层压缩加传输层压缩，传输层优先 Brotli。
2. 关键机制：静态资源构建时用最高等级预压缩，动态内容实时压缩。
3. 对比或注意点：图片等已压缩的格式不需要再压缩。
4. 可追问时补充：zstd 的压缩速度快，适合动态内容。

**常见追问**

- 为什么动态内容不用最高等级 Brotli？→ 最高等级压缩很慢，会增加 TTFB。

### Q15. HTTP 缓存是怎么工作的？

- **难度**: 初级
- **标签**: 缓存

**答案**

**强缓存**：不发请求，直接使用本地缓存。

- `Cache-Control: max-age=31536000`（优先）
- `Expires`（旧，绝对时间）

**协商缓存**：发请求询问服务器资源是否变化，未变化返回 **304**，不返回内容。

- `ETag` / `If-None-Match`（优先，基于内容）
- `Last-Modified` / `If-Modified-Since`（秒级精度）

**推荐策略**：

| 资源 | 策略 |
|------|------|
| HTML | `Cache-Control: no-cache`（每次协商） |
| 带 hash 的 JS / CSS / 图片 | `Cache-Control: max-age=31536000, immutable` |
| 不带 hash 的资源 | 短 max-age + 协商缓存 |
| 敏感数据 | `no-store` |

详细原理见 [浏览器原理](../browser/20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：强缓存不发请求，协商缓存发请求并可能返回 304。
2. 关键机制：强缓存看 Cache-Control，协商缓存看 ETag 和 Last-Modified。
3. 对比或注意点：HTML 用协商缓存，带 hash 的资源长期强缓存。
4. 可追问时补充：`no-cache` 不是不缓存，而是每次都要协商。

**常见追问**

- `no-cache` 和 `no-store` 的区别？→ no-cache 可以缓存但使用前必须验证；no-store 完全不缓存。

### Q16. CDN 为什么能提升性能？

- **难度**: 初级
- **标签**: 网络

**答案**

- **就近访问**：通过 DNS 调度或 Anycast 把用户导向最近的边缘节点，减少网络往返时间（RTT）
- **缓存**：静态资源缓存在边缘节点，不需要回源
- **连接优化**：边缘节点与源站之间有优化过的长连接；支持 HTTP/2、HTTP/3、TLS 1.3
- **其他能力**：压缩、图片处理（格式转换、缩放）、边缘计算

注意：

- 静态资源域名与主站分开时，需要额外的 DNS 和连接，可以用 `preconnect`；在 HTTP/2 下，多域名分散反而可能更慢
- 缓存刷新：带 hash 的资源无需刷新；HTML 更新需要考虑 CDN 缓存时间

**口述模板（30–60 秒）**

1. 一句话结论：CDN 通过就近访问和边缘缓存减少延迟。
2. 关键机制：DNS 调度到最近节点，静态资源在边缘缓存，不需要回源。
3. 对比或注意点：HTTP/2 下不需要多个 CDN 域名分散请求。
4. 可追问时补充：现代 CDN 还提供图片处理和边缘计算。

**常见追问**

- 动态 HTML 能用 CDN 吗？→ 可以通过边缘缓存（短时间缓存 + 后台更新）或边缘渲染，也能利用 CDN 的连接优化加速回源。

### Q17. 图片怎么优化？

- **难度**: 初级
- **标签**: 图片

**答案**

1. **格式**：AVIF（压缩率最高）> WebP > JPEG / PNG；图标用 SVG

```html
<picture>
  <source srcset="hero.avif" type="image/avif" />
  <source srcset="hero.webp" type="image/webp" />
  <img src="hero.jpg" alt="..." width="1200" height="600" />
</picture>
```

2. **尺寸**：按显示尺寸提供图片，使用 `srcset` + `sizes` 适配不同屏幕

```html
<img
  srcset="hero-480.webp 480w, hero-960.webp 960w, hero-1920.webp 1920w"
  sizes="(max-width: 600px) 100vw, 50vw"
  src="hero-960.webp" alt="..." width="960" height="480"
/>
```

3. **加载策略**：首屏外图片 `loading="lazy"`；**LCP 图片不要懒加载**，加 `fetchpriority="high"`
4. **防止 CLS**：设置 `width` / `height`
5. **CDN 图片服务**：URL 参数自动转换格式和尺寸

**口述模板（30–60 秒）**

1. 一句话结论：图片优化包括格式、尺寸、加载策略和防止布局偏移。
2. 关键机制：使用 AVIF / WebP，用 srcset 按屏幕提供合适尺寸，首屏外懒加载。
3. 对比或注意点：LCP 图片不能懒加载，而且应该提高优先级。
4. 可追问时补充：设置宽高避免 CLS。

**常见追问**

- `decoding="async"` 有什么用？→ 提示浏览器异步解码图片，避免阻塞主线程；效果有限，主要用于大图。

### Q18. 怎么实现懒加载？

- **难度**: 初级
- **标签**: 加载

**答案**

**原生懒加载**（推荐）：

```html
<img src="a.jpg" loading="lazy" width="400" height="300" alt="" />
<iframe src="..." loading="lazy"></iframe>
```

浏览器根据与视口的距离自动决定加载时机。

**IntersectionObserver**（需要自定义时，例如组件懒加载、无限滚动）：

```js
const observer = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue
    const img = entry.target
    img.src = img.dataset.src
    observer.unobserve(img)
  }
}, { rootMargin: '200px' }) // 提前 200px 开始加载

document.querySelectorAll('img[data-src]').forEach((img) => observer.observe(img))
```

**不推荐**：监听 scroll 事件并调用 `getBoundingClientRect`，频繁触发且会导致强制布局。

**口述模板（30–60 秒）**

1. 一句话结论：图片和 iframe 优先用原生 `loading="lazy"`，自定义场景用 IntersectionObserver。
2. 关键机制：IntersectionObserver 异步回调，不阻塞主线程，可以用 rootMargin 提前加载。
3. 对比或注意点：监听 scroll 计算位置性能差。
4. 可追问时补充：首屏图片和 LCP 图片不能懒加载。

**常见追问**

- 懒加载会影响 SEO 吗？→ 原生懒加载对爬虫友好；JS 实现时要确保图片地址可以被爬虫获取。

### Q19. 代码分割和按需加载怎么做？

- **难度**: 初级
- **标签**: 资源

**答案**

- **路由级分割**：每个路由一个 chunk

```tsx
const Settings = lazy(() => import('./pages/Settings'))
```

- **组件级分割**：弹窗、富文本编辑器、图表等大组件在需要时加载
- **交互触发加载**：点击按钮时再 `import()`
- **依赖分割**：稳定的框架代码单独打包，利用长期缓存
- **预加载下一步**：鼠标悬停时 `import()` 或 `<link rel="prefetch">`

**注意**：拆得太细会增加请求数和请求瀑布；首屏必需的代码不要拆出去。

**口述模板（30–60 秒）**

1. 一句话结论：通过动态 import 实现路由级和组件级分割。
2. 关键机制：首屏只加载必要代码，其他代码在需要时加载。
3. 对比或注意点：拆分过细会增加请求和瀑布。
4. 可追问时补充：可以在悬停时预加载，兼顾体积和响应速度。

**常见追问**

- 懒加载的组件第一次打开会有延迟怎么办？→ 预加载（悬停或空闲时）加上 loading 状态。

### Q20. `<script>` 的 `async` 和 `defer` 有什么区别？

- **难度**: 初级
- **标签**: 关键渲染路径

**答案**

| 方式 | 下载 | 执行时机 | 顺序 |
|------|------|----------|------|
| 普通 `<script>` | 阻塞 HTML 解析 | 下载完立即执行 | 按顺序 |
| `async` | 并行下载，不阻塞解析 | 下载完立即执行（可能中断解析） | **不保证** |
| `defer` | 并行下载，不阻塞解析 | HTML 解析完成后、`DOMContentLoaded` 前 | 按顺序 |
| `type="module"` | 并行下载 | 默认等同 `defer` | 按顺序 |

**选择**：

- 依赖 DOM 或彼此有依赖的业务脚本：`defer`
- 独立的第三方脚本（统计）：`async`

**口述模板（30–60 秒）**

1. 一句话结论：async 下载完立即执行，defer 等 HTML 解析完再按顺序执行。
2. 关键机制：两者都不阻塞下载，但 async 执行时会中断解析且不保证顺序。
3. 对比或注意点：module 脚本默认是 defer 行为。
4. 可追问时补充：业务脚本用 defer，独立的统计脚本用 async。

**常见追问**

- 把 script 放在 body 底部和 defer 有什么区别？→ 放底部时要等 HTML 解析到那里才开始下载；defer 可以在 head 中提前开始下载。

### Q21. `preload`、`prefetch`、`preconnect` 有什么区别？

- **难度**: 初级
- **标签**: 资源提示

**答案**

| 提示 | 作用 | 优先级 | 场景 |
|------|------|--------|------|
| `preload` | 提前下载**当前页面**一定会用到的资源 | 高 | LCP 图片、字体、关键 CSS 中引用的资源 |
| `prefetch` | 空闲时下载**下一个页面**可能用到的资源 | 最低 | 下一步路由的 chunk |
| `preconnect` | 提前建立连接（DNS + TCP + TLS） | — | 关键的第三方域名、CDN |
| `dns-prefetch` | 只做 DNS 解析 | — | 次要的第三方域名 |
| `modulepreload` | 预加载并解析 ES 模块 | 高 | 模块依赖 |

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin />
<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin />
<link rel="prefetch" href="/assets/settings.js" />
```

**注意**：preload 的资源 3 秒内未使用，控制台会警告；过多的 preload 会抢占关键资源的带宽。

**口述模板（30–60 秒）**

1. 一句话结论：preload 用于当前页面的关键资源，prefetch 用于下一个页面，preconnect 提前建立连接。
2. 关键机制：preload 优先级高，prefetch 在空闲时以最低优先级加载。
3. 对比或注意点：preload 不能滥用，否则会抢占带宽。
4. 可追问时补充：字体 preload 必须加 crossorigin，否则会重复下载。

**常见追问**

- 为什么字体 preload 需要 crossorigin？→ 字体总是以 CORS 模式请求，preload 不加 crossorigin 时请求模式不匹配，无法复用。

### Q22. 什么是重排和重绘？

- **难度**: 初级
- **标签**: 渲染

**答案**

- **重排（Reflow / Layout）**：元素的几何属性（尺寸、位置）变化，浏览器重新计算布局。成本最高，可能影响整个文档
- **重绘（Repaint）**：外观变化但不影响布局（颜色、背景、阴影），重新绘制
- **合成（Composite）**：只改变 `transform`、`opacity`，在合成线程中完成，不需要重排和重绘

**重排一定导致重绘，重绘不一定导致重排。**

**减少重排的方法**：

- 批量修改样式（修改 class 而不是逐个修改 style）
- 读写分离，避免强制同步布局
- 动画使用 `transform` / `opacity`
- 复杂的 DOM 操作在离线状态（DocumentFragment、`display: none`）下完成

**口述模板（30–60 秒）**

1. 一句话结论：重排是重新计算布局，重绘是重新绘制外观，重排成本更高。
2. 关键机制：几何属性变化触发重排，颜色等变化只触发重绘，transform 和 opacity 只触发合成。
3. 对比或注意点：重排一定会重绘。
4. 可追问时补充：读取 offsetHeight 等布局属性会强制浏览器立即重排。

**常见追问**

- 哪些操作会强制重排？→ 读取 `offsetTop`、`clientWidth`、`scrollTop`、`getBoundingClientRect()`、`getComputedStyle()` 等。

### Q23. 防抖和节流有什么区别？各用在什么场景？

- **难度**: 初级
- **标签**: JS

**答案**

| 对比项 | 防抖（debounce） | 节流（throttle） |
|--------|-----------------|------------------|
| 原理 | 停止触发一段时间后才执行一次 | 固定时间间隔内最多执行一次 |
| 场景 | 搜索框输入联想、窗口 resize 结束后计算 | 滚动监听、拖拽、鼠标移动 |

```js
function debounce(fn, wait) {
  let timer
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), wait)
  }
}
```

完整实现见 [手写 H1](40-coding-handwritten.md)。

视觉相关的高频事件（滚动、动画）可以用 `requestAnimationFrame` 节流，与刷新率对齐。

**口述模板（30–60 秒）**

1. 一句话结论：防抖是停下来才执行，节流是固定频率执行。
2. 关键机制：防抖每次触发都重置定时器；节流在间隔内忽略触发。
3. 对比或注意点：搜索输入用防抖，滚动用节流。
4. 可追问时补充：视觉更新可以用 rAF 节流。

**常见追问**

- 防抖如何立即执行第一次？→ 增加 leading 选项，第一次触发时立即执行，之后进入防抖。

### Q24. HTTP/2 下还需要合并请求吗？

- **难度**: 初级
- **标签**: 网络

**答案**

**HTTP/1.1**：同一域名最多 6 个并发连接，请求多时排队，所以需要合并文件、雪碧图、域名分片。

**HTTP/2**：

- **多路复用**：一个连接上并行传输多个请求，不再有连接数限制
- **头部压缩（HPACK）**：减少重复头部的开销
- 合并的必要性降低：细粒度文件可以更好地利用缓存（修改一个模块只让一个文件失效）
- **域名分片反而有害**：增加 DNS 和连接开销，无法复用同一个连接

**但仍然不能无限拆分**：每个请求仍有开销，压缩率在大文件上更高，浏览器也有处理开销。合理的做法是适度拆分。

**口述模板（30–60 秒）**

1. 一句话结论：HTTP/2 多路复用后，合并请求的必要性降低了。
2. 关键机制：一个连接并行传输，没有连接数限制，还有头部压缩。
3. 对比或注意点：域名分片在 HTTP/2 下有害；拆分过细仍有开销。
4. 可追问时补充：HTTP/2 仍有 TCP 层队头阻塞，HTTP/3 基于 QUIC 解决了这个问题。

**常见追问**

- 雪碧图还需要吗？→ 基本不需要，图标用 SVG 或图标字体；HTTP/2 下多个小图片的开销不大。

### Q25. 字体怎么优化？

- **难度**: 初级
- **标签**: 字体

**答案**

1. **格式**：只使用 WOFF2
2. **子集化**：中文字体非常大（几 MB），按使用的字符子集化，或用 `unicode-range` 按需加载
3. **`font-display`**：
   - `swap`：先显示备用字体，加载完成后替换（避免文字不可见，但可能导致 CLS）
   - `optional`：网络慢时直接使用备用字体（适合非关键字体）
4. **预加载**关键字体：`<link rel="preload" as="font" crossorigin>`
5. **减少偏移**：用 `size-adjust`、`ascent-override` 调整备用字体的尺寸，使其与 Web 字体接近
6. **系统字体**：中文页面优先使用系统字体

```css
@font-face {
  font-family: 'Brand';
  src: url('/fonts/brand.woff2') format('woff2');
  font-display: swap;
}
```

**口述模板（30–60 秒）**

1. 一句话结论：使用 WOFF2、子集化、合适的 font-display 和预加载。
2. 关键机制：swap 避免文字不可见，size-adjust 减少替换时的布局偏移。
3. 对比或注意点：中文字体体积很大，必须子集化或使用系统字体。
4. 可追问时补充：非关键字体用 optional，网络慢时直接放弃。

**常见追问**

- FOIT 和 FOUT 是什么？→ FOIT 是字体加载期间文字不可见，FOUT 是先显示备用字体再替换，`swap` 选择的是 FOUT。

### Q26. 骨架屏有什么作用？有什么局限？

- **难度**: 初级
- **标签**: 感知性能

**答案**

**作用**：

- 改善**感知性能**：用户立即看到页面结构，减少等待焦虑
- 预留空间，避免内容加载后的布局偏移（CLS）

**局限**：

- **不改善真实性能**：主体内容出现的时间（LCP）不变
- 骨架屏与真实内容尺寸不一致时，反而导致 CLS
- 骨架屏本身如果依赖 JS 渲染，在 JS 加载前仍然是白屏，所以应该直接写在 HTML 中或由 SSR 输出

**口述模板（30–60 秒）**

1. 一句话结论：骨架屏改善感知性能，但不改善真实性能。
2. 关键机制：提前展示页面结构，并预留空间减少布局偏移。
3. 对比或注意点：LCP 不会因为骨架屏变好，尺寸不一致还会导致 CLS。
4. 可追问时补充：骨架屏应该写在 HTML 中，不依赖 JS。

**常见追问**

- 骨架屏会被计为 LCP 吗？→ 纯色块通常不会被计为 LCP 元素，但如果包含较大的占位图片或文字，可能会被计入。

### Q27. Tree Shaking 是什么？什么情况下会失效？

- **难度**: 初级
- **标签**: 资源

**答案**

Tree Shaking 是在打包时移除**未被使用的导出代码**，依赖 ESM 的静态结构。

**失效情况**：

- 使用 CommonJS（`require` 是动态的，无法静态分析）
- 模块有副作用，且没有声明 `sideEffects: false`
- 导入整个对象：`import _ from 'lodash'` 而不是 `import { debounce } from 'lodash-es'`
- Babel 等工具把 ESM 转成了 CJS
- 类的方法、对象的属性无法单独移除

详见 [webpack 中级 Q11](../webpack/20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：Tree Shaking 基于 ESM 静态分析移除未使用的代码。
2. 关键机制：标记未使用的导出，压缩时删除；有副作用的模块不能删除。
3. 对比或注意点：CJS、副作用、整体导入都会导致失效。
4. 可追问时补充：package.json 的 sideEffects 字段很关键。

**常见追问**

- 怎么检查 Tree Shaking 是否生效？→ 用产物分析工具查看是否包含未使用的模块。

### Q28. 怎么让动画更流畅？

- **难度**: 初级
- **标签**: 渲染, 动画

**答案**

1. **只动画 `transform` 和 `opacity`**：只触发合成，不触发重排和重绘，可以在合成线程上运行，即使主线程繁忙也不卡顿
2. **JS 动画使用 `requestAnimationFrame`**：与屏幕刷新同步，页面隐藏时自动暂停
3. **优先使用 CSS 动画 / Web Animations API**：浏览器可以优化
4. **`will-change: transform`**：提前提升为合成层，但不要滥用（每个层都占用内存）
5. **避免在动画中读取布局属性**

```css
/* 不好：触发布局 */
.box { transition: left 0.3s; }
/* 好：只触发合成 */
.box { transition: transform 0.3s; }
```

**口述模板（30–60 秒）**

1. 一句话结论：动画只修改 transform 和 opacity，JS 动画用 rAF。
2. 关键机制：这两个属性只触发合成，可以在合成线程中完成。
3. 对比或注意点：will-change 不能滥用，合成层过多会占用大量内存。
4. 可追问时补充：60fps 意味着每帧只有约 16.7 毫秒。

**常见追问**

- 为什么 setTimeout 做动画会卡？→ 与刷新率不对齐，可能一帧内执行两次或者跳过一帧，造成抖动。

### Q29. 第三方脚本对性能有什么影响？怎么处理？

- **难度**: 初级
- **标签**: 第三方

**答案**

**影响**：

- 额外的 DNS、连接和下载
- 占用主线程（长任务），影响 INP
- 同步加载时阻塞渲染
- 插入广告等内容导致 CLS
- 不可控：第三方服务慢或挂掉会拖累页面

**处理**：

1. 审计：列出所有第三方脚本，评估必要性
2. 异步加载：`async` / `defer`，或在 `load` 事件后、空闲时加载
3. `preconnect` 关键的第三方域名
4. 为广告位预留空间
5. 用门面模式（facade）：例如视频嵌入、客服组件先显示静态占位，用户点击后才加载真正的脚本
6. 自托管关键的第三方资源
7. 将部分脚本移到 Web Worker（如 Partytown）

**口述模板（30–60 秒）**

1. 一句话结论：第三方脚本会占用网络和主线程，还可能导致布局偏移。
2. 关键机制：异步加载、延迟加载、门面模式减少影响。
3. 对比或注意点：第三方脚本是不可控的，要设置超时和降级。
4. 可追问时补充：定期审计第三方脚本，删除不再需要的。

**常见追问**

- 什么是门面模式？→ 先渲染一个轻量的静态占位，用户交互时才加载真正的重量级组件。

### Q30. Web Worker 能解决什么性能问题？

- **难度**: 初级
- **标签**: JS, 多线程

**答案**

Web Worker 在**独立线程**中运行 JS，不阻塞主线程，适合**计算密集型**任务：

- 大数据量的排序、过滤、聚合
- 文件解析（Excel、CSV）、图片处理
- 加密、压缩、diff 计算

```js
// main.js
const worker = new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })
worker.postMessage(bigData)
worker.onmessage = (e) => render(e.data)

// worker.js
self.onmessage = (e) => {
  const result = heavyCompute(e.data)
  self.postMessage(result)
}
```

**限制**：

- 不能访问 DOM
- 通信需要序列化（结构化克隆），大数据传输有开销，可以用 **Transferable**（如 `ArrayBuffer`）零拷贝转移
- 创建 Worker 有开销，适合较长的任务

**口述模板（30–60 秒）**

1. 一句话结论：Web Worker 把计算密集型任务移出主线程，避免阻塞交互。
2. 关键机制：独立线程运行，通过 postMessage 通信。
3. 对比或注意点：不能操作 DOM，大数据通信有序列化开销。
4. 可追问时补充：用 Transferable 对象零拷贝传输。

**常见追问**

- 有了 Worker 是不是所有任务都应该放进去？→ 不是，短任务的通信开销可能超过收益；DOM 相关的工作也只能在主线程。
