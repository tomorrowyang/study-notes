## 一、底层原理

### Q1. RN 新架构下，一次 setState 到屏幕更新的完整过程？

- **难度**: 高级
- **标签**: RN, Fabric, 原理

**答案**

```text
JS 线程
  1. setState → React 调度更新（按优先级；transition 可中断）
  2. Render：React 协调（reconcile），生成新的元素树
  3. 通过 JSI 调用 Fabric 的 C++ UIManager，克隆并更新 Shadow Tree
     （不可变：只克隆变化路径上的节点，未变化的子树共享）
后台线程 / JS 线程
  4. Commit：Yoga 计算布局，得到每个节点的位置和尺寸；
     新树原子地替换为「当前树」
UI 线程
  5. Mount：对比新旧 Shadow Tree，生成视图变更指令
     （创建、更新属性、插入、删除），应用到原生视图
  6. 平台绘制
```

**与旧架构的区别**：

- 旧：JS 通过 Bridge 发送 JSON 指令，UIManager 在原生侧维护 Shadow Tree，全部异步
- 新：Shadow Tree 在 C++ 中、不可变，可以在任意线程计算；**高优先级的更新（如用户输入）可以在 UI 线程同步渲染**

**口述模板（30–60 秒）**

1. 一句话结论：新架构的更新分为 Render、Commit、Mount 三个阶段。
2. 关键机制：JS 线程中 React 协调后通过 JSI 更新 C++ 中的不可变 Shadow Tree。
3. 对比或注意点：布局在 Commit 阶段由 Yoga 计算，Mount 阶段在 UI 线程更新原生视图。
4. 可追问时补充：不可变的树让多线程处理和并发渲染成为可能。

**常见追问**

- 为什么不可变的 Shadow Tree 能支持并发？→ 每次更新生成新版本的树，旧版本仍然有效；不同线程读取不同版本不会冲突，中断的渲染可以直接丢弃。

### Q2. Bridgeless 模式是什么？

- **难度**: 高级
- **标签**: RN, 架构

**答案**

新架构早期 TurboModules 和 Fabric 已经基于 JSI，但 Bridge 仍然存在（用于初始化、事件、部分旧 API）。**Bridgeless 模式**彻底移除 Bridge：

- 运行时初始化、错误处理、定时器、事件分发都通过新的基础设施（RuntimeScheduler、ReactInstance）
- **RuntimeScheduler**：在 JS 线程上按优先级调度任务，支持 React 的并发特性和微任务语义
- 0.74 起新架构默认启用 Bridgeless；0.82 起旧架构被移除

**影响**：依赖 `NativeModules` 旧接口、`RCTBridge` 的代码需要迁移（兼容层覆盖了部分常用 API）。

**口述模板（30–60 秒）**

1. 一句话结论：Bridgeless 模式是彻底移除旧 Bridge 的运行方式。
2. 关键机制：运行时的初始化、事件、定时器由新的基础设施处理。
3. 对比或注意点：RuntimeScheduler 按优先级在 JS 线程调度任务，支持并发特性。
4. 可追问时补充：依赖 RCTBridge 的原生代码需要迁移。

**常见追问**

- 为什么定时器和微任务的语义也要改？→ 旧架构中 Promise 回调和 setTimeout 的时机与 Web 不一致；新的调度器让事件循环的语义与 Web 对齐。

### Q3. JSI HostObject 的内存和线程安全要注意什么？

- **难度**: 高级
- **标签**: RN, JSI

**答案**

- **生命周期**：JS 持有 HostObject 的引用，C++ 对象通过 `shared_ptr` 管理；JS 对象被 GC 回收时释放引用 → 依赖 GC 的时机，持有大资源（相机帧、大缓冲区）的对象要提供**显式的 `dispose` / `close` 方法**
- **线程安全**：`jsi::Runtime` **不是线程安全的**，只能在 JS 线程访问；原生在其他线程完成工作后，需要通过 CallInvoker 调度回 JS 线程再调用回调
- **不能长期持有 `jsi::Value`**：跨调用保存时要用 `jsi::WeakObject` 或复制数据
- **同步调用的耗时**：同步方法阻塞 JS 线程，只用于快速操作
- **异常**：C++ 异常转换为 `jsi::JSError`

**口述模板（30–60 秒）**

1. 一句话结论：HostObject 的生命周期依赖 JS 的 GC，jsi::Runtime 只能在 JS 线程访问。
2. 关键机制：原生在其他线程完成工作后，要调度回 JS 线程调用回调。
3. 对比或注意点：持有大资源的对象要提供显式释放的方法。
4. 可追问时补充：同步方法只用于快速操作，否则阻塞 JS 线程。

**常见追问**

- VisionCamera 的帧处理器为什么要显式管理帧？→ 每一帧都是大块内存，等 GC 回收会导致内存暴涨，所以处理完立即释放。

### Q4. 小程序的底层架构细节：基础库、Native 中转、页面预加载？

- **难度**: 高级
- **标签**: 小程序, 原理

**答案**

- **基础库**：运行在客户端中的 JS 框架，提供 `Page` / `Component` / `wx.*` API、虚拟 DOM、组件系统（Exparser / glass-easel）；随客户端下发更新，开发者可以设置最低版本
- **Exparser / glass-easel**：组件框架，基于 Shadow DOM 模型实现组件隔离和 slot
- **通信**：逻辑层和渲染层不直接通信，**通过 Native（客户端）中转**（WeixinJSBridge）；API 调用（网络、存储）也走 Native
- **页面预加载**：客户端预先创建 WebView 并注入基础库，打开新页面时直接使用 → 页面打开更快
- **代码包**：下载并缓存在本地，有版本检查和更新机制（启动时检查，下次启动生效；可以用 `UpdateManager` 强制更新）

**口述模板（30–60 秒）**

1. 一句话结论：小程序由客户端、基础库和开发者代码三层组成。
2. 关键机制：逻辑层和渲染层的通信都经过 Native 中转。
3. 对比或注意点：客户端预创建 WebView 并注入基础库，加快页面打开。
4. 可追问时补充：代码包本地缓存，更新默认在下次启动生效。

**常见追问**

- 怎么让用户尽快用上新版本？→ `wx.getUpdateManager()` 监听新版本下载完成，提示用户重启；重大问题时在后台设置最低可用版本。

### Q5. Skyline 与 WebView 渲染在底层上有什么不同？

- **难度**: 高级
- **标签**: 小程序, Skyline

**答案**

| | WebView 渲染 | Skyline |
|--|--------------|---------|
| 渲染引擎 | 浏览器内核（完整的 HTML / CSS） | 自研渲染管线（CSS 子集） |
| 线程 | 每个页面一个 WebView（多个渲染进程 / 线程） | 共享的渲染线程 + 独立的 UI 任务 |
| 内存 | 每个 WebView 有较高的基础开销 | 页面开销小 |
| 逻辑与渲染 | 双线程，setData 跨线程 | 仍然双线程，但支持 Worklet 在 UI 线程运行 |
| 动画 | CSS 动画 / WXS | Worklet、手势系统、共享元素 |
| 布局 | 完整的 CSS 布局 | 支持 Flex 等常用布局，部分特性不支持 |

**本质**：Skyline 把「浏览器」替换成为小程序定制的轻量渲染引擎，与 Flutter 的思路类似（自己的渲染管线），同时保留 WXML / WXSS 的开发方式。

**口述模板（30–60 秒）**

1. 一句话结论：Skyline 用自研的轻量渲染管线替代了浏览器内核。
2. 关键机制：页面共享渲染线程，内存开销更小。
3. 对比或注意点：只支持 CSS 的子集，开发时要注意兼容性。
4. 可追问时补充：Worklet 让动画逻辑在 UI 线程执行，解决跨线程通信的延迟。

**常见追问**

- 为什么不直接用 Flutter？→ 需要兼容大量已有的 WXML / WXSS 代码和开发者习惯，Skyline 保留了原有的开发方式。

## 二、性能与稳定性

### Q6. 大型 RN App 的性能治理体系怎么建设？

- **难度**: 高级
- **标签**: RN, 性能

**答案**

```text
1. 指标定义
   - 启动：冷启动 TTI、热启动
   - 页面：首屏时间（页面打开到内容渲染）、可交互时间
   - 流畅度：JS / UI 线程的掉帧率、卡顿次数（> N ms 的长任务）
   - 资源：内存峰值、包体积
2. 采集
   - 线上：埋点 SDK（原生 + JS 打点），按版本、机型、系统分组
   - 线下：自动化性能测试（Flashlight、Maestro 脚本 + 低端机），PR 中对比
3. 防劣化
   - 性能预算：首屏时间、包体积超标时 CI 报警
   - 发布前在低端机上回归
4. 优化
   - 共性问题在框架层解决（列表组件、图片组件、启动框架）
   - 业务问题按页面分配
5. 看板与复盘
```

**关键**：**低端 Android 机型**是性能问题的主要来源，测试设备和线上分析都要覆盖。

**口述模板（30–60 秒）**

1. 一句话结论：性能治理要有指标、线上采集、线下防劣化和框架层优化。
2. 关键机制：指标覆盖启动、页面首屏、流畅度和资源。
3. 对比或注意点：低端 Android 机型是重点。
4. 可追问时补充：共性问题在框架层解决，PR 中自动对比性能。

**常见追问**

- 首屏时间怎么定义和采集？→ 从路由开始到首屏关键内容渲染完成（在关键组件的 `onLayout` 中打点，或原生侧监听视图变化）。

### Q7. RN 启动的深度优化手段有哪些？

- **难度**: 高级
- **标签**: RN, 启动

**答案**

| 手段 | 说明 |
|------|------|
| **RN 实例预创建** | App 启动后（或闪屏时）提前初始化 RN 运行时并加载基础 bundle，打开 RN 页面时直接使用 |
| **拆包** | 基础包（RN 框架 + 公共库）预加载，业务包按需加载 → 打开页面时只执行业务代码 |
| Hermes 字节码 + 内存映射 | 只加载用到的函数 |
| 首屏数据并行 | 原生在加载 bundle 的同时发起首屏接口请求 |
| 首屏快照 / 缓存 | 显示上次的数据 |
| 延迟加载非首屏模块 | `React.lazy`、inline requires |
| 原生初始化治理 | 统计每个 SDK 的初始化耗时，延迟或懒加载 |

**口述模板（30–60 秒）**

1. 一句话结论：深度优化的核心是预创建 RN 实例和拆包。
2. 关键机制：基础包提前加载，打开页面时只执行业务包。
3. 对比或注意点：原生侧在加载 bundle 的同时并行请求首屏数据。
4. 可追问时补充：治理原生 SDK 的初始化耗时。

**常见追问**

- 预创建实例有什么代价？→ 占用内存；在 App 启动时与其他任务竞争资源 → 放在空闲时机执行。

### Q8. 跨端 App 的稳定性怎么保障？

- **难度**: 高级
- **标签**: 稳定性

**答案**

| 类型 | 采集与处理 |
|------|------------|
| 原生崩溃 | 崩溃 SDK（符号化：iOS dSYM、Android mapping） |
| **JS 异常** | `ErrorUtils.setGlobalHandler`、错误边界；sourcemap 还原（Hermes 的 sourcemap 需要合并） |
| ANR / 卡死 | Android ANR 监控；JS 线程卡死检测（看门狗：定时 ping JS 线程） |
| OOM | 内存监控；大图治理 |
| 白屏 | 页面渲染完成的打点超时；bundle 加载失败 |
| 热更新导致的崩溃 | 启动保护：连续崩溃时回滚 bundle |

**体系**：按版本（原生版本 + bundle 版本）聚合；**崩溃率**告警；灰度发布；问题定位后用热更新修复（JS 问题）。

**口述模板（30–60 秒）**

1. 一句话结论：稳定性要同时覆盖原生崩溃、JS 异常、卡死、OOM 和白屏。
2. 关键机制：JS 异常用全局处理器和错误边界捕获，用 sourcemap 还原。
3. 对比或注意点：热更新要有启动保护，连续崩溃时自动回滚。
4. 可追问时补充：按原生版本和 bundle 版本聚合，灰度发布。

**常见追问**

- JS 异常一定要让 App 崩溃吗？→ 不一定；页面级错误边界展示降级界面，但关键状态损坏时重启更安全。

### Q9. 小程序的性能怎么治理？

- **难度**: 高级
- **标签**: 小程序, 性能

**答案**

- **指标**：启动耗时、首屏渲染耗时、setData 的次数和数据量、页面切换耗时、内存告警
- **工具**：开发者工具的「体验评分」（Audits）、性能面板；`wx.getPerformance()`；We 分析的线上数据
- **规范**：
  - setData 的数据量和频率上限（Lint 规则或运行时检测：封装 setData 记录体积并告警）
  - 图片走 CDN，限制代码包中的图片
  - 分包规划和体积预算
- **框架层**：Taro 等框架层面的优化配置；统一的列表组件
- **持续**：CI 中检查包体积，线上看板按版本对比

**口述模板（30–60 秒）**

1. 一句话结论：小程序性能治理关注启动、首屏、setData 和包体积。
2. 关键机制：封装 setData 记录数据量和频率，超过阈值时告警。
3. 对比或注意点：用体验评分和线上数据分析。
4. 可追问时补充：CI 中检查包体积，分包有体积预算。

**常见追问**

- 怎么在运行时检测 setData 的数据量？→ 在 Page / Component 的构造器外包装一层，拦截 setData，计算 `JSON.stringify(data).length` 并上报（只在开发和采样中开启）。

### Q10. 包体积怎么治理（RN 和小程序）？

- **难度**: 高级
- **标签**: 包体积

**答案**

**RN**：

- JS bundle：移除无用依赖、按需引入（图标库、lodash）；source-map-explorer 分析
- 原生：Android App Bundle（按设备分发）、ABI 拆分、资源压缩、R8 混淆；iOS 的 App Thinning
- 资源：图片压缩、WebP、非必要资源改为在线下载
- 预编译的 iOS 二进制（RN 0.84 起）改善构建时间，对体积影响以实测为准

**小程序**：

- 分包（主包放首页和公共代码）；公共代码放在合适的位置（只被某个分包使用的代码放进该分包）
- 图片、字体放 CDN
- 依赖按需引入；Taro / uni-app 的 tree-shaking
- 按需注入

**通用**：体积预算 + CI 检查 + PR 中展示变化。

**口述模板（30–60 秒）**

1. 一句话结论：包体积治理包括 JS、原生代码和资源三部分。
2. 关键机制：RN 用 App Bundle、ABI 拆分，小程序用分包和 CDN 资源。
3. 对比或注意点：只被某个分包使用的代码要放进该分包。
4. 可追问时补充：设置体积预算，在 CI 中检查。

**常见追问**

- 小程序主包超限怎么办？→ 先分析主包内容，把非首页的页面移到分包，把只在分包中使用的组件和依赖移过去，图片移到 CDN。

## 三、架构

### Q11. 原生 + RN 的混合栈怎么设计？

- **难度**: 高级
- **标签**: RN, 混合开发

**答案**

场景：原有原生 App，逐步引入 RN 页面。

```text
原生路由中心（统一 URL：app://orders/detail?id=1）
   ├─ 原生页面
   └─ RN 页面：RN 容器（Activity / ViewController）+ RN 实例 + 模块名
```

**关键问题**：

| 问题 | 方案 |
|------|------|
| 路由统一 | 原生路由中心，RN 通过原生模块调用路由；每个 RN 页面一个原生容器（原生转场动画和手势返回） |
| **RN 实例** | **共享一个实例**（省内存，页面切换快）或每个业务一个实例（隔离，但内存高）；通常共享基础实例 |
| 数据传递 | 路由参数；全局状态通过原生模块共享（用户信息、配置） |
| 生命周期 | 原生容器的显示 / 隐藏通知 RN 页面 |
| 返回 | Android 物理返回键交给 RN 处理，未处理时关闭容器 |

**口述模板（30–60 秒）**

1. 一句话结论：混合栈的核心是统一的原生路由中心和 RN 容器。
2. 关键机制：每个 RN 页面放在一个原生容器中，使用原生的转场和手势。
3. 对比或注意点：RN 实例通常共享，减少内存和打开时间。
4. 可追问时补充：容器的生命周期要通知 RN 页面。

**常见追问**

- 多个 RN 页面共享实例时怎么区分？→ 每个容器挂载不同的根组件（`moduleName` + `initialProperties`），在同一个运行时中渲染多个根。

### Q12. RN 怎么拆包，实现多业务独立发布？

- **难度**: 高级
- **标签**: RN, 拆包

**答案**

```text
基础包（common.bundle）：RN 框架、React、公共库、公共组件
业务包（orders.bundle、mine.bundle）：只包含业务代码，依赖基础包中的模块
```

**实现要点**：

- **模块 ID 稳定**：Metro 的 `createModuleIdFactory` 用模块路径生成固定的 ID，业务包中引用基础包的模块时 ID 一致
- **过滤**：`processModuleFilter` 在构建业务包时排除基础包中已有的模块
- **加载**：先执行基础包，再按需执行业务包（原生提供加载 bundle 到同一运行时的接口）
- **版本约束**：业务包声明依赖的基础包版本；基础包升级时要重新构建所有业务包
- 替代方案：**Module Federation 2.0 对 Metro 的支持**（Re.Pack / 官方方案）

**口述模板（30–60 秒）**

1. 一句话结论：把 RN 拆成基础包和业务包，业务包只包含业务代码。
2. 关键机制：通过稳定的模块 ID 让业务包引用基础包中的模块。
3. 对比或注意点：业务包与基础包的版本要匹配。
4. 可追问时补充：Module Federation 2.0 支持 Metro，是更标准化的方案。

**常见追问**

- 拆包的收益是什么？→ 业务独立构建和热更新、热更新包体积小、页面打开时只执行业务代码。

### Q13. 热更新平台需要哪些能力？

- **难度**: 高级
- **标签**: 热更新, 平台

**答案**

| 能力 | 说明 |
|------|------|
| 版本匹配 | bundle 绑定**原生版本（runtime version）**；不匹配的不下发 |
| **差量更新** | 新旧 bundle 的二进制差分（bsdiff），减少下载量 |

| 合规 | 不用于发布重大功能变化 |

**口述模板（30–60 秒）**

1. 一句话结论：热更新平台需要版本匹配、差量更新、灰度、签名校验和回滚。
2. 关键机制：bundle 绑定原生版本，不匹配的不下发。
3. 对比或注意点：bundle 必须签名，防止被篡改。
4. 可追问时补充：客户端有启动保护，崩溃时自动回退。

**常见追问**

- 差量更新的基准版本不一致怎么办？→ 服务端为常见的旧版本预生成差分包；没有对应差分包时下发全量。

### Q14. 怎么设计一个多端统一的组件库？

- **难度**: 高级
- **标签**: 组件库, 多端

**答案**

**目标端**：RN App、小程序（Taro）、H5。

**分层**：

```text
设计令牌（颜色、字号、间距、圆角）—— 与平台无关，生成各端的格式
     │
逻辑层（headless）：状态、交互、无障碍的逻辑（hooks）—— 多端共享
     │
视图层：各端的实现（RN 组件 / Taro 组件 / Web 组件）
```

**策略**：

- 共享**设计令牌**和**逻辑**，视图各端实现（视图差异大，强行统一会牺牲体验）
- 统一的 API（属性名、事件名），使用方切换平台的成本低
- 平台扩展名或条件编译选择实现
- 每端独立的视觉回归测试

**口述模板（30–60 秒）**

1. 一句话结论：多端组件库共享设计令牌和逻辑，视图层各端分别实现。
2. 关键机制：逻辑用 headless 的 hooks 共享，API 保持一致。
3. 对比或注意点：视图强行统一会牺牲各端的体验和性能。
4. 可追问时补充：设计令牌从一份源数据生成各端格式。

**常见追问**

- 为什么不用 react-native-web 一套代码覆盖 Web？→ 可行（Expo 支持 Web），适合内部工具；对 Web 体验和 SEO 要求高的场景，单独实现更好。

### Q15. 一套代码覆盖 App、小程序、H5，架构怎么设计？

- **难度**: 高级
- **标签**: 多端架构

**答案**

**选择方案**：

- 以小程序 + H5 为主 → Taro / uni-app
- 以 App 为主 → RN（+ react-native-web 覆盖 H5）
- 三端都重要 → Taro（支持 RN）或「业务逻辑共享 + 视图分端」

**通用的分层**：

```text
业务逻辑层（纯 TS）：领域模型、服务、状态、校验 —— 100% 共享
     │
适配层（接口 + 各端实现）：请求、存储、路由、登录、支付、分享、埋点
     │
视图层：组件库（多端统一 API）+ 页面
```

- **适配层**是关键：业务代码依赖接口（`IStorage`、`IRouter`），各端注入实现
- 平台特有的功能（小程序的订阅消息、App 的推送）通过能力检测或条件编译
- Monorepo 管理：`packages/core`、`packages/adapters/*`、`apps/*`

**口述模板（30–60 秒）**

1. 一句话结论：多端架构分为业务逻辑层、适配层和视图层。
2. 关键机制：业务逻辑是纯 TS 完全共享，平台能力通过适配层的接口注入。
3. 对比或注意点：视图层用多端统一 API 的组件库，必要时分端实现。
4. 可追问时补充：用 Monorepo 管理核心包、适配层和各端应用。

**常见追问**

- 共享代码的比例一般能到多少？→ 业务逻辑接近全部共享；视图层取决于方案，Taro 在小程序和 H5 之间很高，到 App 端需要较多适配。

### Q16. 跨端应用的离线和数据同步怎么设计？

- **难度**: 高级
- **标签**: 离线, 同步

**答案**

场景：外勤、巡检类 App 需要离线工作。

- **本地数据库**：SQLite（WatermelonDB、Drizzle + expo-sqlite）
- **写操作**：先写本地 + **操作日志（outbox）**，联网后按顺序同步到服务端
- **拉取**：基于时间戳或版本号的增量同步
- **冲突**：最后写入胜出 / 字段级合并 / 提示用户；关键数据用服务端版本号做乐观锁
- **幂等**：每个操作有客户端生成的 ID，服务端去重（网络重试不会重复提交）
- **附件**：图片单独上传队列，断点续传

**口述模板（30–60 秒）**

1. 一句话结论：离线方案的核心是本地数据库加操作日志。
2. 关键机制：写操作先写本地，联网后按顺序同步。
3. 对比或注意点：每个操作有客户端 ID，服务端去重保证幂等。
4. 可追问时补充：冲突按业务选择最后写入胜出、字段合并或人工处理。

**常见追问**

- 为什么同步要按顺序？→ 后面的操作可能依赖前面的结果（先创建后修改），乱序会导致失败或数据错误。

### Q18. 怎么把原生 App 渐进迁移到 RN？

- **难度**: 高级
- **标签**: 迁移

**答案**

1. **基础设施**：在原生工程中集成 RN（brownfield）；路由中心；RN 容器；基础原生模块（用户、网络、埋点、配置）
2. **选择试点页面**：变化频繁、交互不复杂、独立性强的页面（例如活动页、设置页、列表详情）
3. **度量**：试点页面的性能（首屏、帧率）、崩溃率、开发效率
4. **扩展**：总结规范（组件库、原生模块的接口），逐步迁移更多页面
5. **保留原生**：性能敏感的页面（首页、复杂动画、音视频）可以保持原生

**风险**：混合栈复杂度；团队需要同时掌握原生和 RN；包体积增加。

**口述模板（30–60 秒）**

1. 一句话结论：先在原生工程中集成 RN 基础设施，再从试点页面开始渐进迁移。
2. 关键机制：路由中心和 RN 容器让原生页面和 RN 页面互相跳转。
3. 对比或注意点：试点选择变化频繁、交互简单的页面。
4. 可追问时补充：性能敏感的页面可以保持原生，用数据决定是否继续推进。

**常见追问**

- 怎么说服团队？→ 用试点页面的数据：开发效率（多端一次开发）、热更新带来的修复速度、性能没有明显下降。

## 五、安全与合规

### Q21. WebView 和 JSBridge 的安全怎么做？

- **难度**: 高级
- **标签**: 安全, WebView

**答案**

| 风险 | 措施 |
|------|------|
| 任意页面调用 Bridge | **域名白名单**：只有可信域名的页面才能调用；按接口分级（敏感接口只允许特定域名） |
| 打开任意 URL | URL 跳转白名单；外部链接用系统浏览器打开 |
| 敏感数据泄露 | 令牌不直接暴露给 H5；用一次性票据换取 |
| Android `addJavascriptInterface` | 只暴露带 `@JavascriptInterface` 注解的方法（Android 4.2+）；不要在不可信页面注入 |
| 文件访问 | 禁止 `file://` 访问（`setAllowFileAccess(false)` 等） |
| 中间人 | 只允许 HTTPS；证书校验不能忽略错误 |
| XSS | H5 本身的 XSS 防护（XSS 在 App 中危害更大，因为可以调用 Bridge） |

**口述模板（30–60 秒）**

1. 一句话结论：WebView 安全的核心是控制哪些页面能调用 Bridge 以及能调用什么。
2. 关键机制：域名白名单加接口分级。
3. 对比或注意点：令牌不直接暴露给 H5，只允许 HTTPS。
4. 可追问时补充：H5 的 XSS 在 App 中危害更大，因为可以调用原生能力。

**常见追问**

- 怎么判断调用 Bridge 的页面的域名？→ 原生在收到调用时读取 WebView 当前的 URL（主框架），而不是信任 JS 传来的参数。

### Q22. 热更新的安全和合规要注意什么？

- **难度**: 高级
- **标签**: 热更新, 合规

**答案**

**安全**：

- bundle 签名（私钥只在发布系统中），客户端用内置公钥校验
- HTTPS 下载 + 哈希校验
- 防止降级攻击（拒绝低于当前版本的 bundle，回滚由服务端显式指令）
- 发布权限和审批

**合规**：

- 苹果：允许下载解释执行的代码，前提是不改变 App 的主要用途、不绕过审核、不提供未审核的新功能
- 国内应用商店和监管：关注隐私合规（新增的权限和数据收集需要重新声明）
- **原则**：热更新用于修复问题和小幅调整，重大功能走正常发版

**口述模板（30–60 秒）**

1. 一句话结论：热更新要用签名防篡改，并遵守应用商店的规则。
2. 关键机制：私钥只在发布系统，客户端用内置公钥校验。
3. 对比或注意点：不能用热更新提供未审核的重大功能。
4. 可追问时补充：拒绝低于当前版本的 bundle，防止降级攻击。

**常见追问**

- 为什么 HTTPS 还不够，还要签名？→ HTTPS 只保护传输；CDN 或存储被入侵时，签名能防止被篡改的 bundle 执行。

### Q23. App 的隐私合规要注意什么？

- **难度**: 高级
- **标签**: 隐私, 合规

**答案**

- **隐私政策同意前**不能收集个人信息、不能初始化收集信息的第三方 SDK（国内监管重点）
- **权限**：按需申请（用到时才申请），说明用途；拒绝后功能降级而不是退出
- **第三方 SDK**：清单和用途披露；SDK 版本要合规
- **iOS**：App 隐私清单（Privacy Manifest）、ATT（跟踪需要授权）
- **Android**：targetSdk 要求、敏感权限
- **小程序**：用户隐私保护指引（在后台配置），调用敏感接口前需要用户同意
- **检测**：上架前用合规检测工具扫描

**口述模板（30–60 秒）**

1. 一句话结论：隐私合规的重点是同意前不收集、权限按需申请、SDK 披露。
2. 关键机制：用户同意隐私政策前，不能初始化收集信息的 SDK。
3. 对比或注意点：iOS 有隐私清单和 ATT，小程序有隐私保护指引。
4. 可追问时补充：上架前用合规检测工具扫描。

**常见追问**

- RN 中怎么保证同意前不初始化 SDK？→ 把 SDK 的初始化从原生的启动流程中移出，在用户同意后通过原生模块触发。

### Q24. RN App 的安全加固有哪些？

- **难度**: 高级
- **标签**: 安全

**答案**

- **敏感数据**：令牌存 Keychain / Keystore；不在 JS bundle 中硬编码密钥（bundle 可以被提取）
- **代码保护**：Hermes 字节码增加逆向难度（但不是加密）；原生代码混淆（R8）
- **网络**：HTTPS；证书锁定（pinning，要有更新策略）
- **完整性**：Root / 越狱检测；运行环境检测（Play Integrity、App Attest）
- **深链接**：校验参数，不能通过深链接直接执行敏感操作
- **日志**：Release 版本移除调试日志

**口述模板（30–60 秒）**

1. 一句话结论：RN 的安全加固覆盖数据存储、代码保护、网络和运行环境。
2. 关键机制：令牌存在 Keychain / Keystore，JS bundle 中不放密钥。
3. 对比或注意点：Hermes 字节码只是增加逆向难度，不是加密。
4. 可追问时补充：用 Play Integrity 和 App Attest 校验运行环境。

**常见追问**

- 证书锁定有什么风险？→ 证书更换时旧版本 App 无法连接 → 锁定公钥而不是证书，并配置备用公钥。

### Q25. 讲一个跨端项目的经验

- **难度**: 高级
- **标签**: 项目经验

**答案**

**STAR 参考**：

- **背景**：「电商 App 的商品详情页是原生开发，iOS 和 Android 两套，需求迭代慢；大促期间需要频繁调整」
- **任务**：「用 RN 重构详情页，支持热更新，首屏时间不劣化」

### Q26. 跨端技术有哪些趋势？

- **难度**: 高级
- **标签**: 趋势

**答案**

（截至 2026-10，以官方为准）

- **RN 新架构全面落地**：旧架构移除，Hermes V1 默认；与 React 新特性（并发、React Compiler）同步；Expo 成为默认的开发方式
- **小程序渲染升级**：Skyline + glass-easel，Worklet 动画；跨端框架跟进 Skyline
- **编译到原生**：uni-app x、KMP / Compose Multiplatform，追求原生性能
- **鸿蒙**：各跨端框架都在适配，成为跨端方案的必选项
- **Web 能力增强**：PWA、View Transitions 等让 H5 体验接近 App
- **AI 辅助**：设计稿到代码、多端代码生成和迁移
