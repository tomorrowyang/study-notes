# 跨端开发系统设计

> 回答结构：先澄清需求和约束 → 给出整体架构 → 展开关键设计 → 说明指标和取舍 → 回应扩展追问。跨端设计题的重点是「体验与效率的平衡」「动态化与合规」「平台差异的隔离」。

---

### S1. 设计 RN 热更新平台

- **难度**: 高级
- **标签**: RN, 热更新, 平台

**澄清问题（面试时先问）**

- App 的规模（日活、业务数量）？是否拆包？
- 是否使用 Expo（可以直接用 EAS Update）？还是需要自建？
- 灰度和回滚的要求？
- 合规要求（哪些变更允许热更新）？

**参考方案**

```text
CI 构建
  │ 按 runtimeVersion 构建 bundle（Hermes 字节码）+ sourcemap
  │ 生成与常见旧版本的差分包（bsdiff）
  │ 签名（私钥在 KMS 中）
  ▼
发布控制台 ──── 发布单（版本、runtimeVersion、灰度规则、审批）
  │
  ▼
更新服务（检查接口）── 读取：发布单 + 设备信息（runtimeVersion、当前 bundle、用户、渠道）
  │                      返回：manifest（全量 / 差分地址、哈希、签名）或无更新
  ▼
CDN（bundle、差分包）
  │
客户端 SDK：检查 → 下载 → 合并差分 → 校验哈希和签名 → 下次启动生效
            启动保护（崩溃回滚）→ 上报更新事件
  │
监控：到达率、下载失败率、按 bundle 版本的崩溃率、JS 错误率 → 自动停止灰度
```

**关键设计**

- **版本匹配**：runtimeVersion 由原生代码的指纹计算（原生依赖变化时自动改变）
- **灰度**：白名单 → 1% → 10% → 全量；按设备 ID 哈希稳定分桶
- **回滚**：服务端把「当前版本」切回上一版；客户端启动保护
- **安全**：签名、HTTPS、拒绝降级
- **拆包场景**：基础包和业务包分别发布，业务包声明依赖的基础包版本

**关键指标**

- 更新到达率（24 小时内多少设备更新到新版本）
- 下载成功率、差分命中率
- 新 bundle 的崩溃率和 JS 错误率 vs 旧版本

**口述模板（2–3 分钟）**

我先确认是否可以直接用 EAS Update；如果需要自建，平台分为构建、发布控制、更新服务、CDN 和客户端 SDK 五部分。

构建时按原生版本（runtimeVersion）生成 Hermes 字节码的 bundle 和 sourcemap，同时生成与常见旧版本的差分包，并用 KMS 中的私钥签名。

发布控制台创建发布单，配置灰度规则并审批。更新服务根据设备的原生版本、当前 bundle 和用户信息决定下发什么，原生版本不匹配的绝不下发。

客户端下载后校验哈希和签名，下次启动生效，并有启动保护：新 bundle 启动后没有确认成功就回滚。

监控按 bundle 版本对比崩溃率和错误率，异常时自动停止灰度。合规上，热更新只用于修复问题和小幅调整。

**扩展追问**

- 紧急修复需要立即生效怎么办？→ 下载完成后提示用户重启，或在下次进入后台时静默重载；关键问题可以设置强制更新。

### S2. 设计原生 + RN + H5 的混合 App 架构

- **难度**: 高级
- **标签**: 混合开发, 架构

**澄清问题（面试时先问）**

- 现有 App 是原生开发吗？各技术栈的页面占比计划？
- 哪些业务需要动态发布？
- 团队构成（原生、前端）？

**参考方案**

```text
┌──────────────────────── App ────────────────────────┐
│ 统一路由中心（app://module/page?params）              │
│   ├─ 原生页面：首页、音视频、相机等性能敏感的页面       │
│   ├─ RN 容器：RN 实例池（基础包预加载）+ 业务包          │
│   └─ WebView 容器：WebView 池 + 离线包 + JSBridge       │
│                                                       │
│ 统一能力层（原生实现，三种页面共享同一套接口）           │
│   用户 / 登录、网络、存储、埋点、分享、支付、配置、权限  │
│   RN：原生模块        H5：JSBridge（域名白名单）         │
│                                                       │
│ 动态化：RN 热更新平台、H5 离线包平台、配置中心           │
│ 监控：崩溃、JS 错误、页面性能（按容器类型和版本）        │
└───────────────────────────────────────────────────────┘
```

**关键设计**

- **路由**：统一 URL，路由表由配置中心下发，可以把某个页面在原生 / RN / H5 之间切换（降级）
- **能力层**：接口定义一次，RN 和 H5 各自暴露；权限按调用方（业务、域名）控制
- **容器**：RN 实例和 WebView 预创建复用
- **降级**：RN 页面加载失败时降级到 H5 版本（同一个 URL 的备用实现）
- **技术栈选择规则**：性能敏感 → 原生；高频迭代的核心业务 → RN；活动和营销 → H5

**关键指标**

- 各类容器的页面打开耗时、崩溃率、白屏率
- 动态发布的次数和到达率

**口述模板（2–3 分钟）**

混合 App 的核心是统一的路由中心和统一的能力层。

路由中心使用统一的 URL，页面可以是原生、RN 或 H5 实现，路由表由配置中心下发，这样某个页面出问题时可以在不同实现之间切换。

能力层用原生实现一次，RN 通过原生模块、H5 通过 JSBridge 使用同一套接口，H5 的调用要按域名白名单控制权限。

性能上 RN 实例和 WebView 都预创建复用，H5 使用离线包。技术栈的选择有明确的规则：性能敏感的用原生，高频迭代的核心业务用 RN，活动页用 H5。

监控按容器类型和版本拆分，便于定位问题出在哪一层。

**扩展追问**

- 三种容器之间怎么共享登录态？→ 由原生的用户模块统一管理；RN 通过原生模块读取；H5 通过 JSBridge 获取一次性票据换取会话，而不是直接拿到令牌。

### S3. 设计一个电商小程序（性能与体验）

- **难度**: 中级
- **标签**: 小程序, 电商

**澄清问题（面试时先问）**

- 原生开发还是 Taro / uni-app？是否需要同时发布 H5 / 其他平台小程序？
- 流量峰值（大促）？
- 核心路径：首页 → 搜索 / 列表 → 详情 → 下单 → 支付？

**参考方案**

```text
主包：首页、tabBar 页面、公共组件和基础库（体积预算）
分包：商品（列表、详情）、交易（购物车、下单）、用户中心、活动（独立分包）
预下载：首页 → 商品分包；详情 → 交易分包

数据：
  首页：数据预拉取 + 本地缓存先渲染 + 初始渲染缓存
  列表：分页追加（路径 setData）、图片懒加载、曝光埋点
  详情：列表页带入的基础信息先渲染（标题、主图、价格），详情数据到达后补充

交易：
  登录：wx.login → 自建登录态（静默）；手机号授权在下单时才请求
  支付：服务端统一下单 → wx.requestPayment → 以服务端回调为准确认结果
  下单防重：前端按钮防重 + 幂等令牌
```

**关键设计**

- **启动**：主包精简、按需注入、预拉取、骨架屏
- **setData**：只传渲染数据；长列表分页追加、组件化
- **图片**：CDN + 按尺寸裁剪 + WebP；懒加载
- **大促**：活动页独立分包；接口限流时前端排队提示；静态数据 CDN 化
- **转化**：分享卡片、订阅消息（下单后请求授权）

**关键指标**

- 启动耗时、首页首屏时间
- 详情页打开时间、下单转化率、支付成功率
- 体验评分

**口述模板（2–3 分钟）**

电商小程序我会先规划分包：主包只放首页和 tabBar 页面，商品、交易、用户中心、活动分别分包，活动页做成独立分包，并根据用户路径配置预下载。

首页使用数据预拉取和本地缓存先渲染，开启初始渲染缓存。列表分页时用路径 setData 只追加新数据，图片走 CDN 按尺寸裁剪。详情页先用列表带过来的基础信息渲染，详细数据到达后补充，这样打开就有内容。

交易链路上，登录是静默的，手机号授权放到下单时才请求，减少流失。支付由服务端统一下单，结果以服务端回调为准，下单接口用幂等令牌防重。

最后用启动耗时、首屏时间、转化率和支付成功率衡量。

**扩展追问**

- 支付成功回调了但订单状态没更新？→ 前端以 `requestPayment` 的结果作为参考，轮询服务端订单状态；服务端以微信的支付通知为准，并有主动查询兜底。

### S4. 设计多端统一的业务开发方案（App + 多平台小程序 + H5）

- **难度**: 高级
- **标签**: 多端, 架构

**澄清问题（面试时先问）**

- 各端的重要程度和流量？
- 现有技术栈和团队？
- 各端功能是否一致？差异有多大？

**参考方案**

```text
Monorepo
├── packages/
│   ├── core/          业务逻辑（纯 TS）：领域模型、服务、状态、校验
│   ├── api/           接口定义和请求（基于适配层）
│   ├── platform/      平台接口（IStorage、IRouter、IAuth、IPay、IShare）
│   ├── adapters/      weapp / alipay / h5 / rn 的实现
│   ├── ui/            多端组件库（设计令牌 + 统一 API）
│   └── tokens/        设计令牌
├── apps/
│   ├── mini/          Taro：微信、支付宝、抖音小程序 + H5
│   └── app/           React Native（Expo）
```

**关键设计**

- **方案**：小程序和 H5 用 Taro（React）；App 用 RN；共享 React 技能和业务逻辑
- **共享层次**：业务逻辑 100% 共享；组件库共享 API 和设计令牌，视图分端实现
- **平台差异**：适配层接口；平台特有功能通过能力检测（`platform().capabilities.subscribeMessage`）
- **质量**：core 层的单元测试覆盖率高（一处测试，多端受益）；各端 E2E 覆盖核心流程
- **发布**：各端独立发布；core 的修改触发受影响的端构建

**关键指标**

- 代码共享比例
- 需求的多端交付周期
- 各端的缺陷率

**口述模板（2–3 分钟）**

我的思路是共享业务逻辑，视图按端适配，而不是追求一套视图代码覆盖所有端。

具体用 Monorepo：core 包放领域模型、服务和状态，是纯 TypeScript；platform 包定义存储、路由、登录、支付等接口，adapters 包为每个端实现；组件库共享设计令牌和 API，视图在各端分别实现。

应用层面，小程序和 H5 用 Taro，App 用 React Native，两者都基于 React，团队技能可以复用。

平台特有的功能通过能力检测处理，避免业务代码中到处判断平台。质量上重点测试 core 层，一次测试多端受益。

最后用代码共享比例和多端交付周期衡量方案效果。

**扩展追问**

- 为什么不用 Taro 同时覆盖 App？→ 可以，但 App 端对性能和原生能力的要求更高，直接用 RN 的生态和控制力更好；视团队情况决定。

### S5. 设计 H5 离线包平台

- **难度**: 高级
- **标签**: 混合开发, 离线包

**澄清问题（面试时先问）**

- 需要离线化的 H5 业务数量？包的大小？
- 更新的实时性要求？
- iOS 和 Android 都要支持？

**参考方案**

```text
构建：H5 项目构建 → 打包为 zip（资源 + manifest：路径映射、版本、哈希）→ 签名 → 上传
平台：离线包管理（业务、版本、灰度、适用的 App 版本）、差分包生成
App：
  启动 / 前台时检查更新（按业务）→ 下载 zip / 差分 → 校验 → 解压到版本目录 → 切换当前版本
  WebView 请求拦截：
    Android shouldInterceptRequest / iOS WKURLSchemeHandler（自定义 scheme）或代理
    URL 命中 manifest → 返回本地文件；未命中 → 走网络
  失效：离线包损坏或过期 → 回退线上
```

**关键设计**

- **URL 映射**：页面仍使用线上 URL（便于降级），拦截层根据 manifest 映射到本地文件
- **HTML 的更新**：HTML 也在离线包中时，更新依赖离线包；需要更实时时 HTML 走线上、静态资源走离线
- **iOS 的限制**：WKWebView 不能直接拦截 http(s) 请求 → 使用自定义 scheme 或本地服务
- **版本一致性**：同一个页面的所有资源来自同一个版本（避免混用）
- **存储管理**：保留当前和上一个版本，清理旧版本

**关键指标**

- 离线包命中率、页面首屏耗时（离线 vs 线上）
- 更新到达率、包下载失败率

**口述模板（2–3 分钟）**

离线包的思路是把 H5 的资源提前下载到本地，WebView 请求时拦截并返回本地文件。

构建时把资源打成 zip，带上 manifest 描述 URL 到文件的映射、版本和哈希，签名后上传到平台。平台管理版本、灰度和适用的 App 版本，并生成差分包。

App 在启动或回到前台时检查更新，下载后校验并解压到独立的版本目录，再切换当前版本，保证同一个页面的资源来自同一个版本。

拦截层在 Android 用 shouldInterceptRequest，iOS 由于 WKWebView 不能拦截 http 请求，使用自定义 scheme。页面使用线上 URL，未命中或离线包损坏时自动回退到网络。

最后用离线包命中率和首屏耗时的对比证明效果。

**扩展追问**

- 离线包和 SSR 能一起用吗？→ SSR 的 HTML 是动态的，不适合离线；可以离线静态资源，HTML 走线上；或者离线一个壳 HTML，数据通过接口获取。

### S6. 设计跨端应用的监控体系

- **难度**: 高级
- **标签**: 监控

**澄清问题（面试时先问）**

- 端的类型：RN App、小程序、H5、混合？
- 已有的监控平台（自研 / Sentry / 云厂商）？
- 关注的问题：崩溃、性能、业务？

**参考方案**

```text
采集 SDK（各端实现，统一的数据模型）
  公共字段：app、端、原生版本、bundle / 代码包版本、设备、系统、用户 ID（脱敏）、会话 ID
  事件：
    错误：原生崩溃、JS 错误、Promise 未处理、请求错误、白屏
    性能：启动、页面首屏、帧率 / 卡顿、setData 耗时（小程序）、内存
    行为：页面访问、点击、曝光
上报：批量、压缩、采样；离线缓存后补报
处理：符号化（dSYM、mapping、sourcemap 按版本匹配）→ 聚合 → 存储
展示与告警：按端、版本、页面、机型；新版本自动对比；告警到责任人
```

**关键设计**

- **统一的数据模型**：各端字段一致，便于横向对比
- **版本维度**：RN 有原生版本 + bundle 版本两个维度；小程序有代码包版本 + 基础库版本
- **符号化**：CI 中上传 sourcemap / dSYM，与版本绑定
- **隐私**：用户同意前不采集；数据脱敏
- **成本**：采样（性能数据）、全量（错误）

**关键指标**

- 崩溃率、JS 错误率、白屏率
- 启动耗时、首屏时间的分位数

**口述模板（2–3 分钟）**

跨端监控的关键是统一的数据模型：每个端有自己的采集 SDK，但上报的字段一致，包括端类型、原生版本、代码包或 bundle 版本、设备和会话，这样可以横向对比。

采集内容分为错误、性能和行为。错误包括原生崩溃和 JS 错误，性能包括启动、首屏、卡顿，小程序还要采集 setData 的耗时。

处理时要按版本做符号化，所以 CI 必须上传 sourcemap 和 dSYM。RN 要同时看原生版本和 bundle 版本两个维度，否则热更新引入的问题无法定位。

隐私上，用户同意前不采集，数据要脱敏。成本上错误全量、性能采样。最后新版本自动和旧版本对比，异常时告警到责任人。

**扩展追问**

- 小程序的白屏怎么检测？→ 页面 onReady 后检查关键节点是否存在（`createSelectorQuery`），或者检查首屏关键数据是否到达；超时上报。

### S7. 设计离线优先的外勤 App

- **难度**: 高级
- **标签**: 离线, RN

**澄清问题（面试时先问）**

- 离线的时长？数据量（任务、表单、照片）？
- 多人是否会修改同一份数据？
- 数据安全要求（设备丢失）？

**参考方案**

```text
RN（Expo）
├─ 本地数据库：SQLite（WatermelonDB / Drizzle）
├─ 同步引擎：
│   拉取：按 updated_at 增量拉取任务和基础数据
│   推送：outbox 操作队列（客户端 ID、顺序、退避重试）
│   附件：独立的上传队列，分片和断点续传
├─ 冲突处理：服务端版本号；冲突时按字段合并或进入人工处理
├─ 网络感知：NetInfo；恢复网络和回到前台时触发同步
├─ 后台任务：expo-background-task（系统允许的范围内）
└─ 安全：数据库加密（SQLCipher）、密钥存在 Keychain / Keystore；远程擦除
```

**关键设计**

- **UI 只读本地数据库**，同步在后台进行 → 在线和离线的体验一致
- **幂等**：客户端 ID，服务端去重
- **同步状态可见**：待同步的数量、失败的操作可以重试
- **照片**：压缩后入队；与表单关联通过客户端 ID

**关键指标**

- 同步成功率、平均同步延迟
- 冲突率、数据丢失事件（目标为 0）

**口述模板（2–3 分钟）**

离线优先的核心原则是 UI 只读写本地数据库，同步完全在后台进行，这样在线和离线的体验一致。

数据库用 SQLite。同步分为拉取和推送：拉取按更新时间增量获取；推送使用操作队列，每个操作有客户端生成的 ID，按顺序发送，失败时退避重试，服务端按 ID 去重保证幂等。照片走独立的上传队列，支持断点续传。

冲突用服务端版本号检测，按字段合并或者交给人工处理。网络恢复和 App 回到前台时触发同步。

安全上数据库加密，密钥存在 Keychain / Keystore，支持远程擦除。

最后同步状态要对用户可见，并以「数据零丢失」作为核心指标。

**扩展追问**

- iOS 后台同步受限怎么办？→ 系统不保证后台执行时间；重要的同步在前台完成，并提示用户「有 N 条待同步」。

### S8. 设计多端统一的组件库

- **难度**: 高级
- **标签**: 组件库, 多端

**澄清问题（面试时先问）**

- 覆盖的端：RN、Taro 小程序、Web？
- 品牌和主题的数量？是否需要暗色模式？
- 由谁维护、使用方数量？

**参考方案**

```text
设计源（Figma Variables）
  ▼
tokens 包：JSON → 构建为 CSS 变量（Web / 小程序）、TS 常量（RN）、主题对象
  ▼
headless 包：组件逻辑 hooks（useSelect、useDialog）、无障碍属性、状态机 —— 平台无关
  ▼
视图包：
  @ui/web     React DOM 实现
  @ui/taro    Taro 组件实现（小程序 + H5）
  @ui/native  RN 实现
  统一的组件 API（props 和事件名一致）
  ▼
文档：Storybook（Web）+ 各端的示例 App
质量：各端视觉回归、API 一致性检查（类型测试）
```

**关键设计**

- **令牌驱动主题**：品牌切换和暗色模式只改令牌
- **API 一致**：用共享的 TypeScript 类型定义各组件的 props，各端实现必须满足
- **平台差异**：允许各端扩展平台特有的属性，但核心属性一致
- **发布**：Changesets 统一管理版本，三个包同版本发布

**关键指标**

- 各端组件的覆盖率（某个组件在多少端可用）
- 使用方的接入数量、问题数

**口述模板（2–3 分钟）**

多端组件库我会分为三层：设计令牌、headless 逻辑和视图实现。

设计令牌从 Figma 导出，构建成各端需要的格式，品牌和暗色模式只需要切换令牌。headless 层用 hooks 实现组件的状态和交互逻辑以及无障碍属性，与平台无关。视图层每个端单独实现，但组件的 props 由共享的 TypeScript 类型约束，保证 API 一致，使用方在不同端写法相同。

这样做的原因是各端的渲染机制差异很大，强行共享视图代码会牺牲体验，而共享逻辑和 API 能获得大部分收益。

质量上各端都有视觉回归，并用类型测试检查 API 一致性。发布用 Changesets 统一版本。

**扩展追问**

- 小程序端的组件能用 headless hooks 吗？→ Taro 中可以直接使用 React hooks；原生小程序需要用 behaviors 或单独实现逻辑。
