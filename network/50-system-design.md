# 计算机网络系统设计题

> 回答结构：先澄清需求和约束（规模、延迟、可靠性、终端类型）→ 给出整体架构 → 说清协议选型和连接管理 → 可靠性与容错 → 安全 → 监控指标 → 主动说取舍和扩展。

### S1. 设计一个即时通讯（IM）系统的长连接层

- **难度**: 高级
- **标签**: 长连接, IM

**澄清问题（面试时先问）**

- 在线用户规模（百万？千万？）、峰值消息量？
- 终端：Web、App、小程序？
- 单聊、群聊，群的最大人数？
- 消息可靠性要求：不丢、不重、有序？
- 是否需要多端同步、已读回执？

**参考方案**

```text
客户端
  ├─ HTTPDNS / 调度服务：返回就近的接入点列表（按负载排序）
  └─ 长连接：WebSocket（Web）/ 自定义 TCP 或 QUIC 协议（App）
       ↓
L4 负载均衡
       ↓
接入层（Gateway 集群）：连接管理、心跳、鉴权、协议编解码；不含业务逻辑
       ↕ 在线路由表（用户 → 接入节点 + 连接 ID），Redis
逻辑层：消息服务（分配序号、存储、投递）、群服务、在线状态服务
       ↕ 消息队列（按接入节点或用户分区）
存储：消息库（按会话分片）、离线消息、同步位点
```

**关键设计**

- **消息可靠性**：
  - 发送：客户端生成消息 ID（幂等去重），服务端确认后才算发送成功，否则重试
  - 投递：每个会话的消息有**单调递增序号**；客户端确认收到的最大序号；断线重连后按序号**增量拉取**
  - 推拉结合：在线时推送，推送失败或重连时拉取
- **有序**：同一会话的消息在同一个分区处理，按序号排序显示
- **群消息**：扩散写（每个成员的收件箱）适合小群；扩散读（群的消息只存一份，成员按位点读取）适合大群
- **心跳**：自适应心跳（探测 NAT 超时），App 在后台时依赖系统推送通道
- **重连**：指数退避 + 抖动；接入层发布时通知客户端迁移
- **多端**：每个设备一个连接，消息投递到用户的所有在线设备，同步位点按设备记录

**关键指标**

- 在线连接数、单机连接数、建连成功率
- 消息端到端延迟（P99）、消息丢失率（序号空洞）、重复率
- 心跳超时率、重连频率

**口述模板（2–3 分钟）**

先确认规模、终端、群规模和可靠性要求。架构分为接入层、逻辑层和存储层。接入层只维护连接、心跳和鉴权，用户在哪个接入节点记录在 Redis 中，逻辑层通过路由表或按节点分区的消息队列把消息投递过去。

可靠性是核心：客户端生成消息 ID 保证幂等，服务端给每个会话的消息分配递增序号，客户端确认收到的位点，断线重连后按位点增量拉取，推拉结合保证不丢。群聊根据规模选择扩散写或扩散读。

连接管理上使用自适应心跳、指数退避重连，发布时分批迁移连接。监控连接数、端到端延迟和序号空洞。

**扩展追问**

- 消息的序号由谁分配？→ 服务端按会话分配（Redis INCR 或会话所在分区的单线程分配），保证会话内单调递增；全局不需要有序。

### S2. 设计大文件上传（分片、断点续传、秒传）

- **难度**: 中级
- **标签**: 上传, HTTP

**澄清问题（面试时先问）**

- 文件大小范围（几 GB？）、并发上传量？
- 存储：对象存储（OSS / S3）还是自建？
- 是否需要秒传（相同文件不重复上传）？
- 弱网环境多吗？

**参考方案**

```text
1. 客户端计算文件哈希（Web Worker 中增量计算，大文件可以抽样哈希 + 完整哈希）
2. 请求「初始化上传」：服务端检查哈希
   - 已存在 → 秒传，直接返回
   - 有未完成的上传 → 返回已完成的分片列表（断点续传）
   - 否则创建上传任务，返回上传 ID
3. 客户端并发上传分片（例如每片 5MB，并发 3–6 个），每片带序号和校验
   - 推荐：服务端签发预签名 URL，客户端直传对象存储（不经过业务服务器）
4. 所有分片完成后请求「合并」，服务端校验整体哈希
```

**关键设计**

- **分片大小**：太小请求太多，太大失败重传代价高；可以根据网速动态调整
- **并发**：并发控制（[手写题 H5](40-coding-handwritten.md)），失败分片单独重试（指数退避）
- **断点续传**：上传状态存储在服务端（上传 ID → 已完成的分片），客户端本地也记录
- **直传对象存储**：使用对象存储的分片上传接口 + 预签名 URL，减轻服务器带宽压力
- **安全**：预签名 URL 短期有效、限制大小和类型；**秒传需要防止哈希被用于探测他人的文件**（例如要求客户端证明拥有文件：服务端随机要求某个范围的哈希）
- **清理**：未完成的上传定期清理（对象存储的生命周期规则）
- **体验**：进度条（按字节）、暂停 / 恢复、页面关闭后恢复

**关键指标**

- 上传成功率、平均速度、分片重试率、秒传命中率

**口述模板（2–3 分钟）**

先确认文件大小、存储方式和是否需要秒传。流程是：客户端在 Web Worker 中计算文件哈希，请求初始化时服务端检查是否已存在，存在则秒传，有未完成的任务则返回已上传的分片实现断点续传。

分片上传时，服务端签发预签名 URL，客户端并发直传对象存储，失败的分片单独重试，全部完成后请求合并并校验哈希。

注意秒传的安全问题：只凭哈希就能「拥有」文件，可以通过要求客户端提供随机范围的哈希来证明持有文件。未完成的上传要定期清理。

**扩展追问**

- 计算大文件哈希太慢怎么办？→ Web Worker 中分块增量计算；或者先用抽样哈希（首尾和中间的若干块）快速判断秒传，再在上传过程中计算完整哈希。

### S3. 设计静态资源的全球加速方案

- **难度**: 中级
- **标签**: CDN, 性能

**澄清问题（面试时先问）**

- 用户分布：国内、海外、全球？
- 资源类型和总量？更新频率？
- 预算？是否需要多 CDN？
- 国内是否需要备案？

**参考方案**

```text
构建：内容哈希文件名 → 预压缩（br + gzip）→ 上传到对象存储（保留旧版本）
DNS：智能解析（按地区、运营商 → 不同的 CDN）
CDN：边缘节点 → 区域节点 → 源站保护层 → 对象存储（源站）
HTML：短缓存或 no-cache，指向带哈希的资源
```

**关键设计**

- **缓存策略**：带哈希的资源 `max-age=31536000, immutable`；HTML `no-cache`
- **发布顺序**：先上传新资源，再切换 HTML；旧资源保留至少一个发布周期（版本偏差）
- **协议**：开启 HTTP/3、TLS 1.3、HTTPS 记录；Brotli 预压缩
- **多 CDN**：国内和海外使用不同的厂商；按质量数据动态调度；任一 CDN 故障时切换
- **回源优化**：源站保护层减少回源；对象存储和 CDN 同一厂商（内网回源）
- **域名**：静态资源和主站同域名或少量域名（连接复用）；`preconnect`
- **图片**：CDN 图片处理（格式转换 AVIF / WebP、尺寸裁剪）
- **容灾**：资源加载失败时切换备用域名（前端重试逻辑）

**关键指标**

- 命中率、回源带宽、各地区下载耗时、资源加载失败率（按地区和 CDN）

**口述模板（2–3 分钟）**

先确认用户分布和预算。构建时生成带内容哈希的文件名并预压缩，上传到对象存储作为源站，保留旧版本。

DNS 智能解析把不同地区和运营商的用户调度到不同的 CDN，CDN 采用边缘、区域、源站保护层的分层结构降低回源。带哈希的资源长期缓存，HTML 每次验证；发布时先上传资源再切换 HTML。

协议上开启 HTTP/3 和 Brotli；图片使用 CDN 的格式转换。前端在资源加载失败时切换备用域名。监控按地区和 CDN 统计耗时和失败率，用于动态调度。

**扩展追问**

- 某个地区的 CDN 节点被污染或劫持怎么办？→ 全站 HTTPS；关键脚本使用 SRI；监控到异常时把该地区切换到其他 CDN。

### S4. 设计一个移动端 H5 在弱网下的网络优化方案

- **难度**: 高级
- **标签**: 弱网, 移动端

**澄清问题（面试时先问）**

- H5 运行在 App 的 WebView 中还是浏览器中？（WebView 可以借助原生能力）
- 用户的网络分布（2G / 3G / 4G / 5G / Wi-Fi 的比例）？
- 核心场景：首屏打开、列表浏览、提交表单？

**参考方案**

```text
首屏：
  - 离线包：H5 资源预先下载到 App 本地，WebView 拦截请求直接返回（0 网络）
  - 或 Service Worker 缓存 + 预缓存
  - 数据预取：App 在打开 WebView 的同时并行请求首屏数据（不等 H5 加载完）
  - HTTPDNS + 连接预热
请求：
  - 统一请求层：超时分级、幂等请求重试（退避 + 抖动）、并发控制、优先级
  - 接口聚合（BFF），减少往返
  - 响应压缩、字段裁剪
资源：
  - 图片按网络质量降级（effectiveType、Save-Data）
  - 非关键资源延迟加载
提交：
  - 幂等键 + 重试；离线时排队，恢复后发送
  - 乐观更新
```

**关键设计**

- **离线包**：版本管理（增量更新、差分包）、校验（签名防篡改）、回退到线上资源
- **网络质量感知**：根据 RTT 和带宽估算动态调整（图片质量、预加载数量、超时）
- **协议**：App 网络库使用 QUIC（Cronet 等），H5 请求可以通过原生代理走 QUIC
- **降级**：接口失败时显示缓存数据并提示，而不是白屏

**关键指标**

- 首屏时间（按网络类型分组的 P50 / P90）、白屏率、接口成功率、重试率

**口述模板（2–3 分钟）**

先确认是否在 App 的 WebView 中，以及用户的网络分布。首屏优化的核心是减少网络依赖：使用离线包或 Service Worker 让资源本地化，App 在打开 WebView 的同时并行预取首屏数据，并使用 HTTPDNS 和连接预热。

请求层统一处理超时、幂等请求的退避重试和优先级，接口在 BFF 中聚合减少往返。图片根据网络质量降级。提交操作使用幂等键，离线时排队。

App 的网络库可以使用 QUIC 改善弱网下的表现。失败时展示缓存数据而不是白屏。监控按网络类型分组的首屏时间和成功率。

**扩展追问**

- 离线包怎么保证安全？→ 包签名校验、HTTPS 下载、版本回滚机制；离线包中的页面仍然要遵守 CSP。

### S5. 设计一个 API 网关

- **难度**: 高级
- **标签**: 网关

**澄清问题（面试时先问）**

- 流量规模、后端服务数量？
- 需要哪些能力：鉴权、限流、路由、灰度、协议转换？
- 部署在云上还是自建？对延迟的要求？

**参考方案**

```text
客户端 → CDN / WAF → L4 负载均衡 → 网关集群（无状态，水平扩展）
网关请求处理链：
  TLS 终止 → 请求解析与校验（大小、头部）→ 路由匹配 → 鉴权（JWT 验签 / 调用认证服务）
  → 限流（本地令牌桶 + Redis 全局限流）→ 灰度路由 → 负载均衡选择实例
  → 转发（连接池、超时、重试、熔断）→ 响应处理 → 日志与指标
配置中心：路由、限流规则热更新
```

**关键设计**

- **性能**：异步非阻塞 I/O；上游连接池；避免在网关中做重的业务逻辑
- **超时与重试**：按路由配置；只重试幂等请求；重试预算
- **熔断**：按上游服务统计错误率和延迟，打开后快速失败
- **限流**：多维度（全局、API、用户、IP）；本地限流（快）+ 全局限流（准）
- **鉴权**：JWT 本地验签（无需调用认证服务）；令牌吊销通过短有效期或吊销列表
- **安全**：请求大小限制、统一的 HTTP 解析（防止请求走私）、清理内部头部、WAF
- **灰度**：按用户 ID、头部、比例路由到不同版本
- **高可用**：网关无状态、多可用区；配置变更可回滚

**关键指标**

- 网关自身的延迟开销（P99）、各上游的错误率和延迟、限流和熔断的触发次数

**口述模板（2–3 分钟）**

先确认规模和需要的能力。网关集群无状态，前面有 WAF 和 L4 负载均衡。请求经过 TLS 终止、校验、路由、鉴权、限流、灰度、负载均衡，最后转发到上游。

转发时使用连接池，按路由配置超时，只重试幂等请求并设置重试预算，上游错误率高时熔断。限流结合本地令牌桶和 Redis 全局限流。鉴权使用 JWT 本地验签。

安全上统一 HTTP 解析防止请求走私，清理内部头部。路由和限流规则通过配置中心热更新。监控网关自身的延迟开销和各上游的健康状况。

**扩展追问**

- 网关本身成为瓶颈怎么办？→ 水平扩展；把耗时的逻辑（复杂的鉴权）移到边缘或服务内；按业务线拆分网关集群，避免互相影响。

### S6. 设计一个实时行情推送系统（股票 / 加密货币）

- **难度**: 高级
- **标签**: 实时推送

**澄清问题（面试时先问）**

- 标的数量、每秒更新次数？在线用户数？
- 延迟要求（毫秒级？秒级？）
- 用户订阅的标的数量？是否需要每一笔成交（不能丢）还是只需要最新价格（可以合并）？

**参考方案**

```text
行情源 → 行情处理服务（标准化、计算）→ 发布订阅（按标的分频道）
  → 推送节点集群（WebSocket）
      - 维护「标的 → 订阅的连接」映射
      - 合并与限频：每个连接每个标的最多每 N 毫秒推送一次最新值
  → 客户端：订阅 / 取消订阅；首次订阅先拉取快照，再接收增量
```

**关键设计**

- **合并（Conflation）**：价格类数据只需要最新值，高频更新时在推送节点合并，按固定频率推送（例如 100–250ms），大幅降低带宽；成交明细等不能丢的数据单独处理
- **快照 + 增量**：订阅时先发送快照，之后发送增量，带序号；序号不连续时重新拉取快照
- **扇出**：热门标的被大量用户订阅 → 每个推送节点只订阅一次上游频道，在节点内扇出
- **协议**：二进制格式（Protobuf）、压缩（permessage-deflate，注意 CPU 开销）
- **背压**：客户端消费慢（发送缓冲区积压）时丢弃旧的更新只保留最新值，或者断开慢客户端
- **页面不可见时**：客户端暂停订阅或降低频率

**关键指标**

- 端到端延迟（行情源到客户端）、推送频率、每个连接的带宽、慢客户端数量

**口述模板（2–3 分钟）**

先确认标的数量、更新频率、延迟要求，以及数据能否合并。行情经过处理服务后按标的发布到发布订阅系统，推送节点订阅上游频道并维护标的到连接的映射。

关键是合并：价格只需要最新值，推送节点按固定频率推送最新值，大幅降低带宽；不能丢的数据单独处理。订阅时先发快照再发增量，带序号检测丢失。

热门标的在节点内扇出，避免重复订阅上游。慢客户端只保留最新值或断开。页面不可见时降低频率。监控端到端延迟和慢客户端数量。

**扩展追问**

- 为什么不直接把每一次更新都推给客户端？→ 高频更新（每秒上百次）会超出客户端的渲染能力和网络带宽，人眼也无法分辨；合并后体验相同而成本大幅降低。

### S7. 设计一个前端网络质量监控平台

- **难度**: 中级
- **标签**: 监控, RUM

**澄清问题（面试时先问）**

- 监控对象：页面加载、接口、静态资源、长连接？
- 数据量（日活）？采样率？
- 维度：地区、运营商、网络类型、设备、版本？

**参考方案**

```text
采集（SDK）：
  - Navigation Timing：DNS、TCP、TLS、TTFB、下载
  - Resource Timing：静态资源（跨域需要 Timing-Allow-Origin）
  - 接口：包装 fetch / XHR，记录耗时、状态码、错误类型、请求 ID
  - 网络信息：effectiveType、RTT 估计
  - 资源加载失败（error 事件捕获）
上报：批量、sendBeacon、采样、失败重试
处理：接入 → 消息队列 → 流处理（清洗、IP 解析为地区和运营商、聚合）→ 时序 / OLAP 存储
展示：分维度的 P50 / P90 / P99、错误率、地图、告警
```

**关键设计**

- **维度**：IP → 地区 + 运营商；URL → 路由模板（避免基数爆炸）
- **错误分类**：DNS 失败、连接失败、超时、TLS 错误、HTTP 状态码、业务错误
- **关联**：请求 ID 与服务端追踪关联，区分网络耗时和服务端耗时（Server-Timing）
- **告警**：按维度检测异常（某地区某运营商错误率上升）
- **拨测**：补充主动监控（真实用户数据不足的地区、发现 CDN 故障）

**关键指标**

- 各阶段耗时分布、接口成功率、资源失败率、按维度的异常

**口述模板（2–3 分钟）**

先确认监控对象和维度。SDK 使用 Navigation Timing 和 Resource Timing 采集各阶段耗时，包装 fetch 采集接口的耗时和错误分类，同时记录网络类型。上报时批量、采样、使用 sendBeacon。

服务端把 IP 解析为地区和运营商，URL 归一化为路由模板，流处理后存入 OLAP 存储，按维度展示分位数和错误率。

通过请求 ID 和 Server-Timing 区分网络耗时和服务端耗时。按维度做异常检测和告警，并用拨测补充主动监控。

**扩展追问**

- 跨域资源的详细耗时为什么是 0？→ 跨域资源需要响应头 `Timing-Allow-Origin` 才能暴露详细的时序数据。

### S8. 设计多地域部署的流量调度方案

- **难度**: 高级
- **标签**: 多地域, 调度

**澄清问题（面试时先问）**

- 地域数量？用户分布？
- 数据是否可以跨地域访问（合规要求）？
- 故障切换的时间要求（RTO）和可接受的数据丢失（RPO）？
- 是否需要按用户固定地域（单元化）？

**参考方案**

```text
第一层：DNS / GSLB（或 Anycast）
  - 默认按地理位置就近
  - 健康检查失败时把该地域的流量切走
第二层：接入层（网关）
  - 按用户归属路由：用户 ID → 所属单元（地域），请求不在归属地时转发或重定向
第三层：单元内闭环
  - 一个用户的请求在归属单元内完成，数据在单元内读写
  - 跨单元数据异步复制（用于容灾）
```

**关键设计**

- **单元化**：按用户 ID 分片到单元，每个单元完整部署（服务 + 数据），避免跨地域同步调用
- **全局数据**（配置、商品目录）：只读副本复制到所有地域
- **故障切换**：
  - DNS 层切换受 TTL 影响 → 结合 Anycast 或客户端的多接入点重试
  - 切换前确认目标地域的容量（预留冗余）
  - 数据：被切换的用户在新单元中可能有复制延迟 → 只读模式或接受 RPO
- **合规**：数据驻留的用户不能被切换到其他国家的地域
- **演练**：定期进行切换演练

**关键指标**

- 跨地域调用比例（应该接近 0）、各地域的负载、切换时间、复制延迟

**口述模板（2–3 分钟）**

先确认地域数量、合规要求以及 RTO 和 RPO。调度分为三层：DNS 或 Anycast 就近接入并在故障时切换；网关按用户归属路由到所属单元；单元内闭环处理请求，避免跨地域同步调用。

全局数据以只读副本复制到所有地域。故障切换时 DNS 受 TTL 影响，可以结合 Anycast 或客户端的多接入点重试；切换前确认容量，复制延迟可能导致短暂的数据不一致，需要只读模式或接受一定的 RPO。

数据驻留的用户不能被切换到其他国家。定期演练，监控跨地域调用比例和复制延迟。

**扩展追问**

- 用户出差到其他国家，请求怎么处理？→ 就近接入后由网关识别归属单元，通过内部专线转发到归属单元处理（延迟增加但数据一致），或者根据合规要求决定。
