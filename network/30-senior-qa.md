# 计算机网络高级 Q&A

> 目标：能从网络层面分析性能和故障，设计 CDN、网关、长连接等基础设施，理解网络安全威胁和协议设计的取舍；回答时给出数据、排查步骤和权衡。

## 一、性能分析

### Q1. 从网络角度分析「输入 URL 到页面显示」的耗时，每一步怎么优化？

- **难度**: 高级
- **标签**: 性能, 全链路

**答案**

假设 RTT = 100ms（跨省移动网络）：

| 阶段 | 典型耗时 | 优化 |
|------|----------|------|
| 重定向（http → https、裸域 → www） | 每次 1+ RTT | HSTS preload；避免链式重定向 |
| DNS | 0–几百 ms | 缓存、`dns-prefetch`、HTTPS 记录、减少域名、HTTPDNS（App） |
| TCP 握手 | 1 RTT | 连接复用；HTTP/3 合并握手 |
| TLS 握手 | 1 RTT（TLS 1.3） | TLS 1.3、会话恢复、0-RTT、边缘终止 |
| 请求 → 首字节（TTFB） | 网络 1 RTT + 服务端处理 | CDN 缓存 HTML、流式渲染、103 Early Hints、服务端优化 |
| 下载 HTML | 受慢启动影响 | 压缩、关键内容在前 14KB 附近、流式输出 |
| 关键子资源 | 每个新域名重复 DNS + TCP + TLS | 同域名（连接复用）、`preconnect`、`preload`、HTTP/2 / HTTP/3 |

**结论**：在高 RTT 网络中，**往返次数**比带宽更重要。冷启动的 HTTPS 页面（重定向 + DNS + TCP + TLS + 请求）可能需要 5–6 个 RTT 才能拿到首字节，即 500ms 以上。

**口述模板（30–60 秒）**

1. 一句话结论：网络耗时由重定向、DNS、TCP、TLS、TTFB 和下载组成，高 RTT 下往返次数是关键。
2. 关键机制：HSTS 减少重定向，TLS 1.3 和 HTTP/3 减少握手往返，CDN 让 RTT 更小。
3. 对比或注意点：每个新域名都要重复 DNS、TCP、TLS，所以要减少关键路径上的域名。
4. 可追问时补充：103 Early Hints 和流式渲染利用服务端的处理时间提前开始加载。

**常见追问**

- 怎么在线上量化每个阶段？→ Navigation Timing / Resource Timing API（`domainLookupStart`、`connectStart`、`secureConnectionStart`、`responseStart`）按阶段上报，按地区、运营商、网络类型分析。

### Q2. 弱网环境（高延迟、高丢包、频繁切换）怎么优化？

- **难度**: 高级
- **标签**: 弱网, 性能

**答案**

**协议层**：

- **HTTP/3**：没有 TCP 队头阻塞，连接迁移（Wi-Fi 和移动网络切换不断开），更快的握手
- 服务端拥塞控制使用 **BBR**（对随机丢包不敏感）
- 合理的 TCP 初始窗口

**减少往返和数据量**：

- 合并关键请求、BFF 聚合接口
- 压缩（br / zstd）、精简响应字段、图片按网络质量降级（`Save-Data` 头、`navigator.connection.effectiveType`）
- 关键内容优先：骨架屏、关键 CSS 内联

**请求策略**：

- **超时分级**：连接超时短（快速失败），读取超时按接口设置
- **重试**：只重试幂等请求，**指数退避 + 随机抖动**，限制总次数
- **请求优先级**：关键请求优先，非关键请求延迟或取消
- 竞速：对关键请求在超时前发起第二个请求（对冲请求），取先返回的（只用于幂等请求，注意放大负载）

**离线和降级**：

- Service Worker 缓存（stale-while-revalidate）
- 本地数据先展示，后台同步
- 乐观更新 + 失败重试队列

**监控**：按网络类型、运营商、地区统计成功率和耗时，找到弱网用户的比例和痛点。

**口述模板（30–60 秒）**

1. 一句话结论：弱网优化从协议、往返次数、数据量、请求策略、离线降级五个方面入手。
2. 关键机制：HTTP/3 解决队头阻塞和网络切换；合并请求减少往返；按网络质量降级资源。
3. 对比或注意点：重试只针对幂等请求，使用指数退避和抖动，避免重试风暴。
4. 可追问时补充：Service Worker 缓存和本地优先，让弱网时仍然可用。

**常见追问**

- 为什么重试要加随机抖动？→ 服务故障恢复时，大量客户端在同一时刻重试会造成「惊群」，再次压垮服务。

### Q3. TTFB 很高，怎么判断是网络问题还是服务端问题？

- **难度**: 高级
- **标签**: 排查

**答案**

**拆分 TTFB**：

```text
TTFB（responseStart - requestStart）≈ 网络往返时间 + 服务端处理时间 + 中间层（CDN、网关）处理时间
```

**步骤**：

1. **Server-Timing 头部**：服务端在响应中报告各阶段耗时，浏览器 DevTools 和 Performance API 可以读取

```http
Server-Timing: db;dur=120, render;dur=80, cache;desc="MISS"
```

2. **对比 RTT**：`connectEnd - connectStart` 约为 1 个 RTT；如果 TTFB 远大于 RTT，主要是服务端或中间层
3. **分段测量**：
   - 在 CDN 边缘测量（CDN 日志中的回源时间）
   - 在负载均衡测量（上游响应时间）
   - 在服务内部测量（追踪）
4. **分地区对比**：只有特定地区或运营商慢 → 网络或 CDN 调度问题；全部慢 → 服务端问题
5. **对比缓存命中和未命中**：CDN 缓存命中的请求也慢 → 网络或 CDN 问题

**口述模板（30–60 秒）**

1. 一句话结论：把 TTFB 拆分为网络往返和各层处理时间。
2. 关键机制：用 Server-Timing 报告服务端耗时，用连接时间估算 RTT，用各层日志分段测量。
3. 对比或注意点：按地区和运营商对比，区分局部的网络问题和全局的服务端问题。
4. 可追问时补充：对比 CDN 缓存命中和未命中的耗时。

**常见追问**

- Server-Timing 有什么安全注意事项？→ 不要暴露内部细节（数据库名、内部服务名）；跨域资源需要 `Timing-Allow-Origin` 才能读取。

## 二、线上问题排查

### Q4. 接口偶发超时，怎么排查？

- **难度**: 高级
- **标签**: 排查

**答案**

**第一步：缩小范围**

- 偶发的比例？集中在某个时间、地区、客户端、服务器实例？
- 超时的时间分布有没有规律？（例如集中在 1 秒、3 秒附近 → SYN 重传；集中在某个固定值 → 某层的超时配置）

**第二步：按层排查**

| 层 | 可能的原因 | 方法 |
|----|------------|------|
| DNS | 解析超时、解析器不稳定 | 客户端上报 DNS 耗时；`dig` 测试 |
| 连接建立 | SYN 丢包、全连接队列溢出、临时端口耗尽 | `netstat -s` 看 overflow；`ss -s`；抓包看 SYN 重传 |
| 连接复用 | **上游已关闭空闲连接，客户端仍然使用** → 偶发的连接重置 | 对比客户端和服务端的 keep-alive 超时；客户端超时应**短于**服务端 |
| 服务端 | GC 停顿、事件循环阻塞、慢查询、锁竞争、下游超时 | 追踪、GC 日志、事件循环延迟指标 |
| 网络 | 丢包、某条链路拥塞 | `mtr`、抓包看重传 |
| 负载均衡 | 某个实例异常但健康检查通过 | 按实例统计错误率 |

**第三步：抓包验证**

```bash
tcpdump -i any host 10.0.0.5 and port 8080 -w capture.pcap
```

用 Wireshark 查看：重传、零窗口、RST、握手耗时、请求和响应的时间差。

**常见根因**：

- Keep-Alive 超时不匹配（Node.js 服务的 `keepAliveTimeout` 默认 5 秒，而 ALB 等负载均衡的空闲超时默认 60 秒 → 负载均衡使用一个已被 Node 关闭的连接 → 502）
- 连接池耗尽，请求排队
- 下游的长尾延迟

**口述模板（30–60 秒）**

1. 一句话结论：先按时间、地区、实例缩小范围，再按 DNS、连接、复用、服务端、网络逐层排查。
2. 关键机制：超时集中在 1 秒、3 秒附近通常是 SYN 重传；固定值通常是某层的超时配置。
3. 对比或注意点：常见的根因是 keep-alive 超时不匹配，上游比下游先关闭连接。
4. 可追问时补充：最终用抓包看重传、RST 和各阶段耗时来验证。

**常见追问**

- Node.js 服务在负载均衡后面，偶发 502 怎么修？→ 设置 `server.keepAliveTimeout` 大于负载均衡的空闲超时（例如 65 秒），并且 `headersTimeout` 大于 `keepAliveTimeout`。

### Q5. 怎么分析一个抓包文件？

- **难度**: 高级
- **标签**: 抓包, 排查

**答案**

**Wireshark 常用过滤器**：

```text
tcp.port == 443
tcp.flags.syn == 1 && tcp.flags.ack == 0        # SYN 包
tcp.analysis.retransmission                     # 重传
tcp.analysis.zero_window                        # 零窗口
tcp.flags.reset == 1                            # RST
http.request || http.response
tls.handshake.type == 1                         # Client Hello
```

**分析步骤**：

1. **Statistics → Conversations**：找到相关的连接
2. **Follow TCP Stream**：查看完整的交互
3. **时间列设置为「与上一个包的时间差」**：找到等待时间长的地方 —— 是谁在等谁？
   - 客户端发出请求后，服务端很久才回复 → 服务端慢
   - 服务端回复了，但很多重传 → 网络问题
4. **Expert Information**：自动标记的异常（重传、乱序、重复 ACK）
5. **TCP Stream Graphs**：吞吐、窗口大小、RTT 的变化

**HTTPS 抓包解密**：设置环境变量 `SSLKEYLOGFILE`（浏览器、Node.js 支持），在 Wireshark 中导入密钥日志。

**QUIC**：大部分头部加密，使用 qlog（端点输出的日志）配合 qvis 分析。

**口述模板（30–60 秒）**

1. 一句话结论：先过滤出相关的连接，再看时间差找到等待的环节。
2. 关键机制：重点关注重传、零窗口、RST 和握手耗时。
3. 对比或注意点：判断是请求后服务端迟迟不响应，还是响应在网络中反复重传。
4. 可追问时补充：HTTPS 用 SSLKEYLOGFILE 解密，QUIC 用 qlog 分析。

**常见追问**

- 看到大量 RST 可能是什么原因？→ 连接到未监听的端口、对端进程崩溃、负载均衡或防火墙超时后清理了连接、应用设置了 `SO_LINGER` 为 0 主动重置。

### Q6. 服务器要支持几十万甚至百万的长连接，有哪些网络层面的挑战？

- **难度**: 高级
- **标签**: 高并发, 长连接

**答案**

| 挑战 | 处理 |
|------|------|
| **I/O 模型** | 事件驱动（epoll / kqueue / io_uring），不能每个连接一个线程；Node.js、Go、Netty 都基于此 |
| **文件描述符** | `ulimit -n`、`fs.file-max`、`fs.nr_open` 调大 |
| **内存** | 每个连接的内核缓冲区（`tcp_rmem` / `tcp_wmem`）和应用缓冲区；百万连接 × 几十 KB = 数十 GB → 减小默认缓冲区，按需增长 |
| **临时端口**（作为客户端，例如压测机） | 多个源 IP |
| **心跳风暴** | 百万连接每 30 秒心跳 = 每秒 3 万多条；时间轮管理定时器，打散心跳时间 |
| **重连风暴** | 服务重启或网络恢复时所有客户端同时重连 → 客户端随机退避；服务端限制建连速率 |
| **负载均衡** | L4 负载均衡的连接跟踪表容量；长连接不均衡 |
| **发布** | 重启会断开所有连接 → 优雅下线（通知客户端迁移、逐步断开）、分批发布 |
| **conntrack** | 防火墙的连接跟踪表满会丢包（`nf_conntrack_max`），高并发场景可以对特定端口关闭跟踪 |

**口述模板（30–60 秒）**

1. 一句话结论：百万长连接需要事件驱动的 I/O、调大文件描述符、控制每个连接的内存。
2. 关键机制：每个连接的内核缓冲区乘以连接数是内存的主要消耗。
3. 对比或注意点：心跳风暴和重连风暴需要打散和退避。
4. 可追问时补充：发布时需要优雅下线，避免所有连接同时断开。

**常见追问**

- 怎么让重启时连接平滑迁移？→ 新实例先启动；旧实例停止接受新连接，向客户端发送「请重连」消息，分批断开；客户端随机延迟后重连到新实例。

### Q7. MTU、MSS 和分片是什么？PMTU 黑洞是怎么回事？

- **难度**: 高级
- **标签**: 网络层

**答案**

- **MTU**：链路层能传输的最大数据包（以太网 1500 字节）
- **MSS**：TCP 段的最大负载 = MTU - IP 头（20）- TCP 头（20）= 1460 字节；握手时双方协商
- **分片**：IP 包大于下一跳的 MTU 时需要分片；分片降低性能，任一分片丢失则整个包重传

**PMTUD（路径 MTU 发现）**：

- 发送设置了「不分片」（DF）标志的包，路径上 MTU 更小的路由器丢弃并返回 ICMP「需要分片」消息，发送方减小包的大小

**PMTU 黑洞**：

- 某些防火墙**屏蔽了所有 ICMP**，发送方收不到「需要分片」的消息
- 现象：**握手成功（包小），传输大数据时卡住**（大包被静默丢弃）
- 常见于 VPN、隧道（额外的封装头部减小了有效 MTU）

**解决**：

- 允许 ICMP 类型 3 代码 4（需要分片）
- 在隧道入口 **MSS 钳制**（修改 SYN 中的 MSS）
- 使用 PLPMTUD（不依赖 ICMP 的探测）
- QUIC：规定最小 1200 字节，自己探测路径 MTU

**口述模板（30–60 秒）**

1. 一句话结论：MTU 是链路的最大包大小，MSS 是 TCP 负载的最大值，超过 MTU 需要分片。
2. 关键机制：PMTUD 依赖 ICMP 消息发现路径上最小的 MTU。
3. 对比或注意点：ICMP 被屏蔽时形成黑洞，表现为握手成功但大数据传输卡住。
4. 可追问时补充：隧道入口做 MSS 钳制是常见的解决方案。

**常见追问**

- 「小请求正常，大响应卡住」除了 MTU 还可能是什么？→ 中间设备的缓冲或检测问题、窗口缩放被中间设备破坏、代理的大小限制。

## 三、协议设计取舍

### Q8. QUIC 为什么基于 UDP，而不是改进 TCP 或设计新的传输层协议？

- **难度**: 高级
- **标签**: QUIC, 协议设计

**答案**

**为什么不改进 TCP**：

- TCP 在**操作系统内核**中实现，更新依赖操作系统升级，客户端设备（尤其是移动设备）升级周期很长
- **中间设备僵化**：防火墙、NAT、负载均衡对 TCP 头部做了假设，新的选项和行为会被丢弃或修改（TFO 的失败就是例子）
- 某些问题是 TCP 设计固有的（字节流有序导致队头阻塞、四元组标识连接）

**为什么不设计新的传输层协议**（例如 SCTP）：

- 中间设备只放行 TCP 和 UDP，新协议无法穿越 NAT 和防火墙

**基于 UDP 的好处**：

- UDP 几乎可以穿越所有网络
- 在**用户态**实现，随应用更新（Chrome 每几周更新一次）
- **加密几乎所有头部**，防止中间设备僵化（中间设备看不到也就无法依赖）

**代价**：

- 用户态处理的 CPU 开销
- 部分网络限制 UDP
- 每个应用自带实现，碎片化

**口述模板（30–60 秒）**

1. 一句话结论：TCP 在内核中、被中间设备僵化，很难演进；新的传输层协议无法穿越 NAT 和防火墙。
2. 关键机制：基于 UDP 可以穿越网络，在用户态实现可以随应用快速更新。
3. 对比或注意点：加密几乎所有头部，防止再次被中间设备僵化。
4. 可追问时补充：代价是 CPU 开销和部分网络对 UDP 的限制。

**常见追问**

- 为什么要加密传输层的头部？→ 防止中间设备根据头部做假设（僵化），保护隐私；只暴露必要的连接 ID 等信息。

### Q9. HTTP/3 一定比 HTTP/2 快吗？

- **难度**: 高级
- **标签**: HTTP/3, 性能

**答案**

**不一定**。

**HTTP/3 有优势的场景**：

- 高丢包（移动网络、跨国）：没有 TCP 队头阻塞
- 高 RTT：握手更少
- 网络切换：连接迁移
- 大量短连接的首次访问（配合 HTTPS 记录）

**HTTP/3 可能更慢的场景**：

- 低延迟低丢包的网络（数据中心内部、优质宽带）：差异很小
- **UDP 被限速或阻断**：回退到 TCP 需要时间
- **CPU 受限**的设备：用户态加密和处理的开销
- 高带宽下的吞吐：内核 TCP 有大量优化（TSO、GRO、零拷贝），QUIC 在追赶（UDP GSO / GRO）
- 中间设备对 UDP 的处理不佳

**结论**：在面向公网用户的场景（尤其移动端），HTTP/3 通常对**尾部延迟**（P95 / P99）改善更明显；需要通过 A/B 测试和真实用户监控确认。

**口述模板（30–60 秒）**

1. 一句话结论：不一定，HTTP/3 在高丢包、高延迟、网络切换的场景中优势明显。
2. 关键机制：没有 TCP 队头阻塞、握手更少、支持连接迁移。
3. 对比或注意点：在优质网络中差异小；UDP 受限或 CPU 受限时可能更慢。
4. 可追问时补充：改善主要体现在尾部延迟，需要用真实用户数据验证。

**常见追问**

- 数据中心内部的服务间通信要用 HTTP/3 吗？→ 通常不需要，内部网络丢包低、延迟低，HTTP/2（gRPC）已经足够，且 TCP 的内核优化更成熟。

### Q10. 什么是 Happy Eyeballs？

- **难度**: 高级
- **标签**: IPv6, 连接

**答案**

**问题**：双栈环境中，如果 IPv6 路径不通，先尝试 IPv6 的客户端要等待超时（可能几十秒）才回退到 IPv4。

**Happy Eyeballs v2（RFC 8305）**：

1. 同时发起 AAAA 和 A 查询（AAAA 结果稍等一下）
2. 优先尝试 IPv6 连接
3. 如果 **250ms** 内没有成功，**并行**尝试 IPv4
4. 使用先成功的连接，取消其他尝试

**扩展**：浏览器对 HTTP/3 和 TCP 也采用类似的竞速策略。

**Node.js**：18 起支持 `autoSelectFamily`（20 中默认开启），实现了类似的算法。早期 Node.js 版本中「localhost 解析到 `::1` 但服务只监听 IPv4」导致的连接失败问题也与此相关。

**口述模板（30–60 秒）**

1. 一句话结论：Happy Eyeballs 在双栈环境中并行尝试 IPv6 和 IPv4，使用先成功的连接。
2. 关键机制：优先 IPv6，短时间内未成功就并行尝试 IPv4。
3. 对比或注意点：避免 IPv6 路径不通时长时间等待超时。
4. 可追问时补充：浏览器对 HTTP/3 和 TCP 也采用类似的竞速。

**常见追问**

- Node.js 中 `fetch('http://localhost:3000')` 连接失败，但浏览器正常，可能是什么原因？→ localhost 解析为 `::1`（IPv6），服务只监听 `127.0.0.1`；新版本 Node.js 的 `autoSelectFamily` 缓解了这个问题，也可以让服务同时监听 IPv6。

## 四、基础设施架构

### Q11. 深入讲讲 CDN 的架构和缓存设计

- **难度**: 高级
- **标签**: CDN, 架构

**答案**

**分层架构**：

```text
用户 → 边缘节点（数量多、离用户近、容量小）
     → 中间层 / 区域节点（数量少、容量大）
     → 源站保护层（Origin Shield，单一的回源出口）
     → 源站
```

- 分层降低回源率：多个边缘节点的未命中合并到中间层
- **请求合并**（Request Collapsing）：同一资源的多个并发未命中只回源一次

**缓存键设计**：

- 默认：协议 + 主机 + 路径 + 查询参数
- **忽略无关的查询参数**（`utm_source` 等），否则缓存命中率极低
- 包含必要的请求头（`Accept-Encoding`、设备类型），避免 `Vary: User-Agent`
- **不要**把 Cookie 加入缓存键（除非确实需要）

**失效**：

- 带哈希的文件名（首选）
- 按 URL、前缀、标签（Surrogate-Key / Cache-Tag）清除
- 软失效：标记为过期，后台更新

**边缘计算**：在边缘执行代码（Cloudflare Workers 等）：A/B 测试、个性化、鉴权、图片处理。

**关键指标**：命中率（按请求和按字节）、回源带宽、边缘 TTFB、错误率。

**口述模板（30–60 秒）**

1. 一句话结论：CDN 是边缘、中间层、源站保护层的分层架构，降低回源率。
2. 关键机制：请求合并让并发未命中只回源一次；缓存键要忽略无关参数。
3. 对比或注意点：不要把 Cookie 和 User-Agent 加入缓存键。
4. 可追问时补充：失效优先用带哈希的文件名，其次用标签清除。

**常见追问**

- 发布新版本后部分用户看到旧页面、新 JS 导致报错，怎么办？→ HTML 短缓存或 no-cache；静态资源带哈希长期缓存且保留旧版本；发布顺序是先上传静态资源，再更新 HTML。

### Q12. 设计一个 API 网关需要考虑哪些网络层面的问题？

- **难度**: 高级
- **标签**: 网关, 架构

**答案**

| 方面 | 要点 |
|------|------|
| **连接管理** | 客户端连接和上游连接分离；上游连接池复用；HTTP/2 到上游（多路复用） |
| **超时** | 连接超时、读取超时、总超时；按路由配置；**超时预算**沿调用链传递（剩余时间） |
| **重试** | 只重试幂等请求或连接失败（请求未发出）；**重试预算**（重试流量不超过总流量的一定比例），防止重试风暴 |
| **熔断** | 上游错误率高时快速失败，定期探测恢复 |
| **限流** | 令牌桶 / 滑动窗口；按用户、IP、API；分布式限流（Redis） |
| **负载均衡** | P2C、最少请求；健康检查（主动 + 被动） |
| **请求体** | 大小限制；流式转发（不缓冲整个请求体）|
| **头部** | 清理和设置 `X-Forwarded-*`；移除内部头部；请求 ID |
| **TLS** | 终止 TLS；上游 mTLS |
| **安全** | WAF、**HTTP 请求走私**防护（统一解析） |
| **可观测** | 每个请求的上游耗时、状态码、重试次数 |

**口述模板（30–60 秒）**

1. 一句话结论：网关的核心是连接管理、超时、重试、熔断、限流和负载均衡。
2. 关键机制：上游使用连接池，超时预算沿调用链传递。
3. 对比或注意点：重试只针对幂等请求，并设置重试预算，防止重试风暴。
4. 可追问时补充：清理转发头部，统一请求解析防止请求走私。

**常见追问**

- 为什么要有重试预算？→ 上游过载时，每层都重试 3 次会造成指数级的流量放大（3 层就是 27 倍），把上游彻底压垮。

### Q13. 什么是 HTTP 请求走私？

- **难度**: 高级
- **标签**: 安全, HTTP

**答案**

**原理**：前端代理和后端服务器对**请求边界**的解析不一致，攻击者在一个请求中「藏」入另一个请求。

**经典场景**（HTTP/1.1）：请求同时包含 `Content-Length` 和 `Transfer-Encoding: chunked`：

- 前端按 `Content-Length` 解析，认为是一个请求
- 后端按 `Transfer-Encoding` 解析，认为第一个请求提前结束，剩余部分是**下一个请求的开头**
- 这个「走私」的请求会和下一个用户的请求拼接 → 绕过前端的安全控制、窃取其他用户的请求、缓存投毒

**HTTP/2 降级走私**：前端使用 HTTP/2，转发给后端时降级为 HTTP/1.1，如果没有正确校验头部（例如 HTTP/2 中注入的 `Content-Length`、头部中的换行），也会产生走私。

**防御**：

- 前后端使用相同的 HTTP 解析实现，或者后端使用 HTTP/2
- 拒绝同时包含 `Content-Length` 和 `Transfer-Encoding` 的请求，拒绝格式不正确的头部
- 不复用前端到后端的连接（性能代价大）
- 及时升级代理和服务器

**口述模板（30–60 秒）**

1. 一句话结论：请求走私利用前端代理和后端对请求边界的解析不一致，把一个请求藏入另一个请求中。
2. 关键机制：经典方式是同时使用 Content-Length 和 Transfer-Encoding，前后端各按一个解析。
3. 对比或注意点：HTTP/2 降级为 HTTP/1.1 时也可能产生走私。
4. 可追问时补充：防御是统一解析、拒绝有歧义的请求、及时升级。

**常见追问**

- 为什么请求走私危害大？→ 走私的请求会影响**其他用户**的请求（拼接、响应错位），可以绕过只在前端实施的访问控制。

### Q14. gRPC 基于 HTTP/2 带来了什么？在前端怎么使用？

- **难度**: 高级
- **标签**: gRPC, HTTP/2

**答案**

**gRPC 利用了 HTTP/2 的能力**：

- 多路复用：一个连接上并发大量调用
- 流：支持服务端流、客户端流、双向流
- 头部压缩
- **Trailers**：在响应正文之后发送状态码（`grpc-status`）

**Protobuf**：二进制序列化，体积小、解析快、强类型。

**前端的限制**：

- 浏览器的 fetch 无法控制 HTTP/2 帧，**无法读取 Trailers** → 不能直接使用 gRPC
- **gRPC-Web**：修改协议，把 Trailers 编码在正文中，需要代理（Envoy）转换；只支持服务端流
- **Connect 协议**：同时支持 gRPC、gRPC-Web 和简单的 HTTP POST + JSON，浏览器直接使用

**负载均衡的坑**：gRPC 使用长连接，L4 负载均衡只在建立连接时分配 → 所有请求落到同一个后端；需要 **L7 负载均衡**（按请求分配）或客户端负载均衡。

**口述模板（30–60 秒）**

1. 一句话结论：gRPC 利用 HTTP/2 的多路复用、流和 Trailers，配合 Protobuf 实现高效的 RPC。
2. 关键机制：状态码在 Trailers 中，所以浏览器无法直接使用。
3. 对比或注意点：前端使用 gRPC-Web 或 Connect 协议。
4. 可追问时补充：长连接下 L4 负载均衡会不均衡，需要 L7 或客户端负载均衡。

**常见追问**

- 微服务之间为什么常用 gRPC 而不是 REST？→ 性能（二进制、多路复用）、强类型的接口定义（代码生成）、流式支持。

## 五、长连接与实时系统

### Q15. 设计一个百万级长连接的推送系统，网络层面怎么设计？

- **难度**: 高级
- **标签**: 长连接, 架构

**答案**

```text
客户端
  → DNS / HTTPDNS（就近接入、按负载调度）
  → L4 负载均衡（TCP 透传或 TLS 终止）
  → 接入层（网关集群：维护连接、心跳、鉴权；无业务逻辑）
       ↕ 路由表（用户 ID → 接入节点），存储在 Redis
  → 消息层（消息队列：Kafka 等）
  → 业务服务
```

**关键设计**：

- **接入层无状态化**：连接信息（用户在哪个节点）存在共享存储中；接入层只负责收发
- **消息投递**：业务服务 → 查路由表 → 发送到对应的接入节点（或通过消息队列按节点分区）
- **可靠性**：消息序号 + 客户端确认 + 离线消息存储 + 重连后增量同步（客户端带上最后的序号）
- **心跳**：客户端发起，自适应间隔（根据 NAT 超时探测）；服务端用时间轮检测超时
- **重连**：指数退避 + 随机抖动；服务端发布时分批迁移
- **协议**：WebSocket（浏览器）或自定义二进制协议（App）；压缩；合并小消息
- **多区域**：就近接入，跨区域通过消息层路由

**容量估算**：单机连接数（受内存限制，几十万）、消息吞吐（扇出：一条群消息 × 群成员数）。

**口述模板（30–60 秒）**

1. 一句话结论：分为接入层、路由层、消息层，接入层只维护连接，不处理业务。
2. 关键机制：用户和接入节点的映射存储在 Redis，业务消息通过路由投递到对应的节点。
3. 对比或注意点：可靠性靠消息序号、客户端确认、离线存储和重连后的增量同步。
4. 可追问时补充：心跳自适应、重连退避、发布时分批迁移连接。

**常见追问**

- 大群（例如 10 万人）的消息怎么推送？→ 扇出放大严重；按接入节点聚合（每个节点只收一份消息，由节点扇出给本地的连接）；非活跃成员只发送通知，打开时拉取。

### Q16. ECH（加密 Client Hello）是什么？对网络运维有什么影响？

- **难度**: 高级
- **标签**: TLS, 隐私

**答案**

**问题**：TLS 1.3 加密了证书，但 Client Hello 中的 **SNI**（要访问的域名）仍然是明文，中间设备可以知道用户访问了哪个网站。

**ECH**：

- 客户端从 DNS（HTTPS 记录）获取服务端的 ECH 公钥
- Client Hello 分为**外层**（明文，SNI 是公共名称，例如 CDN 的通用域名）和**内层**（加密，包含真实的 SNI 和其他敏感扩展）
- 只有持有私钥的服务端（通常是 CDN）能解密内层

**部署**：Chrome、Firefox 已支持；Cloudflare 等 CDN 部署；仍在 IETF 标准化流程中（以官方为准）。

**影响**：

- **隐私**：网络观察者只能看到连接到了某个 CDN，不知道具体网站
- **企业网络**：基于 SNI 的过滤、审计、分流失效 → 企业需要通过端点代理或禁用 ECH（浏览器策略）
- **依赖 DoH**：如果 DNS 查询是明文的，域名仍然泄露

**口述模板（30–60 秒）**

1. 一句话结论：ECH 加密 Client Hello 中的 SNI，让网络观察者无法知道访问的具体域名。
2. 关键机制：客户端从 HTTPS 记录获取公钥，加密内层的 Client Hello。
3. 对比或注意点：需要配合 DoH，否则 DNS 查询仍然泄露域名。
4. 可追问时补充：企业基于 SNI 的过滤和审计会失效。

**常见追问**

- 为什么 ECH 主要在 CDN 上部署？→ 外层 SNI 需要一个「匿名集合」，CDN 上有大量网站共享同一个公共名称，单个网站部署 ECH 的隐私收益很小。

## 六、网络安全

### Q17. DDoS 攻击有哪些类型？怎么防护？

- **难度**: 高级
- **标签**: 安全, DDoS

**答案**

| 类型 | 层 | 例子 | 防护 |
|------|----|------|------|
| **容量型** | L3 / L4 | UDP 洪泛、**反射放大**（DNS、NTP、Memcached：小请求 → 大响应，伪造源地址为受害者） | 带宽和 Anycast 分散、上游清洗、BCP 38（源地址验证） |
| **协议型** | L4 | SYN 洪泛、ACK 洪泛 | SYN Cookies、连接限制 |
| **应用层** | L7 | HTTP 洪泛、慢速攻击（Slowloris：缓慢发送头部，占用连接）、**HTTP/2 Rapid Reset** | WAF、限流、人机验证、超时控制、缓存 |

**防护架构**：

```text
Anycast 分散流量 → 边缘清洗（丢弃明显的攻击流量）→ CDN / WAF（L7 规则、限流、人机验证）
→ 源站（只允许 CDN 的 IP 访问，隐藏源站 IP）
```

**关键点**：

- **隐藏源站 IP**：源站只接受来自 CDN 的流量；历史 DNS 记录、邮件头、子域名可能泄露源站 IP
- 应用层：缓存尽可能多的内容，昂贵的接口（搜索、登录）单独限流
- 预案：攻击时开启更严格的模式（人机验证、地区封禁）

**口述模板（30–60 秒）**

1. 一句话结论：DDoS 分为容量型、协议型和应用层攻击。
2. 关键机制：容量型靠 Anycast 和清洗，协议型靠 SYN Cookies，应用层靠 WAF 和限流。
3. 对比或注意点：要隐藏源站 IP，只允许 CDN 访问。
4. 可追问时补充：反射放大攻击利用伪造源地址，小请求换大响应。

**常见追问**

- 为什么 QUIC 要限制服务端在地址验证前的发送量？→ 防止被用作反射放大攻击的工具（规定在验证客户端地址前，响应不能超过收到数据的 3 倍）。

### Q18. 中间人攻击有哪些形式？证书固定还推荐吗？

- **难度**: 高级
- **标签**: 安全, TLS

**答案**

**中间人攻击的形式**：

- ARP 欺骗、恶意 Wi-Fi 热点
- DNS 劫持
- SSL 剥离（把 HTTPS 降级为 HTTP）→ HSTS 防护
- 用户安装了恶意根证书（或公司代理的根证书）
- CA 误签或被入侵 → 证书透明度可以发现

**证书固定（Certificate Pinning）**：客户端只信任特定的证书或公钥。

| 场景 | 建议 |
|------|------|
| 浏览器（HPKP） | **已被废弃**：配置错误会导致网站长期无法访问（「自杀」），还可以被攻击者利用（勒索固定） |
| 移动 App | 仍有使用，但要谨慎：固定**公钥**（而不是证书）、固定**中间 CA** 而不是叶子证书、准备备份公钥、支持远程更新 |

**替代方案**：证书透明度监控 + CAA 记录 + 短有效期证书。

**口述模板（30–60 秒）**

1. 一句话结论：中间人攻击包括 ARP 欺骗、DNS 劫持、SSL 剥离、恶意根证书和 CA 误签。
2. 关键机制：HSTS 防止降级，证书透明度发现误签。
3. 对比或注意点：浏览器的证书固定已被废弃，风险大于收益。
4. 可追问时补充：App 中使用时固定公钥和备份公钥，并支持远程更新。

**常见追问**

- App 做了证书固定，证书更换时怎么办？→ 固定公钥并提前在 App 中放入新的公钥（备份），新版本发布一段时间后再更换证书；或者固定中间 CA 的公钥。

### Q19. 怎么管理大量的 TLS 证书？证书有效期缩短会带来什么影响？

- **难度**: 高级
- **标签**: 证书, 运维

**答案**

**有效期缩短的时间表**（CA/B 论坛 SC-081，以官方为准）：

- 2026-03-15 起最长 200 天
- 2027-03-15 起最长 100 天
- 2029-03-15 起最长 47 天
- 域名验证结果的复用时间也同步缩短

**影响**：**手动续期不再可行**，任何遗漏都会导致故障（证书过期是常见的线上事故）。

**证书管理方案**：

- **ACME 协议自动化**：Let's Encrypt、ZeroSSL 等；Kubernetes 使用 cert-manager；CDN 和负载均衡的托管证书
- **证书清单**：通过证书透明度日志发现所有为自己域名签发的证书
- **监控**：证书到期提前告警（30 天、7 天）、从外部探测证书链是否完整
- **私钥管理**：存储在 KMS / HSM 中，最小权限
- **内部服务**：内部 CA（服务网格自动签发短期证书，mTLS）

**口述模板（30–60 秒）**

1. 一句话结论：证书有效期正在逐步缩短到 47 天，必须自动化续期。
2. 关键机制：使用 ACME 协议自动申请和续期，Kubernetes 中使用 cert-manager。
3. 对比或注意点：需要证书清单和到期监控，防止遗漏。
4. 可追问时补充：私钥存储在 KMS 中，内部服务使用服务网格的短期证书。

**常见追问**

- 为什么要缩短有效期？→ 减少私钥泄露或误签证书的有效时间窗口；吊销机制不可靠，短有效期是更有效的「吊销」；推动自动化。

## 七、移动与多地域

### Q20. 移动网络有哪些特点？对前端有什么影响？

- **难度**: 高级
- **标签**: 移动网络

**答案**

| 特点 | 影响 | 应对 |
|------|------|------|
| **高且波动的延迟** | 往返次数影响大 | 减少往返、HTTP/3 |
| **无线电状态切换**（空闲 → 激活需要时间，4G 约几十到上百毫秒，3G 更长） | 首个请求有额外的延迟；频繁的小请求让无线电保持激活，耗电 | **批量发送**请求（埋点合并）、避免定时轮询 |
| 网络切换（Wi-Fi ↔ 蜂窝） | TCP 连接断开 | QUIC 连接迁移、重连机制 |
| 运营商 DNS 劫持、运营商级 NAT | 解析错误、IP 共享 | HTTPDNS、HTTPS、限流不完全依赖 IP |
| 带宽和流量费用 | 用户在意流量 | 压缩、图片按网络降级、尊重 `Save-Data` |
| 信号弱、丢包 | 吞吐下降、超时 | BBR、合理的超时和重试 |

**口述模板（30–60 秒）**

1. 一句话结论：移动网络的特点是延迟高且波动、无线电状态切换、网络切换频繁。
2. 关键机制：无线电从空闲到激活需要时间，频繁的小请求耗电。
3. 对比或注意点：批量发送请求，避免定时轮询。
4. 可追问时补充：QUIC 连接迁移解决网络切换问题，HTTPDNS 解决 DNS 劫持。

**常见追问**

- 埋点上报怎么做对移动网络友好？→ 本地缓存批量上报、使用 `sendBeacon` 在页面隐藏时发送、压缩、失败重试、限制队列大小。

### Q21. 多地域部署时，网络层面要考虑什么？

- **难度**: 高级
- **标签**: 多地域, 架构

**答案**

**流量调度**：

- GSLB / Anycast 把用户调度到最近的区域
- 故障时把流量切换到其他区域（需要容量冗余）
- 按用户归属调度（数据在哪个区域，用户就去哪个区域，避免跨区域访问数据）

**跨区域延迟**：

- 跨国 RTT 100–300ms：同步调用链中**每一次跨区域调用都会叠加延迟**
- 尽量让一个请求在一个区域内完成；跨区域只做异步复制

**数据一致性**：

- 单元化架构：按用户分片，每个单元处理自己的用户
- 跨区域复制的延迟导致「写后读」问题 → 写入后的读取路由到主区域，或者使用会话一致性

**合规**：数据驻留要求（个人信息不能出境），影响路由和存储。

**网络连接**：区域之间使用专线或云厂商的骨干网，比公网更稳定。

**口述模板（30–60 秒）**

1. 一句话结论：多地域部署要考虑流量调度、跨区域延迟、数据一致性和合规。
2. 关键机制：用 GSLB 或 Anycast 就近调度，按用户归属路由到数据所在的区域。
3. 对比或注意点：一个请求尽量在一个区域内完成，跨区域只做异步复制。
4. 可追问时补充：数据驻留的合规要求会影响路由设计。

**常见追问**

- 区域故障切换后，用户数据还在故障区域怎么办？→ 依赖异步复制的数据（可能有少量延迟）；切换时可能需要只读模式，或者接受一定的数据丢失窗口（RPO）。

### Q22. 服务网格（Service Mesh）在网络层面做了什么？

- **难度**: 高级
- **标签**: 服务网格

**答案**

**边车代理**（Envoy 等）拦截服务的所有进出流量，提供：

- **mTLS**：服务之间的双向认证和加密，证书自动签发和轮换（零信任）
- **流量管理**：负载均衡、重试、超时、熔断、灰度（按头部、比例路由）
- **可观测**：每个调用的指标、追踪、访问日志，不需要修改应用代码
- **策略**：服务之间的访问控制

**代价**：

- 每次调用多两跳代理，增加延迟（通常毫秒以下）和资源消耗
- 运维复杂度
- **Ambient 模式**（Istio）：节点级的代理处理 L4（mTLS），按需部署 L7 代理，减少边车的开销

**口述模板（30–60 秒）**

1. 一句话结论：服务网格通过边车代理接管服务之间的流量，提供 mTLS、流量管理和可观测性。
2. 关键机制：应用代码不需要修改，代理负责加密、重试、熔断和指标收集。
3. 对比或注意点：代价是额外的延迟、资源消耗和运维复杂度。
4. 可追问时补充：Ambient 模式减少了边车的开销。

**常见追问**

- 应用和服务网格都配置了重试，会怎样？→ 重试次数相乘，造成流量放大；应该只在一处配置重试。

## 八、综合

### Q23. 一个前端页面在某个地区的运营商网络下访问很慢，怎么定位和解决？

- **难度**: 高级
- **标签**: 排查, CDN

**答案**

**定位**：

1. **真实用户监控**数据：按地区和运营商分组，确认影响范围；看哪个阶段慢（DNS、连接、TLS、TTFB、下载）
2. **拨测**：在该地区和运营商的节点进行测试（第三方拨测平台）
3. **DNS**：该运营商的 DNS 解析到了哪个 CDN 节点？是否被调度到了远处（跨运营商、跨地区）？
4. **路由**：`mtr` 查看路径，是否绕路、在哪一跳丢包
5. **CDN 节点**：该节点的命中率、负载

**常见原因和解决**：

| 原因 | 解决 |
|------|------|
| CDN 调度错误（用户被调度到其他运营商的节点，跨网访问） | 联系 CDN 调整调度；使用多家 CDN 按地区分配 |
| 运营商 DNS 问题（使用了公共 DNS，ECS 缺失导致调度不准） | HTTPDNS（App）、调整 CDN 的调度策略 |
| 跨运营商互联拥塞 | 在该运营商部署节点、BGP 多线机房 |
| 该地区节点容量不足 | 扩容或调度到邻近节点 |
| 源站跨网回源慢 | 回源走专线、源站保护层 |

**口述模板（30–60 秒）**

1. 一句话结论：先用真实用户监控确认范围和慢的阶段，再用拨测和 mtr 定位。
2. 关键机制：重点检查 DNS 调度到了哪个节点，是否跨运营商访问。
3. 对比或注意点：国内跨运营商的网络质量差异大，是常见的原因。
4. 可追问时补充：解决方式包括调整 CDN 调度、多 CDN、BGP 多线机房、HTTPDNS。

**常见追问**

- 多 CDN 怎么做？→ 通过智能 DNS 按地区、运营商分配到不同的 CDN，并根据实时的质量数据动态调整；注意缓存失效要同时作用于所有 CDN。

### Q24. 设计一个前端网络请求层，需要考虑哪些问题？

- **难度**: 高级
- **标签**: 前端架构

**答案**

| 方面 | 设计 |
|------|------|
| **超时** | 每个请求都有超时（`AbortSignal.timeout`）；按接口类型配置 |
| **取消** | 组件卸载、路由切换、新的搜索时取消旧请求（AbortController） |
| **重试** | 只重试幂等请求和网络错误 / 5xx / 429；指数退避 + 抖动；遵守 `Retry-After` |
| **去重** | 相同的并发 GET 请求合并为一个 |
| **竞态** | 只使用最后一次请求的结果 |
| **并发控制** | 限制同时进行的请求数，关键请求优先 |
| **缓存** | 内存缓存 + stale-while-revalidate（TanStack Query / SWR） |
| **认证** | 令牌过期时**单飞刷新**（多个请求同时 401 时只刷新一次，其他请求等待） |
| **幂等键** | 非幂等的提交带上 `Idempotency-Key`，安全重试 |
| **错误分类** | 网络错误、超时、业务错误、认证错误，分别处理 |
| **监控** | 上报耗时、错误率、重试次数，带请求 ID |
| **离线** | 检测网络状态，离线时排队，恢复后发送 |

**口述模板（30–60 秒）**

1. 一句话结论：请求层要统一处理超时、取消、重试、去重、竞态、并发、缓存和认证。
2. 关键机制：重试只针对幂等请求，使用退避和抖动；令牌刷新要单飞。
3. 对比或注意点：非幂等的提交使用幂等键，才能安全重试。
4. 可追问时补充：统一的错误分类和监控，带请求 ID 便于排查。

**常见追问**

- 多个请求同时返回 401，怎么只刷新一次令牌？→ 用一个共享的 Promise：第一个请求发起刷新，其他请求等待同一个 Promise，刷新完成后重放各自的请求。

### Q25. 什么时候应该考虑修改服务器的 TCP 参数？有哪些常用参数？

- **难度**: 高级
- **标签**: TCP, 调优

**答案**

**原则**：**先测量后调优**；默认值适合大多数场景；只在明确的问题出现时修改，并在修改前后对比。

| 参数 | 作用 | 场景 |
|------|------|------|
| `net.core.somaxconn`、`tcp_max_syn_backlog` | 队列大小 | 突发连接多、队列溢出 |
| `tcp_tw_reuse` | 作为客户端复用 TIME_WAIT 端口 | 大量短连接到下游 |
| `ip_local_port_range` | 临时端口范围 | 同上 |
| `tcp_congestion_control` | 拥塞控制算法（bbr） | 长距离、有丢包的网络 |
| `tcp_rmem` / `tcp_wmem` | 缓冲区大小 | 高带宽时延积 / 大量连接（减小） |
| `tcp_keepalive_time` | Keepalive 空闲时间 | 清理死连接 |
| `tcp_fin_timeout` | FIN_WAIT_2 超时 | 大量 FIN_WAIT_2 |
| `tcp_slow_start_after_idle` | 空闲后是否重新慢启动 | 长连接间歇传输（设为 0） |
| `fs.file-max`、`ulimit -n` | 文件描述符 | 高并发 |

**容器环境**：部分参数是网络命名空间级别的，需要在 Pod 的 `sysctls` 中设置。

**口述模板（30–60 秒）**

1. 一句话结论：先测量后调优，只在出现明确问题时修改 TCP 参数。
2. 关键机制：常用的有队列大小、TIME_WAIT 复用、临时端口范围、拥塞控制算法、缓冲区大小。
3. 对比或注意点：修改前后要对比，避免照搬网上的「优化配置」。
4. 可追问时补充：容器中部分参数需要在 Pod 级别设置。

**常见追问**

- `tcp_slow_start_after_idle` 为什么对长连接有影响？→ 默认开启时，连接空闲一段时间后拥塞窗口会重置，HTTP/2 长连接在间歇请求时会重新慢启动。

### Q26. 网络领域有哪些值得关注的趋势？

- **难度**: 高级
- **标签**: 趋势

**答案**

（截至 2026-10，以官方为准）

- **HTTP/3 和 QUIC 普及**：更多 CDN 和服务器支持；QUIC 用于更多场景（MASQUE 代理、Media over QUIC）
- **后量子密码**：密钥交换已大规模部署，**后量子证书**和签名是下一步
- **隐私增强**：ECH、DoH、Oblivious HTTP（隐藏客户端 IP）、iCloud Private Relay 类服务
- **证书有效期缩短**：自动化成为必需
- **WebTransport 和 WebCodecs**：浏览器中的低延迟实时传输
- **压缩字典传输**：增量更新
- **BBR 等新拥塞控制**的普及
- **边缘计算**：更多逻辑在 CDN 边缘执行
- **零信任网络**：服务之间的 mTLS、基于身份而不是网络位置的访问控制

**口述模板（30–60 秒）**

1. 一句话结论：趋势是 QUIC 普及、后量子密码、隐私增强、证书自动化和边缘计算。
2. 关键机制：后量子密钥交换已大规模部署，证书是下一步。
3. 对比或注意点：隐私增强（ECH、DoH）改变了传统的网络监控和过滤方式。
4. 可追问时补充：浏览器中的 WebTransport 等让更多实时场景成为可能。

**常见追问**

- 这些趋势对前端工程师有什么影响？→ 部署时开启 HTTP/3 和 HTTPS 记录、证书自动化、压缩字典传输带来的增量更新、实时场景的新选择（WebTransport）。
