## 一、TCP 深入

### Q1. 什么是 SYN 洪泛攻击？半连接队列和全连接队列是什么？

- **难度**: 中级
- **标签**: TCP, 安全

**答案**

**两个队列**（Linux）：

```text
客户端 SYN → 服务端放入「半连接队列」（SYN_RCVD）→ 回复 SYN+ACK
客户端 ACK → 从半连接队列移出，放入「全连接队列」（ESTABLISHED，等待 accept）
应用调用 accept() → 从全连接队列取出
```

| 队列 | 大小控制 | 满了会怎样 |
|------|----------|------------|
| 半连接队列 | `tcp_max_syn_backlog` | 丢弃新的 SYN（启用 SYN Cookies 时除外） |
| 全连接队列 | `min(backlog, somaxconn)` | 默认丢弃 ACK（客户端以为连接已建立，发送数据后超时） |

**SYN 洪泛**：攻击者发送大量伪造源地址的 SYN，不完成握手，占满半连接队列，正常用户无法建立连接。

**防御**：

- **SYN Cookies**：不在队列中保存状态，把连接信息编码在 SYN+ACK 的序号中，收到 ACK 时验证
- 增大半连接队列、减少 SYN+ACK 重试次数
- 上游的 DDoS 防护（清洗）

**全连接队列溢出**的排查：`ss -lnt` 查看 `Recv-Q`（当前队列长度）和 `Send-Q`（队列上限）；`netstat -s | grep overflow`。原因通常是应用处理太慢（accept 不及时）。

**口述模板（30–60 秒）**

1. 一句话结论：服务端有半连接队列和全连接队列，SYN 洪泛通过大量不完成的握手占满半连接队列。
2. 关键机制：SYN Cookies 把状态编码在序号中，不占用队列。
3. 对比或注意点：全连接队列满通常是应用 accept 太慢。
4. 可追问时补充：用 ss -lnt 查看队列长度和上限。

**常见追问**

- Node.js 中 `server.listen` 的 backlog 默认是多少？→ 默认 511，实际还受系统 `somaxconn` 的限制。

### Q2. 服务器上大量 TIME_WAIT 怎么处理？

- **难度**: 中级
- **标签**: TCP, 排查

**答案**

**原因**：服务端**主动关闭**了大量短连接。常见场景：

- HTTP 短连接（服务端在响应后关闭）
- 服务作为**客户端**频繁调用下游服务（没有使用连接池）—— 这种情况更常见，并且会耗尽**临时端口**

**影响**：

- 每个 TIME_WAIT 占用少量内存，通常不是大问题
- 真正的问题：作为客户端时，**临时端口被 TIME_WAIT 占用**，无法建立新连接到同一个目标

**处理**：

| 方法 | 说明 |
|------|------|
| **连接复用**（首选） | HTTP Keep-Alive、连接池（Node.js `http.Agent({ keepAlive: true })`） |
| 让客户端主动关闭 | 服务端不主动关闭，TIME_WAIT 出现在客户端 |
| `tcp_tw_reuse = 1` | 允许作为客户端时复用 TIME_WAIT 的端口（依赖时间戳，安全） |
| 扩大临时端口范围 | `ip_local_port_range` |
| ~~`tcp_tw_recycle`~~ | **已在 Linux 4.12 中移除**，在 NAT 环境下会导致连接失败 |

**口述模板（30–60 秒）**

1. 一句话结论：大量 TIME_WAIT 是因为主动关闭了大量短连接，首选方案是连接复用。
2. 关键机制：TIME_WAIT 本身占用资源少，问题在于作为客户端时临时端口被耗尽。
3. 对比或注意点：可以开启 tcp_tw_reuse，不要使用已被移除的 tcp_tw_recycle。
4. 可追问时补充：常见的根因是服务调用下游时没有使用连接池。

**常见追问**

- 为什么不能直接把 TIME_WAIT 时间改短？→ Linux 中 TIME_WAIT 时间固定为 60 秒（硬编码）；而且缩短会失去 TIME_WAIT 的保护作用。

### Q3. 服务器上大量 CLOSE_WAIT 是什么原因？

- **难度**: 中级
- **标签**: TCP, 排查

**答案**

**CLOSE_WAIT**：对方已经发送了 FIN，本方回复了 ACK，但**本方应用还没有调用 close()**。

**大量 CLOSE_WAIT 几乎总是应用的 bug**：

- 连接没有关闭（异常分支中忘记释放、资源泄漏）
- 连接池中的连接被对方关闭后，没有被检测和清除
- 应用线程或事件循环阻塞，来不及处理关闭事件

**影响**：文件描述符泄漏，最终达到上限（`EMFILE: too many open files`），服务无法接受新连接。

**排查**：

```bash
ss -tanp state close-wait          # 查看是哪个进程、连接到哪里
lsof -p <pid> | wc -l              # 文件描述符数量
```

然后在代码中查找对应的连接（数据库、HTTP 客户端、Redis），检查是否在所有分支中都释放了连接。

**口述模板（30–60 秒）**

1. 一句话结论：CLOSE_WAIT 表示对方已关闭，但本方应用没有调用 close，几乎都是应用的 bug。
2. 关键机制：通常是异常分支中没有释放连接，或连接池没有清理被关闭的连接。
3. 对比或注意点：TIME_WAIT 是正常现象，CLOSE_WAIT 堆积是问题。
4. 可追问时补充：用 ss 找到进程和对端地址，再定位代码。

**常见追问**

- 和 TIME_WAIT 的区别？→ TIME_WAIT 出现在主动关闭方，是协议设计的正常状态，会自动消失；CLOSE_WAIT 出现在被动关闭方，不会自动消失，需要应用关闭。

### Q4. 滑动窗口是怎么工作的？什么是零窗口？

- **难度**: 中级
- **标签**: TCP, 流量控制

**答案**

**发送窗口**：

```text
| 已发送且已确认 | 已发送未确认 | 可以发送 | 不能发送 |
                 ↑                       ↑
              窗口左边界              窗口右边界
收到 ACK → 左边界右移；接收方通告更大的窗口 → 右边界右移
```

- 窗口内的数据可以连续发送，不必等每个确认（提高吞吐）
- 窗口大小 = min(接收方通告的窗口, 拥塞窗口)

**窗口缩放**：TCP 头的窗口字段只有 16 位（最大 64KB），通过窗口缩放选项（握手时协商）扩展到最大 1GB，适应高带宽高延迟的网络。

**零窗口**：接收方缓冲区满（应用读取太慢），通告窗口为 0，发送方停止发送并定期发送**窗口探测**，直到窗口打开。

**带宽时延积（BDP）**：带宽 × RTT，表示「管道中」可以容纳的数据量；窗口小于 BDP 时无法跑满带宽。

**口述模板（30–60 秒）**

1. 一句话结论：滑动窗口允许发送方在未收到确认前连续发送一个窗口的数据。
2. 关键机制：收到确认后窗口右移；窗口大小由接收窗口和拥塞窗口共同决定。
3. 对比或注意点：接收方缓冲区满时通告零窗口，发送方定期探测。
4. 可追问时补充：窗口要大于带宽时延积才能跑满带宽，窗口缩放选项用于扩展窗口。

**常见追问**

- 跨国传输大文件速度很慢可能是什么原因？→ 高 RTT 下窗口不够大（缓冲区配置、窗口缩放未启用），或者丢包导致拥塞窗口收缩。

### Q5. 拥塞控制的经典算法过程是怎样的？

- **难度**: 中级
- **标签**: TCP, 拥塞控制

**答案**

**Reno 的四个阶段**：

```text
cwnd
 │          丢包（3 个重复 ACK）
 │         ╱╲ → ssthresh = cwnd/2, cwnd = ssthresh（快速恢复）
 │    ╱╱╱╱   ╲╱╱╱╱
 │   ╱ 拥塞避免（线性增长）
 │  ╱
 │ ╱ 慢启动（指数增长），到达 ssthresh 后进入拥塞避免
 │╱
 └──────────────────────────── 时间
 超时：ssthresh = cwnd/2, cwnd = 1 → 重新慢启动（更严重的拥塞信号）
```

| 阶段 | 行为 |
|------|------|
| 慢启动 | 每个 RTT cwnd 翻倍 |
| 拥塞避免 | 每个 RTT cwnd 加 1 个 MSS |
| 快速重传 + 快速恢复 | 3 个重复 ACK：cwnd 减半，继续拥塞避免 |
| 超时 | cwnd 回到初始值，重新慢启动 |

**Cubic**（Linux 默认，RFC 9438）：

- cwnd 的增长是**时间**的三次函数，而不是每个 RTT 加 1
- 丢包后快速增长到之前的最大值附近，然后缓慢探测，再加速增长
- 不依赖 RTT，在高带宽长距离网络中表现更好，对不同 RTT 的流更公平

**基于丢包的算法的问题**：只有发生丢包时才知道拥塞，会**填满路由器的缓冲区**（缓冲区膨胀，导致高延迟）；在有随机丢包的无线网络中误判为拥塞。

**口述模板（30–60 秒）**

1. 一句话结论：经典算法包括慢启动、拥塞避免、快速重传和快速恢复。
2. 关键机制：慢启动指数增长，拥塞避免线性增长，丢包时根据信号严重程度减半或重置。
3. 对比或注意点：Cubic 是 Linux 默认算法，增长与时间相关，适合高带宽长距离网络。
4. 可追问时补充：基于丢包的算法会填满缓冲区，在无线网络中会误判。

**常见追问**

- 为什么超时比 3 个重复 ACK 更严重？→ 能收到重复 ACK 说明后续数据还能到达，网络只是轻度拥塞；超时说明可能什么都到不了。

### Q6. BBR 是什么？和 Cubic 有什么区别？

- **难度**: 中级
- **标签**: TCP, 拥塞控制

**答案**

**BBR**（Google 提出）：**基于模型**的拥塞控制，不以丢包作为拥塞信号，而是持续测量：

- **瓶颈带宽**（BtlBw）：一段时间内的最大传输速率
- **最小往返时间**（RTprop）：一段时间内的最小 RTT

目标是以 `BtlBw` 的速率发送，且在途数据量约等于 `BtlBw × RTprop`（带宽时延积），这样既跑满带宽又不填满缓冲区。

| 对比项 | Cubic | BBR |
|--------|-------|-----|
| 拥塞信号 | 丢包 | 带宽和 RTT 的测量 |
| 缓冲区 | 会填满（高延迟） | 尽量保持空（低延迟） |
| 随机丢包的网络 | 误判，吞吐下降明显 | 吞吐受影响小 |
| 公平性 | 同类之间较公平 | BBR v1 与 Cubic 共存时可能不公平；v2 / v3 改进 |

**部署**：Google 服务、YouTube 大规模使用；Linux 中可以通过 `net.ipv4.tcp_congestion_control = bbr` 启用；QUIC 实现中也常用 BBR。

**口述模板（30–60 秒）**

1. 一句话结论：BBR 基于测量的瓶颈带宽和最小 RTT 控制发送速率，而不是等丢包。
2. 关键机制：以瓶颈带宽发送，在途数据量保持在带宽时延积附近。
3. 对比或注意点：在有随机丢包的网络中吞吐更高，延迟更低。
4. 可追问时补充：早期版本与 Cubic 共存时公平性有问题，后续版本在改进。

**常见追问**

- 什么场景适合启用 BBR？→ 长距离、高带宽、有随机丢包的网络（跨国传输、移动网络、视频服务）。

### Q7. Nagle 算法和延迟确认是什么？为什么会导致延迟？

- **难度**: 中级
- **标签**: TCP

**答案**

**Nagle 算法**（发送方）：如果有未确认的数据，就把小数据包攒起来，等收到 ACK 或攒够一个 MSS 再发送，减少小包数量。

**延迟确认**（接收方）：收到数据后不立即回复 ACK，等待一段时间（最长约 40–200ms），希望和响应数据一起发送。

**两者叠加的问题**：

```text
发送方：发送请求的第一部分 → 等待 ACK 才发送第二部分（Nagle）
接收方：收到第一部分 → 等待更多数据或超时才回复 ACK（延迟确认）
→ 双方互相等待，直到延迟确认超时（几十毫秒）
```

**解决**：交互式应用（RPC、游戏、数据库客户端）设置 `TCP_NODELAY` 禁用 Nagle。Node.js 中 `socket.setNoDelay(true)`，`http` 模块的连接默认已启用 noDelay。

**口述模板（30–60 秒）**

1. 一句话结论：Nagle 算法攒小包发送，延迟确认推迟 ACK，两者叠加会导致几十毫秒的延迟。
2. 关键机制：发送方等 ACK，接收方等数据，互相等待直到超时。
3. 对比或注意点：交互式应用设置 TCP_NODELAY 禁用 Nagle。
4. 可追问时补充：Node.js 的 http 默认已启用 noDelay。

**常见追问**

- 有了 TCP_NODELAY，会不会产生大量小包？→ 应用层应该自己合并写入（例如一次写入完整的消息），而不是依赖 Nagle。

### Q8. TCP Keepalive 和应用层心跳有什么区别？

- **难度**: 中级
- **标签**: TCP, 长连接

**答案**

| 对比项 | TCP Keepalive | 应用层心跳 |
|--------|---------------|------------|
| 层级 | 内核 | 应用 |
| 默认 | 关闭；开启后默认空闲 **2 小时**才开始探测 | 应用自己定义（通常 15–60 秒） |
| 检测能力 | 只能检测对端主机或连接是否存活 | 能检测**应用**是否正常（进程卡死时 TCP 仍然存活） |
| 穿越代理 | 只到下一跳（代理会回复） | 端到端 |
| 用途 | 清理死连接 | 保活（防止 NAT 和代理清除）+ 检测 + 携带业务数据 |

**为什么长连接需要应用层心跳**：

- NAT、防火墙、负载均衡的空闲超时通常是几十秒到几分钟，远小于 2 小时
- 对端进程卡死时 TCP 层仍然正常
- 移动网络中断时可能不会收到 FIN 或 RST，连接「半开」

**口述模板（30–60 秒）**

1. 一句话结论：TCP Keepalive 是内核的探活机制，应用层心跳由应用实现，能检测应用是否正常。
2. 关键机制：TCP Keepalive 默认 2 小时才探测，太长。
3. 对比或注意点：NAT 和代理的空闲超时远小于 2 小时，长连接需要应用层心跳保活。
4. 可追问时补充：应用层心跳是端到端的，能穿越代理，还能检测进程卡死。

**常见追问**

- 心跳间隔怎么选？→ 小于路径上最短的空闲超时（通常 30 秒以内）；移动端要考虑耗电，可以根据网络类型动态调整。

### Q9. TCP Fast Open 是什么？为什么没有普及？

- **难度**: 中级
- **标签**: TCP

**答案**

**TFO**：在 SYN 中携带数据，节省 1 个 RTT。

```text
第一次连接：客户端请求 TFO Cookie，服务端在 SYN+ACK 中返回
后续连接：SYN + Cookie + 数据 → 服务端验证 Cookie 后立即处理数据
```

**没有普及的原因**：

- **中间设备**（防火墙、NAT）丢弃带数据的 SYN 或不认识的 TCP 选项（协议僵化）
- 需要操作系统、应用、中间网络的共同支持
- SYN 中的数据可能被重放，应用需要保证幂等
- 浏览器（Chrome）实验后放弃

**启示**：TCP 在内核和中间设备中实现，**很难演进** —— 这正是 QUIC 选择在 UDP 之上、在用户态实现的原因。

**口述模板（30–60 秒）**

1. 一句话结论：TFO 在 SYN 中携带数据，通过 Cookie 验证，节省一个往返。
2. 关键机制：首次连接获取 Cookie，后续连接在 SYN 中携带 Cookie 和数据。
3. 对比或注意点：中间设备的兼容性问题和重放风险导致它没有普及。
4. 可追问时补充：TCP 的协议僵化是 QUIC 在用户态实现的重要原因。

**常见追问**

- 什么是协议僵化？→ 中间设备根据当前协议的实际行为做了假设（例如只允许已知的 TCP 选项），导致协议的新特性无法部署。

### Q10. TCP 的重传超时（RTO）是怎么计算的？

- **难度**: 中级
- **标签**: TCP

**答案**

```text
SRTT   = (1 - α) × SRTT + α × RTT样本            α = 1/8（平滑的 RTT）
RTTVAR = (1 - β) × RTTVAR + β × |SRTT - RTT样本|  β = 1/4（RTT 的波动）
RTO    = SRTT + 4 × RTTVAR                       （最小值 Linux 约 200ms）
```

- 每次超时重传后，RTO **翻倍**（指数退避）
- 重传的数据包的 RTT 不用于计算（无法区分是对原始包还是重传包的确认，Karn 算法）；时间戳选项可以解决
- **尾部丢包**：最后几个包丢失时没有后续数据触发重复 ACK，只能等超时 → **TLP（尾部丢失探测）**、**RACK**（基于时间的丢包检测）改善

**口述模板（30–60 秒）**

1. 一句话结论：RTO 根据平滑的 RTT 加上 4 倍的 RTT 波动计算。
2. 关键机制：每次超时重传后 RTO 翻倍。
3. 对比或注意点：重传包的 RTT 不参与计算。
4. 可追问时补充：尾部丢包只能等超时，TLP 和 RACK 用于更快地检测。

**常见追问**

- 为什么偶发的接口超时经常是 1 秒、3 秒左右？→ 握手阶段的 SYN 重传初始超时是 1 秒，之后指数退避（1、2、4 秒…），所以丢失 SYN 会造成秒级的延迟。

## 二、HTTP/2 与 HTTP/3

### Q11. HTTP/1.1 有哪些性能问题？以前的优化手段在 HTTP/2 中还需要吗？

- **难度**: 中级
- **标签**: HTTP

**答案**

**HTTP/1.1 的问题**：

- **队头阻塞**：一个连接同一时间只能处理一个请求
- 并发受限：每个域名 6 个连接
- 头部冗余：每个请求重复发送 Cookie、User-Agent 等，文本格式
- 每个连接都要握手和慢启动

**HTTP/1.1 时代的优化在 HTTP/2 中**：

| 优化 | HTTP/2 中 |
|------|-----------|
| 域名分片（多个域名增加并发） | **有害**：多个连接无法共享压缩上下文和拥塞窗口，增加 DNS 和握手 |
| 雪碧图、资源内联 | 不再必要，影响缓存粒度 |
| 合并文件 | 适度合并仍然有益（压缩率、请求开销），但不需要合并成一个巨大的文件 |
| Cookie-free 域名 | HPACK 压缩后收益变小 |

**口述模板（30–60 秒）**

1. 一句话结论：HTTP/1.1 的问题是队头阻塞、并发受限、头部冗余。
2. 关键机制：以前通过域名分片、雪碧图、合并文件来绕过这些限制。
3. 对比或注意点：HTTP/2 中域名分片有害，雪碧图和内联不再必要。
4. 可追问时补充：适度的打包仍然有益，但粒度要考虑缓存。

**常见追问**

- HTTP/2 中如果多个域名解析到同一个 IP，且证书覆盖这些域名，会怎样？→ 浏览器可以**连接合并**，复用同一个连接。

### Q12. HTTP/2 的帧、流和 HPACK 是怎么工作的？

- **难度**: 中级
- **标签**: HTTP/2

**答案**

**帧**：最小单位，9 字节帧头（长度、类型、标志、流 ID）+ 负载。

| 帧类型 | 作用 |
|--------|------|
| HEADERS | 头部 |
| DATA | 正文 |
| SETTINGS | 连接参数（最大并发流数、初始窗口） |
| WINDOW_UPDATE | 流量控制 |
| RST_STREAM | 取消单个流 |
| PING | 心跳、测量 RTT |
| GOAWAY | 优雅关闭连接 |

**流**：一个请求-响应对应一个流（客户端发起的流 ID 为奇数）；多个流的帧在一个连接中**交错传输**。

**流量控制**：连接级和流级两层窗口，防止某个流占满带宽。

**HPACK 头部压缩**：

- **静态表**：61 个常用的头部（`:method: GET` 等），用索引表示
- **动态表**：本连接中出现过的头部，后续用索引引用
- **哈夫曼编码**：压缩字符串

**安全事件**：**HTTP/2 Rapid Reset**（CVE-2023-44487）—— 攻击者快速创建并立即取消（RST_STREAM）大量流，绕过并发流限制，造成破纪录的 DDoS；服务器需要限制流的重置频率。

**口述模板（30–60 秒）**

1. 一句话结论：HTTP/2 把报文拆成二进制帧，每个请求是一个流，多个流的帧在一个连接中交错传输。
2. 关键机制：HPACK 用静态表、动态表和哈夫曼编码压缩头部。
3. 对比或注意点：有连接级和流级两层流量控制。
4. 可追问时补充：Rapid Reset 利用快速取消流发动 DDoS，需要限制重置频率。

**常见追问**

- HPACK 为什么不用 gzip 压缩头部？→ 压缩加上攻击者可以控制的内容会导致 CRIME 攻击（通过压缩后的长度推测密钥），HPACK 的设计避免了这一点。

### Q13. HTTP/2 Server Push 为什么被废弃？用什么替代？

- **难度**: 中级
- **标签**: HTTP/2, 性能

**答案**

**Server Push**：服务端在客户端请求之前主动推送资源（例如请求 HTML 时推送 CSS）。

**被废弃的原因**：

- **不知道客户端是否已经缓存**：推送已缓存的资源浪费带宽
- 推送的资源和其他请求竞争带宽，可能拖慢更重要的资源
- 实现复杂，实际收益很小甚至为负
- Chrome 106 移除，其他浏览器也逐步移除；HTTP/3 中几乎没有实现

**替代方案**：

| 方案 | 说明 |
|------|------|
| **103 Early Hints** | 服务端在生成最终响应之前，先发送 `103` 状态码和 `Link: </style.css>; rel=preload` 头部，浏览器开始预加载（浏览器知道自己的缓存） |
| `<link rel="preload">` | 在 HTML 中声明 |
| `preconnect` | 提前建立连接 |

**103 Early Hints 的价值**：服务端思考时间（查询数据库、渲染）期间，浏览器已经开始下载关键资源。CDN 可以缓存 Early Hints 并在回源期间发送。

**口述模板（30–60 秒）**

1. 一句话结论：Server Push 因为不知道客户端缓存、与关键资源竞争带宽而被废弃。
2. 关键机制：替代方案是 103 Early Hints，服务端在最终响应之前发送预加载提示。
3. 对比或注意点：由浏览器决定是否加载，浏览器知道自己的缓存。
4. 可追问时补充：利用服务端的思考时间提前下载关键资源。

**常见追问**

- 103 Early Hints 有什么限制？→ 只能用于导航请求；浏览器只处理 `preload` 和 `preconnect`；中间代理需要支持转发 1xx 响应。

### Q14. QUIC 是怎么建立连接的？0-RTT 是什么？

- **难度**: 中级
- **标签**: QUIC, HTTP/3

**答案**

**QUIC 把传输层握手和 TLS 1.3 握手合并**：

```text
TCP + TLS 1.3：TCP 握手 1 RTT + TLS 握手 1 RTT = 2 RTT 后才能发送请求
QUIC：          首次连接 1 RTT（同时完成传输层和加密握手）
QUIC 0-RTT：    恢复连接时，第一个数据包就携带加密的请求数据
```

**0-RTT 的前提**：客户端之前连接过该服务器，保存了会话票据（PSK）。

**0-RTT 的风险：重放攻击**：

- 攻击者可以截获并重放 0-RTT 数据，服务器无法区分
- 所以 **0-RTT 只能用于幂等请求**（GET），非幂等请求（POST）不应该使用
- 服务端可以通过单次使用的票据、时间窗口限制重放；CDN 通常只对安全的方法启用

**QUIC 的其他特性**：

- **连接 ID**：连接由 ID 标识，而不是四元组 → **连接迁移**（Wi-Fi 切换到 4G 不断开）
- **几乎所有内容都加密**（包括大部分头部），减少中间设备的干扰
- 在**用户态**实现，可以快速迭代

**口述模板（30–60 秒）**

1. 一句话结论：QUIC 合并了传输层和 TLS 握手，首次连接 1 RTT，恢复连接可以 0-RTT。
2. 关键机制：0-RTT 使用之前保存的会话票据，第一个包就携带请求数据。
3. 对比或注意点：0-RTT 数据可以被重放，只能用于幂等请求。
4. 可追问时补充：连接由 ID 标识，网络切换时连接可以迁移。

**常见追问**

- TLS 1.3 over TCP 也有 0-RTT，和 QUIC 的有什么区别？→ TCP 仍然需要 1 RTT 的握手（除非使用 TFO），所以 TCP + TLS 1.3 0-RTT 实际是 1 RTT；QUIC 0-RTT 是真正的 0 RTT。

### Q15. QUIC 是怎么解决队头阻塞的？它的丢包恢复有什么改进？

- **难度**: 中级
- **标签**: QUIC

**答案**

**HTTP/2 over TCP 的队头阻塞**：TCP 保证整个字节流有序，一个包丢失时，后面所有流的数据都要等这个包重传后才能交给应用。

**QUIC**：

- **每个流独立有序**：流 A 的包丢失只阻塞流 A，流 B 的数据可以继续交给应用
- 有序性只在流内部保证

**丢包恢复的改进**：

| 对比项 | TCP | QUIC |
|--------|-----|------|
| 序号 | 字节序号，重传使用相同的序号 → 无法区分原始包和重传包的确认（重传歧义） | **数据包编号单调递增**，重传使用新编号 → RTT 测量准确 |
| 确认 | SACK 最多 3–4 个块 | ACK 帧支持大量范围 |
| 确认延迟 | 不知道接收方延迟了多久 | ACK 帧中包含**确认延迟**，RTT 计算更准确 |
| 拥塞控制 | 内核实现，升级困难 | 用户态实现，可以按应用选择算法（Cubic、BBR） |

**口述模板（30–60 秒）**

1. 一句话结论：QUIC 中每个流独立有序，一个流丢包不阻塞其他流。
2. 关键机制：数据包编号单调递增，重传使用新编号，消除了重传歧义。
3. 对比或注意点：ACK 帧包含确认延迟和大量范围，RTT 测量和丢包检测更准确。
4. 可追问时补充：拥塞控制在用户态实现，可以快速迭代。

**常见追问**

- QUIC 是不是完全没有队头阻塞？→ 流内部仍然有序（同一个流的丢包仍然阻塞这个流）；QPACK 的动态表更新也可能造成跨流的阻塞，QPACK 通过设计减少了这种情况。

### Q16. 浏览器是怎么发现并使用 HTTP/3 的？部署 HTTP/3 有哪些问题？

- **难度**: 中级
- **标签**: HTTP/3, 部署

**答案**

**发现方式**：

1. **Alt-Svc 头部**：首次通过 HTTP/1.1 或 HTTP/2 访问，响应中包含 `Alt-Svc: h3=":443"; ma=86400`，后续请求尝试 HTTP/3
2. **HTTPS DNS 记录**（RFC 9460）：DNS 查询时就知道支持 `h3`，首次访问就可以直接使用 HTTP/3
3. 浏览器通常**同时**尝试 QUIC 和 TCP（竞速），QUIC 失败时使用 TCP

**部署问题**：

- **UDP 被阻断或限速**：部分企业网络、运营商限制 UDP 443 → 必须保留 TCP 回退
- **CPU 开销**：用户态加密和处理，早期比 TCP 高（UDP GSO、硬件卸载在改善）
- **负载均衡**：需要根据连接 ID 路由（连接迁移后四元组变化），L4 负载均衡需要支持 QUIC
- **可观测性**：头部加密，传统的网络监控工具看不到细节；使用 qlog 等工具
- **防火墙和 DDoS 防护**：UDP 放大攻击的防护（QUIC 的地址验证机制限制了放大倍数）

**口述模板（30–60 秒）**

1. 一句话结论：浏览器通过 Alt-Svc 头部或 HTTPS DNS 记录发现 HTTP/3 支持。
2. 关键机制：浏览器同时尝试 QUIC 和 TCP，QUIC 失败时回退。
3. 对比或注意点：部分网络限制 UDP，必须保留 TCP。
4. 可追问时补充：部署难点包括 CPU 开销、负载均衡按连接 ID 路由、可观测性。

**常见追问**

- 为什么首次访问通常不是 HTTP/3？→ 没有 HTTPS 记录时，浏览器要先通过 TCP 访问得到 Alt-Svc 后才知道支持 HTTP/3。

## 三、HTTP 细节

### Q17. HTTP 压缩有哪些方式？怎么选择？

- **难度**: 中级
- **标签**: HTTP, 性能

**答案**

| 算法 | 特点 | 适用 |
|------|------|------|
| gzip | 兼容性最好，速度和压缩率中等 | 兜底 |
| **Brotli（br）** | 静态压缩率比 gzip 高 15–25%，最高级别压缩很慢 | 静态资源**预压缩**（最高级别）、动态内容（中低级别） |
| **Zstandard（zstd）** | 压缩速度快、压缩率高 | 动态内容；Chrome 123、Firefox 126 起支持，Safari 支持较晚（以官方为准） |
| 压缩字典传输 | 使用之前的版本作为字典，只传输差异（增量更新） | 频繁更新的 JS 包；Chrome 已支持（`dcb` / `dcz`），标准化中 |

**协商**：请求头 `Accept-Encoding: gzip, deflate, br, zstd` → 响应头 `Content-Encoding: br` + `Vary: Accept-Encoding`

**实践**：

- 构建时对静态资源预压缩（br 最高级别 + gzip），服务器直接返回
- 动态内容使用较快的级别（br 4–6 或 zstd）
- 图片、视频、字体（woff2）已经压缩，**不要再压缩**
- 小于 1KB 的响应压缩意义不大

**口述模板（30–60 秒）**

1. 一句话结论：常用 gzip、Brotli、Zstandard，通过 Accept-Encoding 协商。
2. 关键机制：静态资源预压缩使用最高级别的 Brotli，动态内容使用较快的级别。
3. 对比或注意点：已经压缩的格式不要再压缩，响应要带 Vary。
4. 可追问时补充：压缩字典传输可以只传输版本之间的差异。

**常见追问**

- 为什么 HTTPS 中压缩敏感数据有风险？→ BREACH 攻击：如果响应同时包含密钥（CSRF 令牌）和攻击者可控的内容，可以通过观察压缩后的长度推测密钥；缓解措施是对令牌随机掩码。

### Q18. Range 请求和断点续传是怎么实现的？

- **难度**: 中级
- **标签**: HTTP

**答案**

```http
GET /video.mp4 HTTP/1.1
Range: bytes=1000000-1999999
If-Range: "etag-abc"

HTTP/1.1 206 Partial Content
Content-Range: bytes 1000000-1999999/52428800
Content-Length: 1000000
Accept-Ranges: bytes
```

- 服务端通过 `Accept-Ranges: bytes` 声明支持
- `If-Range`：文件未修改时返回部分内容，已修改时返回完整文件（200），**防止拼接出损坏的文件**
- 范围无效时返回 `416 Range Not Satisfiable`
- 多个范围：`multipart/byteranges`

**应用**：

- 断点续传下载
- 视频拖动进度条
- 大文件并行分段下载
- PDF 按页加载

**口述模板（30–60 秒）**

1. 一句话结论：客户端通过 Range 头请求部分内容，服务端返回 206 和 Content-Range。
2. 关键机制：If-Range 确保文件没有变化，否则返回完整文件。
3. 对比或注意点：范围无效时返回 416。
4. 可追问时补充：用于断点续传、视频拖动、并行下载。

**常见追问**

- 上传的断点续传怎么做？→ HTTP 没有标准的上传 Range，通常是分片上传（每片独立请求 + 服务端记录已完成的分片），或使用 tus 等协议。

### Q19. 共享缓存（CDN、代理）相关的缓存指令有哪些？

- **难度**: 中级
- **标签**: HTTP, 缓存, CDN

**答案**

| 指令 | 作用 |
|------|------|
| `public` / `private` | 是否允许共享缓存存储；**包含用户数据的响应必须是 private** |
| `s-maxage` | 只对共享缓存有效，覆盖 `max-age` |
| `stale-while-revalidate=60` | 过期后 60 秒内可以先返回旧内容，后台重新验证 |
| `stale-if-error=86400` | 源站出错时可以返回过期的内容（提高可用性） |
| `no-cache` | 每次使用前验证 |
| `no-store` | 不存储 |
| `must-revalidate` | 过期后必须验证，不能返回旧内容 |
| `immutable` | 有效期内不会变化，刷新时也不验证 |
| `CDN-Cache-Control` / `Surrogate-Control` | 只给 CDN 看的缓存头（不同 CDN 支持不同） |

**`Vary`**：告诉缓存哪些请求头会影响响应，缓存键要包含这些头。

- `Vary: Accept-Encoding`：正确
- `Vary: User-Agent`：值太多，缓存几乎无法命中
- `Vary: Cookie`：同上，通常意味着这个响应不应该被共享缓存

**常见事故**：包含用户信息的页面被 CDN 缓存，其他用户看到了别人的数据 → 默认对动态内容设置 `private` 或 `no-store`。

**口述模板（30–60 秒）**

1. 一句话结论：共享缓存的关键指令是 public/private、s-maxage、stale-while-revalidate、stale-if-error。
2. 关键机制：s-maxage 只对 CDN 等共享缓存生效；stale 系列指令提高性能和可用性。
3. 对比或注意点：包含用户数据的响应必须是 private，否则可能泄露给其他用户。
4. 可追问时补充：Vary 决定缓存键，值太多的头会让缓存无法命中。

**常见追问**

- 什么是 Web 缓存欺骗？→ 攻击者诱导用户访问 `/account/profile.css`，服务器忽略后缀返回用户页面，CDN 按 `.css` 后缀缓存，攻击者再访问同一 URL 获取用户数据；防御是 CDN 按源站的 Cache-Control 缓存，而不是按扩展名。

## 四、TLS

### Q20. TLS 1.3 握手的过程是什么？和 TLS 1.2 有什么区别？

- **难度**: 中级
- **标签**: TLS

**答案**

**TLS 1.3（1-RTT）**：

```text
客户端                                              服务端
ClientHello
  + 支持的加密套件
  + key_share（客户端的 ECDHE 公钥，猜测服务端支持的曲线）
  + 支持的版本、SNI、ALPN（h2 / http/1.1）
                         ─────────────────────────►
                                                    ServerHello + key_share（服务端公钥）
                                                    → 双方此时已可计算出握手密钥
                                                    {EncryptedExtensions}
                                                    {Certificate}
                                                    {CertificateVerify}（用私钥签名握手记录）
                                                    {Finished}
                         ◄─────────────────────────
{Finished}
[应用数据]               ─────────────────────────►
```

`{}` 表示已加密 —— **证书也是加密传输的**。

| 对比项 | TLS 1.2 | TLS 1.3 |
|--------|---------|---------|
| 握手往返 | 2 RTT | **1 RTT**（恢复时 0-RTT） |
| 密钥交换 | 支持 RSA 密钥交换（无前向安全） | **只支持 (EC)DHE**，强制前向安全 |
| 加密算法 | 包括 CBC、RC4 等有问题的算法 | 只保留 AEAD（AES-GCM、ChaCha20-Poly1305） |
| 证书 | 明文传输 | 加密传输 |
| 重新协商 | 支持（曾有漏洞） | 移除 |

**口述模板（30–60 秒）**

1. 一句话结论：TLS 1.3 只需要 1 个往返，客户端在第一条消息中就发送了密钥交换的公钥。
2. 关键机制：服务端回复公钥、证书、签名和 Finished，双方计算出相同的密钥。
3. 对比或注意点：移除了 RSA 密钥交换和不安全的算法，强制前向安全，证书加密传输。
4. 可追问时补充：恢复连接时可以 0-RTT，但有重放风险。

**常见追问**

- 如果客户端猜错了服务端支持的曲线怎么办？→ 服务端回复 HelloRetryRequest，客户端用正确的曲线重新发送，多一个往返。

### Q21. 证书链是怎么验证的？什么是证书透明度？

- **难度**: 中级
- **标签**: TLS, 证书

**答案**

**证书链**：

```text
根证书（预装在操作系统 / 浏览器的信任库中，自签名）
  └─ 中间证书（由根 CA 签名）
       └─ 网站证书（由中间 CA 签名）
```

**验证步骤**：

1. 服务器发送网站证书和中间证书（**不需要发送根证书**；忘记发送中间证书是常见的配置错误，部分客户端会失败）
2. 逐级验证签名，直到信任库中的根证书
3. 检查有效期
4. 检查域名是否匹配（SAN 字段）
5. 检查吊销状态（CRL、OCSP；浏览器更多使用自己维护的吊销列表，如 CRLite；Let's Encrypt 已停止 OCSP 服务，以官方为准）
6. 检查**证书透明度（CT）**：证书是否记录在公开日志中（包含 SCT）

**证书透明度**：所有公开信任的证书都必须记录在公开的、只能追加的日志中 → 域名所有者可以监控是否有人为自己的域名签发了证书（发现误签和恶意签发）。

**证书有效期缩短**：CA/B 论坛决定逐步缩短到 47 天（2029 年），**自动化续期（ACME）**是必需的。

**口述模板（30–60 秒）**

1. 一句话结论：浏览器从网站证书逐级验证签名，直到信任库中的根证书。
2. 关键机制：同时检查有效期、域名、吊销状态和证书透明度。
3. 对比或注意点：服务器要发送中间证书，否则部分客户端验证失败。
4. 可追问时补充：证书透明度让误签可以被发现；证书有效期在缩短，必须自动化续期。

**常见追问**

- 部分安卓设备访问 HTTPS 失败，但浏览器正常，可能是什么原因？→ 缺少中间证书（浏览器会自动补全，应用不会）、旧设备的信任库中没有新的根证书。

### Q22. 什么是前向安全？

- **难度**: 中级
- **标签**: TLS

**答案**

**前向安全（Forward Secrecy）**：即使服务器的**长期私钥**将来泄露，**过去**的通信也无法被解密。

**RSA 密钥交换（无前向安全）**：

```text
客户端生成预主密钥 → 用服务器的 RSA 公钥加密发送
→ 攻击者录下了流量，将来拿到服务器私钥 → 解密预主密钥 → 解密所有历史流量
```

**ECDHE 密钥交换（有前向安全）**：

```text
每次连接双方生成临时的密钥对，交换公钥，计算出共享密钥
连接结束后临时私钥被丢弃
服务器的长期私钥只用于签名（证明身份），不参与密钥计算
→ 私钥泄露也无法恢复过去的会话密钥
```

TLS 1.3 **强制**前向安全。

**「先存储，后解密」**：攻击者现在存储加密流量，等量子计算机成熟后破解 ECDHE → 这就是**后量子密钥交换**（Q25）要解决的问题。

**口述模板（30–60 秒）**

1. 一句话结论：前向安全保证长期私钥泄露后，过去的通信无法被解密。
2. 关键机制：每次连接使用临时密钥对进行 ECDHE 交换，用完即丢弃。
3. 对比或注意点：RSA 密钥交换没有前向安全，TLS 1.3 已移除。
4. 可追问时补充：先存储后解密的威胁推动了后量子密钥交换。

**常见追问**

- 会话恢复（会话票据）会影响前向安全吗？→ 会话票据用服务器的票据密钥加密，票据密钥泄露会影响使用这些票据的会话；所以票据密钥需要频繁轮换。

### Q23. HSTS 是什么？preload 列表有什么作用？

- **难度**: 中级
- **标签**: TLS, 安全

**答案**

**问题**：用户输入 `example.com`，浏览器首先通过 HTTP 访问，再被重定向到 HTTPS —— 第一个 HTTP 请求可以被中间人劫持（SSL 剥离攻击）。

**HSTS**：

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

- 浏览器在 `max-age` 内对该域名**只使用 HTTPS**（自动把 HTTP 转换为 HTTPS）
- 证书错误时**不允许用户忽略**
- `includeSubDomains`：包括所有子域名

**preload 列表**：HSTS 只在第一次访问后生效，第一次访问仍然有风险 → 把域名提交到浏览器内置的 HSTS preload 列表，**首次访问就使用 HTTPS**。

**注意**：

- 加入 preload 列表后**很难撤销**（需要等待浏览器版本更新）
- `includeSubDomains` 前要确认所有子域名都支持 HTTPS（内网系统、旧服务）

**口述模板（30–60 秒）**

1. 一句话结论：HSTS 让浏览器对该域名只使用 HTTPS，防止 SSL 剥离攻击。
2. 关键机制：在 max-age 内自动把 HTTP 转换为 HTTPS，证书错误不能忽略。
3. 对比或注意点：首次访问仍有风险，preload 列表可以解决。
4. 可追问时补充：preload 很难撤销，includeSubDomains 前要确认所有子域名支持 HTTPS。

**常见追问**

- 怎么逐步上线 HSTS？→ 从较短的 max-age（几分钟）开始，确认没有问题后逐步增加，最后再加入 preload。

### Q24. TLS 握手对性能有什么影响？怎么优化？

- **难度**: 中级
- **标签**: TLS, 性能

**答案**

| 优化 | 说明 |
|------|------|
| **TLS 1.3** | 1 RTT 握手 |
| **会话恢复** | 会话票据 / PSK，减少计算；0-RTT（注意重放） |
| **HTTP/3** | 传输和加密握手合并 |
| **ECDSA 证书** | 比 RSA 证书小、签名快 |
| **完整的证书链、不要过长** | 证书链越长，握手数据越多；可能超过初始拥塞窗口，多一个往返 |
| OCSP Stapling | 服务器附带吊销状态，客户端不需要单独查询 |
| **连接复用** | HTTP Keep-Alive、HTTP/2、连接合并，减少握手次数 |
| **边缘终止 TLS** | CDN 在离用户近的节点完成握手，RTT 小 |
| `preconnect` | 提前完成 DNS、TCP、TLS |

**后量子密钥交换的影响**：ML-KEM 的公钥更大（ClientHello 增加约 1KB 以上），可能导致 ClientHello 分成多个包；部分有缺陷的中间设备无法处理（实际部署中遇到过兼容性问题）。

**口述模板（30–60 秒）**

1. 一句话结论：优化 TLS 性能的核心是减少往返和减少握手次数。
2. 关键机制：TLS 1.3、会话恢复、HTTP/3 减少往返；连接复用减少握手次数。
3. 对比或注意点：证书链不要过长，使用 ECDSA 证书。
4. 可追问时补充：CDN 边缘终止 TLS，让握手的 RTT 更小。

**常见追问**

- `preconnect` 可以随便加吗？→ 不能，每个预连接都占用资源，未使用的连接在约 10 秒后被关闭；只对很快会用到的关键第三方域名使用。

### Q25. 什么是后量子 TLS？现在部署到什么程度了？

- **难度**: 中级
- **标签**: TLS, 后量子

**答案**

**威胁**：足够强大的量子计算机可以破解 ECDHE 和 RSA。即使量子计算机还未出现，攻击者可以**现在存储加密流量，将来解密**。

**混合密钥交换 X25519MLKEM768**：

- 同时使用经典的 X25519 和后量子的 **ML-KEM-768**（NIST FIPS 203）
- 两个共享密钥组合在一起：**任一算法未被破解，通信就是安全的**（防止新算法存在未知缺陷）

**部署现状（截至 2026，以官方为准）**：

- Chrome 131、Firefox 132 起默认启用；Apple 在 iOS 26 / macOS Tahoe 中默认启用
- Cloudflare 等 CDN 默认支持，其报告大部分人类流量已使用后量子密钥交换
- 已经形成 RFC 标准

**尚未解决**：

- **身份认证**（证书签名）仍然是经典算法 —— 后量子签名（ML-DSA 等）的证书和公钥很大，对握手大小影响严重，标准和部署仍在推进
- 但认证没有「先存储后破解」的问题（只需要在量子计算机出现之前替换）

**口述模板（30–60 秒）**

1. 一句话结论：后量子 TLS 用混合密钥交换防御「现在存储、将来解密」的威胁。
2. 关键机制：X25519 和 ML-KEM 同时使用，任一算法安全，通信就安全。
3. 对比或注意点：主流浏览器已默认启用，但证书签名仍然是经典算法。
4. 可追问时补充：后量子密钥更大，可能遇到中间设备的兼容性问题。

**常见追问**

- 为什么先做密钥交换，而不是先做签名？→ 密钥交换面临「先存储后解密」的威胁，现在的流量将来可能被破解；签名只需在量子计算机可用前替换即可。

## 五、DNS 深入

### Q26. GSLB 和 DNS 负载均衡是怎么工作的？有什么局限？

- **难度**: 中级
- **标签**: DNS, 负载均衡

**答案**

**GSLB（全局服务器负载均衡）**：权威 DNS 根据请求来源返回不同的 IP：

- 根据**地理位置**返回最近的数据中心
- 根据数据中心的**健康状态**和负载
- 按权重分配流量（灰度、迁移）

**局限**：

| 问题 | 说明 | 缓解 |
|------|------|------|
| 看到的是递归解析器的 IP，不是用户的 IP | 用户使用公共 DNS 时，调度可能不准确 | **EDNS Client Subnet**（ECS）：解析器把用户的子网传给权威服务器 |
| 缓存 | TTL 期间无法改变用户的调度，故障切换慢 | 短 TTL；结合 Anycast |
| 不遵守 TTL 的解析器 | 切换后仍有流量到旧地址 | 旧地址保持服务一段时间 |
| 粒度粗 | 无法按请求级别调度 | 结合 L7 负载均衡 |

**Anycast**：多个数据中心宣告**同一个 IP**，由 BGP 路由把用户的流量送到「最近」的节点；DNS 服务器和 CDN 普遍使用。故障时撤销路由宣告，流量自动转移。

**口述模板（30–60 秒）**

1. 一句话结论：GSLB 让权威 DNS 根据地理位置、健康状态和权重返回不同的 IP。
2. 关键机制：权威 DNS 看到的是解析器的 IP，ECS 可以传递用户的子网。
3. 对比或注意点：受 DNS 缓存影响，故障切换不够快。
4. 可追问时补充：Anycast 用同一个 IP 由路由选择最近的节点，故障转移更快。

**常见追问**

- ECS 有什么隐私问题？→ 把用户的子网信息传给了权威服务器，部分公共 DNS（如 1.1.1.1）出于隐私不发送 ECS。

### Q27. HTTPS / SVCB DNS 记录解决了什么问题？

- **难度**: 中级
- **标签**: DNS, HTTP/3

**答案**

**RFC 9460** 定义的 SVCB 记录和 HTTPS 记录（SVCB 的 HTTP 专用形式），在 DNS 中提供连接参数：

```text
example.com. 300 IN HTTPS 1 . alpn="h3,h2" ipv4hint="192.0.2.1" ech="..."
```

| 参数 | 作用 |
|------|------|
| `alpn` | 支持的协议 → **首次访问就可以使用 HTTP/3**，不需要先通过 TCP 获取 Alt-Svc |
| `ech` | ECH 的公钥配置 → 加密 Client Hello |
| `ipv4hint` / `ipv6hint` | 地址提示，减少额外查询 |
| `port` | 非标准端口 |
| 别名模式（优先级 0） | 根域名的别名，解决根域名不能使用 CNAME 的问题 |

**另一个作用**：浏览器收到 HTTPS 记录时，即使 URL 是 `http://`，也会**升级到 HTTPS**（类似 HSTS）。

**口述模板（30–60 秒）**

1. 一句话结论：HTTPS 记录在 DNS 中提供连接参数，例如支持的协议和 ECH 配置。
2. 关键机制：浏览器首次访问就知道支持 HTTP/3，不需要先通过 TCP 获取 Alt-Svc。
3. 对比或注意点：别名模式解决了根域名不能使用 CNAME 的问题。
4. 可追问时补充：ECH 的公钥通过 HTTPS 记录分发。

**常见追问**

- 为什么 ECH 配置要放在 DNS 中？→ 客户端需要在发送 Client Hello 之前就拿到服务器的公钥来加密；DNS 查询（配合 DoH）是唯一合适的渠道。

### Q28. DNSSEC 和 DoH / DoT 分别解决什么问题？

- **难度**: 中级
- **标签**: DNS, 安全

**答案**

| 对比项 | DNSSEC | DoH / DoT |
|--------|--------|-----------|
| 解决的问题 | **记录的真实性**（防篡改、防缓存投毒） | **传输的隐私和完整性**（防窃听、防篡改） |
| 保护的范围 | 从权威服务器到验证者的整个链条 | 客户端到递归解析器这一段 |
| 加密 | 否（签名但不加密） | 是 |
| 部署 | 需要域名所有者签名、解析器验证；普及率有限 | 浏览器和系统普遍支持 |

**DNS 缓存投毒**（Kaminsky 攻击）：攻击者伪造响应，抢在真实响应之前到达递归解析器，污染缓存。缓解：随机化源端口和查询 ID、DNSSEC。

**DoH 的争议**：

- 隐私更好，但企业网络和家长控制依赖 DNS 进行过滤，DoH 绕过了这些控制
- 集中到少数大型 DoH 提供商

**口述模板（30–60 秒）**

1. 一句话结论：DNSSEC 保证记录的真实性，DoH 和 DoT 保护传输过程的隐私。
2. 关键机制：DNSSEC 对记录签名，DoH 和 DoT 加密客户端到解析器的查询。
3. 对比或注意点：两者互补，DNSSEC 不加密，DoH 不验证权威记录的真实性。
4. 可追问时补充：DoH 绕过了企业基于 DNS 的过滤，存在争议。

**常见追问**

- DoH 和 DoT 有什么区别？→ DoT 使用专用端口 853，容易被识别和阻断；DoH 使用 443 端口，混在 HTTPS 流量中，难以区分。

## 六、实时通信与负载均衡

### Q29. WebSocket 的帧结构和安全要点有哪些？

- **难度**: 中级
- **标签**: WebSocket

**答案**

**帧结构要点**：

- FIN 位（是否最后一帧，大消息可以分片）
- 操作码：文本（1）、二进制（2）、关闭（8）、Ping（9）、Pong（10）
- **掩码**：客户端发送给服务端的帧**必须**使用随机掩码 —— 防止恶意页面构造的数据被中间代理误认为 HTTP 请求（缓存投毒）
- 负载长度：7 位 / 16 位 / 64 位

**安全要点**：

| 风险 | 措施 |
|------|------|
| **跨站 WebSocket 劫持**（CSWSH） | WebSocket 不受同源策略限制，握手会携带 Cookie → 服务端必须**检查 Origin**，或使用令牌鉴权 |
| 鉴权 | 握手时验证（Cookie 或一次性令牌）；浏览器的 WebSocket API 不能设置自定义头部，令牌可以通过查询参数（注意日志泄露）或连接后的第一条消息传递 |
| 消息注入 | 校验和限制消息的大小和频率 |
| 明文 | 使用 `wss://` |
| 资源耗尽 | 限制每个用户的连接数、消息速率 |

**口述模板（30–60 秒）**

1. 一句话结论：WebSocket 帧包含操作码、掩码和长度，客户端发送的帧必须使用掩码。
2. 关键机制：掩码防止恶意数据被中间代理误认为 HTTP 请求。
3. 对比或注意点：WebSocket 不受同源策略限制，服务端必须检查 Origin，防止跨站劫持。
4. 可追问时补充：浏览器 API 不能设置自定义头部，令牌通过查询参数或首条消息传递。

**常见追问**

- 通过查询参数传递令牌有什么问题？→ URL 会出现在服务器和代理的日志中；应该使用短期的一次性令牌。

### Q30. 轮询、长轮询、SSE、WebSocket、WebTransport 怎么选？

- **难度**: 中级
- **标签**: 实时通信

**答案**

| 方案 | 方向 | 特点 | 适用 |
|------|------|------|------|
| 短轮询 | 客户端拉 | 简单，浪费请求，有延迟 | 低频更新 |
| 长轮询 | 客户端拉（服务端挂起） | 兼容性好，每条消息一个请求 | 兼容旧环境 |
| **SSE** | 服务端 → 客户端 | 基于 HTTP，**自动重连**、`Last-Event-ID` 续传、文本格式；HTTP/1.1 下占用 6 个连接之一（HTTP/2 下没有这个问题） | 通知、日志流、AI 流式输出 |
| **WebSocket** | 双向 | 低开销、二进制；需要自己实现重连和心跳 | 聊天、协作、游戏 |
| **WebTransport** | 双向，多流 + 数据报 | 基于 HTTP/3，支持**不可靠的数据报**，没有队头阻塞 | 实时游戏、音视频、低延迟场景 |
| WebRTC | 点对点 | 音视频、P2P 数据通道，需要信令和 NAT 穿透 | 音视频通话 |

**选型原则**：只需要服务端推送 → SSE；需要双向低延迟 → WebSocket；需要不可靠传输或多流 → WebTransport（注意兼容性）。

**口述模板（30–60 秒）**

1. 一句话结论：单向推送用 SSE，双向通信用 WebSocket，需要不可靠传输用 WebTransport。
2. 关键机制：SSE 基于 HTTP，自带重连和断点续传；WebSocket 需要自己实现心跳和重连。
3. 对比或注意点：SSE 在 HTTP/1.1 下占用连接数，HTTP/2 下没有问题。
4. 可追问时补充：WebTransport 基于 HTTP/3，支持数据报，没有队头阻塞。

**常见追问**

- AI 聊天的流式输出为什么多数用 SSE（或流式 fetch）而不是 WebSocket？→ 只需要服务端到客户端的流式传输；基于 HTTP，鉴权、负载均衡、CDN 都可以复用现有设施。

### Q31. L4 和 L7 负载均衡有什么区别？

- **难度**: 中级
- **标签**: 负载均衡

**答案**

| 对比项 | L4（传输层） | L7（应用层） |
|--------|--------------|--------------|
| 依据 | IP、端口 | URL、头部、Cookie、内容 |
| 性能 | 高（不解析内容） | 较低（需要解析 HTTP、终止 TLS） |
| 能力 | 转发连接 | 按路径路由、重写、限流、鉴权、灰度、重试 |
| TLS | 透传（可以） | 通常终止 TLS |
| 例子 | LVS、云厂商的网络负载均衡、Maglev | Nginx、Envoy、HAProxy、云厂商的应用负载均衡 |

**常见架构**：

```text
Anycast / DNS → L4 负载均衡（集群入口，高性能）→ L7 负载均衡（路由、TLS 终止）→ 服务
```

**常见算法**：

- 轮询、加权轮询
- 最少连接（长连接场景）
- **一致性哈希**（会话保持、缓存亲和，节点变化时只影响少量请求）
- P2C（随机选两个，选负载低的）

**口述模板（30–60 秒）**

1. 一句话结论：L4 根据 IP 和端口转发连接，L7 根据 HTTP 内容路由请求。
2. 关键机制：L4 性能高，L7 功能强（路由、限流、灰度）。
3. 对比或注意点：常见架构是 L4 作为入口，后面接 L7。
4. 可追问时补充：长连接用最少连接算法，需要亲和性用一致性哈希。

**常见追问**

- WebSocket 长连接的负载均衡有什么问题？→ 连接建立后不会重新分配，扩容时新节点没有流量；需要在客户端重连时重新分配，或者主动迁移部分连接。

### Q32. 一个 HTTP 请求从客户端到后端服务，经过了哪些网络组件？

- **难度**: 中级
- **标签**: 架构

**答案**

```text
浏览器
 → 本地：DNS 解析（缓存 / DoH）、代理设置、Service Worker
 → 家庭路由器（NAT）→ 运营商网络（可能有运营商级 NAT）
 → 互联网骨干
 → CDN 边缘节点（Anycast；TLS 终止；缓存；WAF；DDoS 防护）
 → 回源：CDN 中间层 → 源站
 → 云厂商的 L4 负载均衡
 → L7 负载均衡 / API 网关（路由、鉴权、限流）
 → 服务网格边车代理（Envoy，mTLS）
 → 应用服务
 → 下游：数据库、缓存、其他微服务
```

**每个组件都可能是问题来源**：超时配置、连接复用、缓存、头部修改（`X-Forwarded-For`）、请求体大小限制、空闲超时。

**排查思路**：从请求 ID / 追踪 ID 串联各层日志，逐段确认耗时和错误发生在哪一层。

**口述模板（30–60 秒）**

1. 一句话结论：请求依次经过本地、NAT、运营商、CDN、负载均衡、网关、服务网格，最后到达服务。
2. 关键机制：CDN 负责就近接入和缓存，负载均衡和网关负责路由和防护。
3. 对比或注意点：每一层都有自己的超时、大小限制和连接管理。
4. 可追问时补充：用追踪 ID 串联各层日志，逐段定位问题。

**常见追问**

- 为什么外层的超时要比内层长？→ 外层的超时应该大于内层，否则内层还在处理时外层已经超时返回，造成资源浪费和难以排查的错误；同时内层的重试总时间不能超过外层的超时。
