# 计算机网络真实面试题

> 根据近年公开面经和技术社区讨论整理，`来源倾向`表示这类题目常出现的场景，不代表某公司的固定题库。答案为要点，详细内容见对应链接。

### R1. 从输入 URL 到页面显示，发生了什么？（侧重网络部分）

- **来源倾向**: 必问，几乎每家公司

**答案**

- URL 解析、HSTS 检查、缓存检查（Service Worker、HTTP 缓存）
- DNS 解析（浏览器 → 系统 → 递归解析器 → 根 / 顶级域 / 权威）
- TCP 三次握手（或 QUIC）
- TLS 1.3 握手（1 RTT）
- 发送 HTTP 请求，经过 CDN、负载均衡、网关到达服务
- 接收响应（可能是 304、重定向）
- 渲染部分见[浏览器原理](../browser/10-junior-qa.md)

**口述模板（30–60 秒）**

1. **一句话结论**：网络部分依次是缓存检查、DNS、TCP、TLS、HTTP 请求和响应。
2. **关键机制**：DNS 逐级查询并缓存；TCP 三次握手；TLS 1.3 一个往返协商密钥。
3. **对比或注意点**：每个阶段都有优化手段，高 RTT 下往返次数是关键。
4. **可追问时补充**：HTTP/3 合并了传输和加密握手，恢复连接可以 0-RTT。

详见：[30-senior Q1](./30-senior-qa.md)、[浏览器原理初级 Q5](../browser/10-junior-qa.md)

### R2. 为什么是三次握手？两次行不行？

- **来源倾向**: 高频

**答案**

- 同步双方的初始序号，各自需要对方确认
- 防止历史连接：旧的 SYN 到达时，客户端通过 RST 终止
- 两次握手时服务端无法确认客户端收到了自己的序号

详见：[10-junior Q8](./10-junior-qa.md)

---

### R3. 为什么是四次挥手？TIME_WAIT 为什么是 2MSL？

- **来源倾向**: 高频

**答案**

- 全双工，每个方向单独关闭；被动方可能还有数据要发送
- TIME_WAIT：保证最后的 ACK 能被重传、让旧连接的数据包在网络中消失
- 2MSL：一个 MSL 让 ACK 到达，一个 MSL 让可能重发的 FIN 到达

**口述模板（30–60 秒）**

1. **一句话结论**：TCP 是全双工的，两个方向分别关闭，所以需要四次。
2. **关键机制**：被动方收到 FIN 后可能还有数据，所以 ACK 和 FIN 分开发送。
3. **对比或注意点**：主动关闭方进入 TIME_WAIT，等待 2MSL。
4. **可追问时补充**：作用是保证最后的 ACK 可以重传，并让旧连接的数据包消失。

详见：[10-junior Q9](./10-junior-qa.md)

### R4. 服务器上出现大量 TIME_WAIT / CLOSE_WAIT，怎么处理？

- **来源倾向**: 高频，偏后端和 Node

**答案**

- TIME_WAIT：主动关闭了大量短连接；首选连接复用，`tcp_tw_reuse`，扩大端口范围；不要用已移除的 `tcp_tw_recycle`
- CLOSE_WAIT：应用没有关闭连接，是 bug；用 `ss` 找到进程和对端，检查连接释放逻辑

详见：[20-mid Q2–Q3](./20-mid-qa.md)

### R6. 讲讲拥塞控制，BBR 和 Cubic 有什么区别？

- **来源倾向**: 中频，高级岗加分

**答案**

- 经典：慢启动、拥塞避免、快速重传、快速恢复
- Cubic：基于丢包，增长是时间的三次函数，Linux 默认
- BBR：基于瓶颈带宽和最小 RTT 的测量，不填满缓冲区，对随机丢包不敏感

**口述模板（30–60 秒）**

1. **一句话结论**：拥塞控制通过拥塞窗口防止发送方压垮网络。
2. **关键机制**：慢启动指数增长，拥塞避免线性增长，丢包时减小窗口。
3. **对比或注意点**：Cubic 以丢包作为拥塞信号；BBR 测量带宽和 RTT，延迟更低。
4. **可追问时补充**：BBR 适合长距离、有随机丢包的网络。

详见：[20-mid Q5–Q6](./20-mid-qa.md)

### R9. HTTP/1.1、HTTP/2、HTTP/3 的区别？

- **来源倾向**: 必问

**答案**

- HTTP/1.1：文本、持久连接、队头阻塞、6 个连接
- HTTP/2：二进制帧、多路复用、HPACK；仍有 TCP 层的队头阻塞
- HTTP/3：QUIC（UDP）、流独立、更快的握手、连接迁移、QPACK

**口述模板（30–60 秒）**

1. **一句话结论**：HTTP/2 引入多路复用，HTTP/3 把传输层换成了 QUIC。
2. **关键机制**：HTTP/2 在一个 TCP 连接上交错传输多个流的帧。
3. **对比或注意点**：HTTP/2 的 TCP 丢包会阻塞所有流，HTTP/3 中流相互独立。
4. **可追问时补充**：HTTP/3 握手更快，支持连接迁移，但部分网络限制 UDP。

详见：[10-junior Q25](./10-junior-qa.md)、[20-mid Q11–Q16](./20-mid-qa.md)

### R10. HTTP/2 的多路复用是怎么实现的？还有什么问题？

- **来源倾向**: 高频

**答案**

### R11. QUIC 为什么基于 UDP？0-RTT 有什么风险？

- **来源倾向**: 中频，近年上升

**答案**

- TCP 在内核中、中间设备僵化，难以演进；新传输层协议无法穿越 NAT
- UDP + 用户态实现 + 加密头部
- 0-RTT 数据可以被重放，只能用于幂等请求

详见：[20-mid Q14](./20-mid-qa.md)、[30-senior Q8](./30-senior-qa.md)

### R12. HTTPS 握手过程是怎样的？TLS 1.3 有什么改进？

- **来源倾向**: 必问

**答案**

- TLS 1.3：ClientHello 携带 key_share → ServerHello + 证书 + 签名 + Finished → 客户端 Finished，1 RTT
- 改进：1 RTT、强制前向安全、移除不安全算法、证书加密传输、0-RTT

**口述模板（30–60 秒）**

1. **一句话结论**：TLS 1.3 只需一个往返，客户端在第一条消息中就发送了密钥交换的公钥。
2. **关键机制**：服务端回复公钥、证书和签名，双方用 ECDHE 计算出相同的密钥。
3. **对比或注意点**：相比 1.2 移除了 RSA 密钥交换，强制前向安全。
4. **可追问时补充**：恢复连接可以 0-RTT，但有重放风险。

详见：[20-mid Q20](./20-mid-qa.md)、[浏览器原理中级 Q8](../browser/20-mid-qa.md)

### R13. HTTPS 一定安全吗？中间人攻击怎么实现？

### R15. HTTP 缓存机制？`no-cache` 和 `no-store` 的区别？

- **来源倾向**: 必问

**答案**

### R17. WebSocket 的原理？怎么保证连接稳定？

- **来源倾向**: 高频

**答案**

- HTTP Upgrade 握手 → 101 → WebSocket 帧
- 稳定：应用层心跳（检测半开连接、保活 NAT）、指数退避重连 + 抖动、消息序号和增量同步
- 安全：检查 Origin、握手时鉴权、wss

**口述模板（30–60 秒）**

1. **一句话结论**：WebSocket 通过 HTTP Upgrade 握手，之后使用全双工的帧通信。
2. **关键机制**：应用层心跳检测半开连接，防止 NAT 和代理清理空闲连接。
3. **对比或注意点**：断线后指数退避加抖动重连，避免重连风暴。
4. **可追问时补充**：重连后根据消息序号增量同步，保证不丢消息。

详见：[10-junior Q27](./10-junior-qa.md)、[20-mid Q29](./20-mid-qa.md)、[40-coding H7](./40-coding-handwritten.md)

### R20. 接口偶发超时 / 502，怎么排查？

- **来源倾向**: 高频，实战题

**答案**

- 缩小范围（时间、地区、实例），看超时的分布规律
- 逐层：DNS、连接（SYN 重传、队列溢出）、连接复用（keep-alive 超时不匹配）、服务端（GC、阻塞）、网络（丢包）
- 抓包验证
- Node.js 常见：`keepAliveTimeout` 小于负载均衡的空闲超时

**口述模板（30–60 秒）**

1. **一句话结论**：先缩小范围，再逐层排查，最后抓包验证。
2. **关键机制**：超时集中在 1 秒、3 秒附近通常是 SYN 重传；502 常见于上游先关闭了空闲连接。
3. **对比或注意点**：上游的 keep-alive 超时要大于下游。
4. **可追问时补充**：用追踪 ID 串联各层日志，确定是哪一层出的问题。

详见：[30-senior Q4–Q5](./30-senior-qa.md)

### R24. 设计一个大文件上传方案

- **来源倾向**: 高频（前端场景题）

**答案**

- Web Worker 计算哈希 → 秒传检查 → 分片并发上传（预签名 URL 直传）→ 合并校验
- 断点续传：服务端记录已完成的分片
- 失败分片退避重试；秒传的安全问题

**口述模板（30–60 秒）**

1. **一句话结论**：计算哈希、检查秒传、分片并发上传、最后合并校验。
2. **关键机制**：服务端记录已完成的分片，实现断点续传。
3. **对比或注意点**：分片直传对象存储，减轻服务器带宽压力。
4. **可追问时补充**：秒传要防止通过哈希探测他人的文件。

详见：[50-system-design S2](./50-system-design.md)、[40-coding H5](./40-coding-handwritten.md)

### R25. 设计一个 IM 或消息推送系统

- **来源倾向**: 高频（系统设计）

**答案**

- 接入层（连接、心跳）+ 路由表 + 逻辑层 + 消息队列 + 存储

详见：[50-system-design S1](./50-system-design.md)、[30-senior Q6、Q15](./30-senior-qa.md)
