# Docker 高级 Q&A（能扛追问）

> 目标：底层机制、性能与容量、安全边界、生产事故思路、架构取舍。

## 一、运行时与内核

### Q1. 从 OCI 角度讲清 dockerd、containerd、runc、shim 的职责边界

- **难度**: senior
- **标签**: 运行时, OCI

**答案**

- **dockerd**：Docker 体验与高层 API（镜像构建集成、网络/卷的 Docker 模型、兼容生态）  
- **containerd**：容器生命周期管理、镜像分发存储（越来越多成为核心）  
- **runc**：按 OCI Runtime Spec **真正创建命名空间/cgroup/挂载并 exec** 的低层运行时（一次性）  
- **containerd-shim**：runc 返回后常驻，接管 IO/信号/退出状态，让上层 daemon 重启不杀容器  

高级面试强调：Docker 是「产品拼装」，隔离真相在内核 + OCI runtime。

**口述模板（30–60 秒）**

1. Docker 是上层产品，runc 才落内核隔离。  
2. containerd 管生命周期与镜像。  
3. shim 让容器与 daemon 解耦。  
4. 可追问：CRi-O、containerd 直接被 K8s 使用。

**常见追问**

- 为何 K8s 可以不用 dockershim 了？→ 通过 CRI 直接对接 containerd 等；Docker Engine 不再是唯一路径。

### Q2. User Namespace 与 Rootless Docker 的收益与代价

- **难度**: senior
- **标签**: user ns, rootless

**答案**

**User namespace** 把容器内 UID 0 映射到宿主非特权 UID，降低逃逸后的影响力。  
**Rootless**：daemon 与容器都以非 root 跑，攻击面更小。  

代价：网络（常用 slirp4netns/pasta 用户态）与部分存储/设备能力性能或功能受限；运维复杂度上升；并非所有场景可开。  
面试表达：安全架构选项，不是「开了就万能」。

**口述模板（30–60 秒）**

1. 映射 UID 缩小爆炸半径。  
2. Rootless 更安全也更受限。  
3. 用在多租户/高威胁模型。  
4. 可追问：与 gVisor/Kata 强隔离对比。

**常见追问**

- 为何 rootless 下绑定低端口麻烦？→ 无特权；用反向代理或能力受限。

### Q3. cgroup v1 与 v2 对容器意味着什么？

- **难度**: senior
- **标签**: cgroup

**答案**

v1：多层级控制器分离，历史包袱多。  
v2：统一层级，接口更一致（`cpu.max`、`memory.max`、`io.max`、`pids.max` 等）。主流发行版与新 K8s 走向 **cgroup v2 默认**。  

高级要点：硬限制 vs 权重（如 CPU weight）；内存的 max 与 high（压力信号）；容器指标采集路径变化。  
不必背所有文件，但要能说明「限制写到 cgroup 文件，由内核强制」。

**口述模板（30–60 秒）**

1. 配额最终是内核 cgroup。  
2. v2 是统一现代接口。  
3. 关注 cpu/memory/pids/io 四类。  
4. 可追问：systemd 与 cgroup 驱动关系。

**常见追问**

- `--pids-limit` 防什么？→ fork 炸弹耗尽宿主 PID。

### Q4. overlay2 在高密度写入下有哪些性能与运维风险？

- **难度**: senior
- **标签**: overlay2, 性能

**答案**

- 写放大：小文件修改触发 copy-up  
- inode / 磁盘耗尽：层与 whiteout、未清理缓存  
- 对数据库类 fsync 密集负载不友好  
- 容器层填满导致应用异常，且难一眼看出  

治理：数据落卷/块设备；限制容器可写层；监控 `/var/lib/docker`；定期 prune 策略；构建缓存与镜像 GC 分开谈。

**口述模板（30–60 秒）**

1. overlay 适合读多写少的应用层。  
2. 密集写外置存储。  
3. 监控磁盘与 inode。  
4. 可追问：containerd snapshotter 演进。

**常见追问**

- 换 btrfs/zfs 驱动？→ 少见且运维成本高；多数场景优化负载比换驱动更重要。

### Q5. 容器没有独立内核，安全边界如何讲才不肤浅？

- **难度**: senior
- **标签**: 安全

**答案**

边界 = Namespace 隔离 + cgroup 配额 + **Capabilities 裁剪** + **seccomp** 限制 syscall + **LSMs（AppArmor/SELinux）** + 只读根/UserNS/不特权。  
任一环节过宽（`--privileged`、挂宿主机根、SYS_ADMIN、docker.sock）都会让边界名存实亡。  
内核漏洞仍可能影响所有容器 → 需宿主加固、及时打补丁、必要时强隔离运行时（Kata/gVisor）。

**口述模板（30–60 秒）**

1. 容器是多层防护叠加，不是一堵墙。  
2. privileged/sock/挂根是直接拆墙。  
3. 内核共享是根本风险模型。  
4. 可追问：CIS Docker Benchmark。

**常见追问**

- `--privileged` 到底开了什么？→ 几乎所有能力、设备访问等，接近「容器里的根宿主」。

## 二、构建与供应链

### Q6. 如何设计「可复现 + 快速 + 安全」的构建流水线？

- **难度**: senior
- **标签**: BuildKit, CI

**答案**

- Dockerfile：多阶段、依赖与源码分层、固定基础镜像 digest  
- BuildKit：`cache` mount 加速包管理；`secret`/`ssh` mount 不落层  
- CI：远程缓存 `--cache-to/--cache-from`（registry 模式）对抗短暂 runner  
- 产物：SBOM、漏洞扫描门禁、签名（Cosign 等）、推送不可变 tag+digest  
- 权限：构建节点与业务集群分离，避免业务侧持有推送/socket 特权  

**口述模板（30–60 秒）**

1. 快靠缓存结构，安全靠 secret 与扫描签名。  
2. 可复现靠钉 digest。  
3. 构建与运行权限分离。  
4. 可追问：多架构矩阵构建策略。

**常见追问**

- 每次 CI 仍很慢？→ 先看层顺序，再看远程缓存是否命中，再看是否无意义地 `--no-cache`。

### Q7. BuildKit 的 cache mount 和层缓存有何本质不同？

- **难度**: senior
- **标签**: BuildKit

**答案**

**层缓存**：指令输入不变则整层复用，结果进镜像历史。  
**cache mount**：构建时挂载可读写缓存目录（如 `/root/.cache/go-build`、apk/npm 缓存），**不作为镜像层导出**，却在多次构建间保留，极大加速下载/编译，同时最终镜像保持干净。

**口述模板（30–60 秒）**

1. 层缓存复用镜像层。  
2. cache mount 复用构建机缓存且不进镜像。  
3. 两者互补。  
4. 可追问：cache id 与并发构建共享。

**常见追问**

- 会不会造成脏缓存构建？→ 可能；依赖锁文件与定期清理策略。

### Q8. 多架构镜像（manifest list）在发布与回滚上要注意什么？

- **难度**: senior
- **标签**: 多架构

**答案**

`buildx` 生成的是 **index/manifest list**，同一 tag 下挂多架构 manifest。  
注意：不同架构的 digest 不同；回滚要明确「哪一架构、哪个 index digest」；扫描与签名要对准最终 index；部分旧工具只认单 manifest。  
异构集群（amd64+arm64）要用统一发布流程，避免节点拉错架构。

**口述模板（30–60 秒）**

1. tag 背后是多架构索引。  
2. 回滚与审计对准 digest。  
3. 工具链要能处理 manifest list。  
4. 可追问：本地模拟 vs 真机构建矩阵。

**常见追问**

- 为何交叉编译比 QEMU 快？→ 避免指令翻译；Go/Rust 友好，复杂 C++ 更难。

### Q9. 基础镜像升级与 CVE 治理怎么制度化？

- **难度**: senior
- **标签**: 安全, 治理

**答案**

- 库存：公司基础镜像（黄金镜像）统一维护  
- 扫描：CI 阻断 CRITICAL/HIGH（可分级豁免）  
- 重建：上游 CVE → 触发自动 rebuild 与环境晋级  
- 运行时：节点与运行时补丁节奏；不能只扫不修  
- 指标：镜像平均年龄、高危未修复数量、MTTR  

高级回答要落到「流程+门禁+责任人」，不是偶尔手动 pull。

**口述模板（30–60 秒）**

1. 黄金镜像 + 自动扫描重建。  
2. 门禁与豁免流程。  
3. 运行时补丁同步。  
4. 可追问：Distroless 减少包面是否足够。

**常见追问**

- 业务镜像无 shell 如何应急？→ 临时 debug 容器/短暂提权通道/ephemeral 工具镜像，而不是长期装工具进生产镜像。

## 三、网络与规模

### Q10. 单机 Docker 网络模型扩展到多机时，瓶颈在哪？

- **难度**: senior
- **标签**: 网络, overlay

**答案**

单机 bridge + NAT 足够。多机需要 **overlay**（Swarm）或外部网络方案（K8s CNI：Calico/Cilium…）。  
挑战：跨主机封装开销、MTU、服务发现、NetworkPolicy、排障复杂度、与云 VPC/安全组叠床架屋。  
高级结论：多机容器网络几乎必然进入「编排+CNI」领域，而不是手写一堆 docker network。

**口述模板（30–60 秒）**

1. 单机 NAT 简单，多机要覆盖网络。  
2. 复杂度在发现、策略、排障。  
3. 生产多节点用 K8s CNI 更常见。  
4. 可追问：iptables 规则膨胀与 nftables。

**常见追问**

- Docker Swarm overlay 还用吗？→ 存量有；新项目多数 K8s。

---

### Q11. iptables 规则膨胀、连接跟踪打满如何影响容器网络？

- **难度**: senior
- **标签**: 网络, 性能

**答案**

高连接场景下，NAT/filter 规则多、**conntrack** 表满会导致新建连接失败（表现为偶发超时）。  
治理：提高 conntrack 上限、减少不必要端口发布、合并服务、改用更高效数据路径（部分 CNI/kube-proxy 模式）、观测 `nf_conntrack_count`。  
这是高级运维面试加分项：能从「容器连不上」跳到内核网络资源。

**口述模板（30–60 秒）**

1. 容器网络大量依赖原生 NAT/跟踪。  
2. 打满就偶发失败。  
3. 监控 conntrack 与规则规模。  
4. 可追问：ipvs vs iptables。

**常见追问**

- 如何快速验证？→ 宿主看 conntrack 使用率；对比失败时刻指标。

---

### Q12. 高密度部署时，如何做节点资源与隔离设计？

- **难度**: senior
- **标签**: 容量, 隔离

**答案**

- 强制 memory/cpu/pids limit，避免 noisy neighbor  
- 系统预留（kube 的 system-reserved 思维同样适用裸 Docker 节点）  
- 磁盘：容器日志、镜像、卷分盘或配额  
- 网络带宽与文件描述符上限  
- 租户隔离：不同节点池、网络策略、禁止特权  

只讲「加机器」不加分；要讲 **限制 + 预留 + 观测 + 驱逐/降级策略**。

**口述模板（30–60 秒）**

1. 密度靠配额，稳定靠预留。  
2. 磁盘与 FD 常被忽视。  
3. 用观测验证隔离。  
4. 可追问：OOM 时杀谁的策略。

**常见追问**

- CPU hard limit 过小的副作用？→ 节流导致延迟长尾，被误判为应用 bug。

## 四、存储与有状态

### Q13. 有状态服务容器化的架构取舍怎么谈？

- **难度**: senior
- **标签**: 有状态, 架构

**答案**

决策树：

1. 能否改成无状态 + 托管存储？（优先）  
2. 必须有状态：数据面用云盘/本地 SSD + 明确调度粘性  
3. 备份 RPO/RTO、扩缩容是否允许、故障切换谁做  
4. Docker 单机 Compose 适合小流量；多副本一致性/选主通常需要应用层或 K8s Operator  

面试官听的是：你知道**状态外置**与**编排能力边界**。

**口述模板（30–60 秒）**

1. 先尽量无状态化。  
2. 否则外置盘 + 备份 + 故障域。  
3. 超单机就别硬用纯 Compose。  
4. 可追问：本地盘性能 vs 云盘延迟。

**常见追问**

- 为何有人坚持 DB 不上 K8s？→ 运维复杂度、生态与团队能力；不是绝对对错。

---

### Q14. 容器崩溃后数据一致性如何保证？（应用视角）

- **难度**: senior
- **标签**: 一致性

**答案**

- 持久化到卷后仍要考虑：进程被杀时未刷盘、半写文件  
- 应用用 fsync/事务/WAL；停止时优雅 SIGTERM 与足够 `stop_grace_period`  
- 分布式：至少一次投递 + 幂等；避免「容器重启导致重复任务」无防护  

高级回答把 Docker 停止语义和应用正确性连起来。

**口述模板（30–60 秒）**

1. 卷只保证「文件还在」，不保证「业务一致」。  
2. 优雅停止 + 应用持久化语义。  
3. 任务要幂等。  
4. 可追问：kill 超时导致的半完成发布。

**常见追问**

- stop 信号不是 SIGTERM？→ 取决于入口；错误 ENTRYPOINT 会破坏优雅退出。

## 五、生产事故与排障

### Q15. 设计一套「容器节点磁盘打满」应急与根治流程

- **难度**: senior
- **标签**: 事故, 磁盘

**答案**

**应急**：定位最大户（日志、镜像、overlay、卷、构建缓存）→ 先轮转/截断安全日志 → 删无用镜像（确认未被运行引用）→ 必要时扩容。  
**根治**：json-file 轮转或旁路日志驱动；镜像 GC 策略；构建缓存出业务节点；卷与系统盘分离；告警阈值（80%/inode）。  
禁止在不知情时 `prune -a -f` 误删。

**口述模板（30–60 秒）**

1. 先定位后清理。  
2. 应急止血，根治策略与告警。  
3. 危险命令要确认。  
4. 可追问：只读根如何减少可写层增长。

**常见追问**

- 如何避免清理误伤？→ 按标签保留、按时间、生产清单；先 dry-run 思维。

### Q16. 大范围「容器拉不起来/镜像拉取失败」如何分层排查？

- **难度**: senior
- **标签**: 排障, Registry

**答案**

分层：

1. 单节点 vs 全网：DNS、到 Registry 网络、证书、限流  
2. 认证：机器人账号过期、权限  
3. Registry 本身：存储后端、配额  
4. 限流与并发：滚动更新同时 pull 打爆仓库 → 预拉、daemon 并发参数、节点镜像缓存  
5. 内容：架构不匹配、manifest 被删、tag 被覆盖  

高级思路：**爆炸半径 + 依赖服务健康 + 发布策略**。

**口述模板（30–60 秒）**

1. 先分局部还是全局。  
2. 网络/认证/仓库/限流四象限。  
3. 用预热与节奏避免雪崩。  
4. 可追问：多可用区仓库与回源。

**常见追问**

- 如何证明是限流？→ 仓库侧 429/指标；对照并发 pull 曲线。

### Q17. 宿主负载很高但容器 CPU limit 未打满，可能原因？

- **难度**: senior
- **标签**: 性能

**答案**

- 磁盘 IO 等待（日志狂写、overlay copy-up）  
- 上下文切换过多、连接风暴  
- 内核/守护进程（dockerd、containerd）自身耗资源  
- 内存回收/页缓存压力表现为负载高  
- 偷时间的是旁路进程：杀毒、备份、监控  

要用 `pidstat`/`iostat`/`perf` 等分清 CPU running vs iowait，而不是只看容器 cAdvisor 的 CPU%。

**口述模板（30–60 秒）**

1. load 高≠容器 CPU 配额用满。  
2. 先分 iowait 与系统进程。  
3. 再看 Docker 组件自身。  
4. 可追问：cpu throttling 指标。

**常见追问**

- throttling 高说明什么？→ 触达 CFS 配额，延迟上升。

---

### Q18. Docker daemon 挂了，容器会怎样？你希望怎样？

- **难度**: senior
- **标签**: 可靠性

**答案**

历史上依赖配置与版本：理想情况是 **live-restore** 使容器在 daemon 重启后继续运行。  
要验证当前环境是否开启、重启 daemon 的变更窗口与影响面。  
架构上：关键业务最终应由编排层做多副本，而不是赌单机 daemon 永不死。

**口述模板（30–60 秒）**

1. 查 live-restore 行为。  
2. daemon 仍是单点风险。  
3. 关键靠编排多副本。  
4. 可追问：升级 Docker 的变更策略。

**常见追问**

- 升级 Engine 最佳实践？→ 先耗尽节点流量/副本迁移，再升级，金丝雀节点验证。

## 六、与编排/平台边界

### Q19. 何时该从 Docker Compose 迁到 Kubernetes？

- **难度**: senior
- **标签**: 架构, K8s

**答案**

迁移信号：多节点、自动扩缩、自愈与滚动升级、服务发现与配置密钥体系统一、多环境一致性、资源配额多租户。  
Compose 仍适合：本地开发、单机小工具链、边缘简单栈。  
错误迁移动机：「别人都在用」；正确动机是**调度与运维复杂度已经超过 Compose 模型**。

**口述模板（30–60 秒）**

1. Compose 管单机声明式。  
2. K8s 管集群调度与治理。  
3. 按痛点迁移而非跟风。  
4. 可追问：中间态 ECS/Nomad/Swarm。

**常见追问**

- 原样把 compose 翻译成 K8s 够吗？→ 往往不够，要引入探针、资源、发布、配置模型。

### Q20. 如何看待「应用打包成容器」与「十二要素」的关系？

- **难度**: senior
- **标签**: 架构

**答案**

容器放大了十二要素：配置进环境、无状态进程、端口绑定、日志打 stdout、后端服务当附加资源。  
违反时容器化只会把脏状态藏进卷和可写层，排障更难。  
高级工程师推动的是**应用可云原生化**，而不只是「能 docker run」。

**口述模板（30–60 秒）**

1. 容器是打包，十二要素是设计。  
2. 无状态+外部化配置是关键。  
3. 否则上了容器也难运维。  
4. 可追问：会话粘滞与本地磁盘缓存的治理。

**常见追问**

- 遗留单体只能本地写文件？→ 挂卷 + 逐步拆分；讲演进比讲理想重要。

### Q21. 镜像仓库（Harbor 等）在企业架构中如何定位？

- **难度**: senior
- **标签**: Harbor, 治理

**答案**

企业 Registry 不只是「存镜像」：项目隔离与权限、复制同步（多机房）、漏洞扫描与签名门禁、垃圾回收、审计。  
与 CI/CD、运行时拉取、安全合规形成闭环。  
高可用与存储后端（对象存储）设计是平台题加分项。

**口述模板（30–60 秒）**

1. Harbor 是治理平面不只是磁盘。  
2. 权限、扫描、复制、GC。  
3. 和 CI/运行时闭环。  
4. 可追问：不可变仓库与保留策略。

**常见追问**

- 公网 Docker Hub 直拉的问题？→ 限流、合规、供应被投毒风险；企业应代理/镜像缓存。

## 七、性能与成本

### Q22. 镜像体积优化到什么程度算「够」？有哪些收益递减？

- **难度**: senior
- **标签**: 性能, 成本

**答案**

收益：拉取更快、冷启动更快、攻击面更小、存储成本降。  
手段：多阶段、精简基础镜像、去掉调试器、合并无谓层、压缩与懒加载（视运行时）。  
递减：过度 Distroless 导致排障成本上升；为减 5MB 牺牲构建复杂度不划算。  
用「拉取 P95、节点并发滚动时间」衡量，而不是只晒镜像体积截图。

**口述模板（30–60 秒）**

1. 体积服务发布速度与安全。  
2. 用发布指标衡量。  
3. 避免为小优化付大战。  
4. 可追问：懒加载/流式镜像。

**常见追问**

- 层数越少越好吗？→ 适度；可读性与缓存命中更重要，现代存储也不再「层数迷信」。

### Q23. 启动性能（冷启动）优化从哪几层下手？

- **难度**: senior
- **标签**: 性能

**答案**

1. 镜像拉取与缓存命中（体积、就近仓库、预热）  
2. 应用启动（类加载、迁移、JIT）——往往大于容器本身  
3. 探活太严导致「已启动未就绪」拉长发布  
4. 存储驱动与必要挂载数量  

高级回答会把「容器启动」和「应用就绪」拆开。

**口述模板（30–60 秒）**

1. 先分拉取 vs 进程启动 vs 就绪。  
2. 各自优化。  
3. 探针参数影响发布体感。  
4. 可追问：水平扩容时的镜像预热。

**常见追问**

- Java 容器慢是否 Docker 锅？→ 多半是 JVM/应用；用 CDS/原生镜像等对症。

## 八、对比与选型

### Q24. Docker 与 Podman、containerd 直接使用如何选型表述？

- **难度**: senior
- **标签**: 选型

**答案**

- **Docker**：生态与开发体验强，桌面+文档友好  
- **Podman**：daemonless、更贴近 rootless 理念，兼容部分 Docker CLI  
- **直接 containerd/nerdctl**：更贴近 K8s 生产运行时，减一层  

选型看团队技能、与 K8s 一致性、合规要求；面试强调「运行时标准是 OCI，工具可替换」。

**口述模板（30–60 秒）**

1. 标准是 OCI，产品可换。  
2. Docker 重体验，Podman 重无守护进程，containerd 重运行时。  
3. 按平台战略选。  
4. 可追问：镜像构建是否仍用 BuildKit。

**常见追问**

- 会不会 Docker 消失？→ 引擎形态在变，容器工作流不会消失。

### Q25. 何时使用 `--privileged` 以外的「几乎特权」组合？如何收敛？

- **难度**: senior
- **标签**: 安全

**答案**

一些设备/系统管理容器需要 `SYS_ADMIN`、挂载、host网络等。原则：

- 独立节点池/独立机器，不与业务混部  
- 能力逐项添加并审计，能不用 privileged 就不用  
- 只读根 + 明确设备白名单  
- 网络与密钥最小  

面试忌口：「不知道就 privileged」。

**口述模板（30–60 秒）**

1. 特权是最后手段。  
2. 隔离部署 + 能力清单。  
3. 持续审计。  
4. 可追问：eBPF/节点剂需要的权限模型。

**常见追问**

- 监控 agent 是否要特权？→ 看采集方式；尽量用官方推荐最小权限。

### Q26. 如何设计容器平台的「变更与回滚」？

- **难度**: senior
- **标签**: 发布

**答案**

- 产物不可变：镜像 digest 唯一  
- 环境晋级：dev → staging → prod，配置分离  
- 发布：滚动/金丝雀/蓝绿（单机 Compose 能力有限，讲清）  
- 回滚：重新部署旧 digest，而非改容器内文件  
- 数据库迁移：向后兼容迁移与扩缩容顺序  

高级把 Docker 产物管理嵌入发布工程。

**口述模板（30–60 秒）**

1. 回滚=切回旧 digest。  
2. 配置与镜像版本一起记录。  
3. 迁移要可回滚或兼容。  
4. 可追问：配置错误与代码错误的区分。

**常见追问**

- latest 滚动如何回滚？→ 基本很难可靠回滚，这正是禁用 latest 的原因。

### Q27. 讲一次你理想中的「生产 Dockerfile 审查清单」

- **难度**: senior
- **标签**: 实践, 清单

**答案**

1. 基础镜像来源可信且钉版本/digest  
2. 多阶段，最终无编译器/密钥  
3. 非 root；明确 USER  
4. HEALTHCHECK 合理  
5. `.dockerignore` 完备  
6. 层顺序利于缓存  
7. 无 `latest` 依赖乱飘  
8. 暴露面：端口/能力/卷最小化  
9. 元数据标签：版本、源码修订、构建号  
10. CI 扫描通过  

用清单证明你有工程纪律，而不只是会写 FROM/RUN。

**口述模板（30–60 秒）**

1. 审查看安全、可复现、可运维。  
2. 十条清单快速过。  
3. 不过门禁不入生产。  
4. 可追问：标签规范与溯源。

**常见追问**

- LABEL 有什么用？→ 溯源、CMDB、策略引擎识别。

### Q28. 容器逃逸类问题在面试里如何「安全地」讨论？

- **难度**: senior
- **标签**: 安全

**答案**

只谈**防御与风险模型**：特权、错误挂载、有缺陷的运行时、内核漏洞、弱隔离。  
不提供利用步骤。强调加固基线、及时更新、威胁建模、入侵检测与最小权限。  
这是高级工程师的职业表达方式。

**口述模板（30–60 秒）**

1. 讨论防御面而非利用细节。  
2. 配置失误比「神奇 0day」更常见。  
3. 基线+补丁+监控。  
4. 可追问：运行时安全产品（概念）。

**常见追问**

- 最常见的配置型风险？→ privileged、docker.sock、宿主机根挂载、以 root 跑未知镜像。

### Q29. 如何评估「把构建放进容器」vs「专用构建机」？

- **难度**: senior
- **标签**: CI, 架构

**答案**

容器化构建可复现、易迁移；但涉及 DinD/sock/权限时风险高。  
专用构建机/集群（BuildKit 远程、Kaniko on K8s）可统一缓存与安全策略，成本是平台投入。  
按组织规模：小团队可受限 DinD；中大型收敛到构建平台。

**口述模板（30–60 秒）**

1. 可复现重要，权限隔离更重要。  
2. 规模上来就平台化构建。  
3. 缓存是平台核心价值。  
4. 可追问：远程 BuildKit 拓扑。

**常见追问**

- Kaniko 优缺点？→ 无需特权 daemon 的一种方案；兼容性与性能要实测。

### Q30. 未来趋势：你如何看待 Docker 在云原生版图中的位置？（开放题）

- **难度**: senior
- **标签**: 趋势

**答案**

建议结构：

1. **开发者体验**：Dockerfile/Compose 仍是事实标准入口  
2. **运行时**：生产 K8s 侧更多 containerd；Docker Engine 非唯一  
3. **构建**：BuildKit/buildx 生态独立变强  
4. **替代与互补**：Podman、nerdctl、WASM/边缘、强隔离运行时  

表态要具体：继续深耕镜像构建与本地开发工作流，同时理解 CRI 运行时分工。

**口述模板（30–60 秒）**

1. Docker 心智模型仍重要。  
2. 生产运行时与构建在分工细化。  
3. 学习重点从「会 Docker」扩展到「OCI+编排」。  
4. 可追问：WASM 是否替代容器（短期互补）。

**常见追问**

- 还要不要学 Docker？→ 要；它是云原生基础语言，但别停在只会命令。
