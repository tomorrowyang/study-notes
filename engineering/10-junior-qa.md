## 一、依赖管理

### Q1. 前端工程化要解决什么问题？

- **难度**: 初级
- **标签**: 概述

**答案**

前端工程化是用工具和流程让**多人、长期、大规模**的前端开发变得**高效、稳定、可控**：

| 方面 | 内容 |
|------|------|
| 开发效率 | 脚手架、模块化、热更新、代码生成 |
| 代码质量 | 类型检查、Lint、格式化、测试、代码评审 |
| 构建 | 编译、打包、压缩、拆包、资源优化 |
| 协作 | 依赖管理、Monorepo、规范、Git 工作流 |
| 交付 | CI/CD、部署、灰度、回滚 |
| 运行时 | 监控、错误追踪、性能度量 |
| 架构 | 组件库、微前端、跨团队协作 |

**口述模板（30–60 秒）**

1. 一句话结论：前端工程化用工具和流程让多人长期开发变得高效、稳定、可控。
2. 关键机制：覆盖开发、质量、构建、协作、交付和运行时监控。
3. 对比或注意点：工程化的目标是解决团队的实际问题，不是堆砌工具。
4. 可追问时补充：高级工程师需要能为团队设计和落地工程化体系。

**常见追问**

- 你们团队的工程化体系是怎样的？→ 按「开发 → 质量 → 构建 → 交付 → 监控」的链路介绍，并说出解决了什么问题。

### Q2. npm、yarn、pnpm 有什么区别？

- **难度**: 初级
- **标签**: 包管理

**答案**

| 方面 | npm | yarn（v1 / Berry） | pnpm |
|------|-----|---------------------|------|
| node_modules 结构 | 扁平化（提升） | v1 扁平化；Berry 默认 PnP（无 node_modules） | **内容寻址存储 + 硬链接 + 符号链接** |
| 磁盘占用 | 每个项目一份 | 每个项目一份（PnP 例外） | **全局存储，多个项目共享** |
| 安装速度 | 较慢 | 较快 | 快 |
| 幽灵依赖 | 存在 | v1 存在 | **默认避免** |
| Monorepo | workspaces | workspaces | workspaces（最常用） |

**pnpm 的结构**：

```text
node_modules/
  react -> .pnpm/react@19.2.0/node_modules/react          # 符号链接，只有直接依赖
  .pnpm/
    react@19.2.0/node_modules/react  -> 硬链接到全局存储
    react-dom@19.2.0/node_modules/
      react-dom
      react -> ../../react@19.2.0/node_modules/react       # 依赖的依赖
```

**口述模板（30–60 秒）**

1. 一句话结论：三者的主要区别在于 node_modules 的组织方式。
2. 关键机制：npm 和 yarn v1 扁平化提升依赖，pnpm 使用全局存储加硬链接和符号链接。
3. 对比或注意点：pnpm 节省磁盘、安装快，并且避免了幽灵依赖。
4. 可追问时补充：pnpm 是目前 Monorepo 最常用的包管理器。

**常见追问**

- 什么是幽灵依赖？→ 代码中使用了没有在 `package.json` 中声明的包，因为它被提升到了顶层 node_modules；依赖升级后可能突然消失。

### Q3. 锁文件有什么作用？`npm install` 和 `npm ci` 有什么区别？

- **难度**: 初级
- **标签**: 包管理, 锁文件

**答案**

**锁文件**（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`）记录每个依赖（包括间接依赖）**解析后的确切版本、来源和完整性哈希**，保证所有人和 CI 安装的依赖完全一致。

| 命令 | 行为 |
|------|------|
| `npm install` | 根据 `package.json` 安装，**可能更新锁文件** |
| `npm ci` | **严格按锁文件安装**；锁文件与 `package.json` 不一致时报错；先删除 node_modules |
| `pnpm install --frozen-lockfile` | pnpm 的等价方式（CI 环境默认开启） |

**CI 中必须使用** `npm ci` / `--frozen-lockfile`。锁文件必须提交到仓库。

**口述模板（30–60 秒）**

1. 一句话结论：锁文件记录所有依赖的确切版本和完整性哈希，保证安装结果一致。
2. 关键机制：npm ci 严格按锁文件安装，不一致时报错。
3. 对比或注意点：npm install 可能更新锁文件，CI 中应该使用 npm ci。
4. 可追问时补充：锁文件也是供应链安全的基础，防止自动安装到新发布的恶意版本。

**常见追问**

- 锁文件冲突怎么解决？→ 不要手动合并；以一方为基础重新运行安装，让包管理器重新生成。

### Q4. 语义化版本（semver）是什么？`^` 和 `~` 的区别？

- **难度**: 初级
- **标签**: semver

**答案**

格式：`主版本.次版本.修订版本`（`MAJOR.MINOR.PATCH`）

- 主版本：不兼容的修改
- 次版本：向后兼容的新功能
- 修订版本：向后兼容的问题修复
- 预发布：`2.0.0-beta.1`

| 范围 | 含义 | 例子 |
|------|------|------|
| `^1.2.3` | 不修改**最左边的非零位** | `>=1.2.3 <2.0.0` |
| `^0.2.3` | 同上（0.x 时次版本视为主版本） | `>=0.2.3 <0.3.0` |
| `~1.2.3` | 只允许修订版本变化 | `>=1.2.3 <1.3.0` |
| `1.2.3` | 精确版本 | |

**口述模板（30–60 秒）**

1. 一句话结论：semver 用主、次、修订三段表示不兼容修改、新功能和问题修复。
2. 关键机制：^ 允许不修改最左非零位的升级，~ 只允许修订版本升级。
3. 对比或注意点：0.x 版本中 ^ 只允许修订版本变化。
4. 可追问时补充：semver 是约定，不是保证，所以需要锁文件。

**常见追问**

- 为什么有了 semver 还需要锁文件？→ 维护者可能在次版本中引入破坏性修改或恶意代码；锁文件保证安装的是经过验证的版本。

### Q5. dependencies、devDependencies、peerDependencies 有什么区别？

- **难度**: 初级
- **标签**: 包管理

**答案**

| 类型 | 含义 | 场景 |
|------|------|------|
| `dependencies` | 运行时需要 | 应用：React；库：运行时用到的工具 |
| `devDependencies` | 只在开发和构建时需要 | 构建工具、测试框架、类型定义 |
| `peerDependencies` | **由使用方提供**，库只声明兼容的版本范围 | React 组件库声明 `react` |
| `optionalDependencies` | 安装失败也不影响 | 平台相关的原生模块 |

**对于前端应用**：最终都会被打包，区分主要用于语义和 SSR / Node 部署时的安装范围。

**对于库**：`dependencies` 会被使用方安装；React 这类框架必须放在 `peerDependencies`，否则可能安装两份（多实例导致 Hooks 报错）。

**口述模板（30–60 秒）**

1. 一句话结论：dependencies 是运行时依赖，devDependencies 是开发依赖，peerDependencies 由使用方提供。
2. 关键机制：库把框架声明为 peerDependencies，避免安装多个实例。
3. 对比或注意点：前端应用最终都会被打包，区分主要用于语义和服务端部署。
4. 可追问时补充：React 多实例会导致 Hooks 报错。

**常见追问**

- `overrides` / `resolutions` 是做什么的？→ 强制指定间接依赖的版本，常用于修复安全漏洞或兼容问题。

## 二、Monorepo

### Q6. 什么是 Monorepo？和 Polyrepo 相比有什么优缺点？

- **难度**: 初级
- **标签**: Monorepo

**答案**

**Monorepo**：多个项目（应用、库）放在**一个仓库**中；**Polyrepo**：每个项目一个仓库。

| 方面 | Monorepo | Polyrepo |
|------|----------|----------|
| 代码共享 | 直接引用，修改即时生效 | 发布 npm 包后再升级 |
| 原子提交 | 一次提交修改多个项目 | 跨仓库协调 |
| 依赖版本 | 容易统一 | 容易不一致 |
| 规范和工具 | 统一配置 | 每个仓库各自维护 |
| 构建和 CI | **需要工具优化**（缓存、受影响分析） | 天然隔离 |
| 权限 | 粒度粗（需要 CODEOWNERS） | 按仓库控制 |
| 仓库体积 | 大 | 小 |

**Monorepo 不等于单体应用**：项目之间仍然有清晰的边界，可以独立构建和部署。

**口述模板（30–60 秒）**

1. 一句话结论：Monorepo 是把多个项目放在一个仓库中管理。
2. 关键机制：好处是代码共享、原子提交、依赖和规范统一。
3. 对比或注意点：代价是需要工具优化构建和 CI，权限控制粒度较粗。
4. 可追问时补充：Monorepo 不等于单体应用，项目之间仍有边界，可以独立部署。

**常见追问**

- 什么情况下不适合 Monorepo？→ 项目之间毫无关联、需要严格的权限隔离（外包团队）、技术栈完全不同且没有共享代码。

### Q7. 怎么用 pnpm 搭建一个 Monorepo？

- **难度**: 初级
- **标签**: Monorepo, pnpm

**答案**

```yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'

catalog:              # 统一的依赖版本
  react: ^19.2.0
  typescript: ^5.9.0
```

```json
// apps/web/package.json
{
  "name": "@acme/web",
  "dependencies": {
    "@acme/ui": "workspace:*",
    "react": "catalog:"
  }
}
```

常用命令：

```bash
pnpm install                          # 安装所有工作区
pnpm --filter @acme/web dev           # 在指定包中执行
pnpm --filter "@acme/web..." build    # 包含它依赖的包
pnpm -r build                         # 所有包（按拓扑顺序）
pnpm add zod --filter @acme/api
```

- `workspace:*`：引用工作区内的包，发布时被替换为实际版本号
- `catalog:`：引用 `pnpm-workspace.yaml` 中统一定义的版本

**口述模板（30–60 秒）**

1. 一句话结论：用 pnpm-workspace.yaml 声明工作区，用 workspace 协议引用内部包。
2. 关键机制：--filter 在指定的包中执行命令，-r 按拓扑顺序在所有包中执行。
3. 对比或注意点：catalog 统一管理依赖版本。
4. 可追问时补充：发布时 workspace 协议会被替换为实际版本号。

**常见追问**

- 只用 pnpm workspace 够吗？→ 小型仓库够用；项目多了以后需要 Turborepo / Nx 提供缓存和受影响分析。

### Q8. Turborepo 是什么？怎么配置？

- **难度**: 初级
- **标签**: Turborepo

**答案**

Turborepo 是 Monorepo 的**任务编排和缓存工具**：根据包的依赖关系并行执行任务，并缓存结果。

```json
// turbo.json
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],         // 先构建依赖的包
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
    },
    "test": { "dependsOn": ["build"] },
    "lint": {},
    "dev": { "cache": false, "persistent": true }
  }
}
```

```bash
turbo run build                 # 构建所有包，命中缓存的直接跳过
turbo run build --filter=web... # web 及其依赖
turbo run test --affected       # 只运行受影响的包
```

- `^build`：**依赖的包**的 build 先执行
- `outputs`：需要缓存的产物
- 缓存命中时恢复产物和日志，几乎瞬间完成

**口述模板（30–60 秒）**

1. 一句话结论：Turborepo 根据依赖关系并行执行任务并缓存结果。
2. 关键机制：dependsOn 的 ^build 表示先构建依赖的包，outputs 声明要缓存的产物。
3. 对比或注意点：缓存命中时恢复产物和日志，不再执行。
4. 可追问时补充：配合远程缓存，团队成员和 CI 可以共享缓存。

**常见追问**

- `dependsOn: ["build"]` 和 `["^build"]` 的区别？→ 前者是同一个包中的 build 任务先执行，后者是依赖的包的 build 任务先执行。

### Q9. Nx 是什么？和 Turborepo 有什么区别？

- **难度**: 初级
- **标签**: Nx

**答案**

| 方面 | Turborepo | Nx |
|------|-----------|-----|
| 定位 | 任务编排 + 缓存，**轻量** | **完整的 Monorepo 平台** |
| 配置 | 少 | 多（可以渐进采用） |
| 缓存 | 本地 + 远程 | 本地 + 远程 |
| 受影响分析 | 支持 | 支持（基于项目图，更细） |
| 代码生成器 | 无 | 有（创建库、组件的规范） |
| 模块边界规则 | 无内置 | 有（基于标签的 ESLint 规则） |
| 分布式执行 | 无 | 有（把任务分发到多台机器） |
| 框架插件 | 无 | 丰富（React、Angular、Next.js、Node） |
| 学习成本 | 低 | 中高 |

**选型**：中小规模、希望简单 → Turborepo；大型组织、需要强约束和分布式执行 → Nx。

**口述模板（30–60 秒）**

1. 一句话结论：Turborepo 专注任务编排和缓存，Nx 是完整的 Monorepo 平台。
2. 关键机制：Nx 额外提供代码生成器、模块边界规则和分布式执行。
3. 对比或注意点：Turborepo 配置少、学习成本低，Nx 能力强但更复杂。
4. 可追问时补充：常见路径是先用 Turborepo，规模变大后再引入 Nx。

**常见追问**

- Lerna 还在用吗？→ Lerna 现在由 Nx 团队维护，底层使用 Nx 的任务执行；新项目通常直接选择 Turborepo / Nx + Changesets。

### Q10. Monorepo 中的包怎么发布？Changesets 怎么用？

- **难度**: 初级
- **标签**: 发布, Changesets

**答案**

**Changesets 的流程**：

```bash
pnpm changeset            # 1. 开发者描述本次修改：影响哪些包、升级类型（major/minor/patch）、说明
                          #    生成 .changeset/xxx.md，随 PR 提交
pnpm changeset version    # 2. 发布前：消费 changeset，更新版本号、依赖它的包的版本、生成 CHANGELOG
pnpm changeset publish    # 3. 发布到 npm，打 Git 标签
```

CI 中通常使用 Changesets 的 GitHub Action：自动创建「版本发布 PR」，合并后自动发布。

**版本策略**：

- **独立版本**（默认）：每个包独立升级
- **固定版本**（`fixed`）：一组包始终相同版本（如 `@babel/*`）
- **关联版本**（`linked`）：一组包中升级的包使用相同的版本号

**口述模板（30–60 秒）**

1. 一句话结论：Changesets 让开发者在 PR 中描述修改，发布时统一更新版本和生成 CHANGELOG。
2. 关键机制：changeset 记录影响的包和升级类型，version 命令更新版本，publish 发布。
3. 对比或注意点：支持独立版本和固定版本两种策略。
4. 可追问时补充：CI 中自动创建版本发布 PR，合并后自动发布。

**常见追问**

- 内部依赖的包升级后，依赖它的包怎么处理？→ Changesets 会自动更新依赖方的依赖版本，并根据配置给依赖方升级修订版本。

## 三、代码质量

### Q11. ESLint 和 Prettier 怎么配合？flat config 是什么？

- **难度**: 初级
- **标签**: 代码规范

**答案**

- **ESLint**：发现代码中的问题（潜在 bug、不规范的写法）
- **Prettier**：只负责格式（缩进、换行、引号）
- **分工**：关闭 ESLint 中与格式相关的规则（`eslint-config-prettier`），格式交给 Prettier

**flat config**（ESLint 9 起默认）：用 `eslint.config.js` 导出配置数组，取代 `.eslintrc`：

```js
// eslint.config.js
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import prettier from 'eslint-config-prettier';

export default [
  js.configs.recommended,
  ...tseslint.configs.recommended,
  { files: ['**/*.{ts,tsx}'], rules: { 'no-console': 'warn' } },
  prettier,
];
```

**替代方案**：Biome（Rust 实现的 Lint + 格式化一体工具，速度快）、oxlint。

**口述模板（30–60 秒）**

1. 一句话结论：ESLint 负责发现代码问题，Prettier 负责格式。
2. 关键机制：用 eslint-config-prettier 关闭格式相关的规则，避免冲突。
3. 对比或注意点：ESLint 9 起默认 flat config，用配置数组代替 .eslintrc。
4. 可追问时补充：Biome 和 oxlint 是更快的替代方案。

**常见追问**

- Monorepo 中怎么共享 ESLint 配置？→ 创建一个内部包（`@acme/eslint-config`）导出配置，各包引用并按需扩展。

### Q12. Git Hooks 怎么用？husky 和 lint-staged 分别做什么？

- **难度**: 初级
- **标签**: Git Hooks

**答案**

- **husky**：管理 Git Hooks（`pre-commit`、`commit-msg`、`pre-push`）
- **lint-staged**：只对**暂存区的文件**运行检查（速度快）
- **commitlint**：校验提交信息格式

```json
// package.json
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,md,css}": ["prettier --write"]
  }
}
```

```bash
# .husky/pre-commit
pnpm lint-staged
# .husky/commit-msg
pnpm commitlint --edit "$1"
```

**注意**：本地 Hooks 可以被 `--no-verify` 跳过，**CI 中必须再次检查**。

**口述模板（30–60 秒）**

1. 一句话结论：husky 管理 Git Hooks，lint-staged 只检查暂存区的文件。
2. 关键机制：提交前自动修复和格式化，提交信息由 commitlint 校验。
3. 对比或注意点：本地 Hooks 可以被跳过，CI 中必须再次检查。
4. 可追问时补充：类型检查通常放在 CI 中，因为需要检查整个项目。

**常见追问**

- 为什么不在 pre-commit 中跑完整的测试和类型检查？→ 太慢，影响提交体验；放到 pre-push 或 CI 中。

### Q13. Conventional Commits 是什么？有什么用？

- **难度**: 初级
- **标签**: Git, 规范

**答案**

提交信息格式：`<类型>(<范围>): <描述>`

```text
feat(cart): 支持批量删除商品
fix(auth): 修复刷新令牌并发时重复请求的问题
refactor(ui): 抽取 Table 组件的分页逻辑
feat(api)!: 删除旧的订单接口         # ! 表示破坏性修改

BREAKING CHANGE: /v1/orders 已移除，请使用 /v2/orders
```

常用类型：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`

**用途**：

- 历史清晰，便于评审和追溯
- **自动生成 CHANGELOG**
- **自动确定版本号**（semantic-release：`fix` → patch，`feat` → minor，破坏性 → major）

**口述模板（30–60 秒）**

1. 一句话结论：Conventional Commits 规定提交信息的格式为类型、范围和描述。
2. 关键机制：类型表示修改的性质，感叹号或 BREAKING CHANGE 表示破坏性修改。
3. 对比或注意点：可以据此自动生成 CHANGELOG 和确定版本号。
4. 可追问时补充：用 commitlint 在提交时校验格式。

**常见追问**

- 合并 PR 时用 squash 还是 merge？→ squash 让主干每个提交对应一个 PR，历史清晰，PR 标题按规范书写即可。

### Q14. 常见的 Git 分支策略有哪些？

- **难度**: 初级
- **标签**: Git

**答案**

| 策略 | 说明 | 适合 |
|------|------|------|
| **Git Flow** | `main`、`develop`、`feature/*`、`release/*`、`hotfix/*` | 按版本发布的产品（客户端、SDK） |

**口述模板（30–60 秒）**

1. 一句话结论：常见的有 Git Flow、GitHub Flow 和主干开发。
2. 关键机制：Git Flow 分支多适合按版本发布，GitHub Flow 和主干开发适合持续部署。
3. 对比或注意点：长期分支会带来大量合并冲突。
4. 可追问时补充：主干开发需要特性开关隐藏未完成的功能，以及可靠的 CI。

**常见追问**

- 特性开关有什么风险？→ 开关积累导致代码复杂，需要定期清理已全量的开关。

## 四、CI/CD 与部署

### Q15. CI、CD（持续交付）、CD（持续部署）有什么区别？

- **难度**: 初级
- **标签**: CI/CD

**答案**

| 概念 | 含义 |
|------|------|
| **持续集成（CI）** | 频繁合并代码，每次合并自动构建和测试，尽早发现问题 |
| **持续交付（Continuous Delivery）** | 代码随时处于**可发布**状态，发布到生产需要**人工确认** |
| **持续部署（Continuous Deployment）** | 通过所有检查后**自动发布**到生产 |

**口述模板（30–60 秒）**

1. 一句话结论：CI 是频繁合并并自动构建测试，持续交付是随时可发布，持续部署是自动发布到生产。
2. 关键机制：区别在于发布到生产是否需要人工确认。
3. 对比或注意点：持续部署要求有足够的自动化测试、灰度和监控。
4. 可追问时补充：多数团队采用持续交付，关键业务保留人工审批。

**常见追问**

- 持续部署需要什么前提？→ 可靠的自动化测试、灰度发布、完善的监控和告警、快速回滚。

### Q16. GitHub Actions 的基本概念和一个前端 CI 示例？

- **难度**: 初级
- **标签**: GitHub Actions

**答案**

**概念**：Workflow（工作流，`.github/workflows/*.yml`）→ Job（作业，默认并行，在独立的运行器上）→ Step（步骤，执行命令或使用 Action）；Trigger（`on`：push、pull_request、schedule 等）。

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read          # 最小权限

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm                     # 缓存 pnpm 存储
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo run lint typecheck test build --affected
```

**口述模板（30–60 秒）**

1. 一句话结论：GitHub Actions 由工作流、作业和步骤组成，由事件触发。
2. 关键机制：作业默认并行，在独立的运行器上执行；步骤执行命令或使用 Action。
3. 对比或注意点：要设置最小权限，第三方 Action 应该固定到提交 SHA。
4. 可追问时补充：配合依赖缓存和任务缓存加速。

**常见追问**

- 为什么要设置 `permissions`？→ `GITHUB_TOKEN` 的默认权限可能较大，被攻破的步骤可以用它修改仓库；按需授予最小权限。

### Q17. 一个典型的前端 CI/CD 流水线包含哪些阶段？

- **难度**: 初级
- **标签**: CI/CD

**答案**

```text
PR 阶段（CI）：
  安装依赖（锁文件、缓存）
  → 并行：Lint / 类型检查 / 单元测试（只跑受影响的）
  → 构建
  → 预览环境部署 + E2E 冒烟测试
  → 代码评审

合并到主干后（CD）：
  构建产物（一次构建）
  → 部署到测试 / 预发环境
  → 自动化测试
  → 审批（持续交付）
  → 生产：灰度 → 观察指标 → 全量
  → 失败时回滚
```

**原则**：

- **快速失败**：便宜的检查先执行
- **构建一次，多处部署**：同一个产物部署到不同环境
- 每个阶段都有明确的通过标准

**口述模板（30–60 秒）**

1. 一句话结论：PR 阶段做安装、检查、测试、构建和预览，合并后部署到测试环境、审批、灰度发布。
2. 关键机制：检查并行执行，只跑受影响的部分。
3. 对比或注意点：快速失败，构建一次多处部署。
4. 可追问时补充：生产发布先灰度再全量，失败时回滚。

**常见追问**

- 为什么要「构建一次」？→ 不同环境重新构建可能产生不同的产物（依赖、环境），测试过的不一定是发布的。

### Q18. 前端静态资源怎么部署？缓存策略是什么？

- **难度**: 初级
- **标签**: 部署, 缓存

**答案**

**缓存策略**：

| 资源 | 文件名 | 缓存 |
|------|--------|------|
| JS、CSS、图片、字体 | **带内容哈希**（`app.3f9a2c.js`） | `Cache-Control: public, max-age=31536000, immutable` |
| `index.html` | 固定 | `Cache-Control: no-cache`（每次协商）|

内容变化 → 哈希变化 → 文件名变化 → 自然绕过缓存。

**发布顺序**：

1. **先上传新的静态资源**（与旧的共存，不删除旧文件）
2. **再更新 HTML**（入口切换到新版本）
3. 旧版本的资源保留一段时间（正在使用旧页面的用户还会懒加载旧的代码块）

如果顺序反了：HTML 引用了还没上传的资源 → 白屏。

**口述模板（30–60 秒）**

1. 一句话结论：带内容哈希的资源长期缓存，HTML 不缓存。
2. 关键机制：内容变化导致文件名变化，自然绕过缓存。
3. 对比或注意点：先上传新资源再切换 HTML，旧资源保留一段时间。
4. 可追问时补充：顺序反了会导致白屏，删除旧资源会导致懒加载失败。

**常见追问**

- 为什么不用 `?v=版本号` 的方式？→ 一些 CDN 和代理忽略查询参数；所有文件共用一个版本号，任何修改都会让全部缓存失效。

### Q19. 常见的发布策略有哪些？

- **难度**: 初级
- **标签**: 发布策略

**答案**

| 策略 | 说明 | 优缺点 |
|------|------|--------|
| **滚动发布** | 逐步替换实例 | 资源省；新旧版本共存一段时间 |
| **蓝绿发布** | 两套环境，切换流量 | 切换和回滚快；资源翻倍 |
| **金丝雀 / 灰度** | 先让小部分用户使用新版本，观察指标后逐步放量 | 风险小；需要路由和监控能力 |
| **特性开关** | 代码已部署，功能通过开关控制 | 发布和上线解耦；需要管理开关 |
| **A/B 测试** | 不同用户看到不同版本，比较业务指标 | 用于产品决策 |

**前端的特殊性**：静态资源部署在 CDN，灰度需要在**入口（HTML）层面**按用户分流。

**口述模板（30–60 秒）**

1. 一句话结论：常见的有滚动、蓝绿、金丝雀灰度和特性开关。
2. 关键机制：灰度先让小部分用户使用新版本，观察指标后逐步放量。
3. 对比或注意点：特性开关让部署和上线解耦。
4. 可追问时补充：前端灰度需要在 HTML 入口层面按用户分流。

**常见追问**

- 前端灰度时，同一个用户刷新页面版本会变吗？→ 应该按用户 ID 或 Cookie 固定分桶，保证同一用户看到同一版本。

### Q20. 前端发布后出了问题，怎么回滚？

- **难度**: 初级
- **标签**: 回滚

**答案**

**静态资源的回滚**：因为所有版本的资源都保留着，回滚只需要**把 HTML 切回旧版本**（或把入口指向旧的版本目录），秒级生效。

```text
/assets/app.v1hash.js   # 保留
/assets/app.v2hash.js   # 新版本
index.html → 引用 v2  ──回滚──► 引用 v1
```

**SSR 服务**：切回旧版本的镜像（Kubernetes 回滚 Deployment）。

**要点**：

- 回滚应该是**一键、无需重新构建**的操作
- HTML 的 CDN 缓存要刷新（或本身不缓存）
- 回滚不能解决数据问题（如果新版本写入了不兼容的数据，需要数据修复）
- 接口变更要向后兼容，保证前端可以独立回滚

**口述模板（30–60 秒）**

1. 一句话结论：静态资源回滚就是把 HTML 入口切回旧版本，秒级生效。
2. 关键机制：所有版本的资源都保留着，不需要重新构建。
3. 对比或注意点：HTML 的 CDN 缓存要刷新，SSR 服务回滚镜像。
4. 可追问时补充：接口要向后兼容，前端才能独立回滚。

**常见追问**

- 为什么回滚不应该重新构建？→ 构建耗时长，而且重新构建的产物可能与之前的不同。

### Q21. 不同环境的配置怎么管理？

- **难度**: 初级
- **标签**: 配置

**答案**

| 方式 | 说明 | 问题 |
|------|------|------|
| 构建时注入（`import.meta.env.VITE_API_URL`） | 每个环境构建一次 | 违背「构建一次，多处部署」 |
| **运行时配置** | 部署时生成 `config.json` 或注入到 HTML（`window.__CONFIG__`），应用启动时读取 | 推荐 |
| 配置中心 | 从远程获取配置，支持动态修改 | 复杂度高 |

**注意**：

- 前端的配置**都是公开的**，不能放任何密钥
- 构建时的环境变量只有特定前缀（`VITE_`、`NEXT_PUBLIC_`）会被注入到客户端代码

**口述模板（30–60 秒）**

1. 一句话结论：推荐运行时配置，部署时注入配置，同一个产物用于所有环境。
2. 关键机制：应用启动时读取 config.json 或 HTML 中注入的配置。
3. 对比或注意点：构建时注入需要每个环境构建一次。
4. 可追问时补充：前端配置都是公开的，不能放密钥。

**常见追问**

- 运行时配置会影响首屏吗？→ 注入到 HTML 中的配置没有额外请求；单独请求 `config.json` 会增加一次往返，可以与其他资源并行。

### Q22. CI 中的密钥怎么管理？

- **难度**: 初级
- **标签**: 安全, 密钥

**答案**

- 存在 CI 平台的**加密密钥**中（GitHub Secrets），按环境区分（Environment secrets，配合审批）
- **不要**写入代码、日志、构建产物
- **优先使用 OIDC**：CI 用短期令牌访问云服务和 npm，不需要保存长期密钥
- 最小权限：每个密钥只授予需要的权限
- fork 的 PR 不能访问密钥（默认如此，不要用 `pull_request_target` 绕过）
- 定期轮换；泄露后立即吊销

**口述模板（30–60 秒）**

1. 一句话结论：密钥存在 CI 平台的加密存储中，按环境区分，不能出现在代码和日志中。
2. 关键机制：优先使用 OIDC 获取短期令牌，代替长期密钥。
3. 对比或注意点：fork 的 PR 不能访问密钥，不要用 pull_request_target 绕过。
4. 可追问时补充：最小权限、定期轮换，泄露后立即吊销。

**常见追问**

- 密钥被打印到日志中怎么办？→ GitHub 会自动遮盖已注册的密钥，但经过编码（base64）后不会被识别；发现泄露立即轮换。

### Q23. 什么是预览环境？

- **难度**: 初级
- **标签**: CI/CD

**答案**

每个 PR 自动部署一个**独立的临时环境**（如 `pr-123.preview.example.com`），用于：

- 产品、设计、测试在合并前验收
- 运行 E2E 测试
- PR 关闭后自动销毁

**实现**：静态站点部署到对象存储的独立路径或 Vercel / Netlify 等平台；SSR 应用部署到临时的容器。

**注意**：预览环境连接的后端（测试环境 / 模拟数据）；访问控制（不要公开内部功能）；不使用生产数据和密钥。

**口述模板（30–60 秒）**

1. 一句话结论：预览环境是每个 PR 自动部署的临时环境，用于合并前验收。
2. 关键机制：PR 更新时重新部署，关闭后自动销毁。
3. 对比或注意点：要做访问控制，不能使用生产数据和密钥。
4. 可追问时补充：E2E 测试可以在预览环境上运行。

**常见追问**

- 预览环境的成本怎么控制？→ 静态站点成本很低；SSR 应用可以按需启动、空闲时休眠，并设置自动过期。

## 五、微前端

### Q24. 什么是微前端？什么时候需要微前端？

- **难度**: 初级
- **标签**: 微前端

**答案**

微前端把一个大型前端应用**拆分为多个可以独立开发、独立部署的子应用**，在运行时组合。

**适合的场景**：

- 多个团队维护同一个产品，需要**独立发布**
- **技术栈异构**：老系统（jQuery / AngularJS）和新系统共存，渐进迁移
- 平台型产品，需要集成第三方或其他团队的应用

**不适合的场景**：

- 一个团队、一个技术栈 → Monorepo + 模块化就够了
- 只是想「拆代码」 → 路由懒加载

**代价**：复杂度、性能（重复依赖、多个框架实例）、一致性（样式、交互）、调试困难。

**口述模板（30–60 秒）**

1. 一句话结论：微前端把大型应用拆为多个独立开发、独立部署的子应用，在运行时组合。
2. 关键机制：适合多团队独立发布、技术栈异构、渐进迁移老系统。
3. 对比或注意点：一个团队一个技术栈时用 Monorepo 加懒加载就够了。
4. 可追问时补充：代价是复杂度、性能开销和体验一致性。

**常见追问**

- 微前端的本质是什么？→ 组织问题的技术解法：让团队可以自治（独立开发、测试、部署）。

### Q25. 微前端有哪些实现方案？

- **难度**: 初级
- **标签**: 微前端

**答案**

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **iframe** | 每个子应用一个 iframe | 天然的完全隔离 | 体验差（弹窗、路由、尺寸、性能）、通信麻烦 |
| **single-spa** | 按路由加载子应用，生命周期管理 | 灵活 | 只做调度，没有隔离 |
| **qiankun** | 基于 single-spa + HTML Entry + JS 沙箱 + 样式隔离 | 开箱即用、生态成熟 | 沙箱不是安全边界；Vite（ESM）支持需要插件 |
| **wujie** | iframe 运行 JS + Web Components 渲染 DOM | 隔离彻底、改造成本低、支持保活 | iframe 和代理的开销 |
| **micro-app** | Web Components 风格的接入 | 接入简单 | 隔离不如 iframe |
| **Module Federation** | 构建工具层面的模块共享，运行时加载远程模块 | 共享依赖、粒度细（组件级） | 需要构建工具支持，没有隔离 |
| Web Components | 子应用打包为自定义元素 | 标准、框架无关 | 需要改造 |

**口述模板（30–60 秒）**

1. 一句话结论：常见方案有 iframe、qiankun、wujie、micro-app 和 Module Federation。
2. 关键机制：qiankun 通过 HTML Entry、JS 沙箱和样式隔离加载子应用；Module Federation 在模块层面共享代码。
3. 对比或注意点：iframe 隔离最彻底但体验差；qiankun 生态成熟；wujie 隔离更好。
4. 可追问时补充：Module Federation 适合同技术栈的组件级共享，qiankun 类方案适合应用级集成。

**常见追问**

- 为什么不直接用 iframe？→ 弹窗无法覆盖整个页面、URL 不同步、刷新丢失状态、每个 iframe 重新加载资源、通信只能用 postMessage。

### Q26. qiankun 接入子应用需要做什么？

- **难度**: 初级
- **标签**: qiankun

**答案**

**主应用**：

```ts
import { registerMicroApps, start } from 'qiankun';

registerMicroApps([
  { name: 'orders', entry: '//orders.example.com', container: '#subapp', activeRule: '/orders' },
]);
start({ sandbox: { experimentalStyleIsolation: true } });
```

**子应用**：

1. 导出生命周期：`bootstrap`、`mount`、`unmount`（可选 `update`）
2. 支持独立运行（判断 `window.__POWERED_BY_QIANKUN__`）
3. 设置 `publicPath`（`__webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__`），否则资源路径错误
4. 打包为 UMD 格式（库名与注册的 `name` 一致）
5. 路由的 base 设置为 `activeRule`
6. 子应用服务器允许跨域（主应用通过 fetch 获取子应用的资源）
7. `unmount` 中彻底清理（卸载框架实例、全局监听、定时器）

**口述模板（30–60 秒）**

1. 一句话结论：主应用注册子应用并启动，子应用导出生命周期函数。
2. 关键机制：子应用需要设置 publicPath、打包为 UMD、配置路由 base。
3. 对比或注意点：子应用的资源服务器要允许跨域。
4. 可追问时补充：unmount 中要彻底清理，避免内存泄漏和副作用残留。

**常见追问**

- 为什么子应用的资源服务器要允许跨域？→ qiankun 通过 fetch 获取子应用的 HTML 和脚本，然后在沙箱中执行。

### Q27. Module Federation 是什么？

- **难度**: 初级
- **标签**: Module Federation

**答案**

Module Federation（Webpack 5 引入，2.0 已与构建工具解耦）让一个应用在**运行时加载另一个应用暴露的模块**，并**共享依赖**。

```js
// 远程应用（提供方）
new ModuleFederationPlugin({
  name: 'orders',
  filename: 'remoteEntry.js',
  exposes: { './OrderList': './src/OrderList' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

// 宿主应用（使用方）
new ModuleFederationPlugin({
  name: 'shell',
  remotes: { orders: 'orders@https://orders.example.com/remoteEntry.js' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});
```

```tsx
const OrderList = lazy(() => import('orders/OrderList'));
```

**特点**：模块级（组件级）的共享；依赖可以共享，避免重复加载；**没有隔离**（同一个运行环境）。

**口述模板（30–60 秒）**

1. 一句话结论：Module Federation 让应用在运行时加载其他应用暴露的模块并共享依赖。
2. 关键机制：提供方通过 exposes 暴露模块，使用方通过 remotes 引用。
3. 对比或注意点：shared 配置共享依赖，React 这类库要设置为单例。
4. 可追问时补充：2.0 与构建工具解耦，支持 Rspack、Vite 等。

**常见追问**

- 和 npm 包有什么区别？→ npm 包是构建时集成，更新需要重新构建使用方；Module Federation 是运行时加载，提供方发布后使用方立即生效。

### Q28. 微前端的样式隔离有哪些方式？

- **难度**: 初级
- **标签**: 微前端, 样式

**答案**

| 方式 | 原理 | 问题 |
|------|------|------|
| **命名约定** | BEM、子应用前缀 | 依赖自觉 |
| **CSS Modules / CSS-in-JS** | 构建时生成唯一类名 | 全局样式和第三方库样式仍会冲突 |
| **作用域 CSS（qiankun 的 experimentalStyleIsolation）** | 给子应用的样式规则加上前缀选择器（`div[data-qiankun="orders"] .btn`） | 运行时改写有开销；挂载到 body 的弹窗不在容器中 |
| **Shadow DOM（strictStyleIsolation / wujie）** | 浏览器原生的样式隔离 | 弹窗挂到 body 时脱离 Shadow DOM；部分第三方库不兼容；事件和字体问题 |
| **iframe** | 完全隔离 | 体验问题 |

**弹窗问题**：组件库的弹窗、下拉通常挂载到 `document.body`，脱离子应用的容器 → 样式丢失。解决：把弹窗的挂载点配置到子应用的容器内。

**口述模板（30–60 秒）**

1. 一句话结论：样式隔离有命名约定、CSS Modules、作用域 CSS、Shadow DOM 和 iframe。
2. 关键机制：作用域 CSS 给子应用的样式加前缀选择器，Shadow DOM 是浏览器原生隔离。
3. 对比或注意点：弹窗挂载到 body 会脱离子应用容器，导致样式丢失。
4. 可追问时补充：要把组件库弹窗的挂载点配置到子应用容器内。

**常见追问**

- 主应用的全局样式影响子应用怎么办？→ 主应用也要约束全局样式（重置样式统一由主应用提供），子应用不写全局样式。

### Q29. 主应用和子应用之间怎么通信？

- **难度**: 初级
- **标签**: 微前端, 通信

**答案**

| 方式 | 说明 |
|------|------|
| **props** | 主应用在挂载时把数据和方法传给子应用（用户信息、令牌获取函数、跳转方法） |
| **全局状态**（qiankun 的 `initGlobalState`） | 主应用和子应用共享一个状态对象，订阅变化 |
| **事件总线**（CustomEvent） | 发布 / 订阅 |
| **URL** | 路由参数、查询参数 |
| **共享模块**（Module Federation） | 共享同一个 Store 实例 |
| postMessage | iframe 方案 |

**原则**：

- **尽量少通信**：子应用应该高内聚，大量通信说明拆分边界不合理
- 定义**明确的契约**（事件名、数据结构、版本）
- 主应用只下发通用能力（用户、权限、导航），不暴露内部状态

**口述模板（30–60 秒）**

1. 一句话结论：常用 props、全局状态、事件总线和 URL 通信。
2. 关键机制：主应用通过 props 下发用户信息和通用方法。
3. 对比或注意点：应该尽量少通信，大量通信说明拆分边界不合理。
4. 可追问时补充：通信要有明确的契约和版本。

**常见追问**

- 子应用需要调用主应用的跳转怎么办？→ 主应用通过 props 提供跳转方法，或者子应用修改 URL 由主应用的路由处理。

### Q30. 微前端和 Monorepo 是什么关系？怎么选？

- **难度**: 初级
- **标签**: 微前端, Monorepo

**答案**

**两者解决的问题不同，可以组合使用**：

| 方面 | Monorepo | 微前端 |
|------|----------|--------|
| 层面 | **代码组织**（仓库） | **运行时集成**（部署） |
| 解决 | 代码共享、统一规范、原子提交 | 独立部署、技术栈异构 |
| 发布 | 可以统一发布，也可以独立部署 | 独立发布 |

**组合**：在一个 Monorepo 中管理主应用、子应用和共享库，享受统一的工具链；子应用独立部署。

**选择**：

- 团队只是协作不方便 → Monorepo + 模块边界
- 必须独立发布 / 技术栈异构 / 渐进迁移 → 微前端（可以放在 Monorepo 中）

**口述模板（30–60 秒）**

1. 一句话结论：Monorepo 解决代码组织问题，微前端解决运行时集成和独立部署问题。
2. 关键机制：两者可以组合，在一个 Monorepo 中管理主应用和子应用。
3. 对比或注意点：只是协作问题时 Monorepo 就够了，不需要微前端。
4. 可追问时补充：需要独立发布或技术栈异构时才引入微前端。

**常见追问**

- 为什么说很多团队「不需要微前端」？→ 微前端的运行时成本（性能、复杂度、一致性）很高，很多问题用 Monorepo + 懒加载 + 模块边界就能解决。
