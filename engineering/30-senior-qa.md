# 前端工程化高级 Q&A

> 目标：能为团队从零设计和落地工程化体系，能处理大规模 Monorepo、CI/CD 供应链安全、发布平台与灰度、微前端治理等问题，能度量研发效能并说清投入产出。

---

## 一、体系建设

### Q1. 如何从零为一个 50 人的前端团队建设工程化体系？

- **难度**: 高级
- **标签**: 体系建设

**答案**

**先诊断，再分阶段**：

```text
1. 诊断（2 周）
   - 现状：项目数量、技术栈、仓库结构、构建和 CI 耗时、发布频率、线上故障
   - 痛点访谈：开发者最浪费时间的地方
   - 度量基线：DORA 指标、CI 时长、构建时长

2. 统一基础（1–2 个月）
   - 规范以包的形式共享：@acme/eslint-config、tsconfig、prettier
   - 脚手架：新项目开箱即用（CI、监控、安全头）
   - 依赖治理：锁文件、Renovate、私有仓库代理

3. 提效（2–3 个月）
   - Monorepo（相关性强的项目）+ 远程缓存 + 受影响分析
   - CI 优化：并行、分片、缓存
   - 组件库和业务组件沉淀

4. 交付（并行）
   - 统一的发布平台：构建一次、多环境部署、灰度、一键回滚
   - 监控：错误、性能、按版本对比

5. 运营
   - 效能看板、定期复盘
   - 工程化团队提供服务和支持，而不是只发布规范
```

**原则**：解决真实痛点；**默认正确**（工具内置规范）；渐进推进、先试点再推广；用数据证明收益。

**口述模板（30–60 秒）**

1. 一句话结论：先诊断现状和痛点，再分阶段统一基础、提效、建设交付能力。
2. 关键机制：规范以共享包的形式下发，脚手架默认内置规范和 CI。
3. 对比或注意点：先在一两个团队试点，用数据证明收益后再推广。
4. 可追问时补充：用 DORA 指标和 CI 时长等数据持续度量。

**常见追问**

- 业务团队不愿意配合怎么办？→ 先解决他们最痛的问题（例如 CI 太慢），让工程化成为帮助而不是负担；迁移成本由工程化团队承担（提供 codemod、协助迁移）。

### Q2. 怎么把几十个独立仓库迁移到 Monorepo？

- **难度**: 高级
- **标签**: Monorepo, 迁移

**答案**

**评估**：哪些项目适合合并（共享代码多、经常一起修改）？哪些不适合（独立的产品、权限隔离）？

**步骤**：

1. **搭建骨架**：pnpm workspace + Turborepo / Nx、统一的配置包、CI 模板
2. **保留历史迁移**：用 `git subtree` 或 `git filter-repo` 把仓库移入子目录，保留提交历史
3. **逐个迁移**（先从共享库开始，然后是依赖它们的应用）：
   - 依赖版本对齐（这是最费时的部分）
   - 内部依赖改为 `workspace:*`
   - 构建脚本统一为标准任务名（build、test、lint）
4. **CI 切换**：受影响分析 + 远程缓存；每个应用的部署流水线保持独立
5. **权限**：CODEOWNERS 按目录分配评审人；分支保护
6. **归档旧仓库**：设置为只读，README 指向新位置

**风险**：版本对齐引发的问题；CI 时间在缓存建立前变长；开发者习惯的改变。

**口述模板（30–60 秒）**

1. 一句话结论：先评估哪些项目适合合并，再搭建骨架并逐个迁移。
2. 关键机制：用 git subtree 或 filter-repo 保留历史，内部依赖改为 workspace 协议。
3. 对比或注意点：最费时的是依赖版本对齐。
4. 可追问时补充：用 CODEOWNERS 管理评审权限，部署流水线保持独立。

**常见追问**

- 迁移后仓库变得很大，clone 很慢怎么办？→ 部分克隆（`--filter=blob:none`）、稀疏检出（sparse checkout）、CI 中浅克隆配合主干引用。

### Q3. 大规模 Monorepo（上千个包）会遇到哪些性能问题？

- **难度**: 高级
- **标签**: Monorepo, 规模化

**答案**

| 问题 | 解决 |
|------|------|
| **Git 操作慢**（status、clone） | 部分克隆、稀疏检出、文件系统监控（`core.fsmonitor`）、Scalar |
| **安装慢** | pnpm（硬链接）、依赖缓存、CI 预装依赖的镜像 |
| **项目图计算慢** | 工具的守护进程缓存项目图（Nx daemon） |
| **TypeScript 慢**（IDE 卡顿、类型检查慢） | 项目引用 + 增量构建、拆分 tsconfig、避免巨大的联合类型；TS 原生编译器（tsgo） |
| **CI 时间长** | 受影响分析、远程缓存、**分布式任务执行**（Nx Agents）、分片 |
| **全局变更导致全部重建** | 精细化 `inputs`；减少全局依赖文件；锁文件变化时只影响相关包 |
| **代码评审的范围** | CODEOWNERS、自动分配评审人 |
| **依赖升级困难** | 自动化（Renovate）+ codemod + 分批 |

**口述模板（30–60 秒）**

1. 一句话结论：大规模 Monorepo 的瓶颈在 Git、安装、TypeScript 和 CI。
2. 关键机制：Git 用部分克隆和稀疏检出，TypeScript 用项目引用和增量构建。
3. 对比或注意点：CI 依赖受影响分析、远程缓存和分布式执行。
4. 可追问时补充：精细化 inputs，避免全局文件变化导致全部重建。

**常见追问**

- 分布式任务执行是什么？→ 把任务图中的任务分发到多台机器并行执行，按依赖关系调度，并共享缓存（Nx Agents 等）。

### Q4. 依赖升级怎么在大规模下持续进行？

- **难度**: 高级
- **标签**: 依赖治理

**答案**

**问题**：依赖长期不升级 → 漏洞积累、升级跨度越来越大、最终无法升级。

**体系**：

- **Renovate 自动化**：
  - 分组（同一个生态的包一起升级）
  - 补丁和次版本自动合并（测试通过后）
  - **最小发布时间**（新版本发布 N 天后才升级，规避恶意版本）
  - 安全更新优先、不受冷却期限制
  - 主版本单独的 PR，附带变更日志
- **主版本升级**由平台团队主导：codemod + 迁移指南 + 分批推进
- **度量**：落后的主版本数量、过期依赖比例、高危漏洞的修复时间
- **减少依赖**：定期清理未使用的依赖（knip）、用原生 API 替代小工具库

**口述模板（30–60 秒）**

1. 一句话结论：用 Renovate 自动化持续升级，主版本升级由平台团队用 codemod 推进。
2. 关键机制：分组升级、小版本测试通过后自动合并、设置最小发布时间。
3. 对比或注意点：安全更新优先，不受冷却期限制。
4. 可追问时补充：度量落后的主版本数量，定期清理未使用的依赖。

**常见追问**

- 自动合并安全吗？→ 前提是测试覆盖足够；配合最小发布时间降低恶意版本的风险；主版本不自动合并。

## 二、CI/CD 与发布

### Q5. CI/CD 的供应链安全怎么做？

- **难度**: 高级
- **标签**: 供应链, CI 安全

**答案**

**威胁**：被篡改的依赖或 Action、泄露的密钥、被篡改的构建产物、内部人员。

**防护分层**：

| 层次 | 措施 |
|------|------|
| **源码** | 分支保护、必须评审、签名提交、CODEOWNERS |
| **依赖** | 锁文件、禁止安装脚本、冷却期、私有代理仓库、SCA 扫描 |
| **CI 工作流** | 第三方 Action 固定 SHA；最小权限；避免 `pull_request_target` 执行不可信代码；输入不直接插值到脚本中；静态检查（zizmor） |
| **密钥** | OIDC 代替长期密钥；按环境区分并要求审批；安装依赖的步骤不能访问发布凭证 |
| **构建** | 一次性运行器、可复现构建 |
| **产物** | **provenance（来源证明）**和签名（SLSA）；npm 可信发布 |
| **部署** | 部署前验证产物签名；生产部署需要审批 |

**SLSA**：供应链完整性框架，按级别要求构建在受控平台上、生成不可伪造的来源证明。

**口述模板（30–60 秒）**

1. 一句话结论：CI/CD 供应链安全要覆盖源码、依赖、工作流、密钥、构建和产物各层。
2. 关键机制：Action 固定 SHA、最小权限、OIDC 代替长期密钥、产物生成来源证明。
3. 对比或注意点：安装依赖的步骤不能访问发布凭证。
4. 可追问时补充：用 SLSA 框架衡量供应链的成熟度。

**常见追问**

- 怎么证明线上的产物是从某个提交构建出来的？→ 构建时生成 provenance（记录源码提交、构建平台、构建参数）并签名，部署时验证。

### Q6. 设计一个前端的发布平台需要哪些能力？

- **难度**: 高级
- **标签**: 发布平台

**答案**

| 能力 | 说明 |
|------|------|
| 构建 | 统一的构建镜像、构建一次、产物不可变（按版本存储） |
| 多环境 | 测试 → 预发 → 生产；同一个产物，运行时注入配置 |
| **灰度** | 白名单、比例、地域、用户标签；按版本对比指标 |
| **一键回滚** | 切换入口指向旧版本，无需重新构建 |
| 审批 | 生产发布审批、发布窗口（例如节假日封网） |
| 发布前检查 | 资源完整性、体积预算、安全头 |
| **发布后观测** | 错误率、性能、业务指标按版本对比；异常时自动停止灰度 |
| 审计 | 谁在什么时候发布了什么 |
| 通知 | 发布状态通知到相关人员 |

**口述模板（30–60 秒）**

1. 一句话结论：发布平台需要构建、多环境部署、灰度、一键回滚、审批和发布后观测。
2. 关键机制：同一个产物部署到所有环境，配置在运行时注入。
3. 对比或注意点：灰度时按版本对比指标，异常自动停止。
4. 可追问时补充：回滚只需要切换入口，不需要重新构建。

**常见追问**

- 发布窗口和封网有必要吗？→ 对于高风险时段（大促、节假日）有必要；但更好的方式是提高发布的安全性（灰度、自动回滚），让发布成为低风险的日常操作。

### Q7. 灰度发布中，怎么自动判断新版本是否健康？

- **难度**: 高级
- **标签**: 灰度, 自动化

**答案**

**指标**（新版本 vs 旧版本，同一时间段对比）：

- 技术指标：JS 错误率、白屏率、接口错误率、资源加载失败率、LCP / INP
- 业务指标：转化率、关键流程完成率

**判断方式**：

- 阈值：新版本错误率超过旧版本的 X 倍 / 绝对值超过 Y
- **统计显著性**：样本量足够时再判断（灰度比例太小、时间太短时噪声大）
- 分阶段放量：1% → 5% → 20% → 50% → 100%，每个阶段观察一段时间

**自动动作**：指标异常 → 暂停放量 → 告警 → 自动或人工回滚。

**注意**：前端的错误数据要能**按版本区分**（SDK 上报版本号）。

**口述模板（30–60 秒）**

1. 一句话结论：对比新旧版本同一时间段的技术指标和业务指标判断是否健康。
2. 关键机制：分阶段放量，每个阶段观察足够的样本后再判断。
3. 对比或注意点：灰度比例小时噪声大，要考虑统计显著性。
4. 可追问时补充：指标异常时自动暂停放量并告警，可以自动回滚。

**常见追问**

- 为什么要和旧版本同时段对比，而不是和历史对比？→ 排除流量、时间段、外部因素的影响。

### Q8. 前后端分别发布，怎么保证兼容？

- **难度**: 高级
- **标签**: 兼容, 发布

**答案**

**问题**：前端和后端独立发布，任何时刻都可能出现「新前端 + 旧后端」或「旧前端 + 新后端」。

**原则**：**接口变更向后兼容**，分步发布：

```text
新增字段：后端先发布（新增字段，旧前端忽略）→ 前端再使用
删除字段：前端先停止使用 → 确认没有旧前端（考虑缓存的页面和 App 旧版本）→ 后端再删除
修改语义：新增一个字段 / 接口版本，而不是修改原有的
```

**手段**：

- 契约测试（Pact 等）：验证前端期望的接口与后端实际提供的一致
- OpenAPI 生成类型，CI 中检测破坏性变更
- 接口版本（`/v2/`）
- 特性开关：功能上线由开关控制，前后端都部署后再打开

**口述模板（30–60 秒）**

1. 一句话结论：接口变更要向后兼容，按顺序分步发布。
2. 关键机制：新增字段后端先发布，删除字段前端先停止使用。
3. 对比或注意点：修改语义时新增字段或版本，而不是修改原有的。
4. 可追问时补充：契约测试和 OpenAPI 检测破坏性变更，特性开关控制功能上线。

**常见追问**

- 什么时候能确定没有旧前端了？→ Web 端看 HTML 缓存和用户会话的时长（加上版本检测强制刷新）；App 要看旧版本的占比，可能需要很长时间。

### Q9. 怎么衡量研发效能？

- **难度**: 高级
- **标签**: 研发效能

**答案**

**DORA 四项指标**：

| 指标 | 含义 |
|------|------|
| 部署频率 | 多久发布一次到生产 |
| 变更前置时间 | 从提交到上线的时间 |
| 变更失败率 | 导致故障需要修复的发布比例 |
| 故障恢复时间 | 从故障发生到恢复的时间 |

**前端工程的补充指标**：CI 时长（P50 / P90）、构建时长、PR 从创建到合并的时间、本地启动时间和热更新时间、不稳定测试的比例。

**注意**：

- 指标用于**发现问题和改进**，不要用于考核个人（会被操纵）
- 关注趋势而不是绝对值
- 结合开发者满意度调查（定量 + 定性）

**口述模板（30–60 秒）**

1. 一句话结论：用 DORA 的部署频率、变更前置时间、变更失败率和故障恢复时间衡量。
2. 关键机制：前端补充 CI 时长、构建时长、PR 合并时间等指标。
3. 对比或注意点：指标用于发现问题，不要用于考核个人。
4. 可追问时补充：关注趋势，并结合开发者满意度调查。

**常见追问**

- 怎么证明工程化投入的价值？→ 对比改进前后的指标（例如 CI 从 25 分钟降到 6 分钟，按每天的 CI 次数计算节省的时间）。

### Q10. 远程缓存服务怎么自建？要注意什么？

- **难度**: 高级
- **标签**: 远程缓存

**答案**

**实现**：Turborepo 的远程缓存协议是公开的 HTTP API（按哈希上传 / 下载产物）；可以用对象存储（S3 兼容）+ 一个简单的服务实现，或者使用开源实现。

**要注意**：

| 方面 | 要点 |
|------|------|
| **权限** | 主干 CI 可写，PR 和开发者只读（防投毒） |
| **完整性** | 产物签名（Turborepo 支持签名校验） |
| 隔离 | 按仓库 / 团队隔离命名空间 |
| 生命周期 | 按最后访问时间淘汰 |
| 性能 | 与 CI 运行器在同一区域；大产物分块 |
| 可观测 | 命中率、上传下载耗时 |

**口述模板（30–60 秒）**

1. 一句话结论：远程缓存可以用对象存储加一个实现缓存协议的服务自建。
2. 关键机制：按哈希上传和下载任务产物。
3. 对比或注意点：权限上只允许主干 CI 写入，产物签名防止投毒。
4. 可追问时补充：按最后访问时间淘汰，监控命中率。

**常见追问**

- 命中率低怎么排查？→ 对比哈希输入；常见原因是环境变量、全局文件、不确定的构建。

## 三、微前端治理

### Q11. 你会怎么决策是否引入微前端？

- **难度**: 高级
- **标签**: 微前端, 决策

**答案**

**先问「要解决什么问题」**：

| 问题 | 是否需要微前端 |
|------|----------------|
| 构建慢 | 否 → 构建优化、Monorepo 缓存 |
| 代码耦合 | 否 → 模块边界 |
| 多团队协作冲突 | 不一定 → Monorepo + CODEOWNERS + 模块边界 |
| **必须独立发布**（团队的发布节奏差异大） | 是 |
| **技术栈异构 / 渐进迁移老系统** | 是 |
| **平台集成第三方应用** | 是（通常是 iframe 级隔离） |

**引入的代价**：运行时复杂度、性能、体验一致性、调试、版本协调、平台团队的维护成本。

**如果决定引入**：选择方案（同技术栈 → Module Federation；异构 → qiankun / wujie；不可信 → iframe）；先建平台能力（注册中心、监控、规范）；从一个子应用试点。

**口述模板（30–60 秒）**

1. 一句话结论：先明确要解决的问题，很多问题不需要微前端就能解决。
2. 关键机制：只有在必须独立发布、技术栈异构或集成第三方应用时才引入。
3. 对比或注意点：微前端有运行时复杂度、性能和一致性的代价。
4. 可追问时补充：引入时先建平台能力，从一个子应用试点。

**常见追问**

- 你见过微前端用错的情况吗？→ 例如一个团队、同一技术栈拆成多个子应用，结果增加了部署和联调成本，性能变差。

### Q12. 用微前端渐进迁移一个老系统，怎么做？

- **难度**: 高级
- **标签**: 微前端, 迁移

**答案**

**绞杀者模式（Strangler Fig）**：新系统逐步「包围」老系统，按功能替换，最终下线老系统。

```text
阶段 1：新建主应用（基座），把老系统整体作为一个子应用接入（改动最小）
阶段 2：新功能在新的子应用中开发
阶段 3：按页面 / 模块从老系统迁移到新子应用（按价值和改动频率排序）
阶段 4：老系统中的功能全部迁出后下线
```

**要点**：

- 老系统接入：iframe 或 wujie（改造成本最低）；qiankun 需要老系统导出生命周期
- **共享能力**：登录态、权限、导航由基座统一提供
- **体验一致**：统一的设计系统，老系统的样式逐步对齐
- 迁移的优先级：高频修改的模块优先（收益大）
- 设定老系统的冻结政策：只修 bug，不加功能

**口述模板（30–60 秒）**

1. 一句话结论：采用绞杀者模式，新系统逐步替换老系统的功能。
2. 关键机制：先把老系统整体作为子应用接入，新功能在新的子应用中开发。
3. 对比或注意点：登录、权限、导航由基座统一提供。
4. 可追问时补充：高频修改的模块优先迁移，老系统只修 bug 不加功能。

**常见追问**

- 老系统和新系统的登录态怎么共享？→ 同域部署共享 Cookie 会话；或者基座获取令牌后通过 props 下发。

### Q14. 微前端的稳定性怎么保障？

- **难度**: 高级
- **标签**: 微前端, 稳定性

**答案**

| 风险 | 措施 |
|------|------|
| 子应用加载失败（CDN、发布错误） | 重试、备用地址、降级页面；不影响基座和其他子应用 |
| 子应用运行时报错 | 错误边界隔离；按子应用分类上报 |

**监控**：按子应用拆分错误率、加载耗时、加载失败率；告警通知对应的团队。

**口述模板（30–60 秒）**

1. 一句话结论：子应用的故障不能影响基座和其他子应用。
2. 关键机制：加载失败时重试和降级，运行时错误用错误边界隔离。
3. 对比或注意点：子应用独立灰度，通过注册中心一键回滚。
4. 可追问时补充：监控按子应用拆分，告警通知对应的团队。

**常见追问**

- 基座本身出问题怎么办？→ 基座要尽量轻量和稳定，变更更严格（更多测试、更慢的灰度）。

### Q15. 如果让你实现一个微前端框架，核心模块有哪些？

- **难度**: 高级
- **标签**: 微前端, 设计

**答案**

```text
1. 应用注册与调度
   - 注册：name、entry、activeRule、container、props
   - 路由监听：拦截 pushState / replaceState / popstate，判断需要激活和卸载的应用
   - 生命周期：bootstrap → mount → unmount；状态机，防止并发切换的竞态

2. 加载器
   - HTML Entry：fetch、解析脚本和样式、处理相对路径
   - 缓存与预加载

3. 沙箱
   - JS：代理沙箱（或 iframe）
   - 副作用补丁：定时器、事件监听、动态插入的 style / script（劫持 appendChild）
   - 样式：作用域 CSS 改写或 Shadow DOM

4. 通信
   - props、全局状态（发布订阅）

5. 错误处理与降级

6. 开发工具：调试、日志
```

**难点**：路由切换时的并发（上一个还没卸载完，下一个开始加载）；动态插入的脚本和样式要进入沙箱；第三方库对全局对象的假设。

**口述模板（30–60 秒）**

1. 一句话结论：核心模块是应用注册与调度、加载器、沙箱、通信和错误处理。
2. 关键机制：调度器监听路由变化，管理子应用的生命周期状态机。
3. 对比或注意点：沙箱要劫持动态插入的脚本和样式。
4. 可追问时补充：难点是路由快速切换时的并发和第三方库对全局对象的假设。

**常见追问**

- 为什么要劫持 `appendChild`？→ 子应用运行时动态插入的 `<script>` 需要在沙箱中执行，`<style>` 需要作用域处理，卸载时也要能移除。

### Q16. Module Federation 在生产中有哪些坑？

- **难度**: 高级
- **标签**: Module Federation

**答案**

| 坑 | 说明 | 处理 |
|----|------|------|
| **单例版本不满足** | 宿主的 React 版本不满足远程的要求，只有警告，运行时出错 | 统一版本、`strictVersion`、CI 检查 |
| 远程加载失败 | 远程服务不可用导致页面白屏 | 错误边界、重试、降级 |
| **缓存** | `remoteEntry.js` 被缓存，导致使用旧版本 | `remoteEntry` / manifest 不缓存或短缓存 |
| 发布顺序 | 远程的接口变化，宿主还在使用旧的方式 | 暴露的模块向后兼容、版本化 |
| CSS | 远程模块的样式加载和冲突 | 样式随模块加载、作用域化 |
| 调试困难 | 跨应用的问题难以定位 | 监控中记录远程版本、MF 调试工具 |
| 共享依赖的异步边界 | 忘记异步边界导致报错 | `bootstrap` 文件 |

**口述模板（30–60 秒）**

1. 一句话结论：常见的坑是单例版本不满足、远程加载失败、remoteEntry 被缓存和接口不兼容。
2. 关键机制：单例版本不满足时只有警告，运行时才出错。
3. 对比或注意点：remoteEntry 和 manifest 不能长期缓存。
4. 可追问时补充：远程模块要向后兼容，宿主要有错误边界和降级。

**常见追问**

- 怎么做远程模块的灰度？→ 运行时 API 动态注册远程地址，配置中心按用户返回不同版本的地址。

### Q17. 怎么设计代码质量门禁？

- **难度**: 高级
- **标签**: 质量

**答案**

**PR 合并前必须通过**：

| 检查 | 说明 |
|------|------|
| Lint + 格式 | 零错误 |
| 类型检查 | 严格模式 |
| 单元 / 组件测试 | 受影响的测试通过；新增代码的覆盖率（而不是整体覆盖率） |
| 构建 | 成功 |
| **体积预算** | 包体积超出阈值失败（size-limit） |
| 安全 | 依赖漏洞（高危阻塞）、密钥扫描 |
| E2E 冒烟 | 核心流程 |
| 评审 | CODEOWNERS 的批准 |

**原则**：

- 门禁要**快**且**稳定**（不稳定的门禁会被绕过）
- 新规则先告警再阻塞；存量问题用基线（只检查新增）
- 例外有流程（谁可以豁免、记录原因）

**口述模板（30–60 秒）**

1. 一句话结论：PR 合并前必须通过 Lint、类型检查、测试、构建、体积预算、安全扫描和评审。
2. 关键机制：覆盖率看新增代码，体积超出预算时失败。
3. 对比或注意点：门禁要快且稳定，否则会被绕过。
4. 可追问时补充：新规则先告警再阻塞，存量问题用基线只检查新增。

**常见追问**

- 老项目有几千个 Lint 错误，怎么引入新规则？→ 生成基线文件（ESLint 的抑制功能 / 工具支持），只对新增的问题报错，然后逐步清理。

### Q18. 怎么推动一个新规范在团队中落地？

- **难度**: 高级
- **标签**: 规范, 推动

**答案**

1. **说明为什么**：用真实的问题和数据说明（例如某类 bug 出现了多少次）
2. **工具化**：规范变成 Lint 规则、脚手架模板、CI 检查，而不是文档
3. **降低成本**：提供自动修复（`--fix`、codemod），工程化团队帮忙迁移存量
4. **渐进**：先警告后错误；先新代码后存量；先试点后推广
5. **收集反馈**：规则有争议时调整，有正当理由的场景提供例外
6. **度量**：违规数量的趋势

**口述模板（30–60 秒）**

1. 一句话结论：先说明为什么，再把规范工具化，并提供自动修复降低成本。
2. 关键机制：规范变成 Lint 规则、脚手架和 CI 检查，而不是文档。
3. 对比或注意点：渐进推进，先警告后错误，先新代码后存量。
4. 可追问时补充：收集反馈调整规则，用违规数量的趋势度量效果。

**常见追问**

- 有人用 `eslint-disable` 绕过怎么办？→ 要求注释说明原因（`eslint-comments/require-description`），统计禁用的数量，评审时关注。

### Q19. 怎么管理多个应用的公共配置（ESLint、TS、构建）？

- **难度**: 高级
- **标签**: 配置管理

**以包的形式共享**：

```text
@acme/eslint-config      # 导出 flat config，可组合（base / react / node）
@acme/tsconfig           # base.json、react.json、node.json
@acme/vite-config        # 导出 defineConfig 的工厂函数
```

2. 关键机制：升级只需要更新包的版本。
3. 对比或注意点：配置包的破坏性修改走主版本。
4. 可追问时补充：允许项目覆盖，但要可见以便审计。

**常见追问**

### Q20. AI 编码工具对前端工程化有什么影响？

### Q21. 怎么设计前端的多环境和配置管理？

- **难度**: 高级
- **标签**: 配置, 环境

**答案**

**环境**：本地 → 预览（每个 PR）→ 测试 → 预发（与生产一致的配置）→ 生产。

**配置分类**：

| 类型 | 例子 | 管理方式 |
|------|------|----------|
| 构建时常量 | 功能编译开关 | 构建参数（尽量少） |
| **运行时配置** | API 地址、监控 DSN、第三方的公开 ID | 部署时注入（HTML 内联或 `config.json`） |
| 动态配置 | 特性开关、灰度规则 | 配置中心 |
| 密钥 | **前端不应该有** | 放在 BFF / 服务端 |

**原则**：

- 构建一次，配置在部署时注入
- 配置有 schema 校验（启动时校验，缺失时明确报错）
- 预发环境尽可能与生产一致

**口述模板（30–60 秒）**

1. 一句话结论：配置分为构建时常量、运行时配置、动态配置，前端不应该有密钥。
2. 关键机制：构建一次，运行时配置在部署时注入。
3. 对比或注意点：动态配置（特性开关）由配置中心管理。
4. 可追问时补充：配置要有 schema 校验，预发环境尽量与生产一致。

**常见追问**

- SSR 应用的配置呢？→ 服务端的环境变量可以有密钥（不暴露给客户端）；注意框架中哪些变量会被打包到客户端代码。

### Q23. 怎么在团队中管理多个框架版本并存的问题？

- **难度**: 高级
- **标签**: 技术栈治理

**答案**

**现状**：不同项目使用 React 17 / 18 / 19，Vue 2 / 3，构建工具不同。

**治理**：

- **技术雷达**：明确每个技术的状态（推荐 / 可用 / 暂缓 / 淘汰）
- **支持的版本窗口**：例如「只支持最近两个主版本」，超出的项目必须制定升级计划
- **平台能力的兼容**：组件库、SDK 支持的框架版本范围
- **升级的成本由平台分担**：codemod、迁移指南、专项支持
- **淘汰**：Vue 2（已于 2023 年底停止维护）、AngularJS 等不再维护的技术，制定迁移路线

**口述模板（30–60 秒）**

1. 一句话结论：用技术雷达明确每个技术的状态，规定支持的版本窗口。
2. 关键机制：超出窗口的项目必须制定升级计划。
3. 对比或注意点：平台提供 codemod 和迁移支持，分担升级成本。
4. 可追问时补充：不再维护的框架要有明确的迁移路线。

**常见追问**

- 组件库要同时支持 React 18 和 19 吗？→ 在过渡期内支持（peerDependencies 声明范围，CI 中用两个版本测试），之后放弃旧版本。

  - Changesets 管理对外发布的包
- **结果**：CI P50 从 22 分钟降到 5 分钟；组件修改到业务使用从 1 天降到即时；缓存命中率 80%+
- **复盘**：版本对齐比预期耗时；未声明的环境变量导致过一次缓存错误命中 → 开启严格环境模式

### Q26. 前端工程化有哪些趋势？

- **难度**: 高级
- **标签**: 趋势

**答案**

（截至 2026-10，以官方为准）

- **Rust / Go 工具链**：Rspack、Rolldown、Oxc（oxlint）、Biome、TypeScript 原生编译器（tsgo）→ 构建和检查大幅提速
- **供应链安全成为默认**：pnpm / npm 默认禁止依赖的安装脚本、冷却期；可信发布；Action 固定 SHA；GitHub 对 pwn request 的默认防护
- **Monorepo 工具成熟**：pnpm catalogs、远程缓存、分布式执行
- **Module Federation 2.0**：与构建工具解耦，跨构建工具和 React Native
- **AI 辅助开发**：代码生成、评审、迁移；对规范和自动化检查的依赖增加
- **平台工程**：内部开发者平台（IDP），把工程化能力产品化

**口述模板（30–60 秒）**

1. 一句话结论：工具链向 Rust 和 Go 迁移，供应链安全成为默认配置。
2. 关键机制：Rspack、Rolldown、oxlint、tsgo 带来数量级的提速。
3. 对比或注意点：Monorepo 工具成熟，Module Federation 与构建工具解耦。
4. 可追问时补充：AI 辅助开发和平台工程是新的方向。

**常见追问**

- 工具链变化这么快，团队怎么跟进？→ 通过共享配置包和脚手架统一管理工具版本，平台团队评估和推进升级，业务团队不需要各自跟进。
