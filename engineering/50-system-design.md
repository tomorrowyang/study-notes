# 前端工程化系统设计

> 回答结构：先澄清需求和约束 → 给出整体架构 → 展开关键设计 → 说明指标和取舍 → 回应扩展追问。工程化设计题重点是「规模」「安全」「效率」三者的平衡。

---

### S1. 为 50 个前端应用设计 Monorepo 平台

- **难度**: 高级
- **标签**: Monorepo, 平台

**澄清问题（面试时先问）**

- 团队规模和组织结构？应用之间共享多少代码？
- 是否有必须隔离的项目（权限、合规）？
- 现有的 CI 和部署方式？各应用的发布节奏？
- 技术栈是否统一？

**参考方案**

```text
monorepo/
├── apps/                  50 个应用（各自独立部署）
├── packages/
│   ├── ui/                设计系统
│   ├── shared/            工具、请求、监控 SDK
│   ├── features/          可复用的业务模块
│   └── config/            eslint / tsconfig / vite 配置包
├── tools/generators/      应用和包的生成器
├── pnpm-workspace.yaml    catalogs 统一版本
└── turbo.json / nx.json

CI：受影响分析 → 远程缓存 → 分布式执行 → 每个应用独立的部署流水线
治理：模块边界（标签）+ CODEOWNERS + 依赖版本策略
```

**关键设计**

- **依赖**：pnpm 严格模式；catalogs 统一核心依赖版本；Renovate 分组升级
- **任务**：标准任务名（build / test / lint / typecheck）；精确的 inputs / outputs / env
- **缓存**：远程缓存主干写、PR 只读；签名
- **边界**：`type`（app / feature / ui / util）和 `scope`（业务域）两个维度的标签
- **部署**：每个应用的部署由受影响分析触发，互不阻塞
- **开发体验**：生成器一条命令创建应用；`turbo watch` / 按需启动；IDE 的 TS 项目引用

**关键指标**

- CI P50 / P90 时长、缓存命中率
- 本地安装时间、启动时间
- 依赖版本的分散度（同一个依赖存在多少个版本）

**口述模板（2–3 分钟）**

我先确认应用之间的共享程度和是否有需要隔离的项目，这决定了哪些放进 Monorepo。

结构上分为 apps 和 packages，packages 按设计系统、共享工具、业务模块、配置包划分。依赖用 pnpm 严格模式和 catalogs 统一版本，Renovate 分组升级。

效率上依赖三件事：受影响分析只运行修改相关的任务；远程缓存跨机器复用产物，权限上主干写 PR 只读防止投毒；规模更大时使用分布式任务执行。

治理上用 type 和 scope 两个维度的标签约束模块边界，CODEOWNERS 分配评审。每个应用独立部署，互不阻塞。

最后用 CI 时长、缓存命中率和依赖版本分散度来度量。

**扩展追问**

- 某个团队想要独立的仓库怎么办？→ 评估原因；如果是权限隔离需求，可以保留独立仓库，通过 npm 私有包共享代码。
- 根目录的一个配置修改导致 50 个应用全部重建怎么办？→ 精细化 inputs；配置拆分到配置包中，只影响依赖它的应用。

### S2. 设计一个前端 CI/CD 平台

- **难度**: 高级
- **标签**: CI/CD, 平台

**澄清问题（面试时先问）**

- 支持多少个项目、多少次构建 / 天？
- 部署目标：静态（CDN）、SSR（容器）、小程序？
- 是否有合规要求（审批、审计）？
- 基于现有的 CI（GitHub Actions / GitLab CI）还是自建？

**参考方案**

```text
代码仓库 ──webhook──▶ 流水线编排
                      │
   ┌──────────────────┼──────────────────────┐
   ▼                  ▼                      ▼
 检查阶段           构建阶段                部署阶段
 lint/type/test    统一构建镜像            测试 → 预发 → 灰度 → 全量
 安全扫描          产物上传制品库           审批、发布窗口
                   (按版本不可变)          入口切换 / 回滚
                   sourcemap 上传          发布后观测（自动停止灰度）
                   provenance 签名
                          │
                   制品库（对象存储）── CDN
```

**关键设计**

- **流水线模板**：按项目类型提供模板（SPA / SSR / 组件库），项目只声明差异
- **构建一次多处部署**：配置在部署时注入
- **运行器**：容器化、一次性、自动扩缩容；按团队配额
- **缓存**：依赖缓存、远程任务缓存
- **安全**：OIDC 获取云凭证；密钥按环境隔离；第三方 Action 固定 SHA；产物签名
- **部署**：静态资源先上传、HTML 后切换；保留历史版本；一键回滚
- **可观测**：每条流水线的耗时分解、失败原因分类、不稳定测试统计

**关键指标**

- 流水线成功率、P50 / P90 耗时、排队时间
- 部署频率、变更失败率、回滚耗时

**口述模板（2–3 分钟）**

我会先确认规模、部署目标和合规要求，并且倾向于基于现有的 CI 系统扩展，而不是从零造轮子。

流水线分为检查、构建、部署三个阶段。检查包括 lint、类型、测试和安全扫描；构建使用统一的镜像，产物按版本不可变地存入制品库，同时上传 sourcemap 和生成来源证明；部署按测试、预发、灰度、全量推进，生产需要审批，HTML 后于静态资源切换，回滚只需要切回旧版本。

项目接入通过模板完成，只声明差异。安全上用 OIDC 代替长期密钥，第三方 Action 固定 SHA。

我会用流水线耗时、成功率和 DORA 指标来度量平台的价值。

**扩展追问**

- 构建排队严重怎么办？→ 运行器自动扩缩容；按优先级调度（主干和发布优先）；减少不必要的构建（受影响分析、取消过时的运行）。

### S3. 设计前端灰度发布系统

- **难度**: 高级
- **标签**: 灰度

**澄清问题（面试时先问）**

- SPA 还是 SSR？有没有自己的接入层（网关 / Node）？
- 灰度的维度：用户、比例、地域、渠道？
- 是否需要自动判断健康和自动回滚？
- 前后端是否需要联动灰度？

**参考方案**

```text
         灰度配置中心（规则：白名单、比例、标签；版本）
                     │ 下发
用户请求 ──▶ 接入层（网关 / Edge / Node）
               │ 根据用户 ID 哈希 / Cookie / 标签判断版本
               ├─ 旧版本 HTML ──▶ 引用 /v1.2.0/ 的资源
               └─ 新版本 HTML ──▶ 引用 /v1.3.0/ 的资源
                     │
               监控 SDK 上报版本号
                     │
               指标对比服务（新 vs 旧）──异常──▶ 暂停 / 回滚
```

**关键设计**

- **分流位置**：HTML 入口处（网关 / Edge 函数 / SSR 服务）；静态资源按版本目录并存
- **稳定性**：按用户 ID 哈希分桶，匿名用户用设备 Cookie
- **缓存**：灰度阶段 HTML 不在 CDN 共享缓存，或缓存键包含版本 Cookie
- **放量策略**：内部用户 → 1% → 5% → 25% → 100%，每个阶段有观察时间
- **自动化**：错误率、白屏率、核心指标与旧版本对比，超出阈值暂停并告警
- **联动**：需要前后端同时灰度时，前端请求带上灰度标识，后端网关据此路由

**关键指标**

- 灰度期间新旧版本的错误率、性能、业务转化
- 异常发现时间、回滚耗时

**口述模板（2–3 分钟）**

前端灰度的核心是「在 HTML 入口决定用户使用哪个版本」，因为 HTML 决定了加载哪个版本的静态资源，而静态资源按版本目录并存。

分流在接入层进行，可以是网关、Edge 函数或 SSR 服务。按用户 ID 哈希分桶保证同一个用户版本稳定，匿名用户用设备 Cookie。规则由配置中心下发，支持白名单、比例和标签。

要注意缓存：灰度期间 HTML 不能被 CDN 共享缓存，否则分流失效。

放量分阶段进行，监控 SDK 上报版本号，指标服务对比新旧版本的错误率和业务指标，超出阈值时自动暂停并告警，回滚只需要把配置切回旧版本。

如果需要前后端联动，前端请求带上灰度标识，由后端网关路由到对应版本的服务。

**扩展追问**

- 纯静态部署、没有服务端怎么做？→ CDN 的 Edge 函数分流；或者加载一个很小的引导脚本，根据配置接口决定加载哪个版本的入口（会增加一次请求）。

### S4. 设计微前端基座平台

- **难度**: 高级
- **标签**: 微前端, 平台

**澄清问题（面试时先问）**

- 子应用的数量和技术栈？是否有老系统？
- 子应用是否同时展示多个？
- 是否需要集成第三方或不可信的应用？
- 团队的发布节奏？

**参考方案**

```text
┌──────────────────── 基座 ─────────────────────┐
│ 布局（导航、菜单、头部）  登录 / 权限   全局通知     │
│ 子应用调度器（路由 → 子应用）                      │
│ 加载器（HTML Entry / MF）  沙箱  错误边界          │
│ 通信（props + 全局状态）  监控 SDK                 │
└──────────────────────┬────────────────────────┘
                       │ 读取
             子应用注册中心
             （名称、入口 URL、版本、灰度规则、兼容的基座版本）
                       ▲
                       │ 发布时注册
           子应用独立的 CI/CD
```

**关键设计**

- **方案选择**：同技术栈 → Module Federation；异构 / 老系统 → qiankun 或 wujie；不可信 → iframe
- **注册中心**：子应用发布后注册新版本；运行时读取；回滚 = 切换版本；按用户灰度
- **共享能力**：登录、权限、主题、国际化由基座提供，通过 props 下发
- **隔离**：JS 沙箱 + 样式作用域；子应用卸载时清理副作用
- **容错**：加载重试、备用地址、降级页面；子应用错误不影响基座
- **性能**：共享依赖、预加载下一个可能访问的子应用
- **开发体验**：子应用可以独立运行；本地基座可以指向本地子应用

**关键指标**

- 子应用加载耗时、加载失败率、按子应用的错误率
- 子应用的发布频率（验证独立发布的价值）

**口述模板（2–3 分钟）**

我会先确认子应用的技术栈、是否有老系统、是否有不可信的应用，这决定了技术方案：同技术栈优先 Module Federation，异构或老系统用 qiankun 或 wujie，不可信的用 iframe。

基座负责布局、登录权限、全局通知这些共享能力，以及子应用的调度、加载、沙箱和错误隔离。

关键是子应用注册中心：子应用的 CI 发布后注册新版本，基座运行时读取入口地址。这样子应用可以独立发布、独立灰度，回滚只需要切换版本。

稳定性上，子应用加载失败时重试和降级，运行时错误被错误边界隔离。性能上共享依赖并预加载。

最后用按子应用拆分的加载耗时、失败率和错误率来监控，告警直接通知对应的团队。

**扩展追问**

- 子应用之间怎么共享组件库？→ 共享依赖（单例）；或者组件库本身作为远程模块；版本由平台统一协调。

### S5. 设计组件库的研发和发布流水线

- **难度**: 中级
- **标签**: 组件库, 发布

**澄清问题（面试时先问）**

- 组件库的使用方数量？是否对外开源？
- 支持的框架版本范围？
- 发布节奏？是否需要预发布版本？

**参考方案**

```text
开发：Storybook（文档 + 开发环境）
  │
PR：lint / typecheck / 单元测试 / 视觉回归（截图对比）/ 可访问性检查 / 体积预算
  │  + Changeset 文件（描述变更和版本类型）
  │  + 预览发布（pkg.pr.new / 快照版本，供业务方提前验证）
  │
合并：Changesets 机器人创建「版本 PR」（汇总变更日志、升级版本号）
  │
合并版本 PR：构建 → 发布到 npm（可信发布 / provenance）→ 发布 Storybook 文档
  │
使用方：Renovate 自动升级 PR；主版本附带 codemod
```

**关键设计**

- **产物**：ESM + 类型声明；`exports` 字段；`sideEffects` 声明以支持 tree-shaking；样式按需
- **兼容性**：peerDependencies 声明支持的框架范围；CI 中矩阵测试多个版本
- **质量**：视觉回归防止样式意外变化；可访问性检查
- **破坏性变更**：先废弃（运行时警告 + 文档）、下一个主版本移除、提供 codemod
- **安全**：OIDC 可信发布，不使用长期 npm token

**关键指标**

- 使用方的版本分布（多少使用方停留在旧的主版本）
- 发布频率、缺陷逃逸率

**口述模板（2–3 分钟）**

组件库的流水线我会以 Changesets 为核心：每个 PR 附带一个 changeset 描述变更和版本类型，合并后机器人汇总成版本 PR，合并版本 PR 时自动发布。

PR 阶段除了常规检查，还有视觉回归和可访问性检查，以及体积预算。我还会为每个 PR 发布预览版本，让业务方在合并前验证。

产物要支持 tree-shaking：ESM、`sideEffects` 声明、样式按需。兼容性上用 peerDependencies 声明支持范围，CI 中矩阵测试多个框架版本。

破坏性变更走「废弃、下一个主版本移除、提供 codemod」的流程。发布使用可信发布，不使用长期 token。

我会关注使用方的版本分布，来判断升级成本是否过高。

**扩展追问**

- 视觉回归误报多怎么办？→ 固定字体和渲染环境（容器中运行）、禁用动画、设置差异阈值。

### S6. 设计多环境配置中心（前端）

- **难度**: 中级
- **标签**: 配置

**澄清问题（面试时先问）**

- 需要哪些类型的配置：接口地址、特性开关、灰度、文案？
- 变更的生效时间要求（实时 / 下次刷新）？
- 是否需要按用户维度的配置？

**参考方案**

```text
管理后台（编辑、审批、版本历史、回滚）
      │
配置服务（按应用 + 环境存储；规则评估；审计）
      │
  ┌───┴──────────────┐
  ▼                  ▼
CDN 上的静态配置     评估接口（按用户返回特性开关结果）
(config.<env>.json) 
  │                  │
前端 SDK：启动时加载（带超时和本地缓存兜底）→ 运行时订阅更新（可选）
```

**关键设计**

- **配置分层**：默认值（代码中）→ 环境配置 → 动态规则；缺失时有安全的默认值
- **可用性**：配置服务不可用时使用本地缓存或默认值，不阻塞页面渲染
- **安全**：前端配置都是公开的，不放密钥；按用户评估的开关在服务端计算，不下发所有规则
- **变更管理**：审批、版本历史、一键回滚；变更也要灰度
- **类型安全**：配置有 schema，SDK 提供类型

**关键指标**

- 配置加载耗时、失败率
- 配置变更引发的故障数

**口述模板（2–3 分钟）**

前端配置分为环境配置和动态配置。环境配置（接口地址、监控 DSN）以静态 JSON 的形式放在 CDN，部署时选择对应环境的文件；动态配置（特性开关、灰度规则）由评估接口按用户计算结果返回，不把规则本身暴露给前端。

SDK 启动时加载配置，设置超时，失败时使用本地缓存或代码中的默认值，不能阻塞页面。

配置变更和代码发布一样需要管理：审批、版本历史、一键回滚，重要的变更也要灰度。配置有 schema 校验，SDK 提供类型。

最后强调前端配置都是公开的，不能放密钥。

**扩展追问**

- 配置实时生效怎么做？→ SSE 或长轮询推送；但多数场景下次刷新生效已经足够，更简单。

### S7. 为大型组织设计前端工程规范体系

- **难度**: 高级
- **标签**: 规范, 治理

**澄清问题（面试时先问）**

- 团队数量和技术栈的分散程度？
- 现有规范的执行情况？
- 有没有专门的平台 / 基础架构团队？

**参考方案**

```text
层次                内容                               落地方式
──────────────────────────────────────────────────────────────────
技术选型            技术雷达（推荐 / 可用 / 暂缓 / 淘汰）   架构委员会评审
代码规范            ESLint / Prettier / TS 严格模式        共享配置包 + CI 门禁
提交与分支          Conventional Commits、主干开发          commitlint + 分支保护
依赖                允许的许可证、安全、版本策略            Renovate + SCA + 冷却期
质量                测试、体积、性能、可访问性预算           CI 门禁
安全                CSP、依赖、密钥                        脚手架默认 + 扫描
发布                灰度、回滚、审批                        发布平台
可观测              错误、性能监控                          脚手架默认接入 SDK
```

**关键设计**

- **规范即代码**：每条规范都有对应的工具或检查，而不是只有文档
- **默认正确**：脚手架创建的项目默认满足所有规范
- **分级**：必须（阻塞）/ 推荐（警告）；存量项目有过渡期
- **共建**：规范的修改通过 RFC，业务团队可以参与
- **度量**：各项目的合规程度看板（例如「是否使用最新的配置包版本」）

**关键指标**

- 项目合规率、配置包版本的落后程度
- 规范相关的线上问题数

**口述模板（2–3 分钟）**

规范体系我会从技术选型、代码、提交、依赖、质量、安全、发布、可观测几个层次组织，但核心原则是「规范即代码」：每条规范都要有对应的工具或检查来执行，而不是只写在文档里。

落地方式是共享配置包和脚手架，让新项目默认满足规范；存量项目通过 Renovate 推送配置包的升级，新规则先警告、给过渡期再阻塞。

规范的修改通过 RFC 流程，业务团队可以参与，这样规范更容易被接受。

最后用合规看板度量各项目的状态，用规范相关的线上问题数证明价值。

**扩展追问**

- 某个团队有特殊需求要偏离规范怎么办？→ 允许覆盖，但要记录原因并可见；如果多个团队有同样的需求，说明规范需要调整。

### S8. 设计远程构建缓存服务

- **难度**: 高级
- **标签**: 缓存, 服务

**澄清问题（面试时先问）**

- 使用的工具（Turborepo / Nx / Bazel）？各有不同的协议
- 规模：仓库数量、每天的构建次数、产物大小？
- 部署在内网还是云上？与 CI 运行器的网络距离？

**参考方案**

```text
CI 运行器 / 开发者
   │ HTTP（GET/PUT /artifacts/:hash），Bearer token
   ▼
缓存服务（无状态，多实例）
   ├─ 鉴权：token → 团队 / 仓库；权限（读 / 写）
   ├─ 元数据：哈希、大小、创建时间、最后访问时间、签名
   └─ 存储：对象存储（同区域）
   │
后台任务：按最后访问时间淘汰、容量配额
监控：命中率、延迟、带宽、各团队用量
```

**关键设计**

- **权限**：主干 CI 的 token 可写；PR 和开发者只读 → 防止缓存投毒
- **完整性**：客户端签名产物（HMAC），读取时校验
- **隔离**：按仓库划分命名空间，防止跨仓库读取
- **性能**：对象存储预签名 URL 直接上传 / 下载，服务不转发大文件；与 CI 同区域
- **成本**：LRU 淘汰、团队配额；压缩
- **可用性**：缓存服务故障时客户端降级为本地执行（不能让缓存故障阻塞 CI）

**关键指标**

- 命中率、节省的 CI 时间
- P95 下载延迟、存储成本

**口述模板（2–3 分钟）**

远程缓存服务本质上是一个「按哈希存取产物」的服务。我会做成无状态的 API 层加对象存储，大文件通过预签名 URL 直接在客户端和对象存储之间传输，服务本身只处理鉴权和元数据。

最重要的是安全：缓存投毒会让恶意产物进入生产构建，所以只有主干 CI 可以写入，PR 和开发者只读；产物签名，读取时校验；不同仓库的命名空间隔离。

成本上按最后访问时间淘汰，按团队设置配额。可用性上缓存服务故障时客户端要能降级为本地执行，不能阻塞 CI。

最后用命中率和节省的 CI 时间来证明价值。

**扩展追问**

- 为什么不直接用 CI 自带的缓存（actions/cache）？→ CI 缓存按分支隔离、有容量限制，不能在开发者本地复用；任务级远程缓存粒度更细、跨环境复用。
