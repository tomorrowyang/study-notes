### R1. pnpm 为什么快？为什么能解决幽灵依赖？

- **来源倾向**: 一面、基础工程化
- **难度**: 初级

**答案**

- 全局内容寻址存储，文件通过硬链接复用，同一个版本只存一份
- `node_modules` 顶层只有直接依赖的符号链接，真实文件在 `.pnpm` 中按「包@版本」隔离 → 未声明的依赖无法访问
- 安装并行化

详见：[10-junior-qa.md Q2](./10-junior-qa.md)

**口述模板（30–60 秒）**

1. **一句话结论**：pnpm 用内容寻址存储加硬链接复用文件，用符号链接构建严格的依赖结构。
2. **关键机制**：顶层只有直接依赖，依赖的依赖在 `.pnpm` 中隔离。
3. **对比或注意点**：npm 和 yarn v1 的扁平化会导致幽灵依赖和分身问题。
4. **可追问时补充**：部分老工具依赖扁平结构，可以用 `public-hoist-pattern` 兼容。

### R2. 锁文件的作用？`npm install` 和 `npm ci` 的区别？

- **来源倾向**: 一面
- **难度**: 初级

**答案**

- 锁文件固定依赖树的精确版本和完整性哈希，保证可复现
- `npm ci`：严格按锁文件安装，不一致时失败，先删除 `node_modules`；CI 中使用
- `npm install`：可能更新锁文件

详见：[10-junior-qa.md Q3](./10-junior-qa.md)

### R3. `^1.2.3` 和 `~1.2.3` 的区别？`^0.2.3` 呢？

- **来源倾向**: 一面
- **难度**: 初级

**答案**

- `^1.2.3`：`>=1.2.3 <2.0.0`
- `~1.2.3`：`>=1.2.3 <1.3.0`
- `^0.2.3`：`>=0.2.3 <0.3.0`（0.x 时 minor 被视为破坏性）

### R4. 为什么用 Monorepo？有什么缺点？

- **来源倾向**: 一面 / 二面、项目追问
- **难度**: 中级

**答案**

- 优点：代码共享无需发包、原子提交、统一工具和依赖版本、跨项目重构容易
- 缺点：仓库变大、CI 需要受影响分析和缓存、权限粒度粗、需要模块边界治理
- 工具：pnpm workspace + Turborepo / Nx

详见：[10-junior-qa.md Q6](./10-junior-qa.md)、[30-senior-qa.md Q3](./30-senior-qa.md)

**口述模板（30–60 秒）**

1. **一句话结论**：Monorepo 解决共享代码和跨项目修改的成本问题。
2. **关键机制**：内部包通过 workspace 协议直接引用，修改可以原子提交。
3. **对比或注意点**：代价是 CI 和仓库规模，需要受影响分析、远程缓存和模块边界。
4. **可追问时补充**：不相关、需要权限隔离的项目不适合放在一起。

### R5. Turborepo 的缓存原理？什么情况会错误命中？

- **来源倾向**: 二面
- **难度**: 中级

**答案**

- 缓存键 = 任务的输入文件 + 依赖包的哈希 + 声明的环境变量 + 全局依赖 + 配置
- 命中时恢复输出文件和日志
- 错误命中：使用了未声明的环境变量、读取了 inputs 之外的文件、构建不确定（时间戳）
- 解决：严格环境变量模式、精确 inputs

详见：[20-mid-qa.md Q2](./20-mid-qa.md)、[40-coding-handwritten.md H2](./40-coding-handwritten.md)

### R6. 远程缓存有什么安全风险？

- **来源倾向**: 二面 / 三面
- **难度**: 高级

**答案**

- 缓存投毒：攻击者写入恶意产物，被主干构建复用，进入生产
- 防护：主干 CI 可写，PR 只读；产物签名；按仓库隔离

详见：[20-mid-qa.md Q3](./20-mid-qa.md)、[50-system-design.md S8](./50-system-design.md)

**口述模板（30–60 秒）**

1. **一句话结论**：远程缓存最大的风险是缓存投毒。
2. **关键机制**：PR 中的代码可以计算出某个哈希并写入恶意产物，之后的主干构建命中它。
3. **对比或注意点**：所以只有可信的主干 CI 可以写入，PR 和开发者只读。
4. **可追问时补充**：再加上产物签名校验和命名空间隔离。

### R8. 前端如何做灰度发布？

- **来源倾向**: 二面 / 三面
- **难度**: 高级

**答案**

- 在 HTML 入口分流：网关 / Edge / SSR 按用户哈希决定版本
- 静态资源按版本并存
- HTML 不能被共享缓存
- 监控按版本对比，异常暂停和回滚

详见：[20-mid-qa.md Q12](./20-mid-qa.md)、[50-system-design.md S3](./50-system-design.md)、[40-coding-handwritten.md H9](./40-coding-handwritten.md)

**口述模板（30–60 秒）**

1. **一句话结论**：前端灰度的关键是在 HTML 入口决定用户使用哪个版本。
2. **关键机制**：按用户 ID 哈希稳定分桶，静态资源按版本目录并存。
3. **对比或注意点**：灰度期间 HTML 不能被 CDN 共享缓存。
4. **可追问时补充**：按版本对比错误率，异常时自动暂停并回滚。

### R9. 发版后用户报「页面白屏 / 加载 chunk 失败」怎么办？

- **来源倾向**: 二面、线上问题
- **难度**: 中级

**答案**

- 原因：旧页面请求已被删除的旧 chunk
- 保留旧版本资源一段时间；HTML 不缓存
- 捕获 chunk 加载错误后刷新一次（防止循环）
- 版本检测提示用户刷新

详见：[20-mid-qa.md Q15](./20-mid-qa.md)

### R10. 前端静态资源的缓存策略？

- **来源倾向**: 一面
- **难度**: 初级

**答案**

- 带哈希的资源：`Cache-Control: max-age=31536000, immutable`
- HTML：`no-cache`（协商缓存）
- 部署顺序：先上传资源，再更新 HTML

详见：[10-junior-qa.md Q18](./10-junior-qa.md)

### R12. 什么是微前端？什么时候用？

- **来源倾向**: 一面 / 二面
- **难度**: 中级

**答案**

- 把前端应用拆成可以独立开发、部署的子应用，由主应用在运行时组合
- 适用：多团队必须独立发布、技术栈异构、渐进迁移老系统
- 不适用：单团队、同技术栈、只是构建慢

**口述模板（30–60 秒）**

2. **关键机制**：主应用在运行时按路由加载子应用。
3. **对比或注意点**：代价是运行时复杂度、性能和一致性，很多问题用 Monorepo 就能解决。
4. **可追问时补充**：异构和老系统迁移是最典型的使用场景。

### R13. qiankun 的 JS 沙箱原理？

- **来源倾向**: 二面 / 三面、高频
- **难度**: 高级

**答案**

- 快照沙箱：激活时记录 window 快照，失活时 diff 恢复；只支持单实例
- 代理沙箱：Proxy 拦截，写入 fakeWindow，读取时回退到真实 window；支持多实例
- 用 `with` + `new Function` 让子应用的全局访问指向代理
- 还要劫持定时器、事件监听、动态插入的 script / style

详见：[20-mid-qa.md Q18–Q20](./20-mid-qa.md)、[40-coding-handwritten.md H5](./40-coding-handwritten.md)

**口述模板（30–60 秒）**

1. **一句话结论**：qiankun 有快照沙箱和代理沙箱两种实现。
2. **关键机制**：代理沙箱用 Proxy 把写操作放到 fakeWindow，读取时先查 fakeWindow 再回退到真实 window。
3. **对比或注意点**：快照沙箱只能单实例，代理沙箱支持多个子应用同时运行。
4. **可追问时补充**：沙箱不是安全边界，原型链修改等仍然可能逃逸。

### R15. qiankun 为什么不支持 Vite 开发的子应用？

- **来源倾向**: 二面
- **难度**: 中级

**答案**

- qiankun 通过 fetch 脚本文本 + `with` / `eval` 在沙箱中执行
- Vite 的产物和开发服务都是 ESM（`type="module"`、`import`），无法用 eval 执行
- 解决：插件（vite-plugin-qiankun，牺牲部分沙箱）、wujie、micro-app

详见：[20-mid-qa.md Q21](./20-mid-qa.md)

### R16. wujie 的原理？和 qiankun 有什么区别？

- **来源倾向**: 二面
- **难度**: 中级

**答案**

- JS 在同域 iframe 中运行（天然隔离 window），DOM 渲染在主应用的 Web Component（Shadow DOM）中
- 通过代理把 iframe 中的 DOM 操作指向 Shadow DOM
- 隔离更彻底、支持 ESM；代价是 iframe 的创建开销和代理的复杂度

详见：[20-mid-qa.md Q22](./20-mid-qa.md)

### R17. Module Federation 是什么？shared 怎么工作？

- **来源倾向**: 二面 / 三面
- **难度**: 高级

**答案**

- 运行时从远程应用加载模块，像本地模块一样使用
- shared：协商共享依赖，满足版本范围时复用同一份；`singleton` 保证只有一个实例（React）
- 需要异步边界（bootstrap）
- MF 2.0：运行时与构建工具解耦，支持 manifest、类型同步、运行时插件

详见：[10-junior-qa.md Q27](./10-junior-qa.md)、[20-mid-qa.md Q23–Q24](./20-mid-qa.md)

**口述模板（30–60 秒）**

1. **一句话结论**：Module Federation 让应用在运行时互相加载模块。
2. **关键机制**：shared 依赖在运行时协商版本，满足范围时复用同一份。
3. **对比或注意点**：React 这类库必须设置为单例，版本不满足时只有警告。
4. **可追问时补充**：MF 2.0 把运行时独立出来，支持多种构建工具。

### R19. GitHub Actions 有哪些安全注意事项？

- **来源倾向**: 二面 / 三面、近年热点
- **难度**: 高级

**答案**

- 第三方 Action 固定 commit SHA（tj-actions 事件，CVE-2025-30066）
- 最小权限 `permissions`
- 谨慎使用 `pull_request_target`（pwn request）；新版 checkout 默认拒绝检出 fork PR
- 不可信输入通过 `env` 传入，不直接插值到脚本
- OIDC 代替长期密钥

详见：[20-mid-qa.md Q11](./20-mid-qa.md)、[30-senior-qa.md Q5](./30-senior-qa.md)、[40-coding-handwritten.md H8](./40-coding-handwritten.md)
