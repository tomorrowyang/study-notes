## 一、Monorepo 原理

### Q1. Monorepo 工具的任务图是怎么构建和执行的？

- **难度**: 中级
- **标签**: Monorepo, 任务图

**答案**

**构建任务图**：

1. **项目图**：读取每个包的 `package.json`，根据 `dependencies` / `devDependencies` 中的工作区依赖建立包之间的有向图
2. **任务图**：把「包 × 任务」作为节点，按配置连边
   - `dependsOn: ["^build"]`：`web#build` 依赖 `ui#build`（依赖包的同名任务）
   - `dependsOn: ["build"]`：`web#test` 依赖 `web#build`（同一包的其他任务）
3. 检测环（循环依赖会报错）

**执行**：

- **拓扑排序**：入度为 0 的任务可以执行
- **并行**：同时执行多个就绪的任务，受并发数限制
- 每个任务执行前先查缓存，命中则跳过
- 一个任务失败时，依赖它的任务不再执行（其他独立的任务可以继续，取决于配置）

**口述模板（30–60 秒）**

1. 一句话结论：先根据包的依赖关系构建项目图，再按任务配置构建任务图。
2. 关键机制：^build 表示依赖包的 build 先执行，按拓扑顺序并行执行就绪的任务。
3. 对比或注意点：每个任务执行前先查缓存，循环依赖会报错。
4. 可追问时补充：并发数受机器资源限制，失败的任务会阻止下游任务。

**常见追问**

- 包之间出现循环依赖怎么办？→ 抽取公共部分为新的包，或者调整依赖方向；用工具（`madge`、Nx 项目图）检测。

### Q2. 任务缓存是怎么判断命中的？什么情况会导致错误的缓存命中？

- **难度**: 中级
- **标签**: 缓存

**答案**

**缓存键（哈希）的输入**：

- 任务相关的**源文件**内容（可以通过 `inputs` 配置范围）
- 依赖包的哈希（上游变化 → 下游失效）
- 锁文件中相关的外部依赖版本
- 任务配置（`turbo.json` 中的设置）、执行的命令
- **声明的环境变量**（`env`、`globalEnv`）
- 全局依赖文件（根目录的 `tsconfig.json` 等，`globalDependencies`）

**命中时**：恢复 `outputs` 声明的产物和日志。

**错误命中（缓存「中毒」）的原因**：

| 原因 | 例子 | 解决 |
|------|------|------|
| **未声明的环境变量** | 构建读取 `API_URL`，但没有加入 `env` → 不同环境复用同一个产物 | 声明所有影响产物的环境变量（Turborepo 的严格环境模式会过滤未声明的变量） |
| 未声明的输入文件 | 读取了包外的文件 | 配置 `inputs` / 全局依赖 |
| 任务不确定 | 产物中包含时间戳、随机数 | 让构建可复现 |
| `outputs` 不完整 | 缓存命中后缺少文件 | 声明完整的产物路径 |

**口述模板（30–60 秒）**

1. 一句话结论：缓存键由源文件、依赖包的哈希、外部依赖版本、配置和声明的环境变量计算。
2. 关键机制：命中时恢复声明的产物和日志，不再执行任务。
3. 对比或注意点：最常见的错误命中是构建依赖了没有声明的环境变量。
4. 可追问时补充：任务必须是确定的，产物中不能包含时间戳等变化的内容。

**常见追问**

- 怎么排查缓存为什么没命中？→ 对比两次运行的哈希输入（`turbo run build --dry=json`、Nx 的 `--verbose`），找出变化的输入。

### Q3. 远程缓存是什么？有什么风险？

- **难度**: 中级
- **标签**: 远程缓存

**答案**

**远程缓存**：缓存存储在共享的服务器上（Vercel Remote Cache、Nx Cloud、自建的 S3 兼容存储），团队成员和 CI 共享。一个人构建过的，其他人直接下载产物。

**收益**：CI 时间显著下降（大部分包没有变化）；本地切换分支后的首次构建更快。

**风险与措施**：

| 风险 | 措施 |
|------|------|
| **缓存投毒**：有写权限的人（或被攻破的 CI 任务）上传恶意产物，其他人和生产构建使用 | **只允许受信任的 CI（主干）写入**，开发者和 PR 只读；产物签名 |
| 错误命中导致线上问题 | 正确声明输入；生产构建可以选择不读远程缓存或校验 |
| 泄露：产物中包含源码和配置 | 访问控制、加密 |
| 存储成本 | 设置过期时间 |

**口述模板（30–60 秒）**

1. 一句话结论：远程缓存把任务产物存在共享的服务器上，团队和 CI 共享。
2. 关键机制：一个人构建过的任务，其他人直接下载产物。
3. 对比或注意点：最大的风险是缓存投毒，只允许受信任的 CI 写入。
4. 可追问时补充：产物可以签名，生产构建可以选择不读远程缓存。

**常见追问**

- 为什么 PR 的 CI 不能写入远程缓存？→ PR 中可能包含恶意代码（特别是外部贡献者），写入的产物会被主干和其他人复用。

### Q4. 受影响分析（affected）是怎么实现的？有什么局限？

- **难度**: 中级
- **标签**: 受影响分析

**答案**

**实现**：

1. 获取变更的文件：`git diff --name-only <base>...HEAD`（base 通常是主干的合并基点）
2. 把文件映射到所属的包
3. 在项目图中**反向**查找：依赖这些包的所有包也受影响
4. 全局文件（根配置、锁文件）变化 → 视为全部受影响（或按锁文件中具体变化的依赖判断）

**局限**：

- 依赖于正确的项目图：**未声明的依赖**（动态导入、通过路径引用其他包的文件）不会被识别
- 全局配置变化导致大面积重新执行
- base 选择错误（例如浅克隆没有主干的历史）→ 分析不准确
- 非代码依赖（例如共享的 JSON 资源、环境）需要额外配置

**与缓存的关系**：受影响分析决定「跑哪些」，缓存决定「跑的时候能否跳过」，两者互补。

**口述模板（30–60 秒）**

1. 一句话结论：受影响分析通过 Git 差异找到变更的包，再在项目图中反向找出依赖它们的包。
2. 关键机制：全局配置文件变化时视为全部受影响。
3. 对比或注意点：依赖正确的项目图，未声明的依赖不会被识别。
4. 可追问时补充：CI 中要获取完整的 Git 历史，否则 base 计算不准确。

**常见追问**

- CI 中使用浅克隆会有什么问题？→ 找不到合并基点，无法正确计算差异；需要 `fetch-depth: 0` 或者至少获取主干的引用。

### Q5. Monorepo 中的内部包应该引用源码还是构建产物？

- **难度**: 中级
- **标签**: Monorepo, 内部包

**答案**

| 方式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **引用源码**（Just-in-Time） | `exports` 指向 `src/index.ts`，由使用方的构建工具编译 | 无需预构建、修改即时生效、跳转到源码 | 使用方要能编译它（TS 配置、JSX、别名一致）；构建慢（重复编译） |
| **引用构建产物** | 包先构建到 `dist`，`exports` 指向产物 | 边界清晰、可以缓存、使用方简单 | 需要先构建；开发时需要 watch |
| **TS 项目引用（project references）** | `tsc -b` 增量构建，按引用关系编译 | 类型检查增量、快 | 配置复杂 |

```json
// 引用源码的内部包
{
  "name": "@acme/utils",
  "exports": { ".": "./src/index.ts" }
}
```

**建议**：应用内部使用的包可以引用源码（简单）；需要发布到 npm 的包使用构建产物；类型检查用项目引用加速。

**口述模板（30–60 秒）**

1. 一句话结论：内部包可以引用源码由使用方编译，也可以预先构建后引用产物。
2. 关键机制：引用源码无需预构建，修改即时生效；引用产物边界清晰、可以缓存。
3. 对比或注意点：引用源码要求使用方的编译配置兼容，包多了构建会变慢。
4. 可追问时补充：发布到 npm 的包必须使用构建产物，类型检查可以用项目引用加速。

**常见追问**

- `exports` 字段有什么作用？→ 定义包的公共入口，限制使用方只能导入声明的路径（封装内部文件），并可以按条件（`import`、`require`、`types`）提供不同的文件。

### Q6. 怎么在 Monorepo 中保持依赖版本一致？

- **难度**: 中级
- **标签**: 依赖管理

**答案**

**问题**：不同包依赖同一个库的不同版本 → 重复打包、多实例（React 的 Hooks 报错）、行为不一致。

**手段**：

| 手段 | 说明 |
|------|------|
| **pnpm catalogs** | 在 `pnpm-workspace.yaml` 中统一定义版本，各包用 `catalog:` 引用 |
| 单一版本策略 | 所有包必须使用相同版本（Nx、Rush 支持；`syncpack` 检查） |
| `overrides` | 强制间接依赖的版本 |
| 依赖检查 | CI 中检查是否有同一个库的多个版本（`pnpm why`、`syncpack lint`） |
| Renovate 分组 | 同一个库的升级在一个 PR 中完成 |

**例外**：迁移期间允许暂时存在两个版本，但要有计划。

**口述模板（30–60 秒）**

1. 一句话结论：用 pnpm catalogs 或单一版本策略统一依赖版本。
2. 关键机制：catalogs 在工作区配置中集中定义版本，各包引用。
3. 对比或注意点：版本不一致会导致重复打包和多实例问题。
4. 可追问时补充：CI 中检查重复版本，Renovate 分组升级。

**常见追问**

- 某个应用必须使用旧版本怎么办？→ 用命名的 catalog 允许例外，但要有升级计划和负责人。

### Q7. 怎么在 Monorepo 中约束模块边界？

- **难度**: 中级
- **标签**: 架构, 模块边界

**答案**

**问题**：没有约束时，任何包都可以导入任何包 → 循环依赖、领域之间耦合、UI 库依赖业务代码。

**手段**：

- **Nx 的 `@nx/enforce-module-boundaries`**：给项目打标签（`type:ui`、`scope:orders`），声明哪些标签可以依赖哪些标签

```json
{
  "depConstraints": [
    { "sourceTag": "type:app", "onlyDependOnLibsWithTags": ["type:feature", "type:ui", "type:util"] },
    { "sourceTag": "type:ui", "onlyDependOnLibsWithTags": ["type:ui", "type:util"] },
    { "sourceTag": "scope:orders", "onlyDependOnLibsWithTags": ["scope:orders", "scope:shared"] }
  ]
}
```

- **`exports`**：包只暴露公共入口，禁止深层导入
- **ESLint `no-restricted-imports`** / dependency-cruiser：路径级别的规则
- **CODEOWNERS**：共享包的修改需要对应团队评审

**口述模板（30–60 秒）**

1. 一句话结论：用基于标签的依赖规则约束包之间的依赖方向。
2. 关键机制：给包打上类型和领域的标签，规定哪些标签可以依赖哪些标签。
3. 对比或注意点：用 exports 限制只能导入公共入口。
4. 可追问时补充：CODEOWNERS 让共享包的修改需要对应团队评审。

**常见追问**

- 不用 Nx 怎么做？→ dependency-cruiser 或自定义 ESLint 规则读取包的元数据实现类似的约束（见手写题 H12）。

### Q8. pnpm 的严格模式会带来什么问题？怎么处理？

- **难度**: 中级
- **标签**: pnpm

**答案**

**pnpm 不提升依赖**，所以：

| 问题 | 原因 | 处理 |
|------|------|------|
| 某些包找不到依赖 | 包本身有幽灵依赖（使用了没声明的依赖） | `packageExtensions` 为它补充声明；或 `public-hoist-pattern` 提升特定包 |
| 工具要求依赖在根目录 | 一些老工具（如某些 ESLint 插件、React Native 的 Metro）假设扁平结构 | 提升对应的包；或 `node-linker=hoisted`（放弃严格性） |
| **peer 依赖导致多份副本** | 同一个包在不同 peer 依赖组合下被安装为不同的实例（依赖分身） | 统一 peer 依赖的版本 |
| 构建脚本被阻止 | pnpm 10+ 默认不执行依赖的安装脚本 | 在 `allowBuilds`（pnpm 11）/ `onlyBuiltDependencies`（pnpm 10）中显式允许 |

**口述模板（30–60 秒）**

1. 一句话结论：pnpm 不提升依赖，会暴露包本身的幽灵依赖问题。
2. 关键机制：可以用 packageExtensions 补充声明，或提升特定的包。
3. 对比或注意点：peer 依赖不一致会导致同一个包有多个实例。
4. 可追问时补充：pnpm 10 以后默认不执行依赖的安装脚本，需要显式允许。

**常见追问**

- 为什么默认不执行安装脚本？→ 安装脚本是供应链攻击的主要入口（例如 Shai-Hulud），详见[前端安全专题](../frontend-security/20-mid-qa.md)。

## 二、CI/CD

### Q9. CI 太慢，你会怎么优化？

- **难度**: 中级
- **标签**: CI, 性能

**答案**

**先度量**：每个阶段的耗时（安装、Lint、测试、构建、部署），找到瓶颈。

| 手段 | 说明 |
|------|------|
| **依赖缓存** | 缓存 pnpm 存储（以锁文件哈希为键）；或者使用预装依赖的镜像 |
| **任务缓存（远程）** | 没有变化的包直接复用产物 |
| **只跑受影响的** | `--affected` |
| **并行** | Lint、类型检查、测试拆成并行的 Job |
| **测试分片** | 把测试拆分到多台机器（Playwright `--shard`、Vitest `--shard`） |
| 更快的工具 | esbuild / SWC / Rspack、Vitest、Biome / oxlint |
| **快速失败** | 便宜的检查先跑；失败时取消其他 Job |
| 更强的运行器 | 更多 CPU、自托管运行器 |
| 取消过时的运行 | 同一个 PR 推送新提交时取消旧的运行（`concurrency`） |
| 减少不必要的触发 | 只修改文档时跳过（路径过滤） |

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

**口述模板（30–60 秒）**

1. 一句话结论：先度量每个阶段的耗时，再针对瓶颈优化。
2. 关键机制：依赖缓存、远程任务缓存、只跑受影响的任务和并行分片是收益最大的手段。
3. 对比或注意点：快速失败，便宜的检查先跑，取消过时的运行。
4. 可追问时补充：更换更快的工具和更强的运行器也有明显效果。

**常见追问**

- 优化后怎么防止回退？→ 监控 CI 耗时的趋势，超过阈值告警。

### Q10. 不稳定的测试（flaky test）怎么处理？

- **难度**: 中级
- **标签**: 测试, CI

**答案**

**危害**：开发者习惯性地重新运行 → 真正的失败被忽视；浪费 CI 资源；降低对测试的信任。

**常见原因**：

- 依赖时间（`Date.now()`、时区）、随机数
- 异步等待不正确（固定的 `sleep`、没有等待元素出现）
- 测试之间共享状态（全局变量、数据库数据、执行顺序依赖）
- 依赖外部服务（网络）
- 资源竞争（并行执行时的端口、文件）

**处理流程**：

1. **检测**：记录每个测试的历史结果，识别时好时坏的测试
2. **隔离**：标记为隔离（quarantine），不阻塞合并，但仍然运行和统计
3. **修复**：分配负责人，限期修复
4. **预防**：模拟时间和网络、每个测试独立的数据、等待明确的条件

**口述模板（30–60 秒）**

1. 一句话结论：不稳定的测试会让团队忽视真正的失败，必须检测、隔离并修复。
2. 关键机制：常见原因是依赖时间、异步等待不正确、测试之间共享状态和依赖外部服务。
3. 对比或注意点：自动重试只能缓解，不能代替修复。
4. 可追问时补充：用历史结果识别不稳定的测试，隔离后分配负责人修复。

**常见追问**

- 可以对失败的测试自动重试吗？→ 可以作为短期缓解，但要记录重试的次数，重试后通过的测试仍然视为不稳定。

### Q11. GitHub Actions 有哪些安全风险？怎么防护？

- **难度**: 中级
- **标签**: CI 安全

**答案**

| 风险 | 说明 | 防护 |
|------|------|------|
| **第三方 Action 被篡改** | 标签是可变的；2025-03 `tj-actions/changed-files` 的标签被改指向恶意提交，泄露了大量仓库的密钥（CVE-2025-30066） | **固定到完整的提交 SHA**（附带版本注释）；Dependabot 更新；组织策略强制 |
| **pwn request** | `pull_request_target` 以基础仓库的权限运行，若检出并执行 fork 的代码 → 攻击者获得密钥和写权限 | 避免 `pull_request_target`；必须使用时不执行 PR 的代码；`actions/checkout` v7 默认拒绝这种检出（2026-06） |
| **脚本注入** | 在 `run` 中直接插值 `${{ github.event.pull_request.title }}` → 标题中的 shell 命令被执行 | 通过环境变量传入：`env: TITLE: ${{ ... }}`，在脚本中用 `"$TITLE"` |
| 过大的令牌权限 | `GITHUB_TOKEN` 默认权限 | `permissions` 设置最小权限 |
| 长期密钥 | 云服务和 npm 的长期令牌泄露 | **OIDC** 获取短期令牌；npm 可信发布 |
| 自托管运行器 | 公开仓库的 PR 在自托管运行器上执行 → 持久化攻击 | 公开仓库不用自托管运行器；使用一次性运行器 |
| 缓存投毒 | 低权限的工作流写入缓存，被高权限的工作流使用 | 发布流程不复用 PR 的缓存 |

```yaml
- uses: some-org/some-action@8e5e7e5ab8b370d6c329ec480221332ada57f0ab # v3.2.1
```

**口述模板（30–60 秒）**

1. 一句话结论：主要风险是第三方 Action 被篡改、pwn request、脚本注入和过大的权限。
2. 关键机制：第三方 Action 固定到提交 SHA，令牌设置最小权限，用 OIDC 代替长期密钥。
3. 对比或注意点：避免在 pull_request_target 中执行 fork 的代码，不要在 run 中直接插值不可信的输入。
4. 可追问时补充：tj-actions 事件就是标签被篡改导致大量仓库的密钥泄露。

**常见追问**

- 有没有工具帮助检查？→ zizmor、actionlint、OpenSSF Scorecard 可以检查工作流中的常见问题。

### Q12. 前端灰度发布怎么实现？

- **难度**: 中级
- **标签**: 灰度发布

**答案**

**核心**：前端的静态资源都可以同时存在，灰度的关键是**决定用户拿到哪个版本的 HTML（入口）**。

```text
请求 index.html
   │
   ▼
网关 / CDN 边缘函数 / Node 服务
   - 读取用户标识（用户 ID、Cookie 中的分桶 ID、设备 ID）
   - 规则：白名单（内部员工）→ 比例（hash(uid) % 100 < 灰度比例）→ 地域 / 版本
   - 返回对应版本的 HTML（v2 引用 v2 的资源）
   - 设置 Cookie 固定分桶（保证一致性）
```

**关键点**：

- **一致性**：同一用户始终命中同一版本（按用户 ID 哈希，而不是随机）
- **HTML 不能被共享缓存**（或者缓存键包含分桶）
- **监控按版本拆分**：错误率、性能、业务指标按版本对比
- **自动化**：指标异常时自动停止放量 / 回滚
- **接口兼容**：新旧前端同时存在，后端接口要兼容两个版本

**口述模板（30–60 秒）**

1. 一句话结论：前端灰度的关键是在入口层决定用户拿到哪个版本的 HTML。
2. 关键机制：在网关或边缘函数中按用户标识的哈希分桶，返回对应版本的 HTML。
3. 对比或注意点：同一用户要始终命中同一版本，HTML 不能被共享缓存。
4. 可追问时补充：监控按版本拆分，异常时自动停止放量或回滚。

**常见追问**

- 单页应用打开很久不刷新，灰度怎么生效？→ 定期检查版本（轮询版本文件），有新版本时提示刷新；或在路由切换时检查。

### Q15. 怎么处理发布后「旧页面懒加载代码块失败」的问题？

- **难度**: 中级
- **标签**: 部署, 版本

**答案**

**原因**：用户打开了旧版本的页面，发布后旧版本的代码块被删除（或 CDN 没有），用户点击路由时懒加载失败。

**处理**：

1. **部署侧**：保留旧版本的资源一段时间（例如 7 天或最近 N 个版本），不在发布时清空目录
2. **前端侧**：
   - 捕获代码块加载失败的错误（`ChunkLoadError`、`Failed to fetch dynamically imported module`），**刷新页面一次**（防止无限刷新）
   - Vite 提供 `vite:preloadError` 事件
3. **版本检测**：定期检查版本文件，有新版本时提示用户刷新
4. **Service Worker**：缓存当前版本的所有资源，更新时提示用户

**口述模板（30–60 秒）**

1. 一句话结论：原因是旧页面懒加载的代码块在发布后被删除。
2. 关键机制：部署时保留旧版本的资源一段时间。
3. 对比或注意点：前端捕获加载失败的错误后刷新一次，要防止无限刷新。
4. 可追问时补充：定期检查版本，有新版本时提示用户刷新。

**常见追问**

- 刷新后用户的输入丢失怎么办？→ 在刷新前提示用户；或者在路由切换时（而不是用户操作中）检测并刷新。

### Q17. 怎么保证构建的可复现性？

- **难度**: 中级
- **标签**: 构建

**答案**

**可复现**：相同的源码和依赖，在任何时间、任何机器上构建出相同的产物。

**手段**：

**口述模板（30–60 秒）**

1. 一句话结论：可复现构建要求相同的输入在任何环境都构建出相同的产物。
2. 关键机制：锁文件、固定 Node 和包管理器版本、固定构建镜像。
3. 对比或注意点：产物中不能包含时间戳和绝对路径。
4. 可追问时补充：可复现是缓存有效和供应链验证的基础。

### Q18. 快照沙箱是怎么实现的？

- **难度**: 中级
- **标签**: 沙箱

**答案**

用于**不支持 Proxy 的环境**（qiankun 的 `SnapshotSandbox`）：

- **激活时**：遍历 `window` 的所有属性，保存快照；然后恢复该子应用上次运行时的修改
- **失活时**：再次遍历 `window`，与快照对比，记录子应用做的修改（diff）；然后把 `window` 恢复为快照

```ts
class SnapshotSandbox {
  private snapshot: Record<string, unknown> = {};
  private modified: Record<string, unknown> = {};

  active() {
    for (const key in window) this.snapshot[key] = (window as any)[key];
    Object.assign(window, this.modified);
  }

  inactive() {
    for (const key in window) {
      if ((window as any)[key] !== this.snapshot[key]) {
        this.modified[key] = (window as any)[key];
        (window as any)[key] = this.snapshot[key];
      }
    }
  }
}
```

**局限**：

- 只能**单实例**（同一时间只能运行一个子应用，因为直接修改真实的 window）
- 遍历 window 性能差
- 删除的属性、不可枚举的属性处理不完整

**口述模板（30–60 秒）**

1. 一句话结论：快照沙箱在激活时保存 window 的快照，失活时记录修改并恢复快照。
2. 关键机制：下次激活时再把记录的修改恢复回去。
3. 对比或注意点：直接修改真实的 window，只能同时运行一个子应用。
4. 可追问时补充：用于不支持 Proxy 的环境，遍历 window 性能差。

**常见追问**

- 为什么快照沙箱只能单实例？→ 所有子应用修改的都是同一个真实的 window，多个同时运行会互相覆盖。

### Q19. 代理沙箱（Proxy Sandbox）是怎么实现的？

- **难度**: 中级
- **标签**: 沙箱

**答案**

**多实例代理沙箱**（qiankun 的 `ProxySandbox`）：

- 为每个子应用创建一个 **fakeWindow** 对象
- 用 `Proxy` 代理 fakeWindow：
  - **写入**：写到 fakeWindow，不影响真实的 window
  - **读取**：先读 fakeWindow，没有再读真实的 window
- 子应用的代码在这个代理上执行：`(function(window, self, globalThis){ ... }).call(proxy, proxy, proxy, proxy)`，或者用 `with(proxy)` 处理裸的全局变量访问

**细节**：

- 原生函数（`fetch`、`setTimeout`）通过代理调用时，需要**绑定到真实的 window**，否则报 `Illegal invocation`
- `window.window`、`window.self`、`window.top` 要返回代理本身（或真实值，视情况）
- 一些属性需要「逃逸」到真实的 window（如 `document`、`location`）
- `Symbol.unscopables` 处理 `with` 中的查找

**优点**：支持多个子应用同时运行；不修改真实的 window。

**口述模板（30–60 秒）**

1. 一句话结论：代理沙箱为每个子应用创建一个假的 window，用 Proxy 拦截读写。
2. 关键机制：写入到假 window，读取时先读假 window，没有再读真实 window。
3. 对比或注意点：原生函数要绑定到真实的 window，否则调用报错。
4. 可追问时补充：支持多个子应用同时运行，不修改真实的 window。

**常见追问**

- 子应用的代码怎么在代理上执行？→ 把脚本内容包装成函数，用代理作为 `window`、`self`、`globalThis` 参数传入，配合 `with` 处理直接访问的全局变量。

### Q20. JS 沙箱能防住什么？防不住什么？

- **难度**: 中级
- **标签**: 沙箱, 局限

**答案**

**能防住**（隔离副作用，避免冲突）：

- 子应用之间全局变量的冲突
- 子应用卸载后残留的全局变量
- 配合补丁：定时器、事件监听、动态添加的样式和脚本在卸载时清理

**防不住**：

| 问题 | 原因 |
|------|------|
| **原型链污染** | `Array.prototype.xxx = ...` 修改的是共享的内置对象 |
| **DOM** | 子应用操作 `document`（同一个文档），可以访问和修改其他应用的 DOM |
| Cookie、localStorage | 同源共享 |
| 逃逸 | 通过 `Function('return this')()`、DOM 元素的 `ownerDocument.defaultView` 等获取真实的 window |
| 性能 | 每次全局访问经过 Proxy |

**结论**：同源的 JS 沙箱**不是安全边界**，只用于**防止冲突**；不可信的代码必须用跨源 iframe 隔离。

**口述模板（30–60 秒）**

1. 一句话结论：JS 沙箱能防止全局变量冲突和残留，但不是安全边界。
2. 关键机制：配合补丁可以清理定时器、事件监听和动态添加的样式。
3. 对比或注意点：防不住原型链污染、DOM 访问、存储共享和各种逃逸方式。
4. 可追问时补充：不可信的代码必须用跨源 iframe 隔离。

**常见追问**

- 为什么 wujie 隔离更彻底？→ 子应用的 JS 运行在 iframe 中，拥有独立的 window 和内置对象（原型链不共享），只有 DOM 渲染被代理到主文档的 Web Component 中。

### Q21. HTML Entry 是怎么工作的？

- **难度**: 中级
- **标签**: HTML Entry

**答案**

qiankun 通过 `import-html-entry` 以**子应用的 HTML 地址**作为入口（而不是 JS 入口）：

1. `fetch` 子应用的 HTML
2. 解析 HTML：
   - 提取外链和内联的 **脚本**（按顺序）
   - 提取 **样式**（外链的 CSS 通过 fetch 获取内容，转为内联 `<style>`）
   - 处理相对路径（基于子应用的地址）
   - 移除脚本标签，得到模板
3. 把模板放入容器
4. `fetch` 所有脚本内容，**在沙箱中依次执行**（包装函数 + 代理 window）
5. 从执行结果（或代理 window 上）获取子应用导出的生命周期

**优点**：子应用像独立应用一样开发，接入时不需要知道它的 JS 文件名（哈希变化也没关系）。

**JS Entry 对比**：直接加载子应用的 JS 入口文件，需要一个固定的入口名或清单文件。

**口述模板（30–60 秒）**

1. 一句话结论：HTML Entry 以子应用的 HTML 作为入口，解析出脚本和样式后在沙箱中执行。
2. 关键机制：fetch HTML，提取脚本和样式，处理相对路径，脚本在沙箱中依次执行。
3. 对比或注意点：子应用的 JS 文件名变化不影响接入。
4. 可追问时补充：执行完成后从子应用的导出中获取生命周期函数。

**常见追问**

- 为什么 qiankun 对 Vite 子应用支持不好？→ Vite 产物是 ES 模块（`<script type="module">`），无法用「获取文本 + 包装函数 + eval」的方式在沙箱中执行（模块的 `import` 语法不能在函数中执行）；需要插件把子应用转换，或者使用支持 ESM 的方案。

### Q22. wujie 的原理是什么？

- **难度**: 中级
- **标签**: wujie

**答案**

**核心思想**：**JS 运行在 iframe 中，DOM 渲染在 Web Component（Shadow DOM）中**。

1. 为子应用创建一个**同源的 iframe**（加载主应用的同源空白页，然后注入子应用的脚本），JS 在 iframe 中运行 → 拥有独立的 window 和内置对象，天然隔离
2. 在主文档中创建一个 Web Component（`wujie-app`），子应用的 DOM 渲染在它的 Shadow DOM 中 → 样式隔离
3. **代理 iframe 中的 `document`**：子应用调用 `document.querySelector`、`document.body.appendChild` 时，被代理到 Shadow DOM 中
4. **路由同步**：iframe 的 URL 与主应用的 URL 同步（子应用的路由存在主应用的查询参数中），刷新不丢失
5. **保活模式**：切换时不销毁 iframe 和 Web Component，再次进入时直接恢复

**优缺点**：隔离彻底、子应用几乎无需改造、支持 Vite；代价是 iframe 和代理的开销、弹窗等需要特殊处理。

**口述模板（30–60 秒）**

1. 一句话结论：wujie 让 JS 在 iframe 中运行，DOM 渲染在 Web Component 中。
2. 关键机制：iframe 提供天然的 JS 隔离，Shadow DOM 提供样式隔离，document 的操作被代理到 Shadow DOM。
3. 对比或注意点：路由同步到主应用的 URL，支持保活。
4. 可追问时补充：子应用改造成本低，支持 Vite，代价是 iframe 和代理的开销。

**常见追问**

- 为什么 iframe 要同源？→ 同源才能从主应用直接访问和代理 iframe 的 window 和 document，并注入脚本。

### Q23. Module Federation 的共享依赖是怎么协商版本的？

- **难度**: 中级
- **标签**: Module Federation

**答案**

**配置**：

```js
shared: {
  react: { singleton: true, requiredVersion: '^19.0.0', eager: false },
  lodash: { requiredVersion: '^4.17.0' },
}
```

**协商过程**（简化）：

1. 各应用初始化时，把自己提供的共享依赖**注册到共享作用域**（版本 + 加载函数）
2. 某个应用需要共享依赖时，在作用域中查找**满足 `requiredVersion` 的最高版本**
3. `singleton: true`：只使用一个版本（通常是已注册的最高版本）；如果不满足某个应用的 `requiredVersion`，**发出警告**（`strictVersion: true` 时报错）
4. 非单例：不满足时加载自己的版本（可能同时存在多个版本）

**要点**：

- React、Vue、状态管理库、路由 → 必须 `singleton`
- `eager: true`：打包进入口文件同步提供（避免异步加载），但增加入口体积
- 宿主应用通常需要一个**异步边界**（`import('./bootstrap')`），确保共享作用域初始化完成后再执行业务代码

**口述模板（30–60 秒）**

1. 一句话结论：各应用把共享依赖注册到共享作用域，需要时选择满足版本要求的最高版本。
2. 关键机制：singleton 只使用一个版本，版本不满足要求时警告或报错。
3. 对比或注意点：React 这类框架必须设为单例，否则多实例会出错。
4. 可追问时补充：入口需要异步边界，保证共享作用域初始化后再执行业务代码。

**常见追问**

- 为什么会出现 `Shared module is not available for eager consumption` 错误？→ 共享模块被同步使用，但它是异步提供的；加异步边界（bootstrap 文件），或设置 `eager: true`。

### Q24. Module Federation 2.0 有哪些变化？

- **难度**: 中级
- **标签**: Module Federation

**答案**

（以官方文档为准）

- **运行时与构建工具解耦**：独立的运行时（`@module-federation/enhanced` / runtime），支持 Webpack、Rspack、Rollup、Rolldown、Rsbuild、Vite、Metro（React Native）

- **运行时 API**：`registerRemotes`、`loadRemote`，**动态注册**远程应用（按配置中心下发的地址）
- **Node.js 支持**：服务端渲染中加载远程模块
- 调试工具（Chrome 扩展）

**口述模板（30–60 秒）**

1. 一句话结论：2.0 把运行时与构建工具解耦，支持更多的构建工具。
2. 关键机制：Manifest 描述远程应用的模块和类型，运行时 API 支持动态注册远程应用。
3. 对比或注意点：提供动态类型提示和运行时插件。
4. 可追问时补充：支持 Node.js 和 React Native 的 Metro。

**常见追问**

- 运行时插件能做什么？→ 远程加载失败时重试或降级到备用地址、上报加载耗时、按灰度规则选择远程版本。

### Q25. 微前端的路由怎么设计？

- **难度**: 中级
- **标签**: 微前端, 路由

**答案**

**主应用负责一级路由**（决定加载哪个子应用），**子应用负责自己的二级路由**：

```text
/orders/*   → 子应用 orders（内部路由 base = /orders）
/reports/*  → 子应用 reports
```

**要点**：

- 子应用的路由 `base` 与 `activeRule` 一致
- 统一使用 history 模式（或统一 hash 模式），避免混用
- **子应用之间的跳转**：修改 URL（`history.pushState` + 触发 `popstate`），或主应用提供的导航方法；不要直接调用其他子应用的路由实例
- 子应用卸载时销毁自己的路由实例和监听
- 刷新时直接访问 `/orders/123` → 主应用根据 URL 加载子应用，子应用根据剩余路径渲染
- 404：主应用兜底

**口述模板（30–60 秒）**

1. 一句话结论：主应用负责一级路由决定加载哪个子应用，子应用负责自己的二级路由。
2. 关键机制：子应用的路由 base 与激活规则一致。
3. 对比或注意点：子应用之间通过修改 URL 或主应用提供的方法跳转。
4. 可追问时补充：子应用卸载时要销毁路由实例和监听。

**常见追问**

- 多个子应用同时显示（一个页面中两个子应用）时路由怎么处理？→ 只有一个子应用可以控制 URL；其他子应用使用内存路由。

### Q26. 微前端的性能怎么优化？

- **难度**: 中级
- **标签**: 微前端, 性能

**答案**

| 问题 | 优化 |
|------|------|
| 子应用加载慢 | **预加载**：空闲时预取其他子应用的资源（qiankun `prefetch`，3.x 改为流式加载自动预加载） |
| 重复的依赖（每个子应用都打包 React） | 共享依赖：Module Federation `shared`、externals + CDN（统一版本） |
| 多个框架实例同时运行 | 统一技术栈和版本；卸载不活跃的子应用 |
| 沙箱开销 | 必要时关闭不需要的隔离；wujie 的保活模式避免重复初始化 |
| 首屏 | 主应用尽量轻量；首屏子应用和主应用并行加载 |
| 内存泄漏 | 子应用卸载时彻底清理；监控长时间运行的内存 |

**口述模板（30–60 秒）**

1. 一句话结论：微前端的性能问题主要是子应用加载慢、重复依赖和多个框架实例。
2. 关键机制：空闲时预加载子应用，共享公共依赖。
3. 对比或注意点：统一技术栈和版本可以减少重复，卸载不活跃的子应用。
4. 可追问时补充：子应用卸载时要彻底清理，避免长时间运行的内存泄漏。

**常见追问**

- externals + CDN 和 Module Federation 共享依赖的区别？→ externals 要求所有应用使用 CDN 上的同一个版本（强约束、简单）；MF 可以协商版本，更灵活但更复杂。

### Q27. 微前端的子应用怎么部署和管理版本？

- **难度**: 中级
- **标签**: 微前端, 部署

**答案**

**问题**：主应用中写死子应用的地址和版本 → 子应用发布需要修改主应用。

**方案**：**子应用注册中心（配置中心）**

```json
// 主应用启动时从配置中心获取
{
  "orders": { "entry": "https://cdn.example.com/orders/1.4.2/", "activeRule": "/orders" },
  "reports": { "entry": "https://cdn.example.com/reports/2.0.1/", "activeRule": "/reports" }
}
```

- 子应用发布：构建 → 上传到带版本号的目录 → 在配置中心更新版本（可以先灰度）
- **回滚**：配置中心切回旧版本
- **灰度**：配置中心按用户返回不同的子应用版本
- **兼容性**：子应用依赖主应用提供的能力（props、共享依赖版本），需要声明兼容的主应用版本范围

**口述模板（30–60 秒）**

1. 一句话结论：用配置中心管理子应用的地址和版本，主应用启动时获取。
2. 关键机制：子应用发布到带版本号的目录，在配置中心切换版本。
3. 对比或注意点：回滚和灰度都通过配置中心完成，不需要重新发布主应用。
4. 可追问时补充：子应用要声明兼容的主应用版本，避免能力不匹配。

**常见追问**

- 配置中心挂了怎么办？→ 主应用内置一份兜底配置（构建时的最新版本），或者缓存上一次成功获取的配置。

### Q28. 怎么在 Module Federation 中保证类型安全？

- **难度**: 中级
- **标签**: Module Federation, TypeScript

**答案**

**问题**：`import('orders/OrderList')` 在编译时无法知道类型。

**方案**：

| 方案 | 说明 |
|------|------|
| **MF 2.0 动态类型提示** | 提供方构建时生成类型文件，使用方开发时自动拉取 |
| 共享的类型包 | 在 Monorepo 中定义接口包，双方都依赖 |
| 手写声明文件 | `declare module 'orders/OrderList'`（容易过时） |

**运行时契约**：类型只是编译时的保证，运行时远程模块可能已经更新。需要：

- 暴露的接口有版本，破坏性修改走新的模块名或版本
- 使用方做防御（错误边界、加载失败的降级）
- 集成测试

**口述模板（30–60 秒）**

1. 一句话结论：MF 2.0 可以自动生成并拉取远程模块的类型，也可以用共享的类型包。
2. 关键机制：提供方构建时生成类型文件，使用方开发时下载。
3. 对比或注意点：类型只是编译时的保证，运行时远程模块可能已经更新。
4. 可追问时补充：暴露的接口要有版本，使用方要有错误边界和降级。

**常见追问**

- 远程模块加载失败时怎么降级？→ 错误边界显示降级内容；MF 运行时插件重试或切换到备用地址。

### Q29. 怎么设计团队的脚手架和代码生成器？

- **难度**: 中级
- **标签**: 脚手架

**答案**

**脚手架**：创建新项目（`create-xxx`）；**生成器**：在现有项目中生成代码（页面、组件、库）。

**设计要点**：

- **模板 + 交互**：选择项目类型、功能（路由、状态管理、测试），生成对应的文件
- **把规范固化到模板**：目录结构、ESLint / TS 配置、CI 配置、安全响应头、监控 SDK
- **配置以包的形式共享**：模板中引用 `@acme/eslint-config`、`@acme/tsconfig`，而不是复制配置 → 升级时只需要更新包版本
- **可升级**：提供迁移脚本，让已有项目跟进新规范（类似 `ng update` / Nx `migrate`）
- 工具：Plop、Hygen、Nx 生成器、自研 CLI

**口述模板（30–60 秒）**

1. 一句话结论：脚手架创建新项目，生成器在现有项目中生成代码，都是把规范固化到模板。
2. 关键机制：配置以共享包的形式引用，升级时只需要更新版本。
3. 对比或注意点：复制配置的方式会导致项目之间逐渐不一致。
4. 可追问时补充：提供迁移脚本让已有项目跟进新规范。

**常见追问**

- 脚手架生成的项目怎么跟进后续的规范变化？→ 配置都通过共享包引用；结构性的修改用 codemod 迁移脚本。

### Q30. 前端监控中，sourcemap 和版本怎么管理？

- **难度**: 中级
- **标签**: 监控, sourcemap

**答案**

**问题**：线上的代码是压缩的，错误堆栈无法阅读；但 sourcemap 公开会暴露源码。

**做法**：

1. 构建时生成 sourcemap（`hidden-source-map`：生成但不在产物中引用）
2. CI 中**上传 sourcemap 到监控平台**（Sentry 等），关联**发布版本号**（例如 Git 提交 SHA）
3. **不部署** sourcemap 到公开的 CDN（或部署后限制访问）
4. 前端 SDK 初始化时设置相同的版本号
5. 监控平台根据版本号找到对应的 sourcemap，还原堆栈

**版本号的用途**：按版本统计错误率（灰度对比）、定位引入问题的发布、关联代码提交。

**口述模板（30–60 秒）**

1. 一句话结论：构建时生成 sourcemap 上传到监控平台，但不公开部署。
2. 关键机制：sourcemap 和前端 SDK 使用相同的版本号，监控平台据此还原堆栈。
3. 对比或注意点：hidden-source-map 生成文件但不在产物中引用。
4. 可追问时补充：版本号还用于按版本统计错误率，对比灰度效果。

**常见追问**

- 为什么不直接公开 sourcemap？→ 暴露完整源码（包括注释、内部逻辑），可能泄露敏感信息和接口。

### Q31. 大规模代码修改（例如替换 API）怎么做？

- **难度**: 中级
- **标签**: codemod

**答案**

**codemod**：基于 **AST** 的自动化代码修改。

| 工具 | 特点 |
|------|------|
| **jscodeshift** | 基于 recast，保留格式，生态成熟 |
| **ast-grep** | 基于模式匹配，写法简单，速度快（Rust） |
| ts-morph | 基于 TypeScript 编译器 API，可以使用类型信息 |
| Babel 插件 | 适合编译时转换 |

**流程**：

1. 写 codemod，用测试用例（输入 → 期望输出）验证
2. 在小范围试运行，人工检查
3. 全量运行，**格式化**，运行类型检查和测试
4. 分批提交（按团队 / 目录），便于评审和回滚
5. 无法自动处理的情况标记出来（TODO 注释），人工处理
6. 加 Lint 规则防止新代码使用旧 API

**口述模板（30–60 秒）**

1. 一句话结论：大规模代码修改用基于 AST 的 codemod 自动完成。
2. 关键机制：常用 jscodeshift、ast-grep 和 ts-morph，用测试用例验证转换结果。
3. 对比或注意点：先小范围试运行，再全量运行并分批提交。
4. 可追问时补充：无法自动处理的情况标记出来人工处理，加 Lint 规则防止回退。

**常见追问**

- 为什么不用正则替换？→ 无法理解代码结构（作用域、导入别名、多行），容易误改或漏改。

### Q32. 构建工具怎么选？Webpack、Vite、Rspack？

- **难度**: 中级
- **标签**: 构建工具

**答案**

| 工具 | 特点 | 适合 |
|------|------|------|
| **Vite** | 开发时基于原生 ESM 按需编译，启动快；生产构建基于 Rollup / Rolldown | 新项目首选 |
| **Webpack** | 生态最成熟、配置灵活；构建较慢 | 存量项目、依赖复杂的 Webpack 插件 |
| **Rspack / Rsbuild** | Rust 实现，**兼容 Webpack 的配置和大部分插件**，速度快 | Webpack 项目的提速迁移 |
| Turbopack | Next.js 的构建工具 | Next.js 项目 |
| esbuild | 极快，用作底层编译器 | 库、工具 |

**迁移建议**：Webpack 项目想提速 → Rspack（迁移成本低）；新项目 → Vite；Next.js → Turbopack。

**口述模板（30–60 秒）**

1. 一句话结论：新项目首选 Vite，Webpack 存量项目提速可以迁移到 Rspack。
2. 关键机制：Vite 开发时基于原生 ESM 按需编译，Rspack 用 Rust 实现并兼容 Webpack 配置。
3. 对比或注意点：Webpack 生态最成熟，但构建较慢。
4. 可追问时补充：Next.js 项目使用 Turbopack。

**常见追问**

- 详见 [Vite](../vite/00-roadmap.md) 和 [Webpack](../webpack/00-roadmap.md) 专题。
