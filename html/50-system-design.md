# HTML 系统设计 / 场景题

## 通用答题框架

1. 澄清目标：用户、页面类型、核心指标
2. 约束：SEO、性能、无障碍、安全、浏览器范围、团队技术栈
3. 方案：HTML 输出方式、组件边界、资源加载、交互增强
4. 关键路径：首屏、表单提交、错误恢复、辅助技术路径
5. 风险与演进：监控、灰度、兼容性回退

### S1. 设计一个 SEO 友好的电商商品详情页

- **难度**: senior
- **标签**: SSR, SEO, 性能
- **来源倾向**: 电商 / 内容平台高频场景

**澄清问题**

- 商品数量和更新频率？
- 价格、库存是否强实时？
- 是否需要个性化推荐？
- 主要流量来自搜索、分享还是站内？

**参考方案**

```
CDN
  └─ SSR / ISR 页面
      ├─ head：title、description、canonical、OG、JSON-LD
      ├─ 首屏 HTML：商品标题、主图、价格、核心卖点
      ├─ 延迟区块：评论、推荐、问答
      └─ 客户端增强：SKU 选择、加购、收藏
```

**关键设计**

- 商品基础信息 SSR 或 ISR，保证搜索和分享抓取
- 价格库存可 SSR 输出初值，再客户端刷新，避免长时间展示错误价格
- 主图使用 `picture` / `srcset`，LCP 图片高优先级
- 评论和推荐延迟加载，但为区域预留尺寸
- SKU 选择用原生 radio 或可访问的自定义单选组
- JSON-LD 与页面可见价格、库存保持一致

**口述模板（2–3 分钟）**

1. 先区分 SEO 内容和实时交互内容。
2. 基础内容 SSR / ISR，head 和结构化数据服务端输出。
3. 首屏只保证标题、主图、价格、购买入口，其余延迟。
4. 用 LCP、CLS、INP 和收录率监控效果。
5. 价格一致性和缓存失效是主要风险。

**扩展追问**

- 不同 SKU 是否需要不同 URL？→ 如果搜索需求明确，可生成可索引 URL，并设计 canonical 规则。

### S2. 设计企业设计系统中的可访问基础组件

- **难度**: senior
- **标签**: 设计系统, a11y, 组件
- **来源倾向**: 中后台 / 平台前端常见

**澄清问题**

- 支持哪些框架？React、Vue 还是跨框架？
- 是否需要满足 WCAG 2.2 AA？
- 组件库覆盖哪些高风险组件？

**参考方案**

```
设计令牌（颜色、间距、焦点样式）
  ↓
基础原生组件：Button / Link / Input / Checkbox / Dialog
  ↓
复合组件：Tabs / Menu / Combobox / DatePicker
  ↓
业务组件：搜索筛选、表单页、表格页
```

**关键设计**

- 原生元素优先，组件 API 不允许把按钮渲染成 div
- 强制可访问名称：图标按钮必须提供 `label`
- 焦点样式作为设计令牌，不允许全局移除 outline
- 复杂组件参考 ARIA Authoring Practices
- 组件测试使用 role 查询，CI 跑 axe
- 文档写明键盘交互和读屏行为

**口述模板（2–3 分钟）**

1. 无障碍必须内置在组件层，而不是交给业务记住。
2. 基础组件优先原生，复杂组件按 ARIA 模式实现。
3. API 设计阻止错误用法，例如图标按钮缺名称时报错。
4. 自动化扫描加键盘、读屏人工测试。
5. 用问题分级和发布门禁持续治理。

**扩展追问**

- 业务方要求删掉焦点框怎么办？→ 改成符合品牌的焦点样式，而不是删除。

### S3. 设计 UGC 富文本内容的安全展示方案

- **难度**: senior
- **标签**: XSS, CSP, 富文本
- **来源倾向**: 社区、知识库、评论系统

**澄清问题**

- 允许哪些格式：链接、图片、表格、代码块、视频？
- 内容是否会在 App、小程序、Web 多端展示？
- 是否允许外部嵌入？

**参考方案**

```
编辑器（结构化文档模型）
  → 提交 JSON / 受控 HTML
  → 服务端白名单清洗
  → 存储清洗后内容 + 审计原文
  → 渲染层安全输出
  → CSP / Trusted Types 兜底
```

**关键设计**

- 优先存结构化 JSON，而不是任意 HTML
- 白名单限制标签、属性和 URL 协议
- 外链加 `rel="nofollow ugc noopener noreferrer"`
- 图片走代理或白名单域名，避免追踪和混合内容
- iframe 嵌入只允许白名单服务，并设置 sandbox
- 前端不直接 `innerHTML` 未清洗内容

**口述模板（2–3 分钟）**

1. UGC 的核心是不信任内容。
2. 编辑、服务端、渲染层多层防护。
3. 白名单清洗，URL 和嵌入单独控制。
4. CSP 和 Trusted Types 兜底。
5. 记录审计日志，支持快速下架和重新清洗。

**扩展追问**

- 清洗规则升级后历史内容怎么办？→ 后台批量重新清洗，并保留版本。

### S4. 设计一个高性能营销活动页

- **难度**: mid
- **标签**: LCP, CLS, 静态化
- **来源倾向**: 电商大促、运营活动

**澄清问题**

- 活动访问峰值多大？
- 页面是否强个性化？
- 首屏核心元素是什么：Banner、倒计时还是优惠券？

**参考方案**

```
SSG / CDN 静态 HTML
  ├─ 首屏 Banner：SSR 写入、fetchpriority=high
  ├─ 关键 CSS：内联或小文件优先
  ├─ 业务 JS：defer / module
  ├─ 埋点：async 或交互后加载
  └─ 下方楼层：lazy + 预留尺寸
```

**关键设计**

- 首屏 HTML 尽量静态化
- 首屏图片不懒加载，尺寸和格式优化
- 倒计时文字固定宽度或使用等宽数字，避免布局抖动
- 优惠券按钮使用原生 button，接口失败可重试
- 第三方埋点不阻塞首屏

**口述模板（2–3 分钟）**

1. 活动页目标是快和稳定。
2. 静态 HTML + CDN 承接峰值。
3. 首屏资源优先，非首屏延迟。
4. 第三方脚本降级处理。
5. 用 RUM 看 LCP、CLS、INP 和转化。

**扩展追问**

- 个性化价格怎么办？→ 静态框架 + 个性化接口局部填充，并预留空间。

### S5. 第三方组件通过 iframe 嵌入宿主页面

- **难度**: senior
- **标签**: iframe, postMessage, 安全
- **来源倾向**: SaaS、支付、客服组件

**澄清问题**

- 嵌入方是否可信？
- 是否需要访问宿主登录态？
- 是否需要自适应高度、打开弹窗、跳转？

**参考方案**

```
宿主页面
  └─ iframe（第三方域名）
       ├─ sandbox / allow 最小权限
       ├─ postMessage 协议
       │    ├─ READY
       │    ├─ RESIZE
       │    ├─ OPEN_URL
       │    └─ ERROR
       └─ 第三方服务端鉴权
```

**关键设计**

- iframe 必须有 `title`
- 双方指定目标 origin，校验 source、版本和消息结构
- 高度自适应通过 `RESIZE` 消息，宿主限制最大值
- 第三方不直接读取宿主 cookie，使用短期 token 交换
- 宿主用 CSP `frame-src` 控制允许嵌入的域名
- 第三方页面用 `frame-ancestors` 控制谁能嵌入它

**口述模板（2–3 分钟）**

1. iframe 用于建立安全和故障边界。
2. 权限最小化，通信协议化。
3. 双向限制嵌入来源。
4. 处理高度、弹窗、导航和错误。
5. 监控加载失败率和消息超时。

**扩展追问**

- iframe 内弹窗如何覆盖整个页面？→ 发送消息给宿主，由宿主渲染全局弹窗。

### S6. 设计低代码表单渲染系统

- **难度**: senior
- **标签**: 表单, a11y, Schema
- **来源倾向**: 中后台、审批流

**澄清问题**

- 表单字段类型有哪些？
- 是否需要条件显示、联动校验、动态数组？
- 是否需要草稿、离线和多端渲染？

**参考方案**

```
JSON Schema / 表单 DSL
  ↓
字段注册表
  ├─ text → input
  ├─ select → select / 可访问 Combobox
  ├─ radio → fieldset + radio
  └─ file → input type=file
  ↓
渲染层：label、描述、错误、必填状态统一生成
  ↓
校验层：前端提示 + 后端最终校验
```

**关键设计**

- Schema 中强制字段 label，不允许只有 placeholder
- 渲染器统一生成 `id`、`for`、`aria-describedby`
- 条件隐藏字段要从提交和校验中排除
- 表单分组使用 `fieldset` / `legend`
- 提交失败显示错误摘要，并聚焦第一个错误字段
- 原生 `autocomplete` 由字段语义配置

**口述模板（2–3 分钟）**

1. 低代码表单要把可访问性做成渲染器能力。
2. Schema 描述语义，渲染器选择原生控件。
3. 校验状态统一关联到控件。
4. 动态字段要同步提交和校验。
5. 后端仍然做最终校验。

**扩展追问**

- 自定义字段如何保证质量？→ 注册时要求实现标签、错误、值和焦点接口。

### S7. 多语言站点的 HTML 架构

- **难度**: mid
- **标签**: i18n, SEO
- **来源倾向**: 出海业务

**澄清问题**

- 语言和地区数量？
- 是否有 RTL 语言？
- URL 策略：子目录、子域名还是独立域名？

**参考方案**

```
/zh-CN/products/1
/en-US/products/1
/ar/products/1

每个页面：
  html lang + dir
  canonical
  hreflang alternate
  本地化 title / description / OG
```

**关键设计**

- 服务端根据 URL 输出语言，不只依赖浏览器语言自动跳转
- `hreflang` 双向互相引用
- RTL 页面设置 `dir="rtl"`，CSS 使用逻辑属性
- 用户生成内容用 `dir="auto"` 或 `bdi`
- 日期、货币、复数规则使用 Intl 或服务端本地化库

**口述模板（2–3 分钟）**

1. URL 明确表达语言，便于搜索和分享。
2. HTML 设置 lang、dir、hreflang。
3. 内容和格式都要本地化。
4. RTL 需要布局和交互测试。
5. 监控各语言收录和转化。

**扩展追问**

- 自动按 IP 跳转好吗？→ 可以提示，但不要强制阻止用户和爬虫访问其他语言版本。

### S8. 大型 SPA 首屏 HTML 与 Hydration 优化

- **难度**: senior
- **标签**: SSR, Hydration, INP
- **来源倾向**: 大型 Web 应用

**澄清问题**

- 页面是内容型还是工具型？
- 首屏有多少交互组件？
- 用户设备和网络分布如何？

**参考方案**

```
服务端
  ├─ 流式输出 HTML
  ├─ 首屏关键内容先发
  └─ 慢数据区域 Suspense / 占位
客户端
  ├─ 首屏交互组件优先 Hydration
  ├─ 非关键组件可见时或空闲时 Hydration
  └─ 第三方脚本延迟
```

**关键设计**

- 保证 SSR HTML 合法，减少 Hydration mismatch
- 首屏不需要交互的内容不打包客户端逻辑
- 组件拆分为服务端组件 / 客户端组件（视框架）
- 占位区域预留尺寸，避免 CLS
- 用长任务和 INP 监控 Hydration 成本

**口述模板（2–3 分钟）**

1. 首屏快不只是 HTML 早到，还要尽早可交互。
2. 流式 SSR 改善首屏内容展示。
3. 选择性 Hydration 降低主线程压力。
4. HTML 合法性和占位尺寸要控制。
5. 用 LCP、INP、长任务验证。

**扩展追问**

- 用户在 Hydration 前点击按钮怎么办？→ 关键操作可原生表单兜底，或框架支持事件重放。
