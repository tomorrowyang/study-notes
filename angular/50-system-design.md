# Angular 系统设计题

> 回答结构：先澄清需求和约束 → 给出整体架构（模块划分、数据流）→ 说明关键设计（状态、路由、性能、权限）→ 给出指标和监控 → 讨论取舍和演进。

---

### S1. 设计一个大型企业中后台平台

- **难度**: 高级
- **标签**: 中后台, 架构

**澄清问题（面试时先问）**

- 多少个业务模块和页面？多少个团队并行开发？
- 权限模型：菜单级、按钮级、数据级？多租户吗？
- 是否需要国际化、主题定制？
- 用户的浏览器和网络环境（内网、老浏览器）？

**参考方案**

```text
Nx Monorepo
├─ apps/admin-shell            # 布局、登录、菜单、全局错误处理、路由壳
├─ libs/<domain>/feature-*     # 各业务页面（懒加载路由）
├─ libs/<domain>/data-access   # API 客户端（由 OpenAPI 生成）、SignalStore
├─ libs/shared/ui              # 设计系统：表格、表单、弹窗、布局组件
├─ libs/shared/auth            # 认证、权限服务、守卫、权限指令
└─ libs/shared/util            # 工具、拦截器、错误处理

运行时：
登录 → 获取用户、权限、菜单 → 动态生成菜单 → 懒加载业务路由
请求 → 拦截器（令牌、错误、加载状态）→ BFF / 网关
```

**关键设计**

- **按领域划分**，Nx 模块边界规则强制依赖方向；每个团队负责自己的领域库
- **权限**：路由级 `canMatch`（无权限不下载代码）、按钮级结构指令（H6）、数据级由服务端过滤；权限数据是 Signal，切换账号自动更新
- **通用页面模式**：「查询表单 + 表格 + 详情抽屉」抽象为配置驱动的组件，减少重复代码
- **状态**：页面局部状态用组件级 SignalStore；全局只放用户、权限、字典
- **API 层**：从 OpenAPI 生成类型和客户端，保证前后端类型一致
- **性能**：OnPush + Signals（v22 默认）、虚拟滚动表格、路由懒加载与选择性预加载
- **工程**：受影响分析 + 远程缓存的 CI；统一的 ESLint 规则；组件库 Storybook

**关键指标**

- 首屏时间、路由切换耗时、INP、CI 时长、构建缓存命中率、线上错误率

**口述模板（2–3 分钟）**

我会用 Nx Monorepo 组织代码：一个应用壳负责布局、登录、菜单和全局错误处理，各业务按领域拆成独立的库，每个领域分为页面、数据访问、UI 和工具几层，用模块边界规则限制依赖方向，这样多个团队可以并行开发而不互相干扰。

权限分三级：路由级用 canMatch，没有权限连代码都不会下载；按钮级用结构指令；数据级必须由服务端过滤。权限数据用 Signal 保存，切换账号时界面自动更新。

中后台大部分页面是「查询表单加表格加详情」，我会把它抽象成配置驱动的通用组件，减少重复代码。API 客户端从 OpenAPI 生成，保证类型一致。状态尽量放在组件级的 Store 中，全局只保存用户、权限和字典。

性能方面默认使用 OnPush 和 Signals，表格使用虚拟滚动，路由懒加载并选择性预加载。CI 使用受影响分析和远程缓存，控制构建时长。

**扩展追问**

- 某个业务团队想独立发布怎么办？→ 先评估是否必要；必要时把该领域拆为远程模块（Native Federation），见 S6。
- 菜单由服务端动态下发，路由怎么配置？→ 路由在前端静态注册（保证懒加载和类型），服务端只下发菜单和权限，菜单项映射到已注册的路由。

### S2. 设计一个配置驱动的表单引擎（低代码表单）

- **难度**: 高级
- **标签**: 表单, 低代码

**澄清问题（面试时先问）**

- 表单的复杂度：字段数量、联动规则、校验规则、嵌套和动态数组？
- 配置由谁维护：开发者还是业务人员（可视化设计器）？
- 是否需要多端渲染（Web、移动端）？
- 表单版本管理和历史数据兼容？

**参考方案**

```text
表单设计器（拖拽） ──生成──► 表单 Schema（JSON，带版本）
                                  │
                                  ▼
                       ┌──────────────────────┐
                       │ 表单引擎              │
                       │ - Schema 解析与校验   │
                       │ - 模型（Signal Forms / 响应式表单）│
                       │ - 规则引擎（联动、计算）│
                       │ - 渲染器注册表        │
                       └──────────┬───────────┘
                                  ▼
                 字段组件（输入框、下拉、日期、上传、自定义）
```

**关键设计**

- **Schema**：字段（类型、校验、默认值）+ 布局 + 规则；用 JSON Schema 校验 Schema 本身；带版本号
- **渲染器注册表**：字段类型 → 组件的映射，通过 `InjectionToken` 多提供者扩展；业务可以注册自定义字段
- **字段组件**：统一实现 `ControlValueAccessor` / `FormValueControl`
- **联动规则**：声明式表达式（显示 / 隐藏、必填、选项、计算值），用**安全的表达式求值器**（不用 `eval`），依赖关系做成计算图避免循环
- **隐藏字段**：禁用后不参与校验和提交（H9）
- **性能**：大表单分组、分步、按需渲染；字段级 OnPush
- **数据**：提交的数据带 Schema 版本，历史数据用对应版本的 Schema 渲染

**关键指标**

- 表单渲染耗时、交互延迟（INP）、配置错误率、自定义字段的复用率

**口述模板（2–3 分钟）**

表单引擎的核心是把表单描述为带版本的 JSON Schema，包括字段、布局和联动规则，引擎负责解析 Schema、构建表单模型和渲染。

渲染采用注册表模式：字段类型映射到组件，通过 InjectionToken 的多提供者扩展，业务方可以注册自己的字段类型。所有字段组件统一实现表单控件接口，这样可以接入同一个表单模型。

联动规则用声明式的表达式描述，比如某字段等于某值时显示另一个字段，由安全的表达式求值器执行，不使用 eval，并把规则之间的依赖构造成图来检测循环。隐藏的字段会被禁用，不参与校验和提交。

性能方面，大表单分组和分步渲染，字段组件使用 OnPush。提交的数据记录 Schema 版本，保证历史数据可以用当时的 Schema 正确回显。

**扩展追问**

- 为什么不用 `eval` 执行规则？→ 安全风险（配置可能被篡改导致 XSS）且无法静态分析依赖；用受限的表达式语言或 JSON 逻辑规则。

### S3. 设计一个实时交易看板

- **难度**: 高级
- **标签**: 实时, 性能

**澄清问题（面试时先问）**

- 数据量和频率：多少个品种？每秒多少次更新？
- 需要展示什么：表格、K 线图、深度图？
- 延迟要求？是否允许合并更新？
- 断线重连、数据补齐的要求？

**参考方案**

```text
WebSocket（Zone 外接收）
   │ 原始消息（每秒上千条）
   ▼
数据层（Web Worker 可选）
   - 解析、合并：同一品种每帧只保留最新值
   - 计算：涨跌幅、聚合
   │ 每帧一次批量更新
   ▼
Store：Map<symbol, WritableSignal<Quote>>（每个品种一个信号）
   │
   ▼
表格（虚拟滚动）── 行组件只读取自己品种的信号 → 只刷新变化的行
图表（Canvas，第三方库在 Zone 外更新）
```

**关键设计**

- **接收**：WebSocket 在 Zone 外（或 Zoneless），心跳 + 指数退避重连，重连后拉取快照补齐
- **合并更新**：用 `requestAnimationFrame` 批量处理，**每帧最多更新一次**，丢弃中间值
- **细粒度信号**：每个品种一个信号，行组件只订阅自己的 → 一次行情更新只刷新一行
- **虚拟滚动**：只渲染可见行；不可见的品种可以取消订阅（服务端按需推送）
- **图表**：Canvas 渲染，增量绘制
- **重计算**：放到 Web Worker
- **视觉**：涨跌闪烁用 CSS 动画（合成层），不触发布局

**关键指标**

- 端到端延迟、帧率、长任务数量、内存占用（长时间运行）、重连次数

**口述模板（2–3 分钟）**

实时看板的瓶颈通常不是网络而是渲染，所以核心思路是减少渲染的次数和范围。

WebSocket 在 Angular 的变更检测之外接收数据，接收到的消息先进入合并缓冲区，同一个品种每帧只保留最新的值，通过 requestAnimationFrame 每帧批量处理一次。计算量大的部分可以放到 Web Worker。

状态层为每个品种创建一个独立的信号，表格的每一行只读取自己品种的信号。这样一次行情更新只会刷新对应的那一行，而不是整个表格。表格使用虚拟滚动，不可见的品种可以取消订阅。图表使用 Canvas 增量绘制。

稳定性方面，WebSocket 有心跳和指数退避重连，重连后先拉取快照再继续接收增量。长时间运行要关注内存，限制历史数据的长度。

**扩展追问**

- 为什么不用一个大数组信号保存所有行情？→ 任何一个品种变化都会产生新数组，所有读取它的组件都要重新检查；细粒度信号只影响相关的行。

### S4. 设计企业级 Angular 组件库

- **难度**: 高级
- **标签**: 组件库, 设计系统

**澄清问题（面试时先问）**

- 服务多少个应用？多少个 Angular 版本并存？
- 是否有设计规范和设计令牌？需要多主题吗？
- 无障碍要求（WCAG 级别）？
- 是否需要支持其他框架？

**参考方案**

```text
设计令牌（JSON）──生成──► CSS 变量 / 多主题
         │
行为层：Angular CDK + Angular Aria（焦点、键盘、浮层、ARIA）
         │
组件层：@corp/ui（次级入口点：@corp/ui/button、@corp/ui/table ...）
         │
质量：Storybook 文档、Harness 测试、视觉回归、无障碍自动检查
         │
发布：ng-packagr、Changesets 版本管理、ng update 迁移脚本
```

**关键设计**

- **API 约定**：信号式输入输出、`booleanAttribute` 转换、表单控件接口、`hostDirectives` 组合行为
- **兼容性**：OnPush、Zoneless、SSR 安全（不在构造中访问 DOM）
- **定制**：CSS 变量作为主题定制点，不鼓励 `::ng-deep`；内容投影和模板提供结构定制
- **版本策略**：主版本跟随 Angular 主版本；破坏性变更提供迁移脚本（schematics）
- **测试**：每个组件提供 Harness，业务方测试时使用
- **跨框架**：需要时用 Angular Elements 输出 Web Components（注意包体积）

**关键指标**

- 组件覆盖率（业务中使用库组件的比例）、无障碍问题数、升级耗时、包体积

**口述模板（2–3 分钟）**

组件库我会分三层：设计令牌生成 CSS 变量，用于多主题；行为层基于 CDK 和 Angular Aria，处理焦点、键盘导航、浮层定位和 ARIA 属性；组件层实现设计系统的具体组件。

API 上统一使用信号式的输入输出，表单类组件实现表单控件接口，通过 hostDirectives 组合通用行为。所有组件使用 OnPush，兼容 Zoneless 和 SSR。定制主要通过 CSS 变量和内容投影，不依赖穿透样式。

工程上每个组件是一个次级入口点，方便摇树。每个组件提供 Storybook 文档和测试 Harness，业务方可以用 Harness 写稳定的测试。版本跟随 Angular 主版本，破坏性变更提供迁移脚本，让业务方通过 ng update 自动升级。

**扩展追问**

- 业务方需要的定制超出组件的能力怎么办？→ 提供「无样式」的行为指令让业务自己组合；收集需求后评估是否纳入组件库。

### S5. 规划一个老 Angular 应用的现代化改造

- **难度**: 高级
- **标签**: 迁移, 升级

**澄清问题（面试时先问）**

- 当前版本？代码量和团队规模？
- 是否有测试？第三方依赖情况？
- 业务能否接受功能冻结？目标的时间范围？
- 主要痛点：性能、开发效率、安全（版本不再支持）？

**参考方案**

```text
阶段 0：准备
  - 核心流程 E2E 测试、性能和错误率基线
  - 依赖盘点：不再维护的库找替代
阶段 1：版本升级（逐个主版本，每步可发布）
  - ng update，处理 View Engine 移除、类型化表单等
阶段 2：工具链
  - application builder（esbuild）、Vitest
阶段 3：代码现代化（官方迁移脚本，可与业务开发并行）
  - Standalone、控制流、inject()、信号输入 / 输出 / 查询
阶段 4：响应式与性能
  - OnPush 全覆盖 → 状态迁移到 Signals → Zoneless
  - 表单按需迁移到 Signal Forms（compatForm 渐进）
阶段 5：防回退
  - ESLint 规则、budgets、CI 检查
```

**关键设计**

- **小步快跑**：每一步都可以独立发布，不搞长期分支
- **自动化优先**：官方迁移脚本处理大部分机械性修改
- **按收益排序**：先保证在受支持的版本（安全），再做性能相关，最后是语法现代化
- **与业务并行**：迁移按模块分批，避免冻结业务
- **度量**：每个阶段对比构建时间、包体积、INP、错误率

**关键指标**

- 构建时间、初始包体积、INP、线上错误率、迁移完成比例

**口述模板（2–3 分钟）**

我会把现代化改造拆成几个可以独立发布的阶段，而不是一次性重写。

第一步是准备，补充核心流程的 E2E 测试作为安全网，记录性能和错误率基线，并盘点第三方依赖，提前替换不再维护的库。然后逐个主版本升级，每一步都要构建、测试通过并发布。

版本追上后切换到 esbuild 的构建器和 Vitest，构建速度会有明显提升。接下来用官方迁移脚本做代码现代化，包括 Standalone、新控制流、信号输入输出，这些大部分是机械性的修改，可以和业务开发并行。

性能相关的改造是先让组件全面 OnPush，再把状态迁移到 Signals，最后移除 Zone.js。整个过程用 ESLint 规则和体积预算防止回退，每个阶段对比基线指标，证明改造的收益。

**扩展追问**

- 业务方不愿意投入怎么办？→ 用数据说明风险（不受支持的版本没有安全更新）和收益（构建时间、性能）；尽量与业务需求一起推进。

### S6. 设计多团队协作的 Angular 微前端平台

- **难度**: 高级
- **标签**: 微前端

**澄清问题（面试时先问）**

- 为什么需要微前端：独立发布？技术栈异构？团队自治？
- 有多少个团队和子应用？是否都是 Angular？版本能否统一？
- 子应用之间的交互多吗？

**参考方案**

```text
Shell（Angular）
  - 登录、布局、导航、全局错误处理
  - 远程清单（manifest.json，按环境下发远程地址和版本）
  - 路由：loadRemoteModule → 远程的路由配置
       │
       ├─ remote-orders（Angular，Native Federation，独立部署）
       ├─ remote-reports（Angular）
       └─ legacy-app（其他框架 → iframe / Web Components）

共享依赖：@angular/*、rxjs、@corp/ui、@corp/auth（单例）
通信：共享的 auth / 事件服务；URL 作为主要的状态传递方式
```

**关键设计**

- **Native Federation**：基于 esbuild 和导入映射，与 Angular 的 application builder 兼容（v22 弃用 Webpack 构建器）
- **共享依赖**：Angular 及核心库以单例共享，**要求主版本统一**；平台团队负责统一升级
- **运行时清单**：远程地址和版本由清单下发，支持灰度和快速回滚
- **契约**：子应用暴露的路由和组件接口有版本；共享库的破坏性变更走流程
- **隔离**：同源方案没有安全隔离，子应用之间是信任关系；不可信或异构的应用用 iframe
- **质量**：每个远程独立 CI；集成环境的冒烟测试；远程加载失败时显示降级页面

**关键指标**

- 各子应用的发布频率、加载失败率、共享依赖的重复打包量、首屏时间

**口述模板（2–3 分钟）**

首先要确认微前端是否真的必要。如果只是多个团队协作，Nx Monorepo 加模块边界通常就够了；只有在需要独立发布或技术栈异构时才引入微前端。

如果确实需要，我会用 Native Federation，因为它基于 esbuild 和导入映射，与 Angular 当前的构建器兼容。Shell 应用负责登录、布局、导航和全局错误处理，通过运行时清单获取各个远程应用的地址和版本，这样可以对单个子应用做灰度和回滚。

Angular 和核心库以单例共享，这要求所有子应用的 Angular 主版本一致，所以平台团队需要负责统一升级节奏。子应用之间尽量通过 URL 传递状态，减少运行时耦合。

需要注意同源的微前端没有安全隔离，子应用之间是互相信任的；不可信或其他框架的应用用 iframe 接入。最后，远程加载失败时要显示降级页面，并在集成环境做冒烟测试。

**扩展追问**

- 某个团队想先升级 Angular 怎么办？→ 共享依赖时无法单独升级；可以临时不共享（各自打包，体积增加），或者推动统一升级。

### S7. 用 Angular 设计一个需要 SEO 的电商站点

- **难度**: 高级
- **标签**: SSR, 电商

**澄清问题（面试时先问）**

- 页面类型：首页、列表、详情、购物车、结算？各自的 SEO 需求？
- 商品数量和更新频率？价格和库存的实时性要求？
- 流量规模和地域？是否有 CDN？

**参考方案**

```text
CDN（缓存 HTML 和静态资源）
   │
Angular SSR（Node，多实例）
   - 混合渲染（按路由配置 RenderMode）：
     首页、分类页：SSR + CDN 短缓存
     商品详情：SSR（或预渲染热门商品）+ CDN 缓存 + 失效
     购物车、结算、用户中心：CSR（不需要 SEO，个性化）
   - 增量水合：评论、推荐等区块 hydrate on viewport
   - HTTP 传输缓存：服务端请求的数据不在客户端重复请求
   │
API / BFF
```

**关键设计**

- **按路由选择渲染模式**：需要 SEO 的页面服务端渲染，个性化页面客户端渲染
- **缓存**：公开页面可以缓存在 CDN；价格和库存这类实时数据在客户端单独获取（或使用短 TTL）
- **增量水合 + 事件重放**：减少首屏 JS 执行，用户早期的点击不丢失
- **图片**：`NgOptimizedImage`，LCP 图片设置 `priority`
- **SEO**：`Title` / `Meta` 服务设置元信息，结构化数据（JSON-LD），sitemap
- **SSR 稳定性**：服务端请求超时、降级为 CSR；避免在服务端访问浏览器 API；用 `PendingTasks` 跟踪自定义异步任务

**关键指标**

- LCP、INP、CLS、TTFB、SSR 错误率、CDN 命中率、搜索收录量

**口述模板（2–3 分钟）**

我会使用 Angular SSR 的混合渲染，按路由选择渲染模式：首页、分类页和商品详情需要 SEO，使用服务端渲染并在 CDN 缓存；购物车、结算和用户中心不需要 SEO 且是个性化的，使用客户端渲染。

商品详情的价格和库存实时性要求高，不适合跟页面一起长时间缓存，所以页面主体缓存在 CDN，价格和库存在客户端单独获取。

首屏性能方面，评论、推荐等首屏以下的区块使用增量水合，进入视口时才加载和水合，事件重放保证用户早期的点击不丢失。HTTP 传输缓存避免客户端重复请求服务端已经获取的数据。商品主图作为 LCP 元素，使用 NgOptimizedImage 并设置优先级。

稳定性方面，服务端请求设置超时，失败时降级为客户端渲染，并用 PendingTasks 跟踪自定义的异步任务，保证 SSR 能正确等待数据。

**扩展追问**

- 热门商品可以预渲染吗？→ 可以在构建时预渲染热门商品，但商品多且更新频繁时，SSR + CDN 缓存 + 主动失效更合适。

### S8. 设计一个支持离线的现场作业应用（PWA）

- **难度**: 高级
- **标签**: PWA, 离线

**澄清问题（面试时先问）**

- 离线场景：完全离线多久？需要离线查看还是离线录入？
- 数据量：离线需要缓存多少数据？
- 冲突：多人同时修改同一条数据怎么办？
- 设备：手机、平板？是否需要拍照、定位？

**参考方案**

```text
Angular 应用（@angular/service-worker）
   - 应用外壳和静态资源：Service Worker 预缓存
   - 数据：IndexedDB（Dexie 等），本地优先读写
   - 操作队列（Outbox）：离线时的修改记录为操作，联网后按顺序同步
   - 同步服务：
       联网检测（online 事件 + 心跳）
       上传队列（幂等键，失败重试）
       下载增量（基于版本号 / 时间戳）
       冲突处理（服务端检测版本，返回冲突交给用户选择）
   - 版本更新：SwUpdate 检测新版本，提示用户刷新
```

**关键设计**

- **本地优先**：界面读写本地数据库，同步在后台进行；状态用 Signals 反映同步状态（待同步数量、最后同步时间）
- **操作队列**：每个操作带客户端生成的 ID（幂等键），服务端去重；按顺序上传
- **冲突**：乐观锁（版本号）；冲突时展示双方的值让用户选择，或按字段合并
- **附件**：照片压缩后存在本地，联网后分片上传
- **存储**：申请持久化存储（`navigator.storage.persist()`），监控配额
- **安全**：本地数据的敏感程度；设备丢失时的处理（会话过期、远程清除）

**关键指标**

- 同步成功率、待同步操作的积压量、冲突率、离线可用的功能比例

**口述模板（2–3 分钟）**

我会采用本地优先的架构。应用外壳和静态资源由 Angular 的 Service Worker 预缓存，保证离线可以打开。业务数据存在 IndexedDB 中，界面直接读写本地数据库，同步在后台进行。

离线时的修改不是直接调用接口，而是记录为操作放入队列，每个操作带有客户端生成的唯一 ID 作为幂等键。联网后同步服务按顺序上传，服务端根据幂等键去重，避免重复提交。下载方面根据版本号拉取增量数据。

冲突用乐观锁检测：每条数据带版本号，服务端发现版本冲突时返回双方的数据，由用户选择或按字段合并。照片这类附件先压缩存在本地，联网后分片上传。

界面上用信号展示同步状态，比如待同步数量和最后同步时间。还要申请持久化存储防止被浏览器清理，并通过 SwUpdate 提示用户更新到新版本。

**扩展追问**

- Service Worker 更新后旧页面还在运行怎么办？→ `SwUpdate.versionUpdates` 检测到新版本时提示用户刷新；不兼容的数据结构变更要做本地数据库迁移。
