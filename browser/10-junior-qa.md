## 一、浏览器架构

### Q1. 浏览器由哪些部分组成？

- **难度**: 初级
- **标签**: 架构

**答案**

| 组件 | 作用 |
|------|------|
| 用户界面 | 地址栏、标签页、书签等浏览器自身的 UI |
| 浏览器引擎 | 在用户界面和渲染引擎之间协调 |
| **渲染引擎** | 解析 HTML / CSS，计算布局并绘制页面（Blink、WebKit、Gecko） |
| **JS 引擎** | 解析并执行 JS（V8、JavaScriptCore、SpiderMonkey） |
| 网络 | HTTP 请求、缓存、连接管理 |
| 存储 | Cookie、localStorage、IndexedDB、HTTP 缓存 |
| 图形 | 与 GPU 和操作系统交互，最终显示像素 |

**口述模板（30–60 秒）**

1. 一句话结论：浏览器主要由界面、渲染引擎、JS 引擎、网络、存储和图形几部分组成。
2. 关键机制：渲染引擎负责把 HTML 和 CSS 变成像素，JS 引擎负责执行脚本。
3. 对比或注意点：现代浏览器把这些组件分布在多个进程中。
4. 可追问时补充：Chrome 的渲染引擎是 Blink，JS 引擎是 V8。

**常见追问**

- 渲染引擎和 JS 引擎是什么关系？→ 在同一个渲染进程的主线程上运行，JS 通过 DOM API 操作渲染引擎中的 DOM。

### Q2. 主流浏览器的内核分别是什么？

- **难度**: 初级
- **标签**: 内核

**答案**

| 浏览器 | 渲染引擎 | JS 引擎 |
|--------|---------|---------|
| Chrome、Edge、Opera、国内大部分浏览器 | Blink | V8 |
| Safari（以及 iOS 上的所有浏览器，欧盟地区除外） | WebKit | JavaScriptCore |
| Firefox | Gecko | SpiderMonkey |

- Blink 是 2013 年从 WebKit 分叉出来的
- iOS 上长期要求所有浏览器使用 WebKit，所以 iOS 上的 Chrome 实际是 WebKit 内核（欧盟地区因法规允许其他引擎）
- Android WebView 基于 Chromium

**口述模板（30–60 秒）**

1. 一句话结论：Chrome 系是 Blink + V8，Safari 是 WebKit + JavaScriptCore，Firefox 是 Gecko + SpiderMonkey。
2. 关键机制：Blink 从 WebKit 分叉而来，两者有共同的历史。
3. 对比或注意点：iOS 上的浏览器基本都是 WebKit 内核，兼容性问题要按 Safari 处理。
4. 可追问时补充：Android WebView 是 Chromium 内核，可以单独更新。

**常见追问**

- 为什么 iOS 上 Chrome 的表现和 Safari 一样？→ iOS 的平台限制要求使用 WebKit，Chrome 只是换了外壳。

### Q3. 为什么 Chrome 是多进程架构？有哪些进程？

- **难度**: 初级
- **标签**: 架构, 进程

**答案**

| 进程 | 职责 |
|------|------|
| **浏览器进程** | 地址栏、标签页等 UI，管理子进程，协调导航，存储访问 |
| **渲染进程** | 解析 HTML / CSS、执行 JS、布局、绘制；运行在**沙箱**中 |
| **GPU 进程** | 处理所有 GPU 任务，合成最终画面 |
| **网络服务** | 网络请求（作为独立进程或浏览器进程中的服务） |
| 插件 / 工具进程 | 音视频解码、扩展、存储服务等 |

**为什么多进程**：

- **稳定性**：一个页面崩溃不影响其他页面和浏览器
- **安全性**：渲染进程运行在沙箱中，无法直接访问文件系统和系统资源；站点隔离防止跨站数据泄露
- **性能**：多个进程可以利用多核 CPU

**代价**：内存占用更高（每个进程都有独立的内存空间和公共基础设施的副本），Chrome 在内存紧张时会合并进程。

**口述模板（30–60 秒）**

1. 一句话结论：多进程是为了稳定性、安全性和性能。
2. 关键机制：浏览器进程管理 UI 和协调，渲染进程在沙箱中处理页面，GPU 进程负责绘制，网络服务处理请求。
3. 对比或注意点：代价是内存占用较高。
4. 可追问时补充：站点隔离让不同站点运行在不同的渲染进程中，防御 Spectre 类攻击。

**常见追问**

- 一个标签页就是一个进程吗？→ 不完全是。按站点分配进程，同一站点的多个标签页可能共享进程，一个页面中的跨站 iframe 会使用单独的进程。

### Q4. 进程和线程有什么区别？渲染进程中有哪些线程？

- **难度**: 初级
- **标签**: 进程, 线程

**答案**

- **进程**：操作系统分配资源的单位，有独立的内存空间，进程之间通过 IPC 通信
- **线程**：CPU 调度的单位，同一进程中的线程共享内存

**渲染进程中的主要线程**：

| 线程 | 职责 |
|------|------|
| **主线程** | 执行 JS、解析 HTML / CSS、样式计算、布局、生成绘制记录、事件处理 |
| **合成线程**（Compositor） | 接收绘制结果，分块，处理滚动和合成动画，生成合成帧 |
| **光栅线程** | 把图块光栅化为位图（常借助 GPU） |
| Worker 线程 | Web Worker、Service Worker |
| IO 线程 | 与其他进程通信 |

关键点：JS 执行和渲染共用**主线程**，所以长时间运行的 JS 会阻塞渲染和交互。

**口述模板（30–60 秒）**

1. 一句话结论：进程是资源分配单位，线程是调度单位。
2. 关键机制：渲染进程中有主线程、合成线程、光栅线程等。
3. 对比或注意点：JS 和渲染共用主线程，所以长任务会导致卡顿。
4. 可追问时补充：合成线程独立于主线程，所以 transform 动画和滚动在主线程繁忙时也能流畅运行。

**常见追问**

- JS 为什么是单线程的？→ JS 需要操作 DOM，多线程同时修改 DOM 会产生竞争问题；Worker 提供了不访问 DOM 的多线程能力。

## 二、导航与网络

### Q5. 从输入 URL 到页面显示，发生了什么？

- **难度**: 初级
- **标签**: 导航, 综合

**答案**

```text
1. 处理输入
   - 判断是搜索关键词还是 URL，补全协议
   - 触发当前页面的 beforeunload

2. 网络请求（浏览器进程 / 网络服务）
   - 检查 HSTS、缓存（Service Worker、HTTP 缓存）
   - DNS 解析 → TCP 连接 → TLS 握手（HTTP/3 使用 QUIC）
   - 发送 HTTP 请求，接收响应
   - 处理重定向（3xx），根据 Content-Type 判断是页面还是下载

3. 提交导航
   - 浏览器进程选择或创建渲染进程（站点隔离）
   - 把响应数据流交给渲染进程，更新地址栏和历史记录

4. 渲染（渲染进程）
   - 解析 HTML 构建 DOM，遇到资源发起请求（预加载扫描器提前发现）
   - 解析 CSS 构建 CSSOM，执行 JS
   - 样式计算 → 布局 → 分层 → 绘制 → 光栅化 → 合成 → 显示

5. 加载完成
   - DOMContentLoaded → 加载图片等资源 → load
```

**口述模板（30–60 秒）**

1. 一句话结论：分为输入处理、网络请求、提交导航、渲染和加载完成几个阶段。
2. 关键机制：网络阶段包括缓存检查、DNS、TCP、TLS、HTTP；渲染阶段包括解析、样式、布局、分层、绘制、合成。
3. 对比或注意点：网络在浏览器进程或网络服务中完成，渲染在沙箱化的渲染进程中完成。
4. 可追问时补充：这个问题可以无限深挖，准备好展开任何一个环节。

**常见追问**

- 渲染进程是什么时候创建的？→ 浏览器在发起网络请求时就可以并行准备渲染进程，响应到达后直接提交，减少等待。

### Q6. DNS 解析的过程是什么？

- **难度**: 初级
- **标签**: 网络, DNS

**答案**

**查询顺序**：

1. 浏览器 DNS 缓存
2. 操作系统缓存（以及 hosts 文件）
3. 本地 DNS 服务器（运营商或公共 DNS，如 8.8.8.8）
4. 本地 DNS 服务器**迭代查询**：根域名服务器 → 顶级域名服务器（.com）→ 权威域名服务器 → 返回 IP

**相关概念**：

- 客户端到本地 DNS 是**递归查询**，本地 DNS 到各级服务器是**迭代查询**
- TTL：记录的缓存时间
- **DoH**（DNS over HTTPS）：加密 DNS 查询，防止被监听和篡改
- CDN 通过 DNS 的 CNAME 和智能解析把用户调度到最近的节点

**优化**：`dns-prefetch`、`preconnect`、减少域名数量。

**口述模板（30–60 秒）**

1. 一句话结论：DNS 依次查询浏览器缓存、系统缓存、本地 DNS，再由本地 DNS 迭代查询根、顶级和权威服务器。
2. 关键机制：客户端到本地 DNS 是递归查询，之后是迭代查询，结果按 TTL 缓存。
3. 对比或注意点：DoH 加密 DNS 查询，提高隐私和安全性。
4. 可追问时补充：CDN 依赖 DNS 智能解析实现就近访问。

**常见追问**

- DNS 用 TCP 还是 UDP？→ 通常是 UDP（端口 53），响应过大或区域传送时使用 TCP；DoH 走 HTTPS。

### Q7. TCP 三次握手和四次挥手是怎样的？

- **难度**: 初级
- **标签**: 网络, TCP

**答案**

**三次握手**：

```text
客户端 → SYN(seq=x) → 服务端
客户端 ← SYN+ACK(seq=y, ack=x+1) ← 服务端
客户端 → ACK(ack=y+1) → 服务端
```

为什么是三次：确认**双方的发送和接收能力都正常**，并同步初始序列号；两次的话，服务端无法确认客户端能收到自己的数据，且历史的重复连接请求可能导致服务端建立无效连接。

**四次挥手**：

```text
客户端 → FIN → 服务端          （客户端不再发送）
客户端 ← ACK ← 服务端
客户端 ← FIN ← 服务端          （服务端数据发送完毕后）
客户端 → ACK → 服务端          （客户端进入 TIME_WAIT，等待 2MSL）
```

为什么是四次：TCP 是全双工，每个方向需要单独关闭；服务端收到 FIN 后可能还有数据要发送，所以 ACK 和 FIN 分开发送。

**口述模板（30–60 秒）**

1. 一句话结论：三次握手建立连接，四次挥手断开连接。
2. 关键机制：三次握手确认双方收发能力并同步序列号；四次挥手因为全双工需要两个方向分别关闭。
3. 对比或注意点：TIME_WAIT 等待 2MSL，确保最后的 ACK 送达并让旧连接的数据包消失。
4. 可追问时补充：TCP 握手加 TLS 握手要多个往返，这是 HTTP/3 改进的重点。

**常见追问**

- 为什么要等待 2MSL？→ 如果最后的 ACK 丢失，服务端会重发 FIN，客户端需要能够响应；同时让本连接的残留报文在网络中消失。

### Q8. HTTPS 是怎么保证安全的？

- **难度**: 初级
- **标签**: 网络, TLS

**答案**

HTTPS = HTTP + TLS，提供三种保障：

| 保障 | 实现 |
|------|------|
| **机密性** | 对称加密传输数据（AES-GCM、ChaCha20） |
| **完整性** | AEAD 加密模式自带完整性校验 |
| **身份认证** | 证书 + CA 签名，证明服务器身份 |

**TLS 1.3 握手（简化，1-RTT）**：

```text
客户端 → ClientHello（支持的加密套件、密钥交换参数） → 服务端
客户端 ← ServerHello（选定套件、密钥交换参数）+ 证书 + 签名 + Finished ← 服务端
（双方通过 ECDHE 算出相同的会话密钥）
客户端 → Finished + 加密的 HTTP 请求 → 服务端
```

- **非对称加密**（ECDHE）用于协商密钥，**对称加密**用于传输数据（对称加密更快）
- ECDHE 提供**前向保密**：即使服务器私钥泄露，过去的通信也无法解密
- 证书验证：浏览器用内置的根证书验证证书链、域名、有效期、吊销状态

**口述模板（30–60 秒）**

1. 一句话结论：HTTPS 通过 TLS 提供机密性、完整性和身份认证。
2. 关键机制：非对称加密协商会话密钥，对称加密传输数据，证书和 CA 证明服务器身份。
3. 对比或注意点：TLS 1.3 握手只需要 1 个往返，并且强制前向保密。
4. 可追问时补充：证书链验证依赖浏览器或系统内置的根证书。

**常见追问**

- 为什么不全程使用非对称加密？→ 非对称加密计算成本高，速度慢，只用于密钥协商。

### Q9. 常见的 HTTP 状态码有哪些？

- **难度**: 初级
- **标签**: 网络, HTTP

**答案**

| 状态码 | 含义 |
|--------|------|
| 101 | 协议切换（WebSocket 升级） |
| 103 | Early Hints，提前告知要预加载的资源 |
| 200 | 成功 |
| 204 | 成功但无内容（预检请求、上报接口） |
| 206 | 部分内容（Range 请求，断点续传、视频） |
| 301 / 308 | 永久重定向（308 不允许改变请求方法） |
| 302 / 307 | 临时重定向（307 不允许改变请求方法） |
| 304 | 未修改，使用缓存 |
| 400 | 请求错误 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 不存在 |
| 405 | 方法不允许 |
| 429 | 请求过多（限流） |
| 500 | 服务器错误 |
| 502 | 网关收到上游的无效响应 |
| 503 | 服务不可用 |
| 504 | 网关等待上游超时 |

**口述模板（30–60 秒）**

1. 一句话结论：1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误。
2. 关键机制：304 用于协商缓存，206 用于范围请求。
3. 对比或注意点：301 / 302 可能被浏览器把 POST 改为 GET，308 / 307 保持方法不变。
4. 可追问时补充：401 是未认证，403 是已认证但无权限。

**常见追问**

- 502 和 504 有什么区别？→ 502 是上游返回了无效响应（例如上游进程崩溃），504 是上游响应超时。

### Q10. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

- **难度**: 初级
- **标签**: 网络, HTTP

**答案**

| 版本 | 传输层 | 主要特点 | 主要问题 |
|------|-------|---------|---------|
| HTTP/1.1 | TCP | 持久连接（keep-alive），文本协议 | 应用层队头阻塞：一个连接同时只能处理一个请求；浏览器每个域名最多 6 个连接 |
| HTTP/2 | TCP | 二进制分帧、**多路复用**、头部压缩（HPACK） | **TCP 层队头阻塞**：丢包时所有流都要等待 |
| HTTP/3 | **QUIC（UDP）** | 流之间独立、1-RTT / 0-RTT 建连、连接迁移、QPACK | 部分网络环境限制 UDP |

**口述模板（30–60 秒）**

1. 一句话结论：HTTP/2 解决了应用层队头阻塞，HTTP/3 解决了 TCP 层队头阻塞。
2. 关键机制：HTTP/2 通过多路复用在一个连接上并行传输；HTTP/3 基于 QUIC，每个流独立。
3. 对比或注意点：HTTP/3 建连更快，网络切换时连接不中断。
4. 可追问时补充：HTTP/2 的服务器推送已经被 Chrome 移除，改用 103 Early Hints。

**常见追问**

- 浏览器怎么知道服务器支持 HTTP/3？→ 通过响应头 `Alt-Svc` 或 DNS 的 HTTPS 记录。

## 三、渲染基础

### Q11. 浏览器的渲染流程是怎样的？

- **难度**: 初级
- **标签**: 渲染

**答案**

```text
HTML ──解析──> DOM 树
CSS  ──解析──> CSSOM（样式规则）
        ↓
样式计算（Style）：为每个 DOM 节点计算最终样式
        ↓
布局（Layout）：计算每个元素的位置和尺寸，生成布局树
        ↓
分层（Layer）：根据层叠上下文、transform 等划分图层
        ↓
绘制（Paint）：为每个层生成绘制指令列表
        ↓
分块与光栅化（Raster）：把层分成图块，转为位图（GPU）
        ↓
合成（Composite）：合成线程把图块组合成帧，交给 GPU 显示
```

- 前面的阶段（样式、布局、绘制）在**主线程**，分块和合成在**合成线程**，光栅化在**光栅线程 / GPU**
- 布局树只包含可见元素（`display: none` 的元素不在其中，伪元素在其中）

**口述模板（30–60 秒）**

1. 一句话结论：渲染流程是解析、样式计算、布局、分层、绘制、光栅化、合成。
2. 关键机制：主线程负责到绘制，合成线程负责分块和合成，GPU 负责光栅化和显示。
3. 对比或注意点：修改不同的属性会从不同的阶段开始重新执行。
4. 可追问时补充：transform 只需要从合成阶段开始，所以性能最好。

**常见追问**

- 什么是 Render Tree？→ 旧的说法，指 DOM 和 CSSOM 合并后的可见节点树；Chrome 中对应的是布局树。

### Q12. HTML 是怎么被解析成 DOM 的？

- **难度**: 初级
- **标签**: 解析

**答案**

```text
字节流 ──解码──> 字符流 ──分词──> 标记（Token）──树构建──> DOM 树
```

1. **解码**：根据 `Content-Type` 的 charset 或 `<meta charset>` 把字节转为字符
2. **分词（Tokenization）**：状态机识别开始标签、结束标签、属性、文本、注释
3. **树构建**：用栈维护当前打开的元素，根据标记创建节点并插入树中
4. **容错**：HTML 解析器会自动修复错误（未闭合的标签、错误的嵌套），所以 HTML 永远不会「解析失败」

**特点**：

- **增量解析**：边下载边解析，不需要等整个文档下载完
- 遇到同步 `<script>` 时暂停解析，执行脚本（脚本可能调用 `document.write` 修改文档）
- **预加载扫描器**在主解析器暂停时继续扫描后续 HTML，提前发现并下载资源

**口述模板（30–60 秒）**

1. 一句话结论：HTML 经过解码、分词、树构建生成 DOM。
2. 关键机制：分词是一个状态机，树构建用栈维护打开的元素，并且有很强的容错能力。
3. 对比或注意点：解析是增量的，同步脚本会暂停解析。
4. 可追问时补充：预加载扫描器在解析暂停时提前发现资源。

**常见追问**

- 为什么 `<meta charset>` 要放在最前面？→ 浏览器需要尽早确定编码，否则可能先按错误的编码解析，再重新解析。

### Q13. 回流（重排）和重绘有什么区别？

- **难度**: 初级
- **标签**: 渲染

**答案**

| 操作 | 触发条件 | 重新执行的阶段 |
|------|---------|---------------|
| **回流（Reflow / Layout）** | 几何属性变化：宽高、位置、字体大小、内容、窗口尺寸 | 样式 → 布局 → 分层 → 绘制 → 合成 |
| **重绘（Repaint）** | 外观变化：颜色、背景、阴影、visibility | 样式 → 绘制 → 合成 |
| **只合成** | `transform`、`opacity`（元素已在独立合成层） | 合成 |

**强制回流**：读取 `offsetWidth`、`getBoundingClientRect()` 等属性时，浏览器必须立即计算最新布局。

优化方法见 [性能优化初级 Q22](../performance/10-junior-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：回流是重新计算布局，重绘是重新绘制外观。
2. 关键机制：回流从布局阶段开始，重绘从绘制阶段开始，transform 只需要合成。
3. 对比或注意点：回流一定导致重绘。
4. 可追问时补充：读取布局属性会强制同步回流。

**常见追问**

- `visibility: hidden` 和 `display: none` 的区别？→ display none 不在布局树中，切换会回流；visibility hidden 仍占据空间，只触发重绘。

### Q14. 什么是事件循环？宏任务和微任务有哪些？

- **难度**: 初级
- **标签**: 事件循环

**答案**

JS 在主线程上单线程执行，通过**事件循环**处理异步任务：

```text
1. 从任务队列中取出一个任务（宏任务）执行
2. 执行完后，清空微任务队列（执行过程中新加入的微任务也会执行）
3. 如果需要，进行渲染（rAF → 样式 → 布局 → 绘制）
4. 回到第 1 步
```

| 类型 | 来源 |
|------|------|
| **任务（宏任务）** | script 整体、`setTimeout`、`setInterval`、事件回调、`MessageChannel`、网络回调 |
| **微任务** | `Promise.then / catch / finally`、`await` 之后的代码、`queueMicrotask`、`MutationObserver` |

```js
console.log(1)
setTimeout(() => console.log(2))
Promise.resolve().then(() => console.log(3))
console.log(4)
// 输出：1 4 3 2
```

**口述模板（30–60 秒）**

1. 一句话结论：事件循环每次执行一个任务，然后清空微任务，再视情况渲染。
2. 关键机制：Promise 回调是微任务，setTimeout 是任务，所以 Promise 先执行。
3. 对比或注意点：微任务会一直执行到队列为空，无限产生微任务会阻塞渲染。
4. 可追问时补充：渲染不是每轮循环都发生，通常与屏幕刷新率对齐。

**常见追问**

- `await` 后面的代码是同步还是异步？→ await 后面的代码相当于放在 `.then` 中，是微任务。

### Q15. `setTimeout` 的时间准确吗？

- **难度**: 初级
- **标签**: 事件循环, 定时器

**答案**

**不准确**，只能保证**至少**等待指定时间：

1. 到期后只是把回调放入任务队列，需要等主线程空闲，前面的任务执行完才能执行
2. **嵌套限制**：嵌套超过 5 层后，最小延迟为 4ms
3. **后台标签页**：浏览器会限制定时器（通常最多每秒执行一次，长时间后台还会更严格）
4. 电量节省模式、设备休眠也会影响

**需要精确计时时**：

- 动画用 `requestAnimationFrame`
- 计算经过时间用 `performance.now()` 而不是累加延迟
- 倒计时每次根据真实时间校正

**口述模板（30–60 秒）**

1. 一句话结论：setTimeout 不准确，只保证最少等待时间。
2. 关键机制：到期后进入任务队列，要等前面的任务执行完。
3. 对比或注意点：嵌套有 4ms 最小延迟，后台标签页会被节流。
4. 可追问时补充：倒计时要用真实时间差校正，而不是依赖定时器间隔。

**常见追问**

- `setTimeout(fn, 0)` 是立即执行吗？→ 不是，它会在当前任务和所有微任务执行完之后，作为新的任务执行。

### Q16. `requestAnimationFrame` 是什么？

- **难度**: 初级
- **标签**: 渲染, 动画

**答案**

`requestAnimationFrame(callback)` 让浏览器在**下一次渲染之前**调用回调：

- 执行频率与显示器刷新率一致（60Hz 时约 16.7ms 一次，120Hz 时约 8.3ms）
- 页面隐藏时暂停，节省资源
- 回调参数是当前帧的时间戳

```js
function animate(timestamp) {
  const progress = Math.min((timestamp - start) / duration, 1)
  el.style.transform = `translateX(${progress * 300}px)`
  if (progress < 1) requestAnimationFrame(animate)
}
const start = performance.now()
requestAnimationFrame(animate)
```

**与 setTimeout 的区别**：rAF 与刷新率同步，不会出现一帧执行两次或跳帧的情况。

**口述模板（30–60 秒）**

1. 一句话结论：rAF 在下一次渲染前执行回调，频率与屏幕刷新率一致。
2. 关键机制：在事件循环的渲染步骤中、样式计算之前执行。
3. 对比或注意点：页面隐藏时暂停；setTimeout 不与刷新率对齐，动画可能抖动。
4. 可追问时补充：动画要根据时间戳计算进度，而不是每帧固定步长，以适配不同刷新率。

**常见追问**

- 为什么要根据时间戳计算进度？→ 不同设备刷新率不同，固定步长在 120Hz 屏幕上动画会快一倍。

## 四、事件与 DOM

### Q17. DOM 事件流是什么？

- **难度**: 初级
- **标签**: 事件

**答案**

事件传播分为三个阶段：

```text
捕获阶段：window → document → html → body → ... → 目标的父元素
目标阶段：目标元素
冒泡阶段：目标的父元素 → ... → body → html → document → window
```

```js
el.addEventListener('click', handler)                    // 冒泡阶段（默认）
el.addEventListener('click', handler, { capture: true }) // 捕获阶段
```

- `event.stopPropagation()`：阻止继续传播
- `event.stopImmediatePropagation()`：同时阻止当前元素上的其他监听器
- `event.preventDefault()`：阻止默认行为（链接跳转、表单提交）
- `event.target`：触发事件的元素；`event.currentTarget`：绑定监听器的元素
- 不冒泡的事件：`focus`、`blur`（可用 `focusin` / `focusout` 代替）、`mouseenter`、`mouseleave`、`load` 等

**口述模板（30–60 秒）**

1. 一句话结论：事件流分为捕获、目标、冒泡三个阶段。
2. 关键机制：默认在冒泡阶段触发，capture 选项在捕获阶段触发。
3. 对比或注意点：target 是触发事件的元素，currentTarget 是绑定监听器的元素。
4. 可追问时补充：focus、mouseenter 等事件不冒泡。

**常见追问**

- 为什么要有捕获阶段？→ 历史上 Netscape 用捕获、IE 用冒泡，W3C 标准合并了两者；捕获阶段可以在事件到达目标前进行拦截。

### Q18. 什么是事件委托？有什么好处？

- **难度**: 初级
- **标签**: 事件

**答案**

把子元素的事件监听器绑定在**父元素**上，利用冒泡在父元素中根据 `event.target` 判断来源：

```js
list.addEventListener('click', (event) => {
  const item = event.target.closest('li[data-id]')
  if (!item || !list.contains(item)) return
  handleClick(item.dataset.id)
})
```

**好处**：

- 减少监听器数量，节省内存
- 动态添加的子元素自动生效，无需重新绑定

**注意**：

- 使用 `closest` 处理点击到子元素内部的情况
- 不冒泡的事件无法委托
- 委托层级过高（例如都绑定在 document 上），每次事件都要执行判断

React 17+ 把事件委托在应用的根容器上，而不是 document。

**口述模板（30–60 秒）**

1. 一句话结论：事件委托是把监听器绑定在父元素上，利用冒泡处理子元素的事件。
2. 关键机制：通过 event.target 和 closest 找到实际的子元素。
3. 对比或注意点：好处是监听器少、动态元素自动生效；不冒泡的事件不能委托。
4. 可追问时补充：React 把事件委托在根容器上。

**常见追问**

- 为什么要用 closest？→ 点击的可能是 li 内部的 span，target 是 span 而不是 li。

### Q19. `DOMContentLoaded` 和 `load` 有什么区别？

- **难度**: 初级
- **标签**: 事件, 生命周期

**答案**

| 事件 | 触发时机 |
|------|---------|
| `DOMContentLoaded` | HTML 解析完成，DOM 构建完毕，**defer 脚本执行完**之后；不等待图片、样式表（但如果有脚本在样式表之后，需要等样式表加载） |
| `load` | 页面所有资源（图片、样式、iframe、脚本）加载完成 |

相关：

- `document.readyState`：`loading` → `interactive`（对应 DOMContentLoaded 前后）→ `complete`（对应 load）
- `beforeunload`：离开前提示
- `pagehide` / `pageshow`：配合 bfcache
- `visibilitychange`：页面可见性变化，是上报数据最可靠的时机

**口述模板（30–60 秒）**

1. 一句话结论：DOMContentLoaded 在 DOM 构建完成后触发，load 在所有资源加载完成后触发。
2. 关键机制：defer 脚本在 DOMContentLoaded 之前执行。
3. 对比或注意点：async 脚本可能在 DOMContentLoaded 之前或之后执行。
4. 可追问时补充：页面数据上报应该在 visibilitychange 中进行，而不是 unload。

**常见追问**

- CSS 会延迟 DOMContentLoaded 吗？→ CSS 本身不会；但如果 CSS 后面有同步脚本，脚本要等 CSS 加载完才能执行，从而间接延迟。

## 五、存储

### Q20. Cookie、localStorage、sessionStorage、IndexedDB 有什么区别？

- **难度**: 初级
- **标签**: 存储

**答案**

| 对比项 | Cookie | localStorage | sessionStorage | IndexedDB |
|--------|--------|--------------|----------------|-----------|
| 容量 | 约 4KB | 约 5MB | 约 5MB | 大（按磁盘配额） |
| 生命周期 | 可设置过期时间 | 永久，除非清除 | 标签页关闭即清除 | 永久，除非清除 |
| 是否随请求发送 | **是** | 否 | 否 | 否 |
| API | 字符串操作 | 同步 | 同步 | 异步，支持事务和索引 |
| 作用域 | Domain + Path | 同源 | 同源 + 同一标签页 | 同源 |
| Worker 中可用 | 否（Cookie Store API 部分支持） | 否 | 否 | 是 |

**选择**：

- 认证信息：HttpOnly Cookie
- 少量配置：localStorage
- 表单草稿等标签页级数据：sessionStorage
- 大量结构化数据、离线数据：IndexedDB

**注意**：localStorage 是**同步**的，大量读写会阻塞主线程。

**口述模板（30–60 秒）**

1. 一句话结论：Cookie 小且随请求发送，Web Storage 是简单的键值存储，IndexedDB 是异步的大容量数据库。
2. 关键机制：sessionStorage 以标签页为作用域，localStorage 以源为作用域。
3. 对比或注意点：localStorage 是同步 API，会阻塞主线程。
4. 可追问时补充：认证信息应该放在 HttpOnly Cookie 中，避免被 XSS 读取。

**常见追问**

- 复制标签页时 sessionStorage 会复制吗？→ 会，新标签页会得到一份副本，之后两者独立。

### Q21. Cookie 有哪些属性？

- **难度**: 初级
- **标签**: 存储, 安全

**答案**

```text
Set-Cookie: sid=abc; Domain=example.com; Path=/; Max-Age=3600; Secure; HttpOnly; SameSite=Lax
```

| 属性 | 作用 |
|------|------|
| `Domain` | 可访问的域名；设置后子域名也可访问；不设置时只有当前主机 |
| `Path` | 可访问的路径 |
| `Expires` / `Max-Age` | 过期时间；都不设置时是会话 Cookie |
| `Secure` | 只在 HTTPS 下发送 |
| `HttpOnly` | JS 无法读取（防止 XSS 窃取） |
| `SameSite` | 跨站请求时是否发送：`Strict`、`Lax`（Chrome 默认）、`None`（必须同时设置 Secure） |
| `Partitioned` | CHIPS：按顶级站点分区存储的第三方 Cookie |

**SameSite 的取值**：

- `Strict`：跨站请求都不发送（从外部链接进入也不带，体验差）
- `Lax`：跨站的顶级导航 GET 请求发送，其他跨站请求（iframe、fetch、POST 表单）不发送
- `None`：都发送，用于第三方场景

**口述模板（30–60 秒）**

1. 一句话结论：Cookie 的属性控制作用域、过期时间和安全性。
2. 关键机制：HttpOnly 防止 JS 读取，Secure 只在 HTTPS 发送，SameSite 控制跨站发送。
3. 对比或注意点：Chrome 默认 SameSite=Lax，设置 None 必须同时设置 Secure。
4. 可追问时补充：Partitioned 属性用于按顶级站点分区的第三方 Cookie。

**常见追问**

- 「跨站」和「跨域」有什么区别？→ 跨域（跨源）比较协议、主机和端口；跨站比较「协议 + 可注册域名」（eTLD+1），例如 a.example.com 和 b.example.com 跨源但同站。

## 六、安全基础

### Q22. 什么是同源策略？限制了什么？

- **难度**: 初级
- **标签**: 安全

**答案**

**同源**：协议、主机、端口都相同。

**限制**：

- **DOM 访问**：不同源的页面不能互相访问 DOM（iframe、`window.open`）
- **数据读取**：不能读取跨源请求的响应（fetch / XHR 需要 CORS 授权）
- **存储**：Cookie（按域名）、localStorage、IndexedDB 按源隔离

**不限制的**：

- 跨源**嵌入**资源：`<img>`、`<script>`、`<link>`、`<video>`、`<iframe>`
- 跨源**发送**请求（表单提交、跳转），只是不能读取响应——这也是 CSRF 能够发生的原因

**口述模板（30–60 秒）**

1. 一句话结论：同源策略要求协议、主机、端口相同，限制跨源读取 DOM、响应和存储。
2. 关键机制：可以跨源嵌入资源和发送请求，但不能读取响应。
3. 对比或注意点：同源策略不阻止请求发出，所以需要额外的 CSRF 防护。
4. 可追问时补充：CORS 是服务端授权跨源读取的机制。

**常见追问**

- 跨源请求被 CORS 拦截时，请求到达服务器了吗？→ 简单请求已经到达并被处理了，只是浏览器不把响应交给 JS；需要预检的请求在预检失败时不会发送实际请求。

### Q23. 有哪些跨域解决方案？

- **难度**: 初级
- **标签**: 安全, 跨域

**答案**

| 方案 | 原理 | 适用 |
|------|------|------|
| **CORS** | 服务端返回 `Access-Control-Allow-Origin` 等响应头授权 | 标准方案，首选 |
| **反向代理** | 开发服务器代理或 Nginx 转发，使请求变为同源 | 开发环境、BFF |
| `postMessage` | 窗口之间（iframe、window.open）安全通信 | 跨源页面通信 |
| JSONP | 利用 `<script>` 可以跨源加载，回调函数接收数据 | 只支持 GET，有安全风险，已基本淘汰 |
| WebSocket | 不受同源策略限制（服务端应校验 Origin） | 实时通信 |
| `document.domain` | 设置为相同的父域名 | **已被废弃**，Chrome 默认禁用 |

**口述模板（30–60 秒）**

1. 一句话结论：标准方案是 CORS，开发时常用代理，页面之间用 postMessage。
2. 关键机制：CORS 由服务端通过响应头授权，代理通过服务端转发绕开浏览器限制。
3. 对比或注意点：JSONP 只支持 GET 且有安全风险，document.domain 已被废弃。
4. 可追问时补充：WebSocket 不受同源限制，服务端必须校验 Origin 头。

**常见追问**

- postMessage 需要注意什么？→ 发送时指定 targetOrigin，接收时校验 `event.origin`，否则可能被恶意页面利用。

### Q24. 什么是 XSS？有哪些类型？

- **难度**: 初级
- **标签**: 安全, XSS

**答案**

**XSS（跨站脚本攻击）**：攻击者把恶意脚本注入到页面中，在用户的浏览器中执行，可以窃取 Cookie、伪造操作、篡改页面。

| 类型 | 原理 | 示例 |
|------|------|------|
| **存储型** | 恶意脚本存储在服务器（评论、昵称），其他用户访问时执行 | 评论内容包含 `<img src=x onerror=...>` |
| **反射型** | 恶意脚本在 URL 参数中，服务端直接拼接到页面返回 | 搜索结果页显示 `?q=<script>...` |
| **DOM 型** | 前端 JS 把不可信的数据写入 DOM | `el.innerHTML = location.hash.slice(1)` |

**基本防御**：

- 输出时根据上下文转义（HTML、属性、JS、URL）
- 避免 `innerHTML`、`eval`、`v-html`、`dangerouslySetInnerHTML`；必须使用时用 DOMPurify 净化
- Cookie 设置 HttpOnly
- CSP 限制脚本来源

详见 [中级 Q26](20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：XSS 是把恶意脚本注入页面执行，分为存储型、反射型和 DOM 型。
2. 关键机制：根源是把不可信的数据当作代码或 HTML 处理。
3. 对比或注意点：存储型影响范围最大，DOM 型完全发生在前端。
4. 可追问时补充：防御组合是转义、避免危险 API、HttpOnly 和 CSP。

**常见追问**

- React 能防止 XSS 吗？→ 默认会转义文本内容，但 `dangerouslySetInnerHTML`、`href="javascript:..."` 等仍有风险。

### Q25. 什么是 CSRF？怎么防御？

- **难度**: 初级
- **标签**: 安全, CSRF

**答案**

**CSRF（跨站请求伪造）**：用户已登录 A 网站，访问恶意网站 B，B 构造请求发往 A，浏览器自动携带 A 的 Cookie，A 误以为是用户本人的操作。

```html
<!-- 恶意网站中 -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker" />
  <input name="amount" value="10000" />
</form>
<script>document.forms[0].submit()</script>
```

**防御**：

| 方法 | 原理 |
|------|------|
| **SameSite Cookie** | `Lax` / `Strict` 让跨站请求不携带 Cookie（Chrome 默认 Lax） |
| **CSRF Token** | 页面中包含随机 Token，请求时提交，服务端校验；攻击者无法读取 Token |
| **校验 Origin / Referer** | 服务端检查请求来源 |
| 敏感操作二次确认 | 验证码、密码 |

**注意**：GET 请求不应该有副作用；SameSite=Lax 允许顶级导航的 GET 请求携带 Cookie。

**口述模板（30–60 秒）**

1. 一句话结论：CSRF 利用浏览器自动携带 Cookie 的特性，伪造用户的请求。
2. 关键机制：攻击者可以发送请求，但无法读取响应和页面中的 Token。
3. 对比或注意点：防御方式有 SameSite、CSRF Token 和 Origin 校验。
4. 可追问时补充：GET 请求不能有副作用，否则 SameSite=Lax 也挡不住。

**常见追问**

- 使用 Authorization 头（Bearer Token）还需要防 CSRF 吗？→ 浏览器不会自动添加 Authorization 头，所以天然免疫 CSRF；但 Token 存在 localStorage 中会面临 XSS 风险。

### Q26. 浏览器缓存有哪些位置？查找顺序是什么？

- **难度**: 初级
- **标签**: 缓存

**答案**

**查找顺序**：

1. **Service Worker 缓存**：SW 拦截请求，自行决定返回缓存还是请求网络
2. **Memory Cache**：内存缓存，当前页面已加载的资源，关闭标签页即释放
3. **Disk Cache**（HTTP 缓存）：按 HTTP 缓存头存储在磁盘
4. 网络请求（HTTP/2 的推送缓存已随服务器推送被移除）

Network 面板中显示为 `(ServiceWorker)`、`(memory cache)`、`(disk cache)`。

HTTP 缓存的强缓存和协商缓存规则见 [中级 Q5](20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：查找顺序是 Service Worker、内存缓存、磁盘缓存，最后是网络。
2. 关键机制：内存缓存速度最快但生命周期短，磁盘缓存遵循 HTTP 缓存规则。
3. 对比或注意点：Service Worker 完全由开发者控制。
4. 可追问时补充：HTTP 缓存按网络分区键存储，不同顶级站点之间不共享缓存。

**常见追问**

- 为什么不同网站引用同一个 CDN 上的 jQuery 不能共享缓存？→ 浏览器对 HTTP 缓存做了分区（按顶级站点），防止通过缓存探测用户的浏览历史。

### Q27. Web Worker、Service Worker、Shared Worker 有什么区别？

- **难度**: 初级
- **标签**: Worker

**答案**

| 类型 | 作用 | 生命周期 | 作用范围 |
|------|------|---------|---------|
| **Web Worker**（Dedicated） | 在后台线程执行计算 | 随创建它的页面 | 一个页面 |
| **Shared Worker** | 多个同源页面共享一个 Worker | 所有连接的页面关闭后结束 | 同源的多个页面 |
| **Service Worker** | 拦截网络请求、离线缓存、推送通知、后台同步 | 独立于页面，由浏览器按需启动和终止 | 注册的作用域（scope） |

共同点：都不能访问 DOM，通过 `postMessage` 通信。

Service Worker 要求 HTTPS（localhost 除外）。

**口述模板（30–60 秒）**

1. 一句话结论：Web Worker 用于后台计算，Shared Worker 在多个页面间共享，Service Worker 是网络代理。
2. 关键机制：Service Worker 独立于页面运行，拦截作用域内的请求。
3. 对比或注意点：都不能访问 DOM，Service Worker 需要 HTTPS。
4. 可追问时补充：Service Worker 空闲时会被浏览器终止，不能在其中保存全局状态。

**常见追问**

- Shared Worker 的兼容性如何？→ Safari 曾长期不支持，近年已支持；跨标签页通信也可以用 BroadcastChannel。

### Q28. JS 的垃圾回收是怎样的？

- **难度**: 初级
- **标签**: 内存, GC

**答案**

**基本算法**：

- **引用计数**：记录对象被引用的次数，为 0 时回收。问题：**循环引用**无法回收（早期 IE 的 DOM 与 JS 对象循环引用导致泄漏）
- **标记清除**（现代浏览器使用）：从根对象（全局对象、调用栈中的变量）出发，标记所有可达的对象，回收不可达的对象。循环引用的对象如果不可达，也会被回收

**V8 的优化**：

- **分代回收**：新生代（存活时间短）用 Scavenge 快速回收，老生代用标记清除 + 整理
- **增量、并发、并行**：减少 GC 造成的主线程停顿

详见 [中级 Q24](20-mid-qa.md)。

**口述模板（30–60 秒）**

1. 一句话结论：现代浏览器使用基于可达性的标记清除算法。
2. 关键机制：从根对象出发标记可达对象，回收不可达的对象。
3. 对比或注意点：引用计数无法处理循环引用。
4. 可追问时补充：V8 使用分代回收，并通过增量和并发标记减少停顿。

**常见追问**

- 闭包一定会导致内存泄漏吗？→ 不会，闭包只是延长了被引用变量的生命周期，闭包本身不可达时会被正常回收。

### Q29. 页面的生命周期有哪些状态？

- **难度**: 初级
- **标签**: 生命周期

**答案**

Page Lifecycle API 定义的状态：

| 状态 | 说明 |
|------|------|
| **active** | 可见且有焦点 |
| **passive** | 可见但没有焦点 |
| **hidden** | 不可见（切换标签页、最小化） |
| **frozen** | 浏览器冻结页面以节省资源，定时器和任务暂停（bfcache 中的页面也是冻结的） |
| **terminated** | 页面已卸载 |
| **discarded** | 浏览器为节省内存丢弃了页面，再次访问时重新加载 |

**相关事件**：`visibilitychange`、`freeze` / `resume`、`pagehide` / `pageshow`。

**实践**：

- 在 `visibilitychange`（hidden）时保存状态和上报数据
- 页面恢复时检查 `document.wasDiscarded`，恢复用户的状态
- 不要依赖 `unload`

**口述模板（30–60 秒）**

1. 一句话结论：页面生命周期包括 active、passive、hidden、frozen、terminated 和 discarded。
2. 关键机制：浏览器会冻结或丢弃后台页面以节省资源。
3. 对比或注意点：hidden 是最后一个可靠的保存和上报时机。
4. 可追问时补充：被丢弃的页面再次访问时，通过 wasDiscarded 判断并恢复状态。

**常见追问**

- 为什么不能依赖 unload？→ 移动端切换应用、浏览器丢弃页面时 unload 不会触发；而且 unload 监听会阻止 bfcache。

### Q30. 怎么判断一个新的 Web API 能不能在生产中使用？

- **难度**: 初级
- **标签**: 兼容性

**答案**

1. **查兼容性**：MDN 的兼容性表格、Can I Use
2. **看 Baseline 状态**：
   - **Baseline Newly available**：所有主流浏览器（Chrome、Edge、Firefox、Safari）的最新版本都已支持
   - **Baseline Widely available**：达到 Newly available 30 个月之后，可以放心使用
   - **Limited availability**：至少一个主流浏览器不支持
3. **对照用户数据**：根据监控中真实用户的浏览器版本分布判断
4. **渐进增强**：特性检测，不支持时降级

```js
if ('IntersectionObserver' in window) {
  // 使用 IntersectionObserver
} else {
  // 降级方案
}

if (CSS.supports('content-visibility', 'auto')) { /* ... */ }
```

**口述模板（30–60 秒）**

1. 一句话结论：查兼容性表格和 Baseline 状态，并结合真实用户的浏览器分布判断。
2. 关键机制：Baseline Widely available 表示所有主流浏览器支持超过 30 个月。
3. 对比或注意点：不确定时使用特性检测和渐进增强。
4. 可追问时补充：Vite 7 起默认构建目标就是 baseline-widely-available。

**常见追问**

- 特性检测和 UA 检测哪个好？→ 特性检测更可靠，UA 可以被伪造且版本判断容易出错。
