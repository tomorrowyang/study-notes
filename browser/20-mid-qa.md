## 一、进程与架构

### Q1. Chrome 的多进程架构是怎样演进的？

- **难度**: 中级
- **标签**: 架构

**答案**

**演进**：

1. **单进程浏览器**（早期 IE）：一个页面崩溃导致整个浏览器崩溃；插件漏洞可以直接攻击系统
2. **多进程**（Chrome 2008）：浏览器进程 + 每个标签页一个渲染进程 + 插件进程，渲染进程在沙箱中
3. **站点隔离**（2018）：按站点分配渲染进程，跨站 iframe 也运行在单独的进程中（OOPIF）
4. **服务化（Servicification）**：把网络、存储、音频等功能拆分为独立的服务，可以运行在独立进程中，也可以在资源紧张的设备上合并到浏览器进程

**进程分配的灵活性**：

- 桌面端内存充足时，服务独立进程，隔离性更好
- 低内存设备（部分 Android）合并服务到同一个进程，节省内存
- 渲染进程数量有上限，超过时同站点的页面会共享进程

**口述模板（30–60 秒）**

1. 一句话结论：Chrome 从多进程发展到站点隔离和服务化。
2. 关键机制：渲染进程按站点隔离，网络、存储等功能拆分为可独立部署的服务。
3. 对比或注意点：进程模型会根据设备内存动态调整。
4. 可追问时补充：站点隔离的直接原因是 Spectre 攻击。

**常见追问**

- 多进程浪费内存怎么办？→ 按设备内存调整进程模型，同站点共享进程，后台页面可以被冻结或丢弃。

### Q2. 什么是站点隔离？进程是怎么分配的？

- **难度**: 中级
- **标签**: 架构, 安全

**答案**

**站点隔离（Site Isolation）**：不同**站点**（scheme + eTLD+1，例如 `https://example.com`）的文档运行在不同的渲染进程中，包括跨站 iframe。

**为什么**：

- Spectre 等侧信道攻击可以读取**同一进程内**的任意内存
- 如果攻击者页面和银行页面在同一进程中，攻击者可能读取银行页面的数据
- 进程隔离让攻击者进程中根本不存在其他站点的数据

**进程分配**：

- 同一站点的页面可以共享进程（例如 `a.example.com` 和 `b.example.com` 同站）
- 跨站 iframe 运行在独立的进程中（**OOPIF**，Out-of-Process iframe）
- 浏览器进程负责把页面各部分的渲染结果合成到一起
- 配合 **ORB / CORB**：阻止渲染进程获取不应该读取的跨站数据（例如通过 `<img>` 请求 JSON）

**口述模板（30–60 秒）**

1. 一句话结论：站点隔离让不同站点运行在不同的渲染进程中，包括跨站 iframe。
2. 关键机制：Spectre 可以读取同进程内存，进程隔离让攻击者进程中不存在其他站点的数据。
3. 对比或注意点：按站点而不是按源隔离，同站不同子域可能共享进程。
4. 可追问时补充：ORB 防止通过 img、script 等标签把跨站的敏感数据加载到攻击者进程中。

**常见追问**

- 为什么按站点而不是按源隔离？→ 历史上 `document.domain` 允许同站的不同子域互相访问，必须在同一进程；Chrome 也在推进按源隔离（Origin-Agent-Cluster）。

### Q3. 渲染进程中的线程是怎么协作的？

- **难度**: 中级
- **标签**: 架构, 线程

**答案**

```text
主线程
  JS 执行、HTML / CSS 解析、样式计算、布局、预绘制（属性树）、绘制（生成显示列表）
      │ 提交（commit）
      ▼
合成线程
  接收层和属性树，分块（tiling），调度光栅化，处理滚动和合成动画，生成合成帧
      │
      ├──> 光栅线程 / GPU：把图块光栅化为纹理
      │
      ▼
  合成帧 ──> Viz（GPU 进程中的显示合成器）──> 屏幕
```

**关键点**：

- 主线程提交后，合成线程可以独立运行
- 主线程繁忙时，**滚动和 transform / opacity 动画**仍然可以在合成线程中进行
- 合成线程收到输入事件时，如果该区域没有需要主线程处理的事件监听（非 passive），可以直接滚动

**口述模板（30–60 秒）**

1. 一句话结论：主线程负责到绘制，合成线程负责分块和合成，光栅化由光栅线程和 GPU 完成。
2. 关键机制：主线程提交后，合成线程可以独立处理滚动和合成动画。
3. 对比或注意点：这就是 transform 动画在主线程繁忙时也流畅的原因。
4. 可追问时补充：非 passive 的事件监听会迫使合成线程等待主线程。

**常见追问**

- 为什么要提交而不是直接共享数据？→ 提交时复制一份状态给合成线程，主线程可以继续修改下一帧，两个线程互不阻塞。

## 二、导航与网络

### Q4. 浏览器导航的详细流程是什么？

- **难度**: 中级
- **标签**: 导航

**答案**

```text
浏览器进程（UI 线程）
  1. 处理输入，触发当前页面的 beforeunload
  2. 开始导航，通知网络服务发起请求
网络服务
  3. 检查 Service Worker（如果有，先启动 SW，可开启 Navigation Preload 并行请求）
  4. DNS → 连接 → TLS → 发送请求
  5. 收到响应头：
     - 3xx：重定向，回到第 3 步
     - 根据 Content-Type 和嗅探判断：HTML 交给渲染进程；其他类型可能触发下载
     - 安全检查（Safe Browsing、ORB）
浏览器进程
  6. 选择渲染进程（根据站点；可能在请求期间已经预先启动）
  7. 提交导航（Commit）：把响应数据流交给渲染进程，更新地址栏、历史记录、安全指示
渲染进程
  8. 解析与渲染，加载子资源
  9. 渲染进程通知加载完成（load），浏览器停止加载指示
```

**卸载旧页面**：新页面提交后，旧页面执行 `pagehide` / `unload`，或进入 bfcache。

**口述模板（30–60 秒）**

1. 一句话结论：导航由浏览器进程协调，网络服务请求，提交后交给渲染进程渲染。
2. 关键机制：响应头决定是渲染还是下载，提交导航时才切换地址栏和历史记录。
3. 对比或注意点：渲染进程可以在请求期间提前启动，节省时间。
4. 可追问时补充：有 Service Worker 时要先启动 SW，Navigation Preload 可以让 SW 启动和网络请求并行。

**常见追问**

- 为什么地址栏不是一输入就变化？→ 导航提交后才更新，防止地址栏显示的 URL 与实际页面内容不一致（地址栏欺骗）。

### Q5. 详细讲讲 HTTP 缓存机制

- **难度**: 中级
- **标签**: 缓存, HTTP

**答案**

**判断流程**：

```text
请求资源
 ├─ 有缓存？
 │   ├─ 新鲜（在 max-age 内）→ 直接使用（强缓存，200 from cache）
 │   └─ 过期 → 带上 If-None-Match / If-Modified-Since 请求
 │             ├─ 未修改 → 304，使用缓存并更新新鲜度
 │             └─ 已修改 → 200，返回新内容并更新缓存
 └─ 无缓存 → 正常请求
```

**`Cache-Control` 指令**：

| 指令 | 含义 |
|------|------|
| `max-age=N` | 新鲜期 N 秒 |
| `s-maxage=N` | 共享缓存（CDN、代理）的新鲜期，优先于 max-age |
| `no-cache` | 可以缓存，但每次使用前必须向服务器验证 |
| `no-store` | 不缓存 |
| `private` / `public` | 只能被浏览器缓存 / 可以被共享缓存 |
| `must-revalidate` | 过期后必须验证，不能使用过期内容 |
| `immutable` | 新鲜期内不会变化，刷新页面时也不需要验证 |
| `stale-while-revalidate=N` | 过期后 N 秒内可以先使用旧内容，后台验证 |

**验证器**：

- `ETag` / `If-None-Match`：基于内容（强 ETag 或 `W/` 弱 ETag），优先级更高
- `Last-Modified` / `If-Modified-Since`：秒级精度；文件内容不变但修改时间变化会导致不必要的更新

**启发式缓存**：没有 `Cache-Control` 和 `Expires` 但有 `Last-Modified` 时，浏览器按 `(当前时间 - Last-Modified) × 10%` 估算新鲜期，可能导致意外的缓存。

**`Vary`**：例如 `Vary: Accept-Encoding`，缓存键包含这些请求头。

**用户行为的影响**：普通刷新会验证主文档；强制刷新（Ctrl+Shift+R）跳过缓存。

**口述模板（30–60 秒）**

1. 一句话结论：先判断缓存是否新鲜，新鲜则直接使用，过期则带验证器请求，未修改返回 304。
2. 关键机制：Cache-Control 控制新鲜期和缓存行为，ETag 和 Last-Modified 用于验证。
3. 对比或注意点：no-cache 是每次验证，no-store 才是不缓存；没有缓存头时会触发启发式缓存。
4. 可追问时补充：immutable 让刷新时也不验证，适合带 hash 的资源。

**常见追问**

- 为什么一定要给 HTML 设置缓存头？→ 不设置时可能触发启发式缓存，用户拿到旧的 HTML，引用的是旧版本资源。

### Q6. HTTP/2 是怎么工作的？

- **难度**: 中级
- **标签**: 网络, HTTP/2

**答案**

**二进制分帧**：HTTP 消息被拆分为帧（HEADERS 帧、DATA 帧），每帧带有流 ID。

**多路复用**：

- 一个 TCP 连接上有多个**流**（stream），每个请求响应对应一个流
- 不同流的帧可以交错发送，接收端按流 ID 重组
- 解决了 HTTP/1.1 的应用层队头阻塞（一个慢请求阻塞后续请求）

**头部压缩（HPACK）**：

- 静态表（常用头部）+ 动态表（本连接中出现过的头部）+ 哈夫曼编码
- 重复的 Cookie、User-Agent 等只需要发送索引

**优先级**：原始的依赖树优先级过于复杂，实际实现不一致；现在使用 RFC 9218 的 `Priority` 头（urgency + incremental）。

**服务器推送**：Chrome 已移除（实际收益小，容易推送已缓存的资源），替代方案是 103 Early Hints。

**仍存在的问题**：TCP 层队头阻塞——一个 TCP 包丢失，所有流的后续数据都要等重传。

**口述模板（30–60 秒）**

1. 一句话结论：HTTP/2 通过二进制分帧和多路复用，在一个连接上并行传输多个请求。
2. 关键机制：每帧带流 ID，交错发送后按流重组；HPACK 压缩重复的头部。
3. 对比或注意点：服务器推送已被移除，TCP 层的队头阻塞仍然存在。
4. 可追问时补充：丢包率高的移动网络中，HTTP/2 可能不如多个 HTTP/1.1 连接。

**常见追问**

- 为什么丢包时 HTTP/2 可能比 HTTP/1.1 更差？→ HTTP/2 所有请求共享一个 TCP 连接，一次丢包阻塞所有请求；HTTP/1.1 的多个连接之间互不影响。

### Q7. QUIC 和 HTTP/3 解决了什么问题？

- **难度**: 中级
- **标签**: 网络, HTTP/3

**答案**

QUIC 基于 UDP，在用户态实现可靠传输、拥塞控制和加密：

| 问题 | QUIC 的解决方式 |
|------|-----------------|
| TCP 队头阻塞 | 每个流独立处理丢包和重传，一个流丢包不影响其他流 |
| 建连慢（TCP + TLS 需要 2–3 个 RTT） | 传输和加密握手合并：首次 1-RTT，恢复连接 0-RTT |
| 网络切换时连接中断 | 使用连接 ID 而不是四元组标识连接，切换网络后连接继续（连接迁移） |
| TCP 升级困难（内核实现，中间设备僵化） | 用户态实现，可以快速迭代；数据几乎全部加密，中间设备无法干预 |

**HTTP/3**：HTTP 语义运行在 QUIC 上，头部压缩改为 QPACK（适配乱序到达）。

**挑战**：部分网络环境限制 UDP；UDP 在用户态处理的 CPU 开销较高。浏览器会同时尝试并回退到 HTTP/2。

**口述模板（30–60 秒）**

1. 一句话结论：QUIC 在 UDP 上实现可靠传输，解决了 TCP 的队头阻塞、建连慢和连接迁移问题。
2. 关键机制：流之间独立，握手合并，用连接 ID 标识连接。
3. 对比或注意点：部分网络限制 UDP，浏览器需要回退到 HTTP/2。
4. 可追问时补充：QUIC 在用户态实现，可以快速迭代，不依赖操作系统升级。

**常见追问**

- 0-RTT 有什么风险？→ 0-RTT 数据没有防重放保护，只能用于幂等请求。

### Q8. TLS 握手和证书验证的细节是什么？

- **难度**: 中级
- **标签**: 网络, TLS

**答案**

**TLS 1.2 vs 1.3**：

| 对比项 | TLS 1.2 | TLS 1.3 |
|--------|---------|---------|
| 握手往返 | 2-RTT | 1-RTT（恢复时 0-RTT） |
| 密钥交换 | 支持 RSA（无前向保密）和 ECDHE | 只支持 (EC)DHE，强制前向保密 |
| 加密套件 | 很多，包括不安全的 | 只保留 AEAD 套件 |
| 证书 | 明文传输 | 加密传输 |

**证书验证**：

1. 构建**证书链**：服务器证书 → 中间证书 → 根证书（根证书在操作系统或浏览器的信任库中）
2. 用上级证书的公钥验证下级证书的签名
3. 检查域名（SAN 字段）、有效期、用途
4. 检查吊销状态：OCSP / OCSP Stapling（服务器附带 OCSP 响应）、浏览器的 CRLSet 等
5. 证书透明度（CT）：证书必须记录在公开日志中，防止 CA 违规签发

**常见问题**：服务器没有发送中间证书导致部分客户端验证失败；证书过期。

**口述模板（30–60 秒）**

1. 一句话结论：TLS 1.3 将握手减少到 1 个往返并强制前向保密。
2. 关键机制：证书验证要构建证书链、验证签名、检查域名、有效期和吊销状态。
3. 对比或注意点：证书透明度防止 CA 违规签发证书。
4. 可追问时补充：服务器需要发送完整的中间证书，否则部分客户端会验证失败。

**常见追问**

- 中间人攻击怎么防御？→ 攻击者没有合法证书，浏览器验证失败会警告；HSTS 防止降级为 HTTP。

### Q9. 详细讲讲 CORS

- **难度**: 中级
- **标签**: 安全, 跨域

**答案**

**简单请求**（同时满足）：

- 方法是 GET、HEAD、POST
- 只包含安全的请求头（Accept、Content-Language 等）
- Content-Type 是 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`

简单请求直接发送，浏览器根据响应头决定 JS 能否读取响应。

**预检请求**（其他情况，例如 `Content-Type: application/json`、PUT、自定义头）：

```text
OPTIONS /api/data
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, x-token

响应：
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: content-type, x-token
Access-Control-Max-Age: 600       （预检结果缓存时间）
```

**带凭证的请求**（`fetch(url, { credentials: 'include' })`）：

- 响应必须有 `Access-Control-Allow-Credentials: true`
- `Access-Control-Allow-Origin` **不能是 `*`**，必须是具体的源
- 同时受 SameSite 限制：跨站请求要携带 Cookie，Cookie 必须是 `SameSite=None; Secure`

**其他**：

- `Access-Control-Expose-Headers`：允许 JS 读取的额外响应头
- 动态回显 Origin 时，要加 `Vary: Origin`，否则 CDN 可能把 A 源的响应缓存后返回给 B 源

**口述模板（30–60 秒）**

1. 一句话结论：CORS 分为简单请求和预检请求，服务端通过响应头授权跨源读取。
2. 关键机制：非简单请求先发送 OPTIONS 预检，确认允许的方法和头部后才发送实际请求。
3. 对比或注意点：带凭证的请求不能使用通配符，Cookie 还要满足 SameSite=None。
4. 可追问时补充：动态回显 Origin 要加 Vary: Origin。

**常见追问**

- 为什么 JSON 请求会触发预检？→ `application/json` 不在简单请求的 Content-Type 范围内，这是为了保护不支持 CORS 的旧服务器不受跨源的非常规请求影响。

### Q10. 浏览器是怎么管理连接的？

- **难度**: 中级
- **标签**: 网络

**答案**

- **HTTP/1.1**：同一主机（host + port + 协议）最多 6 个并发连接；keep-alive 复用连接
- **HTTP/2 / HTTP/3**：同一源通常只使用一个连接；满足证书覆盖和 IP 相同时，**不同域名也可以复用同一个连接**（连接合并）
- **连接池**：按网络分区键分区（与顶级站点关联），防止跨站跟踪
- **预连接**：`preconnect` 提前完成 DNS + TCP + TLS；浏览器也会根据用户的输入和历史预测连接
- **带凭证与不带凭证的请求**分别使用不同的连接（因此字体等 CORS 资源的 preconnect 需要 `crossorigin`）

**口述模板（30–60 秒）**

1. 一句话结论：HTTP/1.1 每个主机最多 6 个连接，HTTP/2 和 HTTP/3 通常每个源一个连接。
2. 关键机制：连接按网络分区键分区，带凭证和不带凭证的请求使用不同的连接。
3. 对比或注意点：preconnect 用于 CORS 资源时需要 crossorigin，否则建立的连接无法使用。
4. 可追问时补充：HTTP/2 支持连接合并，多个域名可以复用同一个连接。

**常见追问**

- 为什么 HTTP/2 下域名分片有害？→ 每个域名都需要额外的 DNS、TCP、TLS，而且无法共享同一个连接的拥塞窗口和压缩上下文。

## 三、解析与渲染

### Q11. 什么是预加载扫描器？HTML 解析有哪些阻塞情况？

- **难度**: 中级
- **标签**: 解析

**答案**

**解析阻塞**：

- 同步 `<script>`：主解析器暂停，下载并执行脚本（脚本可能调用 `document.write` 修改后续文档）
- 同步脚本之前有未加载完的样式表：脚本要等样式表加载完才能执行（脚本可能读取样式）

**预加载扫描器（Preload Scanner）**：主解析器被阻塞时，一个轻量的扫描器继续扫描后续的 HTML，**提前发现** `<img>`、`<link>`、`<script>` 等资源并开始下载。

**预加载扫描器发现不了的资源**：

- JS 动态插入的元素和资源
- CSS 中的 `background-image`、`@import`、字体
- `data-src` 等懒加载属性中的地址
- 由 JS 渲染的内容（CSR）

所以 LCP 图片应该直接写在 HTML 中，或者使用 `preload`。

**`document.write`**：在网络较慢的情况下，Chrome 会阻止通过 `document.write` 插入的跨站脚本。

**口述模板（30–60 秒）**

1. 一句话结论：同步脚本会阻塞解析，预加载扫描器在阻塞期间提前发现资源。
2. 关键机制：扫描器只扫描 HTML 中的标签，不执行 JS，不解析 CSS。
3. 对比或注意点：CSS 背景图、JS 插入的资源无法被提前发现。
4. 可追问时补充：这是 LCP 图片要写在 HTML 中的原因。

**常见追问**

- 推测性解析失败会怎样？→ 如果脚本通过 document.write 改变了后续文档，提前下载的资源可能被浪费。

### Q12. CSS 和 JS 是怎么阻塞渲染的？

- **难度**: 中级
- **标签**: 关键渲染路径

**答案**

| 资源 | 阻塞 DOM 解析 | 阻塞首次渲染 | 说明 |
|------|--------------|-------------|------|
| head 中的 `<link rel="stylesheet">` | 否 | **是** | 浏览器不会渲染没有样式的页面，避免 FOUC |
| `media` 不匹配的样式表 | 否 | 否 | 例如 `media="print"`，仍会以低优先级下载 |
| body 中的样式表 | 否 | 阻塞其后内容的渲染 | Chrome 中渲染会在该样式表之前暂停 |
| 同步 `<script>` | **是** | 是 | 还要等之前的样式表加载完才能执行 |
| `<script defer>` / `type="module"` | 否 | 否 | 解析完成后执行 |
| `<script async>` | 执行时中断 | 否 | |
| `@import` | — | 是 | 串行加载，加剧阻塞 |

**结论**：

- CSS 是**渲染阻塞**资源，也会**间接阻塞**脚本执行
- 同步 JS 是**解析阻塞**资源

**口述模板（30–60 秒）**

1. 一句话结论：CSS 阻塞渲染，同步 JS 阻塞解析，CSS 还会阻塞其后脚本的执行。
2. 关键机制：浏览器不渲染无样式的内容；脚本可能读取样式，必须等 CSS 准备好。
3. 对比或注意点：媒体不匹配的样式表不阻塞渲染，@import 会串行加载。
4. 可追问时补充：这就是关键 CSS 内联、脚本使用 defer 的原因。

**常见追问**

- 为什么不建议使用 `@import`？→ 浏览器要先下载并解析外层 CSS 才能发现 @import 的文件，形成串行请求链。

### Q13. 样式计算是怎么进行的？

- **难度**: 中级
- **标签**: 渲染, CSS

**答案**

**1. 解析 CSS**：把样式表解析为规则（选择器 + 声明）。

**2. 选择器匹配**：

- 选择器**从右向左**匹配：`.nav li a` 先找到所有 `a`，再检查祖先中是否有 `li`、`.nav`
- 原因：从右向左可以快速排除不匹配的元素；从左向右则需要遍历大量后代
- 浏览器对规则按最右边的选择器（id、class、标签）建立索引，只检查可能匹配的规则

**3. 层叠**：按来源（用户代理、用户、作者）、`!important`、**层级（`@layer`）**、优先级、出现顺序决定最终值。

**4. 继承与计算值**：

- 继承：`color`、`font` 等可继承属性从父元素继承
- 计算值：相对单位（`em`、`%`）转为绝对值（部分要到布局阶段才能确定）

**优化**：

- 避免过于复杂的选择器和 `:has()` 的大范围使用
- 减少大范围的样式失效（修改 body 上的 class 会让大量元素重新计算）

**口述模板（30–60 秒）**

1. 一句话结论：样式计算包括选择器匹配、层叠、继承和计算值。
2. 关键机制：选择器从右向左匹配，可以快速排除不匹配的元素。
3. 对比或注意点：在祖先元素上修改 class 会导致大范围的样式重新计算。
4. 可追问时补充：浏览器对规则建立索引，只检查可能匹配的规则。

**常见追问**

- `:has()` 为什么可能影响性能？→ 它让父元素的样式依赖于后代的变化，后代变化时需要向上检查。

### Q14. 布局阶段做了什么？

- **难度**: 中级
- **标签**: 渲染, 布局

**答案**

**输入**：DOM 和计算后的样式。

**输出**：布局树（Chrome LayoutNG 中为不可变的 Fragment 树），包含每个元素的位置和尺寸。

**过程**：

- 根据 `display` 决定布局算法：块布局、行内布局、Flex、Grid、表格
- 从根开始，父元素向子元素传递约束（可用宽度），子元素计算后返回尺寸
- 行内布局：文本分段、断行、处理双向文本

**布局树与 DOM 的差异**：

- `display: none` 的元素不在布局树中
- 伪元素（`::before`）在布局树中
- 匿名块：块元素中混合了行内内容时，会生成匿名块盒

**增量布局**：只重新布局被标记为「脏」的部分；但修改某些属性（例如宽度）可能影响父元素和兄弟元素。

**`contain: layout`** 可以把布局影响限制在元素内部。

**口述模板（30–60 秒）**

1. 一句话结论：布局阶段根据样式计算每个元素的位置和尺寸，生成布局树。
2. 关键机制：父元素向下传递约束，子元素返回尺寸，按 display 选择布局算法。
3. 对比或注意点：布局树与 DOM 不是一一对应的。
4. 可追问时补充：增量布局只处理脏节点，contain 可以限制布局的影响范围。

**常见追问**

- 什么是 BFC？→ 块级格式化上下文，一个独立的布局区域，内部元素不影响外部（例如阻止外边距合并、包含浮动）。

### Q15. 分层和绘制阶段做了什么？

- **难度**: 中级
- **标签**: 渲染, 绘制

**答案**

**分层**：

- 有些元素需要独立的合成层：3D transform、`will-change: transform / opacity`、`<video>`、`<canvas>`、有合成动画的元素、需要独立滚动的区域等
- 层叠上下文决定绘制顺序；与合成层重叠的元素可能被**隐式提升**为合成层，以保证顺序正确

**预绘制（Pre-paint）**：Chrome 构建**属性树**（transform 树、clip 树、effect 树、scroll 树），描述每个元素的变换、裁剪、透明度和滚动关系。

**绘制**：

- **不是直接画像素**，而是生成**绘制指令列表**（显示列表），例如「在 (x, y) 处画一个矩形」「画文本」
- 按层叠顺序（背景 → 浮动 → 行内内容 → 定位元素）记录

**口述模板（30–60 秒）**

1. 一句话结论：分层决定哪些内容需要独立的合成层，绘制生成绘制指令列表而不是像素。
2. 关键机制：属性树描述变换、裁剪、透明度和滚动，合成线程可以根据它独立处理。
3. 对比或注意点：与合成层重叠的元素可能被隐式提升，导致层数量过多。
4. 可追问时补充：真正的像素是在光栅化阶段生成的。

**常见追问**

- 层叠上下文和合成层是一回事吗？→ 不是。层叠上下文是 CSS 概念，决定绘制顺序；合成层是浏览器的实现机制，决定哪些内容单独光栅化和合成。

### Q16. 光栅化和合成是怎么进行的？

- **难度**: 中级
- **标签**: 渲染, 合成

**答案**

**分块（Tiling）**：合成线程把每个层分成图块（例如 256×256 或更大），因为层可能非常大（长页面），不需要一次性光栅化全部内容。

**光栅化**：

- 把绘制指令转为像素（位图 / GPU 纹理）
- **优先光栅化视口附近的图块**
- Chrome 使用 GPU 光栅化，并在 GPU 进程中执行（OOP-R，Out-of-Process Raster）

**合成**：

- 合成线程根据属性树（位置、变换、透明度、裁剪）计算每个图块应该绘制在哪里，生成**合成帧**（由一系列 draw quad 组成）
- 合成帧发送到 GPU 进程的 **Viz**，Viz 把多个来源的帧（页面、跨站 iframe、浏览器 UI）合成后显示

**滚动的实现**：滚动只是改变 scroll 树中的偏移，合成线程重新合成即可；如果新露出的区域还没有光栅化，就会短暂出现空白（checkerboarding）。

**口述模板（30–60 秒）**

1. 一句话结论：合成线程把层分块，光栅化后根据属性树生成合成帧，由 Viz 显示。
2. 关键机制：优先光栅化视口附近的图块，光栅化在 GPU 进程中进行。
3. 对比或注意点：滚动和 transform 只需要重新合成，不需要重新光栅化。
4. 可追问时补充：快速滚动时看到的空白就是图块还没有光栅化。

**常见追问**

- 为什么 transform 缩放后文字可能模糊？→ 合成时缩放的是已经光栅化的纹理，没有重新光栅化；浏览器会在动画结束后重新光栅化。

### Q17. 浏览器一帧中做了哪些事？

- **难度**: 中级
- **标签**: 渲染, 帧

**答案**

以 60Hz 为例，每帧约 16.7ms：

```text
VSync 信号
  ↓
输入事件处理（连续事件如 mousemove、touchmove、scroll 会对齐到帧）
  ↓
定时器、其他任务（事件循环中的任务）
  ↓
滚动、resize 事件，媒体查询、CSS 动画更新
  ↓
requestAnimationFrame 回调
  ↓
样式计算 → 布局 → 预绘制 → 绘制（主线程）
  ↓
提交给合成线程 → 分块、光栅化 → 合成 → 显示
  ↓
空闲时间：requestIdleCallback
```

- 主线程工作超过帧预算时会**掉帧**
- 合成线程独立运行，主线程掉帧时合成动画和滚动仍可能保持流畅
- 高刷新率屏幕（120Hz）每帧只有约 8.3ms

**口述模板（30–60 秒）**

1. 一句话结论：一帧中依次处理输入、任务、rAF、样式、布局、绘制，然后提交合成。
2. 关键机制：主线程工作超过帧预算就会掉帧。
3. 对比或注意点：连续输入事件会对齐到帧，rAF 在样式计算之前执行。
4. 可追问时补充：高刷新率屏幕的帧预算更短。

**常见追问**

- 为什么 rAF 中修改 DOM 是合适的？→ rAF 在本帧样式和布局之前执行，修改会在本帧中一次性生效，不会额外触发布局。

## 四、事件循环

### Q18. HTML 规范中的事件循环是怎样的？

- **难度**: 中级
- **标签**: 事件循环

**答案**

**组成**：

- **多个任务队列**：按任务源区分（用户交互、定时器、网络、DOM 操作等），浏览器可以决定优先从哪个队列取任务（通常输入事件优先）
- **一个微任务队列**

**一轮循环（简化）**：

```text
1. 从某个任务队列中选出最早的可运行任务并执行
2. 执行微任务检查点：依次执行微任务，直到队列为空（执行中新加入的也会执行）
3. 如果是渲染时机（Rendering Opportunity）：
   - 处理 resize、scroll 事件
   - 评估媒体查询、更新动画、全屏
   - 执行 rAF 回调
   - 执行 IntersectionObserver / ResizeObserver 回调
   - 更新渲染（样式、布局、绘制）
4. 如果空闲，可以执行 requestIdleCallback
```

**渲染时机**：浏览器根据刷新率、页面是否可见、是否有视觉变化决定是否渲染，**不是每轮循环都渲染**。

**口述模板（30–60 秒）**

1. 一句话结论：每轮循环执行一个任务，清空微任务，在合适时机进行渲染。
2. 关键机制：有多个任务队列，浏览器可以优先处理输入；渲染步骤中执行 rAF 和观察者回调。
3. 对比或注意点：渲染不是每轮都发生，与刷新率对齐。
4. 可追问时补充：长任务和无限微任务都会推迟渲染。

**常见追问**

- 每个 rAF 回调之间会执行微任务吗？→ 会，每个回调执行完后都会执行一次微任务检查点。

### Q19. 怎么分析复杂的事件循环输出顺序？

- **难度**: 中级
- **标签**: 事件循环

**答案**

```js
async function a1() {
  console.log('a1 start')
  await a2()
  console.log('a1 end')
}
async function a2() {
  console.log('a2')
}

console.log('script start')
setTimeout(() => console.log('timeout'), 0)
a1()
new Promise((resolve) => {
  console.log('promise executor')
  resolve()
}).then(() => console.log('then1')).then(() => console.log('then2'))
queueMicrotask(() => console.log('microtask'))
console.log('script end')
```

**输出**：

```text
script start
a1 start
a2
promise executor
script end
a1 end
then1
microtask
then2
timeout
```

**分析步骤**：

1. 同步代码按顺序执行：`a1` 中 `await` 之前的代码和 `a2` 的同步部分立即执行；Promise 执行器是同步的
2. 微任务按入队顺序：`await` 之后的代码（a1 end）先入队 → then1 → microtask；then2 在 then1 执行后才入队
3. 微任务清空后，执行下一个任务 timeout

**规则**：

- `await x`：x 是原生 Promise 时，后续代码在一个微任务后执行（现代引擎已经优化，不再多等两个微任务）
- `.then` 链：下一个 then 在前一个执行完后才入队
- `MutationObserver` 回调也是微任务

**口述模板（30–60 秒）**

1. 一句话结论：先执行同步代码，再按入队顺序执行微任务，最后执行下一个任务。
2. 关键机制：await 之后的代码相当于 then 回调；then 链中下一个回调在前一个执行后才入队。
3. 对比或注意点：Promise 执行器是同步执行的。
4. 可追问时补充：返回一个 thenable 或 Promise 的 then 回调会额外多等待几个微任务。

**常见追问**

- `then` 中返回一个 Promise 会怎样？→ 需要额外的微任务来解析这个 Promise（通常多 2 个微任务），所以后续 then 会延后。

### Q20. 浏览器和 Node.js 的事件循环有什么区别？

- **难度**: 中级
- **标签**: 事件循环, Node

**答案**

| 对比项 | 浏览器 | Node.js |
|--------|--------|---------|
| 实现 | HTML 规范，各浏览器实现 | libuv |
| 结构 | 任务队列 + 微任务队列 + 渲染 | 多个阶段：timers → pending callbacks → poll → check → close callbacks |
| 特有 API | rAF、rIC | `setImmediate`（check 阶段）、`process.nextTick` |
| 微任务时机 | 每个任务之后 | 每个回调之后（Node 11+ 与浏览器一致） |
| 优先级 | — | `process.nextTick` 队列优先于 Promise 微任务 |
| 渲染 | 有 | 无 |

```js
// Node 中
setTimeout(() => console.log('timeout'), 0)
setImmediate(() => console.log('immediate'))
// 在主模块中顺序不确定；在 I/O 回调中 immediate 一定先执行
```

**口述模板（30–60 秒）**

1. 一句话结论：浏览器的事件循环包括任务、微任务和渲染；Node 基于 libuv，分为多个阶段。
2. 关键机制：Node 有 setImmediate 和 process.nextTick，nextTick 优先于 Promise。
3. 对比或注意点：Node 11 之后，每个回调执行完都会清空微任务，与浏览器一致。
4. 可追问时补充：主模块中 setTimeout 0 和 setImmediate 的顺序不确定。

**常见追问**

- 为什么主模块中顺序不确定？→ 取决于进入事件循环时 1ms 的定时器是否已经到期，这与进程启动的耗时有关。

### Q21. 浏览器是怎么处理输入事件的？

- **难度**: 中级
- **标签**: 事件, 合成

**答案**

```text
操作系统 → 浏览器进程（知道点击位置，但不知道页面内容）
        → 渲染进程的合成线程
            ├─ 命中测试：该位置是否在「非快速滚动区域」（有非 passive 的触摸 / 滚轮监听）？
            │   ├─ 否：合成线程直接处理滚动，不等主线程
            │   └─ 是：把事件交给主线程，等待 JS 执行后（可能 preventDefault）再滚动
            └─ 主线程：命中测试找到目标元素，分发事件（捕获 → 目标 → 冒泡）
```

**事件合并**：`mousemove`、`touchmove`、`pointermove`、`wheel` 等连续事件会被合并，对齐到下一帧的 rAF 之前派发，减少主线程负担。需要全部原始事件（例如绘图应用）时使用 `getCoalescedEvents()`。

**优化启示**：

- 滚动相关的监听使用 `{ passive: true }`
- 事件委托在 document 上且不是 passive 时，整个页面都会成为非快速滚动区域

**口述模板（30–60 秒）**

1. 一句话结论：输入事件先到合成线程，没有非 passive 监听的区域可以直接滚动，不等主线程。
2. 关键机制：非快速滚动区域需要等待主线程执行监听器，判断是否 preventDefault。
3. 对比或注意点：连续事件会被合并并对齐到帧。
4. 可追问时补充：在 document 上注册非 passive 的触摸监听，会让整个页面的滚动依赖主线程。

**常见追问**

- 为什么 Chrome 把 document 上的 touchstart 默认设为 passive？→ 大量网站在 document 上注册触摸监听但从不 preventDefault，导致滚动卡顿；默认 passive 修复了这个问题。

## 五、JS 引擎

### Q22. V8 是怎么执行 JS 的？

- **难度**: 中级
- **标签**: V8

**答案**

```text
源码
  ↓ 解析（Parser）：生成 AST；对暂时不调用的函数只做预解析（惰性解析）
  ↓
Ignition（解释器）：生成字节码并执行，同时收集类型反馈（feedback）
  ↓ 函数变热
Sparkplug（基线编译器）：把字节码快速编译为机器码，不做优化
  ↓ 更热
Maglev（中层优化编译器）：基于类型反馈快速生成优化代码
  ↓ 非常热
TurboFan / Turboshaft（顶层优化编译器）：生成高度优化的机器码
  ↑
去优化（Deopt）：类型假设不成立时，回退到字节码执行
```

**分层的意义**：编译越优化越慢；大部分代码只执行几次，用解释器启动快、内存少；热点代码再逐步优化，平衡启动速度和峰值性能。

**惰性解析**：页面中大量代码可能从不执行，预解析只检查语法和变量引用，真正调用时再完整解析。

**代码缓存**：V8 会缓存编译结果，二次访问时跳过解析和编译。

**口述模板（30–60 秒）**

1. 一句话结论：V8 先解析为 AST，用 Ignition 解释执行字节码，热点代码逐步交给 Sparkplug、Maglev、TurboFan 优化。
2. 关键机制：解释器收集类型反馈，优化编译器基于反馈做推测优化，假设失效时去优化。
3. 对比或注意点：分层编译平衡了启动速度和峰值性能。
4. 可追问时补充：V8 的顶层编译器正在从 TurboFan 的 Sea of Nodes 迁移到 Turboshaft。

**常见追问**

- 为什么需要解释器，不直接编译为机器码？→ 机器码占用内存大、编译耗时，而大部分代码只执行少量次数，直接编译不划算。

### Q23. 什么是隐藏类和内联缓存？

- **难度**: 中级
- **标签**: V8, 优化

**答案**

**隐藏类（Hidden Class / Shape / Map）**：

- JS 对象是动态的，如果每次访问属性都要查找哈希表，会很慢
- V8 为结构相同的对象分配相同的隐藏类，记录属性名和在内存中的偏移
- 添加属性时，隐藏类按**转换链**变化

```js
const a = { x: 1 }  // 隐藏类 C0 → C1(x)
a.y = 2             // C1 → C2(x, y)

const b = { y: 2 }
b.x = 1             // 与 a 的属性顺序不同，隐藏类不同
```

**内联缓存（Inline Cache）**：

- 在属性访问的位置缓存「隐藏类 → 偏移」
- 下次访问时，隐藏类相同就直接按偏移读取
- **单态**（一种隐藏类，最快）→ **多态**（2–4 种）→ **超态**（更多，退化为慢速查找）

**写出引擎友好的代码**：

- 在构造函数中一次性初始化所有属性，保持相同的顺序
- 避免 `delete` 属性（可能转为字典模式）
- 函数参数类型保持一致
- 数组元素类型保持一致（避免混合整数、浮点数和对象，避免空洞）

**口述模板（30–60 秒）**

1. 一句话结论：隐藏类描述对象的结构，内联缓存在访问位置缓存隐藏类和属性偏移。
2. 关键机制：结构相同的对象共享隐藏类，单态访问可以直接按偏移读取。
3. 对比或注意点：属性顺序不同、delete 属性都会导致隐藏类不同或退化。
4. 可追问时补充：保持对象结构和参数类型一致，让代码保持单态。

**常见追问**

- 实际业务中需要关注这些吗？→ 一般业务代码不需要刻意优化；在热点路径（大量循环、底层库）中才值得关注。

### Q24. V8 的垃圾回收是怎样的？

- **难度**: 中级
- **标签**: V8, GC

**答案**

**分代假说**：大部分对象很快就不再使用，少数对象会存活很久。

**新生代**（较小，几 MB 到几十 MB）：

- **Scavenge 算法**：分为两个半空间（From / To），存活对象复制到 To 空间，然后交换
- 存活两次的对象**晋升**到老生代
- 复制算法只处理存活对象，新生代存活率低，所以很快
- Chrome 使用**并行 Scavenge**（多线程同时复制）

**老生代**：

- **标记-清除**：标记可达对象，清除不可达对象
- **标记-整理**：移动存活对象，消除内存碎片
- **增量标记**：把标记拆分为多个小步骤，穿插在 JS 执行中
- **并发标记**：在后台线程中标记，主线程继续执行 JS
- **写屏障**：JS 修改对象引用时记录下来，保证并发标记的正确性

**目标**：减少「全停顿」（Stop-The-World）的时间，V8 的 GC 项目名为 **Orinoco**。

**口述模板（30–60 秒）**

1. 一句话结论：V8 使用分代回收，新生代用 Scavenge 复制算法，老生代用标记清除和标记整理。
2. 关键机制：存活多次的对象晋升到老生代；通过增量、并发、并行减少主线程停顿。
3. 对比或注意点：写屏障保证并发标记期间引用变化的正确性。
4. 可追问时补充：频繁创建大量临时对象会导致频繁的新生代 GC。

**常见追问**

- 为什么新生代用复制算法？→ 新生代对象存活率低，复制算法的成本与存活对象数量成正比，而且复制后没有碎片。

### Q25. 什么是去优化？怎么避免？

- **难度**: 中级
- **标签**: V8, 优化

**答案**

**原因**：优化编译器根据类型反馈做**推测性优化**，例如假设某个函数的参数总是整数，生成只处理整数的机器码。当实际执行违反假设时（传入了字符串），优化代码无法处理，必须**去优化**：丢弃优化代码，恢复到解释器的状态继续执行。

**常见的去优化原因**：

- 参数或变量的类型变化
- 对象的隐藏类变化（属性顺序不同、动态添加或删除属性）
- 数组元素类型变化（从整数数组变为包含浮点数或对象的数组）
- 访问越界的数组索引
- 使用 `arguments` 的某些方式

**影响**：频繁的去优化和重新优化（优化抖动）会严重影响性能。

**排查**：Node 中可以使用 `--trace-deopt` 查看去优化的原因。

**口述模板（30–60 秒）**

1. 一句话结论：去优化是推测性优化的假设失效后，回退到解释器执行。
2. 关键机制：优化编译器基于类型反馈做假设，假设不成立时必须丢弃优化代码。
3. 对比或注意点：常见原因是类型变化、对象结构变化和数组元素类型变化。
4. 可追问时补充：用 `--trace-deopt` 可以查看去优化的原因。

**常见追问**

- TypeScript 能帮助避免去优化吗？→ 间接帮助：类型约束让代码更倾向于类型稳定，但运行时引擎不使用 TS 的类型信息。

### Q26. XSS 怎么系统地防御？

- **难度**: 中级
- **标签**: 安全, XSS

**答案**

**1. 输出编码（按上下文）**

| 上下文 | 处理 |
|--------|------|
| HTML 内容 | 转义 `& < > " '` |
| HTML 属性 | 属性值加引号并转义 |
| URL | 校验协议（只允许 http / https），`encodeURIComponent` |
| JS 中 | 避免拼接；使用 JSON 序列化并转义 `<` |

**2. 避免危险的 API**：`innerHTML`、`outerHTML`、`document.write`、`eval`、`new Function`、`setTimeout(string)`；框架中的 `dangerouslySetInnerHTML`、`v-html`

**3. 必须插入 HTML 时**：使用 DOMPurify 净化；或使用 `setHTML()`（Sanitizer API，以浏览器支持为准）

**4. CSP**：限制脚本来源，禁止内联脚本（见 Q28）

**5. Trusted Types**：强制危险 API 只接受经过策略处理的类型，从源头杜绝 DOM 型 XSS（Chromium 支持）

```http
Content-Security-Policy: require-trusted-types-for 'script'
```

**6. 降低损失**：Cookie 设置 HttpOnly，敏感操作二次验证

**口述模板（30–60 秒）**

1. 一句话结论：XSS 防御的核心是按上下文编码输出，避免危险 API，并用 CSP 和 Trusted Types 作为纵深防御。
2. 关键机制：转义让数据不会被当作代码；CSP 限制脚本来源；Trusted Types 限制危险 API 的输入。
3. 对比或注意点：URL 要校验协议，防止 `javascript:` 伪协议。
4. 可追问时补充：HttpOnly 不能防止 XSS，但可以防止 Cookie 被窃取。

**常见追问**

- 富文本编辑器的内容怎么安全展示？→ 服务端和前端都使用白名单净化（DOMPurify），配合 CSP。

### Q27. CSRF 防御的细节有哪些？

- **难度**: 中级
- **标签**: 安全, CSRF

**答案**

**SameSite Cookie**：

- `Lax`（Chrome 默认）：跨站的顶级导航 GET 请求携带 Cookie，跨站 POST、iframe、fetch 不携带
- 局限：同站不同源的子域（例如被攻破的 `evil.example.com`）发起的请求被视为同站，仍会携带
- 局限：GET 请求有副作用时无法防御

**CSRF Token**：

- **同步器 Token**：服务端生成随机 Token 存在会话中，页面表单中包含，提交时校验
- **双重提交 Cookie**：Token 同时放在 Cookie 和请求头 / 参数中，服务端比较两者是否一致（攻击者无法读取 Cookie）
- Token 应该放在请求头（如 `X-CSRF-Token`）或请求体中，而不是 URL 中（会泄露到日志和 Referer）

**Origin / Referer 校验**：检查 `Origin` 头是否为允许的源；`Sec-Fetch-Site` 头（`same-origin`、`same-site`、`cross-site`）提供更明确的信息。

**推荐组合**：SameSite=Lax + 对状态修改请求校验 Origin 或 Token + GET 请求无副作用。

**口述模板（30–60 秒）**

1. 一句话结论：推荐组合是 SameSite Cookie、Token 或 Origin 校验，并保证 GET 无副作用。
2. 关键机制：攻击者能发送请求但读不到 Token；SameSite 让跨站请求不带 Cookie。
3. 对比或注意点：SameSite 无法防御来自同站子域的攻击。
4. 可追问时补充：Sec-Fetch-Site 头可以直接判断请求是否跨站。

**常见追问**

- 为什么 SameSite 不能完全替代 Token？→ 同站子域被攻破时仍可发起请求；部分旧浏览器不支持；GET 有副作用时也无法防御。

### Q28. CSP 是什么？怎么配置？

- **难度**: 中级
- **标签**: 安全, CSP

**答案**

**CSP（内容安全策略）**：通过响应头声明页面可以加载和执行哪些资源，即使存在注入点，恶意脚本也无法执行。

**严格 CSP（推荐）**：基于 nonce，而不是域名白名单（白名单容易被 JSONP、CDN 上的其他脚本绕过）：

```http
Content-Security-Policy:
  script-src 'nonce-{随机值}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self';
  report-to csp-endpoint
```

```html
<script nonce="{随机值}" src="/main.js"></script>
```

- `nonce`：每次响应生成新的随机值，只有带正确 nonce 的脚本才能执行
- `'strict-dynamic'`：被信任的脚本动态加载的脚本也被信任（便于使用打包器的动态 chunk）
- `object-src 'none'`、`base-uri 'none'`：防止插件和 base 标签劫持

**上线策略**：先使用 `Content-Security-Policy-Report-Only` 只报告不拦截，收集违规报告后再正式启用。

**口述模板（30–60 秒）**

1. 一句话结论：CSP 声明页面可以加载和执行哪些资源，是 XSS 的纵深防御。
2. 关键机制：推荐基于 nonce 和 strict-dynamic 的严格 CSP，而不是域名白名单。
3. 对比或注意点：域名白名单容易被同域的 JSONP 等绕过。
4. 可追问时补充：先用 Report-Only 模式收集违规报告，再正式启用。

**常见追问**

- 静态托管的页面（无法每次生成 nonce）怎么办？→ 使用基于 hash 的 CSP，为每个内联脚本计算 hash。

### Q29. 什么是点击劫持？怎么防御？

- **难度**: 中级
- **标签**: 安全

**答案**

**点击劫持**：攻击者把目标网站用透明 iframe 覆盖在诱导性的页面上，用户以为点击的是攻击者页面的按钮，实际点击的是目标网站的按钮（例如「确认转账」「关注」）。

**防御**：

```http
Content-Security-Policy: frame-ancestors 'self' https://trusted.example.com
X-Frame-Options: DENY            （旧标准，作为兼容）
```

- `frame-ancestors` 控制哪些页面可以嵌入当前页面，优先于 `X-Frame-Options`
- 敏感操作增加二次确认
- 旧的 JS 防御（`if (top !== self) top.location = self.location`）可以被绕过，不推荐单独使用

**口述模板（30–60 秒）**

1. 一句话结论：点击劫持是用透明 iframe 诱导用户点击目标网站的按钮。
2. 关键机制：通过 frame-ancestors 或 X-Frame-Options 禁止页面被不可信的站点嵌入。
3. 对比或注意点：JS 防嵌套的方法可以被 iframe sandbox 等方式绕过。
4. 可追问时补充：需要被嵌入的页面（如嵌入式组件）要精确配置允许的来源。

**常见追问**

- `X-Frame-Options` 和 `frame-ancestors` 同时设置时以谁为准？→ 支持 CSP 的浏览器以 frame-ancestors 为准。

### Q30. 第三方 Cookie 现在是什么情况？

- **难度**: 中级
- **标签**: 存储, 隐私

**答案**

**各浏览器的现状（截至 2026-10）**：

| 浏览器 | 第三方 Cookie |
|--------|--------------|
| Safari | ITP 默认阻止 |
| Firefox | Total Cookie Protection 默认按顶级站点分区 |
| Chrome | **默认仍允许**；2025 年宣布不再推出单独的选择弹窗，维持用户在设置中选择的现状；无痕模式默认阻止 |

**Privacy Sandbox**：2025-10 Google 宣布退役大部分 API（Topics、Protected Audience、Attribution Reporting、Shared Storage、Related Website Sets 等），继续支持 **CHIPS、FedCM、Storage Access API**、存储分区、UA Client Hints 等。

**仍然重要的机制**：

- **CHIPS**（`Set-Cookie: ...; Secure; SameSite=None; Partitioned`）：第三方 Cookie 按顶级站点分区存储，适用于嵌入式组件（客服、地图）
- **Storage Access API**：iframe 中请求访问非分区的 Cookie（Safari、Firefox 场景必需）
- **存储分区**：iframe 中的 localStorage、IndexedDB、HTTP 缓存按顶级站点分区

**对业务的影响**：依赖第三方 Cookie 的跨站登录、广告追踪、嵌入组件，需要在 Safari / Firefox 中适配。

**口述模板（30–60 秒）**

1. 一句话结论：Safari 和 Firefox 默认限制第三方 Cookie，Chrome 仍然默认允许。
2. 关键机制：Privacy Sandbox 的大部分 API 已退役，CHIPS、FedCM 和 Storage Access API 继续支持。
3. 对比或注意点：说「Chrome 已禁用第三方 Cookie」是错误的。
4. 可追问时补充：嵌入式组件推荐使用 CHIPS 分区 Cookie，以兼容所有浏览器。

**常见追问**

- 跨站单点登录怎么做？→ 基于顶级重定向的 OAuth / OIDC 流程，不依赖第三方 Cookie；FedCM 提供浏览器原生的联合登录。

### Q31. Service Worker 的生命周期是怎样的？

- **难度**: 中级
- **标签**: Service Worker

**答案**

```text
注册（navigator.serviceWorker.register）
  ↓
下载、解析
  ↓
install 事件：预缓存资源（event.waitUntil）
  ↓
waiting：如果有旧的 SW 控制着页面，新 SW 等待
  ↓（所有旧页面关闭，或调用 skipWaiting）
activate 事件：清理旧缓存（event.waitUntil）
  ↓
控制页面：拦截 fetch，处理 push、sync 等事件
  ↓
空闲时被终止，有事件时被重新启动
```

**更新检查**：导航时、调用 `registration.update()` 时，浏览器会检查 SW 脚本是否变化（字节对比），SW 脚本本身的 HTTP 缓存最多 24 小时。

**注意**：

- `skipWaiting` + `clients.claim()` 让新 SW 立即接管，但可能导致页面使用旧版资源和新版 SW 混用
- 首次注册的 SW 不会控制当前页面，需要刷新或 `clients.claim()`
- SW 会被随时终止，不能依赖全局变量保存状态

**口述模板（30–60 秒）**

1. 一句话结论：SW 经历注册、安装、等待、激活、控制页面的生命周期。
2. 关键机制：install 时预缓存，activate 时清理旧缓存；旧 SW 控制页面时新 SW 等待。
3. 对比或注意点：skipWaiting 立即接管可能导致新旧版本混用。
4. 可追问时补充：SW 空闲时会被终止，不能在全局变量中保存状态。

**常见追问**

- 怎么提示用户有新版本？→ 监听 registration 的 `updatefound` 和新 SW 进入 waiting 状态，提示用户刷新，用户确认后再 skipWaiting。

### Q32. 同源的多个标签页之间怎么通信？

- **难度**: 中级
- **标签**: 通信

**答案**

| 方式 | 特点 |
|------|------|
| **BroadcastChannel** | 同源的所有上下文（标签页、iframe、Worker）广播消息，最简单 |
| `storage` 事件 | 修改 localStorage 时，**其他**同源标签页收到事件；兼容性最好 |
| SharedWorker | 多个标签页连接同一个 Worker，可以维护共享状态 |
| Service Worker | 通过 `clients.matchAll()` 向所有页面发送消息 |
| IndexedDB + 轮询 | 不推荐 |
| `window.postMessage` | 需要持有目标窗口的引用（`window.open`、`opener`），也适用于跨源 |

```js
const channel = new BroadcastChannel('auth')
channel.postMessage({ type: 'logout' })
channel.onmessage = (event) => {
  if (event.data.type === 'logout') location.href = '/login'
}
```

**场景**：一个标签页退出登录，其他标签页同步退出；购物车数量同步。

手写见 [手写 H4](40-coding-handwritten.md)。

**口述模板（30–60 秒）**

1. 一句话结论：同源标签页通信首选 BroadcastChannel，兼容性要求高时用 storage 事件。
2. 关键机制：BroadcastChannel 向同源的所有上下文广播；storage 事件在其他标签页中触发。
3. 对比或注意点：storage 事件不会在修改它的标签页中触发。
4. 可追问时补充：需要共享状态时用 SharedWorker；跨源通信用 postMessage。

**常见追问**

- 怎么保证多个标签页中只有一个在执行任务（例如轮询）？→ 使用 Web Locks API（`navigator.locks.request`）选出一个领导者。
