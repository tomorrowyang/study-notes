# 浏览器原理系统设计题

> 回答结构：先澄清需求和约束 → 给出整体架构 → 讲清关键设计和浏览器机制的取舍 → 说明指标和验证方式 → 回答扩展追问。浏览器方向的系统设计重点考察能否把底层原理落到工程方案中。

### S1. 设计一个简化的浏览器渲染引擎

- **难度**: 高级
- **标签**: 渲染, 架构

**澄清问题（面试时先问）**

- 支持的范围：HTML 子集、CSS 子集（块布局、行内布局）、是否执行 JS？
- 输出目标：Canvas、终端、图片？
- 是否需要增量更新（DOM 变化后只重新渲染部分内容）？
- 是否要求多线程（合成线程）？

**参考方案**

```text
HTML 字符串 ──> Tokenizer ──> Tree Builder ──> DOM 树
CSS 字符串  ──> CSS Parser ──> 样式规则
                                  │
DOM + 规则 ──> 样式计算（选择器匹配、层叠、继承）──> 带样式的节点
                                  │
              布局（块布局：垂直排列；行内布局：断行）──> 布局树（盒子 + 位置尺寸）
                                  │
              绘制（按层叠顺序生成绘制指令列表）──> DisplayList
                                  │
              光栅化（执行指令，画到 Canvas）──> 屏幕
```

**关键设计**

- **模块分阶段**：每个阶段有明确的输入和输出（参考 BlinkNG），便于测试和增量更新
- **DOM**：节点类型（元素、文本），父子指针
- **样式**：选择器从右向左匹配；按最右边的选择器建立索引（id、class、tag 三个哈希表）
- **布局**：
  - 块布局：子元素宽度 = 父元素内容宽度 - 外边距；高度由内容累加
  - 行内布局：测量文本宽度，超出行宽时换行
  - 不处理浮动、定位等复杂情况，或者作为扩展
- **绘制**：先背景和边框，再内容；输出 `DrawRect`、`DrawText` 等指令
- **增量更新**：
  - 节点上有 dirty 标记：样式脏、布局脏、绘制脏
  - DOM 变化时标记节点和祖先，下一帧只处理脏节点
  - 修改颜色只需要重新绘制；修改宽度需要重新布局
- **帧调度**：DOM 修改只标记，在 rAF 时机统一执行流水线（批处理）

**关键指标**

- 每个阶段的耗时（样式、布局、绘制）
- 增量更新时实际处理的节点数量
- 渲染结果与真实浏览器的一致性（用截图对比测试）

**口述模板（2–3 分钟）**

1. **范围**：我先限定为 HTML 子集和块、行内布局，不执行 JS，输出到 Canvas。
2. **流水线**：解析 HTML 和 CSS → 样式计算 → 布局 → 生成绘制指令 → 光栅化，每个阶段的输入输出明确。
3. **样式**：选择器从右向左匹配，按最右边的选择器建立索引，减少需要检查的规则。
4. **布局**：块布局纵向排列，行内布局测量文本宽度并断行，生成带位置和尺寸的盒子树。
5. **绘制**：不直接画像素，而是生成指令列表，便于缓存和在其他线程光栅化。
6. **增量更新**：用脏标记区分样式脏、布局脏、绘制脏，DOM 修改只标记，帧时机统一处理。
7. **扩展**：再进一步可以加分层和合成，让滚动和 transform 动画不需要重新绘制。

**扩展追问**

- 怎么支持滚动？→ 把可滚动区域作为单独的层，滚动只改变偏移，用已光栅化的内容重新合成。
- 怎么支持 JS？→ 嵌入 JS 引擎（例如 QuickJS），暴露 DOM 绑定，JS 修改 DOM 后标记脏节点。
- 怎么测试？→ 参考 WPT 的方式：参考测试（两个页面渲染结果应该相同）。

### S2. 设计前端安全防护体系

- **难度**: 高级
- **标签**: 安全

**澄清问题（面试时先问）**

- 业务类型：电商、金融、内容平台、管理后台？敏感程度？
- 是否有用户生成内容（评论、富文本）？
- 是否需要被第三方嵌入，或嵌入第三方内容？
- 现有的认证方式：Cookie 会话还是 Token？
- 是否有合规要求（等保、PCI DSS）？

**参考方案**

```text
┌──────────────── 开发阶段 ────────────────┐
│ 安全编码规范、ESLint 安全规则、依赖漏洞扫描、代码审查 │
└──────────────────────────────────────────┘
┌──────────────── 传输层 ──────────────────┐
│ 全站 HTTPS + HSTS（preload），TLS 1.3        │
└──────────────────────────────────────────┘
┌──────────────── 响应头 ──────────────────┐
│ CSP（nonce + strict-dynamic）、Trusted Types   │
│ frame-ancestors、X-Content-Type-Options       │
│ Referrer-Policy、Permissions-Policy、COOP      │
└──────────────────────────────────────────┘
┌──────────────── 应用层 ──────────────────┐
│ XSS：框架默认转义、富文本 DOMPurify、URL 协议校验 │
│ CSRF：SameSite + Token / Origin 校验           │
│ 认证：HttpOnly + Secure Cookie、短期 Token      │
│ 第三方：SRI、沙箱 iframe、最小权限             │
└──────────────────────────────────────────┘
┌──────────────── 监控与响应 ───────────────┐
│ CSP 违规报告、异常请求监控、漏洞响应流程         │
└──────────────────────────────────────────┘
```

**关键设计**

- **XSS 纵深防御**：
  - 第一层：框架默认转义，禁止 `dangerouslySetInnerHTML` / `v-html`（ESLint 规则），例外需要审批
  - 第二层：富文本统一经过 DOMPurify 等净化组件
  - 第三层：严格 CSP，即使有注入也无法执行
  - 第四层：Trusted Types，从 API 层面阻止 DOM XSS
- **CSP 上线**：先 Report-Only 收集违规，分析后修复，再正式启用；违规报告接入监控
- **认证凭证**：会话 Cookie 使用 `HttpOnly; Secure; SameSite=Lax`；不在 localStorage 中存放长期 Token
- **第三方脚本**：使用 SRI（`integrity` 属性）校验 CDN 资源；能自托管的自托管；不可信的内容放入 sandbox iframe
- **供应链**：锁定依赖版本，`npm audit` / SCA 扫描，CI 中阻断高危漏洞
- **敏感操作**：二次验证、操作日志

**关键指标**

- CSP 违规数量和趋势
- 依赖中高危漏洞数量和修复时长
- 安全扫描和渗透测试发现的问题数量
- 安全响应头覆盖率

**口述模板（2–3 分钟）**

1. **澄清**：先了解业务敏感度、是否有用户生成内容、认证方式。
2. **分层**：我把安全体系分为开发阶段、传输层、响应头、应用层、监控响应五层。
3. **XSS**：框架转义、富文本净化、严格 CSP、Trusted Types 四层防御，任何一层被绕过还有下一层。
4. **CSRF**：SameSite=Lax 作为基础，状态修改请求再校验 Origin 或 Token。
5. **凭证**：HttpOnly Cookie，避免在 localStorage 中保存长期 Token。
6. **第三方和供应链**：SRI、沙箱 iframe、依赖扫描。
7. **上线和运营**：CSP 先 Report-Only，违规报告接入监控，建立漏洞响应流程。

**扩展追问**

- Token 放在 localStorage 还是 Cookie？→ Cookie（HttpOnly）可以防止被 XSS 读取，但需要防 CSRF；localStorage 无 CSRF 风险，但 XSS 可以直接读取。推荐 HttpOnly Cookie + CSRF 防护。
- 怎么推动团队落地？→ 把规则做进工具链（ESLint、CI、模板项目），而不是只靠文档。

### S3. 设计跨域与单点登录架构

- **难度**: 高级
- **标签**: 跨域, 认证

**澄清问题（面试时先问）**

- 系统之间是同站（`*.example.com`）还是跨站（不同的顶级域名）？
- 有哪些客户端：Web、App、小程序？
- 是否需要接入第三方身份提供商（企业微信、钉钉、OIDC）？
- 前后端是否分离部署？API 是否与页面同源？

**参考方案**

```text
                    ┌──────────────────┐
                    │  认证中心（IdP）    │
                    │  sso.example.com   │
                    │  会话 Cookie       │
                    └──────────────────┘
                     ↑ ① 重定向登录    │ ② 带授权码重定向回来
                     │                ↓
┌───────────────────────┐   ③ 授权码换 Token（服务端）
│ 业务系统 A（a.com）      │ ─────────────────────> IdP
│ BFF 设置本站会话 Cookie  │
└───────────────────────┘
┌───────────────────────┐
│ 业务系统 B（b.com）      │ ① 重定向到 IdP：IdP 已有会话，直接返回授权码，无需再次登录
└───────────────────────┘
```

**关键设计**

- **同站系统**：可以使用 `Domain=.example.com` 的 Cookie 共享会话（简单，但所有子域共享，一个子域被攻破影响全部）
- **跨站系统**：**基于顶级重定向的 OAuth 2.0 / OIDC 授权码流程（+ PKCE）**：
  - 不依赖第三方 Cookie（IdP 的 Cookie 在顶级导航中是第一方 Cookie）
  - 授权码在服务端（BFF）换取 Token，Token 不暴露给浏览器
  - 业务系统设置自己的 HttpOnly 会话 Cookie
- **不推荐的方案**：iframe 中读取 IdP 的 Cookie（第三方 Cookie 在 Safari、Firefox 中被阻止）
- **API 跨域**：
  - 推荐 BFF / 网关同源代理，从根本上避免跨域
  - 必须跨域时使用 CORS 白名单 + 凭证（`SameSite=None; Secure`）
- **单点登出**：IdP 通知所有业务系统（后端通道登出）；前端用 BroadcastChannel 同步同源标签页
- **FedCM**：浏览器原生的联合登录 API，可以作为增强

**关键指标**

- 登录成功率、登录耗时
- 跨系统跳转免登录成功率
- Token 刷新失败率

**口述模板（2–3 分钟）**

1. **澄清**：先确认系统是同站还是跨站，这决定了能否共享 Cookie。
2. **同站**：可以共享父域 Cookie，但安全边界变大。
3. **跨站**：使用 OIDC 授权码流程，所有跳转都是顶级导航，不依赖第三方 Cookie。
4. **Token 安全**：授权码在 BFF 换取 Token，浏览器只持有本站的 HttpOnly 会话 Cookie。
5. **API 跨域**：优先用 BFF 同源代理，必须跨域时配置 CORS 白名单。
6. **登出**：IdP 后端通道通知各系统，同源标签页用 BroadcastChannel 同步。

**扩展追问**

- 静默续期怎么做？→ 以前用隐藏 iframe 访问 IdP（依赖第三方 Cookie，已不可靠）；现在用 Refresh Token（服务端保存）或顶级重定向。
- 为什么需要 PKCE？→ 防止授权码被截获后被他人兑换，对公开客户端（SPA、App）是必需的。

### S4. 设计离线可用和多标签页同步的应用

- **难度**: 高级
- **标签**: PWA, 存储, 通信

**澄清问题（面试时先问）**

- 离线时需要哪些功能：只读浏览，还是可以编辑？
- 数据量多大？是否有多设备同步？
- 冲突如何处理：最后写入优先，还是需要合并？
- 目标浏览器：是否需要支持 Safari？

**参考方案**

```text
┌──────────────── 页面（多个标签页） ────────────────┐
│ UI ←→ 本地数据层（IndexedDB 封装）                    │
│        ↕ BroadcastChannel：数据变化通知其他标签页      │
│ 写操作 → 本地写入 + 加入待同步队列（outbox）            │
└───────────────────────────────────────────────────┘
          ↓ fetch
┌──────────────── Service Worker ──────────────────┐
│ 静态资源：预缓存（App Shell）                        │
│ API：网络优先 / SWR                                 │
│ Background Sync：网络恢复后发送待同步队列（Chromium） │
└───────────────────────────────────────────────────┘
          ↓
┌──────────────── 服务端 ──────────────────────────┐
│ 增量同步接口（基于版本号 / 时间戳）、冲突检测          │
└───────────────────────────────────────────────────┘
```

**关键设计**

- **App Shell**：Service Worker 预缓存页面框架和静态资源，离线也能打开
- **本地数据**：IndexedDB 作为主数据源（本地优先），UI 读取本地数据，同步在后台进行
- **待同步队列**：离线时写操作存入 outbox 表；网络恢复后按顺序发送，携带幂等 ID 防止重复提交
- **同步触发**：Background Sync（仅 Chromium）；其他浏览器在 `online` 事件、页面可见、定时器时触发
- **多标签页**：
  - 数据变化通过 BroadcastChannel 通知其他标签页刷新
  - 同步任务用 **Web Locks API** 保证只有一个标签页执行
- **冲突处理**：
  - 简单：最后写入优先（基于服务端时间戳）
  - 字段级合并：不同字段的修改可以合并
  - 复杂协作：CRDT（例如 Yjs）
- **存储配额**：`navigator.storage.estimate()` 查看配额；`navigator.storage.persist()` 申请持久化；Safari 可能清除 7 天未使用的站点数据

**关键指标**

- 离线可用率、同步成功率、同步延迟
- 冲突发生率
- 存储使用量

**口述模板（2–3 分钟）**

1. **澄清**：先确认离线是只读还是可以编辑，冲突怎么处理。
2. **资源离线**：Service Worker 预缓存 App Shell。
3. **数据离线**：IndexedDB 作为本地主数据源，UI 读本地，后台同步。
4. **写操作**：离线时写入待同步队列，带幂等 ID，网络恢复后发送。
5. **多标签页**：BroadcastChannel 通知数据变化，Web Locks 保证同步任务只在一个标签页执行。
6. **冲突**：按场景选择最后写入优先、字段合并或 CRDT。
7. **兼容**：Background Sync 只在 Chromium 中可用，其他浏览器用 online 事件兜底；注意 Safari 的存储清除策略。

**扩展追问**

- IndexedDB 的 API 太难用怎么办？→ 使用 idb、Dexie 等封装库。
- Schema 变化怎么处理？→ IndexedDB 的版本号和 `onupgradeneeded` 中做迁移。

### S5. 设计白屏和崩溃监控系统

- **难度**: 高级
- **标签**: 稳定性, 监控

**澄清问题（面试时先问）**

- 应用类型：SPA、SSR、H5 嵌入 App？
- 需要监控哪些问题：JS 错误、资源加载失败、白屏、页面崩溃、卡死？
- 数据量和采样要求？
- 是否需要回放用户操作？

**参考方案**

```text
页面 SDK
  ├─ JS 错误：window.onerror、unhandledrejection、框架错误边界
  ├─ 资源错误：捕获阶段监听 error 事件
  ├─ 白屏检测：加载后检测关键容器 / 采样点
  ├─ 卡死检测：Long Animation Frames，长时间无响应
  └─ 心跳 ──> Service Worker（崩溃检测）
                 ↓
            上报（sendBeacon）──> 采集服务 ──> 存储 ──> 聚合分析、告警
                                                 ↑
                                         Source Map 还原堆栈
浏览器原生：Reporting API（crash、deprecation、CSP 违规）
```

**关键设计**

- **白屏检测**：
  - 方案一：页面加载完成后（例如 load 后若干秒），在页面的多个采样点用 `document.elementsFromPoint` 检查，如果都是容器元素（html、body、#app），判断为白屏
  - 方案二：检查根节点是否有子元素，或关键元素是否出现（MutationObserver）
  - 方案三：截图像素分析（成本高，用于抽样）
  - 白屏时附带上下文：路由、错误日志、资源加载情况
- **崩溃检测**（页面 JS 已无法执行）：
  - Reporting API 的 `crash` 报告（Chromium）
  - Service Worker 心跳：页面每隔几秒发送心跳；pagehide 时发送正常关闭消息；SW 发现心跳中断且没有关闭消息 → 判断为崩溃
- **错误聚合**：按错误类型 + 消息 + 规范化的堆栈生成指纹；Source Map 只放在内部服务器，不公开
- **噪声过滤**：浏览器扩展错误、跨域脚本的 `Script error.`（加 `crossorigin` 获取详情）、爬虫
- **上报**：sendBeacon / `fetch keepalive`；批量、采样、失败重试

**关键指标**

- JS 错误率（按会话或 PV）、白屏率、崩溃率
- 资源加载失败率
- 告警准确率（误报率）

**口述模板（2–3 分钟）**

1. **澄清**：确认应用类型和要监控的问题范围。
2. **采集**：JS 错误、资源错误、白屏、卡死、崩溃，分别使用不同的检测机制。
3. **白屏**：加载后在多个采样点检查是否只有容器元素，附带路由和错误上下文。
4. **崩溃**：页面 JS 已经无法执行，所以依赖 Reporting API 或 Service Worker 心跳检测。
5. **处理**：按指纹聚合，Source Map 在服务端还原，过滤扩展和爬虫噪声。
6. **告警**：按错误率和影响用户数告警，关联发版记录快速定位。

**扩展追问**

- 怎么快速定位是哪次发版引入的？→ 上报中带版本号，错误率按版本分组对比，与灰度发布结合。
- 用户行为回放怎么做？→ rrweb 记录 DOM 快照和增量变化，注意脱敏和数据量。

### S6. 设计安全的第三方 iframe 嵌入与通信方案

- **难度**: 高级
- **标签**: 安全, iframe, 通信

**澄清问题（面试时先问）**

- 方向：我们嵌入第三方，还是我们的组件被第三方嵌入？
- 被嵌入的内容是否需要登录态？
- 需要哪些交互：调整高度、传递数据、调用父页面能力？
- 是否需要支持 Safari（第三方 Cookie 限制）？

**参考方案**

```text
宿主页面（host.com）
  <iframe
    src="https://widget.com/embed"
    sandbox="allow-scripts allow-forms allow-popups"
    allow="clipboard-write"
    referrerpolicy="strict-origin-when-cross-origin"
    loading="lazy">
      │
      │ postMessage（指定 targetOrigin，校验 event.origin）
      │ 消息协议：{ type, id, payload }，请求-响应模式
      ↓
组件页面（widget.com）
  响应头：Content-Security-Policy: frame-ancestors https://host.com
  Cookie：Partitioned（CHIPS）或 Storage Access API
```

**关键设计**

- **嵌入第三方（我们是宿主）**：
  - `sandbox` 只授予必要的权限；**不要同时给 `allow-scripts` 和 `allow-same-origin` 给同源内容**（可以移除 sandbox）
  - `allow` 属性（Permissions Policy）控制摄像头、地理位置等能力
  - 跨站 iframe 运行在独立进程（站点隔离），安全性有保障
- **被嵌入（我们是组件）**：
  - `frame-ancestors` 白名单，防止点击劫持
  - 登录态：第三方 Cookie 在 Safari、Firefox 中受限 → 使用 CHIPS 分区 Cookie，或通过 Storage Access API 请求访问，或用 postMessage 传递短期 Token
- **通信协议**：
  - 发送时指定 `targetOrigin`，**不使用 `*`**（否则 iframe 被导航到其他站点后消息会泄露）
  - 接收时校验 `event.origin` 和 `event.source`
  - 消息带类型和 ID，实现请求-响应和超时
  - 使用 `MessageChannel` 建立专用通道，避免与其他消息混淆
- **高度自适应**：组件内用 ResizeObserver 监听高度变化，postMessage 通知宿主调整 iframe 高度
- **性能**：`loading="lazy"`；跨站 iframe 有进程开销，控制数量

**关键指标**

- 嵌入加载成功率和耗时
- 消息通信失败率和超时率
- 安全事件（异常来源的消息被拒绝的次数）

**口述模板（2–3 分钟）**

1. **澄清**：确认我们是宿主还是组件、是否需要登录态。
2. **隔离**：宿主用 sandbox 和 allow 属性最小授权；跨站 iframe 本身运行在独立进程。
3. **防嵌入**：组件用 frame-ancestors 白名单防止点击劫持。
4. **通信**：postMessage 指定 targetOrigin，接收时校验 origin 和 source，消息带类型和 ID 实现请求-响应。
5. **登录态**：第三方 Cookie 受限，使用 CHIPS、Storage Access API 或传递短期 Token。
6. **体验**：ResizeObserver 自适应高度，懒加载 iframe。

**扩展追问**

- 为什么 `allow-scripts` 和 `allow-same-origin` 不能同时给同源内容？→ iframe 中的脚本可以访问父页面并移除自身的 sandbox 属性，沙箱失效。
- 怎么防止恶意页面伪造消息？→ 校验 event.origin 是否在白名单中，消息中再带签名或一次性 nonce。

### S7. 高频渲染场景的技术选型

- **难度**: 高级
- **标签**: 渲染, Canvas, WebGL

**澄清问题（面试时先问）**

- 场景：数据可视化（几十万个点）、在线文档 / 表格、白板、游戏、地图？
- 元素数量和更新频率？
- 是否需要文本编辑、无障碍、选择复制、SEO？
- 目标设备：是否包括低端手机？

**参考方案**

| 方案 | 适合的元素规模 | 优点 | 缺点 |
|------|----------------|------|------|
| DOM / SVG | 数千 | 事件、无障碍、样式、文本选择都是原生的 | 元素多时样式、布局、绘制成本高 |
| Canvas 2D | 数万 | 立即模式，无 DOM 开销 | 需要自己实现命中测试、文本编辑、无障碍 |
| WebGL | 数十万到百万 | GPU 并行绘制 | 开发复杂，文本渲染麻烦 |
| WebGPU | 百万级 + 计算 | 计算着色器、更低开销 | 支持度仍在提升 |
| OffscreenCanvas + Worker | 与上面组合 | 渲染移出主线程 | 与 DOM 交互需要通信 |

**关键设计**

- **混合方案**：主体内容使用 Canvas / WebGL，交互控件（输入框、菜单、提示框）使用 DOM 覆盖层
- **Canvas 优化**：
  - 分层 Canvas：静态背景和动态内容分开，减少重绘
  - 脏矩形：只重绘变化的区域
  - 离屏缓存：复杂但不变的图形预先绘制到离屏 Canvas
  - 适配 DPR：`canvas.width = cssWidth * devicePixelRatio`，否则在高清屏上模糊
- **命中测试**：空间索引（四叉树、R 树）快速找到点击位置的元素
- **主线程**：OffscreenCanvas 在 Worker 中渲染；数据处理在 Worker 中进行
- **无障碍**：为 Canvas 内容维护一份隐藏的 DOM 或 ARIA 描述
- **帧调度**：所有更新合并到 rAF 中统一处理

**关键指标**

- FPS 和长帧比例
- 交互延迟（INP）
- 内存和 GPU 内存占用
- 低端设备上的表现

**口述模板（2–3 分钟）**

1. **澄清**：先了解元素规模、更新频率，以及是否需要文本编辑和无障碍。
2. **选型原则**：几千个元素用 DOM / SVG；数万用 Canvas；数十万以上用 WebGL / WebGPU。
3. **混合方案**：主体用 Canvas，交互控件用 DOM 覆盖层，兼顾性能和原生能力。
4. **Canvas 优化**：分层、脏矩形、离屏缓存、适配 DPR。
5. **交互**：空间索引实现命中测试。
6. **线程**：OffscreenCanvas 和数据处理放到 Worker。
7. **验证**：在低端设备上测试 FPS 和交互延迟。

**扩展追问**

- 在线表格为什么多数用 Canvas？→ 单元格数量巨大，DOM 方案即使虚拟化，滚动时的样式和布局成本也高；Canvas 只绘制可见区域，性能可控。
- Canvas 中的文本输入怎么实现？→ 编辑时在单元格位置覆盖一个真实的 input / contenteditable。

### S8. 设计浏览器兼容性治理方案

- **难度**: 中级
- **标签**: 兼容性, 工程

**澄清问题（面试时先问）**

- 用户的浏览器分布：桌面 / 移动、是否有大量旧版 Android WebView、国产浏览器？
- 业务对旧浏览器的要求：完整功能、核心功能可用，还是只显示升级提示？
- 团队规模和技术栈？

**参考方案**

```text
1. 数据：埋点统计浏览器和版本分布 ──> 确定支持范围（Browserslist）
2. 构建：
   - 语法：Babel / SWC 按 Browserslist 转译
   - API：core-js 按需 polyfill（usage 模式）
   - CSS：PostCSS + Autoprefixer
   - 可选：现代 / 传统双包（module / nomodule）
3. 编码：
   - ESLint 插件检查不兼容的 API（eslint-plugin-compat）
   - 特性检测 + 渐进增强
   - 使用 Baseline 判断新特性能否使用
4. 测试：真机 / 云测试平台覆盖主要浏览器；视觉回归测试
5. 线上：错误按浏览器版本聚合；不支持的浏览器显示降级页面
```

**关键设计**

- **支持范围基于数据**：例如覆盖 99% 的用户，长尾浏览器显示升级提示
- **语法 vs API**：转译只解决语法问题（箭头函数、可选链），API 缺失需要 polyfill（`Promise.withResolvers`、`structuredClone`）
- **双包策略**：现代浏览器加载体积更小的现代包，旧浏览器加载转译后的传统包
- **CSS**：`@supports` 做渐进增强；新的布局特性（容器查询、`:has()`）需要回退方案
- **WebView**：Android 旧版 WebView 和 iOS 版本是主要的兼容性风险
- **治理机制**：
  - 新特性使用前查看 Baseline 状态
  - 兼容性问题沉淀为知识库和 lint 规则
  - 定期根据数据调整支持范围，淘汰旧浏览器

**关键指标**

- 按浏览器版本统计的错误率
- 兼容性问题导致的客诉数量
- polyfill 带来的包体积

**口述模板（2–3 分钟）**

1. **数据**：先用埋点统计浏览器分布，确定支持范围。
2. **构建**：按 Browserslist 转译语法、按需 polyfill、CSS 加前缀；可以使用现代 / 传统双包。
3. **编码**：lint 规则检查不兼容的 API，特性检测和渐进增强。
4. **测试**：云测试平台覆盖主要浏览器和 WebView。
5. **线上**：错误按浏览器版本聚合，不支持的浏览器显示降级页面。
6. **持续治理**：用 Baseline 判断新特性能否使用，定期根据数据调整支持范围。

**扩展追问**

- polyfill 让包体积变大怎么办？→ 按需引入（usage 模式）；双包策略；或者使用 polyfill 服务按 UA 返回（注意第三方服务的安全风险，例如 polyfill.io 事件）。
- 国产浏览器有什么特点？→ 多为 Chromium 内核但版本可能较旧，部分有极速 / 兼容双模式，需要通过 `<meta name="renderer" content="webkit">` 指定极速模式。
