### S1. 设计一个高并发电商网站（商品详情、列表、购物车）

- **难度**: 高级
- **标签**: 电商, 缓存, 性能

**澄清问题（面试时先问）**

- 流量规模？有没有大促（流量突增 10 倍以上）？
- 商品数量？价格和库存的更新频率？
- 是否有个性化（会员价、推荐）？
- 部署平台：Vercel 还是自托管？多区域？
- SEO 的重要程度？

**参考方案**

```text
用户 → CDN（静态资源、静态外壳缓存）
     → Next.js 集群（多实例，共享 Redis 缓存）
          ├─ 服务端组件 / 数据访问层
          │    ├─ 商品服务（缓存，按标签失效）
          │    ├─ 库存服务（实时，流式）
          │    ├─ 价格服务（短缓存）
          │    └─ 用户服务（个性化，流式）
          └─ Server Actions（加购、下单）→ 订单服务
     ← 商品后台修改 → 消息队列 → 失效服务 → revalidateTag
```

**关键设计**

| 页面 / 部分 | 策略 |
|-------------|------|
| 首页、分类页 | 静态外壳 + 缓存的商品列表（`cacheLife('minutes')`）；个性化推荐流式 |
| 商品详情 | `generateStaticParams` 预渲染热门商品；商品信息 `'use cache: remote'` + `cacheTag('product-id')` |
| 库存、会员价 | Suspense 流式，请求时获取 |
| 购物车 | 客户端组件 + Server Actions，乐观更新；头部的购物车数量用 `'use cache: private'` 或流式 |
| 搜索 | URL 状态，服务端渲染结果，搜索服务独立 |
| 下单 | Server Action：鉴权 → 校验 → 价格和库存以服务端为准 → 幂等键防止重复提交 |

**大促**：

- 预热：提前访问热门商品页填充缓存
- 降级：推荐等非关键服务关闭或返回默认内容
- 库存：显示「有货 / 紧张」而不是精确数字，减少实时查询
- 限流：下单接口限流 + 排队

**关键指标**

- LCP < 2.5s、INP < 200ms、TTFB（外壳）< 200ms
- 缓存命中率、回源 QPS
- 下单成功率、Action 错误率

**口述模板（2–3 分钟）**

先确认流量规模、个性化程度和部署方式。整体是 CDN 加多实例的 Next.js 集群，使用 Redis 作为共享缓存。

渲染策略按数据特性划分：商品信息变化不频繁，用 use cache 加商品标签，后台修改时通过消息队列触发失效；库存和会员价实时性强，放在 Suspense 中流式渲染；购物车是客户端组件，配合 Server Actions 和乐观更新。热门商品在构建时预渲染，其余按需生成。

下单在 Server Action 中，价格和库存以服务端为准，使用幂等键防止重复提交。大促时提前预热缓存，非关键服务降级，下单接口限流。

监控方面关注核心网页指标、缓存命中率和下单成功率。

**扩展追问**

- 商品价格修改后多久生效？→ 管理后台修改走 Server Action 用 `updateTag` 立即生效；批量导入走消息队列 + `revalidateTag`，秒级生效。
- 多区域部署怎么保证缓存一致？→ 每个区域独立的缓存 + 失效事件广播到所有区域；或者全局的 KV 存储。

### S2. 设计一个多租户 SaaS 平台

- **难度**: 高级
- **标签**: 多租户, 架构

**澄清问题（面试时先问）**

- 租户通过子域名（`acme.app.com`）还是自定义域名（`app.acme.com`）访问？
- 租户之间的数据隔离要求（共享数据库 / 独立数据库）？
- 租户是否可以自定义主题、功能开关？
- 租户数量和最大租户的规模？

**参考方案**

```text
请求 acme.app.com/dashboard
  → proxy：解析 Host → 查询租户（缓存）→ 重写到 /[tenant]/dashboard
  → app/[tenant]/layout.tsx：加载租户配置（主题、功能开关）
  → 数据访问层：所有查询自动带上 tenantId
```

**关键设计**

- **路由**：`app/[tenant]/...`，proxy 中把域名重写为路径参数（用户看到的 URL 不变）
- **租户解析**：域名 → 租户 ID 的映射存在 Redis / Edge Config 中，proxy 中读取，避免每个请求查数据库
- **数据隔离**：
  - 数据访问层从会话中取 `tenantId`，**不信任** URL 中的租户参数做授权（用户可能访问其他租户的域名）
  - 校验「当前用户属于该租户」
  - 数据库层面：行级安全（PostgreSQL RLS）作为第二道防线
- **缓存**：缓存键和标签都包含租户 ID（`tenant-acme:products`）；`'use cache'` 函数的参数包含 tenantId
- **主题**：租户配置中的颜色转为 CSS 变量，在根布局中注入
- **自定义域名**：平台 API 添加域名和证书；proxy 中支持任意 Host
- **功能开关**：租户配置 + 套餐，服务端判断，客户端只接收结果

**关键指标**

- 租户解析延迟、按租户的错误率和响应时间
- 跨租户访问的告警（应该为 0）

**口述模板（2–3 分钟）**

先确认访问方式和数据隔离要求。路由上使用 [tenant] 动态段，proxy 根据 Host 查找租户并重写到对应路径，映射关系缓存在 Redis 或边缘配置中。

最重要的是数据隔离：数据访问层从会话中获取租户 ID，校验用户属于该租户，所有查询都带上租户条件，数据库开启行级安全作为第二道防线。URL 中的租户只用于路由，不用于授权。

缓存的键和标签都要包含租户 ID，避免串数据。主题通过 CSS 变量注入，功能开关在服务端判断。

监控按租户统计，跨租户访问必须告警。

**扩展追问**

- 大租户需要独立部署怎么办？→ 支持把特定租户的域名路由到独立的部署（独立数据库 + 独立实例），代码相同，配置不同。

### S3. 设计一个内容平台（博客 / 文档站），支持百万级页面

- **难度**: 高级
- **标签**: 内容站, SEO, 缓存

**澄清问题（面试时先问）**

- 内容来源：CMS、Markdown 文件还是数据库？
- 更新频率？发布后多久可见？
- 是否需要多语言、搜索、评论？
- 是否有付费内容？

**参考方案**

```text
CMS → Webhook（签名）→ Route Handler → revalidateTag
构建：只预渲染热门的 1 万篇 → 其余首次访问时生成并缓存
页面：文章内容（use cache + 标签）+ 评论（流式）+ 阅读量（after 中记录）
CDN：缓存 HTML，s-maxage + stale-while-revalidate
```

**关键设计**

- **构建时间**：百万页面不能全部在构建时生成，只预渲染热门页面，其余按需生成
- **Markdown 渲染**在服务端组件中完成（解析库不进入客户端包）
- **SEO**：`generateMetadata`、`sitemap.ts`（超过 5 万条时用 `generateSitemaps` 拆分）、结构化数据（JSON-LD）、`hreflang`
- **付费内容**：内容主体放在 Suspense 中，根据会员状态决定渲染全文还是摘要；**付费内容不能进入共享缓存**的完整版本
- **搜索**：独立的搜索服务（Algolia、Meilisearch），发布时同步索引
- **阅读量**：`after()` 中异步记录，不影响响应
- **图片**：CDN 图片服务，`next/image` 自定义 loader

**关键指标**

- 构建时间、按需生成的首次访问延迟
- 发布到可见的延迟
- 搜索引擎收录量、核心网页指标

**口述模板（2–3 分钟）**

内容站的核心是静态化和缓存。百万页面不能在构建时全部生成，只预渲染热门页面，其余首次访问时生成并缓存。文章内容使用 use cache 加标签，CMS 发布时通过签名验证的 Webhook 按标签失效。

Markdown 在服务端组件中渲染，解析库不进入客户端。SEO 方面使用 generateMetadata、拆分的 sitemap 和结构化数据。

付费内容要特别注意：完整版本不能进入共享缓存，根据会员状态在请求时决定渲染全文或摘要。

阅读量在 after 中异步记录，搜索使用独立的搜索服务。

**扩展追问**

- 撤稿需要立即生效怎么办？→ 失效标签的同时调用 CDN 清除 API；页面中检查文章状态，已撤稿返回 404 或 410。

### S4. 设计一个 AI 聊天应用（流式输出）

- **难度**: 高级
- **标签**: AI, 流式, Route Handler

**澄清问题（面试时先问）**

- 单轮还是多轮对话？是否需要保存历史？
- 是否需要工具调用、文件上传、生成式 UI？
- 计费方式（按 token）？限流要求？
- 模型提供商是否需要切换？

**参考方案**

```text
客户端（useChat 等）
  → POST /api/chat（Route Handler，流式响应）
       ├─ 鉴权 + 限流 + 额度检查
       ├─ 加载会话历史（截断到上下文窗口内）
       ├─ 调用模型（流式），工具调用在服务端执行
       ├─ 边接收边转发给客户端（SSE / 流式文本）
       └─ 结束后（after）：保存消息、记录 token 用量
  会话列表：服务端组件渲染
```

**关键设计**

- **为什么用 Route Handler 而不是 Server Action**：需要流式响应、可能被并发调用；Server Actions 是串行的
- **流式**：`ReadableStream` 返回，反向代理关闭缓冲；客户端增量渲染 Markdown
- **中断**：客户端 `AbortController`；服务端监听 `request.signal`，中止对模型的调用（节省成本）
- **安全**：
  - API 密钥只在服务端
  - 提示词注入：系统提示和用户输入分离；工具调用需要权限检查和确认（尤其是有副作用的工具）
  - 模型输出渲染为 Markdown 时要清洗，防止 XSS
- **成本控制**：按用户限流（H11）、额度检查、上下文截断或摘要
- **持久化**：流结束后在 `after()` 中保存；流中断时保存已生成的部分
- **模型切换**：统一的抽象层（例如 AI SDK）

**关键指标**

- 首个 token 的延迟（TTFT）、每秒 token 数
- 每个用户的 token 用量、成本
- 错误率、中断率

**口述模板（2–3 分钟）**

聊天接口用 Route Handler 实现，因为需要流式响应和并发，Server Actions 是串行的。请求进来先鉴权、限流和检查额度，然后加载截断后的会话历史，调用模型并把流式结果直接转发给客户端。

客户端可以中断，服务端监听 request.signal 同时中止模型调用以节省成本。流结束后在 after 中保存消息和记录 token 用量。

安全方面，密钥只在服务端，模型输出渲染前要清洗，有副作用的工具调用需要权限检查和用户确认，防止提示词注入导致越权操作。

部署时反向代理要关闭缓冲，监控首个 token 延迟和成本。

**扩展追问**

- 用户刷新页面时，正在生成的回答怎么办？→ 服务端继续生成并保存（不依赖客户端连接），客户端重新加载后从数据库读取；或者支持断点续传（可恢复的流）。

### S5. 设计一个大型后台管理系统（基于 App Router）

- **难度**: 中级
- **标签**: 后台, 权限

**澄清问题（面试时先问）**

- 用户规模？是否需要 SEO？（通常不需要）
- 权限模型：角色、菜单、按钮、数据权限？
- 是否有多个团队开发不同模块？
- 数据量：表格是否需要服务端分页、导出？

**参考方案**

```text
app/
  (auth)/login
  (admin)/layout.tsx       ← 侧边栏、顶栏（根据权限生成菜单）
  (admin)/users/page.tsx   ← 列表：searchParams 驱动的服务端分页
  (admin)/users/[id]/@modal ← 拦截路由实现详情弹窗
features/<domain>/        ← actions、queries、components
lib/permissions.ts        ← 权限检查
```

**关键设计**

- **是否用 Next.js**：后台不需要 SEO，Vite + React 也是好选择；用 Next.js 的收益在于全栈（Server Actions 直接访问后端）、服务端分页、统一的鉴权
- **权限**：
  - 菜单：服务端根据权限生成，只渲染有权限的项
  - 页面：数据访问层检查，无权限返回 403 页面
  - 按钮：服务端组件根据权限决定是否渲染
  - **每个 Server Action 都检查权限**（隐藏按钮不等于禁止操作）
- **表格**：筛选、排序、分页放在 URL 中，服务端查询；客户端只负责交互
- **批量操作和导出**：大量数据导出使用后台任务，完成后通知下载
- **弹窗**：拦截路由 + 并行路由，可以通过 URL 分享
- **多团队**：monorepo，按领域分包；或 Multi-Zones

**关键指标**

- 页面切换速度、表格查询时间
- Action 的错误率和权限拒绝次数（异常增长可能是越权尝试）

**口述模板（2–3 分钟）**

首先说明选型：后台不需要 SEO，Vite 加 React 也可以；选择 Next.js 是看重全栈能力和统一的服务端鉴权。

权限是核心：菜单和按钮在服务端根据权限渲染，页面数据在数据访问层检查，每个 Server Action 都独立检查权限，因为隐藏按钮不能阻止直接调用。

表格的筛选、排序、分页都放在 URL 中，由服务端查询，刷新和分享都能保留状态。详情使用拦截路由实现弹窗。大量数据的导出用后台任务处理。

多团队时使用 monorepo 按领域拆分。

**扩展追问**

- 权限修改后，已登录用户什么时候生效？→ 权限从数据库或缓存实时读取（带短缓存和标签），修改时失效；不要把权限完整地存在 JWT 中，否则要等到令牌过期。

### S6. 设计一个 Next.js 应用的自托管部署方案

- **难度**: 高级
- **标签**: 部署, 运维

**澄清问题（面试时先问）**

- 运行环境：Kubernetes、虚拟机还是云服务？
- 流量规模和实例数量？
- 使用了哪些特性：ISR、Cache Components、图片优化、Server Actions？
- 发布频率？是否需要灰度？

**参考方案**

```text
CI：安装 → 类型检查 / lint / 测试（并行）→ next build（固定 BUILD_ID）→ 构建镜像
    → 上传 .next/static 到对象存储 + CDN（保留旧版本）
CD：Kubernetes 滚动发布 / 灰度
运行时：
  CDN（静态资源 + 可缓存的 HTML）
    → Ingress / Nginx（关闭缓冲、剥离内部请求头、TLS）
      → Next.js Pods（standalone，非 root）
          ├─ Redis：cacheHandler / cacheHandlers、限流
          ├─ 图片优化：独立服务或 CDN 图片处理
          └─ OpenTelemetry → 追踪 / 日志 / 指标
```

**关键设计**

- **一致性**：所有实例使用同一个构建；统一的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`；共享缓存
- **静态资源**：上传到 CDN，**保留旧版本**（版本偏差）；`assetPrefix`
- **流式**：Nginx `proxy_buffering off`
- **安全**：网关剥离 `x-middleware-subrequest` 等内部头；限制请求体大小；及时打补丁
- **优雅关闭**：Kubernetes `preStop` + 处理 SIGTERM，等待进行中的请求（包括流式响应）完成
- **健康检查**：存活和就绪探针使用轻量的 Route Handler
- **灰度**：按 Cookie 或比例路由到新版本；注意新旧版本的 Server Action 兼容
- **扩缩容**：基于 CPU 和请求延迟

**关键指标**

- 实例的 CPU、内存、事件循环延迟
- 缓存命中率、Redis 延迟
- 发布期间的错误率（版本偏差导致的 chunk 加载失败）

**口述模板（2–3 分钟）**

先确认运行环境和使用的特性。CI 中并行做检查，构建时固定构建 ID，静态资源上传到 CDN 并保留旧版本，防止发布期间旧客户端加载不到资源。

运行时多实例需要保证一致：同一个构建、统一的 Server Actions 加密密钥、Redis 作为共享缓存处理器。网关层关闭缓冲以支持流式，同时剥离内部请求头。

发布时使用滚动或灰度，处理 SIGTERM 优雅关闭。监控事件循环延迟、缓存命中率和发布期间的错误率。

**扩展追问**

- 图片优化占用了大量 CPU 怎么办？→ 拆分为独立服务，或者使用 CDN 图片处理（自定义 loader），Next.js 实例只负责渲染。

### S7. 设计一个实时协作的文档 / 白板应用的 Next.js 部分

- **难度**: 高级
- **标签**: 实时, 协作

**澄清问题（面试时先问）**

- 同时编辑人数？延迟要求？
- 冲突解决：CRDT 还是 OT？是否需要离线编辑？
- 部署平台是否支持 WebSocket？

**参考方案**

```text
Next.js：
  - 文档列表、权限、分享设置：服务端组件 + Server Actions
  - 编辑器页面：服务端渲染文档快照（首屏和 SEO）→ 客户端编辑器接管
实时层（独立服务）：
  - WebSocket 服务（Yjs / Liveblocks / PartyKit 等）
  - 鉴权：Next.js 签发短期令牌，实时服务验证
持久化：
  - 实时服务定期把 CRDT 状态写入数据库 / 对象存储
  - 快照生成后失效 Next.js 中文档的缓存
```

**关键设计**

- **为什么实时层独立**：Serverless 不支持长连接；长连接服务和 Web 渲染的扩展方式不同
- **首屏**：服务端渲染文档快照，编辑器加载后与实时状态同步（客户端编辑器 `dynamic` + `ssr: false`，用快照作为占位）
- **鉴权**：Next.js 中检查文档权限后签发短期令牌（包含文档 ID 和权限），实时服务只验证令牌
- **冲突**：CRDT（Yjs）天然支持离线和合并
- **在线状态**：光标、选区通过 awareness 协议广播，不持久化

**关键指标**

- 同步延迟、连接数、重连次数
- 文档加载时间、快照大小

**口述模板（2–3 分钟）**

Next.js 负责文档列表、权限和首屏渲染，实时协作由独立的 WebSocket 服务负责，因为 Serverless 不支持长连接，而且两者的扩展方式不同。

编辑器页面先在服务端渲染文档快照，保证首屏和分享预览，客户端编辑器加载后接管并与实时服务同步。鉴权由 Next.js 检查权限后签发短期令牌，实时服务只验证令牌。

冲突解决使用 CRDT，支持离线编辑。实时服务定期保存状态，并失效 Next.js 中的文档缓存。

**扩展追问**

- 权限被撤销后，正在编辑的用户怎么处理？→ 短期令牌过期后无法续期；需要立即生效时由 Next.js 通知实时服务断开该用户的连接。

### S8. 设计一个 Next.js 应用的前端监控与性能平台接入

- **难度**: 中级
- **标签**: 监控, 性能

**澄清问题（面试时先问）**

- 需要监控哪些：错误、性能、用户行为？
- 使用现有平台（Sentry、Datadog）还是自建？
- 数据量和采样率？隐私要求？

**参考方案**

```text
客户端：
  instrumentation-client.ts → 初始化错误和性能 SDK
  useReportWebVitals → LCP、INP、CLS、TTFB（按路由维度）
  error.tsx / global-error.tsx → 上报渲染错误
服务端：
  instrumentation.ts → OpenTelemetry（渲染、fetch、数据库的追踪）
  onRequestError → 服务端错误（带路由类型：页面 / Action / Route Handler / proxy）
关联：
  请求 ID / trace ID 从服务端传到客户端（响应头或 meta），客户端上报带上，前后端链路串联
构建：
  上传 source map 到监控平台，生产环境不公开
```

**关键设计**

- **按路由聚合**：使用路由模板（`/products/[id]`）而不是实际 URL，避免基数爆炸
- **区分渲染类型**：服务端组件错误（digest）、客户端错误、Action 错误、hydration 错误
- **采样**：错误全量，性能和追踪按比例采样
- **隐私**：不上报个人信息，URL 中的参数脱敏
- **发布关联**：错误和性能数据带上部署版本，快速定位回归

**关键指标**

- 错误率（按路由、按版本）、核心网页指标的 P75
- 服务端渲染时间、数据请求时间分布

**口述模板（2–3 分钟）**

客户端在 instrumentation-client 中初始化监控 SDK，用 useReportWebVitals 按路由上报核心网页指标，error.tsx 上报渲染错误。服务端在 instrumentation 中初始化 OpenTelemetry，用 onRequestError 统一捕获服务端组件、Action、Route Handler 和 proxy 的错误。

前后端通过 trace ID 串联，构建时上传 source map 但不公开。

数据按路由模板聚合，避免基数爆炸；错误全量上报，性能数据采样；所有数据带上部署版本，用于发现回归。

**扩展追问**

- 生产环境服务端组件的错误在客户端只有 digest，怎么定位？→ onRequestError 上报的数据中包含 digest 和完整堆栈，用 digest 关联查找。
