# 算法场景设计

> 回答结构：先澄清需求和约束（数据规模、实时性、运行环境）→ 选择数据结构和算法 → 说明复杂度 → 说明工程细节（主线程、内存、边界）→ 回应扩展追问。这类题考察「把算法用到前端真实场景中」的能力。

### S1. 设计搜索框的自动补全

- **难度**: 中级
- **标签**: Trie, 防抖, 缓存

**澄清问题（面试时先问）**

- 词库在前端（几千到几万条，如城市、命令面板）还是后端（海量）？
- 是否需要拼音、首字母、模糊匹配？
- 排序依据：热度、个性化、匹配质量？

**参考方案**

```text
前端词库（小）：
  构建 Trie（同时插入原词、拼音全拼、首字母，节点指向原词 ID）
  输入 → 防抖（约 150ms）→ Trie 前缀匹配 → 收集候选 → 打分排序 → Top K

后端词库（大）：
  输入 → 防抖 → 请求（AbortController 取消旧请求）→ 结果缓存（LRU，键为前缀）
  已有结果的前缀扩展：用户在「abc」的结果基础上输入「abcd」时，可以先在本地过滤，再等服务端结果

模糊匹配（命令面板）：
  子序列匹配 + 打分：连续匹配、单词开头 / 驼峰边界加分，间隔扣分
```

**关键设计**

- **竞态**：只展示最后一次输入的结果（取消旧请求或比较请求序号）
- **缓存**：前缀 → 结果的 LRU 缓存，回删时直接命中
- **大词库在前端**：在 Web Worker 中构建 Trie 和搜索，避免阻塞输入
- **高亮**：返回匹配的位置区间，渲染时拆分文本
- **可访问性**：`combobox` 角色、上下键选择、`aria-activedescendant`

**关键指标**

- 输入到展示的延迟（P95）
- 建议的点击率

**口述模板（2–3 分钟）**

我先确认词库的规模和位置。词库在前端的话，构建一棵 Trie，同时把拼音全拼和首字母也插入，节点指向原词 ID，这样输入中文、拼音、首字母都能匹配；查询复杂度只和前缀长度有关，然后按热度和匹配质量打分取前 K 个。词库大时把构建和搜索放到 Web Worker 中。

词库在后端的话，输入防抖后请求，用 AbortController 取消旧请求解决竞态；结果按前缀做 LRU 缓存，用户回删时直接命中；输入更长的前缀时可以先在已有结果中本地过滤，提升响应速度。

命令面板这类模糊匹配用子序列匹配加打分，连续匹配和单词边界匹配加分。

最后还要做高亮和键盘可访问性，用输入到展示的延迟和点击率衡量效果。

**扩展追问**

- 词库很大时 Trie 占内存太多？→ 压缩前缀树；或者只在前端保留热门词，长尾走服务端。

### S2. 设计一个前端任务调度器（类似 React Scheduler）

- **难度**: 高级
- **标签**: 堆, 时间切片

**澄清问题（面试时先问）**

- 任务的类型：渲染更新、数据处理、埋点上报？
- 需要多少个优先级？是否需要取消？
- 运行环境：只有浏览器主线程，还是可以用 Worker？

**参考方案**

```text
任务：{ id, callback, priority, startTime, expirationTime }
  expirationTime = startTime + timeout(priority)
    Immediate: -1（立即过期）  UserBlocking: 250ms  Normal: 5s  Low: 10s  Idle: 永不过期

两个最小堆：
  timerQueue：延迟任务，按 startTime 排序
  taskQueue：可执行任务，按 expirationTime 排序

调度循环（每次 MessageChannel 宏任务）：
  把 timerQueue 中到期的任务移到 taskQueue
  while 堆顶任务存在：
    如果任务未过期 且 时间片（约 5ms）已用完 → 让出，调度下一次宏任务
    执行 callback(didTimeout)
      返回函数 → 任务未完成，保留在堆中，下次继续
      否则 → 出堆
```

**关键设计**

- **最小堆**：插入和取出最紧急任务都是 O(log n)
- **时间切片**：用 `performance.now()` 判断，让出后用 MessageChannel 继续（setTimeout 嵌套有 4ms 最小延迟）
- **防饥饿**：过期的任务不再让出，保证低优先级任务最终执行
- **取消**：标记 `callback = null`，出堆时跳过（延迟删除，避免 O(n) 的堆中删除）
- **输入优先**：`navigator.scheduling.isInputPending()`（如可用）在有用户输入时提前让出

**关键指标**

- 长任务数量、INP
- 任务的平均等待时间（按优先级）

**口述模板（2–3 分钟）**

调度器的核心是两个最小堆。每个任务根据优先级计算一个过期时间，可执行的任务放在按过期时间排序的堆中，堆顶就是最紧急的任务；延迟任务放在按开始时间排序的另一个堆中，到期后移过去。用堆是因为插入和取出最紧急任务都是 O(log n)。

执行时用时间切片：每次执行任务前检查是否已经用完约 5ms 的时间片，用完就让出主线程，通过 MessageChannel 调度下一个宏任务继续。不用 setTimeout 是因为它嵌套时有 4ms 的最小延迟。

任务可以返回一个函数表示还没完成，下次继续执行，这样长任务可以被拆开和中断。

为了防止饥饿，已经过期的任务不再让出，一定会被执行。取消任务时只把回调置空，出堆时跳过，避免在堆中间删除。

最后用长任务数量和 INP 衡量效果。

**扩展追问**

- 为什么不用 `requestIdleCallback`？→ 触发频率不稳定（可能每秒只有 20 次左右，后台标签页更少），且 Safari 支持较晚。

### S3. 设计 10 万节点的树形组件

- **难度**: 高级
- **标签**: 树, 虚拟列表

**澄清问题（面试时先问）**

- 节点数量和层级深度？数据一次性加载还是懒加载？
- 需要哪些功能：展开折叠、搜索、勾选（父子联动）、拖拽？

**参考方案**

```text
数据层：
  原始数据 → Map<id, Node>（含 parentId、children ids、depth）
  展开状态：Set<id>
  可见列表：根据展开状态对树做 DFS 得到扁平数组 visible[]（只包含展开路径上的节点）

渲染层：
  虚拟列表渲染 visible[]（固定行高 → 直接计算；缩进 = depth × 宽度）

操作：
  展开 / 折叠：在 visible 中插入 / 删除该节点的可见子树（而不是全量重算）
  搜索：遍历一次，匹配的节点及其祖先加入结果集，自动展开祖先
  勾选：
    向下：设置子树所有节点
    向上：父节点根据子节点状态计算（全选 / 半选 / 未选），用计数避免重复遍历
```

**关键设计**

- **扁平化 + 虚拟列表**是性能的核心：DOM 只有可视区域的几十个节点
- **勾选联动**：每个节点维护 `checkedCount`（已选中的叶子数）和 `leafCount`；勾选时向下设置子树并向上更新祖先计数，O(子树大小 + 深度)
- **搜索**：在 Worker 中完成；结果中保留祖先路径
- **懒加载**：节点首次展开时请求子节点

**关键指标**

- 首次渲染时间、展开 / 勾选的响应时间（目标 < 100ms）
- 内存占用

**口述模板（2–3 分钟）**

10 万节点的树不能直接渲染，核心是「扁平化加虚拟列表」。

数据层用 Map 存所有节点，记录父子关系和深度；展开状态用一个 Set。根据展开状态做一次 DFS 得到可见节点的扁平数组，渲染层用虚拟列表只渲染可视区域，缩进按深度计算。

展开和折叠时只在扁平数组中插入或删除这个节点的可见子树，而不是全量重算。

勾选联动是另一个难点：每个节点维护叶子总数和已选叶子数，勾选时向下设置整个子树，向上沿祖先路径更新计数，就能 O(1) 判断每个父节点是全选、半选还是未选。

搜索放到 Worker 中，匹配的节点加上它的所有祖先构成结果树，并自动展开祖先。

最后用展开和勾选的响应时间衡量，目标在 100ms 以内。

**扩展追问**

- 勾选根节点时要遍历 10 万个节点，会卡吗？→ 一次遍历 10 万个对象通常在几十毫秒内；更进一步可以惰性处理：只记录「某子树整体被选中」的标记，读取时再向下推导。

### S4. 协同编辑方案选型（OT vs CRDT）

- **难度**: 高级
- **标签**: OT, CRDT

**澄清问题（面试时先问）**

- 编辑对象：纯文本、富文本、表格、白板？
- 是否需要离线编辑？是否需要端到端加密 / 去中心化？
- 同时编辑的人数？是否已经有中心服务器？

**参考方案**

```text
方案 A：CRDT（Yjs）
  客户端：Yjs 文档 + 编辑器绑定（ProseMirror / Monaco / CodeMirror）
  同步：WebSocket 服务器只负责转发和持久化增量更新（服务器不需要理解操作语义）
  离线：IndexedDB 持久化本地更新，联网后合并
  感知：awareness 协议（光标、选区、在线用户）

方案 B：OT
  中心服务器维护文档版本，客户端提交「基于版本 v 的操作」
  服务器把操作与 v 之后的操作做转换，应用后广播
  客户端收到确认前的本地操作需要与远端操作互相转换
```

**关键设计**

- **选型**：需要离线、去中心化、多种数据类型 → CRDT；已有成熟的 OT 服务、文档模型复杂且需要服务端校验 → OT
- **CRDT 的成本**：元数据（每个字符的 ID）、墓碑 → 需要快照和垃圾回收
- **撤销**：只撤销自己的操作（Yjs 的 UndoManager 按来源追踪）
- **权限**：服务器校验更新的来源和权限
- **持久化**：定期把增量合并为快照

**关键指标**

- 操作同步延迟（P95）、冲突导致的异常数（目标 0）
- 文档大小增长、加载时间

**口述模板（2–3 分钟）**

协同编辑的核心问题是并发操作的一致性，有 OT 和 CRDT 两种方案。

OT 由中心服务器确定操作顺序，并发操作根据对方的操作做转换，比如对方在前面插入了字符，我的插入位置要后移。它需要中心服务器，离线支持较难。

CRDT 让数据结构本身满足「任意顺序合并结果一致」，文本中每个字符有全局唯一且可排序的 ID，插入表示为「在某个 ID 之后」。服务器只需要转发和存储更新，天然支持离线和去中心化。

如果需要离线编辑或者多种数据类型，我会选择基于 CRDT 的 Yjs，配合编辑器绑定、WebSocket 同步、IndexedDB 离线存储和 awareness 显示光标。代价是元数据和墓碑会让文档增长，需要定期做快照和垃圾回收。

撤销只撤销自己的操作，服务器要校验权限。最后用同步延迟和文档大小监控。

**扩展追问**

- 两个人同时在同一位置插入，顺序怎么定？→ CRDT 用 ID 中的客户端 ID 等确定性规则排序，所有副本得到相同的顺序。

### S5. 设计前端请求缓存与去重层

- **难度**: 中级
- **标签**: LRU, 缓存

**澄清问题（面试时先问）**

- 哪些请求可以缓存（GET、幂等的查询）？
- 数据的新鲜度要求？是否需要跨页面 / 刷新后保留？
- 是否已经使用 TanStack Query / SWR？

**参考方案**

```text
request(key, fetcher, { ttl, staleTime })
  1. 并发去重：inflight Map<key, Promise> —— 相同请求进行中时复用同一个 Promise
  2. 缓存：LRU<key, { data, fetchedAt }>（容量限制）
     - 新鲜（< staleTime）：直接返回
     - 过期但在 ttl 内：返回旧数据，同时后台刷新（stale-while-revalidate）
     - 超过 ttl：重新请求
  3. 失效：mutation 后按 key 前缀失效（['user', id]）
  4. 错误：失败不写缓存；inflight 中移除，允许重试
```

**关键设计**

- **键**：URL + 排序后的参数（参数顺序不同应视为同一个请求）
- **LRU**：限制内存；页面长时间运行时避免无限增长
- **SWR**：体验好（先显示旧数据），后台刷新完成后通知订阅者
- **竞态**：同一个 key 的旧请求结果晚于新请求返回时不能覆盖（比较请求的发起时间）
- **持久化**：需要时写入 IndexedDB，注意敏感数据

**关键指标**

- 缓存命中率、重复请求减少的比例

**口述模板（2–3 分钟）**

我会在请求层加三个能力：并发去重、缓存、失效。

并发去重用一个 Map 保存进行中的 Promise，相同的请求复用同一个，完成或失败后移除。缓存用 LRU 限制容量，记录每条数据的获取时间：新鲜时直接返回；过期但在 TTL 内时先返回旧数据并在后台刷新，也就是 stale-while-revalidate；超过 TTL 才重新请求。

缓存的键是 URL 加排序后的参数。修改数据后按键的前缀失效相关缓存。要注意竞态：同一个键的旧请求不能覆盖新请求的结果。

实际项目中我会直接用 TanStack Query，它已经实现了这些能力，自己实现时重点是这几个机制。

**扩展追问**

- 失败的请求要缓存吗？→ 一般不缓存；可以短时间缓存 404 等确定的结果，避免反复请求。

### S6. 设计埋点上报队列

- **难度**: 中级
- **标签**: 队列, 限流

**澄清问题（面试时先问）**

- 事件量（每秒多少个）？是否有高优先级事件（错误、支付）？
- 能否接受少量丢失？页面关闭时要保证送达吗？

**参考方案**

```text
track(event)
  → 采样（按事件类型）
  → 内存队列（区分优先级：错误 / 关键业务优先）
  → 批量触发：达到 N 条 或 每 T 秒 或 页面隐藏（visibilitychange → hidden）
  → 发送：
      正常：fetch（keepalive）
      页面隐藏 / 关闭：navigator.sendBeacon（有大小限制，超出则拆分）
  → 失败：退避重试；仍失败写入 IndexedDB，下次启动补发
  → 限流：令牌桶限制单位时间的上报次数，防止异常循环打满服务端
```

**关键设计**

- **批量**：减少请求数
- **页面隐藏时上报**：`visibilitychange` 比 `unload` 更可靠（移动端不一定触发 unload）
- **去重**：事件带唯一 ID，服务端去重（补发和重试可能重复）
- **队列上限**：超过上限时丢弃低优先级事件，避免内存增长
- **不阻塞主线程**：序列化和压缩可以放到空闲时间或 Worker

**关键指标**

- 上报成功率、事件延迟
- 请求数 / 事件数的比例

**口述模板（2–3 分钟）**

埋点上报的核心是「批量、可靠、不影响页面」。

事件先经过采样进入内存队列，队列按优先级区分，错误和关键业务事件优先。批量发送的触发条件是达到一定条数、超过一定时间、或者页面隐藏。页面隐藏和关闭时用 sendBeacon，它在页面卸载后也能发送，但有大小限制，需要拆分。

失败时退避重试，仍然失败就写入 IndexedDB，下次启动时补发。因为有重试和补发，每个事件要带唯一 ID 让服务端去重。

为了防止代码异常导致事件暴增，用令牌桶限制上报速率，队列也有上限，超过时丢弃低优先级事件。

最后用上报成功率和事件延迟衡量。

**扩展追问**

- 为什么不在 `beforeunload` 中发送？→ 移动端经常不触发；而且会影响 bfcache；`visibilitychange` 到 `hidden` 是更可靠的最后时机。

### S7. 设计大文件上传

- **难度**: 中级
- **标签**: 分片, 哈希, 并发

**澄清问题（面试时先问）**

- 文件大小范围（几百 MB 到几十 GB）？
- 是否需要秒传、断点续传、暂停？
- 存储：自己的服务还是对象存储（S3 分片上传）？

**参考方案**

```text
1. 分片：file.slice，固定大小（如 5MB；对象存储有最小分片要求）
2. 哈希（Web Worker 中）：
   - 增量 MD5（spark-md5）或抽样哈希（大文件提速）
   - 计算过程可以显示进度，并可取消
3. 预检：POST /upload/init { hash, size, name }
   → 已存在：秒传
   → 部分存在：返回已上传的分片列表
4. 上传：并发控制（如 4 个），跳过已上传的分片；失败的分片退避重试
   → 每个分片带分片哈希，服务端校验
5. 合并：所有分片完成后通知合并（对象存储：CompleteMultipartUpload）
6. 暂停 / 恢复：AbortController 取消进行中的请求；恢复时重新预检
```

**关键设计**

- **并发控制**：限制同时进行的请求数（浏览器对同一域名的连接数也有限制）
- **进度**：已完成分片的字节数 + 进行中分片的进度
- **动态分片大小**：根据上一个分片的耗时调整（网络好时加大）
- **直传对象存储**：服务端只签发预签名 URL，文件不经过应用服务器

**关键指标**

- 上传成功率、平均速度
- 秒传命中率

**口述模板（2–3 分钟）**

大文件上传的核心是分片、哈希、并发和断点续传。

先把文件按固定大小分片，在 Web Worker 中增量计算文件哈希，避免阻塞主线程；文件特别大时可以用抽样哈希提速，但需要服务端最终校验。

拿到哈希后先预检：服务端已有完整文件就秒传，有部分分片就返回已上传的列表。上传时用并发控制同时传几个分片，跳过已上传的，失败的分片退避重试，每个分片带哈希让服务端校验。全部完成后通知服务端合并。

暂停用 AbortController 取消进行中的请求，恢复时重新预检即可。如果使用对象存储，我会让服务端签发预签名 URL，文件直传，不经过应用服务器。

最后用上传成功率和秒传命中率衡量。

**扩展追问**

### S8. 设计关系图 / 拓扑图的可视化

- **难度**: 高级
- **标签**: 图, 布局, 空间索引

**澄清问题（面试时先问）**

- 节点和边的数量（几百、几千、几万）？
- 需要哪些交互：拖拽、缩放、点击、框选、路径高亮？
- 布局类型：力导向、层次（DAG）、树？

**参考方案**

```text
数据：邻接表；节点 { id, x, y, ... }

布局：
  力导向：节点间斥力（库仑）+ 边的引力（弹簧），迭代收敛
         斥力的计算 O(n²) → Barnes-Hut 四叉树近似 O(n log n)
         在 Web Worker 中计算，逐帧把坐标发回主线程
  层次布局（DAG）：拓扑排序分层 → 减少交叉（层内排序）→ 坐标分配（Sugiyama 算法）

渲染：
  < 几千个节点：SVG / Canvas
  更多：Canvas / WebGL；视口裁剪，只绘制可见区域
  缩放时的细节层次（LOD）：缩小时不绘制文字和细节

交互：
  命中检测：四叉树空间索引，点击 / 悬停时 O(log n) 找到节点
  路径高亮：BFS（无权）/ Dijkstra（带权）求最短路径
  框选：四叉树范围查询
```

**关键设计**

- **四叉树**同时用于布局加速（Barnes-Hut）和交互的命中检测
- **布局在 Worker 中**：主线程只负责渲染和交互
- **增量布局**：新增节点时只局部调整，保持用户的「心理地图」
- **大图**：先展示聚合后的社区（社区发现算法），点击后展开

**关键指标**

- 首次布局时间、交互帧率（目标 60fps）
- 能流畅支持的节点数量

**口述模板（2–3 分钟）**

我先确认图的规模和布局类型，这决定了算法和渲染方式。

布局上，一般关系图用力导向：节点之间有斥力，边产生引力，迭代到稳定。朴素的斥力计算是 O(n²)，我会用 Barnes-Hut 算法，用四叉树把远处的节点群近似成一个质点，降到 O(n log n)，并且把布局计算放到 Web Worker 中。如果是有方向的依赖图，用层次布局：先拓扑排序分层，再减少边的交叉。

渲染上，几千个节点以内可以用 SVG 或 Canvas，更多时用 Canvas 或 WebGL，并做视口裁剪和细节层次。

交互上同样用四叉树做空间索引，点击和悬停时快速找到节点，框选是范围查询；路径高亮用 BFS 或 Dijkstra。

节点特别多时先按社区聚合展示，点击后展开。最后用布局时间和交互帧率衡量。

**扩展追问**

- 为什么不每次点击时遍历所有节点判断？→ 一万个节点时每次鼠标移动都遍历会导致掉帧；四叉树把命中检测降到 O(log n)。
