## 一、前端框架中的算法

### Q1. 虚拟 DOM diff 为什么能从 O(n³) 降到 O(n)？

- **难度**: 高级
- **标签**: diff, React

**答案**

**两棵树的最小编辑距离**（树编辑距离）的通用算法是 O(n³)，1000 个节点就是 10⁹ 次运算，不可接受。

React / Vue 基于三个**启发式假设**降到 O(n)：

1. **只比较同层节点**：跨层移动视为删除 + 新建（实际中很少发生）
2. **类型不同的元素产生不同的树**：`div` 变成 `span`，直接销毁整棵子树重建，不再比较子节点
3. **用 key 标识同层的子节点**：列表中通过 key 找到对应的旧节点，复用而不是重建

**代价**：假设不成立时不是最优解（例如跨层移动会重建），但在 UI 场景中很少见，换来线性复杂度。

**口述模板（30–60 秒）**

1. 一句话结论：通用的树 diff 是 O(n³)，框架通过启发式假设降到 O(n)。
2. 关键机制：只比较同层、类型不同直接替换、用 key 识别列表中的节点。
3. 对比或注意点：代价是跨层移动等情况不是最优，但在 UI 中很少发生。
4. 可追问时补充：这就是为什么 key 要稳定，用下标作为 key 会导致错误的复用。

**常见追问**

- 用 index 作为 key 有什么问题？→ 在列表头部插入时所有 key 对应的元素都变了，导致大量不必要的更新，以及带状态的组件（输入框）状态错位。

### Q2. React 的列表 diff 和 Vue 3 的快速 diff 有什么区别？

- **难度**: 高级
- **标签**: diff, Vue, React

**答案**

**React（单向遍历）**：

1. 第一轮：从左到右按顺序比较，key 相同就复用，遇到不同就停止
2. 把剩余的旧节点放进 Map（key → 节点）
3. 第二轮：遍历剩余的新节点，从 Map 中找可复用的节点；用 `lastPlacedIndex` 判断是否需要移动（旧位置小于 lastPlacedIndex 就需要移动）

缺点：把最后一个节点移到最前面时，React 会移动除它之外的所有节点。

**Vue 3（快速 diff）**：

1. 预处理：**头部**相同的节点、**尾部**相同的节点先处理掉
2. 只剩新增或只剩删除时直接处理
3. 中间乱序部分：建立新节点 key → 下标的 Map，得到「新节点在旧列表中的位置」数组 `source`
4. **对 `source` 求最长递增子序列（LIS）**：LIS 中的节点相对顺序没变，**不需要移动**；其他节点移动或新建

LIS 保证了**移动次数最少**。

**口述模板（30–60 秒）**

1. 一句话结论：React 是单向遍历加 lastPlacedIndex，Vue 3 是双端预处理加最长递增子序列。
2. 关键机制：Vue 3 把中间部分映射为旧位置数组，LIS 中的节点不需要移动。
3. 对比或注意点：React 在把末尾节点移到开头时会移动很多节点，Vue 3 只移动一个。
4. 可追问时补充：React 选择单向遍历是因为 Fiber 是单向链表，不方便从尾部遍历。

**常见追问**

- 为什么 React 不用双端比较？→ Fiber 的兄弟节点是单向链表（`sibling`），没有反向指针。

### Q3. Vue 3 中最长递增子序列是怎么求的？

- **难度**: 高级
- **标签**: LIS, Vue

**答案**

需要的不只是长度，而是**具体的序列（下标）**：

1. 贪心 + 二分维护 `result`（存下标，对应的值递增，含义同 tails）
2. 用 `p` 数组记录每个元素加入时**前一个元素的下标**（前驱）
3. 最后从 `result` 的末尾沿着前驱回溯，得到正确的序列

```text
source = [3, 1, 5, 4, 2]（-1 表示新节点，跳过）
最终 result 回溯得到下标 [1, 3] 或类似，对应值 [1, 4]
```

**为什么需要回溯**：`result` 在过程中会被替换，最终数组里的下标可能不构成合法的递增子序列；但每个位置的前驱是在插入时记录的，回溯链一定是合法的。

完整实现见 [40-coding-handwritten.md H5](./40-coding-handwritten.md)。

**口述模板（30–60 秒）**

1. 一句话结论：Vue 3 用贪心加二分求 LIS，并记录前驱以还原具体序列。
2. 关键机制：每个元素加入时记录它前一个元素的下标。
3. 对比或注意点：最终的 result 数组本身不一定是合法的序列，需要从末尾回溯。
4. 可追问时补充：复杂度 O(n log n)。

**常见追问**

- `source` 中的 `-1`（新节点）怎么处理？→ 跳过，新节点需要创建，不参与「不移动」的判断（Vue 源码中用 0 表示新节点，位置存储为下标 + 1）。

### Q4. React Scheduler 为什么用最小堆？时间切片是怎么实现的？

- **难度**: 高级
- **标签**: 堆, React, 调度

**答案**

**最小堆**：

- 任务按**过期时间**（开始时间 + 优先级对应的超时时间）排序，堆顶是最紧急的任务
- 需要频繁「插入新任务」和「取出最紧急的任务」→ 最小堆的 O(log n) 比排序数组的 O(n) 插入更好
- 有两个堆：`taskQueue`（已到开始时间）和 `timerQueue`（延迟任务，按开始时间排序）

**时间切片**：

- 每次执行任务前检查是否超过时间片（约 5ms），超过就**让出主线程**（`shouldYield`）
- 用 `MessageChannel` 调度下一个宏任务继续执行（不用 `setTimeout` 是因为嵌套时有 4ms 的最小延迟；不用 `requestIdleCallback` 是因为触发频率不稳定）
- 任务返回一个函数表示「还没完成」，下次继续执行（可中断）

**口述模板（30–60 秒）**

1. 一句话结论：Scheduler 用最小堆按过期时间管理任务，用时间切片避免长时间占用主线程。
2. 关键机制：堆顶是最紧急的任务，插入和取出都是 O(log n)。
3. 对比或注意点：每 5ms 左右检查一次是否让出，用 MessageChannel 调度下一个宏任务。
4. 可追问时补充：不用 setTimeout 是因为有最小延迟，不用 requestIdleCallback 是因为不稳定。

**常见追问**

- 饥饿问题怎么处理？→ 低优先级任务的过期时间到了之后，即使有更高优先级的任务也会被执行（过期任务不再让出）。

### Q5. React 的 Lane 模型为什么用位运算？

- **难度**: 高级
- **标签**: 位运算, React

**答案**

Lane 用 **31 位二进制**表示优先级，每一位（或几位）是一条「车道」：

```text
SyncLane            0b0000000000000000000000000000010
InputContinuousLane 0b0000000000000000000000000001000
DefaultLane         0b0000000000000000000000000100000
TransitionLanes     0b0000000001111111111111110000000（多条）
IdleLane            0b0100000000000000000000000000000
```

**位运算的好处**：

- **集合操作 O(1)**：合并 `a | b`、交集 `a & b`、移除 `a & ~b`、判断包含 `(set & lane) !== 0`
- 一个整数可以表示「一批」优先级（例如多个 transition 同时进行）
- **取最高优先级**：`lanes & -lanes` 取最低位的 1（数值越小优先级越高）

**相比旧的 expirationTime**：单个数值无法表达「一组更新」，也无法区分「同一优先级下的不同批次」。

**口述模板（30–60 秒）**

1. 一句话结论：Lane 用二进制位表示优先级，位运算可以 O(1) 完成集合操作。
2. 关键机制：合并用或运算，判断包含用与运算，取最高优先级用 lanes & -lanes。
3. 对比或注意点：一个整数就能表示一组优先级，解决了 expirationTime 无法表示批次的问题。
4. 可追问时补充：数值越小优先级越高，最低位的 1 就是最高优先级。

**常见追问**

- `x & -x` 为什么能取最低位的 1？→ `-x` 是 `~x + 1`（补码），最低位的 1 以下全部翻转后加 1 恢复，与原数只有该位相同。

### Q6. 响应式系统中的「glitch」是什么？怎么用拓扑顺序避免？

- **难度**: 高级
- **标签**: 依赖图, Signals

**答案**

**glitch（毛刺）**：依赖图中出现菱形依赖时，某个计算值读取到了「部分更新」的中间状态。

```text
     a
    / \
   b   c      b = a * 2, c = a + 1, d = b + c
    \ /
     d
a 变化时，如果先更新 b 就立即重算 d，此时 c 还是旧值 → d 短暂地得到错误的结果
```

**解决方式**：

- **拓扑顺序更新**：按照依赖图的拓扑序（或高度 / 深度）更新，保证 d 在 b、c 都更新后才计算
- **Push-Pull（现代 Signals 的方案）**：变化时只向下**推送「脏」标记**（不计算）；读取时**拉取**，按需从上游重新计算，并通过版本号判断依赖是否真的变化 → 天然 glitch-free，且只计算被读取的值

**口述模板（30–60 秒）**

1. 一句话结论：glitch 是菱形依赖中读取到部分更新的中间状态。
2. 关键机制：可以按拓扑顺序更新，或者使用 push-pull 模型。
3. 对比或注意点：push-pull 先推送脏标记，读取时再拉取计算，避免中间状态。
4. 可追问时补充：版本号用于判断依赖的值是否真的变化，避免不必要的重算。

**常见追问**

- Push-pull 为什么更高效？→ 没有被读取的 computed 不会计算（惰性）；值没有变化时下游不需要重算。

### Q7. 模板编译器 / 解析器用到了哪些算法？

- **难度**: 高级
- **标签**: 编译, 状态机

**答案**

**编译流程**：解析（Parse）→ 转换（Transform）→ 生成（Generate）。

| 阶段 | 算法 / 数据结构 |
|------|----------------|
| 词法分析 | **有限状态机**：根据当前状态和字符决定转移（标签开始、属性名、属性值、文本） |
| 语法分析 | **栈**：开始标签入栈，结束标签出栈匹配，构建 AST |
| 表达式解析 | 递归下降、运算符优先级（Pratt 解析） |
| 转换 | **树的遍历**（访问者模式），进入和退出两个阶段 |
| 优化 | 静态节点标记（后序遍历：所有子节点静态时自身才静态）、静态提升 |
| 生成 | 树的遍历，拼接代码字符串 |

**口述模板（30–60 秒）**

1. 一句话结论：模板编译分为解析、转换、生成三个阶段。
2. 关键机制：词法分析用有限状态机，构建 AST 用栈匹配标签。
3. 对比或注意点：转换阶段是树的遍历，静态标记要用后序遍历。
4. 可追问时补充：表达式解析可以用递归下降或 Pratt 解析处理优先级。

**常见追问**

- 为什么静态标记要用后序遍历？→ 一个节点是否静态取决于它的所有子节点，必须先处理子节点。

## 二、字符串与进阶数据结构

### Q8. KMP 算法的原理？

- **难度**: 高级
- **标签**: 字符串, KMP

**答案**

**问题**：在文本 s 中查找模式 p。暴力 O(nm)，失配时文本指针回退。

**KMP**：预处理模式串的 **next 数组**（`next[i]` = `p[0..i]` 的最长相等真前缀和真后缀的长度）；失配时**文本指针不回退**，模式指针跳到 `next[j-1]`。O(n + m)。

```ts
function buildNext(p: string): number[] {
  const next = new Array(p.length).fill(0);
  for (let i = 1, len = 0; i < p.length; i++) {
    while (len > 0 && p[i] !== p[len]) len = next[len - 1];
    if (p[i] === p[len]) len++;
    next[i] = len;
  }
  return next;
}
```

完整查找见 [40-coding-handwritten.md H10](./40-coding-handwritten.md)。

**口述模板（30–60 秒）**

1. 一句话结论：KMP 通过预处理模式串，让失配时文本指针不回退。
2. 关键机制：next 数组记录每个前缀的最长相等前后缀长度。
3. 对比或注意点：失配时模式指针跳到 next[j-1]，复用已经匹配的部分。
4. 可追问时补充：时间 O(n + m)，暴力是 O(nm)。

**常见追问**

- JS 的 `indexOf` 用的是 KMP 吗？→ 引擎有自己的实现（如 Boyer-Moore-Horspool 等启发式算法），实际中通常更快；KMP 的价值在于最坏情况的保证。

### Q9. 正则表达式的回溯和 ReDoS 是什么？

- **难度**: 高级
- **标签**: 正则, 安全

**答案**

JS 的正则引擎是**回溯型**（NFA 回溯）：匹配失败时回退尝试其他分支。

**灾难性回溯**：嵌套量词或有重叠的分支，例如 `/^(a+)+$/` 匹配 `"aaaaaaaaaaaaaaaaaaaaaaaa!"` → 尝试的拆分方式呈**指数级**增长，CPU 卡死。

**ReDoS**：攻击者构造输入让服务端（Node.js）的正则卡死，阻塞事件循环。

**防护**：

- 避免嵌套量词 `(a+)+`、`(a|a)*`、`(.*)*`
- 限制输入长度
- 使用静态检查工具（eslint-plugin-regexp、safe-regex）
- 需要线性时间保证时使用 RE2 等非回溯引擎

**口述模板（30–60 秒）**

1. 一句话结论：JS 的正则是回溯型引擎，嵌套量词可能导致指数级的回溯。
2. 关键机制：匹配失败时引擎会尝试所有可能的拆分方式。
3. 对比或注意点：在 Node.js 服务端会阻塞事件循环，形成 ReDoS。
4. 可追问时补充：避免嵌套量词、限制输入长度、用 RE2 等线性引擎。

**常见追问**

- 怎么改写 `/^(\w+\s?)*$/`？→ 去掉重叠：`/^\w+(\s\w+)*\s?$/`，每个字符只有一种匹配方式。

### Q10. 布隆过滤器是什么？前端有什么用？

- **难度**: 高级
- **标签**: 布隆过滤器

**答案**

用 **m 位的位数组 + k 个哈希函数**判断元素「**可能存在**」或「**一定不存在**」：

- 添加：k 个哈希值对应的位设为 1
- 查询：k 个位都是 1 → 可能存在（有误判）；有一个为 0 → 一定不存在
- 不支持删除（计数布隆过滤器可以）
- 空间极小：1% 误判率约需每个元素 10 位

**应用**：

- Feed 流去重（已看过的内容）、推荐去重
- 缓存穿透防护（不存在的键直接拒绝）
- 浏览器的恶意网址检测（早期 Chrome 的安全浏览本地过滤）
- 爬虫 URL 去重

**口述模板（30–60 秒）**

1. 一句话结论：布隆过滤器用位数组和多个哈希函数判断元素是否可能存在。
2. 关键机制：所有位都是 1 才可能存在，有一个为 0 就一定不存在。
3. 对比或注意点：有误判但没有漏判，不支持删除。
4. 可追问时补充：空间非常小，常用于去重和缓存穿透防护。

**常见追问**

- 误判率和什么有关？→ 位数组大小 m、元素数量 n、哈希函数个数 k；最优 k ≈ (m/n) · ln 2。

### Q11. 跳表是什么？为什么 Redis 用跳表？

- **难度**: 高级
- **标签**: 跳表

**答案**

**跳表**：在有序链表上建立多层「索引」，每个节点以一定概率（如 1/2）出现在上一层。查找从最高层开始，向右走到不能再走时下降一层。

| 操作 | 平均复杂度 |
|------|-----------|
| 查找 / 插入 / 删除 | O(log n) |
| 范围查询 | O(log n + k) |

**Redis 的有序集合（ZSet）用跳表而不是平衡树**：

- 实现简单（没有旋转），代码易维护
- **范围查询**方便（底层是链表，找到起点后顺序遍历）
- 并发场景下更容易做到局部修改

**口述模板（30–60 秒）**

1. 一句话结论：跳表是在有序链表上建立多层随机索引，平均 O(log n)。
2. 关键机制：查找从最高层开始，不能前进时下降一层。
3. 对比或注意点：相比平衡树实现更简单，范围查询更方便。
4. 可追问时补充：Redis 的有序集合就是用跳表实现的。

**常见追问**

- 为什么用随机层数？→ 不需要像平衡树那样维护严格的平衡，期望上每层节点数减半，保证 O(log n)。

### Q12. 为什么数据库索引用 B+ 树而不是红黑树？

- **难度**: 高级
- **标签**: B+ 树, 红黑树

**答案**

| | 红黑树 | B+ 树 |
|--|--------|-------|
| 分支数 | 2 | 几百（一个节点一个磁盘页） |
| 树高（百万数据） | 约 20 | 3–4 |
| 适用 | **内存**中的有序结构（Java TreeMap、Linux 调度器） | **磁盘**索引 |
| 范围查询 | 中序遍历 | 叶子节点链表顺序扫描 |

**原因**：磁盘 IO 远慢于内存访问，B+ 树一个节点存很多键，**树高低 → IO 次数少**；数据都在叶子节点，叶子节点之间有链表，范围查询高效。

**前端关联**：IndexedDB 的底层实现（如 Chrome 使用 LevelDB，基于 LSM 树）、对有序数据的查询。

**口述模板（30–60 秒）**

1. 一句话结论：B+ 树为磁盘设计，分支多、树矮，减少 IO 次数。
2. 关键机制：一个节点对应一个磁盘页，存几百个键。
3. 对比或注意点：红黑树适合内存中的有序结构。
4. 可追问时补充：B+ 树的数据在叶子节点，叶子之间有链表，范围查询高效。

**常见追问**

- 红黑树和 AVL 树的区别？→ AVL 严格平衡，查找略快但插入删除旋转多；红黑树近似平衡，插入删除更快，工程中更常用。

### Q13. LFU 缓存怎么实现 O(1)？

- **难度**: 高级
- **标签**: LFU, 设计

**答案**

**LFU**：淘汰**访问次数最少**的；次数相同时淘汰最久未使用的。

**结构**：

- `keyMap`：key → { value, freq }
- `freqMap`：freq → 该频率下的 key 集合（**有序**，按最近使用的顺序；JS 中可以用 Map / Set 的插入顺序）
- `minFreq`：当前最小频率

**操作**：

- `get`：频率 +1，从旧频率的集合移到新频率的集合；如果旧集合空了且旧频率是 minFreq，minFreq + 1
- `put` 新 key：容量满时从 `freqMap[minFreq]` 中删除最早的 key；新 key 频率为 1，`minFreq = 1`

```ts
class LFUCache {
  private keys = new Map<number, { value: number; freq: number }>();
  private freqs = new Map<number, Set<number>>();
  private minFreq = 0;

  constructor(private capacity: number) {}

  get(key: number): number {
    const node = this.keys.get(key);
    if (!node) return -1;
    this.touch(key, node);
    return node.value;
  }

  put(key: number, value: number): void {
    if (this.capacity <= 0) return;
    const node = this.keys.get(key);
    if (node) {
      node.value = value;
      this.touch(key, node);
      return;
    }
    if (this.keys.size >= this.capacity) {
      const bucket = this.freqs.get(this.minFreq)!;
      const evict = bucket.values().next().value!; // Set 的插入顺序：最早的就是最久未使用的
      bucket.delete(evict);
      this.keys.delete(evict);
    }
    this.keys.set(key, { value, freq: 1 });
    this.bucket(1).add(key);
    this.minFreq = 1;
  }

  private touch(key: number, node: { freq: number }) {
    const old = this.freqs.get(node.freq)!;
    old.delete(key);
    if (old.size === 0 && this.minFreq === node.freq) this.minFreq++;
    node.freq++;
    this.bucket(node.freq).add(key);
  }

  private bucket(freq: number): Set<number> {
    if (!this.freqs.has(freq)) this.freqs.set(freq, new Set());
    return this.freqs.get(freq)!;
  }
}
```

**口述模板（30–60 秒）**

1. 一句话结论：LFU 用两个哈希表和一个最小频率变量实现 O(1)。
2. 关键机制：频率表的每个桶按使用顺序保存 key，淘汰时取最小频率桶中最早的。
3. 对比或注意点：访问时 key 从旧频率桶移到新频率桶，必要时更新最小频率。
4. 可追问时补充：新插入的 key 频率为 1，最小频率重置为 1。

**常见追问**

- LRU 和 LFU 怎么选？→ LRU 适合访问有时间局部性的场景；LFU 适合热点稳定的场景，但对访问模式的变化反应慢（旧的热点难以淘汰）。

### Q14. 区间查询问题：线段树和树状数组

- **难度**: 高级
- **标签**: 线段树, 树状数组

**答案**

**问题**：数组频繁「修改单个元素」和「查询区间和 / 最值」。

| 方法 | 修改 | 查询 |
|------|------|------|
| 普通数组 | O(1) | O(n) |
| 前缀和 | O(n) | O(1) |
| **树状数组（BIT）** | O(log n) | O(log n)（前缀和类） |
| **线段树** | O(log n) | O(log n)（和、最值、区间修改） |

**树状数组**（代码短）：

```ts
class FenwickTree {
  private tree: number[];
  constructor(n: number) {
    this.tree = new Array(n + 1).fill(0);
  }
  /** 下标 i（从 1 开始）加上 delta */
  add(i: number, delta: number) {
    for (; i < this.tree.length; i += i & -i) this.tree[i] += delta;
  }
  /** 前 i 个元素的和 */
  sum(i: number): number {
    let s = 0;
    for (; i > 0; i -= i & -i) s += this.tree[i];
    return s;
  }
}
```

**应用**：逆序对计数、区间统计；前端中较少直接用到，但在虚拟列表中维护不定高度的前缀和（频繁修改某项高度、查询偏移量）时是一种选择。

**口述模板（30–60 秒）**

1. 一句话结论：频繁修改和区间查询的场景用树状数组或线段树，两者都是 O(log n)。
2. 关键机制：树状数组用 i & -i 跳跃，线段树把区间二分存储。
3. 对比或注意点：树状数组代码短，适合前缀和类查询；线段树更通用，支持最值和区间修改。
4. 可追问时补充：虚拟列表维护不定高度的偏移量时可以用树状数组。

**常见追问**

- 虚拟列表用树状数组和用「脏标记 + 前缀和惰性重算」怎么选？→ 高度修改分散且频繁时树状数组更稳定；修改集中在可视区域附近时惰性重算更简单。

### Q16. 一致性哈希是什么？

- **难度**: 高级
- **标签**: 哈希, 分布式

**答案**

**问题**：用 `hash(key) % N` 分配到 N 台服务器，增减服务器时几乎所有 key 都要重新分配（缓存大面积失效）。

**一致性哈希**：

- 把哈希值空间组织成一个**环**（0 ~ 2³²-1）
- 服务器和 key 都映射到环上；key 顺时针找到的第一台服务器负责它
- 增减一台服务器只影响环上相邻的一段 key（约 1/N）
- **虚拟节点**：每台服务器映射多个点，解决分布不均

**前端关联**：CDN 节点选择、灰度分桶（需要稳定性）、SSR 服务的缓存分片。

**口述模板（30–60 秒）**

1. 一句话结论：一致性哈希让服务器增减时只有少量 key 需要重新分配。
2. 关键机制：服务器和 key 都映射到哈希环上，key 顺时针找到第一台服务器。
3. 对比或注意点：取模方式在服务器数量变化时几乎所有 key 都会迁移。
4. 可追问时补充：用虚拟节点解决负载不均衡。

**常见追问**

- 查找「顺时针第一个节点」怎么做？→ 节点位置排序后二分查找，O(log n)。

### Q17. 常见的限流算法有哪些？

- **难度**: 高级
- **标签**: 限流

**答案**

| 算法 | 原理 | 特点 |
|------|------|------|
| 固定窗口 | 每个时间窗口计数 | 简单；窗口边界可能出现 2 倍突发 |
| **滑动窗口** | 记录时间戳或细分子窗口 | 平滑；内存较多 |
| **令牌桶** | 以固定速率放令牌，请求取令牌 | **允许一定突发**（桶容量） |
| 漏桶 | 请求进入队列，以固定速率流出 | 输出平滑，不允许突发 |

**前端应用**：

- 接口请求的客户端限流（防止重复提交、批量请求控制）
- 埋点上报的速率控制
- 与防抖 / 节流的关系：节流类似固定速率，防抖是「静默一段时间后执行」

**令牌桶（惰性补充）**：

```ts
class TokenBucket {
  private tokens: number;
  private last = Date.now();
  constructor(private capacity: number, private ratePerSec: number) {
    this.tokens = capacity;
  }
  tryTake(): boolean {
    const now = Date.now();
    // 不用定时器，在取令牌时根据经过的时间补充
    this.tokens = Math.min(this.capacity, this.tokens + ((now - this.last) / 1000) * this.ratePerSec);
    this.last = now;
    if (this.tokens < 1) return false;
    this.tokens -= 1;
    return true;
  }
}
```

**口述模板（30–60 秒）**

1. 一句话结论：常见限流算法有固定窗口、滑动窗口、令牌桶和漏桶。
2. 关键机制：令牌桶以固定速率补充令牌，允许桶容量范围内的突发。
3. 对比或注意点：固定窗口在边界处可能出现两倍的突发。
4. 可追问时补充：令牌可以在取用时根据时间惰性补充，不需要定时器。

**常见追问**

- 分布式限流怎么做？→ 计数放在 Redis（Lua 脚本保证原子性）；或网关层统一限流。

### Q18. 协同编辑中的 OT 和 CRDT 是什么？

- **难度**: 高级
- **标签**: OT, CRDT, 协同

**答案**

**问题**：多人同时编辑同一文档，操作并发到达，如何保证所有人最终看到相同的结果？

**OT（操作转换，Operational Transformation）**：

- 并发操作到达时，根据对方的操作**转换**自己的操作（例如对方在前面插入了 3 个字符，我的插入位置 +3）
- 通常需要**中心服务器**确定操作顺序
- 代表：Google Docs（早期）、ShareDB

**CRDT（无冲突复制数据类型）**：

- 数据结构本身设计成**任意顺序合并结果都一致**（满足交换律、结合律、幂等）
- 文本 CRDT 给每个字符分配**全局唯一且可排序的 ID**（如 Lamport 时间戳 + 客户端 ID），插入位置用「在某个 ID 之后」表示
- 支持**去中心化 / 离线**编辑
- 代表：Yjs、Automerge

| | OT | CRDT |
|--|-----|------|
| 服务器 | 通常需要中心 | 可以去中心化 |
| 离线 | 较难 | 天然支持 |
| 复杂度 | 转换函数复杂 | 数据结构复杂、元数据开销 |

**口述模板（30–60 秒）**

1. 一句话结论：OT 通过转换并发操作保证一致，CRDT 通过数据结构本身保证合并一致。
2. 关键机制：OT 根据对方的操作调整自己的操作位置；CRDT 给每个字符唯一的可排序 ID。
3. 对比或注意点：OT 通常需要中心服务器，CRDT 天然支持离线和去中心化。
4. 可追问时补充：前端常用的 Yjs 就是基于 CRDT 的。

**常见追问**

- CRDT 的删除怎么处理？→ 通常是「墓碑」（标记删除而不是真正删除），之后通过垃圾回收清理，否则元数据会持续增长。

### Q19. 大文件上传中的哈希和分片用到了哪些算法？

- **难度**: 高级
- **标签**: 哈希, 前端

**答案**

- **分片**：按固定大小切分（`file.slice`），并发上传（并发控制）
- **文件哈希**（秒传和断点续传的依据）：
  - 增量计算：spark-md5 逐片 `append`，避免一次读入内存
  - 放到 **Web Worker** 中计算，不阻塞主线程

- **断点续传**：服务端返回已上传的分片列表，客户端跳过
- **完整性**：每个分片带哈希，服务端校验后再合并

**口述模板（30–60 秒）**

1. 一句话结论：大文件上传用分片加文件哈希实现秒传和断点续传。
2. 关键机制：哈希在 Web Worker 中增量计算，不阻塞主线程。
3. 对比或注意点：抽样哈希速度快但可能冲突，要配合服务端校验。
4. 可追问时补充：分片并发上传时要控制并发数。

**常见追问**

- 为什么不用 SHA-256 而用 MD5？→ 这里只是用于去重和完整性校验，不是安全用途，MD5 更快；需要防篡改时用 SHA-256（Web Crypto API）。

### Q20. 扁平数组转树为什么能做到 O(n)？

- **难度**: 高级
- **标签**: 树, 哈希表

**答案**

**朴素方法**：对每个节点遍历数组找子节点 → O(n²)。

**O(n) 方法**：一次遍历，用 Map 记录 id → 节点；遇到父节点还没出现时**先创建占位**，之后再补充数据。

```ts
interface Item { id: number; parentId: number | null; name: string }
interface Node extends Item { children: Node[] }

function arrayToTree(items: Item[]): Node[] {
  const map = new Map<number, Node>();
  const roots: Node[] = [];
  for (const item of items) {
    // 子节点可能先于父节点出现，先用占位对象，之后合并数据
    const node = Object.assign(map.get(item.id) ?? { children: [] }, item) as Node;
    map.set(item.id, node);
    if (item.parentId === null) {
      roots.push(node);
    } else {
      if (!map.has(item.parentId)) map.set(item.parentId, { children: [] } as unknown as Node);
      map.get(item.parentId)!.children.push(node);
    }
  }
  return roots;
}
```

**口述模板（30–60 秒）**

1. 一句话结论：用 Map 记录 id 到节点的映射，一次遍历完成。
2. 关键机制：子节点出现时直接挂到父节点的 children 上。
3. 对比或注意点：父节点还没出现时先创建占位，之后合并数据。
4. 可追问时补充：要考虑父节点不存在（孤儿节点）和循环引用的数据异常。

**常见追问**

- 树转回扁平数组？→ DFS 或 BFS 遍历，记录 parentId；深度很大时用迭代。

### Q21. 随机算法：洗牌和蓄水池抽样

- **难度**: 高级
- **标签**: 随机

**答案**

**Fisher-Yates 洗牌**：从后往前，每个位置与「它及之前」的随机位置交换。每种排列概率相等，O(n)。

```ts
function shuffle<T>(arr: T[]): T[] {
  for (let i = arr.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
  return arr;
}
```

**错误做法**：`arr.sort(() => Math.random() - 0.5)` → 分布不均匀（排序算法对不一致的比较结果没有保证）。

**蓄水池抽样**：从**长度未知的数据流**中等概率抽取 k 个：前 k 个直接放入；第 i 个（从 1 开始）以 k/i 的概率替换池中随机一个。

**口述模板（30–60 秒）**

1. 一句话结论：洗牌用 Fisher-Yates，数据流抽样用蓄水池抽样。
2. 关键机制：Fisher-Yates 每个位置与它及之前的随机位置交换。
3. 对比或注意点：用 sort 加随机比较的洗牌分布不均匀。
4. 可追问时补充：蓄水池抽样中第 i 个元素以 k/i 的概率被选中，最终每个元素概率相同。

**常见追问**

- `Math.random` 能用于安全场景吗？→ 不能，用 `crypto.getRandomValues`。

### Q22. 实际代码中，复杂度之外还要考虑什么？

- **难度**: 高级
- **标签**: 性能, 工程

**答案**

- **常数因子**：O(n) 的两次遍历可能比 O(n log n) 的一次排序慢，要实测
- **数据规模**：n 很小时简单的 O(n²) 可能更快（插入排序在小数组中比快排快，TimSort 就利用了这一点）
- **内存访问模式**：数组连续访问对缓存友好；链表和对象图的随机访问慢
- **JS 引擎优化**：
  - 数组元素类型保持一致（SMI → Double → 通用元素，降级不可逆）
  - 避免稀疏数组和 `delete` 数组元素
  - 对象形状（Hidden Class）稳定，热点函数保持单态
  - 预分配数组 vs 动态 `push`（差异通常不大）
- **分配和 GC**：循环中创建大量临时对象 / 数组（`slice`、展开运算符）会增加 GC 压力
- **主线程**：长任务分片（时间切片）或放到 Worker

**口述模板（30–60 秒）**

1. 一句话结论：复杂度之外还要考虑常数因子、数据规模、内存访问和引擎优化。
2. 关键机制：小规模数据下简单算法可能更快，例如 TimSort 对小片段用插入排序。
3. 对比或注意点：数组元素类型要保持一致，避免引擎降级优化。
4. 可追问时补充：前端还要考虑主线程阻塞，长任务分片或放到 Worker。

**常见追问**

- 怎么确认优化有效？→ 用真实数据规模做基准测试（多次运行取中位数），Performance 面板查看。

- 滚动数组时为什么 0-1 背包要倒序？→ 正序会让 `dp[j - w]` 已经是本轮更新过的值，相当于同一物品用了多次。

### Q24. 编辑器 / IDE 的功能中用到了哪些算法？

- **难度**: 高级
- **标签**: 应用

**答案**

| 功能 | 算法 / 数据结构 |
|------|----------------|
| 文本存储 | **Piece Table**（VS Code）：原始文本 + 追加缓冲区 + 片段表，插入删除不复制大文本；Rope（平衡树存字符串片段） |
| 行号定位 | 平衡树中维护每个片段的换行数 |
| 文件 diff | **Myers diff 算法**（最短编辑脚本，O(ND)） |
| 模糊搜索（Cmd+P） | 子序列匹配 + 打分（连续匹配、单词边界加分） |
| 自动补全 | Trie、前缀匹配 + 排序 |
| 括号匹配 | 栈 |
| 语法高亮 | 增量解析（Tree-sitter）、TextMate 语法（正则状态机） |
| 撤销 / 重做 | 两个栈；协同时用 OT / CRDT |

**口述模板（30–60 秒）**

1. 一句话结论：编辑器在文本存储、diff、搜索、补全中大量使用算法。
2. 关键机制：VS Code 用 Piece Table 存储文本，插入删除不需要复制大字符串。
3. 对比或注意点：文件 diff 用 Myers 算法求最短编辑脚本。
4. 可追问时补充：模糊搜索是子序列匹配加打分排序。

**常见追问**

- 模糊搜索的打分怎么设计？→ 连续匹配、匹配在单词开头或驼峰边界、匹配位置靠前加分；间隔越大扣分越多。

### Q25. 面试中遇到没见过的算法题，怎么应对？

- **难度**: 高级
- **标签**: 方法

**答案**

1. **澄清和举例**：确认输入输出、数据范围（决定目标复杂度）、边界情况
2. **从暴力解开始**：说出暴力解和复杂度，确认理解正确
3. **找瓶颈，匹配模式**：
   - 重复查找 → 哈希表
   - 有序 / 单调 → 二分、双指针
   - 连续子数组 → 滑动窗口、前缀和
   - 下一个更大 → 单调栈
   - 最值 + 动态插入 → 堆
   - 所有方案 → 回溯
   - 最优解 + 子问题重叠 → DP
   - 依赖关系 → 拓扑排序
   - 连通性 → 并查集 / DFS
4. **从小例子找规律**
5. **说出思路后再写**：得到面试官认可后再编码
6. **写完用例子走一遍**，检查边界

**口述模板（30–60 秒）**

1. 一句话结论：先澄清和举例，从暴力解开始，再找瓶颈匹配常见的模式。
2. 关键机制：根据数据范围反推目标复杂度。
3. 对比或注意点：思路得到认可后再写代码。
4. 可追问时补充：写完一定用例子走一遍并检查边界。

**常见追问**

- 面试官给了提示还是想不出来？→ 把思考过程说出来，写出能写的部分（暴力解），比沉默好。

### Q26. 前端工程师学算法的意义和重点是什么？

- **难度**: 高级
- **标签**: 方法

**答案**

**意义**：

- 理解框架原理（diff、调度、响应式依赖图）
- 解决实际性能问题（大数据量的列表、树、搜索、可视化）
- 工具开发（编译器、构建工具的依赖图、Monorepo 任务调度）
- 面试门槛

**重点**（按投入产出排序）：

1. 数组、字符串、哈希表、双指针、滑动窗口（最高频）
2. 二叉树递归、BFS / DFS
3. 栈 / 单调栈、堆
4. 回溯、基础 DP
5. 前端特色题：LRU、扁平转树、LIS、并发控制、版本号比较
6. 图（拓扑排序）、Trie、并查集

**口述模板（30–60 秒）**

1. 一句话结论：算法帮助前端理解框架原理和解决实际的性能问题。
2. 关键机制：框架中的 diff、调度、响应式都依赖算法。
3. 对比或注意点：学习时按频率和投入产出排序，先掌握高频题型。
4. 可追问时补充：前端特色题（LRU、扁平转树、LIS）要重点准备。

**常见追问**

- 工作中真的会用到吗？→ 直接写经典算法的机会不多，但「选择合适的数据结构」「识别 O(n²) 的瓶颈」每天都在用。
