# CSS 系统设计 / 场景题

## 通用答题框架

1. 澄清目标：业务类型、设备范围、品牌要求、性能指标
2. 约束：浏览器矩阵、团队规模、技术栈、SSR、可访问性要求
3. 方案：令牌、分层、组件边界、构建与产物
4. 关键路径：首屏样式、主题切换、响应式断点、动效
5. 风险与演进：兼容回退、视觉回归、性能监控

---

### S1. 设计企业级多品牌主题系统

- **难度**: senior
- **标签**: Design Tokens, 主题
- **来源倾向**: 中后台 / SaaS 平台常见

**澄清问题**

- 品牌数量？是否运行时切换？
- 是否需要暗色模式、高对比模式？
- 组件库是自研还是基于开源二次封装？

**参考方案**

```
Design Tokens（JSON / Figma 同步）
  ├─ primitive：色板、字号刻度、间距刻度
  ├─ semantic：surface / text / border / brand / danger
  └─ component：button-bg / input-border
构建：Style Dictionary 生成 CSS 变量 + TS 类型
运行时：<html data-brand="a" data-theme="dark">
组件：只消费 semantic / component token
```

**关键设计**

- 主题切换只修改变量映射，不重新加载组件 CSS
- 首屏通过 SSR / cookie 写入 `data-theme`，避免闪烁
- 对比度自动检查纳入 CI
- 提供 `@layer` 层级，业务覆盖有规范

**口述模板（2–3 分钟）**

1. 令牌三层：基础、语义、组件。
2. 多品牌 = 同一语义令牌映射到不同基础色板。
3. 组件禁止硬编码颜色。
4. 首屏主题无闪烁，SSR 输出主题属性。
5. 用视觉回归和对比度检查防回归。

**扩展追问**

- 品牌色接近导致对比度不足？→ 令牌层生成派生色时校验 WCAG 对比度。

### S2. 设计组件库的 CSS 架构

- **难度**: senior
- **标签**: 组件库, 架构
- **来源倾向**: 基础架构 / 设计系统岗位

**澄清问题**

- 使用者是 React、Vue 还是多框架？
- 是否要求按需加载样式？
- 是否支持 SSR、微前端？

**参考方案**

```
@layer reset, tokens, base, components, utilities, overrides;

tokens.css     → CSS 变量
base.css       → 排版、焦点样式
components/    → 每组件独立样式（Modules / 原生 CSS）
utilities.css  → 少量工具类
```

**关键设计**

- 默认样式低特异性（单类名或 `:where()`）
- 对外暴露 CSS 变量和 `className`，复杂组件可暴露 `::part`
- 弹层组件统一挂载点与 z-index 令牌
- 按组件拆分 CSS，支持 tree-shaking
- 视觉回归测试覆盖主要状态

**口述模板（2–3 分钟）**

1. 目标是隔离、可覆盖、可按需加载。
2. 用 @layer 明确样式优先级。
3. 组件靠令牌和扩展点定制，而不是让用户覆盖内部选择器。
4. 弹层和 z-index 统一治理。
5. 发布时考虑 breaking change 与迁移指南。

**扩展追问**

- 用户深度覆盖内部类名怎么办？→ 文档声明非公开 API，升级不保证兼容。

### S3. 移动端 H5 适配方案设计

- **难度**: mid
- **标签**: 移动端, 响应式
- **来源倾向**: 电商 / 活动页高频

**澄清问题**

- 设计稿尺寸？是否有平板与 PC？
- 是否在 App WebView 中运行？
- 是否有刘海屏、横屏需求？

**参考方案**

```
viewport meta（width=device-width）
流体排版：clamp() + rem
布局：Flex / Grid
断点：基于内容（如 360 / 768 / 1024）
安全区：env(safe-area-inset-*)
高度：dvh / svh
细线：hairline 工具类
```

**关键设计**

- 优先响应式，不推荐整页缩放
- 组件级适配用容器查询
- 点击区域不小于 44×44 CSS 像素
- 横屏和键盘弹出时测试固定定位

**口述模板（2–3 分钟）**

1. 现代方案以响应式和流体单位为主。
2. 处理安全区、动态视口和 1px 细线。
3. 断点根据内容，不按机型穷举。
4. WebView 要测试键盘和底部固定栏。
5. 用真机矩阵验证。

**扩展追问**

- 为什么不再推荐 lib-flexible？→ 依赖 JS 改根字号，现代可用 vw、clamp 和容器查询替代。

### S4. 大型应用的 CLS 与首屏样式治理

- **难度**: senior
- **标签**: 性能, CLS
- **来源倾向**: 性能优化专项

**澄清问题**

- CLS 主要发生在哪些页面和元素？
- 是否有广告、推荐流、动态 Banner？
- 是否 SSR？

**参考方案**

```
监控：RUM 采集 CLS + 归因元素
图片：width/height + aspect-ratio
动态区块：min-height 占位
字体：preload 关键字体 + size-adjust
样式：关键 CSS 内联，非关键异步
动画：仅 transform / opacity
CI：Lighthouse 预算 + 视觉回归
```

**口述模板（2–3 分钟）**

1. 先用 RUM 找到真实 CLS 来源。
2. 图片、广告、字体、动态内容分别治理。
3. 为异步内容预留空间。
4. 关键 CSS 降低首屏阻塞。
5. 在 CI 设置性能预算防回归。

**扩展追问**

- 推荐流必须动态插入怎么办？→ 在下方插入或预留固定高度槽位，避免推动当前阅读内容。

### S5. 微前端环境下的样式隔离与共享

- **难度**: senior
- **标签**: 微前端, 隔离
- **来源倾向**: 大型平台架构

**澄清问题**

- 子应用是否同一设计系统？
- 是否允许不同版本组件库并存？
- 是否使用 Shadow DOM 或 iframe？

**参考方案**

```
基座
  ├─ 全局 reset + design tokens
  ├─ 字体、主题、z-index 规范
  └─ 弹层挂载容器
子应用
  ├─ CSS Modules / scoped
  ├─ 禁止修改 html/body 全局样式
  └─ 卸载时清理动态 style
```

**关键设计**

- 设计令牌由基座统一提供，子应用消费变量
- 强隔离场景使用 Shadow DOM，但处理好字体和弹层
- 组件库版本冲突时考虑命名前缀或 Shadow 隔离

**口述模板（2–3 分钟）**

1. 共享令牌，隔离实现。
2. 子应用不能污染全局。
3. 弹层统一挂到基座容器。
4. 隔离强度按冲突风险选择。
5. 监控样式泄漏与重复加载。

**扩展追问**

- Shadow DOM 中如何用全局主题？→ CSS 变量可穿透 Shadow 边界。

### S6. 数据可视化 / 大表格页面的样式性能

- **难度**: senior
- **标签**: 性能, 表格
- **来源倾向**: B 端复杂页面

**澄清问题**

- 行数和列数规模？是否需要固定列和表头？
- 是否频繁更新单元格？

**参考方案**

```
虚拟滚动（行 + 列）
固定表头：position: sticky
固定列：sticky + 层级令牌
单元格：简单选择器、避免复杂阴影
离屏区块：content-visibility（非虚拟化场景）
数字列：tabular-nums
```

**口述模板（2–3 分钟）**

1. 大表格核心是减少 DOM 和渲染成本。
2. sticky 实现固定表头和固定列。
3. 单元格样式简单化，避免昂贵效果。
4. 频繁更新只改必要属性。
5. 用 Performance 验证滚动帧率。

**扩展追问**

- sticky 固定列阴影怎么做？→ 用伪元素渐变阴影，不在每个单元格加 box-shadow。

### S7. 动效系统设计

- **难度**: mid
- **标签**: 动画, 设计系统
- **来源倾向**: C 端产品体验

**澄清问题**

- 动效用于反馈、引导还是品牌表达？
- 是否需要支持减少动效？
- 是否有页面切换动画需求？

**参考方案**

```
动效令牌：
  --duration-fast: 120ms
  --duration-base: 200ms
  --easing-standard: cubic-bezier(.2, 0, 0, 1)
组件动效：hover、展开、Toast、Modal
页面过渡：View Transitions（渐进增强）
滚动动效：scroll-driven animations（渐进增强）
无障碍：prefers-reduced-motion 降级
```

**口述模板（2–3 分钟）**

1. 动效是交互语言，需要令牌统一。
2. 优先 transform / opacity。
3. 新能力渐进增强。
4. 尊重减少动效偏好。
5. 用帧率和用户反馈验证。

**扩展追问**

- 为什么要统一 easing？→ 保持产品动效风格一致，降低设计和实现成本。

### S8. 从 Sass + BEM 迁移到现代 CSS 的方案

- **难度**: senior
- **标签**: 迁移, 工程化
- **来源倾向**: 老项目治理

**澄清问题**

- 代码量和团队规模？
- 浏览器支持范围？
- 是否允许运行时 CSS-in-JS？

**参考方案（渐进迁移）**

```
阶段 1：引入 CSS 变量替代 Sass 颜色变量
阶段 2：引入 @layer，整理 reset / vendor / components
阶段 3：新组件使用 CSS Modules 或原生 Nesting
阶段 4：用容器查询替代部分 JS 尺寸判断
阶段 5：清理死代码，建立 Stylelint 规范
```

**口述模板（2–3 分钟）**

1. 不做一次性重写，按收益分阶段迁移。
2. 先变量和层级，因为影响最大。
3. 新代码用新规范，旧代码按模块迁移。
4. 用 Stylelint 和视觉回归保证质量。
5. 迁移指标包括包体积、覆盖冲突数量和开发效率。

**扩展追问**

- Sass 还需要保留吗？→ 若仍依赖 mixin、函数和复杂循环，可以保留；只为嵌套和变量则可逐步移除。
